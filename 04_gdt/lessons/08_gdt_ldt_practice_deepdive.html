01 — Quick Recap

Why the LDT Existed At All

You already know the shape of this from the GDT article: TI=0 in a selector means "look in the shared catalog," TI=1 means "look in my own private supplement." What's worth dwelling on is why any process would ever want a private supplement in the first place.

Picture a real 16-bit DOS or Windows 3.x program from the late 1980s. It wasn't written against a single flat 4GB address space the way a modern Linux binary is — it was written assuming it could carve out and juggle many small segments of its own: one for its code, several for different chunks of data, maybe one per open document, one per loaded resource. Each segment topped out at 64KB, so a real application routinely needed dozens of them, defined and redefined constantly as it ran.

A modern kernel isn't going to manage that for you. Linux's GDT, as the previous article showed, hands every process exactly the same small, boring, flat set of code/data descriptors and calls it done — one shared catalog, same entries for everyone. That's fine for a program that thinks in flat pointers. It's useless for a program that thinks in dozens of tiny segments it wants to allocate and free at will. The LDT is the escape hatch: a table a process gets to define for itself, without the kernel needing to babysit every allocation in the one shared, systemwide table.

💡 The One-Sentence Version
The GDT is the catalog the kernel curates for everyone. The LDT is a scratch catalog a process gets to fill in itself — and almost nothing running today wants that, except software whose entire job is pretending to be something written decades ago.

Made concrete, a real Windows 3.x-era program's segment table might have looked something like this — a fistful of small, independently sized, independently movable segments, nothing like the one giant flat address space a modern binary assumes:

SegmentHoldsTypical size
CS (code)The program's executable instructionsup to 64KB
DS (main data)Global variables, window handles, small buffersa few KB – 64KB
Dialog resource segmentOne loaded dialog box templatea few hundred bytes – a few KB
Document/buffer segmentOne open document's editable contentsup to 64KB, one per open document
Bitmap/resource segmentOne loaded icon, bitmap, or string tablevaries, often small

That's easily a dozen-plus segments for a modest application, each one independently allocatable and freeable — the LDT is simply where all of those extra, private, program-specific entries had to live, since the shared GDT was never meant to track one specific program's ever-changing document count.

A Brief Timeline, For Grounding

  1. 1978 — Intel 8086Real mode only, no protection, no descriptor tables — but segmentation as a concept (segment × 16 + offset) is already here.
  2. 1982 — Intel 80286Protected mode arrives, and with it the GDT and LDT exactly as this series describes them — the hardware this whole chapter is about is over four decades old.
  3. 1990 — Windows 3.0 "standard mode"Runs Win16 applications in genuine 16-bit protected mode, leaning hard on the LDT for every program's private segment set — the target this chapter's Wine section reproduces.
  4. 1995 — Windows 95 / growing 32-bit dominanceMainstream software increasingly adopts flat 32-bit addressing; heavy LDT usage becomes the exception, not the rule, even before 64-bit CPUs exist.
  5. 2003 — AMD64 / x86-64 and long modeLong mode arrives and, as Section 07 covers, effectively finishes the job — flat 64-bit addressing becomes the only mode genuinely new software targets.

That "except" from the callout above is the whole subject of this chapter. It's not a hypothetical corner case in a spec document — it's live code, in real, still-maintained software, that people run today.

02 — The Doorway From User-Space

The Syscall: modify_ldt()

Loading gdtr is a privileged instruction — ordinary programs can't touch it, full stop. But a process's own LDT is a different story: it's the one piece of segmentation the kernel is willing to let user-space partially control, because by definition it can only affect that process itself. On Linux, the doorway is a genuinely real, documented syscall: modify_ldt().

// from <asm/ldt.h> and the modify_ldt(2) man page int modify_ldt(int func, void *ptr, unsigned long bytecount); // func == 0 read the calling process's current LDT entries // func == 1 write one 16-bit-only-capable LDT entry (legacy form) // func == 0x11 write one LDT entry, in a form that also allows // 32-bit segments — this is the form real emulators use // // note: func == 0 (the read side) isn't just for symmetry — a debugger // attached to a Wine process via ptrace() can call it too, to learn // what a traced program's own segment registers actually point at // before trying to interpret a "segment-relative" memory watch. struct user_desc { unsigned int entry_number; // which LDT slot to fill unsigned int base_addr; // the segment's Base unsigned int limit; // the segment's Limit unsigned int seg_32bit:1; unsigned int contents:2; unsigned int read_exec_only:1; unsigned int limit_in_pages:1; unsigned int seg_not_present:1; unsigned int useable:1; };

Read that struct closely and it's the same handful of fields from the Segment Descriptor in the GDT article — base, limit, a 32-bit-vs-16-bit flag, a present bit — just repackaged as something a user-mode process is allowed to hand to the kernel. Call modify_ldt(0x11, &desc, sizeof(desc)) and the kernel writes a real Segment Descriptor into your process's private LDT, in RAM it controls, on your behalf. From that point on, a selector with TI=1 and the right index genuinely resolves through your custom descriptor — the actual segmentation hardware does the base+offset arithmetic, exactly as described back in the GDT lookup formula, just rooted in ldtr instead of gdtr.

The LDT lookup formula — same shape as the GDT's Descriptor Address = ldtr.base + (selector.index × 8) Identical arithmetic to the GDT article's formula. The only thing that changed is which register — and which table — supplies the base.
🛡️ The Kernel Doesn't Trust You Blindly
Letting user-space write directly into a table the CPU's segmentation hardware trusts sounds dangerous, and the kernel treats it that way: modify_ldt()'s implementation validates every entry before installing it — rejecting attempts to mark a descriptor as a system-segment type (which could otherwise be abused to fabricate something like a call gate), and constraining what privilege level and type bits a plain user process is allowed to set. The syscall gives you a private table to fill in, not a blank check to forge arbitrary hardware trust.

One easy mix-up worth heading off: modify_ldt() is not how ordinary thread-local storage works on Linux, even on 32-bit x86. That job historically belonged to a sibling syscall, set_thread_area() — and tellingly, it manages a small reserved range of entries in the GDT, not the LDT, precisely because TLS is common enough that Linux gave it a lightweight, shared-table-friendly mechanism instead of routing every thread through a private per-process table.

🧵 set_thread_area() — the common case

Installs one small TLS segment per thread into a reserved slice of the GDT. This is what glibc actually uses for ordinary thread-local variables on 32-bit x86 — mundane, frequent, and nothing to do with emulating old software.

📔 modify_ldt() — the rare case

Installs arbitrary custom segments into a process's private LDT. This is the one reserved for exactly the software this chapter is about — Wine, DOSEMU, and historically NaCl — not for routine thread-local storage.
🤔 Why Does a 2020s Kernel Still Ship This?
Because something still needs it — and it's exactly the kind of software this chapter is about. Nobody writes new 64-bit Linux programs that call modify_ldt(); you won't find it in a typical server or webapp binary. It survives in the kernel's syscall table for one specific reason: certain programs must faithfully reproduce the segmented memory model of software written before flat addressing was the norm, and the only way to reproduce genuine hardware segmentation is to actually use the hardware's segmentation.
It isn't a free lunch. modify_ldt() is a small, rarely exercised corner of the kernel — and rarely exercised code paths are exactly where security bugs like to hide. It's been implicated in real kernel hardening discussions over the years, and some hardened kernel configurations (grsecurity-style builds, and the mainline CONFIG_X86_16BIT option) let you disable 16-bit segment support outright, explicitly trading away Wine/DOS-emulator compatibility for a smaller attack surface. Reviving old hardware features for compatibility isn't free — it's a genuine, ongoing security-vs-compatibility trade-off, not just a historical footnote.

One more detail worth knowing, because it foreshadows this chapter's ending: an LDT installed via modify_ldt() is scoped to the calling process (and is inherited across a plain fork(), then copied-on-write same as the rest of the address space). That's a genuinely different mechanism from how modern 64-bit code gets a private "segment" for thread-local storage. A 64-bit program that wants per-thread storage reachable through %fs or %gs doesn't call modify_ldt() at all — it calls arch_prctl(ARCH_SET_FS, ...), which just pokes a base address straight into a model-specific register, bypassing the descriptor-table machinery entirely. Long mode kept a tiny sliver of segmentation alive (an fs/gs base you can relocate), but even that sliver no longer needs the LDT to work. The two mechanisms coexist in the kernel; almost nothing modern chooses the LDT one.

03 — The Headline User

Wine: Real Hardware Segmentation, On Purpose

Wine — the compatibility layer that lets Windows programs run on Linux and other Unix-like systems — is not a museum piece. It's actively developed, and it underpins huge chunks of the "Windows games running on Linux/Steam Deck" ecosystem. Most of what Wine does today is running ordinary 32-bit and 64-bit Windows executables, which need essentially no segmentation trickery at all — same flat-segments story as native Linux binaries.

But Wine's job has always included a harder case: genuinely old 16-bit Windows applications (Win16, the Windows 3.x-era binary format) and certain DOS-era software. These programs were written assuming real x86 segmentation — far pointers, segment:offset addressing, dozens of small segments swapped in and out. You cannot correctly run that code by just mapping it into a flat address space and hoping; the program's own logic depends on segment boundaries actually behaving like segment boundaries.

This isn't purely academic, either. Wine is the engine underneath Proton, Valve's compatibility layer that lets a huge fraction of the Windows game library run on the Steam Deck and on Linux desktops through Steam. The overwhelming majority of Proton's traffic is ordinary 32-bit and 64-bit titles that never touch the LDT. But the same Wine codebase — LDT-management code included — is what's sitting underneath it, ready for the rarer case of a genuinely old, genuinely segmented title someone still wants to launch. The compatibility problem this chapter is about isn't hypothetical or confined to hobbyist retrocomputing circles; it's shipped, today, inside one of the most widely used pieces of gaming software on Linux.

🍷 What Wine Actually Does About It
Wine's source tree includes dedicated LDT-management code (historically dlls/ntdll/ldt.c, now living under dlls/ntdll/unix/) whose entire job is translating "this Win16 app wants segment N to mean base X, limit Y" into real calls to modify_ldt() on Linux. The result: the actual x86 segmentation unit — the same hardware this whole series has been describing — does real base+offset translation for that guest program's segment registers. Wine isn't faking segmentation in software here; it is re-arming genuine, decades-old CPU hardware and pointing it at a live process.

On other Unix-like hosts that lack Linux's modify_ldt(), Wine falls back to platform equivalents — i386_set_ldt() on the BSDs and older macOS, or sysarch() — because the underlying need is the same everywhere x86 segmentation exists: give this one process its own private, hardware-enforced table of extra segments.

⚙️ A Nuance Worth Knowing: No V86 Mode Required
Most Win16 applications ran under what Windows 3.x called "standard mode" — genuine 16-bit protected mode, not the raw real-mode 8086 emulation DOS programs needed. That distinction matters here: a 32-bit protected-mode CPU can execute 16-bit code natively, governed entirely by the D-bit in the code segment's descriptor (the same default-operand-size flag from the Segment Descriptor field table in the GDT article). So Wine doesn't need to drop the CPU into virtual-8086 mode at all for this case — installing a 16-bit-flagged LDT descriptor via modify_ldt() is sufficient by itself. Contrast that with DOSEMU's real-mode DOS support two sections from now, which genuinely does need vm86() because true DOS real-mode code assumes 8086-style addressing the D-bit trick alone can't reproduce.
A telling nuance: because this really does depend on genuine x86 segment mechanics, Win16 support has generally only been available in 32-bit Wine builds/prefixes — much the way real 64-bit Windows itself dropped the ability to run 16-bit programs. That's not a Wine limitation so much as a hint about where this chapter is headed: 64-bit long mode and rich segmentation don't really coexist.

Watch the Routing Happen

Here's the piece that ties straight back to the TI bit from the GDT article. A Wine process still has the same boring, shared, flat GDT every other Linux process has — plus its own private LDT, freshly populated via modify_ldt(), holding real 16-bit segment descriptors for the Win16 guest program it's hosting. Which table a given lookup uses is decided by exactly one bit in the selector.

▶ Choose which selector to resolve

That third button is worth trying deliberately. If a selector claims TI=1 but the process never actually populated that LDT slot via modify_ldt(), the descriptor the CPU fetches has its present bit clear — and hardware refuses to complete the access. This is the same privilege-and-validity checking machinery from the GDT article's worked example, just guarding a table that happens to usually be empty. It's exactly why a stray or corrupted selector on a typical 64-bit Linux process reliably faults instead of silently reading garbage: there's normally nothing behind door TI=1 at all.

04 — Play By Play

What Actually Happens, Step By Step

It's easy to wave a hand at "Wine calls modify_ldt()" and move on. It's more convincing to walk through what that sequence really looks like the moment a Win16 program is loaded.

  1. The user launches an old .exeWine's loader inspects the binary and recognizes a 16-bit New Executable (NE) header instead of the 32/64-bit PE header modern Windows programs use.
  2. Wine reads the program's segment tableThe NE header itself lists the segments this program was built with — how many, how big, which one is the entry point's code segment — exactly the information a real Windows 3.x loader would have consumed in 1990.
  3. Wine allocates real memory for each segmentFor every listed segment, Wine mmap()s a plain chunk of linear memory to actually hold that segment's bytes — this part is unremarkable, ordinary memory allocation.
  4. Wine calls modify_ldt() per segmentFor each segment, Wine issues modify_ldt(0x11, &desc, sizeof(desc)) with base_addr pointing at that freshly allocated memory and limit set to the segment's real size — often nowhere near 4GB, sometimes just a few KB, precisely reproducing the "many small segments" model from Section 01.
  5. The kernel writes the descriptor and hands back a selectorThe kernel validates the request, writes an 8-byte Segment Descriptor into this process's private LDT, and Wine now has a real selector — index and TI=1 — to load into a segment register for the guest program's thread.
  6. The guest program runs, and the CPU does the restFrom here on, every far pointer dereference the Win16 program performs is a genuine selector:offset access. The segmentation unit — not Wine's own interpreter — enforces the segment's limit and computes the linear address, exactly as described throughout this whole series.
🔁 The Payoff
Notice what Wine didn't have to build: its own software model of segment limits, its own bounds-checking on every memory access, its own translation layer between "segment 4, offset 0x1A2" and a real address. It got all of that for free, at full hardware speed, just by asking the kernel — once, via modify_ldt() — to set up descriptors the CPU already knows how to use.
05 — A Second Approach, and a Bigger Principle

DOSBox, and Segmentation as a Sandbox

Wine isn't the only still-relevant emulator dealing with segmented programs — and it's worth contrasting it with a genuinely different strategy for the same underlying problem. DOSBox (and its actively maintained forks) is a full PC emulator built to run real DOS-era 16-bit software: games, utilities, whole segmented programs, exactly the kind Wine's Win16 support targets from the Windows side.

DOSBox takes a different route to get there than Wine does. Instead of arming the host's real segmentation hardware on the guest program's behalf, DOSBox emulates an entire virtual x86 CPU in software — including its own model of segment registers, its own segment:offset math, its own protection checks — all tracked as ordinary data structures inside the emulator process. The guest DOS program's segments are real to it, but the host CPU never sees them as segments at all; from the host's point of view, DOSBox is just one ordinary flat-addressed process doing arithmetic.

🍷 Wine's approach — real hardware

Calls modify_ldt() so the actual x86 segmentation unit performs genuine base+offset translation for the guest program's segment registers. Faster once set up, but only works on hosts whose CPU and OS actually expose real segmentation — which is exactly why it's tied to 32-bit builds.

📦 DOSBox's approach — software model

Emulates segment registers, limits, and address translation entirely as data inside its own interpreter/recompiler. Slower per-access than real hardware doing it, but fully portable — it runs identically on ARM Macs and other hosts with no x86 segmentation hardware at all.

Between those two poles sits a third real example that actually splits the difference: DOSEMU, a Linux-specific DOS emulator that runs real-mode DOS code inside the kernel's vm86() virtual-8086 mode, then goes a step further for programs that expect DPMI — the DOS Protected Mode Interface many later DOS games and tools relied on to escape real mode's 1MB ceiling. To host a DPMI client faithfully, DOSEMU's DPMI server allocates genuine 32-bit protected-mode segments for it, and — like Wine — does that by calling modify_ldt() to install real descriptors in the emulated process's LDT. It's the same syscall Wine uses, aimed at a different generation of segmented software.

🕹️ DOSEMU vs. DOSBox — Same Goal, Opposite Tactics
Both run old DOS software. DOSEMU leans on the host's real x86 hardware as hard as it can — vm86() for real-mode code, modify_ldt() for protected-mode DPMI segments — which is fast, but ties it to actual x86 Linux hosts. DOSBox leans on none of that, modeling the whole CPU in portable software — slower per access, but it's exactly why DOSBox runs unmodified on ARM laptops and phones that have no x86 segmentation hardware to borrow in the first place.

That contrast points at a bigger, more general idea worth pulling out on its own: a local descriptor table isn't only useful for backward compatibility. The underlying trick — "give this one piece of code its own small, hardware-bounded window into memory, cheaply" — has been reused for security, not just nostalgia.

🔒 The Principle: Segmentation As a Cheap Sandbox
Google's Native Client (NaCl) project — a scheme for safely running untrusted native machine code inside a browser — used exactly this trick on 32-bit x86. Rather than paying for a whole separate process and page-table switch per sandbox, NaCl's x86-32 implementation used modify_ldt()-installed segments to force untrusted, JIT-generated code's memory accesses through a segment with a fixed, restrictive base and limit. The segmentation hardware itself — not a software bounds check that clever generated code might find a way around — refused any access outside the sandbox. Cheap, and enforced by silicon.
The general principle, stripped to its essence One modify_ldt() call = one hardware-enforced memory boundary, for one specific piece of code No new process. No new page tables. No software bounds-check to write, and none for an attacker to try to bypass — the CPU itself refuses out-of-bounds access.

That's the general principle beneath both of this chapter's examples: an LDT entry is a remarkably cheap way to hand one specific piece of code a private, hardware-enforced view of memory, without standing up an entire new process or page-table hierarchy for it. Mostly, today, that cheapness gets spent on backward compatibility. Occasionally, it's gotten spent on sandboxing instead.

It's also worth noting how that sandboxing story ends, because it rhymes with everything else in this chapter. Native Client's segmentation-based trick was specific to 32-bit x86 — on 64-bit x86, segment bases and limits are mostly ignored by the hardware for exactly the same long-mode reasons this chapter keeps circling back to, so a 64-bit NaCl sandbox couldn't lean on the same mechanism. Its x86-64 implementation switched to a different technique entirely (base-and-mask address confinement instead of hardware segment limits), and NaCl itself was eventually superseded in browsers by WebAssembly's own sandboxing model. Even the "clever sandboxing" use of the LDT turned out to be a 32-bit-era trick, not a lasting one.

06 — Tallying It Up

Who Still Uses LDTs, and Why

Put the last three sections side by side and a short, honest list falls out. This isn't a mainstream feature with a long tail of users — it's a short, specific list of programs with a genuine reason to touch it.

GDT Usage Today vs. LDT Usage Today

📖 The GDT — quietly universal

Consulted on every single memory access, for every process, all the time — even though its entries are deliberately boring, flat, do-nothing-special descriptors. You cannot opt out of the GDT; the segmentation unit isn't optional silicon.

📔 The LDT — almost always empty

For the vast majority of processes on a vast majority of machines, ldtr holds a null selector its entire life. It only gets populated by name-brand exceptions: things faithfully emulating segmented-era software, or — rarely — squeezing a sandbox boundary out of cheap hardware.
07 — Make It Concrete

Watching modify_ldt() Actually Fire

All of this is easy to take on faith and hard to actually see — but you don't need special tools to catch it happening. Linux's strace traces every syscall a process makes, modify_ldt() included, and Wine is more than willing to make the call the moment it needs a custom segment.

$ strace -f -e trace=modify_ldt wine notepad.exe modify_ldt(0x11, {entry_number=3, base_addr=0x7f2a10000000, limit=0xffff, seg_32bit=0, ...}, 16) = 0 // a real 16-bit LDT entry just got installed for this process — // exactly the descriptor this chapter's canvas animation depicts, // now sitting in real kernel memory backing a real ldtr

For a modern 64-bit Windows game running under Proton, you'll typically see nothing at all under that same filter — which is itself the point this chapter has been making. The syscall's presence or absence in the trace is a direct, observable signal of whether the program underneath actually needed genuine segmentation, or was flat all along.

Try comparing traces. Running the same strace -f -e trace=modify_ldt filter against an ordinary modern 64-bit Linux binary — a text editor, a compiler, anything built in the last decade — will almost always come back completely empty for the process's entire lifetime. That silence is the "0" from this page's opening hero stat, made observable.
08 — The Honest Ending

Why It's Never Coming Back

It would be tempting to end this chapter by suggesting the LDT is quietly making a comeback. It isn't, and it's worth being straightforward about that rather than manufacturing false suspense.

64-bit long mode — the mode every modern 64-bit OS actually runs its processes in — guts segmentation almost entirely. Base and limit checking for CS/SS/DS/ES are hardware-disabled in long mode; addresses through those registers are just flat 64-bit pointers, full stop, with paging doing essentially all the real protection work. (This series' companion piece, "Long Mode — What Happened to Segmentation on a 64-bit CPU," walks the full register-by-register story — the short version is that only fs/gs keep a genuinely live Base field, kept alive specifically for thread-local storage, set via that very same arch_prctl(ARCH_SET_FS, ...) call from Section 02.)

A genuinely 64-bit program, running in long mode, therefore has essentially zero reason to ever populate an LDT. There's no old segmented code to emulate — it was born flat. That's exactly why the hero stat at the top of this page reads "0 LDTs a 64-bit program ever needs": it isn't an exaggeration, it's close to the literal truth for ordinary software.

The honest summary LDT usage today ≈ { software emulating pre-flat-addressing programs } ∪ { rare, deliberate hardware-sandbox tricks } Not a growing set. Not shrinking to zero either, as long as Wine and DOSBox still have users — but never coming back into the mainstream.

Laid out across every mode a real x86 CPU can run in, the pattern is stark — the LDT only ever mattered where segmentation itself mattered, and long mode is precisely where the series of modes stops caring:

🌍 It Was Always An x86 Story
Worth remembering as this series wraps up its detour: the GDT/LDT split isn't some universal operating-systems concept every architecture eventually grows — it's a specifically x86 artifact, inherited all the way from the 80286. ARM, RISC-V, and most other architectures that came after never adopted segmented memory as a hardware protection mechanism at all; they went straight to paging. The LDT isn't just a living fossil in time — running decades-old code today — it's also increasingly a living fossil in architecture, as more of the software world's compute quietly moves onto chips that never had an LDT to begin with.
🦖 A Genuine Living Fossil
That's really the right way to think about the LDT in 2026: not "obsolete and gone," and not "secretly still important" — a living fossil. Kept alive in the kernel's syscall table and the x86 instruction set by one specific, valuable niche: faithfully running yesterday's software today. As long as someone wants to run a 16-bit Windows program or a decades-old DOS game correctly, on real x86 hardware, the LDT — and modify_ldt(), and the segmentation unit underneath both — still has exactly one job to do, and still does it.
One last cousin worth a mention: segment selectors do occasionally do real work elsewhere in the 64-bit world too — just usually through the GDT, not the LDT. 64-bit Windows's WoW64 layer, for instance, uses a well-documented technique nicknamed "Heaven's Gate," where a nominally 32-bit process performs a far jump to a fixed GDT selector (0x33) describing a genuine 64-bit code segment, briefly running true 64-bit instructions before jumping back. It's the same underlying mechanism this whole series has described — a selector routing through a table to a descriptor that changes what the CPU does next — just applied to mode-switching rather than memory bounding, and rooted in the shared GDT rather than a private LDT. Segmentation hardware never fully retired; it just mostly stopped needing a private table to do its remaining jobs.
09 — Quick Reference

Glossary & Key Terms

LDT (Local Descriptor Table)
An optional, per-process array of Segment Descriptors, selected by TI=1, that a process can populate with its own private segments.
modify_ldt()
The Linux syscall (func, ptr, bytecount) that lets user-space read or install real Segment Descriptors into its own process's LDT.
struct user_desc
The descriptor format modify_ldt() accepts from user-space: entry number, base, limit, and the same 32-bit/present/type-style flags a real Segment Descriptor carries.
Wine
A compatibility layer that runs Windows programs on Linux and other Unix-like systems; its 32-bit builds use modify_ldt() to give genuine segmentation hardware to old Win16/DOS-era guest programs.
Win16
The 16-bit Windows 3.x-era application format, written assuming real segment:offset addressing with many small (≤64KB) segments per program.
DOSBox
A full DOS-era PC emulator that reproduces segmentation entirely in software, without exercising the host's own segmentation hardware or LDT.
DOSEMU
A Linux-specific DOS emulator that uses vm86() for real-mode code and modify_ldt() to give DPMI clients genuine protected-mode segments.
DPMI
The DOS Protected Mode Interface — a standard many later DOS programs used to run in 32-bit protected mode with real segments instead of cramped real-mode memory.
vm86 Mode
A CPU submode letting the kernel run real-mode (16-bit, unprotected-style) code as a controllable, trappable guest inside protected mode.
arch_prctl / FS base
The syscall 64-bit programs use to set a relocatable %fs base for thread-local storage directly — the modern replacement for descriptor-table tricks, needing no LDT at all.
Native Client (NaCl)
A historical Google browser sandboxing scheme whose x86-32 implementation used modify_ldt()-installed segments as a hardware-enforced boundary for untrusted code.
TI Bit
The bit in a segment selector that chooses which table a lookup uses: 0 routes to the shared GDT, 1 routes to the process's own LDT.
Long Mode
The 64-bit operating mode where segmentation is almost entirely disabled by hardware, leaving genuine 64-bit programs with no practical reason to ever touch an LDT.
CONFIG_X86_16BIT
A Linux kernel build option gating 16-bit segment support; disabling it trades Wine/DOS-emulator compatibility for a smaller kernel attack surface.
