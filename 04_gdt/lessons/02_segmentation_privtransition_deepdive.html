01 — The Problem Nobody Mentions

Why a Ring Transition Needs a New Stack

Here's a question that sounds pedantic until you actually think it through: when a Ring 3 program calls into the kernel, whose stack does the kernel code run on?

Your gut answer is probably "the same one — why would it change?" And that gut answer is exactly the bug that would exist if CPUs didn't handle this specially. The user program's stack is pointed to by ss:esp (or ss:rsp in 64-bit mode) — an address the user program itself controls. It set that pointer. It can move it. It can hand the kernel a stack pointer that's deliberately garbage, or one that points into memory it doesn't even own, or one that's one push away from wrapping around into something sensitive.

⚠️ Why This Actually Matters
If the kernel's privileged handler code kept using that same, attacker-controlled esp the moment CPL flipped to 0, then every local variable the kernel pushes, every saved register, every return address for its own internal function calls would be sitting in memory the untrusted process already controls. A malicious program could hand the kernel a stack pointer aimed at its own code, corrupt kernel locals on purpose, or engineer a stack overflow to smash something it has no business touching — all while the CPU thinks it's running at CPL 0 with full privilege. Privilege escalation would be a one-line exploit.
Make it concrete — Say a process deliberately sets esp to point one byte below the end of its own address space right before making a syscall, with no stack-switch hardware in the picture. The very first push the kernel's handler performs would fault or wrap into unmapped or unrelated memory it never intended to touch. Or worse: the process points esp at a region it fully controls and has pre-filled with crafted data, hoping the kernel will push a saved register on top of it and then, later, pop something the process planted instead — quietly hijacking a return address while the CPU still believes it's running at CPL 0. Neither scenario is exotic; it's just what "the kernel trusted a pointer the user supplied" looks like once you follow it through.

So the rule has to be absolute: the instant the CPU's privilege level rises, the stack must change too — to a stack that lives in kernel memory, that the user process cannot read, write, or even locate. And critically, this can't be something the kernel's own handler code does as its first instruction, because between "CPL becomes 0" and "the kernel gets a chance to run any instruction at all," there's a gap — and during that gap the CPU is already privileged but hasn't done anything yet. That gap has to be zero-width. Which means the stack switch has to be done by hardware, atomically, as part of the transition itself, before a single instruction of kernel code executes.

The one-line rule No ring transition is ever "just" a jump to a new address. It is always: new stack, then jump. The CPU performs the stack switch as an inseparable part of the transition — not as something the handler remembers to do.
02 — Where the New Stack Comes From

The TSS Supplies the Trusted Address

Fine — the CPU needs a fresh, trusted ss:esp pair the instant it enters Ring 0. But where does it get one? It can't invent an address out of thin air, and it certainly can't ask the user program. The answer is a structure you've already met by name in the base segmentation article, when descriptor types were introduced: the Task State Segment (TSS).

Recall that a TSSD (Task State Segment Descriptor) is a system descriptor (S flag cleared) that can only live in the GDT. What actually sits at the address that descriptor points to is a block of memory — the TSS itself — and buried inside it are fields that exist for exactly this moment: a saved stack pointer for each privilege level the kernel is willing to be entered at.

TSS FieldHoldsUsed When
ss0 / esp0Kernel stack segment selector + pointer for CPL 0Any transition into Ring 0 — the field that matters for ordinary syscalls, faults, and interrupts
ss1 / esp1Stack for CPL 1Essentially unused by Linux and virtually every modern OS — CPL 1/2 go unused
ss2 / esp2Stack for CPL 2Same — unused in practice
rsp0 / rsp1 / rsp264-bit equivalents in the long-mode TSS layoutx86-64 kernels — same idea, wider pointers, no separate ss field needed since 64-bit mode uses flat addressing for the stack segment
IST1–IST7Interrupt Stack Table — seven extra dedicated stack pointersSpecific, especially dangerous vectors (double fault, NMI) that get forced onto a known-good stack regardless of what esp0/rsp0 currently is

In practice, on Linux, only one of those fields is doing real work on every single syscall and interrupt: the CPL-0 stack pointer (esp0 on 32-bit, rsp0 in the long-mode TSS on 64-bit). The kernel maintains one TSS per CPU core, and before it ever lets a process run, it makes sure that core's TSS points esp0/rsp0 at the top of that specific thread's kernel stack — the same kernel stack the trap frame from the PCB/threads article gets pushed onto.

💡 Tying the Threads Together
Remember the Task Register (tr) that quietly holds a selector pointing at the current TSS? This is the payoff. On a transition into Ring 0 via the classic interrupt-gate mechanism, the CPU doesn't search anywhere exotic for the new stack — it goes straight to tr → current TSS → ss0:esp0, copies that pair into the live ss and esp registers, and only then starts pushing the trap frame. The TSS descriptor type mentioned but not detailed in the base segmentation article turns out to be the single piece of hardware plumbing that makes a trustworthy ring transition possible at all.
Side note — Linux doesn't use the TSS for its originally-intended purpose (hardware task switching, where the CPU itself swaps an entire register set via a task-gate — see later in this article). It repurposes the structure purely as a vehicle for esp0/rsp0 and the I/O permission bitmap. One structure, one field that actually matters day to day, used billions of times a second across a fleet of machines.

The IST — a Stack You Can Trust Even When Trust Has Already Broken Down

Go back to the threat this whole article opened with: what if the thing that's broken is the stack pointer itself? A stack overflow in the kernel, or a fault that happens while esp0/rsp0 is mid-update, could in principle mean the CPU tries to deliver a trap using a stack pointer that's already corrupt — which for something like a double fault (a fault that happens while handling another fault) would be catastrophic: no reliable stack means no reliable trap frame means no reliable recovery.

This is exactly what the seven IST (Interrupt Stack Table) entries in the 64-bit TSS are for. A handful of especially dangerous vectors — double fault and NMI (non-maskable interrupt) chief among them — can be configured in the IDT to always use one specific, dedicated, known-good stack from the IST list, completely bypassing whatever rsp0 currently happens to be. It's the same "never trust the stack you're handed" principle from section 01, applied one level deeper: even the kernel doesn't fully trust its own current stack pointer for the handful of faults that are most likely to occur precisely because something already went wrong with it.

03 — Concrete Stack Contents

The Trap Frame, Made Literal

The PCB/threads article told you traps push "a small, fixed bundle" onto the kernel stack and called it the trap frame, without showing you what's actually in the bundle. Here it is, concretely, for the classic legacy mechanism: a software interrupt like int 0x80 (32-bit Linux's original syscall gate) or any hardware interrupt firing while the CPU is in Ring 3.

The moment such a trap fires with a privilege-level change pending, the CPU performs this sequence, entirely in hardware, before any kernel instruction runs:

  1. 1. Save the old ss:esp temporarilyThe CPU holds onto the current (user-mode) stack segment selector and stack pointer — it needs them in a moment, but not on the stack that's about to be abandoned.
  2. 2. Load new ss:esp from the TSSss and esp are overwritten with the ss0/esp0 values fetched from the current TSS, as covered above. The CPU is now, for the first time, pointed at the kernel stack.
  3. 3. Push the old ssThe user-mode stack segment selector — saved in step 1 — is pushed onto the brand-new kernel stack. This is the first byte of the trap frame.
  4. 4. Push the old espThe user-mode stack pointer follows immediately. Together, these two values are the only reason the CPU will ever be able to find the user stack again.
  5. 5. Push eflagsThe full flags register — condition codes, interrupt-enable flag, everything — captured exactly as it was at the moment of the trap.
  6. 6. Push the old csThe code segment selector that was active in Ring 3, CPL and all, so the CPU knows exactly which privilege level and code segment to snap back to later.
  7. 7. Push the old eipThe address of the very next instruction the user program would have executed. This is the resume point — the literal definition of "pick up exactly where you left off."
  8. 8. (Some vectors only) Push an error codeA handful of exceptions — page fault, general protection fault, and a few others — push one extra 32-bit word describing why the fault happened (e.g., was it a read or a write, present or not-present page). Ordinary syscalls and most interrupts skip this; it's specific to certain fault vectors.

Only after all of that has landed on the kernel stack does the CPU finally set CPL = 0 and load cs:eip from the interrupt/trap gate descriptor the vector pointed to — jumping into the kernel's registered handler. Here's that entire bundle laid out visually, as it actually sits in memory the instant the handler gets its first instruction:

User Stack (ss:esp) — before the trap
… program's own data …whatever the process pushed
esp →top of user stack at trap time
Kernel Stack (new ss0:esp0) — right after the trap
esp0 (new) → eip (old)resume address — pushed last
cs (old)carries the old CPL = 3
eflagscondition codes, IF, etc.
esp (old)user stack pointer, preserved
ss (old)user stack selector — pushed first
error code (only some exceptions)pushed after eip, when present
🧠 This Is the Trap Frame
Everything the PCB/threads article called "the trap frame" is exactly this bundle: old ss, old esp, eflags, old cs, old eip, plus an optional error code. It's not a separate concept from the trap frame — it's the trap frame's literal byte layout, sitting on the kernel stack, for as long as the handler needs it. When the handler finishes and executes iret, it reads this exact bundle back off the stack to figure out how to resume — nothing about the return path is magic; it's just this same memory, read in reverse.
04 — The Fast Path

Why syscall / sysret Exist

The mechanism above works, but notice how much it does: consult tr, walk to the TSS, read esp0, and — this is the expensive part — look up a gate descriptor in the IDT (Interrupt Descriptor Table) by vector number, which means a full descriptor fetch and a privilege check (comparing the gate's DPL against the caller's CPL) before the CPU even knows where to jump. For a hardware interrupt that fires rarely, that overhead is a rounding error. But for the single most common Ring 3 → Ring 0 crossing of all — "user program wants an ordinary kernel service," i.e., an actual system call — paying full descriptor-table overhead on every single call adds up fast, because programs make syscalls constantly.

x86-64's answer is a purpose-built instruction pair: syscall to go in, sysret to come back. The entire idea is to skip the descriptor-table lookup completely for this one extremely common case, and instead read the destination straight out of a small, fixed set of Model-Specific Registers (MSRs) — registers the kernel configures once, at boot, and the CPU consults directly, with no memory access and no table walk.

MSRHolds
IA32_STARPacked selector values: the kernel cs/ss to load on entry, and the (offset) user cs/ss to restore on sysret
IA32_LSTARThe target rip for syscall when the calling code is in 64-bit (long) mode — this is the kernel's syscall entry point
IA32_CSTARThe target rip for syscall issued from 32-bit compatibility mode under a 64-bit kernel
IA32_FMASK (SFMASK)A bitmask applied to rflags on entry — bits set here are forcibly cleared, e.g. clearing the interrupt-enable flag automatically

On syscall: the current rip is saved into rcx, rflags is saved into r11, rflags is masked using IA32_FMASK, cs/ss are loaded from IA32_STAR, rip is loaded from IA32_LSTAR, and CPL becomes 0. On sysret, it runs in reverse: rip comes back from rcx, rflags comes back from r11, cs/ss are reloaded from the other half of IA32_STAR, and CPL returns to 3. No IDT, no gate descriptor, no privilege-check table walk — just register-to-register moves plus two MSR reads. That's the entire reason it's fast.

Notice that IA32_STAR alone supplies three different selector values out of one 64-bit register, by packing them into separate bit ranges the CPU reads directly — the same "one register, several meaningful fields" idea as the segment selector's index/TI/RPL split from the base article, just applied to a whole different register:

SYSRET CS/SS base
bits 63–48
SYSCALL CS/SS base
bits 47–32
target EIP (compat mode only)
bits 31–0

The CPU doesn't store four independent selectors here — it stores two selector bases and derives the rest by fixed offsets (kernel ss is kernel cs + 8, for instance), because the GDT layout Linux uses places matching code/data pairs at predictable, adjacent slots. One packed register, read with zero memory access, is enough to fully describe where both the entry and the exit land.

The rcx Problem: Why the Syscall ABI Uses r10, Not rcx

Here's a small but very real consequence of how syscall works, visible the moment you look at Linux's actual syscall calling convention. Ordinary x86-64 function calls pass their fourth argument in rcx. But syscall overwrites rcx with the return address the instant it executes — so if the syscall ABI also used rcx for an argument, the instruction would clobber its own input before the kernel ever got to read it.

The fix is simple once you see the cause: the Linux syscall calling convention passes arguments in rdi, rsi, rdx, r10, r8, r9 — identical to the normal C calling convention except the fourth argument moves from rcx to r10, specifically to dodge this exact collision. It's a small, permanent scar left on the userspace ABI by a hardware design decision made purely for speed.

Side note — AMD shipped syscall/sysret first, as part of its original x86-64 design. Intel's earlier fast-path answer, back in the 32-bit Pentium II era, was a different pair: sysenter/sysexit, configured through their own MSRs (IA32_SYSENTER_CS/ESP/EIP) rather than STAR/LSTAR. Both instruction pairs chase the identical goal — skip the IDT for the common syscall case — and modern 64-bit Intel chips support syscall too, so sysenter mostly survives today only in 32-bit compatibility paths and legacy vsyscall/vDSO code. Two vendors, two competing shortcuts, converging on the same idea.
⚠️ The Catch — syscall Does NOT Auto-Switch the Stack
Here's the detail that trips people up, because it breaks the pattern from section 03: unlike the interrupt-gate path, syscall does not consult the TSS and does not automatically move rsp to a kernel stack. rsp is left exactly where the user program had it, even though CPL is now 0. Speed was the whole point, and an automatic stack switch through the TSS was part of what made the legacy path slower — so the fast path simply skips it and leaves the job to software.

So who does the stack switch instead? The kernel's own syscall entry code, in its very first few instructions, by hand. The standard trick (what Linux actually does) is swapgs — an instruction that swaps the gs base register with a value stashed in a kernel MSR, instantly giving the freshly-entered, still-on-the-user-stack code access to a per-CPU data area without touching any general-purpose register. From that per-CPU area, the entry code reads a saved kernel stack pointer, stows the incoming (user) rsp somewhere safe, and only then manually loads rsp with the kernel stack address — all before it dares push anything or call any further function. Only after that hand-rolled swap has happened is it actually safe to start using ordinary kernel C code.

Side note — This hand-rolled stack switch is exactly the kind of few dozen instructions of raw assembly every production kernel has somewhere near its syscall entry point (Linux keeps it in entry_64.S). It's also historically been a rich source of security bugs — get the ordering of swapgs wrong relative to a speculative execution boundary and you get exactly the kind of side channel that Spectre-family attacks went looking for. Trading hardware guarantees for software speed means the software has to get it exactly right, every time.
05 — Watch It Happen

The Full Round Trip, Step by Step

Time to put the whole thing together, start to finish, for both mechanisms. Pick a path below and watch exactly what moves — the stack pointer, the trap frame, and the CPL badge — through the entire out-and-back journey.

First, a quick reconciliation with the "three doors into the kernel" from the PCB/threads article — syscall, exception, and hardware interrupt. All three are traps in the CPU's eyes, but only one of them has a purpose-built shortcut:

DoorWhich mechanism can carry it?Error code?
System CallEither — int 0x80 (legacy/32-bit) or syscall (fast path, 64-bit)No
Exception / FaultInterrupt/trap-gate mechanism only — there is no "fast" exception pathSometimes (page fault, GPF, and a few others)
Hardware InterruptInterrupt-gate mechanism only, dispatched by vector number off the IDTNo

syscall/sysret is the odd one out on purpose: it was built for exactly one door and doesn't even attempt to serve the other two. A CPU exception can't announce itself through a register-only MSR shortcut — it needs the full generality of an IDT vector, because the CPU itself is the one raising it, asynchronously, mid-instruction, with no cooperation from any program.

▶ Choose a transition mechanism to animate

Now the two paths, laid out in full — not merged, so you can see exactly where they diverge and exactly where they end up in the same place.

Legacy path — int 0x80 in, iret out

  1. 1. User program executes int 0x80Or a hardware device fires an interrupt asynchronously — either way, CPL is 3 and ss:esp still point at the user stack at this instant.
  2. 2. CPU looks up the vector's gate descriptor in the IDTThe vector number (0x80, or the device's assigned IRQ line) selects a slot; the gate descriptor there is checked — its DPL must permit the caller's CPL — and supplies the eventual target cs:eip.
  3. 3. CPU reads ss0:esp0 from the current TSS via trAnd switches ss:esp to it immediately — hardware, atomic, no software involved yet.
  4. 4. CPU pushes the trap frame onto the new kernel stackOld ss, old esp, eflags, old cs, old eip — in that order — plus an error code if this particular vector supplies one.
  5. 5. CPL becomes 0; cs:eip loads from the gate descriptorThe kernel's registered handler starts executing, on the kernel stack, at full privilege.
  6. 6. Handler does its work, then executes iretiret pops eip, cs, and eflags. Because the popped cs's privilege level differs from the current CPL, iret also pops esp and ss — switching the stack back to the user's, in the same instruction.
  7. 7. Execution resumes in Ring 3Exactly at the instruction after int 0x80, on the original user stack, with the original flags. Nothing observable changed from the program's point of view.

Fast path — syscall in, sysret out

  1. 1. User program executes syscallCPL is 3, rsp still points at the user stack — and, critically, will keep pointing there for a few more instructions yet.
  2. 2. CPU saves rip→rcx, rflags→r11, masks rflags, loads cs/ss/rip from MSRsIA32_STAR supplies the kernel cs/ss, IA32_LSTAR supplies the target rip, IA32_FMASK clears whichever rflags bits the kernel configured (typically the interrupt-enable flag). CPL becomes 0. No IDT was ever consulted.
  3. 3. Kernel entry code runs swapgs and manually swaps rspStill, technically, running on the user's stack for these first few instructions — this is why this hand-written assembly has to be so careful. Once rsp points at the kernel stack, the incoming user rsp is stashed safely, and it's finally safe to push normal data.
  4. 4. Kernel entry code pushes whatever the C handler will needUnlike the legacy path, this isn't one atomic hardware bundle — it's ordinary push instructions the kernel's own assembly chose to execute, building up enough of a frame for the C syscall handler to run normally.
  5. 5. The kernel handler does its workArguments arrive in rdi, rsi, rdx, r10, r8, r9 (note r10, not rcx — see the ABI note above) plus the syscall number in rax.
  6. 6. Kernel restores rsp to the saved user value, then executes sysretsysret reloads rip from rcx, rflags from r11, and cs/ss from the other half of IA32_STAR. CPL returns to 3.
  7. 7. Execution resumes in Ring 3Same destination as the legacy path — right after the syscall instruction, original stack, original flags — just gotten to by a leaner, MSR-driven route with more of the bookkeeping done by hand.
✅ The Whole Point, Stated Plainly
A syscall is designed to be indistinguishable from an ordinary function call from the caller's point of view — same "call, do work, return with a result" shape. Everything in this section exists purely so that illusion holds up perfectly, even though underneath it, the CPU tore down an entire privilege context and rebuilt it twice.
06 — The Older Aristocracy

Call Gates & Task Gates: Roads Less Traveled

The interrupt/trap-gate mechanism and syscall/sysret aren't the only descriptor-table-based ways to change privilege — they're just the two that won. Two older, System-type descriptors (siblings of the TSSD from the base article, with the S flag cleared the same way) offered more controlled, more structured privilege escalation. You'll rarely see either used in a modern general-purpose OS, but you should know they exist and roughly why they lost.

Call Gate Descriptor
A System-type descriptor that lets a program invoke a specific, pre-registered privileged procedure via an ordinary-looking call instruction targeting the gate's selector — as if calling a regular subroutine. The CPU checks privilege against the gate itself, optionally switches stacks (again via the TSS), and jumps to a fixed entry point, exactly like a much more constrained, subroutine-flavored version of the interrupt-gate mechanism.
Task Gate Descriptor
Points at a TSS and, when invoked, tells the CPU to perform a full hardware task switch: save the entire current register set into the outgoing TSS, and load an entirely new register set — including cr3, meaning a whole new address space — from the incoming TSS, all done by the CPU itself with no software register-saving code at all.

Hardware task switching sounds appealing on paper — the CPU does all the bookkeeping for you. In practice it lost decisively to software-managed context switching (the PCB/TCB-based approach from the earlier article) for reasons that should sound familiar by now: it's rigid (the format of what gets saved is fixed by the CPU, not the OS), it saves and restores far more state than most switches actually need, and — the recurring theme of this entire page — it's slow relative to a kernel just doing the minimal necessary work in software. Call gates suffer a milder version of the same problem: real, useful privilege checking, but with more table-walking overhead than a purpose-built instruction like syscall needs to pay.

📌 Why They Faded
Every mechanism on this page is trading the same two things against each other: how much the hardware automates versus how fast the common case runs. Task gates automate the most and are the slowest. Call gates automate a fair amount and sit in the middle. Interrupt/trap gates automate what's needed for traps specifically. syscall/sysret automate the least — pushing real work onto the kernel's own entry code — and are the fastest of all. Modern OS design consistently chose the fast end for the path that runs the most often, and reserved the fully automatic, heavier mechanisms for the rare cases (or dropped them entirely).

Zooming back out, every System-type descriptor this series has now touched turns out to belong to one small family — all S-flag-cleared, all living primarily in the GDT, each aimed at a different flavor of "controlled transfer of control":

System DescriptorWhat It Points ToTriggers a Stack Switch?Status
TSS Descriptor (TSSD)A Task State SegmentN/A — it's the source of the switch, not a triggerAlive and load-bearing, every trap
Interrupt/Trap GateA handler entry point (cs:eip), looked up via IDT vectorYes, automatic via TSSAlive — the only path for exceptions/interrupts

07 — Side by Side

Two Paths, Compared

🐢 int 0x80 / iret (interrupt-gate)

Target address found by walking the IDT and checking a gate descriptor's DPL. Stack switch to ss0:esp0 is fully automatic, pulled from the TSS by hardware. Works uniformly for syscalls, faults, and interrupts. Slower, because of the table walk and privilege check on every single trip.

⚡ syscall / sysret (fast path)

Target address read directly from IA32_STAR/IA32_LSTAR — no table, no walk. Stack switch is not automatic — the kernel's entry code must swapgs and move rsp itself. Purpose-built for one job only: a Ring 3 program deliberately requesting a kernel service.
Propertyint 0x80 → iretsyscall → sysret
Target lookupIDT gate descriptor, by vector numberIA32_STAR / IA32_LSTAR MSRs directly
Privilege checkGate DPL vs. caller CPL, checked by hardwareNone — any Ring 3 code may execute it; the kernel handler itself must validate arguments
Stack switchAutomatic, via TSS ss0:esp0Manual — kernel entry code does swapgs + rsp swap
Error code supportYes, for applicable exception vectorsN/A — not an exception mechanism
Works for interrupts / faults?Yes — general-purpose trap mechanismNo — syscalls only, by design
Typical use today32-bit legacy syscall entry, all interrupts/exceptions on any modeThe default syscall path for 64-bit user programs
Relative speedSlower — table walk + automatic stack switchFaster — the entire reason it exists

Both still coexist on real machines today: interrupts and CPU exceptions have no choice but to go through the gate-descriptor mechanism (there's no "exception equivalent" of syscall), while an ordinary 64-bit Linux program making a deliberate syscall — read(), write(), mmap() — almost always rides the fast path instead.

08 — Quick Reference

Glossary & Key Terms

Ring Transition
Any change in CPL — most importantly Ring 3 → Ring 0 (entering the kernel) and back, always accompanied by a stack switch when crossing that boundary.
TSS (ss0 / esp0, rsp0)
The Task State Segment's saved Ring-0 stack pointer fields — where hardware gets the trusted kernel stack address for the legacy interrupt/trap-gate path.
Trap Frame
The concrete bundle pushed onto the kernel stack on entry: old ss, old esp, eflags, old cs, old eip, plus an optional error code.
int 0x80
The classic 32-bit Linux software-interrupt syscall gate — a deliberate trap instruction that triggers the interrupt-gate transition mechanism.
iret
The return instruction for the interrupt/trap-gate path — pops the trap frame and, when a privilege change is detected, also restores ss:esp.
syscall / sysret
x86-64's fast-path instruction pair for entering and leaving Ring 0, purpose-built for the "user wants a kernel service" case, bypassing the IDT.
IA32_STAR / LSTAR / CSTAR / FMASK
The Model-Specific Registers that configure syscall's target CS/SS, target RIP (64-bit and compat mode), and the RFLAGS mask, respectively.
swapgs
The instruction the kernel's syscall entry code uses to reach a per-CPU data area (holding the kernel stack address) without an automatic hardware stack switch.
Call Gate
An older System-type descriptor letting a call instruction invoke a pre-registered privileged routine with a hardware-checked privilege boundary.
Task Gate
An older System-type descriptor triggering a full hardware task switch — entire register set (including cr3) swapped by the CPU via a pair of TSSs.
IST (Interrupt Stack Table)
Seven extra dedicated stack pointers in the 64-bit TSS, forced for specific dangerous vectors (double fault, NMI) so those handlers never depend on a possibly-corrupt current stack.
r10 (syscall ABI)
Stands in for rcx as the 4th syscall argument register on Linux, because syscall itself overwrites rcx with the return address before the kernel can read it.
sysenter / sysexit
Intel's earlier, MSR-driven fast syscall path (predating x86-64's syscall/sysret), now largely confined to 32-bit compatibility and legacy vDSO code.
