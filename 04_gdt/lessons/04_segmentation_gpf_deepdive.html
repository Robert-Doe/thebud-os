01 — The Rule The Base Modules Only Half-Told You

The Real Check: MAX(CPL, RPL) ≤ DPL

Think of this whole article as an autopsy. Every fault the CPU can raise over a segment access leaves a trail — a precise reason it fired, a precise number that decided it. Section by section, this piece works through that trail: the formula behind the privilege check, why RPL is a separate knob from CPL at all, the faults that have nothing to do with privilege, and finally the error code the CPU leaves behind so you can reconstruct exactly what happened after the fact.

📜 Where We Left Off
From the GDT article's worked example, step five: "The CPU compares the descriptor's DPL against the current CPL and the selector's RPL. If the access isn't allowed... a general protection fault fires instead." That's technically true. It's also hiding the one detail that actually matters: how two separate numbers — CPL and RPL — get "compared" against a single DPL.

Here's the honest version. For an ordinary data-segment access — loading a selector into ds, es, fs, gs, or ss, or more generally touching a segment through one of those registers — the CPU does not check CPL against DPL, and it does not check RPL against DPL. It checks both at once, by taking whichever of the two is numerically worse, and comparing that against DPL.

The Actual Rule (Data Segment Access) MAX(CPL, RPL) ≤ DPL Remember: lower numbers mean MORE privileged. So this reads — "the less-privileged of the two requesting parties must still be privileged enough for the target segment."

Why take the worse of the two instead of just checking CPL? Because either number could be the weak link. CPL says how privileged the currently running code really is. RPL says what privilege level this specific access is claiming to be happening at — and as you're about to see, a routine can deliberately understate its own privilege on a single access, on purpose. The check has to honor whichever number is stingier, or the whole mechanism would be pointless.

Case 1 — The Obvious Fault

CPL3 RPL3 target DPL0
MAX(3, 3) = 3   →   is 3 ≤ 0? No.
✕ General Protection Fault

Ordinary user-mode code (CPL 3), using its own ordinary selector (RPL 3, matching CPL as usual), reaches for a kernel-only segment (DPL 0). Exactly the fault you'd expect — and exactly the case the GDT article's one-line summary was describing.

Case 2 — The Kernel Deliberately Lowers Itself

CPL0 RPL3 target DPL3
MAX(0, 3) = 3   →   is 3 ≤ 3? Yes.
✓ Access Granted

A kernel routine (CPL 0, full hardware privilege) is servicing a user request and needs to touch a user-owned data segment (DPL 3). It deliberately loads that access with RPL forced to 3. Even though the code itself is running at CPL 0, MAX(CPL, RPL) still evaluates to 3 — the CPU treats this one access as if it were happening at user privilege, and since the target genuinely allows DPL 3, it succeeds.

Case 3 — The Same Trick, Catching a Bad Pointer

CPL0 RPL3 target DPL0
MAX(0, 3) = 3   →   is 3 ≤ 0? No.
✕ General Protection Fault

Same kernel routine, same deliberately-lowered RPL = 3 — but this time the selector it was handed actually resolves to a kernel-only segment (DPL 0), whether from a bug or a hostile caller trying to trick the kernel into touching kernel memory on the user's behalf. Because RPL was forced to 3, the CPU catches it before a single byte is touched. This is the mechanism working exactly as designed.

🛡️ "Can't I Just Set RPL = 0 and Get Kernel Access?"
No — and this is the detail that makes the whole scheme airtight. MAX(CPL, RPL) always takes the worse (numerically higher) of the two. If code is genuinely executing at CPL 3, forging RPL = 0 in a selector changes nothing: MAX(3, 0) is still 3. RPL can only ever make an access look less privileged than CPL by setting it higher — it can never make an access look more privileged, because CPL — which ordinary code cannot forge; it's fixed by which code segment is actually executing — always sets the floor.

Three Ways People Misremember the Rule

"Just check CPL vs DPL"wrong
Ignores RPL entirely. Under this (incorrect) model, Case 3 from above would wrongly succeed — the kernel's CPL 0 would satisfy any DPL, and the confused-deputy catch would never fire.
"Just check RPL vs DPL"wrong
Ignores CPL entirely. Under this (incorrect) model, the "RPL=0 cheat" from later in this article would wrongly succeed — any code could claim RPL 0 and access anything, regardless of its real privilege.
MAX(CPL, RPL) ≤ DPLcorrect
Takes the worse of the two before comparing. Neither a privileged deputy borrowing lower privilege, nor unprivileged code forging higher privilege, can slip past it. Both surrounding examples resolve correctly under this model — and only this model.
Scope note: everything above describes the check for loading and using a data-segment register (ds/es/fs/gs/ss). Code-segment access via far call/jmp uses a related but distinct rule involving the target's conforming bit — a conforming code segment can be entered without an exact privilege match, a non-conforming one requires CPL = DPL exactly. That's a big enough topic for its own article; this one stays focused on the data-segment rule, which is also the one the GDT worked example was describing.
02 — Confused Deputies and the Reason RPL Exists

Why RPL Isn't Just Redundant CPL

Here's the question a careful reader should be asking: if the CPU already knows CPL straight out of cs, why does a selector need its own separate privilege field at all? Couldn't the whole check just use CPL alone?

Walk through what goes wrong if it did. Imagine a kernel routine implementing something like a read() system call. A user process hands it a buffer pointer and asks the kernel to fill it with data. The kernel is running at CPL 0 — full privilege — for the entire duration of that syscall handler. If the hardware's privilege check used CPL alone, then every single memory access the kernel makes would sail through regardless of DPL, since CPL 0 satisfies any DPL. That includes the access to the user's buffer — which is fine — but it would equally include an access to a segment the user buffer pointer was never supposed to be able to reach, if that pointer were wrong, corrupted, or maliciously crafted.

This exact shape of bug — a highly-privileged program tricked into misusing its own authority on behalf of a less-privileged caller — is a well-known category. Security researcher Norm Hardy named it the confused deputy problem in 1988: the kernel is the "deputy," acting with full authority, and it gets "confused" into spending that authority somewhere the original requester could never have reached directly.

🧠 The Deliberate Fix
Before touching a user-supplied pointer, the kernel loads (or reuses) a data-segment selector for that one specific access with RPL forced to 3 — matching what a genuine user-mode CPL would be. Now MAX(CPL, RPL) = MAX(0, 3) = 3 for that access, no matter how privileged the kernel code around it actually is. The CPU ends up applying the exact same restriction a real CPL-3 accessor would face — using RPL as a way for a privileged deputy to temporarily borrow its caller's lower privilege for one specific touch of memory.

✕ A World Without RPL

The check would have to be CPL ≤ DPL alone. Kernel code, always CPL 0, would satisfy every DPL on the machine for every access it ever makes — including ones aimed at attacker-supplied pointers. There would be no hardware-level way to say "for this one touch, treat me as if I were only as privileged as my caller."

✓ A World With RPL

The kernel can voluntarily narrow its own effective privilege, access by access, just by choosing what RPL to put in the selector it uses. Privilege becomes something the deputy can temporarily lend down to match the request it's fulfilling — not an all-or-nothing property of which ring the code happens to run in.
  1. User calls read(buf, 100)Passes a pointer to buf, expecting the kernel to fill it with up to 100 bytes.
  2. Kernel enters the syscall handler at CPL 0Full hardware privilege, for the entire duration of the call — this doesn't change.
  3. Before writing through the pointer, the kernel sets RPL = 3On the selector it's about to use for this specific write — not a general change, just for this one access.
  4. The CPU runs MAX(CPL, RPL) ≤ DPL using RPL = 3Not the kernel's real CPL = 0 — the check is now anchored to the caller's privilege level instead.
  5. Two outcomesIf buf genuinely lives in a DPL 3 user segment: MAX(0,3)=3 ≤ 3, check passes, the kernel writes the data. If buf's selector actually resolves to a DPL 0 kernel structure — attacker trickery, or a kernel bug — the check fails and a GPF fires before any write happens.
Historical corroboration: this pattern is real enough that x86 shipped a dedicated instruction for it — ARPL (Adjust RPL Field) — which raises a selector's RPL to at least a given value, exactly so kernel code could safely enforce "treat this access as no more privileged than the caller" before touching a caller-supplied selector. Companion instructions VERR/VERW let code verify a selector is even readable/writable at the current privilege before committing to use it.

Segmented multitasking operating systems of the era — OS/2 among the most prominent — leaned on exactly this: per-process LDTs, and kernel code paths that used ARPL routinely whenever a syscall handler had to touch memory on a caller's behalf. The specific mechanism has mostly faded from daily use on flat-segment Linux, but the underlying problem it solved never went away — it's the same shape of question modern mechanisms like capability-based sandboxing and strict syscall argument validation are still answering: how does a more-privileged component avoid being tricked into spending its privilege on a less-privileged caller's behalf?

🔗 Tying Back to the Series
The earlier GDT article noted that Linux flattens segmentation almost entirely — one Base = 0, full-range segment per privilege level — and leans on paging plus explicit range checks (its own copy_to_user/copy_from_user machinery) for this exact confused-deputy protection instead of RPL games. That's a software-level descendant of the same idea. But the RPL mechanism above is genuine, live x86 hardware behavior on every chip you're running this page on — it's simply not the primary tool Linux reaches for today, on flat segments where DPL differences between kernel and user segments already do most of the work.

04 — Faults Before You Even Get to DPL

Selector Loading Faults

Not every GPF is a privilege violation. Two entire categories of fault happen from a malformed or out-of-range selector, before DPL ever enters the picture.

Index Out of Range

Recall the GDT lookup formula from the previous article: Descriptor Address = table.base + (selector.index × 8). That address has to land inside the table — and "inside" is defined by the table's limit field, loaded into gdtr or ldtr. If index × 8 (plus 7, for the last byte of the 8-byte descriptor) exceeds the table's limit, there is no descriptor to fetch — the CPU can't even reach the DPL check.

GDT entries32 gdtr.limit32×8−1 = 255 (0xFF) selector.index40
40 × 8 = 320   →   is 320 + 7 ≤ 255? No.
✕ General Protection Fault

Index 40 asks for a slot that would start at byte 320 — but the table only covers bytes 0–255. The fault fires purely from bounds-checking the index against the limit, long before any DPL, Type, or even Base field is read.

Null Selector: Legal in ds/es/fs/gs, Illegal in ss

A null selector is index = 0, TI = 0 — pointing at GDT slot zero, which by convention is never a usable descriptor. What happens when you load one depends entirely on which register you load it into, and this is one of the easiest facts in the whole subject to get backwards.

✓ ds, es, fs, gs — allowed

Loading a null selector into any of these four is explicitly legal. Nothing faults at load time. The register is simply marked unusable. It's only when code later tries to actually reference memory through that register — e.g. mov eax, [es:ebx] — that the CPU faults, because there's no valid descriptor backing the access.

✕ ss — illegal, always

Loading a null selector into ss faults immediately, at load time. ss must always reference a valid, present, writable data segment, because the CPU can push or pop through it at any moment — an interrupt, a call, an exception — with no warning. A stack segment that might turn out to be unusable would leave the machine unable to safely handle its own very next event.
🔑 Load-Time vs. Use-Time Faults
This pair is a genuinely useful illustration that not every illegal-looking state faults the instant it's created. x86 sometimes defers the fault to the moment the illegal state is actually exploited — a null es is harmless sitting in a register; it only becomes a problem the moment something tries to dereference through it. ss gets no such grace period, because the CPU itself might need to use it unpredictably at any time.
instructionmov ss, ax ax0x0000 index / TI / RPL0 / 0 / 0
Target register is ss, selector is null (index 0)   →   illegal for ss regardless of what slot 0 even contains.
✕ General Protection Fault, at load time

Notice this fault doesn't even need a DPL, or a Type, or an index-range check to fire — "null selector, destination is ss" is sufficient on its own. It's the one selector-loading fault that's unconditional.

05 — Right Descriptor, Wrong Kind of Segment

Type Mismatches

Recall the descriptor's Type field from the GDT article — it says what kind of segment this is: code, data, or a system structure like a TSS or LDT. Each segmentation register only accepts certain Types, and loading the wrong kind is its own distinct fault, independent of any privilege check.

Loading a Register With the Wrong Kind of Descriptor

As a rule, a data register — ds, es, fs, gs, or ss — may only be loaded with a descriptor for a data segment (with one narrow exception: ds/es/fs/gs may also hold a readable code segment, but ss never can — it must always be a writable data segment). Loading any of these registers with a non-readable code-segment descriptor, or with a system-segment descriptor such as a TSS or LDT descriptor, is a straightforward Type mismatch and faults immediately.

instructionmov ds, ax descriptor at that indexTSS descriptor (S=0)
ds requires a data-segment (S=1) descriptor   →   found a system segment instead.
✕ General Protection Fault

The index and RPL were perfectly valid, the table lookup succeeded, and DPL was never even reached — the descriptor is simply the wrong kind of "card" for the register being loaded.

The same logic runs the other direction for cs: it may only be loaded (via a far call/jmp/ret, an interrupt/task gate, or the CPU's own initial boot state) with a descriptor for a code segment. Loading it with an ordinary data-segment descriptor is also a Type mismatch.

Executing From a Non-Executable Segment

There's a second, subtler flavor of this fault: even if cs somehow ends up pointing at a descriptor whose Type marks the segment as data rather than code, the fault doesn't necessarily wait for a load instruction — the moment the CPU tries to fetch and execute an instruction from that segment, the Type check runs again and fails, because execution demands an executable Type regardless of how the register got there.

instructionjmp far ptr [selector] target descriptor Typedata, read/write (non-executable)
cs is about to be loaded with a descriptor whose Type says "data"   →   execution requires an executable Type.
✕ General Protection Fault

DPL is irrelevant here — this segment might even have DPL 3 and CPL might be 3, a perfect privilege match. It still faults, because privilege was never the problem; the segment simply isn't the kind of thing you're allowed to run.

🧩 The Type Field Is Doing Access-Control Work Too
It's tempting to think DPL is the only field standing between code and a fault. It isn't. Type answers a logically prior question — "is this even the right category of thing to be doing this with?" — before privilege is ever consulted. A perfectly-matched DPL 3-to-CPL 3 access still faults instantly if you try to execute a segment whose Type says "data."

07 — Reading the Trap Frame

The GPF Error Code

When #GP fires, the CPU doesn't hand the fault handler an empty-handed "something broke." It pushes a 32-bit error code onto the exception stack frame — forensic detail identifying exactly which selector and which table were implicated, so kernel fault-handling code (and human debuggers staring at a crash dump) can pinpoint the precise selector load or memory reference that caused it.

FieldMeaning
EXTSet if the exception was provoked by an event external to the currently executing instruction stream — e.g. delivery of a hardware interrupt through a bad gate — rather than directly by the instruction itself.
IDTSet if the selector index in this error code refers to a gate descriptor inside the IDT rather than the GDT/LDT — relevant when the fault happened during interrupt or exception delivery itself.
TIMeaningful only when IDT is clear — 0 means the implicated index is a GDT index, 1 means it's an LDT index. Mirrors the exact same TI bit from the original segment selector.
Selector IndexThe 13-bit index of the specific selector involved. Read this out of the trap frame and you know precisely which GDT/LDT slot the CPU was using when it faulted.

If the error code is exactly zero, the fault generally wasn't caused by a specific selector reference at all — it points to some other flavor of general-protection condition, such as attempting a privileged instruction outside Ring 0.

🔍 Why Debuggers Actually Print This
A kernel panic dump or a human debugging a fault doesn't have to guess "something about segments broke." Decode the error code and you get a sentence: "selector index 5, GDT, not from interrupt delivery, not external." That's the difference between grepping through every selector load in a crash and going straight to the one that mattered.

Decoding One in the Other Direction

Given a raw error code, the decode runs just as mechanically as any of the formulas above. Suppose a crash dump shows a #GP with error code 0x4B.

error code0x4B = 75 = 0b01001011
EXT = bit0 = 1  ·  IDT = bit1 = 1  ·  TI = bit2 = irrelevant (IDT is set)  ·  index = 75 >> 3 = 9

Reading left to right: the implicated table is the IDT (not the GDT/LDT), specifically gate 9, and the fault was provoked by an external event — a hardware interrupt arrived and tried to use IDT slot 9, and whatever it found there wasn't a valid, sufficiently-privileged gate. Same four fields every time; only the bit pattern changes.

08 — Now You Try: Reading a Real Fault

A Worked Walkthrough

Here's a fabricated but realistic crash log. Walk it through the same way a kernel developer would, using nothing but the formula and the error-code layout above.

🧾 The Log
CPL at fault = 3 · faulting instruction mov ds, ax where ax = 0x002B · the GDT has 12 entries (limit = 0x5F) · descriptor at the resolved index is a data segment with DPL = 0.
  1. Decode the selector0x002B = 43 decimal = binary 00101011. Index = 43 >> 3 = 5. TI = bit 2 = 0 (GDT). RPL = low 2 bits = 3.
  2. Validate the index against the limit12 entries means valid indices run 0–11, limit = 0x5F = 95 bytes covers up to index 11. Index 5 is well within range — no out-of-bounds fault here.
  3. Fetch the descriptor's DPLGiven as DPL = 0 in the log — a kernel-only data segment.
  4. Apply the ruleCPL = 3, RPL = 3 (both already at user level here — no deliberate lowering trick involved). MAX(3, 3) = 3. Is 3 ≤ 0? No.
  5. ConcludeOrdinary privilege violation — user-mode code tried to load a kernel-only segment into ds. Predicted error code: index 5, TI 0 (GDT), IDT 0, EXT 0 → (5 << 3) = 0x28.
✏️ Try It Yourself
A different fault: CPL = 3 (genuine — this is ordinary user code), and it loads fs with a selector where it has deliberately set RPL = 0, hoping that claiming top privilege on the selector will let it slip past the check. The target descriptor, at a valid GDT index, has DPL = 0. Does this access succeed? Compute MAX(CPL, RPL) yourself before reading on.
CPL3 RPL (forged)0 target DPL0
MAX(3, 0) = 3   →   is 3 ≤ 0? No.
✕ General Protection Fault — the cheat does not work

Exactly as the callout back in section one promised: forging a lower RPL cannot rescue an access when the real CPL is the one that's actually too weak. MAX always takes the worse of the two, and CPL — which the running code cannot fake — sets the floor.

✏️ One More: Decode the Error Code, Not Just the Verdict
Back in section 4, loading a null selector into ss faulted unconditionally. Suppose that fault's trap frame shows error code 0x0000. Does a zero error code mean nothing was implicated — or does it mean something else here?

Decode it the same way: index = 0 >> 3 = 0, TI = 0, IDT = 0, EXT = 0. The error code genuinely is zero — but not because no selector was implicated. It's because the implicated selector is index 0 (the null selector itself), and index 0 happens to encode as all-zero bits in every field. Reading an error code always requires knowing the faulting instruction too; the two together, not the error code alone, tell the full story. That's exactly why the format in section 7 exists — to be read alongside the instruction that triggered it, not in isolation.

09 — Quick Reference

Glossary & Key Terms

General Protection Fault (#GP)
Exception vector 13. Raised whenever a segmentation-related legality or privilege check fails — the CPU's catch-all name for a whole family of distinct checks.
CPL (Current Privilege Level)
The CPU's live, actual privilege level right now, carried inside cs. Cannot be forged by ordinary code — it's set by which code segment is genuinely executing.
RPL (Requestor Privilege Level)
A 2-bit field inside a selector, stating the privilege level a specific access is claiming to happen at — independently settable, per access, by whoever built the selector.
DPL (Descriptor Privilege Level)
The minimum privilege required to access a given segment, fixed inside its descriptor.
MAX(CPL, RPL) ≤ DPL
The actual data-segment privilege check — the numerically worse (less privileged) of CPL and RPL must still satisfy the target's DPL.
Confused Deputy Problem
Term coined by Norm Hardy (1988) for a highly-privileged program tricked into misusing its own authority on behalf of a less-privileged caller — exactly what RPL, used deliberately, defends against.
Null Selector
index = 0, TI = 0. Legal to load into ds/es/fs/gs (faults only on later use); illegal to load into ss at all (faults immediately).
Type Mismatch
Loading a segmentation register with a descriptor of the wrong kind — e.g. a system-segment descriptor into ds, or a data descriptor into cs. Faults independently of any privilege check.
GPF Error Code
32-bit value pushed onto the trap frame on #GP: EXT, IDT, and TI bits plus a 13-bit selector index, identifying exactly which selector/table caused the fault.
ARPL (Adjust RPL Field)
x86 instruction that raises a selector's RPL to at least a given value — historically used by kernel code to safely enforce reduced privilege before touching a caller-supplied selector.
