You already know the GDT as a settled, working structure — base, limit, 8-byte descriptors, a clean lookup formula. This page is about the one moment none of that was true yet: the first few hundred microseconds after power-on, when the table doesn't exist, the CPU is still pretending it's 1978, and a handful of real assembly instructions have to build the table and throw the switch, once, with nothing to fall back on if they get it wrong.

01 — Set the Scene

Powering On Into 1978

Here is a fact that surprises almost everyone the first time they hear it stated plainly: when you press the power button on a modern x86 machine — a 2026 laptop with a chip built on a process node its own designers can barely see under a light microscope — the CPU does not boot up modern. It boots up as an Intel 8086. Specifically, it resets into 16-bit real mode: the same primitive addressing scheme the companion piece on memory addressing history describes for the original 1978 chip — segment × 16 + offset, a 20-bit address bus capping out at 1MB of addressable memory, and critically, no protection whatsoever. No privilege levels. No rings. No concept of "this code shouldn't be allowed to touch that memory." Any instruction can address any byte.

Why would a chip this advanced deliberately cripple itself on every single boot? Backward compatibility, stretched across nearly five decades. Every x86 CPU since the 80286 has had to guarantee that software written for the original 8086 could still run unmodified — and the only way to make that promise ironclad is to make it the CPU's default, reset-time state, not an opt-in mode a modern OS remembers to request. So the reset vector always lands in real mode, full stop, no exceptions, no matter how many billions of transistors are sitting idle around it.

Real mode addressing, in full Physical Address = (Segment × 16) + Offset The entire addressing scheme available at the reset vector. No descriptors, no lookup table, no privilege check — just a shift and an add.

This is the mode your machine's firmware — legacy BIOS, or the earliest bytes of a UEFI implementation's compatibility path — wakes up in. It's the mode the very first bytes of a classic bootloader, loaded from disk sector zero into memory address 0x7C00, execute in. Nothing about protected mode exists yet. There is no GDT. There is no gdtr pointing at anything meaningful. If an instruction right now tried to use a segment selector the way the GDT article described — index, TI bit, RPL — the CPU wouldn't know what any of those words mean. It isn't that mode yet.

What about UEFI specifically? Modern UEFI firmware actually performs a version of this exact real-mode-to-protected/long-mode transition itself, very early, invisibly, before a traditional OS bootloader ever gets control — which is part of why UEFI systems boot faster. But the underlying requirement doesn't change: some piece of code, at some point after reset, still has to build a GDT and flip the switch by hand. This page follows the classic, explicit version of that story because it's the clearest place to see every instruction doing real work.

Put the two modes side by side and the gap is stark — this is genuinely the difference between the state the CPU wakes up in, and the state everything else in this series assumes it's already in:

🕰️ The Uncomfortable Truth
Every time this machine boots, for a brief stretch measured in microseconds, it is — architecturally, not metaphorically — running as an unprotected 8086. Everything from this series about rings, descriptors, and privilege checks starts its existence after that stretch ends.
02 — The Bootstrapping Problem

The Chicken and the Egg

Here's the puzzle that makes this whole sequence necessary, and it's worth sitting with because it's a genuine logical trap, not just a formality. Protected mode's entire definition depends on the GDT. The moment the CPU is told "you are now in protected mode," every segment register — cs, ds, es, ss, and the rest — is redefined to hold not a raw base address the old way, but a selector: an index into a Segment Descriptor Table. From that instant forward, the CPU refuses to treat those registers any other way.

So ask the obvious question: what happens if protected mode gets switched on and the GDT the selectors are supposed to point into simply doesn't exist yet? Nothing good. A selector pointing at descriptor slot 2 in a table that has zero entries isn't a minor inconvenience — it's a reference to memory nobody defined the meaning of. The CPU cannot function correctly, cannot fetch its next instruction reliably, cannot do anything protected-mode-shaped, with zero descriptors on hand.

Which means the order of operations is forced, and it only works one way: the GDT must be built and locatable before the CPU is ever told to enter protected mode — not simultaneously, not just after, before. And since nothing except real-mode code is running at this point, the GDT has to be built by hand, in real mode, using real-mode-style flat addressing, sitting in memory the still-primitive CPU can reach.

💡 The Aha, Early
A bootloader doesn't ask the operating system for a GDT. There is no operating system yet — that's the entire point of a bootloader. It has to author the table itself, by hand, in real mode, as raw bytes sitting at a fixed memory address, and only then dare to flip the switch that makes that table load-bearing.

In practice this hand-built table is almost always the smallest table that could possibly work: three descriptors. Not because three happens to be a nice round number, but because three is the minimum the architecture will actually accept.

03 — Building the Table by Hand

The Minimal GDT: Three Slots

Recall from the main GDT article that descriptor slot 0 is a mandatory null descriptor — the architecture requires it to exist and requires the CPU to fault if anything ever tries to actually use it as a live segment. A bootloader's hand-built GDT respects that rule from the first byte. Beyond the null descriptor, the smallest useful table adds exactly two more entries: one flat code segment and one flat data segment, both with Base 0x00000000 and a Limit spanning the full 4GB range, both at ring 0, since nothing resembling user mode exists yet either.

IndexSelectorDescriptorBaseLimitPurpose
0never usedNull descriptor——Required by the architecture; touching it as a real segment faults on purpose.
10x08Flat code segment0x000000000xFFFFFFFFExecutable, readable, ring 0. Covers the entire address space.
20x10Flat data segment0x000000000xFFFFFFFFWritable, ring 0. Also covers the entire address space.

Selector values come straight from the GDT lookup formula in the main article: index × 8. Index 1 → 0x08. Index 2 → 0x10. No coincidence — it's the same arithmetic, just running for the very first time.

As raw bytes, sitting in memory, that table looks like this — genuinely the kind of thing you'd find, byte for byte, near the top of a real "hello world" bootloader:

hand-built gdt, as it sits in memory; index 0 — the mandatory null descriptor: 8 zero bytes
gdt_start:
gdt_null:      dq 0x0000000000000000

; index 1 — flat code segment, base 0, limit 0xFFFFF (×4K granularity)
gdt_code:      dw 0xFFFF            ; limit bits 0-15
               dw 0x0000            ; base bits 0-15
               db 0x00              ; base bits 16-23
               db 10011010b         ; access: present,ring0,code,readable
               db 11001111b         ; 4K gran, 32-bit, limit bits 16-19
               db 0x00              ; base bits 24-31

; index 2 — flat data segment, otherwise identical
gdt_data:      dw 0xFFFF
               dw 0x0000
               db 0x00
               db 10010010b         ; access: present,ring0,data,writable
               db 11001111b
               db 0x00
gdt_end:

; the 6-byte "pseudo-descriptor" lgdt actually loads: limit, then base
gdt_descriptor:
    dw gdt_end - gdt_start - 1   ; size in bytes, minus 1
    dd gdt_start                 ; linear address of the table
Only 24 bytes of actual table. Three descriptors × 8 bytes each. This is, quite literally, the entire protection apparatus the CPU needs to hear about before it's willing to leave 1978 behind — everything else (paging, user-mode segments, TSS descriptors, an LDT) gets added later, by the kernel, once it's actually running.
04 — Reading the Raw Bytes

What 10011010b Actually Says

It's worth slowing down on those two binary literals from the code block above — 10011010b and 11001111b — because they're not arbitrary magic numbers. Every single bit is a deliberate answer to a question the CPU will ask about that segment on every access. Reading them bit by bit is genuinely the fastest way to understand what a Segment Descriptor's Type/DPL/flags fields from the main GDT article actually look like as real, physical bits.

Bit(s)NameCode seg valueData seg valueMeaning
7Present11Segment is valid and in memory — a 0 here faults on use.
6–5DPL0000Descriptor Privilege Level — ring 0, since nothing else exists yet.
4S (descriptor type)111 = a normal code/data segment, not a system segment like a TSS.
3Executable101 = code segment, 0 = data segment. This is the bit that tells them apart.
2Direction / Conforming00For code: not conforming. For data: segment grows up, not down.
1Readable / Writable11Code: readable (not just executable). Data: writable.
0Accessed00Set to 1 by the CPU the first time the segment is actually used.

The second byte, 11001111b, is a 4-bit flags nibble stacked on top of the high 4 bits of the 20-bit Limit field:

Bit(s)NameValueMeaning
7G (Granularity)1Limit is counted in 4KB pages, not raw bytes — how a 20-bit limit field covers a full 4GB.
6D/B (default size)11 = 32-bit protected mode segment (vs. 0 for a 16-bit one).
5L (long mode)0Reserved for 64-bit code segments — irrelevant here, we're only reaching protected mode.
4AVL0Free for OS use; ignored by the CPU entirely.
3–0Limit bits 16–191111Combined with the earlier 0xFFFF, gives a 20-bit limit of 0xFFFFF — ×4K granularity = 4GB, the whole address space.
💡 Why Granularity Matters Here
A raw 20-bit Limit field can only count up to 0xFFFFF — about 1MB — one byte at a time. Setting the G bit changes the units to 4KB pages instead, so that same 20-bit field can describe a limit up to 4GB. Without it, a "flat" segment covering all of memory literally couldn't be expressed.
05 — The Sequence

Five Instructions That Change Everything

With the table built and sitting at a known address, the actual mode switch is almost anticlimactically short. Here is the real sequence, in order, exactly as it appears — give or take label names — in essentially every x86 bootloader ever written.

  1. 1. Disable interruptsAn interrupt firing mid-transition would try to use the current (soon-to-be-invalid) interrupt handling setup — real mode's Interrupt Vector Table, which protected mode doesn't use the same way. Nothing is ready to handle an interrupt safely across this boundary, so the CPU is told, bluntly, to stop listening for a moment.
  2. 2. Load the GDT's address into gdtrThe lgdt instruction — a privileged instruction, but real mode has no privilege concept yet to stop it — reads the 6-byte pseudo-descriptor and populates gdtr with the table's base and limit. This is the moment the table stops being "just some bytes in memory" and becomes the thing the CPU will actually consult.
  3. 3. Set the Protection Enable bit in CR0Bit 0 of the CR0 control register is literally named PE. Reading CR0 into a general register, OR-ing in 0x1, and writing it back is the single, literal bit flip that turns protected mode on. Not a metaphor — one bit, one instruction sequence, and the CPU's fundamental operating mode changes underneath it.
  4. 4. Immediately perform a far jumpNot "eventually" — immediately, the very next instruction. This is non-negotiable, and the next section explains exactly why in mechanical detail.
  5. 5. Reload the remaining segment registersLanding inside the far jump's target, cs is now valid — the jump itself loaded it. But ds, es, fs, gs, and ss still hold whatever real-mode segment values they had a moment ago, which are now meaningless garbage under protected-mode interpretation. Each gets explicitly reloaded with the flat data selector before anything touches memory through them.

As actual code, steps 1 through 4 look like this:

the switch itself — 16-bit real mode codecli                          ; (1) mask interrupts — nothing downstream
                             ;     of this is safe to interrupt yet

lgdt [gdt_descriptor]         ; (2) gdtr now points at our 3-entry table

mov eax, cr0               ; (3) read CR0 into a general register...
or  eax, 0x1              ;     ...set bit 0, the PE bit...
mov cr0, eax              ;     ...write it back. Protected mode
                             ;     is now ON, this instant.

jmp 0x08:protected_start     ; (4) FAR JUMP — reloads cs with a real
                             ;     selector, flushes stale pipeline state

And landing on the other side of that jump, in genuinely 32-bit protected-mode code now, step 5 finishes the job:

the landing — 32-bit protected mode code[BITS 32]
protected_start:
    mov ax, 0x10       ; (5) selector for gdt_data (index 2 × 8)
    mov ds, ax
    mov es, ax
    mov fs, ax
    mov gs, ax
    mov ss, ax
    mov esp, 0x90000  ; a real, sane 32-bit protected-mode stack
Step 3, isolated CR0 ← CR0 | 0x00000001 One bit, bit 0, named PE. Everything else in this entire series exists downstream of this single write succeeding.
06 — The Instruction Everyone Asks About

Why a Far Jump, Specifically?

This is the step that trips people up, because "just jump to the next instruction" sounds like it shouldn't need a special kind of jump at all. Here's the concrete mechanical reason it does.

Modern x86 CPUs — even ones running this ancient boot dance — fetch and partially decode instructions ahead of where execution currently is, as part of a pipeline. At the moment CR0's PE bit flips, the CPU's pipeline may still be holding onto instructions it fetched and started decoding under the old real-mode assumptions — in particular, a cached, real-mode-flavored notion of what cs means and how addresses built from it should be interpreted. A plain near jump, or simply falling through to the next instruction, doesn't force any of that stale state to be thrown out.

A far jump — one that specifies both a new segment selector and an offset, like jmp 0x08:protected_start — is different by definition. Loading cs with a genuinely new selector is exactly the kind of event the architecture guarantees will flush the instruction pipeline and force a fresh fetch, this time correctly interpreting 0x08 as a protected-mode selector — an index into the GDT, RPL 0, TI 0 — rather than as an old-style real-mode segment base. That's the whole reason for choosing this specific instruction at this specific moment: it isn't stylistic, it's the one operation guaranteed to reload cs and clear stale pipeline state in the same breath.

❌ Without the far jump

Execution could continue momentarily on pre-decoded instructions that still assume real-mode segment semantics — an inconsistent, unpredictable window where PE=1 in CR0 but cs hasn't been meaningfully reinterpreted yet.

✅ With the far jump

cs is forcibly reloaded from the GDT as a real protected-mode selector, the pipeline is flushed, and execution resumes cleanly at protected_start with the CPU fully, consistently in protected mode.
⚠️ This Is Why Every Bootloader Does This
Skim the boot code of GRUB, a minimal "hello world" OS tutorial, or the Linux kernel's own early boot/ assembly, and you will find this exact pattern — set PE, then far jump, no instructions in between — because it isn't a stylistic convention someone picked. It's the one sequence the architecture actually requires to land safely in protected mode.
07 — What Happens If It's Wrong

The Failure Mode: Triple Faults

One detail sharpens why this sequence has to be exactly right: cli only masks maskable interrupts — external events like a keyboard press or a timer tick. It does nothing to stop a fault, the CPU's own reaction to something like a malformed descriptor, a bad limit, or an invalid opcode. Faults aren't optional; the CPU raises them regardless of the interrupt flag.

So what happens if the hand-built GDT has a mistake in it — say, the access byte is wrong, or lgdt pointed at the wrong address — and a fault fires the instant protected mode goes live? Normally a fault is handled by consulting a table of handlers: the real-mode Interrupt Vector Table, or, in protected mode, the Interrupt Descriptor Table (IDT). But at this exact moment in boot, neither is in a usable state for a protected-mode fault — the IDT hasn't been built yet either; that's a separate piece of setup this page hasn't even covered.

When the CPU tries to handle a fault and can't even locate a valid handler for it, it doesn't just give up quietly — it raises a second fault (a double fault) trying to report the first one. And if that also can't be handled — which, at this point in boot, it can't — the CPU gives up entirely and does something drastic: a triple fault, which on real hardware simply resets the machine. No blue screen, no message, no log. The computer just reboots, instantly, and you're staring at the BIOS splash screen again wondering what happened.

⚠️ The Debugging Reality
Anyone who has hand-written a bootloader has hit this: one wrong byte in the GDT, one missing far jump, and the machine doesn't print an error — it just silently restarts, over and over, in a fraction of a second, with nothing to read. This is exactly why hobbyist OS developers lean so heavily on emulators like QEMU or Bochs for this stage: those tools can pause on a triple fault and dump the CPU's exact register state, instead of just resetting like real silicon does.
So why is cli still step one, if it can't stop faults? Because it still matters for the class of interrupt it can stop. A timer or keyboard interrupt firing between lgdt and the far jump would try to use whatever interrupt-handling state currently exists — and since that state is also about to become invalid, masking it removes one entire category of things that could go wrong during a window where the CPU is already in a fragile, half-transitioned state.

09 — Two Practical Wrinkles

A20, and the Road to Long Mode

Two things worth knowing exist right around this same moment in a real bootloader, even though neither is really about the GDT itself.

The A20 line. The original 8086's 20-bit address bus meant addresses naturally wrapped around at 1MB — some early software came to quietly depend on that wraparound as a feature. Later chips with wider address buses had to add a gate on address line 20 (the "A20 line") that, by default, still forces this old wraparound behavior for compatibility. Since protected mode wants to actually use memory above 1MB, a bootloader typically has to explicitly enable the A20 line — commonly through the keyboard controller or BIOS interrupt 0x15 — as a small, separate housekeeping step near this same point in the boot sequence. It's a compatibility quirk from the same 1978-era lineage as real mode itself, not a GDT concept — full detail belongs in the memory-addressing history piece, not here.

The second wrinkle is bigger: everything on this page gets a CPU into 32-bit protected mode. Getting from there into 64-bit long mode — where modern 64-bit operating systems actually run — is a further, separate transition. It requires building an additional set of in-memory structures (paging tables, since long mode cannot be entered without paging enabled), setting the PAE bit, and setting the LME bit in a model-specific register called EFER before finally enabling paging itself. That's a real, meaty topic on its own — worth flagging here so the boundary is clear, but genuinely out of scope for this page.

🧠 Why Mention This At All
Because it's easy to assume "protected mode" and "the mode my 64-bit OS runs in" are the same thing. They're not — protected mode is a real, complete, load-bearing stop along the way, not a rounding error on the path to long mode. The GDT you've been studying this whole series is protected mode's structure, built and used exactly as described here, whether or not a long-mode transition follows it moments later.
10 — Not Hypothetical

This Exact Sequence, In Real Code

None of this is a teaching simplification invented for this page. The same cli → lgdt → CR0.PE → far jump shape shows up, largely unchanged, across nearly every real piece of x86 boot software in existence.

GRUB2 (i386-pc)bootloader
GRUB's real-mode stage builds its own small hand-rolled GDT and performs this exact transition before it ever loads a kernel — visible in its boot.S/diskboot.S assembly sources.
Linux kernelarch/x86/boot
The kernel's own early boot code — pmode.c and pmjump.S — calls go_to_protected_mode(), which does this same dance before the "real" kernel entry point ever runs.
coreboot / SeaBIOSfirmware
Open-source firmware projects perform their own real-mode-to-protected-mode transitions early during POST, often more than once across handoffs between firmware stages.
OSDev.org tutorialsteaching
Nearly every "write your own bootloader" tutorial in the hobbyist OS community walks through precisely these five steps, usually as the very first real milestone.
11 — The Point of All This

Not Abstract. Real. Once.

It's easy, reading about selectors, descriptor privilege levels, and lookup arithmetic, to start treating the GDT as a piece of pure theory — a diagram, a formula, an idea the hardware happens to implement. It isn't. It is a 24-byte structure, built by hand out of literal bytes, sitting at a fixed address in ordinary RAM, loaded by one real instruction (lgdt), activated by one real bit flip (cr0's PE bit), and made to stick by one real far jump — a sequence you could type into a text editor, assemble, and boot on real hardware this afternoon.

And it runs once. Not once per process, not once per context switch — once, in the first fraction of a second after this specific machine powered on, before an operating system, before a scheduler, before a single process control block existed. Everything the rest of this series takes for granted — that cs holds a meaningful selector, that a descriptor privilege level means something, that Ring 0 and Ring 3 are real and enforced — only exists because that handful of instructions ran, in order, without a mistake, that one time.

💡 The Aha Moment
The GDT isn't a concept the CPU was born understanding. It's a structure a bootloader teaches the CPU to trust, in real time, by force — and the moment that teaching succeeds is the exact moment this entire series' subject matter starts being true.
12 — Quick Reference

Glossary & Key Terms

Real Mode
The 16-bit, unprotected addressing mode (segment×16+offset, 1MB max) every x86 CPU resets into, regardless of how modern the chip actually is.
Protected Mode
The 32-bit mode where segment registers hold selectors indexing into a GDT/LDT, and privilege levels are enforced in hardware.
CR0
A control register holding CPU-mode flags; bit 0 is PE (Protection Enable) — the literal bit that turns protected mode on.
lgdt
Privileged instruction that loads gdtr from a 6-byte pseudo-descriptor (2-byte limit + 4-byte base) in memory.
Far Jump
A jump that reloads cs with a new selector and an offset in one instruction — required right after setting PE to flush stale pipeline state.
Null Descriptor
The mandatory, unusable GDT entry at index 0; using it as a live segment deliberately faults.
Flat Segment
A descriptor with Base 0x00000000 and a limit spanning the full address range — the entire "segment" is the whole address space.
A20 Line
A gate on the 21st physical address line, defaulting to forcing old 8086-style 1MB wraparound; typically enabled by the bootloader around this same point.
Long Mode
The 64-bit mode reachable from protected mode only after setting up paging structures, PAE, and the LME bit in EFER — a separate transition.
Reset Vector
The fixed memory address the CPU always begins fetching instructions from immediately after power-on, always in real mode.
Access Byte
The descriptor byte encoding Present, DPL, S, Executable, and Readable/Writable — e.g. 10011010b for a flat ring-0 code segment.
Triple Fault
A fault the CPU cannot deliver even after a double fault, forcing an immediate hardware reset — the classic outcome of a broken GDT setup.
IDT
The Interrupt Descriptor Table — protected mode's table of fault/interrupt handlers, not yet built at the moment this page describes.
