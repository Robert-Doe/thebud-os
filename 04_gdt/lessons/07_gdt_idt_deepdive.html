The IDT: The GDT's
Cousin for Traps

You already know the GDT: an array of 8-byte Segment Descriptors, found through gdtr, indexed by a selector's index field. You also already know there are three doors into the kernel — syscall, exception, interrupt — and that a trap frame gets pushed the instant any of them fires. What you don't know yet is the missing link: how the CPU decides, in the space of a few nanoseconds, which exact function to run once a trap fires. That's the Interrupt Descriptor Table's entire job, and it turns out to be the GDT's structural twin.

00 — Where We Left Off

Two Loose Threads, Left Dangling On Purpose

Two earlier pieces of this series each left you with an unfinished sentence. The GDT article told you, almost in passing, that the CPU consults a whole separate table to dispatch interrupts — "more on that elsewhere." The PCB/threads article told you there are three doors into Ring 0 — system call, exception, hardware interrupt — and that the instant any of them fires, the CPU pushes a small trap frame onto the kernel stack and jumps into a handler. It never told you how the CPU picks the handler. It just said a handler runs.

Both loose threads tie off in the same place. That place is the Interrupt Descriptor Table (IDT) — and once you see it, you'll realize you already know 90% of how it works, because you learned the shape of this exact mechanism when you learned the GDT.

📎 Quick Refresher, In One Line Each
GDT: array of 8-byte Segment Descriptors, base found via gdtr, indexed as gdtr.base + index × 8. Trap frame: the minimal PC/flags/registers bundle the CPU pushes to the kernel stack on every trip into Ring 0, regardless of which of the three doors was used. Keep both in your other hand — you'll need them in a minute.
01 — The Spine of This Whole Page

The Exact Same Shape, One Field Different

Here's the parallel, stated as bluntly as possible, because everything below is just this sentence unpacked in more and more detail:

📖 GDT answers

"Which memory segment does this selector mean?" Found via gdtr. Indexed by a selector's index field — an arbitrary slot number chosen by whoever set up that segment.

📟 IDT answers

"Which handler function does this interrupt/exception/syscall number mean?" Found via idtr — gdtr's sibling register. Indexed directly by a small integer called a vector number, 0–255.
💡 The Aha Moment
A GDT selector's index is a drawer number in the segment catalog — the CPU doesn't know or care what's in drawer 15 until it opens it. A vector number is a drawer number in an entirely different catalog: the CPU doesn't know or care what code runs for vector 14 until it opens that drawer. Same filing-cabinet idea, same "base register + index × entry-size" arithmetic, completely different cabinet, completely different thing being filed.

Think of the IDT as an emergency-services switchboard. You don't dial the fire department's direct line, the ambulance's direct line, and the police direct line separately — you dial one number, 911, and the switchboard looks up exactly which responder to dispatch based on what you tell it. A vector number is the "911" the CPU dials. The IDT is the switchboard. The gate descriptor it looks up is the dispatch slip telling the CPU precisely which responder — which handler function — to send.

02 — The Index Into This Table

What Exactly Is a Vector Number?

A vector number is nothing mystical — it's just an integer from 0 to 255, because the IDT has exactly 256 possible slots. But unlike a GDT index (which the kernel assigns however it likes), the low end of vector-number space is not up for grabs: Intel reserved it, by hardware convention, for a fixed set of CPU-defined conditions.

Vectors 0 – 31Intel-reserved
CPU-defined exceptions — the same on every x86 chip, not configurable by the OS. Faults, traps, and aborts the hardware itself decides to raise while executing an instruction.
Vectors 32 – 255OS/hardware-assignable
Free for the operating system to wire up however it wants — hardware interrupts (timer, keyboard, disk, network card) and software-triggered interrupts (like the legacy int 0x80 Linux syscall vector).

Why 32? The legacy 8259 PIC (Programmable Interrupt Controller) originally fired hardware IRQ0–IRQ15 straight onto vectors 0–15 — which collided head-on with Intel's own exception vectors once Intel later reserved 0–31 for itself. The now-standard fix, which every mainstream x86 OS performs at boot, is to remap the PIC (or configure the APIC) so hardware IRQs land on vectors 32 and up instead, safely clear of the reserved range.

Where the Word "Vector" Actually Comes From

It's not a marketing term. Back on the original 8086, running purely in real mode with no protection at all, the CPU didn't have an IDT — it had an Interrupt Vector Table (IVT), hard-wired to always live at physical address 0. Each of its 256 entries was literally a 4-byte far pointer — a vector, in the mathematical sense of "a value that points somewhere" — straight to an interrupt handler, no descriptor, no privilege check, no protection whatsoever. The IDT is the protected-mode descendant of that idea: same 256-slot indexing scheme, same name for the index, but every entry upgraded from a bare pointer into a full gate descriptor with a selector, a type, and a DPL standing guard in front of it.

Who Actually Writes These 256 Entries?

The IDT doesn't arrive pre-filled — it's just reserved memory until the kernel populates it, early in boot, before interrupts are ever turned on. Linux does this in its trap-and-interrupt initialization path (historically trap_init(), walking through arch/x86/kernel/idt.c today), calling helper functions with names like set_intr_gate() and set_system_intr_gate() once per vector — one call to wire vector 14 to do_page_fault, one to wire vector 0 to the divide-error handler, one (with DPL forced to 3) to wire vector 0x80 to the legacy syscall entry point, and so on, all before lidt ever runs to make the table live.

One Layer Below the Vector: Who Assigns Hardware Interrupts a Number At All?

The "PIC remap" sidenote above skated past a real question: how does a physical keyboard controller end up tied to vector 33 specifically, rather than any other free slot? That's the job of the interrupt controller sitting between devices and the CPU — and which controller you have changes how that assignment happens.

8259 PIClegacy, single-core era
A pair of chained chips offering 15 usable interrupt lines, each remapped to one fixed vector by the OS at boot. Simple, but has no real concept of "which CPU core should handle this" — awkward on multiprocessor hardware.
APIC (Local + I/O)modern standard
The I/O APIC routes external device lines to a chosen vector and a chosen CPU core's Local APIC, which is what actually delivers the interrupt into that core's IDT dispatch. This is also how cores signal each other directly — an Inter-Processor Interrupt (IPI), the mechanism a scheduler uses to force a different core to reschedule right now — itself just another vector dispatched through that core's IDT.
03 — Finding the Table Itself

The idtr Register

Exactly like the GDT, the IDT is just an array sitting somewhere in ordinary kernel RAM — and exactly like the GDT, the CPU needs a dedicated register to know where that array starts and how big it is. That register is idtr, and it is deliberately gdtr's sibling in every structural sense: same job, same privilege requirements, different table.

What idtr actually stores idtr = { base address of the IDT in RAM, size of the IDT in bytes } Loaded once, typically at boot, via the privileged lidt instruction — the direct counterpart to lgdt for the GDT.
⚠️ Why idtr Is Locked Down Exactly Like gdtr
If user-mode code could repoint idtr at memory of its own choosing, it could fabricate a gate descriptor for, say, vector 14 (page fault) that jumps straight into attacker-controlled code running at Ring 0 — the instant any process anywhere on the machine faults. lidt is refused outside Ring 0 for the identical silicon-level reason lgdt is: whoever controls the dispatch table controls what "the kernel" even means.

There's an even more literal way in which gdtr and idtr are twins: the memory operand lgdt and lidt each read from is the exact same shape of structure, called a pseudo-descriptor. Both instructions expect a tiny packed record in RAM — not the table itself, just directions to it — and both interpret that record identically.

FieldSizeMeaning
Limit2 bytesSize of the table in bytes, minus 1 — so 256 gate descriptors × 16 bytes gives a limit of 4095
Base Address8 bytes (64-bit mode) / 4 bytes (32-bit mode)The linear address of the table's very first byte

Load a 10-byte pseudo-descriptor with lidt, and the CPU copies those two fields straight into the live idtr register. Load an identically-shaped pseudo-descriptor with lgdt, and it lands in gdtr instead. Same packing format, same instruction family, same privilege requirement — only the destination register differs.

04 — What's Actually Sitting In Each Slot

Gate Descriptors, Not Segment Descriptors

Here's the one place the parallel bends slightly, and it's worth being precise about it. A GDT slot holds a Segment Descriptor — a description of a chunk of memory. An IDT slot holds something with a different name and a different job: a Gate Descriptor — a description of exactly one handler entry point, plus the rules for who's allowed to walk through that gate.

Gate descriptors are 8 bytes wide in 32-bit mode — the same size as a Segment Descriptor, pure coincidence of history — but 16 bytes wide in 64-bit (long) mode, because a 64-bit handler address needs more room than an 8-byte slot can hold. They come in three flavors:

Interrupt GateIF cleared
Jumps to the handler and automatically clears the interrupt flag (IF) on entry — the CPU won't be interrupted again mid-handler unless that handler explicitly re-enables interrupts itself. The default choice for most hardware interrupt and exception handlers, where you don't want a second interrupt landing on top of the first before it's been dealt with.
Trap GateIF untouched
Functionally almost identical — same selector+offset jump — but does not auto-clear IF. Interrupts stay enabled through the handler. More typically used for things like debug exceptions, where keeping interrupts live during the handler is actually desirable rather than dangerous.
Task Gatemostly obsolete
An older x86 mechanism that triggers a full hardware task switch (via a Task State Segment) instead of a plain jump. Almost no modern OS uses it — software-managed context switching, the kind covered in the PCB article, made this hardware feature redundant.
📌 Why the IF-Clearing Choice Actually Matters
Picture a hardware interrupt handler that didn't clear IF on entry, servicing a device that keeps re-firing the same interrupt line before the handler finishes. Without the automatic clear, a second copy of the same handler could start before the first one returns — stacking up recursively, corrupting whatever shared state the handler touches, potentially never unwinding. That is exactly the failure mode Interrupt Gates exist to prevent by default. Trap Gates deliberately opt back into the risk only where it's actually safe — a debug exception handler, for instance, generally isn't going to re-trigger itself in a tight loop the way a busy device interrupt could.

Whichever flavor, every gate descriptor holds the same three load-bearing pieces of information:

Segment Selector
e.g. 0x08
Points, via the GDT (yes — back through the very table from the previous article), at the code segment the handler lives in.
Offset
e.g. 0xffffffff81234560
The handler's actual entry-point address within that code segment — split across a few sub-fields to make room for a full 64-bit address.
DPL
0, 1, 2, or 3
Whether user-mode code is even allowed to voluntarily trigger this vector via a software interrupt instruction — the single field that decides who's allowed to dial this particular extension.
🧠 Why DPL Lives on the Gate, Not Just the Handler
A hardware interrupt or CPU exception doesn't ask permission — the timer fires, a page fault happens, and the CPU dispatches through the gate regardless of DPL. DPL only matters for software-triggered vectors, raised deliberately by an int n instruction from user code. There, DPL is the gatekeeper: attempt int 14 from Ring 3 against a DPL-0 gate, and you get a general protection fault instead of a page-fault handler running on demand. This is precisely why one specific vector — the legacy Linux syscall gate — is set up differently, which the syscall section below covers in full.

What's Actually Packed Into Those 16 Bytes

The "gate-field" boxes above are the conceptual version. The literal 64-bit-mode bit layout is a little more cramped, because a 64-bit offset has to be split into pieces to fit around the older, narrower fields that history left in place:

What's an IST? The Interrupt Stack Table is a small x86-64 feature that lets a specific gate force the CPU onto one of a handful of pre-designated, always-known-good kernel stacks, instead of whatever stack happens to be live. It exists for exactly the vectors where you can't trust the current stack pointer at all — a double fault or an NMI arriving in the middle of an already-corrupted stack is precisely the scenario IST was built for. Most gates leave IST at 0 and use ordinary stack-switch rules; only a handful of the scariest vectors bother setting it.
05 — The Arithmetic

Turning a Vector Into a Real Address

And here's where the GDT parallel stops being a metaphor and becomes literally the same formula, just with different numbers plugged in. Every gate descriptor is a fixed size, so finding gate number vector is, again, plain array indexing.

The IDT lookup formula (64-bit mode) Gate Descriptor Address = idtr.base + (vector × 16) In 32-bit mode this is idtr.base + (vector × 8) — same shape, smaller slot, because a 32-bit offset fits in less room.

Set that next to the formula from the GDT article and the family resemblance is impossible to miss:

Side by side Descriptor Address = gdtr.base + (selector.index × 8) Gate Address = idtr.base + (vector × 16) base register + index × fixed-entry-size. Same instruction shape in the CPU's microcode either way — only the register, the multiplier, and what's stored at the far end differ.

Once the CPU has that gate descriptor in hand, it isn't computing a linear address the way a GDT lookup does — it's extracting a code selector and an offset, and preparing to jump there, not just read data from there. That's the next section.

Worth running the numbers concretely, because "×16 instead of ×8" sounds like a footnote until you see how quickly it separates two vectors' storage in memory:

07 — Play By Play

A Worked Example: a Page Fault, Start to Finish

  1. Something happensA running program dereferences a pointer into a page that isn't currently mapped. The paging unit can't complete the access, so the CPU raises hardware vector 14 — the page-fault exception.
  2. CPU consults idtrBefore anything else, the CPU reads the IDT's base address straight out of the idtr register — say, for illustration, 0xfffffe0000000000.
  3. Compute the gate descriptor's address0xfffffe0000000000 + (14 × 16) = 0xfffffe00000000e0. Structurally the exact same "base + index × size" arithmetic as a GDT lookup — just idtr instead of gdtr, and a fixed 16-byte size instead of 8.
  4. CPU reads the gate descriptorIt unpacks a code-segment selector and an offset — together, the entry point of whatever function the kernel registered for vector 14. On Linux, that's the page-fault handler.
  5. Ring-transition machinery runsEverything covered elsewhere in this series clicks in here: the CPU switches to the kernel stack (via the TSS, if a ring change is needed), pushes the trap frame — PC, flags, faulting stack pointer, a handful of registers — and only then jumps to the exact address the gate descriptor named.
  6. The specific handler runsThe function Linux registered for vector 14 executes. It has access to CR2 (a dedicated register the CPU also loads with the exact faulting address) and the error code pushed alongside the trap frame, and decides what to do — grow the stack, page something in from disk, or send the process a fatal SIGSEGV if the access was simply invalid.
✅ Notice What Just Connected
Step 5 is exactly the trap-frame push the PCB/threads article described as happening on "any of the three doors," without explaining how the CPU knew where to jump to. Steps 2–4 are that missing piece: the IDT dispatch is what runs before the trap frame finishes landing, and it's what decides which specific handler code the trap frame is even being built for.

What If Step 2 Itself Fails?

Worth asking, because it's exactly what the earlier IST sidenote was setting up: what happens if idtr points somewhere corrupted, or the current stack is already broken when a fault lands? The CPU doesn't just silently misbehave — it raises vector 8, the double fault, a dedicated exception that exists specifically to catch "a fault occurred while trying to service another fault." This is precisely the scenario a gate's IST field is built for: the double-fault gate is normally configured to force dispatch onto a small, always-clean, pre-reserved stack via IST, rather than trusting whatever stack pointer got the CPU into trouble in the first place. And if that fails too — a fault while already handling a double fault — there's nowhere left to go: the CPU gives up and triple-faults, which on real hardware means an immediate reset.

08 — One Vector, Deliberately Different

Why int 0x80 Is Allowed to Work

Page faults and timer ticks are involuntary — the CPU raises them on its own, and DPL is irrelevant because user code never asked for them. But there's a third category from the vector table above: software interrupts, deliberately triggered by user-mode code executing an int n instruction. And for those, DPL is the entire ballgame.

Old-style Linux x86 syscalls work by having user-mode code load syscall arguments into registers and then execute int 0x80 — vector 128, decimal. That instruction is, mechanically, no different from a stray, buggy int 14: it asks the CPU to dispatch through a specific IDT gate. The only reason it's allowed to succeed at all, instead of faulting immediately, is one field on that specific gate descriptor:

🔑 The One Fact That Makes int 0x80 Legal
Vector 128's gate descriptor is deliberately configured with DPL = 3. That's it. That's the whole mechanism. Every other vector a user program might try to int into — including 14, including 32 — has a gate DPL of 0, so the CPU refuses the attempt with a general protection fault before the handler ever runs. Vector 128 is the one door in the whole 256-slot table the kernel deliberately propped open for Ring 3 to knock on.
Why "legacy"? Modern x86-64 Linux mostly uses a dedicated syscall instruction instead, paired with model-specific registers (not the IDT at all) to jump straight to the syscall entry point — faster than the full interrupt-dispatch path, because it skips a lot of the gate-lookup and privilege-check machinery. int 0x80 still works today, kept alive mainly for 32-bit compatibility and old binaries, which is exactly why it's the version worth learning first: it's the one that actually goes through the IDT you just spent this whole page learning.

Once int 0x80's gate has been located and its DPL check passed, everything downstream is identical to the page-fault walkthrough above: ring transition, trap frame push, jump to the registered handler — in this case, the kernel's central syscall dispatcher, which reads the syscall number out of a register and routes to the specific read(), write(), or fork() implementation the PCB article already introduced you to.

The Faster Path That Skips the IDT Entirely

It's worth being precise about what the modern syscall instruction actually skips, since "faster" undersells it. It bypasses the IDT lookup, the gate-type check, and the DPL check completely — it was designed from the ground up to avoid exactly the machinery this whole page has been walking through.

🐢 int 0x80 — through the IDT

Raises vector 128, which forces a real IDT lookup: idtr.base + 128×16, a gate-descriptor fetch, a DPL=3 check against CPL=3, then the ring transition and trap frame push. Every step from this page runs, in full, on every single legacy syscall.

⚡ syscall — bypasses the IDT

The handler address isn't looked up in any table at boot-configured lookup time — it's read straight out of a Model-Specific Register, IA32_LSTAR, set once by the kernel at startup. No vector, no gate descriptor, no DPL check: the instruction itself is only usable from Ring 3 by definition, so there's nothing left to gate.
So is the IDT irrelevant on a modern 64-bit Linux box? Not remotely — exceptions and hardware interrupts still have nowhere else to go, so vectors 0–31 and 32+ still dispatch exactly as described on this page, every single time a page faults or a timer tick lands. It's specifically the syscall entry path that grew a shortcut; the fault and interrupt paths never did, because those can't be triggered by a cooperative instruction with known-fixed semantics the way a syscall can.

📌 The One-Sentence Takeaway
The GDT and the IDT are the same idea — a base register plus a fixed-size index into an array the kernel alone controls — pointed at two completely different problems: one describing where memory lives, the other describing which code runs when something happens.
10 — Quick Reference

Glossary & Key Terms

IDT (Interrupt Descriptor Table)
The system-wide array of Gate Descriptors that vector numbers index into, dispatching syscalls, exceptions, and hardware interrupts to specific handler code.
idtr
Control register holding the IDT's base address and size in RAM; loaded only via the privileged lidt instruction, gdtr's sibling.
Vector Number
An integer 0–255 identifying which IDT slot to dispatch through — 0–31 reserved by Intel for CPU exceptions, 32–255 free for OS/hardware assignment.
Gate Descriptor
An IDT entry (8 bytes in 32-bit mode, 16 in 64-bit mode) holding a code selector, an offset, and a DPL — the IDT's counterpart to a GDT Segment Descriptor.
Interrupt Gate
A gate type that automatically clears the interrupt flag (IF) on entry, preventing nested interrupts unless the handler re-enables them explicitly.
Trap Gate
A gate type functionally similar to an Interrupt Gate but that leaves IF untouched — interrupts stay enabled through the handler, typically used for debug exceptions.
Task Gate
A largely obsolete gate type that triggers a hardware task switch via a TSS instead of a plain jump; superseded by software-managed context switching.
DPL (on a gate)
Controls whether user-mode code may voluntarily trigger this specific vector with a software interrupt instruction — the field that makes int 0x80 legal while int 14 is not.
CR2
The control register the CPU loads with the faulting linear address whenever a page fault (vector 14) occurs, read by the page-fault handler.
int 0x80
The legacy Linux software-interrupt syscall mechanism — vector 128, whose gate descriptor is deliberately set to DPL 3 so Ring 3 code can trigger it on purpose.
Pseudo-Descriptor
The small packed { limit, base } record that lgdt/lidt read from memory to load gdtr/idtr — same shape for both instructions, only the destination register differs.
IST (Interrupt Stack Table)
A per-gate field forcing dispatch onto one of a few pre-designated, always-known-good kernel stacks — used for vectors like double fault and NMI where the current stack can't be trusted.
syscall / IA32_LSTAR
The modern fast syscall path: a dedicated instruction that reads its handler address from a Model-Specific Register instead of performing an IDT lookup at all.
APIC (Local + I/O)
The modern successor to the 8259 PIC: the I/O APIC routes device lines to a chosen vector and CPU core; each core's Local APIC delivers the interrupt into that core's own IDT dispatch.
IPI (Inter-Processor Interrupt)
An interrupt one CPU core sends directly to another via the Local APIC — commonly used to force a remote core to reschedule — dispatched through the IDT exactly like any other vector.
Double Fault (#DF, vector 8)
The dedicated exception raised when a fault occurs while the CPU is already trying to service another fault; typically forced onto a dedicated IST stack since the current stack can't be trusted.
