01 — The Big Idea

What Is the GDT, Actually?

Think of a large library with one central card catalog at the front desk — a numbered set of drawers, and every drawer holds one card describing exactly one book: where it sits on the shelves, how thick it is, who's allowed to check it out. The Global Descriptor Table (GDT) is precisely this catalog, except every "card" is a Segment Descriptor, and every "book" is a memory segment.

It is, structurally, nothing more exotic than an array of 8-byte Segment Descriptors, sitting somewhere in ordinary RAM — but RAM the kernel controls, that user-mode code cannot directly edit. There is normally exactly one GDT for the whole system (occasionally one per CPU on multiprocessor machines, kept in sync), which is precisely what makes it "Global": every process, every segment selector with TI=0, is looking things up in this same shared table.

💡 The Aha Moment
A segment selector's index field, from the previous article, is nothing more than which drawer number to open in this specific catalog. The GDT is what turns "drawer number 2" into an actual, meaningful Segment Descriptor — base address, size, type, and privilege, all included.
02 — Two Catalogs, Different Scope

GDT vs LDT

Recall the TI bit from the segment selector: 0 selects the GDT, 1 selects the currently active Local Descriptor Table (LDT). Same structure — an array of 8-byte descriptors — completely different scope.

📖 GDT — the shared catalog

One per system. Holds descriptors every process can reference: the kernel's own code/data segments, the standard user-mode code/data segments every process uses, Task State Segment descriptors, and (notably) the descriptor that describes where the current LDT itself lives.

📔 LDT — the private supplement

Optional, and potentially different for every process. Used only if a process needs extra segments beyond what the GDT already offers — historically more relevant to old segmented MS-DOS/Windows-style programs than to typical Linux processes.
So an LDT descriptor lives... in the GDT? Yes — deliberately recursive. An LDT is itself just a segment, described by a special system-type Segment Descriptor (the S flag cleared) that, by rule, can only appear in the GDT. So finding a process's LDT is itself a GDT lookup, using a selector kept in the ldtr register. The GDT really is the one root catalog everything ultimately traces back to.
03 — Finding the Catalog Itself

The gdtr Register

If the GDT is just an array sitting in RAM, the CPU needs to know two things to use it: where it starts, and how big it is. Both live in a dedicated control register called gdtr — holding the GDT's base memory address plus its size (limit). A sibling register, ldtr, holds the address and size of whichever LDT is currently active for the running process.

What gdtr actually stores gdtr = { base address of the GDT in RAM, size of the GDT in bytes } Loaded once (typically at boot, by the kernel) via a privileged instruction — ordinary user-mode code cannot read or modify gdtr's contents.
⚠️ Why gdtr Is Locked Down
If user-mode code could repoint gdtr at memory of its own choosing, it could fabricate a Segment Descriptor with DPL 0, Base 0, and Limit covering all of RAM — and hand itself full, unrestricted access to everything. Loading gdtr/ldtr is itself a privileged instruction, refused outside Ring 0, for exactly the same silicon-level reason any other privileged instruction is refused there.
04 — The Arithmetic

Turning an Index Into a Real Address

Here's the entire trick, and it's genuinely just arithmetic. Every Segment Descriptor is exactly 8 bytes wide. So to find descriptor number index, the CPU just does simple array indexing — the same math a compiler generates for array[i] in any language.

The GDT lookup formula Descriptor Address = gdtr.base + (selector.index × 8) Read 8 bytes starting at that address, and you have the full Segment Descriptor — Base, Limit, Type, DPL, and everything else from the previous article.

And once that descriptor is in hand, the very first formula from this whole series clicks fully into place:

Full journey, start to finish Linear Address = Descriptor.Base + Offset Where Descriptor.Base was fetched using exactly the gdtr + index×8 arithmetic above.

06 — Play By Play

A Worked Example

  1. Start with a selectorSay cs holds a selector with index = 15, TI = 0 (GDT), RPL = 3 (user-mode access).
  2. Consult gdtrThe CPU reads the GDT's base address straight out of the gdtr register — say, for illustration, 0x00120000.
  3. Compute the descriptor's address0x00120000 + (15 × 8) = 0x00120078. This is a plain array index — no page tables, no paging unit involved yet.
  4. Fetch the 8-byte descriptorThe CPU reads those 8 bytes and unpacks Base, Limit, Type, DPL, and the rest, exactly as laid out in the previous article's field table.
  5. Check privilege before proceedingThe CPU compares the descriptor's DPL against the current CPL and the selector's RPL. If the access isn't allowed — say, RPL/CPL 3 trying to touch a DPL 0 segment — a general protection fault fires instead of completing the access.
  6. Compute the linear addressAssuming the privilege check passes, the descriptor's Base field is added to the offset from the original logical address, producing the final linear address — ready to be handed to the paging unit.
07 — One Layer Deeper

How Linux Actually Uses the GDT

Here's a twist worth knowing: Linux uses segmentation about as little as the hardware will allow. Rather than giving every process a tightly bounded segment the way old MS-DOS programs needed, Linux defines just a small, fixed handful of GDT entries — essentially one flat code segment and one flat data segment for Kernel Mode, and one flat code segment and one flat data segment for User Mode, each with Base = 0 and Limit covering the full addressable range.

In other words, Linux uses the segmentation unit mostly just to carry the CPL (via which code segment's DPL is active) and otherwise gets out of the way, leaving essentially all real memory protection and address flexibility to the paging unit. The GDT is still consulted on every memory access — the hardware pipeline doesn't skip steps — but its entries are deliberately boring by design.

🧠 Why This Is a Smart Design Choice
Two protection mechanisms doing overlapping jobs (segmentation and paging) is redundant complexity. By flattening segmentation down to "cover everything, differ only by privilege level," Linux keeps one real protection mechanism — paging — as the source of truth, while still getting Ring 0 / Ring 3 separation almost for free out of the segmentation hardware it can't disable anyway.
08 — Quick Reference

Glossary & Key Terms

GDT (Global Descriptor Table)
The one shared, system-wide array of Segment Descriptors that TI=0 selectors index into.
LDT (Local Descriptor Table)
An optional, per-process array of additional Segment Descriptors, indexed by TI=1 selectors, itself described by an entry in the GDT.
gdtr
Control register holding the GDT's base address and size in RAM; loaded only via a privileged instruction.
ldtr
Control register holding the currently active LDT's base address and size.
Descriptor Address Formula
gdtr.base + (selector.index × 8) — plain array indexing into 8-byte descriptor slots.
Flat Segmentation (Linux)
Linux's approach of giving Kernel/User code/data segments Base=0 and a limit spanning the full address range, leaving real protection to paging.
