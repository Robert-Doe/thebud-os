01 — What Intel Actually Meant To Build

The Ambitious Original Plan

Go back to the PCB/threads article for a second. It described a context switch as fundamentally a software job: the kernel notices it's time to run someone else, hand-writes every register the outgoing thread cares about into that thread's PCB, then hand-reads a completely different set of saved values out of the incoming thread's PCB back into live registers. All of that — the deciding, the saving, the loading — is code the kernel author had to write.

When Intel designed protected mode for the 80286 (1982) and then fully fleshed it out for the 32-bit 80386 (1985), they looked at that whole dance and asked a genuinely bold question: what if the CPU just did this itself? Not "provide a fast instruction the kernel can call" — actually own the entire context switch, in silicon, with the kernel barely involved.

🎯 The Pitch, As Intel Saw It
Give every task its own Task State Segment (TSS) — a fixed-format block of memory holding a complete snapshot of that task: every general-purpose register, every segment register, the flags register, the instruction pointer, and even the page-table base (CR3). Then switching from Task A to Task B becomes a single instruction: a far jmp or call targeting Task B's TSS descriptor, or a jump through a special IDT/GDT/LDT entry called a task gate. The CPU handles the rest, automatically, with no kernel code running in between.

There wasn't even just one way to trigger this. Intel gave the kernel — and, deliberately, occasionally even user code — several distinct doors into a hardware task switch:

Far JMP to a TSS selector
A one-way switch. Task A doesn't expect to come back to where it left off via this mechanism.
Far CALL to a TSS selector
A nested switch — sets the NT flag and stamps a back-link, so a later IRET can hand control right back to Task A.
Jump/call through a Task Gate
One extra layer of indirection: the gate itself carries its own DPL, letting the kernel control who's allowed to trigger the switch, independent of the TSSD's own DPL.
A hardware interrupt/exception via a Task Gate in the IDT
The most radical option — an interrupt itself becomes a full task switch, with no ordinary interrupt handler code running first.

Just like the ordinary segment descriptors from the earlier article, every one of these paths still goes through a privilege check before the CPU lets it happen — the requesting CPL and the gate/descriptor's own DPL have to line up correctly, exactly the same DPL-vs-CPL logic you already learned. Hardware task switching was never meant to be a privilege-bypass shortcut; it was meant to be the normal way every context switch happened, guarded by the same rules as everything else.

And "handles the rest" was meant literally. On execution of that far jump, the processor would, in hardware:

  1. Freeze and dump Task AWrite the live values of every general register, every segment selector, EFLAGS, and the current instruction pointer out into Task A's own TSS in memory — the exact "save" half of a context switch, done by microcode instead of kernel code.
  2. Mark the linkSet the NT (Nested Task) flag and stamp a "previous task" back-link into the new TSS, so a task reached via a call or interrupt could later hand control back with an iret — tasks could nest, like stack frames, entirely in hardware.
  3. Load Task B wholesalePull every one of those same fields back out of Task B's TSS and pour them into the live registers — including, remarkably, CR3. Loading a new address space was not a separate step the kernel had to remember; switching tasks and switching page tables were the same hardware event.
  4. Resume in Task BExecution simply continues at whatever EIP was stored in Task B's TSS, at whatever privilege level Task B's saved CS implies. From the outside, the entire context switch happened between one instruction and the next.
Wait — task gates could fire from an interrupt, too. A task gate could sit in the IDT itself, meaning a hardware interrupt or CPU exception could trigger a full hardware task switch directly, with no software handler running at all until the new task's own code began executing. Intel wasn't just proposing hardware-assisted scheduling — they were proposing hardware-assisted everything that used to require the kernel to run first.

What did one of these task gates actually look like as bits in memory? Structurally, it's a close cousin of the segment descriptor from the earlier article — same 8-byte size, same idea of "a selector plus some access rules" — but it points at a TSS instead of at ordinary code or data:

No base, no limit, no offset field worth mentioning — unlike a call gate, a task gate doesn't even point at a specific instruction. It just names a TSS selector and says "go run whatever's in there." The whole notion of "resume at a specific address" is irrelevant, because the destination TSS's own saved EIP already says where to resume. Everything about the target task's identity is carried entirely by which TSS you point at — which is a tidy encapsulation of the whole 1985 idea in one small structure.

This is worth sitting with, because it is a genuinely different philosophy from the one your machine actually runs today. The TSS wasn't a minor convenience field. It was Intel's attempt to make the operating system's single most fundamental, most frequently executed piece of logic — "who runs next, and how do I safely swap them in" — something the kernel didn't have to write at all.

😲 Even "Full Hardware" Wasn't Actually Full
Look closely at that field list: there's no FPU/x87 state anywhere in it. Intel's own "do the entire context switch in hardware" structure didn't cover the floating-point register file. Instead, the CPU used a separate trick — a TS ("task switched") bit in CR0, set automatically on every task switch, that caused the next FPU instruction to fault (#NM) so software could lazily save and restore FPU state by hand. Even in Intel's most maximalist hardware vision, a piece of the switch still had to be done in software. That should be a hint about how the rest of this story goes.

The TSSD's Type field — the same field the segmentation article showed you, just with different values this time — also quietly encodes something clever: whether a given TSS is currently busy. A 32-bit Available TSS descriptor uses type 0x9; the exact same descriptor flips to type 0xB, "Busy," the instant the CPU switches into it, and flips back on the way out via iret. That's the hardware's own guard against re-entrancy — you cannot far-jump into a TSS that's already marked busy (except by returning to it through the nested-task chain via iret), which is precisely the kind of double-entry bug a kernel's own scheduler has to guard against by hand today.

Now compare that to the structure actually used today. In 64-bit long mode, AMD and Intel didn't just stop using hardware task switching — they physically redesigned the TSS format, and the redesign is itself a confession. Task gates aren't even supported in 64-bit mode; the CPU won't let you attempt a hardware task switch at all. So the fields that only existed to support one got deleted:

🔍 The One Field That Actually Kept Its Original Job: I/O Map Base
Ordinarily, touching a hardware I/O port with in/out requires full Ring 0, or at least a CPL numerically ≤ the CPU's IOPL flag. The I/O permission bitmap is Intel's escape hatch for a narrower case: a normally-unprivileged process that a kernel deliberately trusts with a handful of specific ports — a userspace X server needing direct video-card port access, say. Each bit in the bitmap, one per I/O port number, says "this specific process may access this specific port directly, no trap, no kernel mediation." The I/O Map Base field just holds the byte offset, inside that same TSS, where the bitmap begins — a pointer to a pointer's target, tucked inside a structure that's mostly retired. Linux exposes this to userspace through the ioperm() and iopl() syscalls, and updates the live TSS's bitmap on a context switch only for the rare process that actually uses them.

The hardware column touches every field, every time, no exceptions — it's a fixed microcoded sequence and it cannot skip a row just because that row didn't change. The software column skips almost everything that doesn't actually need touching. That gap is the entire reason this article exists.

Notice, too, that "skipped" isn't a shortcut the software path discovered — it's a shortcut the hardware path was structurally incapable of taking. A microcoded instruction sequence baked into the silicon has no way to ask "does this specific process even use an LDT?" or "did any segment register actually change since last time?" It just runs its fixed list, top to bottom, every time. Software gets to ask those questions, because software is, by definition, allowed to have an opinion.

04 — The Twist

Why Operating Systems Abandoned It

Here's the part that surprises people: hardware task switching didn't lose because it was buggy, or unsafe, or hard to program. It lost a straightforward speed contest. A hand-written software context switch, running on the very same CPU, reliably beat the CPU's own built-in task-switch instruction. Let that sit for a second — the manufacturer's own "let silicon do it" feature was slower than a kernel engineer's assembly loop.

Reason one: hardware can't skip work it doesn't know is unnecessary

A hardware task switch is unconditional. It doesn't know — and architecturally can't know — that your operating system uses a flat memory model where ds, es, and ss barely ever change between tasks. It reloads all six segment registers anyway, every single switch, because the microcode sequence has no branch for "actually, skip this one, nothing changed." A software context switch, written by someone who knows exactly how their OS uses segmentation, simply never touches those registers at all when they don't need it.

Reason two: hardware can't be tuned, inlined, or scheduled around

Software context-switch code lives inside the compiler's and CPU's normal optimization machinery — it can be hand-written in assembly, inlined at the call site, reordered by the compiler, and its instructions can be predicted and speculated around like any other code. A hardware task switch is none of that. It's a fixed, opaque, serializing event: the pipeline can't speculate past it, can't overlap it with other work, can't reorder around it. It is, by design, a wall.

Reason three: the kernel needs to do other bookkeeping anyway

A real context switch is never just "save registers, load registers." The scheduler also has to update run-queue statistics, decide who runs next, handle timing accounting, and possibly wake up other waiters — logic that has to be software regardless. Once you accept that software has to run right before and right after the switch either way, folding the register save/restore into that same hand-tuned software path costs you almost nothing extra, while a hardware task switch forces an awkward, expensive detour through a completely separate, fixed-cost mechanism.

Reason four: it forces a TLB flush you often don't even need

Remember that CR3 sits right there in the TSS as an ordinary field, saved and loaded exactly like every other one. That means a hardware task switch reloads CR3 every single time — even when switching between two threads of the same process, which by definition share one address space and one CR3 value already. Reloading CR3 isn't free: it's specifically what triggers a full flush of the TLB, the CPU's cache of virtual-to-physical translations, forcing every subsequent memory access to walk the page tables from scratch until the cache warms back up. A software context switch knows exactly when the address space is actually changing and only reloads CR3 — and pays that TLB tax — when it truly has to. Thread-to-thread switches within one process, which are extremely common, pay nothing at all on this front.

🐌 Hardware Task Switch (TSS far jmp)

Touches all 8 GP registers, all 6 segment selectors, LDTR, EFLAGS, EIP, and CR3 — unconditionally, every time. Fully serializing; the pipeline cannot work around it. Fixed sequence, no OS-specific tuning possible.

⚡ Software Context Switch

Touches only what's known to have changed — often just the stack pointer, a handful of callee-saved registers, and CR3 (only if the address space differs). Hand-optimized, inlinable, and integrated directly with the scheduler's other bookkeeping.
📌 One Honest Exception, From Linux's Own History
Classic 32-bit Linux actually did use a sliver of hardware task switching — for exactly one case. Handling a double fault safely means you cannot trust the current kernel stack is even valid (that's often why you're in a double fault). x86-32 has no IST mechanism to solve that. So 32-bit Linux kept one dedicated, statically-allocated TSS reachable via a task gate purely for #DF: a hardware task switch guarantees a fresh, known-good stack pointer with zero reliance on whatever the old stack pointer currently held. It's a tiny, single-purpose use of the very mechanism the rest of the kernel abandoned — solving precisely the problem the 64-bit IST field (Section 06) was later built to solve more cheaply.
05 — What The TSS Is Actually For, Part One

RSP0 and Crossing Rings

So if task switching itself is dead, why does every modern x86-64 kernel still keep a TSS around and load it at boot? Because one job never went away: supplying a trustworthy stack pointer the moment the CPU changes privilege level.

Think about what has to happen the instant user-mode (CPL 3) code triggers a trap into the kernel (CPL 0) — a page fault, a hardware interrupt, a software int instruction. The CPU is about to start executing kernel code, and it needs somewhere to push the interrupted context (SS, old RSP, RFLAGS, CS, RIP). It absolutely cannot keep using whatever stack pointer user-mode code happened to have loaded — that stack is untrusted, might be misaligned on purpose, and handing the kernel's first instructions a stack an attacker controls is exactly the kind of hole real exploits are built from.

🔑 Where RSP0 Comes From
For any Ring 3 → Ring 0 transition made through the classic interrupt/trap-gate mechanism (hardware interrupts, CPU exceptions, the legacy int instruction), the CPU reads a brand-new stack pointer straight out of RSP0 in the currently loaded TSS, switches RSP to it, and only then starts pushing the trap frame. This is the field the segmentation article's TSSD entry was quietly pointing at all along — a real hardware register-loading step that happens on essentially every syscall and interrupt your machine handles. The "Crossing the Ring" companion piece in this series walks this exact hand-off byte-by-byte, frame-push by frame-push, if you want the full mechanical play-by-play; the short version that matters here is simply: the TSS is where that trusted address lives.
But wait — doesn't the fast syscall path use this too? Actually, no, and it's worth being precise here. The SYSCALL/SYSRET instruction pair — the one Linux and Windows actually use for ordinary system calls — is a separate, MSR-driven mechanism. The new CS/SS come from the IA32_STAR MSR and the new RIP from IA32_LSTAR. Critically, SYSCALL does not automatically switch the stack pointer at all — RSP still holds the user-mode value the instant kernel code starts running. The kernel's own entry code has to manually pivot onto a safe per-CPU kernel stack (typically via swapgs plus a known per-CPU pointer) before it dares do anything else. RSP0 is for the older gate-based path — interrupts, exceptions, and legacy traps — not for the fast syscall path. Both roads lead to "the kernel supplies its own stack, in software or via the TSS," which is really the whole theme of this page.

Concretely, here's the sequence the CPU actually runs when a user-mode page fault fires and lands on a gate-based path:

  1. Fault detected mid-instructionThe CPU notices the memory access is invalid and prepares to deliver vector 14 (#PF) using the IDT entry registered for it.
  2. Privilege check: is this a ring change?The CPU compares the target gate's code segment CPL (0, kernel) against the CPL that was running (3, user). They differ — this is a real privilege escalation, not a same-ring trap.
  3. RSP0 is read from the current TSSBecause the privilege level is changing, the CPU pulls a fresh SS:RSP straight out of the currently loaded TSS's RSP0 field — never touching the old, untrusted user-mode stack pointer for this step.
  4. The trap frame is pushed — onto the new stackOld SS, old RSP, RFLAGS, CS, RIP, and (for a page fault specifically) an error code all get pushed — but onto the brand-new kernel stack from step 3, not the old one.
  5. The kernel's page-fault handler beginsExecution jumps to the handler's address from the IDT gate, already running at CPL 0, already standing on a stack the kernel itself controls and trusts completely.
What if there's no privilege change at all? If an interrupt fires while the CPU is already at CPL 0 — one kernel-mode interrupt handler getting interrupted by another, for instance — step 2 finds no privilege change, and the CPU skips the RSP0 lookup entirely, simply continuing to push the trap frame onto whatever stack was already active. The TSS's stack-pointer fields only ever get consulted at the exact moment a ring boundary is being crossed — which is a nice, tight illustration of just how narrowly scoped the TSS's surviving job really is.

Either way — via RSP0 or via manual swapgs plumbing — the principle from the very first article in this series is being enforced in concrete silicon: crossing from a lower ring to a higher one is never something the lower ring gets to control the mechanics of. The higher ring always insists on stepping onto ground it trusts first.

06 — What The TSS Is Actually For, Part Two

The Interrupt Stack Table

RSP0 solves the ordinary case. But some exceptions are not ordinary — they're the CPU telling you something has gone wrong in a way that makes even RSP0 unsafe to trust. What if the "normal" kernel stack pointer is the problem? A kernel stack overflow is a real, observed failure mode — and it triggers a page fault at the exact moment the CPU has no good stack to push the resulting trap frame onto.

Long mode's answer is the Interrupt Stack Table (IST): up to 7 alternate stack pointers — IST1 through IST7 — stored right there in the same TSS as RSP0. Each entry in the IDT (the interrupt descriptor table) can optionally tag itself with a 3-bit IST index. A value of 0 means "use the normal RSP0-based logic." A nonzero value means something much stronger:

🛡️ The IST Guarantee
"For this specific vector, don't even look at the current stack pointer — no matter what it is, no matter whether it's valid, corrupted, or mid-overflow — switch RSP unconditionally to this known-good, dedicated, always-valid address before running the handler." That's a stronger promise than RSP0 makes, and it's reserved for exactly the exceptions where you can't afford to be wrong about stack validity.
Double Fault (#DF, vector 8)
Fired when the CPU fails to even deliver a first exception. Classic cause: a kernel stack overflow triggers a page fault, and the page-fault handler's own attempt to push a frame fails too. Needs a stack that has nothing to do with the one that just broke.
NMI (Non-Maskable Interrupt)
Can arrive at literally any instruction boundary, including mid-way through the kernel's own interrupt entry code. You cannot assume any particular stack state is stable when this fires.
Machine Check (#MC, vector 18)
The hardware itself is reporting it may be malfunctioning. This is the last moment you want to discover your stack pointer is also broken.
Debug Exception (#DB, vector 1)
Commonly given its own IST slot too, since debug traps can legitimately fire from awkward, half-finished kernel states while single-stepping.

Linux and Windows both assign small, dedicated, permanently-mapped stacks to several of these vectors via IST slots, set up once at boot. It's the direct architectural descendant of the double-fault-only task gate that 32-bit Linux relied on — same underlying worry ("what if the stack itself is the thing that's broken"), a cheaper and more general hardware mechanism to answer it.

07 — The Final Irony

One TSS Per Core — Not Per Task

Sit with how far this has drifted from the original 1985 pitch. The TSS was designed to be one per task — every runnable task in the system was meant to own its own TSS, and switching between hundreds of them was supposed to be routine. Modern Linux and Windows instead keep exactly one TSS per physical CPU core, set up once, essentially for the lifetime of the machine.

  1. Boot time: one TSS descriptor per core is built in the GDTEach CPU core gets its own TSS structure and its own TSSD entry in the (per-core) GDT — not one per process, not one per thread. Just one, permanently, per core.
  2. ltr loads it into the Task RegisterThe privileged ltr ("load task register") instruction loads that TSS's selector into the CPU's hidden Task Register (TR) — a 16-bit visible selector backed by a hidden cache of that TSS's base address and limit, exactly like the segmentation registers from the earlier article cache their descriptor's contents. ltr runs once, at boot, and essentially never again.
  3. RSP0 gets rewritten constantly, not the TSS itselfHere's the trick that makes "one TSS per core" compatible with running thousands of different tasks: the kernel doesn't reload the whole TSS on every context switch — it just overwrites that one core's TSS's RSP0 field (and IST fields, rarely) to point at whichever task is about to run next. The TSS became a fixed piece of per-core furniture; only one small field inside it churns.
  4. The actual task-switching, meanwhile, is 100% softwareRegister save/restore for the ten thousand real task switches your machine does per second happens exactly the way the PCB/threads article described: by hand, in the scheduler's switch_to-style code, using each task's own PCB/TCB — never by touching the Task Register, never by a far jump to a TSS descriptor.

📜 The TSS's Job, 1985

One TSS per task, in their thousands. A far jmp/call or a task gate performs the CPU's most important repeated operation — the full context switch — entirely in hardware, unconditionally saving and restoring every register, every segment, and the address space itself.

🖥️ The TSS's Job, Today

One TSS per core, loaded once at boot via ltr and essentially never reloaded again. Its only living duties: hand the CPU a trustworthy Ring-0 stack pointer on a privilege change (RSP0), and hand it a guaranteed-good emergency stack for the handful of exceptions that can't trust anything else (IST1–7).
✅ The Shape of the Whole Story
Intel built a mechanism for switching between many TSSs. Operating systems kept exactly one TSS, forever, per core — and repurposed a couple of its fields as a mailbox for "here's the stack to use right now." The structure survived; the entire premise it was designed around didn't. And yet that narrow surviving job is not optional trivia — it runs on every syscall, every hardware interrupt, every page fault your machine handles, all day, every day.
History rhymed once more, one layer up. When Intel and AMD later designed hardware support for running whole guest operating systems (VT-x's VMCS, AMD-V's VMCB), they faced the exact same design fork the TSS once represented — and made the same choice the industry already made once. A "VM exit/entry" absolutely does save and restore a large, fixed set of guest state in hardware, but crucially the hypervisor still gets fine control over exactly which pieces get saved eagerly versus lazily, precisely because a fully rigid all-or-nothing hardware switch was already a known, learned-the-hard-way mistake.
08 — Quick Reference

Glossary & Key Terms

TSS (Task State Segment)
A fixed-format memory structure originally meant to hold one task's complete CPU state; today, on x86-64, reduced mainly to stack-pointer fields (RSP0–2, IST1–7) plus an I/O bitmap pointer.
TSSD (TSS Descriptor)
The 8-byte system-type descriptor (S flag cleared) that describes a TSS's location and size — can only live in the GDT, never an LDT.
Task Register (TR)
A hidden CPU register holding the selector of the currently loaded TSS, plus a cached copy of that TSS's base address and limit.
ltr (Load Task Register)
The privileged instruction that loads a TSS selector into TR — run once per core at boot on modern kernels, essentially never again.
Task Gate
A special IDT/GDT/LDT entry that triggers a full hardware task switch, including from directly inside interrupt/exception handling. Not supported at all in 64-bit long mode.
RSP0 / ESP0
The Ring-0 stack pointer field in the currently loaded TSS, loaded automatically by the CPU whenever a trap or interrupt raises privilege from Ring 3 to Ring 0 via a gate.
IST (Interrupt Stack Table)
Seven alternate, always-trusted kernel stack pointers (IST1–IST7) a 64-bit TSS can supply, used for exceptions like double fault and NMI where the normal stack pointer can't be trusted.
Double Fault (#DF)
Vector 8 — fired when the CPU fails to deliver an exception normally, often from a kernel stack overflow; a canonical IST use case.
SYSCALL / SYSRET
The fast, MSR-driven system-call entry mechanism used by modern OSes; unlike gate-based traps, it does not use RSP0 — the kernel switches stacks manually.
I/O Permission Bitmap
An optional per-TSS bitmap, pointed to by the TSS's I/O Map Base field, granting fine-grained access to individual I/O ports without full Ring 0.
TLB (Translation Lookaside Buffer)
The CPU's cache of virtual-to-physical translations. Reloading CR3 flushes it — a real cost a hardware task switch paid on every single switch, needed or not.
CR3 / PDBR
The page-directory/page-table base register — the root of the current address space. Part of the original TSS; loaded manually by software today, and only when the address space actually changes.
Lazy FPU Switching
A technique using CR0's TS flag: the CPU faults (#NM) on the first FPU instruction after a switch, letting software save/restore FPU state only when actually needed — notably, never covered by the hardware TSS switch itself.
