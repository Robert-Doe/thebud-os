01 The Tools You'll Use

Head First Moment

Building an OS is like building a house in the middle of the ocean — you can't live in it while you build it, and you can't test it on your real computer without destroying what you're typing on. You need a fake computer inside your real computer. That's QEMU.

QEMU — The Fake Computer

QEMU is a hardware emulator. It pretends to be a complete x86 PC: it has a fake CPU, fake RAM, a fake hard disk, and a fake screen. When we say make run, your BobOS boots inside QEMU. If it crashes, QEMU crashes — not your real Windows machine. You can also pause it, inspect its registers mid-execution, and restart it in under a second.

Why x86?

x86 is the instruction set used by nearly every Windows and Linux desktop CPU (Intel and AMD). It's also the architecture that most OS books and tutorials target — so there's a huge community, tons of documentation, and your CPU already knows how to run what you build natively. When we say "32-bit x86", we mean the version of x86 where memory addresses are 4 bytes wide (up to 4 GB of RAM).

# The command you'll run for every OS module:
make disk.img    # builds the OS into a disk image file
make run         # starts QEMU booting from that disk image

# What QEMU actually executes:
qemu-system-i386 -drive format=raw,file=disk.img -m 128M

The flag -drive format=raw,file=disk.img tells QEMU "treat this file as if it were a physical hard disk." The flag -m 128M says "give the fake computer 128 megabytes of RAM."

NASM — The Assembly Compiler

NASM stands for Netwide Assembler. Assembly is the language closest to raw machine instructions — one line of assembly is usually one CPU instruction. NASM reads your .asm files and produces raw binary bytes that the CPU can execute directly. We use NASM for the bootloader (Module 01) and a few other files where we must control the exact binary output.

NASM vs GCC

GCC is the C compiler we use for everything else. You write C (higher-level, readable) and GCC translates it to assembly, then to binary. NASM is for the rare cases where we can't trust GCC to produce exactly the right bytes — like the bootloader, which must be exactly 512 bytes and end with 0x55 0xAA.

Make — The Automated Build Script

Typing nasm -f bin bootloader.asm -o boot.bin and then gcc -c kernel.c -o kernel.o and then linking them together every time you change a file would be exhausting. Make reads a Makefile and figures out exactly which commands need to re-run based on what changed. make run = "build everything that's out of date, then start QEMU."

WSL — Windows Subsystem for Linux

The OS tools we use (GCC for cross-compilation, NASM, GNU LD the linker) are Linux tools. WSL lets you run a real Linux environment inside Windows. When you see wsl -d Ubuntu -- bash -c "..." in a command, it means "run this command in your Ubuntu Linux environment." The path /mnt/c/Users/... is how Linux inside WSL sees your Windows C: drive.

02 Number Systems: Hex, Binary, Decimal

Head First Moment

Humans count in base 10 because we have 10 fingers. CPUs count in base 2 because transistors have two states: on and off. Programmers use base 16 (hex) because it maps cleanly onto groups of 4 binary bits. Same number, three different ways to write it.

Why Hex Everywhere?

When you see 0xB8000 or 0x55AA in the tutorials, those are hexadecimal (base 16) numbers. The 0x prefix is just C's way of saying "this is hex, not decimal." Hex uses digits 0–9 plus letters A–F, where A=10, B=11, C=12, D=13, E=14, F=15.

HexDecimalBinaryWhere you'll see it

0xF1511114 bits all on
0xFF25511111111one byte, all 8 bits on
0x558501010101alternating bits — part of boot signature
0xAA17010101010alternating bits — part of boot signature
0x100040961 0000 0000 0000one page (4 KB) — key size in paging
0xB8000753664—VGA text buffer address (see Module 03)
0xFFFFFFFF4,294,967,29532× 1smaximum 32-bit address (4 GB − 1)

Converting Hex to Decimal in Your Head

0x10  = 1×16 + 0×1            = 16
0x100 = 1×256 + 0×16 + 0×1   = 256
0x1000 = 1×4096               = 4096  (one page!)
0xFF  = 15×16 + 15×1          = 240 + 15 = 255

Why Memory Addresses Are in Hex

A memory address like 0xB8000 looks cryptic, but in hex every 2 digits = 1 byte = 8 bits. So 0xB8000 is 3 bytes wide and tells you exactly where in the CPU's 4 GB address range you are. In decimal it would be 753,664 — harder to compare at a glance.

The Rule of Thumb

One hex digit = 4 bits. Two hex digits = 1 byte (8 bits). Eight hex digits = 4 bytes = one 32-bit address. So when you see 0x00000000 through 0xFFFFFFFF, that's the entire 4 GB address space of a 32-bit CPU.

03 The CPU: What It Actually Does

Head First Moment

The CPU is a machine with one job: fetch an instruction from memory, execute it, move to the next one, repeat forever. That's the entire loop. Power on the CPU and it starts at a fixed address in memory, reads one instruction, does what it says (add two numbers, jump somewhere, write to a port), then reads the next one. Your OS is just a long list of instructions that this loop executes.

The Fetch-Decode-Execute Cycle

while (power_on) {
    instruction = memory[EIP];   /* FETCH: read bytes at current address */
    EIP += instruction.length;   /* ADVANCE: move to next instruction */
    execute(instruction);        /* EXECUTE: do the thing */
}

EIP is the Instruction Pointer — the CPU's "bookmark" for where it is in the program. Every instruction execution either increments EIP to the next instruction, or a jump/call replaces it with a new address.

Real Mode vs Protected Mode

When your PC powers on, the x86 CPU starts in Real Mode — a 1970s compatibility mode where memory addresses are only 20 bits wide (1 MB maximum), there's no memory protection, and any program can access any address. This is the mode BIOS and the bootloader run in.

Module 02 switches the CPU to Protected Mode — the modern mode where addresses are 32 bits (4 GB), memory is protected between programs, and the CPU enforces privilege rings. This switch is a one-way door: you flip bit 0 of a control register (CR0) and never go back.

Module 01 — bootloader runs in Real Mode Module 02 — switch to Protected Mode Modules 04–24 — everything runs in Protected Mode

04 Registers: The CPU's Hands

Head First Moment

Think of registers as the CPU's hands — tiny storage slots built directly into the chip. There are only about 16 of them but they're the fastest storage that exists (faster than RAM by 100×). Every operation the CPU does reads from and writes to registers. RAM is the desk; registers are what you're holding in your hands right now.

General-Purpose Registers (the Workhorses)

EAX
Extended Accumulator
The primary math register. Addition, multiplication, return values from functions all land here. Syscall number goes in EAX before int 0x80.
EBX
Extended Base
General purpose. Used as first argument to syscalls in BobOS (int 0x80). Often holds a base address for memory access.
ECX
Extended Counter
Loop counter by convention. The rep prefix instruction uses ECX to know how many times to repeat. Second syscall argument.
EDX
Extended Data
Overflow from multiplication goes here. Third syscall argument. Also used for I/O port numbers with the in/out instructions.
ESI
Extended Source Index
Source address for memory copy operations (movs). Often used as a general pointer.
EDI
Extended Destination Index
Destination address for memory copy. Pair with ESI for rep movsd (copy blocks of memory).

Special-Purpose Registers (the Control Panel)

ESP
Extended Stack Pointer
Always points to the top of the stack. PUSH decrements ESP then writes; POP reads then increments. This is how function calls work.
EBP
Extended Base Pointer
Stack frame anchor. At the start of a function, EBP is set to ESP — giving a stable "floor" to reference local variables and arguments even as ESP moves.
EIP
Extended Instruction Pointer
The CPU's bookmark — address of the NEXT instruction to execute. You can't write to it directly; JMP, CALL, and RET change it.
EFLAGS
Flags Register
32 individual bits, each a flag. After a CMP, the Zero Flag (ZF) is set if results were equal. Conditional jumps like JE check these flags.

Control Registers (the Boss Registers — Ring 0 Only)

CR0
Control Register 0
Bit 0 (PE): set to 1 = enter Protected Mode. Bit 31 (PG): set to 1 = enable paging. Flipping these bits is the biggest moment in Modules 02 and 07.
CR2
Page Fault Address
When a page fault occurs, the CPU stores the address that caused the fault here. Your page fault handler reads CR2 to know what address was accessed.
CR3
Page Directory Base
Holds the physical address of the Page Directory for the current process. Switch CR3 = switch address spaces. Writing CR3 also flushes the TLB (CPU's address translation cache).

Segment Registers (Historical Relics Still Used)

CS
Code Segment
Which segment the currently-executing code lives in. In Protected Mode, this holds a selector — an index into the GDT (Module 04). CS selector 0x08 = kernel code.
DS / ES / FS / GS
Data Segments
Point to the data segment. In BobOS (flat memory model) we set all data segment registers to 0x10 (kernel data selector) and forget about them.
SS
Stack Segment
Which segment the stack lives in. In a flat model, same as DS (0x10). When ESP points to something, it's relative to SS — in our setup that's always the whole 4 GB space.

Sub-Registers (Parts of the Big Ones)

Each 32-bit register (EAX, EBX, etc.) can be accessed in smaller pieces. You'll see these in legacy or tight code:

EAX = 32 bits  [bits 31–0]  — the whole thing
 AX = 16 bits  [bits 15–0]  — low 16 bits of EAX
 AH =  8 bits  [bits 15–8]  — high byte of AX
 AL =  8 bits  [bits  7–0]  — low byte of AX (most commonly used sub)

Example: if EAX = 0x12345678
   AX  = 0x5678
   AH  = 0x56
   AL  = 0x78

There Are No Dumb Questions

Q: Why are registers named EAX, EBX etc. with "E"?
The "E" stands for "Extended." The original 8086 (1978) had 16-bit registers called AX, BX, CX, DX. When 32-bit CPUs arrived in 1985, they extended the registers to 32 bits and added the "E" prefix. 64-bit CPUs (x86-64) extended them again and added an "R" prefix: RAX, RBX. In BobOS we use 32-bit (E-prefixed) throughout.
Q: What does "volatile" mean in asm volatile("...")?
It tells the compiler "don't optimize this away or move it around." The C optimizer sometimes removes or reorders code it thinks has no effect. For hardware access (writing to CR0, reading from ports, issuing interrupts), that reordering would be catastrophic. volatile is a stop sign for the optimizer.

05 Assembly Language: Talking to the CPU

Head First Moment

C is like giving instructions to a very capable employee: "sort this list." Assembly is like telling that employee exactly which hand to move, exactly where to reach, exactly how many inches to move their arm. Verbose, precise, and unavoidable when you need exact control — like the bootloader, which must be exactly 512 bytes.

The Most Common Instructions — Plain English

InstructionExampleWhat it means in English
MOV mov eax, 5 Put the value 5 into register EAX. ("Move" is a misnomer — it copies, not moves.)
MOV mov eax, [ebx] Read 4 bytes from memory at the address stored in EBX, put the result in EAX. The brackets [] mean "the value AT this address" (dereference).
ADD add eax, ecx EAX = EAX + ECX. Sets flags (ZF if result is 0, CF if overflow).
SUB sub esp, 16 ESP = ESP − 16. This is how functions allocate local variables on the stack.
CMP cmp eax, 0 Subtract (EAX − 0) but throw the result away — only keep the flags. Used before conditional jumps.
JMP jmp 0x7C00 Unconditionally set EIP to 0x7C00. Execution continues there.
JE / JZ je done Jump if Equal (or Zero flag set). Only jumps if the previous CMP said "equal."
JNE / JNZ jne loop Jump if Not Equal. Keep looping until values match.
JL / JG jl too_small Jump if Less / Greater than. Uses signed comparison flags.
PUSH push eax ESP -= 4 (grow stack down), then write EAX to memory at [ESP]. The stack grows downward in x86 — this surprises everyone the first time.
POP pop ebx Read 4 bytes from [ESP] into EBX, then ESP += 4 (shrink stack). The reverse of PUSH.
CALL call my_func PUSH EIP (the return address), then JMP to my_func. When the function does RET, it POPs that address back into EIP.
RET ret POP the saved return address off the stack into EIP. Execution resumes after the CALL that called this function.
INT int 0x80 Trigger software interrupt number 0x80. This is how user programs call the kernel in BobOS (Module 11). The CPU looks up the handler address in the IDT and jumps to it.
INT int 0x13 BIOS interrupt 0x13 = disk services. The bootloader uses this to read sectors from disk into RAM (only works in Real Mode).
IRET iret Interrupt RETurn. Used at the end of interrupt handlers and to jump to user mode (Module 14). Pops EIP, CS, and EFLAGS off the stack — restoring the CPU state from before the interrupt.
CLI / STI cli CLear Interrupts / SeT Interrupts. CLI temporarily disables hardware interrupts (like the keyboard or timer) so a critical section of kernel code can't be interrupted mid-way through.
HLT hlt Halt the CPU until the next interrupt arrives. Used in the kernel idle loop to save power instead of spinning pointlessly.
NOP nop No Operation. Does nothing for exactly one CPU cycle. Used for alignment, timing, or padding.
LGDT lgdt [gdt_ptr] Load Global Descriptor Table. Tells the CPU where in memory the GDT lives. Used once during boot (Module 04).
LIDT lidt [idt_ptr] Load Interrupt Descriptor Table. Tells the CPU where interrupt handler addresses are stored (Module 05).
OR / AND or eax, 1 Bitwise OR. or eax, 1 sets bit 0 of EAX without touching other bits. Used to flip individual bits in control registers.

GCC Inline Assembly — The Hybrid

Sometimes you need one or two assembly instructions inside a C function. GCC lets you embed them using asm volatile("..."):

/* Read a value from CR0 into a C variable */
uint32_t cr0;
asm volatile("mov %%cr0, %0" : "=r"(cr0));

/* The %% means a literal % (register prefix in AT&T syntax)
   The %0 is a placeholder for the first output operand
   "=r"(cr0) means "store the result in any register, then in cr0" */

/* Write to CR0 */
asm volatile("mov %0, %%cr0" :: "r"(cr0));

/* Read EFLAGS */
uint32_t flags;
asm volatile("pushf; pop %0" : "=r"(flags));
AT&T vs Intel Syntax

There are two ways to write x86 assembly. NASM uses Intel syntax: mov eax, 5 (destination first). GCC inline asm uses AT&T syntax: movl $5, %eax (source first, % before registers, $ before constants). The tutorials use Intel syntax in .asm files and AT&T syntax inside asm volatile() blocks. The meaning is identical; only the notation differs.

06 Memory Addresses & The Memory Map

Head First Moment

RAM is like a giant row of numbered mailboxes — 4,294,967,296 of them in a 32-bit system (4 billion = 4 GB). Each mailbox holds exactly 1 byte. An "address" is just a mailbox number. When the CPU says "read from 0xB8000," it's asking "what's in mailbox number 753,664?" The layout of who owns which mailboxes is called the memory map.

The x86 Physical Memory Map

When a PC powers on, certain address ranges are pre-assigned to specific hardware — even before your OS loads. This is fixed by the PC standard:

0x00000000
Interrupt Vector Table (IVT) — first 1KB in Real Mode
0x00000400
BIOS Data Area — 256 bytes of BIOS variables
0x00007C00
★ BOOTLOADER LOAD ADDRESS — BIOS always loads 512 bytes here
0x00007E00
Free RAM — where our kernel loads (after the bootloader)
0x000A0000
VGA graphics memory (VESA modes)
0x000B8000
★ VGA TEXT BUFFER — write here to print to screen (Module 03)
0x000C0000
Video BIOS ROM
0x000F0000
System BIOS ROM
0x00100000
Extended RAM starts (1 MB+) — where most of our kernel lives
0x00400000
User programs load here (ELF base address, Module 16)
0xBFFFFFFF
Top of user space (below kernel)
0xC0000000
Kernel virtual address space (top 1 GB)
0xFFFFFFFF
Top of 32-bit address space

Why 0x7C00?

The BIOS always loads the bootloader at address 0x7C00. This is a historical accident from the original IBM PC (1981). The designers reserved the bottom 32 KB for the OS, then the bootloader at 0x7C00, leaving exactly 512 bytes for it and 512 bytes below 0x8000 for the stack. Every x86 PC still does this in 2025.

Physical vs Virtual Addresses

Before paging (Module 07): every address you use is a physical address — the actual mailbox number in RAM. After paging: every address in a program is a virtual address — the CPU's Memory Management Unit (MMU) translates it to a physical address using a table of your choosing. Two programs can both use address 0x400000 in their virtual space — they map to different physical frames. This is how process isolation works.

What "Identity Mapping" Means

In early paging setup (Module 07), we create a page table where virtual address X maps to physical address X. This is called "identity mapping" — like a map where every road on the map corresponds exactly to the same road in real life, same scale, 1:1. We do this for the kernel so that addresses don't change when we enable paging.

07 The Stack & Function Calls

Head First Moment

The stack is a region of RAM used like a spring-loaded plate dispenser at a cafeteria. You push a plate (PUSH) and the spring compresses — the top of the stack goes down in memory. You pop a plate (POP) and it springs back up. The important rule: x86 stacks grow downward. High addresses are the "bottom" of the stack; low addresses are the "top."

The Call Convention (How C Functions Work in Assembly)

; Calling: result = add(3, 4);
push 4          ; push second argument
push 3          ; push first argument
call add        ; PUSH EIP (return addr), JMP to add

; Inside add():
push ebp        ; save caller's frame pointer
mov ebp, esp    ; set new frame base
sub esp, 8      ; reserve 8 bytes for local vars

; Access arguments:  [ebp + 8] = first arg (3), [ebp + 12] = second arg (4)
; Access locals:     [ebp - 4] = first local,   [ebp - 8] = second local

mov eax, [ebp + 8]    ; EAX = 3
add eax, [ebp + 12]   ; EAX = 3 + 4 = 7
; return value is in EAX

mov esp, ebp    ; restore stack pointer (discard locals)
pop ebp         ; restore caller's frame pointer
ret             ; POP return address → EIP
Why Does Context Switching Save ESP?

When BobOS switches from process A to process B (Module 10), it saves A's ESP value and loads B's ESP. Each process has its own kernel stack. Saving/restoring ESP is all that's needed to "save" and "restore" the entire call chain — because all the local variables, return addresses, and saved registers are already on that stack. ESP is the thread's entire state.

08 Bits, Bytes & Bitwise Operations

Head First Moment

A bit is a light switch: 0 = off, 1 = on. Eight switches together = 1 byte. Bitwise operations let you flip individual switches without touching the others. This is how OS code packs multiple yes/no flags into a single number — and how you read/write specific fields in hardware registers.

The Four Bitwise Operations

/* OR: set specific bits (turn switches ON) */
cr0 = cr0 | 0x1;    /* set bit 0 (PE = protected mode) */
cr0 |= 0x80000000;  /* set bit 31 (PG = paging) — same thing, shorthand */
/* Before: cr0 = 0000...0000 */
/* After:  cr0 = 0000...0001 — only bit 0 changed, nothing else touched */

/* AND: clear specific bits (turn switches OFF) */
pte = pte & ~0x2;   /* clear bit 1 (remove WRITE permission) */
/* ~0x2 = NOT 0x2 = 0xFFFFFFFD = 1111...1101 — AND keeps everything except bit 1 */

/* XOR: toggle bits (flip a switch) */
flags ^= 0x200;  /* toggle bit 9 (interrupt enable flag) */
/* XOR with 1 flips the bit: 0→1, 1→0 */

/* NOT: invert all bits */
mask = ~0x2;     /* 0xFFFFFFFD — used as a mask in AND above */

Bit Shifting

/* Left shift: multiply by 2^n  */
1 << 3  = 8      (0001 → 1000 = move bit 3 positions left)
1 << 12 = 4096   (= one page size!)

/* Right shift: divide by 2^n or extract a field */
address >> 12    /* throw away bottom 12 bits = page number */
address & 0xFFF  /* keep only bottom 12 bits = offset within page */

/* Extracting bit fields from a register */
uint32_t pde = page_directory[index];
uint32_t frame_addr = pde & 0xFFFFF000;  /* top 20 bits = frame number */
int present = pde & 1;                   /* bit 0 = is page present? */
int writable = (pde >> 1) & 1;          /* bit 1 = is page writable? */

Paging Uses Bit Fields Everywhere

A page directory entry (32 bits) packs multiple fields into one 4-byte number:

Bits 31–12:  Physical frame address (the page it points to)
Bit 11–9:    Available for OS use (we use bit 9 for CoW flag!)
Bit 8:       Global
Bit 7:       Page size (0=4KB, 1=4MB)
Bit 6:       Dirty (CPU sets this when page is written)
Bit 5:       Accessed (CPU sets this when page is read/written)
Bit 4:       Cache disable
Bit 3:       Write-through
Bit 2:       User/Supervisor (PAGE_USER — must be set for user access!)
Bit 1:       Read/Write (PAGE_WRITE)
Bit 0:       Present (PAGE_PRESENT — must be 1 for CPU to use this entry)

#define PAGE_PRESENT  0x001   /* 0000 0000 0001 */
#define PAGE_WRITE    0x002   /* 0000 0000 0010 */
#define PAGE_USER     0x004   /* 0000 0000 0100 */
#define PAGE_COW      0x200   /* 0010 0000 0000 (our custom bit 9) */

09 CPU Privilege Rings

Head First Moment

Imagine a nuclear power plant. The control room (Ring 0) has operators who can flip any switch — shut down the reactor, redirect power, override safety systems. Visitors in the observation gallery (Ring 3) can only watch through glass. The hardware enforces this — visitors physically cannot reach the control panel. CPU rings work the same way: the hardware prevents user programs from issuing privileged instructions.

Ring 0 — Kernel Mode
Can execute ANY instruction. Can read/write CR0, CR3. Can use LGDT, LIDT, CLI, STI, HLT. Can access all memory. This is where BobOS kernel code runs.
Ring 3 — User Mode
Can only execute safe instructions. Any attempt to read CR0, use LGDT, or access kernel memory → immediate hardware exception (General Protection Fault). Shell, user programs, and test apps run here.

Rings 1 and 2 exist in the x86 spec but are never used by modern OSes (Linux, Windows, BobOS). The real divide is always Ring 0 vs Ring 3.

How the CPU Knows What Ring You're In

The bottom 2 bits of the CS (Code Segment) register are the Current Privilege Level (CPL). CS=0x08 means you're in Ring 0 (kernel); CS=0x1B means you're in Ring 3 (user). The CPU checks CPL against every instruction you execute. This is why the GDT (Module 04) has separate entries for kernel code (0x08, CPL=0) and user code (0x1B, CPL=3).

/* GDT selector encoding:
   Bits 15–3: Index into GDT (which descriptor)
   Bit  2:    Table indicator (0=GDT, 1=LDT)
   Bits 1–0:  Requested Privilege Level (RPL)

   0x08 = 0000 1000b = index 1, GDT, RPL=0 → kernel code (Ring 0)
   0x10 = 0001 0000b = index 2, GDT, RPL=0 → kernel data
   0x1B = 0001 1011b = index 3, GDT, RPL=3 → user  code (Ring 3)
   0x23 = 0010 0011b = index 4, GDT, RPL=3 → user  data            */
How a Syscall Crosses the Ring Boundary

A user program (Ring 3) executes int 0x80. The CPU looks up interrupt 0x80 in the IDT, sees it has a DPL=3 gate (a special field that says "user programs are allowed to trigger this"), and automatically: saves the user stack pointer and instruction pointer, switches CS to 0x08 (Ring 0), switches the stack to the kernel stack (from TSS.esp0), and jumps to the handler. The kernel runs in Ring 0. When it's done, iret reverses all of this in one instruction.

10 Interrupts & Exceptions

Head First Moment

Interrupts are how hardware gets the CPU's attention. Without them, the CPU would have to constantly ask "has a key been pressed? how about now? now?" (polling). With interrupts, the keyboard says "HEY!" and the CPU immediately pauses whatever it's doing, runs the keyboard handler, then resumes — like a surgeon being paged in the middle of an operation. The CPU saves its exact state, handles the emergency, and picks up exactly where it left off.

Three Types of Interrupts

/* 1. HARDWARE INTERRUPTS (IRQs) — from physical devices */
IRQ 0  → Timer (fires 100 times/second — drives the scheduler)
IRQ 1  → Keyboard (key pressed or released)
IRQ 14 → ATA Primary Hard Disk (read/write complete)

/* After PIC remapping (Module 05), these arrive as: */
IRQ 0  → IDT vector 32 (0x20)
IRQ 1  → IDT vector 33 (0x21)
/* Why remap? Vectors 0–31 are reserved for CPU exceptions */

/* 2. CPU EXCEPTIONS — the CPU itself triggered this */
Vector 0  → Divide by Zero
Vector 13 → General Protection Fault (Ring 3 tried a privileged instruction)
Vector 14 → Page Fault (accessed unmapped/protected memory — CR2 has the address)

/* 3. SOFTWARE INTERRUPTS — your code triggered this deliberately */
int 0x80  → System call (BobOS kernel entry point)

The IDT — The Interrupt Lookup Table

The Interrupt Descriptor Table is an array of 256 entries. Each entry says "when interrupt N fires, jump to this address." When the keyboard fires IRQ 1 (mapped to vector 33), the CPU looks up IDT[33], finds the address of your keyboard handler, and jumps there. Module 05 builds this table.

The Interrupt Handler Pattern

; Every interrupt handler does the same thing:
isr_keyboard:
    pushad              ; save ALL 8 general-purpose registers
    push ds             ; save segment registers
    push es

    ; ... do the actual work (read keyboard port, etc.) ...

    ; Send EOI (End of Interrupt) to PIC — REQUIRED after hardware IRQ
    mov al, 0x20
    out 0x20, al        ; tells PIC "I handled it, send more"

    pop es
    pop ds
    popad               ; restore all registers (in reverse order)
    iret                ; restore EIP, CS, EFLAGS — resume where we left off
Forgetting EOI Breaks Everything

The PIC (Programmable Interrupt Controller) will not send any more IRQs until you send an EOI (0x20 to port 0x20). Forget it and your keyboard stops working after the first keypress, your timer stops firing, and everything freezes. This is one of the most common beginner bugs in OS development.

11 Port I/O: Talking to Hardware

Head First Moment

Imagine the CPU has 65,536 post boxes, numbered 0 to 0xFFFF. Each hardware device owns one or more boxes. To send the keyboard controller a command, you drop a letter in its box (OUT instruction). To read the last key pressed, you pick up what's in its mailbox (IN instruction). These "boxes" are called I/O ports and they're completely separate from memory addresses.

/* Reading from a port (IN instruction) */
uint8_t inb(uint16_t port) {
    uint8_t val;
    asm volatile("inb %1, %0" : "=a"(val) : "Nd"(port));
    return val;
}

/* Writing to a port (OUT instruction) */
void outb(uint16_t port, uint8_t val) {
    asm volatile("outb %0, %1" :: "a"(val), "Nd"(port));
}

Key Port Addresses You'll Encounter

0x60   — Keyboard data port: read the scancode of the last pressed key
0x64   — Keyboard status/command port
0x20   — PIC1 command port: send EOI (0x20) here after IRQ 0–7
0x21   — PIC1 data port: set IRQ mask (which IRQs to allow)
0xA0   — PIC2 command port: send EOI (0x20) here after IRQ 8–15
0x70   — CMOS/RTC index register (real-time clock)
0x1F0  — ATA Primary drive data port (read/write disk sectors)
0x1F7  — ATA Primary drive command/status port

12 The Build Pipeline: Compile → Link → Run

Head First Moment

Your OS source code is just text. Turning it into something QEMU can boot requires a chain of transformations: the assembler converts .asm to raw machine bytes; the compiler converts .c to object files; the linker combines them all, assigns final addresses, and produces the bootable binary. Each step has a specific tool and specific flags.

Step by Step

# 1. NASM assembles the bootloader to raw binary
nasm -f bin bootloader.asm -o boot.bin
# -f bin = output raw bytes, no extra headers

# 2. GCC compiles C files to object files
i686-elf-gcc -c kernel.c -o kernel.o -ffreestanding -nostdlib
# -ffreestanding = don't assume a standard C library exists
# -nostdlib      = don't link standard libraries (we have none)
# -c             = compile only, don't link yet
# i686-elf-gcc   = cross compiler targeting 32-bit x86 (not your host CPU)

# 3. GNU LD links everything together
i686-elf-ld -T linker.ld boot.o kernel.o -o kernel.bin
# -T linker.ld = use our custom linker script

# 4. Combine bootloader + kernel into a disk image
cat boot.bin kernel.bin > disk.img
# QEMU reads disk.img as if it were a physical hard disk

The Linker Script (linker.ld)

The linker needs to know "put the kernel at address 0x1000 in memory." The linker script tells it where to place each section:

SECTIONS {
    . = 0x1000;          /* start placing code at address 0x1000 */

    .text : {            /* .text = executable code section */
        *(.text)         /* include .text from ALL object files */
    }

    .data : {            /* .data = initialized global variables */
        *(.data)
    }

    .bss : {             /* .bss = zero-initialized globals */
        *(.bss)
        *(COMMON)
    }
}
What is BSS?

BSS stands for Block Started by Symbol — a section for global variables that start as zero. Instead of storing 10,000 zeros in the binary (wasting disk space), the BSS section just records how many bytes need to be zeroed. The bootloader or kernel startup code zeroes this region at boot. You'll see bss_start and bss_end symbols used in Module 02's startup code.

Cross-Compiler — Why i686-elf-gcc Instead of Just gcc?

Your Windows machine's GCC compiles programs for Windows (64-bit). We need to compile programs for a bare-metal 32-bit x86 PC with no operating system. A cross-compiler is a compiler that runs on machine A (your Windows PC) but produces code for machine B (the bare-metal QEMU PC). The prefix i686-elf- means "target: i686 (32-bit x86), file format: ELF." Without a cross-compiler, GCC would produce code that assumes Windows libraries exist — which they don't in our bare-metal world.

The 0x55AA Boot Signature

The BIOS checks the last 2 bytes of the 512-byte boot sector. If they're 0x55 0xAA, it says "this is a bootable disk" and jumps to 0x7C00. If those bytes are wrong, the BIOS ignores the disk. This is why every bootloader ends with: times 510-($-$$) db 0 (pad to byte 510 with zeros) followed by dw 0xAA55 (write the signature — note: stored little-endian, so 0x55 comes first in memory).
