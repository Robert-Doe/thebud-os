The single insight you need going in

You already use struct vfs_ops vtables to dispatch open/read/write to different filesystems. A driver framework is the same idea one layer down: struct driver_ops vtables dispatching to different hardware. If you drew the VFS dispatch diagram from Module 19 and replaced "filesystem" with "hardware device," you've already understood Module 27.

01 — The Big Analogy

Head First Moment

A USB hub has a standard connector. You can plug in a mouse, a keyboard, a flash drive, or a webcam — all through the same port, all using the same USB protocol. The hub doesn't know what's plugged in until it asks ("enumerate"). Each device announces its type and capabilities. The host then loads the right driver.

Your driver framework works identically. The kernel has a standard "connector" (driver_ops vtable). Each driver fills it in and calls driver_register(). At boot, the kernel calls probe() on every registered driver. The ones that respond "I'm here" get a /dev/ entry. From that point on, user space doesn't know or care what's behind /dev/eth0.

02 — The driver_ops Vtable

/* driver.h — every driver fills this in */
struct driver_ops {
    const char *name;       /* "kbd", "disk", "eth0" — becomes /dev/<name> */
    dev_type_t  type;       /* DEV_CHAR, DEV_BLOCK, or DEV_NET */

    int (*probe)(void);                             /* detect hardware */
    int (*read) (uint8_t *buf, uint32_t len);       /* read data       */
    int (*write)(const uint8_t *buf, uint32_t len); /* write data      */
    int (*ioctl)(uint32_t cmd, void *arg);          /* device control  */
};
You've Seen This Before

Compare to struct vfs_ops from Module 19: open · read · write · close. The shape is identical. probe() replaces open() (it's the one-time "are you there?" check rather than per-fd open). ioctl() is added for device-specific commands that don't fit read/write. The pattern — name + function pointers — is the same because the problem is the same: dispatch to different implementations through a common interface.

Implementing a driver: keyboard example

/* A driver wrapper around the existing keyboard code */
static int kbd_probe(void) {
    /* Keyboard always exists on PS/2 — just verify IRQ1 is wired */
    keyboard_init();
    return 0;   /* always succeeds */
}
static int kbd_read(uint8_t *buf, uint32_t len) {
    int n = 0;
    while (n < (int)len) {
        char c = keyboard_getchar();
        if (!c) break;
        buf[n++] = (uint8_t)c;
    }
    return n;
}
static int kbd_ioctl(uint32_t cmd, void *arg) {
    (void)cmd; (void)arg;
    return -1;   /* no ioctl commands defined yet */
}

struct driver_ops kbd_driver = {
    .name  = "kbd",
    .type  = DEV_CHAR,
    .probe = kbd_probe,
    .read  = kbd_read,
    .write = 0,       /* keyboard is read-only */
    .ioctl = kbd_ioctl,
};

03 — Registration and Probe

/* driver.c */
struct driver_entry driver_table[MAX_DRIVERS];
int driver_count = 0;

int driver_register(struct driver_ops *ops) {
    if (driver_count >= MAX_DRIVERS) return -1;
    driver_table[driver_count].ops       = ops;
    driver_table[driver_count].active    = 0;
    driver_table[driver_count].dev_major = next_major++;
    driver_count++;
    return 0;
}

void driver_probe_all(void) {
    for (int i = 0; i < driver_count; i++) {
        struct driver_ops *ops = driver_table[i].ops;
        vga_print("[driver] probing: "); vga_print(ops->name);

        if (ops->probe && ops->probe() == 0) {
            driver_table[i].active = 1;
            vga_print(" ... OK\n");
        } else {
            vga_print(" ... not found\n");
        }
    }
}
probe() Returns 0 = Present, -1 = Absent

For real hardware, probe() tries to talk to the device — send a reset, read an ID register, check an I/O port. If the device doesn't respond, probe() returns -1 and the driver stays inactive. The NE2000 probe does a hardware reset and checks that the ISR register acknowledges it. A PCI driver would read the vendor/device ID from config space.

Registering drivers in kernel_main()

/* kernel.c — before any user processes start */
void kernel_main(void) {
    /* ... all the usual init ... */
    driver_init();

    driver_register(&kbd_driver);
    driver_register(&disk_driver);
    driver_register(&ne2000_net_driver);

    devfs_init();         /* mount /dev */
    driver_probe_all();   /* probe each in order */

    /* now /dev/kbd, /dev/disk, /dev/eth0 exist if probe() succeeded */
    process_create(user_main);
    /* ... */
}

04 — devfs: /dev as a VFS Backend

/* devfs.c — open() is just a driver lookup */
int devfs_open(const char *name, struct file_descriptor *fd) {
    const char *dev_name = name;
    /* strip "/dev/" prefix */
    if (name[0]=='/' && name[4]=='/') dev_name += 5;

    struct driver_ops *ops = driver_find(dev_name);
    if (!ops) return -1;

    fd->type  = FD_DEVFS;
    fd->inode = (uint32_t)(uintptr_t)ops; /* store vtable pointer */
    fd->valid = 1;
    return 0;
}

/* read() just calls through the vtable */
int devfs_read(struct file_descriptor *fd, uint8_t *buf, uint32_t len) {
    struct driver_ops *ops = (struct driver_ops *)(uintptr_t)fd->inode;
    if (!ops || !ops->read) return -1;
    return ops->read(buf, len);
}
The Elegant Part: VFS Dispatch Doesn't Change

The VFS layer's vfs_read(fd, buf, n) function from Module 19 doesn't need to know about devfs at all. It checks fd->type: if FD_DEVFS, it calls devfs_read() instead of the filesystem read. One new if branch in the VFS dispatch is all it takes to add an entire new class of file descriptors.

05 — SYS_IOCTL: When Read/Write Aren't Enough

/* syscall.c — case SYS_IOCTL = 24 */
case SYS_IOCTL: {
    int fd_num = (int)frame->ebx;
    uint32_t cmd = (uint32_t)frame->ecx;
    void *arg    = (void *)(uintptr_t)frame->edx;

    struct file_descriptor *fd = &vfs_get_fd_table()[fd_num];
    if (!fd->valid || fd->type != FD_DEVFS) return SYSCALL_EBADF;
    return devfs_ioctl(fd, cmd, arg);
}

Example: query NIC MAC address via ioctl

/* Defined cmd numbers — agree between kernel and user space */
#define IOCTL_ETH_GET_MAC  0x8901

/* In user_prog.c */
uint8_t mac[6];
int fd = sys_open("/dev/eth0", 0);
syscall(SYS_IOCTL, fd, IOCTL_ETH_GET_MAC, (int)mac);
/* mac[] now contains the NE2000's hardware MAC address */

07 — Brain Exercise

Sharpen Your Pencil

You want to add a /dev/null device — reads return 0 bytes, writes silently discard everything (like Unix's /dev/null). Write the complete driver_ops struct for it. How many lines of code? Write it before reading on.

Answer: 7 lines. probe() returns 0 (always present), read() returns 0 (EOF), write() returns len (accept all bytes, discard them), ioctl() returns -1. name="null", type=DEV_CHAR. That's it. The framework does the rest — one driver_register() call and /dev/null exists.

There Are No Dumb Questions

Q: How does Linux's driver model differ from this?
Linux uses a bus-based model: PCI, USB, platform, and other bus types each have their own probe/remove callbacks. Drivers declare which device IDs they support (vendor:device pairs for PCI, compatible strings for device tree). The bus core matches drivers to devices automatically. Our model is simpler: no bus abstraction, no hotplug, no device tree — just a flat table of statically registered drivers.
Q: What is a major and minor device number?
In Unix, every device file has two numbers: major (which driver handles it) and minor (which instance within that driver). /dev/sda is major=8, minor=0. /dev/sdb is major=8, minor=16. The kernel routes open(/dev/sda) to the driver registered for major=8. Our driver_table index acts as an implicit major number — we just don't expose it to user space yet.
Q: Why does ioctl take a void* arg instead of separate registers?
ioctl commands often pass complex structs — a struct termios for serial port settings, a struct ifreq for network interface config. You can't fit an arbitrary struct in CPU registers. The convention is to pass a pointer to user-space memory containing the argument. The kernel then copies it in (copy_from_user) or copies results out (copy_to_user) to avoid security issues. We skip the copy check here for simplicity.

08 — What's Next

Module 28 — POSIX Compliance

With a driver framework and devfs in place, the last step is making BobOS's syscall interface look like POSIX. Module 28 adds errno, standardizes error codes, wraps socket calls in BSD-compatible socket()/bind()/sendto()/recvfrom() semantics, adds select() for waiting on multiple fds, and adds stat() and lseek(). After Module 28, a simple POSIX program can be cross-compiled and run on BobOS with minimal changes.
