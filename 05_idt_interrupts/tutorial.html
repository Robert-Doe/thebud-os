IDT & Interrupts

The IDT is your OS's emergency contact list. When the CPU divides by zero, accesses bad memory, or the keyboard fires — it looks up the IDT and calls your handler. Without this, any exception silently resets the machine.

01 — The Big Analogy

Head First Moment

Think of the IDT as a 256-entry phone directory nailed to the CPU's wall. When something urgent happens — a divide-by-zero, a page fault, a key press — the CPU looks up the vector number, finds the phone number (the handler address) in the directory, and calls it. Without a directory, it has no idea who to call, so it panics and reboots.

You build that phone directory. You decide what happens when the CPU divides by zero (print an error and kill the process). You decide what happens on IRQ1 (read the keyboard). You are the operator.

02 — Two Things This Module Builds

Part 1: The IDT

A table of 256 gate descriptors. Each one says: "when interrupt N fires, jump to this address at this privilege level." We fill entries 0–31 with CPU exception handlers, 32–47 with IRQ handlers, and leave the rest empty for now (0x80 comes in Module 11).

Part 2: The PIC

The 8259A Programmable Interrupt Controller sits between the hardware (keyboard, timer, disk) and the CPU. By default, hardware IRQs conflict with CPU exceptions (both use vectors 0–15). We reprogram the PIC to remap IRQs to vectors 32–47, where they don't collide.

03 — The ISR Assembly Stubs

Here's a critical detail: when the CPU calls your interrupt handler, the C calling convention doesn't apply. The CPU pushes its own state onto the stack (EIP, CS, EFLAGS, and for some exceptions an error code). You need assembly "stubs" that capture all of this, then call your C handler.

; isr.asm — one stub per interrupt vector
; ISR 0: divide by zero (no error code)
isr0:
    push dword 0    ; fake error code (CPU doesn't push one for #DE)
    push dword 0    ; interrupt number
    jmp isr_common_stub

; ISR 14: page fault (CPU DOES push an error code)
isr14:
    push dword 14   ; interrupt number
    jmp isr_common_stub

isr_common_stub:
    pusha                   ; save EAX,ECX,EDX,EBX,ESP,EBP,ESI,EDI
    push ds
    push es
    mov ax, 0x10            ; switch to kernel data segment
    mov ds, ax
    mov es, ax
    push esp                ; pass pointer to stack frame as argument
    call isr_handler        ; the C function
    add esp, 4
    pop es
    pop ds
    popa
    add esp, 8              ; discard error code + vector number
    iret                    ; restore EIP, CS, EFLAGS
Why the fake error code?

Some CPU exceptions (like #PF page fault) push an error code; others (like #DE divide error) don't. If you handle both cases with one isr_common_stub, your stack frame must be uniform. So for exceptions that don't push an error code, you push a fake zero yourself — then every handler sees the same interrupt_frame struct layout.

04 — The interrupt_frame Struct

struct interrupt_frame {
    /* pushed by isr_common_stub (in reverse order of pusha) */
    uint32_t edi, esi, ebp, esp_dummy;
    uint32_t ebx, edx, ecx, eax;
    uint32_t ds, es;
    /* pushed by individual stubs */
    uint32_t int_no, err_code;
    /* pushed by the CPU automatically */
    uint32_t eip, cs, eflags;
    /* only present when crossing privilege levels (ring 3 → 0): */
    uint32_t user_esp, user_ss;
};

Your C handler receives a pointer to this struct. You can read any register value, inspect the faulting instruction (eip), and even modify them — whatever you write back gets restored by iret.

05 — PIC Remapping

/* pic.c — reprogram both PIC chips */
void pic_init(void) {
    /* ICW1: start init sequence */
    outb(0x20, 0x11);   /* master PIC command */
    outb(0xA0, 0x11);   /* slave PIC command */
    /* ICW2: vector offsets */
    outb(0x21, 0x20);   /* master IRQs → vectors 32–39 */
    outb(0xA1, 0x28);   /* slave IRQs  → vectors 40–47 */
    /* ICW3: cascade wiring */
    outb(0x21, 0x04);   /* master: slave on IRQ2 */
    outb(0xA1, 0x02);
    /* ICW4: 8086 mode */
    outb(0x21, 0x01);
    outb(0xA1, 0x01);
    /* mask all IRQs initially */
    outb(0x21, 0xFF);
    outb(0xA1, 0xFF);
}
Unmasking IRQs

After PIC init, all IRQs are masked (disabled). To enable the timer (IRQ0): pic_clear_mask(0). Keyboard (IRQ1): pic_clear_mask(1). Each pic_clear_mask call clears one bit in the PIC's Interrupt Mask Register. At the end of every IRQ handler, you must send an EOI (End of Interrupt) to the PIC: outb(0x20, 0x20).

There Are No Dumb Questions

Q: What happens if I don't send EOI at the end of an IRQ handler?
The PIC thinks you're still handling the interrupt. It won't send any more IRQs from that IRQ line (or any lower-priority IRQs) until it gets EOI. Your timer stops ticking, your keyboard goes dead, and the OS hangs. EOI is the single most common IRQ handler bug.
Q: What's the difference between an interrupt and an exception?
Exceptions are synchronous — they happen because of something the CPU just tried to do (divide by zero, bad memory access). Interrupts are asynchronous — they happen at any time because external hardware (keyboard, timer) signaled the CPU. Both use the same IDT mechanism; the difference is in who triggers them.
