Flags, comparisons, and jumps: how "if" actually happens

There is no if instruction. There's "do some arithmetic, notice some leftover facts about the result as single bits, then optionally jump based on those bits." Every loop and branch you've ever written boils down to exactly that.

EFLAGS: the CPU's sticky notes

Almost every arithmetic and logic instruction silently updates a set of single-bit flags describing the result. Compare and jump instructions just read those bits — they don't recompute anything.

FlagSet when…
ZF (Zero)the result was exactly zero
SF (Sign)the result's top bit is 1 (negative, if signed)
CF (Carry)an unsigned add overflowed past the top, or unsigned subtract borrowed
OF (Overflow)a signed add/subtract produced a result that can't fit — sign flipped wrongly
PF (Parity)the low byte of the result has an even number of 1 bits (rarely used directly)

CF vs OF — the question every beginner gets backwards

CF is about unsigned wraparound (255+1 wraps to 0, CF=1). OF is about signed wraparound (127+1 as signed bytes becomes -128, OF=1). The exact same addition can set one, both, or neither — it depends entirely on whether you, the programmer, intended the bits as signed or unsigned. The hardware computes both every time and lets the chosen jump instruction decide which one matters.

cmp is just sub that throws away the answer

cmp a, b internally computes a − b, sets the flags exactly as a real subtraction would, and discards the numeric result — only the flags survive. This is the single fact that makes the whole system click:

cmp eax, ebx ; if eax == ebx: result of (eax-ebx) is 0 -> ZF=1 ; if eax < ebx (unsigned): subtraction borrows -> CF=1 ; if eax < ebx (signed): SF != OF

test a, b is the same idea but for bitwise AND instead of subtraction — handy for checking individual bits without modifying anything: test eax, eax followed by a jump-if-zero is the idiomatic way to check "is EAX zero?"

Conditional jumps: reading flags, not values

A conditional jump like je doesn't compare anything itself — it just asks "is ZF currently 1?" That's why cmp (or any flag-setting instruction) must come immediately before the jump that depends on it.

Why jg/jl vs ja/jb both exist — and why mixing them up is a real bug class

x86 gives you a signed family (jg, jl, jge, jle) and a separate unsigned family (ja, jb, jae, jbe) because the bit pattern 0xFFFFFFFF means "-1" if signed and "4,294,967,295" if unsigned — same bits, opposite ordering. Using jl when you meant "unsigned less than" is a classic OS-dev bug, especially when comparing pointers or sizes (which are inherently unsigned) — the comparison silently does the wrong thing instead of erroring.

From C-like control flow to raw jumps

A while loop is nothing but a comparison and a conditional jump back to the top:

// while (count != 0) { ... count--; } loop_top: cmp ecx, 0 je loop_end ; ... loop body ... dec ecx jmp loop_top loop_end:

And an if/else is a comparison, a conditional jump over the "then" block, with an unconditional jump at the end of "then" to skip "else":

// if (a == b) { x(); } else { y(); } cmp eax, ebx jne else_branch ; call x() jmp end_if else_branch: ; call y() end_if:

The dedicated loop counter: ECX + loop

x86 has a single instruction, loop, that decrements ECX and jumps if ECX is still nonzero — combining dec + jnz into one opcode. It exists purely because counted loops are so common:

mov ecx, 10 ; loop 10 times again: ; ... body ... loop again ; ecx-- ; if ecx != 0, jump to again

It's rarely used in modern hand-tuned code (a separate dec/jnz pair is often faster on current CPUs), but you'll see it constantly in textbook examples and old boot code, so recognizing it instantly is worth the five seconds it takes to memorize.

Calling conventions: the unwritten contract

The CPU doesn't enforce "argument 1 goes in this register" — that's a software agreement between caller and callee, called a calling convention. Mismatch the convention between two pieces of code and you get garbage, not an error.

cdecl (classic 32-bit C)
args on the stack, caller cleans up
Arguments pushed right-to-left before call; return value in EAX; the caller adjusts ESP afterward (so functions can take a variable number of args, like printf).
System V AMD64 (modern 64-bit Linux)
first 6 args in registers
RDI, RSI, RDX, RCX, R8, R9 hold the first six integer/pointer arguments, in that order; only overflow args go on the stack. Far fewer memory accesses than cdecl.

Why this matters the moment you write an OS

Your kernel's interrupt handlers, your bootloader-to-kernel handoff, and any C code you link against assembly all depend on agreeing about a calling convention. Get it wrong and arguments silently land in the wrong register or at the wrong stack offset — the classic "it compiles and then does something insane" bug.

Try this: predict the flags and the jump

mov eax, 5 mov ebx, 5 cmp eax, ebx jne somewhere ; taken or not? mov ecx, 0xFFFFFFFF ; this is -1 if read as signed cmp ecx, 0 jl label_a ; taken or not? (signed) jb label_b ; taken or not? (unsigned)

Answer: jne somewhere is not taken — EAX equals EBX so ZF=1, and jne fires on ZF=0. The compare of ECX (0xFFFFFFFF) against 0: as a signed comparison, 0xFFFFFFFF means -1, which is less than 0, so jl label_a is taken. As an unsigned comparison, 0xFFFFFFFF is the largest possible value (4,294,967,295), which is not below 0, so jb label_b is not taken. Same bits, same cmp, opposite answers depending only on which jump family you read them with.
