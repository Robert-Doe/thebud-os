Page 05 — Capstone

From power-on to your kernel: a real boot sequence, byte by byte

Everything on the last four pages was preparation for this. We'll walk the exact path: BIOS hands control to 512 bytes of your code in 16-bit real mode, you build a descriptor table, flip one bit, and land in 32-bit protected mode with flat memory — the environment every "OS from scratch" tutorial assumes you already have.

real mode → protected mode GDT A20 line paging, briefly

Step 0: what the BIOS guarantees you

When a legacy BIOS finishes its power-on self test, it looks for a bootable disk: one whose first sector (512 bytes) ends with the magic bytes 0x55 0xAA at offset 510–511. If found, it loads those 512 bytes to physical address 0x7C00 and jumps there — in 16-bit real mode, with no paging, no memory protection, and only the bottom ~1MB of address space reachable.

; boot.asm — assembled with: nasm -f bin boot.asm -o boot.bin org 0x7C00 ; tell the assembler where this code will live bits 16 ; BIOS starts us in 16-bit real mode start: cli ; disable interrupts while we set up segments xor ax, ax mov ds, ax ; ds = 0 mov es, ax ; es = 0 mov ss, ax ; ss = 0 mov sp, 0x7C00 ; stack grows down from right below our code sti ; interrupts back on ; ... real-mode setup goes here (page 1 of 2) ... times 510-($-$$) db 0 ; pad to 510 bytes with zeros dw 0xAA55 ; the boot signature, little-endian on disk = AA 55... wait: db order!

Notice the last line: we want the bytes 0x55, 0xAA at offsets 510, 511 — and dw 0xAA55 emits exactly that, because a 16-bit immediate written with dw is stored little-endian (low byte first). This is endianness from page 02 showing up in literally the first 512 bytes of every x86 OS ever booted.

Why 0x7C00 specifically?

It's a historical IBM PC convention from the original 5150 — nothing more principled than "that's where it's always been." Real mode can address 1MB total (20-bit addresses, more on this below), and conventional RAM below the BIOS data area starts low; 0x7C00 leaves enough room below it for a small stack while staying comfortably under 0xA0000 where video memory begins.

Why we zero the segment registers explicitly

Real mode forms addresses as segment × 16 + offset — so physical address 0x7C00 could be reached as DS=0x0000,offset=0x7C00 OR as DS=0x07C0,offset=0x0000, among other combinations. The BIOS doesn't guarantee which one it used when it jumped to you. If you don't pin DS/ES/SS to a known value yourself, every [label] memory reference computes a different physical address than you intended — a brutal bug to chase blind.

Step 1: talk to the BIOS while you still can (16-bit only)

Real mode gives you one superpower you'll never have again after this page: BIOS interrupts. The instruction int 0x10 calls BIOS video services; int 0x13 calls disk services. Once you're in protected mode, these stop working — the BIOS's interrupt handlers were written for real-mode segment:offset addressing and 16-bit registers, so you must do everything yourself (your own video driver, your own disk driver) from that point on. This is why OS tutorials print a message and load the rest of the kernel from disk before switching modes.

; Print "Booting..." using BIOS teletype output (int 0x10, ah=0x0E) mov si, msg print_loop: lodsb ; al = [ds:si], si++ (note: si is 16-bit here) cmp al, 0 je print_done mov ah, 0x0E ; BIOS teletype function int 0x10 jmp print_loop print_done: msg: db "Booting...", 0

Step 2: the A20 line — a 1980s bug you must fix yourself

The original 8086 had only 20 address lines, so any address calculation that overflowed past 1MB silently wrapped around to 0 instead of erroring. When the 80286 added a 21st address line, IBM kept the wraparound behavior by default for backward compatibility with software that accidentally depended on it — by physically gating the 21st line (called A20) off unless explicitly enabled.

Every protected-mode OS must enable A20 before relying on memory above 1MB, or addresses silently alias back into the first megabyte. The classic method is via the keyboard controller:

enable_a20: in al, 0x92 ; read System Control Port A or al, 2 ; set bit 1 (the "fast A20" enable bit) out 0x92, al ; write it back

The in/out instructions read/write hardware I/O ports — a completely separate 16-bit address space from memory, accessed only via these two instructions (and implicitly via AL/AX/EAX and, for the port number, DX). This is how software talks to hardware controllers like the keyboard, disk, and PIC directly.

Step 3: build a GDT — the table that defines "what memory even is"

Protected mode doesn't use segment×16+offset addressing. Instead, each segment register becomes an index into a Global Descriptor Table (GDT) — an array of 8-byte entries, each describing a memory region's base address, size limit, and access permissions. For a basic "flat" OS, you define exactly two useful descriptors: one code segment and one data segment, both spanning the entire 4GB address space.

gdt_start: dq 0 ; entry 0 must be a null descriptor gdt_code: ; entry 1: code segment, base=0, limit=4GB dw 0xFFFF ; limit (low 16 bits) dw 0x0000 ; base (low 16 bits) db 0x00 ; base (next 8 bits) db 10011010b ; access byte: present, ring 0, code, executable, readable db 11001111b ; flags + limit (high 4 bits): 4KB granularity, 32-bit db 0x00 ; base (high 8 bits) gdt_data: ; entry 2: data segment, same range, different access byte dw 0xFFFF, 0x0000 db 0x00, 10010010b, 11001111b, 0x00 gdt_end: gdt_descriptor: dw gdt_end - gdt_start - 1 ; size of GDT minus 1, 16-bit dd gdt_start ; linear address of GDT, 32-bit

The base/limit fields are deliberately scrambled across the 8 bytes for historical reasons (backward compatibility with the 80286's smaller descriptor format) — this is exactly the kind of "go compute the address by hand" exercise page 03 was building toward. The access byte's bits encode present/absent, privilege ring (0=kernel through 3=user), and segment type — full detail belongs in an Intel manual, but recognizing the shape (1001 1010 for kernel code, 1001 0010 for kernel data) gets you through almost every tutorial's boilerplate.

Step 4: the actual mode switch — flip one bit, then immediately jump

This is the single most important sequence in the whole page. Three things have to happen in this exact order, with no instructions in between the flag flip and the jump:

lgdt [gdt_descriptor] ; 1. load the GDT's address into the CPU's GDTR register mov eax, cr0 or eax, 1 ; 2. set bit 0 of CR0 — the Protection Enable (PE) bit mov cr0, eax ; we are now technically "in" protected mode... jmp 0x08:protected_mode_start ; 3. far jump — REQUIRED, see below bits 32 protected_mode_start: mov ax, 0x10 ; 0x10 = offset of gdt_data = selector for data segment mov ds, ax mov es, ax mov ss, ax mov esp, 0x90000 ; new, bigger 32-bit stack ; we are now genuinely running 32-bit protected-mode code

Why a "far jump" and not a regular jmp?

Setting CR0's PE bit changes how the CPU interprets instructions you fetch after this point, but the CPU's instruction prefetch queue may already contain bytes it fetched and decoded before the switch, using the old 16-bit rules. A far jump (one that explicitly reloads CS with a new selector — here, 0x08, the offset of gdt_code in the GDT) flushes that stale prefetch queue and forces the CPU to fetch fresh bytes using the new mode and the new code segment. Skip this and you get bizarre, hard-to-debug crashes right after the mode switch.

Why selector 0x08 and 0x10, not "1" and "2"?

A segment selector isn't just an index — it's a 16-bit value where bits 3–15 are the descriptor's index (×8, since each descriptor is 8 bytes) and the bottom 3 bits encode the requested privilege level and table type. gdt_code is the 2nd entry (index 1) → selector 1×8 = 0x08. gdt_data is the 3rd entry (index 2) → selector 2×8 = 0x10. This is page 03's "address = base + index×scale" idea wearing a different hat.

Step 5 (preview): paging, the next mountain

Protected mode with a flat GDT gives you 32-bit linear addresses that map directly to physical memory — useful, but every process shares the same physical layout. Paging adds one more layer of indirection: the CPU translates linear addresses through a page directory and page table (each a 4KB array of 4-byte entries) into physical addresses, enabling virtual memory, per-process isolation, and on-demand loading.

; the conceptual shape, not full working code: mov eax, page_directory mov cr3, eax ; cr3 = physical address of the page directory mov eax, cr0 or eax, 0x80000000 ; bit 31 of cr0 = Paging enable (PG) mov cr0, eax ; paging is now live for every memory access

Notice the pattern repeating: a control register (CR3 this time, not CR0 alone), a single bit flip, and from that instruction onward every memory access is reinterpreted. This is the same shape as the real-mode → protected-mode switch — x86 likes "set a pointer, flip a control bit" as its mechanism for changing what memory access fundamentally means.
