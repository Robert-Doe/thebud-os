Endianness: which end of the number comes first in memory

The number forty-two doesn't care how it's written. Memory does. Endianness is just an agreement about which byte of a multi-byte value gets the lowest address — and x86 made a choice that confuses everyone exactly once.

Scenario

Imagine writing the date "2026" on four separate index cards, one digit each, then handing them to a friend to place in four numbered mail slots, left to right. Do you hand them "2, 0, 2, 6" (most significant digit first — the way you'd read it aloud) or "6, 2, 0, 2" (least significant digit first)? Either way, your friend can reconstruct "2026" perfectly — as long as they know which convention you used. Endianness is exactly this agreement, applied to bytes instead of digits.

Big-endian: write it the way you'd say it

Big-endian stores the most significant byte (MSB) at the lowest address — the same left-to-right order you'd read a number aloud. Network protocols (TCP/IP headers) use big-endian, which is why it's also called "network byte order."

Take the 32-bit value 0x12345678. In big-endian memory, starting at address 0x1000:

0x100012
0x100134
0x100256
0x100378

Bytes appear in the same order as you'd write the hex number. Intuitive to read in a debugger, but mildly annoying to extract "just the low byte" from in hardware.

Little-endian: x86's choice

Little-endian stores the least significant byte (LSB) at the lowest address. x86 and x86-64 (and ARM in its default mode) are little-endian. The same value 0x12345678 at address 0x1000 looks like:

0x100078
0x100156
0x100234
0x100312

Bytes appear "backwards" from how you'd write the number — which is exactly why staring at a raw hex dump of x86 memory is so disorienting the first time.

Why would anyone choose little-endian?

It's not arbitrary cruelty. Little-endian has a genuine engineering advantage: the address of a value never changes when you reinterpret it as a smaller type.

; 32-bit value 0x000000FF at address 0x1000, little-endian: ; 0x1000: FF 0x1001: 00 0x1002: 00 0x1003: 00 ; Reading just the low 8 bits (AL-sized) means reading address 0x1000 — ; the SAME address as the start of the 32-bit value. No offset math needed.

In big-endian, the low byte of that same value would sit at 0x1003 — so "give me this as a byte instead of a dword" requires knowing the full width up front to compute the offset. Little-endian lets hardware add small numbers (the common case) by just looking at the first byte or two, without caring how wide the full value eventually turns out to be.

Where this bites OS developers specifically

  • Reading multi-byte fields from disk/network structures by hand. File system superblocks, ELF headers, partition tables — when you dump them in a hex editor, multi-byte numeric fields are backwards from how you'd naturally read them.
  • Building values byte-by-byte into a boot sector. If you hand-assemble a 16-bit or 32-bit immediate value into raw bytes (e.g. writing a disk address into a boot sector), you must write the low byte first.
  • Network code. TCP/IP headers are big-endian by spec, but x86 is little-endian. Every OS networking stack calls byte-swap functions (htons, ntohl, or by hand bswap) at the boundary. Forget one and your port numbers come out as nonsense like 0x3930 instead of 0x1357.
  • It is NOT about bit order. Endianness only governs byte order within a multi-byte value. Inside a single byte, bit 7 is always the most significant bit regardless of endianness — there's no such thing as "little-endian bits" in any architecture you'll meet here.

The bswap instruction and the mental flip-test

x86 has a dedicated instruction, bswap reg, that reverses the byte order of a 32- or 64-bit register in place — this exists specifically because byte-order conversion is common enough to deserve hardware support.

; eax = 0x12345678 bswap eax ; eax = 0x78563412

The flip-test, for whenever you're staring at a hex dump

If you know the architecture is little-endian (true for essentially every OS-dev tutorial and every x86/ARM system you'll touch), and you see consecutive bytes 78 56 34 12 in memory representing a 32-bit value, mentally reverse the byte order to get 0x12345678. Do this every single time you read a raw memory or disk dump — it becomes automatic within a week.

Try this: predict the bytes

You write the 16-bit value 0xABCD to memory address 0x2000 on an x86 machine using mov [0x2000], ax (with AX = 0xABCD). What byte sits at address 0x2000, and what byte sits at 0x2001?

Answer: 0x2000 holds 0xCD (the low byte), 0x2001 holds 0xAB (the high byte) — little-endian means the least significant byte gets the lowest address, full stop.

Try this: the network boundary

Your OS's network stack receives a raw Ethernet frame and needs to read a 16-bit "EtherType" field that arrives as bytes 08 00 (meaning IPv4, per the IEEE spec, which is big-endian on the wire). If you naively load those two bytes into an x86 register with a 16-bit mov, what value do you actually get, and what do you need to do about it?

Answer: A plain little-endian load interprets byte 08 as the low byte and 00 as the high byte, giving 0x0008 — wrong! The wire value is meant to be read big-endian as 0x0800. You must byte-swap (or just compare against the raw byte sequence in network order) before treating it as a normal x86 integer.
