Assembly & OS-from-Scratch Refresher

You're not "writing assembly." You're driving the CPU by hand.

Every high-level language you've used has been lying to you a little — kindly. x = x + 1 hides a register, a load, an add, and a store. An OS has nowhere to hide that. This refresher rebuilds the picture from the silicon up: register sizes, byte order, addressing, the stack, control flow, and finally the exact sequence of instructions that takes a CPU from "just powered on, confused, 16-bit" to "running your kernel in 32-bit protected mode with paging on."

x86 / x86-64 focused NASM syntax head-first style: scenario → model → drill ends with a real boot sector

The promise of this refresher

You will be able to look at a line like mov [ebx+esi*4+8], al and immediately know: which register, what size, what address is being computed, and what byte ends up where. That single skill is 80% of reading OS source code.

Why this matters for OS dev specifically
No runtime, no stdlib, no safety net
When you write an OS, there's no C runtime to set up your stack, no malloc, no "the OS will handle that" — because you ARE the OS. Assembly is how you do the first few hundred instructions before C even has a stack to stand on.

The one mental model to hold onto

A CPU core, at any instant, is just:

a handful of registers (very fast, very few) + a giant flat array of bytes called memory (slower, huge) + one instruction pointer saying "execute this byte sequence next"

Every single thing your OS does — printing a character, switching processes, handling a keyboard interrupt — is some combination of: move bytes between registers and memory, do arithmetic/logic on registers, and conditionally change where the instruction pointer points next. That's it. There is no fourth thing.

A note on "headfirst style"

You'll see boxed scenarios before formal definitions, lots of "wait, why would it do that?" moments answered immediately, and repetition of the same idea from different angles. This is intentional — the goal is for the ideas to survive contact with actual OS source code next week, not just to sound right today.

Before you start

You don't need to have ever written assembly. You do need to be comfortable with hexadecimal and binary — if "0x2A is 00101010 is 42" doesn't feel obvious, spend ten minutes with a base-converter first. Everything downstream assumes that's automatic.
