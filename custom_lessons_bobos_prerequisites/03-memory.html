Memory is just numbered mailboxes — addressing is just arithmetic

RAM is a long row of byte-sized mailboxes, each with a unique number (the address). Every "pointer," "array," and "struct field" you've ever used in a high-level language compiles down to: take a number, maybe do a little arithmetic on it, go look in that mailbox.

Addressing modes: the menu of ways to say "go here"

An instruction operand doesn't just say "memory" — it says exactly how to compute the address. x86's general addressing form is:

address = base_register + (index_register × scale) + displacement

where scale is 1, 2, 4, or 8 (matching byte/word/dword/qword element sizes — perfect for indexing arrays without a separate multiply), and any piece you don't need is simply omitted.

ModeExamplePlain English
Immediatemov eax, 5The value 5 itself, no memory touched
Registermov eax, ebxCopy EBX's value into EAX
Directmov eax, [0x4000]Read the dword at the fixed address 0x4000
Register indirectmov eax, [ebx]Treat EBX as a pointer; read what it points to
Base + displacementmov eax, [ebx+8]A struct field 8 bytes into the struct EBX points to
Base + index*scale + dispmov eax, [ebx+esi*4+8]arr[i] where arr starts at EBX+8, i is in ESI, elements are 4 bytes

Square brackets mean "go there," not "this number"

Q: What's the difference between mov eax, ebx and mov eax, [ebx]?

A: The first copies EBX's value into EAX directly — no memory access at all. The second treats EBX's value as an address, goes to memory, reads 4 bytes starting there, and puts those bytes into EAX. Brackets always mean "dereference" — go to the mailbox numbered by what's inside the brackets, don't just copy the number itself. This single distinction is where most assembly beginners get lost first.

Size matters even when the brackets look the same

mov [ebx], al writes 1 byte. mov [ebx], ax writes 2 bytes. mov [ebx], eax writes 4 bytes — all starting at the same address. The assembler infers the access size from which register you used; when there's no register on either side (e.g. moving an immediate to memory), you must say so explicitly: mov byte [ebx], 5 vs mov dword [ebx], 5.

Scenario

You're indexing into an array of 4-byte integers. The array starts at address stored in EBX, and you want element i (stored in ECX). Without scaled indexing you'd write mov eax, [ebx + ecx*4] in one instruction — the CPU's address-generation hardware does the multiply-by-4 and the add for free, in parallel with everything else, costing no extra cycles versus a plain load. This is precisely why arrays in C compile to tight, fast code: "scale by element size" is something the hardware does, not something your program has to compute step by step.

The stack: a pile of plates, growing the "wrong" way

The stack is just a region of memory accessed in last-in-first-out order, tracked by the ESP (stack pointer) register, which always points at the most-recently-pushed item. The critical, endlessly-confusing fact:

The stack grows DOWN

On x86, push decreases ESP before writing, and pop increases ESP after reading. "Pushing more stuff" moves you toward lower addresses, not higher ones. This is a historical convention, not a law of physics — but every x86 OS, compiler, and calling convention assumes it, so fighting it will only hurt you.

; esp = 0x7FFC initially, stack region grows toward lower addresses push eax ; esp -= 4 -> esp = 0x7FF8, [0x7FF8] = old eax push ebx ; esp -= 4 -> esp = 0x7FF4, [0x7FF4] = old ebx pop ecx ; ecx = [0x7FF4] (old ebx), then esp += 4 -> esp = 0x7FF8

Why "down" actually makes sense

In a flat memory layout, code and static data conventionally sit at low addresses, and the stack starts near the top of available memory and grows downward toward the heap, which grows upward from just above the static data. Two regions growing toward each other from opposite ends use the available space efficiently — if they collide, you've genuinely run out of memory, rather than wasting a fixed split between them.

The stack frame: how function calls actually work

A "function call" is three plain mechanisms working together: call pushes the return address and jumps; the callee sets up a frame using EBP as a fixed reference point; ret pops that return address back into EIP.

my_function: push ebp ; save caller's frame pointer mov ebp, esp ; ebp = fixed reference point for THIS call sub esp, 16 ; reserve 16 bytes of local variables ; ... body uses [ebp-4], [ebp-8] for locals, [ebp+8] for the first argument ... mov esp, ebp ; deallocate locals: snap esp back pop ebp ; restore caller's frame pointer ret ; pop return address into eip, jump there

Notice why arguments live above EBP (positive offsets) and locals live below it (negative offsets): the caller pushed the arguments before executing call, so they're already on the stack at a higher address than anything the callee pushes afterward — and call itself then pushes the return address right above the arguments, with EBP set up one slot beyond that.

call
push return addr, jump
Pushes EIP's current value (the instruction right after the call), then jumps to the target.
ret
pop into eip
Pops the top of stack and jumps there — works only if the stack is exactly as call left it.
ebp / rbp
frame anchor
Doesn't move during the function body, so locals/args stay at fixed offsets even as esp wiggles.

Why mismatched push/pop crashes your OS specifically

In application code, a stack imbalance usually just crashes one process. In kernel code, if an interrupt handler pushes one more thing than it pops before executing iret, the CPU pops garbage into EIP/CS/EFLAGS and jumps to a random address in privileged mode — often hard-locking or silently corrupting the whole machine. Stack discipline matters more, not less, the closer you get to the metal.

Try this: trace the stack pointer

ESP starts at 0x9000. Walk through each instruction and write the new ESP value, plus what (if anything) gets written or read at which address.

push eax ; ? push ebx ; ? push ecx ; ? pop edx ; ? (which register's old value ends up in edx?) add esp, 8 ; ? (this is a common "pop without caring about the value" trick)

Answer: After the three pushes, ESP = 0x8FF4 (0x9000 − 12), with [0x8FF8]=ecx, [0x8FFC]=ebx, [0x9000-4=0x8FFC] wait — careful: push order is eax at 0x8FFC, ebx at 0x8FF8, ecx at 0x8FF4, ESP=0x8FF4. pop edx reads [0x8FF4] = old ecx, EDX = old ECX, ESP becomes 0x8FF8. add esp, 8 just adds 8 directly without reading memory — a fast way to discard two pushed values you don't need back — leaving ESP = 0x9000, right back where it started.
