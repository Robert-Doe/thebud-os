Registers: the same box, four zoom levels

A register is a tiny piece of storage built directly into the CPU — not memory, not cache, the actual silicon the ALU reaches into without a memory access at all. x86 has very few of them, and that scarcity explains most of the instruction set's personality.

Scenario

You're a clerk with exactly one desk drawer (a register). You can hold a full sheet of paper in it (32 bits), or you can fold that same sheet in half and only look at the bottom half (16 bits), or fold it in quarters and look at just the bottom quarter (8 bits). It's still one physical drawer — you're just choosing how much of it you read or write. That's a register's size suffix in a sentence.

The classic 8 (16-bit ancestry)

x86 grew up from the 16-bit 8086. It originally had eight 16-bit general-purpose registers, each with a "personality" baked in by convention (even though the hardware doesn't strictly enforce most of these anymore):

Why these names still matter

Modern compilers and OS code don't really respect "AX is for math" as a rule anymore — any general-purpose register can hold almost anything. But a few roles are still hard-wired into specific instructions: CX is the implicit counter for loop, DX is the implicit port register for in/out, and SP is touched implicitly by push/pop/call/ret. Knowing the legacy names tells you instantly why some instruction "mysteriously" only works with one specific register.

Same drawer, four labels: the naming ladder

This is the single most important diagram on this page. AL, AX, EAX, and RAX are not four different registers. They are four different views into the same 64-bit storage. Writing to AL changes the bottom 8 bits of RAX and leaves everything above untouched (with one trap — see the callout below).

RAX — 64 bits (bits 63–0) · x86-64 only
upper 32 (unused alone)
EAX — 32 bits (bits 31–0)
 
upper 16
AX — 16 bits (bits 15–0)
 
 
AH — bits 15–8
AL — bits 7–0

So AL is the bottom byte, AH is the byte just above it, AX = AH:AL together, EAX adds another 16 bits on top of AX, and RAX adds another 32 bits on top of that. Same trick applies to B, C, D (giving AL/AH, BL/BH, CL/CH, DL/DH) — but SI, DI, BP, SP only get a high/low split down to 16 bits historically; their single-byte forms (SIL, DIL, BPL, SPL) only exist in 64-bit mode.

The trap: writing EAX zeroes the top of RAX, but writing AX/AL doesn't touch EAX's top

This is one of the most-quoted x86-64 gotchas. mov eax, 5 doesn't just set the low 32 bits — it zero-extends and clears bits 63–32 of RAX too. But mov ax, 5 or mov al, 5 leaves the upper bits of EAX/RAX completely untouched — whatever garbage was there stays. Mixing 32-bit and 16-bit writes to "the same register" without realizing this is a classic source of OS-dev heisenbugs.

al, bl, cl, dl…
1 byte. Holds 0–255 unsigned or -128–127 signed.
16-bit

2 bytes. The original 8086 width. Still used for real-mode boot code.
32-bit
eax, ebx, ecx…
4 bytes. "e" = extended. The protected-mode workhorse size.
64-bit

8 bytes. "r" = register, x86-64 only. Plus r8–r15, all-new registers with no legacy alias.

Special-purpose registers you can't skip

  • EIP / RIP — instruction pointer. Always holds the address of the next instruction to execute. You cannot mov into it directly; you change it via jumps, calls, and returns.
  • EFLAGS / RFLAGS — status flags. A bag of single bits set automatically by arithmetic/comparison instructions: Zero (ZF), Carry (CF), Sign (SF), Overflow (OF), and more. Conditional jumps read these. Full detail on page 04.
  • CS, DS, SS, ES, FS, GS — segment registers. 16-bit registers that, in real mode, get multiplied to form addresses; in protected mode, they become indexes into a descriptor table instead. CS = code segment, SS = stack segment, DS = default data segment. These are central to the OS-bootstrap page.
  • CR0–CR4 — control registers (32/64-bit only). Global "mode switches" for the whole CPU — bit 0 of CR0 is the famous Protection Enable bit that flips the CPU from real mode into protected mode. CR3 holds the physical address of the page table root once paging is on.

Why so few registers?

x86 only has 8 general-purpose registers in 32-bit mode (16 in 64-bit mode with r8–r15). Compare that to RISC architectures with 32. This scarcity is why the stack and memory operands matter so much in x86 — you constantly spill values to memory because you simply run out of drawers. When you write boot code, you'll feel this immediately: you're juggling segment setup, a loop counter, and a pointer with only a few registers to spare.

Q: If RAX/EAX/AX/AL overlap, why does the assembler let me use AL and ECX in the same instruction without confusion?

A: Because the assembler statically knows, from the mnemonic you typed, exactly which physical register and which width you mean — there's no runtime ambiguity. The overlap only matters for you, tracking what value ends up where after several instructions touch the same register at different widths.

Try this: trace it by hand

Assume RAX starts at all zero bits. Execute these four instructions in order and write down the full 64-bit hex value of RAX after each one. Do this on paper before checking the answer.

mov eax, 0x11223344 mov al, 0xFF mov ah, 0x00 mov eax, 0x99

Answer (no peeking until you've tried)

After line 1: 0x0000000011223344 (eax write zero-extends to 64 bits). After line 2: 0x00000000112233FF (only the bottom byte changes). After line 3: 0x0000000011220000... wait — careful: AH is bits 15–8, so it overwrites the second byte, giving 0x0000000011220000FF→ actually: bits 7-0 stay 0xFF from step 2, AH only touches bits 15-8, so result is 0x00000000112200FF. After line 4: 0x0000000000000099 (32-bit write zero-extends the full upper 32 bits again, erasing everything above bit 31).
