BROWSER B07 — JS INTERPRETER

Tagged Values & Type Confusion

JavaScript has no static types — every value can be a number, string, object, or function at runtime. The engine uses a tagged union to track types. Confuse the tag and you have arbitrary read/write. This is how most browser exploits start.

tagged union
type tag + value in one word
NaN-boxing
V8/JSC pack type into NaN bits
type confusion
treat object A as type B
addrof/fakeobj
primitives built from type confusion

01 — The Big Analogy

Head First Moment

Imagine a warehouse with unlabelled boxes. Each box has a sticky note saying what's inside: "NUMBER", "STRING", "OBJECT". The forklift driver (JS engine) reads the sticky note to know how to handle the box. A type confusion bug is like switching sticky notes: the driver picks up a box labelled "NUMBER" but it's actually filled with pointers to other boxes. Instead of doing math, it starts following those pointers — now it can read or write anywhere in the warehouse.

02 — The Tagged Value

/* js_value.h — simplified NaN-boxing */
typedef enum {
    JS_NUMBER = 0,
    JS_STRING = 1,
    JS_OBJECT = 2,
    JS_BOOL   = 3,
    JS_NULL   = 4,
    JS_UNDEF  = 5,
} js_type_t;

typedef struct {
    js_type_t type;
    union {
        double   number;
        char    *string;
        void    *object;  /* heap pointer */
        int      boolean;
    } u;
} js_value_t;

/* Helpers */
static inline js_value_t js_number(double n) {
    return (js_value_t){ .type=JS_NUMBER, .u.number=n };
}
static inline js_value_t js_object(void *ptr) {
    return (js_value_t){ .type=JS_OBJECT, .u.object=ptr };
}
static inline int js_is_number(js_value_t v) {
    return v.type == JS_NUMBER;
}

/* Addition: must check types! */
js_value_t js_add(js_value_t a, js_value_t b) {
    if (js_is_number(a) && js_is_number(b))
        return js_number(a.u.number + b.u.number);
    /* string coercion, etc. */
    return js_string(js_to_string(a), js_to_string(b));
}

03 — A Type Confusion Bug

/* Suppose the engine has an ARRAY type and an OBJECT type.
   Arrays have a length field; objects have a property map pointer.
   If the engine reads an object as an array:
   - obj->length field is actually obj->prop_map pointer (a heap addr)
   - Reading "array[0]" computes: base + 0*8 — reads object fields
   - Writing "array[i]" writes to computed address: arbitrary write!
*/

typedef struct { uint32_t length; js_value_t *data; } js_array_t;
typedef struct { uint64_t prop_map; /* pointer */ } js_object_t;

/* BUG: wrong cast — treats js_object_t* as js_array_t* */
void type_confusion_demo(js_value_t val) {
    if (val.type == JS_OBJECT) {
        /* attacker tricks the engine into taking this path
           with a value whose type field says OBJECT
           but whose object pointer points to an array layout */
        js_array_t *arr = (js_array_t*)val.u.object;
        /* arr->length is actually the prop_map pointer value */
        printf("length = %u\n", arr->length);  /* leaks a heap addr! */
        /* arr->data[0] reads at prop_map+0 — arbitrary read */
    }
}
addrof and fakeobj Primitives

addrof(obj): confuse the engine into returning an object's heap address as a JS number. fakeobj(addr): confuse the engine into treating a JS number (an address) as an object pointer. Together: read any object's address, forge a fake object at any address, read/write anywhere in the heap. These two primitives are the building blocks of every modern browser exploit (B10 goes deep on this).

04 — The Eval Loop

/* A minimal tree-walking interpreter */
js_value_t eval(ast_node_t *node, env_t *env) {
    switch (node->type) {
    case AST_NUMBER:
        return js_number(node->num);
    case AST_BINOP:
        js_value_t left  = eval(node->left,  env);
        js_value_t right = eval(node->right, env);
        switch (node->op) {
        case OP_ADD: return js_add(left, right);
        case OP_MUL:
            /* type check: must be numbers */
            if (!js_is_number(left) || !js_is_number(right))
                return js_throw("TypeError: not a number");
            return js_number(left.u.number * right.u.number);
        }
    case AST_CALL:
        js_value_t fn = eval(node->callee, env);
        if (fn.type != JS_FUNCTION)
            return js_throw("TypeError: not a function");
        return call_function(fn.u.object, node->args, env);
    /* ... */
    }
}

06 — Brain Exercise

Sharpen Your Pencil

Real JS engines use NaN-boxing: a 64-bit IEEE 754 NaN has 51 "quiet NaN payload" bits unused. V8 packs the type tag and object pointer into those bits, so a JS value is always exactly 8 bytes — no separate type field. The number zero is just 0.0; a pointer to an object is a NaN with the pointer in the low 48 bits.

How would a type confusion bug work in a NaN-boxed engine? If the attacker can flip the NaN bit of a floating-point number, they can make the engine think a double value is a pointer. What would the "pointer" point to, and can the attacker control the value of the double to make it point somewhere useful?

There Are No Dumb Questions

Q: Why not just add runtime type checks everywhere?
Performance. A modern JS engine executes millions of operations per second. Adding a type check to every arithmetic operation would be catastrophic for speed. The solution is speculative optimization (JIT compilation, B08): assume a variable is always a number, emit fast code, and "deoptimize" back to the slow path if a type check fails at runtime. Bugs arise at the deoptimization boundaries.
Q: Is this why JavaScript has typeof, instanceof, etc.?
Yes — those are userland ways to ask the engine "what type is this value?" They read the same tag bits the engine uses internally. The difference: userland code uses them for logic; the engine uses them to decide how to interpret raw memory. Getting the engine's internal type decision wrong is the bug class we're discussing.

07 — What's Next

Up Next: B08 — JIT Compiler

The tree-walking interpreter is too slow. The JIT compiler watches hot code paths and emits native x86 machine code on the fly. New attack surface: the JIT emitter itself must not generate exploitable code, and the JIT compiled code lives in memory that must be executable but not writable (W^X).
