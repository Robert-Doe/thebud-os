BROWSER B02 — RENDERER SANDBOX

The Syscall Whitelist

A separate process isn't enough — an exploited renderer still has full access to every Linux syscall. The sandbox cuts that surface down to a handful: read, write, and exit. Everything else triggers SIGKILL.

01 — The Big Analogy

Head First Moment

A separate renderer process is like putting a contract worker in a different office. Good — they can't walk into the vault. But they still have a company phone and can call anyone in the building (all syscalls available). The sandbox takes away most of the phones. The renderer can only call the front desk (read/write the IPC pipe) and reception (exit). Any other call silently kills them.

02 — seccomp-BPF: A Kernel Syscall Filter

#include <linux/seccomp.h>
#include <linux/filter.h>
#include <sys/prctl.h>

/* BPF program: allow read/write/exit, kill everything else */
struct sock_filter sandbox_filter[] = {
    /* load syscall number from seccomp_data */
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
             offsetof(struct seccomp_data, nr)),
    /* allow read */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_read,  0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    /* allow write */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_write, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    /* allow exit / exit_group */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_exit,  0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_exit_group, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    /* kill everything else */
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
};

void install_sandbox(void) {
    struct sock_fprog prog = {
        .len    = sizeof(sandbox_filter)/sizeof(sandbox_filter[0]),
        .filter = sandbox_filter,
    };
    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);  /* required first */
    prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);
    /* from this point: any syscall not in list → SIGKILL */
}
Must Call Before Doing Anything Sensitive

install_sandbox() must be called before loading any untrusted content, and after all setup that needs privileged syscalls (opening the IPC pipe, allocating memory). Once installed, the filter is irrevocable — even root cannot remove it for this process.

JIT Makes Sandboxing Hard

A pure sandbox would block mmap with PROT_EXEC — no writable+executable memory. But the JS JIT compiler (B08) needs to write machine code and then execute it. Chrome's solution: generate code in a separate "JIT process" that sends compiled bytecode to the renderer over IPC. The renderer maps the code read-only. W^X preserved, JIT preserved.

04 — The Renderer with Sandbox Installed

/* renderer.c — sandboxed renderer */
int main(void) {
    /* Phase 1: setup (before sandbox) */
    /* IPC fds already open (from fork in B01) */
    /* pre-allocate any memory we'll need */
    void *work_buf = malloc(4 * 1024 * 1024);

    /* Phase 2: install sandbox — point of no return */
    install_sandbox();

    /* Phase 3: event loop (only read/write/exit allowed) */
    struct ipc_msg msg;
    while (ipc_recv(STDIN_FILENO, &msg) == 0) {
        if (strcmp(msg.type, "LOAD") == 0) {
            render_page(msg.payload, work_buf);
            ipc_send(STDOUT_FILENO, "PAINTED", "ok");
        }
    }
    return 0;
    /* open("evil.txt") here → SIGKILL, process dies */
}

06 — Brain Exercise

Sharpen Your Pencil

Our BPF filter is a flat list of comparisons — O(n) per syscall. With 300+ syscalls to consider, real Chrome uses a more complex BPF program that does a binary search via jump instructions to check whitelists in O(log n).

Try adding mmap to the whitelist, but only when prot does NOT include PROT_EXEC. You'll need to load a syscall argument from the BPF seccomp_data struct. Look up the args[1] field offset — this is argument-level filtering, much more precise than syscall-level.

There Are No Dumb Questions

Q: Can an attacker just call a syscall directly (bypassing libc)?
Yes — and that's fine. seccomp-BPF intercepts at the kernel boundary, not in userspace. Every syscall, whether via libc wrapper, inline asm, or VDSO, goes through the kernel's seccomp check before executing. There's no way to bypass it from userspace.
Q: Windows doesn't have seccomp. How does Chrome sandbox on Windows?
Windows uses Job Objects (to restrict process rights), Integrity Levels (to limit what resources can be accessed), and an AppContainer (which restricts network, file, and registry access). The renderer runs at Low integrity with a restricted token. It's conceptually similar — reduce the attack surface — but implemented via Windows ACL/token mechanisms instead of syscall filtering.

07 — What's Next

Up Next: B03 — Same-Origin Policy

The sandbox stops the renderer from reaching outside via syscalls. The Same-Origin Policy (SOP) stops JavaScript inside the renderer from reaching across to a different website's data. Two orthogonal defences: one at the OS layer, one at the web platform layer.
