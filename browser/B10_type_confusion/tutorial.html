01 — The Exploit Chain

1
Type confusion bug: trigger engine bug that confuses an OBJ_MAP (metadata) with OBJ_FIXED_ARRAY (raw data store). The map's pointer fields are now read as array element values.
2
addrof primitive: use the confused object to read an arbitrary object's heap address as a JS integer. This defeats ASLR inside the heap.
3
fakeobj primitive: use the confused object to make the engine treat an arbitrary integer as a heap pointer, creating a fake JS object at any address.
4
Arbitrary read/write: craft a fake ArrayBuffer at a controlled address; set its backing store pointer to any address; read/write memory anywhere in the process.
5
Code execution: overwrite a JIT code page (or a function pointer) with shellcode. Jump to it → RCE inside the renderer sandbox.

02 — The Bug: Confusing Map and FixedArray

/* Engine internals */
typedef struct {
    uint8_t  obj_type;      /* OBJ_MAP or OBJ_FIXED_ARRAY */
    uint32_t instance_size;
    void    *prototype;     /* pointer to prototype object */
    void    *constructor;   /* pointer to constructor */
} obj_map_t;

typedef struct {
    uint8_t  obj_type;      /* OBJ_FIXED_ARRAY */
    uint32_t length;
    uint64_t elements[];    /* raw 64-bit values */
} obj_fixed_array_t;

/* BUG: engine reads a Map object as a FixedArray.
   map->instance_size (uint32) lands at array->length.
   map->prototype     (ptr)    lands at array->elements[0].
   map->constructor   (ptr)    lands at array->elements[1].

   Reading elements[0] returns the prototype POINTER as an integer.
   That pointer is an address in the heap → addrof! */

03 — Building addrof and fakeobj

/* addrof: get heap address of any object */
uint64_t addrof(gc_obj_t *target) {
    /* 1. Set up a confused object that reads target's map */
    confused_arr->backing = (uint64_t*)target;
    /* 2. Read element[0] — which is actually target->map ptr */
    uint64_t addr = confused_arr->elements[0];
    return addr;  /* heap address of target's map */
}

/* fakeobj: make engine believe address X is a valid object */
gc_obj_t *fakeobj(uint64_t addr) {
    /* Write addr into confused object as if setting an element */
    confused_arr->elements[0] = addr;
    /* Read back through the map interpretation — returns a
       js_value_t pointing to addr as if it were a live object */
    return (gc_obj_t*)confused_arr->backing;
}

/* Arbitrary read: read 8 bytes at any address */
uint64_t arb_read(uint64_t addr) {
    /* Create a fake ArrayBuffer whose backing_store = addr */
    fake_ab->backing_store = addr;
    uint64_t *view = (uint64_t*)get_data_view(fake_ab);
    return view[0];
}

/* Arbitrary write */
void arb_write(uint64_t addr, uint64_t val) {
    fake_ab->backing_store = addr;
    uint64_t *view = (uint64_t*)get_data_view(fake_ab);
    view[0] = val;
}
ASLR Is Bypassed by addrof

ASLR (Address Space Layout Randomization) randomizes where the heap, stack, and libraries are loaded. Once an attacker has addrof, they can leak the address of any known object and compute the base addresses of all other regions. ASLR is defeated — not by a separate bug, but as a consequence of the type confusion primitive.

04 — Code Execution

/* Step 5: overwrite a JIT-compiled function's code pointer */

/* 1. Find address of a known JS function */
uint64_t fn_addr = addrof(target_function);

/* 2. Read the JIT code pointer from the function object
      (at a known offset in the function struct) */
uint64_t jit_code_ptr = arb_read(fn_addr + CODE_PTR_OFFSET);

/* 3. Allocate a buffer with our shellcode */
uint8_t shellcode[] = {
    0x48, 0x31, 0xc0,       /* xor rax, rax */
    0x48, 0xff, 0xc0,       /* inc rax      */
    /* ... execve("/bin/sh", ...) ... */
};

/* 4. Find a writable page (mmap or reuse JIT buffer in W state) */
uint64_t sc_addr = alloc_writable_exec(shellcode, sizeof(shellcode));

/* 5. Overwrite the function's JIT code pointer */
arb_write(fn_addr + CODE_PTR_OFFSET, sc_addr);

/* 6. Call the function — jumps to shellcode */
target_function();  /* shell spawned! */

06 — Brain Exercise

Sharpen Your Pencil

Modern engines add "pointer compression" — heap pointers are stored as 32-bit offsets from a heap base rather than full 64-bit addresses. This halves memory use and means addrof only leaks a 32-bit offset, not a full virtual address.

How does an attacker still defeat ASLR if they only have 32-bit compressed pointers? Can they leak the heap base from some other engine data structure? What about module base addresses (for ROP chains) — do those still need a separate leak?

There Are No Dumb Questions

Q: Does every browser exploit follow this exact chain?
The primitives are universal; the bug that provides them varies. Some bugs give addrof directly; others give a length extension (out-of-bounds array read/write) which is then used to build addrof and fakeobj. Some exploits skip the fake ArrayBuffer and use a DataView or TypedArray instead. The template — (bug) → (addrof + fakeobj) → (arb r/w) → (code exec) — is consistent across V8, SpiderMonkey, and JavaScriptCore CVEs from 2018 onwards.
Q: What mitigations exist against this chain?
Pointer authentication (PAC on ARM64), cage-based heap isolation, hardened ArrayBuffer backing store (separate allocation), CFI (control-flow integrity) to prevent jumping to arbitrary addresses, and the sandbox itself (B02) which limits what shellcode can do. No single mitigation stops the chain — defense in depth applies each layer as a hurdle.
