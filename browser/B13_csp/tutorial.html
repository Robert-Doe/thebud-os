BROWSER B13 — CONTENT SECURITY POLICY

CSP: Allow Lists

CSP tells the browser "only run scripts from these sources." Even if an attacker injects a script tag via XSS, the browser refuses to execute it — unless the CSP has one of three common misconfigurations that make it bypassable.

01 — The Big Analogy

Head First Moment

CSP is like a venue with a guest list. The bouncer (browser) checks every script against the list before letting it run. An injected script from evil.com? Not on the list — blocked. But if the venue owner (developer) accidentally adds "anyone from the same city" (unsafe-inline) to the list, the bouncer has to let everyone in. CSP is only as strong as the list it enforces.

02 — Parsing a CSP Header

/* csp.h */
typedef struct {
    char **script_src;   /* allowed script origins */
    int    n_scripts;
    int    unsafe_inline;
    int    unsafe_eval;
    char **nonces;       /* 'nonce-abc123' values */
    int    n_nonces;
    char **hashes;       /* 'sha256-...' values */
    int    n_hashes;
} csp_policy_t;

/* Parse: Content-Security-Policy: script-src 'nonce-abc' https://cdn.example.com */
csp_policy_t *csp_parse(const char *header) {
    csp_policy_t *p = calloc(1, sizeof(*p));
    char *tok = strtok(strdup(header), " ;");
    char *directive = NULL;
    while (tok) {
        if (strcmp(tok, "script-src") == 0)
            directive = "script-src";
        else if (directive && strcmp(directive,"script-src")==0) {
            if (strcmp(tok,"'unsafe-inline'") == 0)
                p->unsafe_inline = 1;
            else if (strncmp(tok,"'nonce-",7) == 0)
                add_nonce(p, tok+7);  /* strip 'nonce-' prefix */
            else
                add_src(p, tok);
        }
        tok = strtok(NULL, " ;");
    }
    return p;
}

int csp_allows_script(csp_policy_t *p, const char *origin,
                      const char *nonce) {
    if (p->unsafe_inline) return 1;         /* anything goes */
    if (nonce && nonce_matches(p, nonce)) return 1;
    return origin_in_allowlist(p, origin);
}

03 — Three Common Bypass Classes

BypassVulnerable CSPWhy it worksFix
unsafe-inline script-src 'self' 'unsafe-inline' Allows any inline <script> — XSS works directly Remove 'unsafe-inline'. Use nonces or hashes instead.
JSONP endpoint script-src https://accounts.google.com google.com has a JSONP endpoint: ?callback=alert(1)// — attacker loads it as a script, callback is user-controlled code Remove domains with JSONP endpoints from script-src. Use strict-dynamic.
Open redirect script-src https://trusted.com trusted.com/redirect?url=evil.com/x.js — browser follows redirect, ends up loading from evil.com, origin is trusted.com Ensure allowlisted domains have no open redirects. Or use hash/nonce. 
/* JSONP bypass demo */
/* Victim CSP: script-src https://api.example.com */
/* api.example.com has: GET /data?callback=FUNCTION_NAME */
/* Attacker injects: */
/* <script src="https://api.example.com/data?callback=alert(1)//"></script> */
/* Response: alert(1)//({"data":"..."}) */
/* Browser executes: alert(1) — XSS! */

/* The correct CSP to stop JSONP bypasses: */
/* Content-Security-Policy: script-src 'strict-dynamic' 'nonce-RANDOM' */
/* strict-dynamic: only scripts with the correct nonce can run,
   and scripts they dynamically load are also trusted.
   Origin-based allowlists are ignored. */
Nonces: The Right Approach

A nonce (number used once) is a random value generated fresh per HTTP response. The server adds 'nonce-RANDOM' to the CSP header and nonce="RANDOM" to each legitimate <script> tag. An injected script tag has no nonce — blocked. The nonce must be cryptographically random (16+ bytes) and truly per-request, or an attacker can predict or reuse it.

05 — Brain Exercise

Sharpen Your Pencil

CSP report-uri (or report-to) sends a JSON report to a URL whenever a violation occurs. This is valuable for detecting XSS attempts. But can an attacker abuse report-uri itself?

Consider: the violation report includes the blocked-uri of the resource that was blocked. If an attacker can force a CSP violation on a URL containing sensitive data (e.g., a fragment identifier or path that includes a token), does the report leak that data to the report-uri endpoint? There Are No Dumb Questions

Q: Does CSP prevent all XSS?
No — CSP reduces the impact of XSS but doesn't prevent injection. If the server generates HTML without escaping user input, the XSS injection still happens. CSP is a second line of defence: even if injection occurs, the browser won't execute the injected script (if the CSP is strict). The first line of defence is input validation and output escaping.
Q: What's the difference between CSP Level 2 and Level 3?
Level 2 added nonces and hashes. Level 3 added strict-dynamic (which makes nonce-based CSPs work with dynamic script loading) and deprecated unsafe-inline when a nonce or hash is present. Most modern deployments target Level 2 minimum; Level 3 with strict-dynamic is the recommended baseline for new applications.

06 — What's Next

Up Next: B14 — CORS

CSP controls what scripts run on your page. CORS controls what cross-origin requests your page's scripts can make and read responses from. The two mechanisms are complementary: CSP is server-to-browser; CORS is browser-to-server. Misconfigurations in CORS let attackers read your API responses from their malicious page.
