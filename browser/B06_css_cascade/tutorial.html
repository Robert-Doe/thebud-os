Specificity & Cascade

01 — The Big Analogy

Head First Moment

CSS cascade is like a courtroom with three judges deciding what color your button is. Judge 1 checks the rule's origin (browser default < author stylesheet < inline style). Judge 2 checks specificity — how precisely the selector targets the element. Judge 3 breaks ties by order: the last rule wins. All three judges confer; the most senior overrules the others.

!important is like calling in the Supreme Court — it overrules everyone. Use it only as a last resort.

02 — Computing Specificity

/* specificity.h
   Triple (a, b, c):
   a = number of ID selectors       (#id)
   b = number of class/attr/pseudo  (.class, [attr], :hover)
   c = number of element/pseudo-el  (div, ::before)
   Compare lexicographically: (1,0,0) > (0,255,255)
*/
typedef struct { int a, b, c; } specificity_t;

specificity_t compute_specificity(const char *selector) {
    specificity_t s = {0,0,0};
    const char *p = selector;
    while (*p) {
        if (*p == '#') { s.a++; p++; }          /* ID */
        else if (*p == '.' || *p == '[' ||
                 (*p==':' && p[1]!=':')) {       /* class/attr/pseudo */
            s.b++; p++;
        } else if (*p == ':' && p[1] == ':') {   /* pseudo-element */
            s.c++; p += 2;
        } else if (isalpha(*p) || *p == '*') {   /* element */
            if (*p != '*') s.c++;
            p++;
        } else { p++; }
        /* skip selector name chars */
        while (*p && !strchr(" #.[:>+~*", *p)) p++;
    }
    return s;
}

int specificity_gt(specificity_t a, specificity_t b) {
    if (a.a != b.a) return a.a > b.a;
    if (a.b != b.b) return a.b > b.b;
    return a.c > b.c;
}

03 — The :visited Timing Side-Channel

/* History sniffing attack (pre-2010, now mitigated) */

/* Attacker's page creates 10,000 invisible links */
for (int i = 0; i < urls_count; i++) {
    dom_node_t *a = dom_create_element("a");
    dom_set_attr(a, "href", target_urls[i]);
    /* :visited links get color:red, unvisited stay blue */
    dom_append_child(document_body, a);
}

/* After layout, getComputedStyle reveals visited status:
   - visited:   computed color = rgb(255,0,0)   → link was visited
   - unvisited: computed color = rgb(0,0,255)   → not visited
   This leaks browsing history!                              */

/* Modern mitigation: getComputedStyle always returns
   unvisited colors even for :visited links.
   Only paint-time differs — and paint timing is also
   carefully obfuscated. */
CSS Can Leak Information

The :visited attack worked because CSS applied different visual styles based on browsing history, and JS could query those styles. The fix: limit what properties can differ for :visited (only color-like properties), and never expose :visited styles via getComputedStyle. This is a classic case of a feature (privacy-friendly link coloring) becoming an attack vector when combined with a JS API.

05 — Brain Exercise

Sharpen Your Pencil

CSS custom properties (variables) like --my-color: red don't participate in the cascade the same way as regular properties — they're inherited and can be overridden at any level. But they can also be read by JS via getComputedStyle(el).getPropertyValue('--my-color').

Could an attacker use CSS custom properties set by :visited rules to re-create the history sniffing attack? Try to design the attack, then think about why the browser's existing mitigation (blocking getComputedStyle for :visited) also blocks this variant.

There Are No Dumb Questions

Q: What does "cascade" actually mean?
It refers to the waterfall of style sources: browser UA stylesheet → user stylesheets → author stylesheets → inline styles. Each level "cascades" on top of the previous, and !important rules cascade in reverse. The name comes from Cascading Style Sheets — the mechanism is the whole point of the language.
Q: Why does specificity use (a,b,c) instead of a single number?
To prevent "carrying" — if specificity were a single number with IDs worth 100, classes worth 10, and elements worth 1, then 11 class selectors (110) would beat one ID selector (100). The (a,b,c) triple compares lexicographically, so any ID beats any number of classes. This was an intentional design choice to give authors meaningful control.

06 — What's Next

Up Next: B07 — JS Interpreter

CSS is declarative and safe. JavaScript is imperative and dangerous — it can read the DOM, make network requests, access cookies, and execute arbitrary logic. The JS interpreter is the most security-critical component of the browser. A single type confusion bug in the engine can give an attacker arbitrary code execution.
