x86 Emitter & W^X

The interpreter is too slow for tight loops. The JIT watches hot code and emits native x86 instructions directly into memory — then jumps to them. The constraint: memory must be either writable or executable, never both. That's W^X.

01 — The Big Analogy

Head First Moment

The interpreter reads your JS source and executes it line by line — like a human translator reading French aloud to an English audience, word by word. The JIT compiler is like hiring a translator who watches your most-used phrases, writes them out in English once, then hands the audience a card to read directly — no translator needed. First time is slow (compilation); every subsequent use is fast (native execution).

W^X is the security rule: the translator can only write on the card OR let people read it — not both simultaneously. This stops an attacker from modifying compiled code that's already being executed.

03 — Allocating Executable Memory

/* jit.c — allocate a code buffer with W^X enforcement */
#include <sys/mman.h>

typedef struct {
    uint8_t *buf;
    size_t   size;
    size_t   pos;
} jit_buf_t;

jit_buf_t jit_alloc(size_t size) {
    /* Step 1: allocate WRITABLE, not executable */
    void *mem = mmap(NULL, size,
                     PROT_READ | PROT_WRITE,   /* W, not X */
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    return (jit_buf_t){ .buf=mem, .size=size, .pos=0 };
}

void jit_finalize(jit_buf_t *j) {
    /* Step 2: flip to EXECUTABLE, remove write permission */
    mprotect(j->buf, j->size, PROT_READ | PROT_EXEC);  /* X, not W */
    /* now W^X: was writable, now executable — never both */
}

/* Emit raw x86 bytes */
void emit_byte(jit_buf_t *j, uint8_t b)  { j->buf[j->pos++] = b; }
void emit_u32 (jit_buf_t *j, uint32_t v) {
    memcpy(j->buf + j->pos, &v, 4); j->pos += 4;
}

04 — Emitting x86: A Simple Add Function

/* JIT compile: function(a, b) { return a + b; }
   x86-64 System V ABI: args in RDI, RSI; return in RAX */

void *jit_compile_add(jit_buf_t *j) {
    void *entry = j->buf + j->pos;

    /* mov rax, rdi   — load first arg into rax */
    emit_byte(j, 0x48); emit_byte(j, 0x89); emit_byte(j, 0xF8);
    /* add rax, rsi   — add second arg */
    emit_byte(j, 0x48); emit_byte(j, 0x01); emit_byte(j, 0xF0);
    /* ret            — return */
    emit_byte(j, 0xC3);

    jit_finalize(j);   /* make executable */

    return entry;
}

/* Call the JIT-compiled function */
typedef long (*jit_fn_t)(long, long);
jit_buf_t buf = jit_alloc(4096);
jit_fn_t add = jit_compile_add(&buf);
printf("JIT add(3, 4) = %ld\n", add(3, 4));  /* 7 */
JIT Spraying

An attacker who can control the values the JIT compiles into immediate constants can "spray" shellcode bytes across executable JIT pages. By carefully crafting JavaScript constants like 0x90909090 (NOP sled) or jump instructions as immediates, the attacker fills JIT pages with exploitable patterns. If they can redirect execution into the middle of a JIT page, they land on their shellcode. W^X alone doesn't stop this — it stops external writes, not the JIT's own code generation.

06 — Brain Exercise

Sharpen Your Pencil

Our JIT assumes add(a,b) always gets integer arguments. But JavaScript is dynamic — someone might call add("hello", 3). The JIT needs a "guard": before the fast path, check that both arguments are actually numbers. If not, jump to the interpreter (deoptimize).

Add a type guard to the emitted code: check that RDI and RSI both have the integer tag (in NaN-boxing: check the top bits are not NaN). Emit a conditional jump to a deopt_handler label if the check fails. How does this guard get removed if the JIT observes that the function is always called with numbers?

There Are No Dumb Questions

Q: Can the JIT be disabled for security?
Yes — many sandboxed environments (iOS WKWebView without the JIT entitlement, some CSP configurations) run JS without a JIT. Performance drops 5–10x but the attack surface is dramatically reduced: no executable pages generated at runtime, no JIT spraying, no deopt boundary bugs. It's a legitimate security tradeoff.
Q: What's the "JIT process" Chrome uses?
Chrome's V8 JIT compiles code in the renderer process — the same process running untrusted JS. A proposal called "V8 Sandbox" moves JIT compilation into a separate privileged process; the renderer sends IR to the JIT process over IPC and gets back read-only compiled code. This means a type confusion in the renderer can't directly corrupt JIT compilation. It's analogous to the GPU process architecture in B04.

07 — What's Next

Up Next: B09 — Garbage Collector

The JIT allocates objects freely; the GC reclaims them when no longer reachable. The mark-and-sweep algorithm must find all live objects before freeing dead ones. A use-after-free bug occurs when the GC frees an object that the JIT still has a cached pointer to — another exploit primitive.
