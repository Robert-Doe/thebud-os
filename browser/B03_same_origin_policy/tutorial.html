BROWSER B03 — SAME-ORIGIN POLICY

The Origin Boundary

JavaScript from evil.com must not read your inbox at mail.google.com. The Same-Origin Policy enforces this: scripts can only access data from the exact same scheme + host + port triple they were loaded from.

3-tuple
scheme + host + port = origin
strict
all 3 parts must match exactly
XHR/fetch

CORS

01 — The Big Analogy

Head First Moment

Imagine every website is a gated community. You can walk around freely inside your own community (same origin). But if you're a visitor from another community (different origin), the gate guard (browser SOP check) won't let you peek into residents' mailboxes (read their DOM/cookies/localStorage). You can knock on the door and wait to be let in (CORS), but you can't just reach through the fence.

02 — Parsing an Origin

/* sop.h */
typedef struct {
    char scheme[16];  /* "https" */
    char host[256];   /* "mail.google.com" */
    int  port;        /* 443 */
} origin_t;

int origin_parse(const char *url, origin_t *out) {
    /* url = "https://mail.google.com:443/inbox" */
    char *colon = strstr(url, "://");
    if (!colon) return -1;
    int slen = colon - url;
    strncpy(out->scheme, url, slen);
    out->scheme[slen] = '\0';

    char *host_start = colon + 3;
    char *slash = strchr(host_start, '/');
    char *port_colon = strchr(host_start, ':');
    if (port_colon && (!slash || port_colon < slash)) {
        int hlen = port_colon - host_start;
        strncpy(out->host, host_start, hlen);
        out->host[hlen] = '\0';
        out->port = atoi(port_colon + 1);
    } else {
        int hlen = slash ? slash - host_start : strlen(host_start);
        strncpy(out->host, host_start, hlen);
        out->host[hlen] = '\0';
        /* default ports */
        out->port = strcmp(out->scheme,"https")==0 ? 443 : 80;
    }
    return 0;
}

int origin_same(const origin_t *a, const origin_t *b) {
    return strcmp(a->scheme, b->scheme) == 0
        && strcmp(a->host,   b->host)   == 0
        && a->port == b->port;
}

Subdomains Are Different Origins

api.example.com and example.com are different origins even though one is a subdomain of the other. This surprises many developers. The relaxation mechanism is document.domain (deprecated) or CORS headers. Never assume subdomains can freely read each other — they can't by default.

04 — Enforcing SOP on XHR

/* xhr.c — simplified XHR with SOP check */
int xhr_send(const char *document_url, const char *request_url,
             char *response_buf, int buf_size) {
    origin_t doc_origin, req_origin;
    origin_parse(document_url, &doc_origin);
    origin_parse(request_url,  &req_origin);

    if (!origin_same(&doc_origin, &req_origin)) {
        /* cross-origin request: check CORS headers (B14) */
        /* for now: block it */
        fprintf(stderr, "SOP: blocked cross-origin request\n"
                "  document: %s://%s:%d\n"
                "  request:  %s://%s:%d\n",
                doc_origin.scheme, doc_origin.host, doc_origin.port,
                req_origin.scheme, req_origin.host, req_origin.port);
        return -1;  /* BLOCKED */
    }
    /* same origin: proceed with request */
    return http_fetch(request_url, response_buf, buf_size);
}
SOP Is Enforced by the Browser, Not the Server

The server never sees a blocked SOP request. The browser checks the origin before sending (for simple requests) or after a preflight (for complex ones). A server cannot opt out of SOP — only opt in to cross-origin sharing via CORS headers. This is why SOP works even for servers that don't know about CORS.

06 — Brain Exercise

Sharpen Your Pencil

SOP blocks JavaScript from reading cross-origin responses. But it doesn't stop a page from sending cross-origin requests — a form POST to bank.com goes through even from evil.com. The browser sends the request; it just won't give evil.com the response.

This means SOP alone doesn't stop CSRF (Cross-Site Request Forgery). If you're logged in to bank.com, and evil.com tricks your browser into POSTing to bank.com/transfer — that POST succeeds. What mechanism does bank.com need to add to detect that the request came from evil.com? (Hint: B17 covers this.)

There Are No Dumb Questions

Q: What about <img src="https://other.com/image.png">? That's cross-origin loading.
SOP allows cross-origin embedding for images, scripts, CSS, and iframes — that's how CDNs work. What it blocks is cross-origin reading from JavaScript. You can load an image from another origin; you cannot call canvas.getImageData() on it or read its pixels (that would be "tainted canvas"). The distinction is embedding vs. programmatic reading.
Q: What is "origin" for a file:// URL?
Each file:// URL is its own unique origin in most browsers — file:///a.html and file:///b.html cannot access each other. Some browsers (Firefox, older Chrome) used to allow it but it's a security risk (a local HTML file with XSS could read all your local files). The null origin ("null") is also special and appears for sandboxed iframes and data: URLs.

07 — What's Next

Up Next: B04 — Site Isolation

SOP is enforced in software by the JS engine — but what about hardware-level attacks like Spectre that can read across process boundaries using timing? Site Isolation puts different origins into different OS processes, so a Spectre attack in a compromised renderer can only read that site's own data.
