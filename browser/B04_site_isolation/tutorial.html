BROWSER B04 — SITE ISOLATION

One Process Per Site

SOP is a software check — Spectre can bypass software. Site isolation enforces origin boundaries at the hardware level: different sites live in different OS processes with separate address spaces. Spectre can only leak what's in the same process.

01 — The Big Analogy

Head First Moment

SOP is a rule enforced by a security guard standing inside a shared building (the renderer process). Spectre lets an attacker pick the guard's pocket while standing next to them — same address space, timing side-channel, game over.

Site isolation moves each website into its own separate building entirely. Even if an attacker has full Spectre capability inside their building, they can only steal furniture from that same building. Your bank data is across the street in a different building.

02 — Site vs Origin

/* site_isolation.h
   site key = scheme + eTLD+1 (not full host!)
   eTLD+1: "google.com" from "mail.google.com"
           "co.uk" is a public suffix, so "bbc.co.uk" is the eTLD+1
*/
const char *get_site_key(const char *url) {
    origin_t o;
    origin_parse(url, &o);
    /* strip to registrable domain using public suffix list */
    const char *etld1 = public_suffix_registrable(o.host);
    static char key[256];
    snprintf(key, sizeof(key), "%s://%s", o.scheme, etld1);
    return key;
}
/*
   https://mail.google.com  → "https://google.com"
   https://docs.google.com  → "https://google.com"  (SAME renderer)
   https://evil.com         → "https://evil.com"    (DIFFERENT renderer)
   https://bbc.co.uk        → "https://bbc.co.uk"
*/
Origin vs Site

Origin = scheme + host + port (fine-grained, B03). Site = scheme + eTLD+1 (coarser, for process allocation). mail.google.com and docs.google.com are different origins but the same site — they share a renderer process. This balances security (cross-site isolation) with memory cost (not one process per subdomain).

03 — The Site-to-Renderer Map

/* site_isolation.c */
#define MAX_SITES 64
struct site_entry {
    char site_key[256];
    pid_t renderer_pid;
    int   to_fd;
    int   from_fd;
} site_map[MAX_SITES];
int n_sites = 0;

/* Get or create a renderer for this site */
struct site_entry *get_renderer_for_url(const char *url) {
    const char *key = get_site_key(url);
    /* look up existing renderer */
    for (int i = 0; i < n_sites; i++)
        if (strcmp(site_map[i].site_key, key) == 0)
            return &site_map[i];
    /* spawn new renderer for this site */
    struct site_entry *e = &site_map[n_sites++];
    strncpy(e->site_key, key, sizeof(e->site_key)-1);
    e->renderer_pid = spawn_renderer(&e->to_fd, &e->from_fd);
    printf("[browser] new renderer PID=%d for site=%s\n",
           e->renderer_pid, key);
    return e;
}

/* Navigate a tab to a new URL */
void navigate(int tab_id, const char *url) {
    struct site_entry *r = get_renderer_for_url(url);
    tabs[tab_id].renderer = r;
    ipc_send(r->to_fd, "LOAD", url);
}
https://google.com→PID 1001(mail, docs, drive tabs)
https://bank.com→PID 1002(1 tab)
https://evil.com→PID 1003(1 tab)
https://news.com→PID 1004(2 tabs)

04 — Out-of-Process Iframes (OOPIF)

/* A page at https://news.com embeds:
   <iframe src="https://evil-ad.com/ad.html"></iframe>

   Without OOPIF: the iframe runs in news.com's renderer —
   same process, Spectre can read news.com's data.

   With OOPIF: the iframe gets its own renderer process. */

void process_iframe(const char *parent_url, const char *iframe_url) {
    const char *parent_site = get_site_key(parent_url);
    const char *iframe_site = get_site_key(iframe_url);

    if (strcmp(parent_site, iframe_site) != 0) {
        /* cross-site iframe: put it in a separate renderer */
        struct site_entry *r = get_renderer_for_url(iframe_url);
        ipc_send(r->to_fd, "RENDER_IFRAME", iframe_url);
        printf("[browser] OOPIF: %s in separate renderer PID=%d\n",
               iframe_url, r->renderer_pid);
    } else {
        /* same site: iframe can share the parent's renderer */
        struct site_entry *r = get_renderer_for_url(parent_url);
        ipc_send(r->to_fd, "RENDER_IFRAME_INPROC", iframe_url);
    }
}

06 — Brain Exercise

Sharpen Your Pencil

Site isolation requires the browser to know the public suffix list (PSL) to compute eTLD+1. The PSL is a Mozilla-maintained list of all known public suffixes (co.uk, com.au, etc.). It's a plain text file with ~9000 entries.

What happens if a new country code TLD adds a new public suffix and the browser's bundled PSL hasn't been updated yet? Who has the wrong site grouping, and what's the security impact? Could an attacker register a domain to exploit this lag?

There Are No Dumb Questions

Q: Does site isolation fully mitigate Spectre?
It significantly reduces the risk. Spectre can read memory in the current process — with site isolation, that's only data from that one site's renderer. But the renderer still contains the browser's own code and data structures, so a sufficiently powerful Spectre attack in a renderer could still read rendering engine state. Full mitigation requires hardware fixes (retpoline, IBRS) and high-resolution timer reduction (SharedArrayBuffer/COOP restrictions).
Q: How does the browser handle navigation from one site to another in the same tab?
When you click a link from evil.com to bank.com, the browser does a "cross-site navigation." It creates a new renderer for bank.com (or reuses an existing one), transfers rendering to it, and discards the evil.com renderer state. This is called a "browse instance swap" — the tab keeps its history, but the process behind it changes.
