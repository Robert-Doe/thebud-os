01 — The Big Analogy

Head First Moment

Two strangers want to share a secret in public without eavesdroppers learning it. They each hold up colored paint (public key). They each mix it with a secret private color (private key). They exchange their mixed colors publicly. Each mixes the received color with their own private color — and both end up with the same unique shade that nobody watching could reproduce. This is Diffie-Hellman key exchange. TLS wraps it in certificates to prove you're talking to the real server, not a man-in-the-middle.

02 — The 7-State Handshake

0CLIENTClientHelloTLS version, cipher suites, client random, key_share (pub key)
1SERVERServerHellochosen cipher, server random, key_share (server pub key)
2both[derive keys]ECDH → shared secret → HKDF → handshake_secret, app_secret
3SERVEREncryptedExtensionsALPN, SNI confirmation — encrypted

typedef enum {
    TLS_INIT, TLS_CLIENT_HELLO_SENT, TLS_SERVER_HELLO_RCVD,
    TLS_KEYS_DERIVED, TLS_CERT_RCVD, TLS_CERT_VERIFIED,
    TLS_ESTABLISHED
} tls_state_t;

typedef struct {
    tls_state_t  state;
    uint8_t      client_random[32];
    uint8_t      server_random[32];
    uint8_t      shared_secret[32];   /* from ECDH */
    uint8_t      handshake_key[32];   /* from HKDF */
    uint8_t      app_key[32];         /* session key */
    x509_cert_t *server_cert;
} tls_ctx_t;

03 — Key Derivation with HKDF

/* tls.c — derive handshake and application keys */
void tls_derive_keys(tls_ctx_t *ctx) {
    /* ECDH: shared_secret = client_priv * server_pub */
    x25519(ctx->shared_secret,
           ctx->client_private_key,
           ctx->server_public_key);

    /* HKDF-Extract: early_secret = HKDF(0, 0) */
    uint8_t early_secret[32];
    hkdf_extract(early_secret, NULL, 0, NULL, 0);

    /* HKDF-Expand: handshake_secret from shared_secret */
    uint8_t derived[32];
    hkdf_expand_label(derived, early_secret, "derived", NULL, 32);
    hkdf_extract(ctx->handshake_key, ctx->shared_secret, 32,
                 derived, 32);

    /* Application traffic secret */
    hkdf_expand_label(ctx->app_key, ctx->handshake_key,
                      "s ap traffic", transcript_hash(), 32);
}

04 — Certificate Validation: What Breaks Without It

/* cert_validate.c */
int validate_cert_chain(x509_cert_t *cert, const char *hostname) {
    /* Step 1: chain to a trusted root */
    if (!chain_to_trusted_root(cert)) return 0;  /* untrusted CA */

    /* Step 2: check expiry */
    if (cert->not_after < time(NULL)) return 0;  /* expired */

    /* Step 3: hostname match (SAN or CN) */
    if (!cert_matches_hostname(cert, hostname)) return 0;

    /* Step 4: check revocation (OCSP) */
    if (check_ocsp(cert) == REVOKED) return 0;

    return 1;  /* valid */
}

/* BAD: skipping validation */
int validate_cert_insecure(x509_cert_t *cert, const char *host) {
    return 1;  /* always valid — VULNERABLE TO MITM */
}

/* MitM attack with no cert validation:
   Attacker sits between client and server.
   Client connects to "bank.com" → actually connects to attacker.
   Attacker presents self-signed cert for "bank.com".
   Without validation: client accepts it. Attacker decrypts all traffic.
   Attacker forwards to real bank.com with their own TLS session.
   Client sees encrypted connection (padlock!) — but to the attacker. */
The Padlock Means Encrypted, Not Safe

HTTPS means the connection is encrypted. It says nothing about who it's encrypted to. If certificate validation is skipped or a rogue CA is trusted, an attacker can decrypt everything while the browser shows a padlock. This is why certificate pinning, Certificate Transparency logs, and CAA DNS records exist — to make it harder for a rogue CA to issue a valid cert for your domain.

06 — Brain Exercise

Sharpen Your Pencil

TLS 1.3 removed 0-RTT resumption's forward secrecy for the 0-RTT data. In 0-RTT, the client sends application data with the very first flight using a session ticket from a previous connection. If the session ticket is ever compromised, an attacker can decrypt those 0-RTT bytes — but not the rest of the session.

0-RTT data is also replay-able: an attacker can record the 0-RTT flight and re-send it to the server. Why is this a problem for non-idempotent requests (like POST)? How do servers mitigate replay attacks on 0-RTT data without abandoning the feature entirely?

There Are No Dumb Questions

Q: What's the difference between TLS 1.2 and 1.3?
TLS 1.2 required 2 round trips before application data could flow; TLS 1.3 reduced it to 1 RTT (or 0-RTT for resumption). TLS 1.3 also removed weak cipher suites (RSA key exchange — which doesn't provide forward secrecy), RC4, MD5/SHA-1 for signing, and negotiable compression. The result: faster, simpler, and far fewer misconfiguration opportunities. Mandatory forward secrecy (ECDHE only) means past traffic is safe even if the server's private key is later compromised.
Q: What is Certificate Transparency?
Every publicly trusted certificate must be logged in a publicly auditable CT log before browsers will accept it. This means if a rogue CA issues a cert for your domain, it appears in the public log and your monitoring can detect it within minutes. Chrome requires SCTs (Signed Certificate Timestamps) in every certificate since 2018. You can monitor your own domain's certs at crt.sh.
