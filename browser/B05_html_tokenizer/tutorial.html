01 — The Big Analogy

Head First Moment

HTML parsing is like reading a book in a foreign language with no punctuation — you have to infer sentence boundaries as you go. The parser sees a stream of characters and decides: "is this a tag? an attribute? text content?" based entirely on what state it's currently in. The tricky part: HTML was designed to be fault-tolerant. <p>Hello</p></b> is invalid, but every browser must parse it — and parse it the same way.

typedef enum {
    STATE_DATA, STATE_TAG_OPEN, STATE_TAG_NAME,
    STATE_BEFORE_ATTR, STATE_ATTR_NAME,
    STATE_BEFORE_ATTR_VAL, STATE_ATTR_VAL_DQ,
    STATE_ATTR_VAL_SQ, STATE_ATTR_VAL_UNQUOTED,
    STATE_AFTER_ATTR_VAL, STATE_SELF_CLOSING,
    STATE_END_TAG_OPEN, STATE_COMMENT_START,
    STATE_SCRIPT_DATA,  /* special raw-text state */
} tok_state_t;

typedef struct {
    tok_state_t state;
    char        tag_name[64];
    char        attr_name[64];
    char        attr_val[1024];
    int         is_end_tag;
} tokenizer_t;

void tokenizer_feed(tokenizer_t *t, char c, dom_builder_t *dom) {
    switch (t->state) {
    case STATE_DATA:
        if (c == '<') { t->state = STATE_TAG_OPEN; break; }
        dom_append_text(dom, c);
        break;
    case STATE_TAG_OPEN:
        if (c == '/') { t->state = STATE_END_TAG_OPEN; break; }
        if (c == '!') { t->state = STATE_COMMENT_START; break; }
        if (isalpha(c)) {
            t->is_end_tag = 0;
            t->tag_name[0] = tolower(c);
            t->tag_name[1] = '\0';
            t->state = STATE_TAG_NAME;
        }
        break;
    case STATE_TAG_NAME:
        if (c == '>') {
            /* emit open tag token */
            dom_open_tag(dom, t->tag_name);
            /* switch to raw-text state for script/style */
            if (strcmp(t->tag_name,"script")==0 ||
                strcmp(t->tag_name,"style")==0)
                t->state = STATE_SCRIPT_DATA;
            else
                t->state = STATE_DATA;
        } else if (isspace(c)) {
            t->state = STATE_BEFORE_ATTR;
        } else {
            strncat(t->tag_name, &c, 1);
        }
        break;
    /* ... ~75 more states ... */
    }
}

03 — Parser Differentials and mXSS

Mutation XSS (mXSS)

A sanitizer serializes your HTML to a string, then the browser re-parses it. If the sanitizer's parser and the browser's parser interpret the same bytes differently, the sanitizer says "safe" while the browser renders a script. This is mutation XSS.

/* Classic mXSS: inserting HTML into innerHTML triggers re-parsing */

/* Step 1: attacker supplies this string */
const char *payload = "<noscript><p title='</noscript>"
                      "<img src=x onerror=alert(1)>'>";

/* Step 2: sanitizer sees <noscript> as harmless, allows it.
   Sanitizer's parser (with scripting disabled) treats the
   </noscript> inside the attribute as closing the noscript
   element — payload looks safe.

   Step 3: browser sets innerHTML with the "sanitized" string.
   Browser's parser (scripting enabled) treats <noscript> as
   raw text — </noscript> inside attributes is NOT a closer.
   The img tag and its onerror handler are now OUTSIDE noscript.
   XSS fires. */

/* Lesson: sanitize after serialization+re-parse, not before. */
The Fix: Parse, Don't String-Match

A correct sanitizer (like DOMPurify) parses the HTML into a DOM tree using the browser's own parser, walks the tree to remove dangerous nodes/attributes, then serializes back to a string. It never tries to make security decisions on raw HTML strings.

05 — Brain Exercise

Sharpen Your Pencil

Our tokenizer has a STATE_SCRIPT_DATA for raw-text elements. In this state, the only way to exit is seeing the exact string </script>. But what about </SCRIPT> or </Script>? HTML tag names are case-insensitive.

Add case-insensitive exit detection to STATE_SCRIPT_DATA. Then consider: could an attacker craft a string that exits raw-text state prematurely and injects a new script tag? Try: <script>var x = "</script><script>alert(1)</script>".

There Are No Dumb Questions

Q: Why does HTML have ~80 states? That seems like a lot.
The HTML spec was written to describe how browsers already behaved — meaning all the quirks and special cases of IE, Netscape, and early Firefox were codified. Special elements like <script>, <style>, <textarea>, <title> have unique parsing rules. Comments have their own states. DOCTYPE detection, CDATA, character references — each adds states. It grew organically, not by design.
Q: Why can't we just use a regex to parse HTML?
HTML is not a regular language — it has nesting (requires a stack/push-down automaton at minimum), context-sensitive parsing (the same bytes mean different things inside <script> vs. <div>), and complex error recovery rules. The famous Stack Overflow answer "you can't parse HTML with regex" is correct — not as a joke, but as a formal computational theory statement.
