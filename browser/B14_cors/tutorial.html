BROWSER B14 — CORS

Cross-Origin Resource Sharing

SOP blocks cross-origin reads by default. CORS is the server's opt-in to allow them. Get it wrong — Access-Control-Allow-Origin: * with credentials — and any website can read your users' private API responses.

01 — The Big Analogy

Head First Moment

SOP is the default locked door between websites. CORS is the server sliding a note under the door: "I'll allow visitors from example.com." The browser checks this note before passing the response to the requesting script. If the note says "everyone welcome" (*) but also "with credentials" — that's like leaving your front door open with your diary on the table.

02 — Simple vs Preflighted Requests

/* cors.c — CORS check implementation */

/* "Simple" requests (GET/POST with simple headers) go directly.
   "Complex" requests (PUT/DELETE/custom headers) require preflight. */

int is_simple_request(const char *method, http_headers_t *headers) {
    if (strcmp(method,"GET")==0 || strcmp(method,"HEAD")==0 ||
        strcmp(method,"POST")==0)
    {
        /* also check Content-Type for POST */
        const char *ct = get_header(headers, "Content-Type");
        if (ct && strstr(ct,"application/json")) return 0; /* complex */
        return 1;
    }
    return 0;  /* PUT, DELETE, etc. = complex */
}

/* Preflight: browser sends OPTIONS first */
void send_preflight(const char *url, const char *method,
                    const char *origin) {
    http_request_t req = {
        .method = "OPTIONS",
        .url    = url,
        .headers = {
            {"Origin",                        origin},
            {"Access-Control-Request-Method", method},
            {"Access-Control-Request-Headers","Authorization"},
        }
    };
    http_send(&req);
    /* Server must respond with:
       Access-Control-Allow-Origin: https://your-site.com
       Access-Control-Allow-Methods: PUT, DELETE
       Access-Control-Allow-Headers: Authorization
       Only then does browser send the actual request */
}

03 — Three CORS Misconfigurations

/* MISCONFIGURATION 1: reflect Origin header blindly */
void cors_handler_bad1(http_request_t *req, http_response_t *res) {
    const char *origin = get_header(req, "Origin");
    /* BUG: echo back whatever origin was sent */
    set_header(res, "Access-Control-Allow-Origin", origin);
    set_header(res, "Access-Control-Allow-Credentials", "true");
    /* attacker sends Origin: https://evil.com
       response: Access-Control-Allow-Origin: https://evil.com
       browser lets evil.com read the credentialed response! */
}

/* MISCONFIGURATION 2: null origin */
void cors_handler_bad2(http_request_t *req, http_response_t *res) {
    const char *origin = get_header(req, "Origin");
    if (strcmp(origin,"null")==0 || is_trusted(origin))
        set_header(res, "Access-Control-Allow-Origin", origin);
    /* "null" origin is sent by sandboxed iframes and data: URLs
       attacker creates: <iframe sandbox="allow-scripts" src="data:...">
       which sends Origin: null — trusted! */
}

/* MISCONFIGURATION 3: overly broad wildcard */
void cors_handler_bad3(http_request_t *req, http_response_t *res) {
    set_header(res, "Access-Control-Allow-Origin", "*");
    set_header(res, "Access-Control-Allow-Credentials", "true");
    /* INVALID: spec forbids * with credentials, but some servers
       try it anyway. Modern browsers reject this combination. */
}

/* CORRECT implementation */
void cors_handler_good(http_request_t *req, http_response_t *res) {
    static const char *ALLOWED[] = {
        "https://app.example.com", "https://www.example.com", NULL
    };
    const char *origin = get_header(req, "Origin");
    for (int i = 0; ALLOWED[i]; i++) {
        if (strcmp(origin, ALLOWED[i]) == 0) {
            set_header(res, "Access-Control-Allow-Origin", origin);
            set_header(res, "Vary", "Origin");  /* important for caches */
            set_header(res, "Access-Control-Allow-Credentials", "true");
            return;
        }
    }
    /* Origin not in allowlist: send no CORS headers → blocked */
}
Vary: Origin Is Critical

If the server reflects the Origin header in ACAO and a CDN caches the response without Vary: Origin, the first requester's allowed origin gets cached and served to everyone — including blocked origins. Always add Vary: Origin when reflecting the Origin header.

05 — Brain Exercise

Sharpen Your Pencil

CORS only restricts reading responses — it doesn't stop the request from being sent (for simple requests). A GET to https://bank.com/transfer?to=attacker&amount=1000 would be sent by the browser even from evil.com; the attacker just can't read the response.

But wait — if the transfer happens server-side on GET receipt, the attacker doesn't need to read the response. They just need the request to be sent. What web security mechanism exists specifically to prevent this type of cross-site request forgery? (Hint: B17 covers it.) And why doesn't CORS help here?

There Are No Dumb Questions

Q: What is CORB (Cross-Origin Read Blocking)?
CORB is a browser defence that blocks cross-origin reads of HTML, JSON, and XML responses even when the server sends permissive CORS headers, if the request was not an XHR or fetch (e.g., it came from an img or script tag). This prevents Spectre-based attacks from loading sensitive data into the renderer's memory via side-channel-readable tags. It's an automatic browser mitigation, not a header you set.
Q: Can CORS be used to call an API on localhost from a web page?
The browser sends the request (localhost is a different origin from example.com), and if localhost's server responds with the right CORS headers, the response is readable. This is how browser devtools extensions communicate with local servers. Security consideration: any website can probe your localhost if your local server has permissive CORS, potentially fingerprinting installed software or attacking local admin UIs.

06 — What's Next

Up Next: B15 — HTTP Request Smuggling

CORS is about what the browser allows. HTTP smuggling is about confusing the server. When a front-end proxy and back-end server disagree on where one HTTP request ends and the next begins, an attacker can "smuggle" a partial request that gets prepended to another user's next request — rewriting their headers or poisoning cache entries.
