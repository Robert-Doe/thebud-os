BROWSER B09 — GARBAGE COLLECTOR

Mark, Sweep, Free

JavaScript allocates objects constantly and never frees them manually. The GC finds objects no longer reachable from roots and reclaims them. A use-after-free happens when the GC frees an object that the engine still holds a pointer to.

mark
DFS from roots, set mark bit
sweep
free all unmarked objects
UAF
use-after-free = dangling pointer
write barrier
incremental GC safety mechanism

01 — The Big Analogy

Head First Moment

The GC is like a cleaning crew that sweeps through the engine room every so often. First they put a green sticky note on every machine actively being used (mark). Then they remove every machine without a sticky note (sweep). The problem: if an engineer has the machine's serial number written on a notepad but the cleaning crew already took it away — that's a use-after-free. The engineer goes to use serial number 0xDEAD and finds something completely different sitting there now.

02 — The Heap and Mark Bits

/* gc.h — minimal mark-and-sweep heap */
#define HEAP_SIZE    (1024 * 1024)  /* 1MB */
#define MAX_OBJECTS  4096

typedef struct gc_obj {
    uint8_t   marked;
    uint8_t   type;       /* OBJ_ARRAY, OBJ_STRING, etc. */
    uint16_t  n_refs;     /* number of child pointers */
    struct gc_obj **refs; /* child pointers (for marking) */
    uint8_t   data[];     /* payload */
} gc_obj_t;

static gc_obj_t *heap[MAX_OBJECTS];
static int       heap_count = 0;

gc_obj_t *gc_alloc(size_t size, uint8_t type) {
    gc_obj_t *obj = malloc(sizeof(gc_obj_t) + size);
    obj->marked = 0;
    obj->type   = type;
    obj->n_refs = 0;
    obj->refs   = NULL;
    heap[heap_count++] = obj;
    if (heap_count >= MAX_OBJECTS) gc_collect();
    return obj;
}

03 — Mark and Sweep

/* Roots: global variables, stack values, registers */
extern gc_obj_t **gc_roots;
extern int        gc_root_count;

/* MARK PHASE: DFS from all roots */
void gc_mark_object(gc_obj_t *obj) {
    if (!obj || obj->marked) return;  /* already visited */
    obj->marked = 1;
    for (int i = 0; i < obj->n_refs; i++)
        gc_mark_object(obj->refs[i]);  /* recurse into children */
}

void gc_mark_phase(void) {
    for (int i = 0; i < gc_root_count; i++)
        gc_mark_object(gc_roots[i]);
}

/* SWEEP PHASE: free all unmarked objects */
void gc_sweep_phase(void) {
    int write = 0;
    for (int i = 0; i < heap_count; i++) {
        if (heap[i]->marked) {
            heap[i]->marked = 0;  /* clear for next collection */
            heap[write++] = heap[i];
        } else {
            free(heap[i]);        /* not reachable → free */
        }
    }
    heap_count = write;
}

void gc_collect(void) {
    gc_mark_phase();
    gc_sweep_phase();
}

04 — Use-After-Free

/* UAF demo: engine caches a pointer to an object,
   GC collects the object, engine uses the stale pointer */

gc_obj_t *cached_obj = gc_alloc(64, OBJ_ARRAY);
cached_obj->data[0]  = 42;

/* attacker removes all references to cached_obj from roots */
remove_from_roots(cached_obj);

/* GC runs — cached_obj is unmarked, gets freed */
gc_collect();

/* BUG: engine still has `cached_obj` pointer */
printf("%d\n", cached_obj->data[0]);
/* cached_obj memory is now free — could be reallocated
   to a different object. Reading it is undefined behavior.
   Writing to it corrupts whatever now lives at that address. */

/* Exploit: allocate a new object at the same address */
gc_obj_t *evil = gc_alloc(64, OBJ_FUNCTION);  /* same slot! */
/* Now cached_obj == evil — type confusion via UAF!
   Engine thinks cached_obj is OBJ_ARRAY,
   but it's actually OBJ_FUNCTION. Exploit proceeds. */
Heap Grooming

Attackers deliberately spray many same-sized allocations before triggering a UAF to control which object gets placed at the freed address. This "heap grooming" (or "heap feng shui") maximizes the chance that the UAF pointer now points to an attacker-controlled object of the right size and type to enable type confusion (B10).

06 — Brain Exercise

Sharpen Your Pencil

Our stop-the-world GC pauses all JS execution while marking and sweeping. For a page with 100MB of heap, this pause could be hundreds of milliseconds — a terrible user experience. Incremental GC breaks the work into small slices, but now new objects can be allocated and pointers can change between mark slices.

This requires a "write barrier": every time a pointer inside a marked object is updated, the barrier adds the target to the mark worklist. Without it, a pointer added after the object was marked would be missed. How would you implement a write barrier in gc_obj_set_ref()?

There Are No Dumb Questions

Q: Why not just use reference counting instead of mark-and-sweep?
Reference counting is simple but can't collect cycles: if object A points to B and B points to A, both have refcount > 0 forever even if nothing else refers to them. Python and Swift use refcounting + a separate cycle detector. V8 uses a generational GC (fast "young" generation + slow "old" generation) which handles cycles naturally.
Q: Can the GC be used as a security mitigation?
Yes — some engines zero memory before freeing it (zeroing sweeper) to prevent UAF reads from returning useful data. Others use pointer authentication (PAC on ARM) or "handle-based" references (the engine uses an indirection table; if an object is moved or freed, the handle is invalidated) to make UAF pointers invalid rather than dangerous. Chrome's MiraclePtr (PartitionAlloc quarantine) is a recent example of GC-adjacent UAF mitigation.
