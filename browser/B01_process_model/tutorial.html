01 — The Big Analogy

Head First Moment

Old browsers (IE6, Firefox 1) were single-process: one bad tab crashed the whole browser, and one malicious script could read data from every other tab. It was like running every website in the same room with the same keychain.

Modern browsers are more like a bank. The browser process is the vault manager — it holds your cookies, passwords, and settings. Each tab is a teller window staffed by a contract worker (renderer process) with no access to the vault. The teller can only pass requests through a slot (IPC pipe), which the vault manager checks before acting on.

02 — The Browser Process in C

/* browser.c — the main browser process */
#include <unistd.h>
#include <sys/wait.h>
#include "ipc.h"

#define MAX_TABS 8
struct tab { pid_t pid; int to_fd; int from_fd; } tabs[MAX_TABS];

pid_t spawn_renderer(int *to_fd, int *from_fd) {
    int p2r[2], r2p[2];  /* parent-to-renderer, renderer-to-parent */
    pipe(p2r); pipe(r2p);
    pid_t pid = fork();
    if (pid == 0) {
        /* child = renderer */
        dup2(p2r[0], STDIN_FILENO);
        dup2(r2p[1], STDOUT_FILENO);
        close(p2r[0]); close(p2r[1]);
        close(r2p[0]); close(r2p[1]);
        execl("./renderer", "renderer", NULL);
        _exit(1);
    }
    /* parent: keep write end to renderer, read end from renderer */
    close(p2r[0]); close(r2p[1]);
    *to_fd   = p2r[1];
    *from_fd = r2p[0];
    return pid;
}

int main(void) {
    /* open two tabs */
    tabs[0].pid = spawn_renderer(&tabs[0].to_fd, &tabs[0].from_fd);
    tabs[1].pid = spawn_renderer(&tabs[1].to_fd, &tabs[1].from_fd);

    ipc_send(tabs[0].to_fd, "LOAD", "https://example.com");
    ipc_send(tabs[1].to_fd, "LOAD", "https://other.com");

    struct ipc_msg msg;
    while (ipc_recv(tabs[0].from_fd, &msg) == 0)
        printf("[tab0] %s: %s\n", msg.type, msg.payload);

    /* if renderer crashes, SIGCHLD tells us — restart it */
    waitpid(tabs[0].pid, NULL, 0);
    printf("Tab 0 renderer exited — respawning\n");
}

03 — IPC Message Format

/* ipc.h — simple length-prefixed JSON messages */
struct ipc_msg {
    char type[32];
    char payload[1024];
};

int ipc_send(int fd, const char *type, const char *payload) {
    struct ipc_msg m;
    strncpy(m.type, type, sizeof(m.type)-1);
    strncpy(m.payload, payload, sizeof(m.payload)-1);
    return write(fd, &m, sizeof(m)) == sizeof(m) ? 0 : -1;
}

int ipc_recv(int fd, struct ipc_msg *m) {
    ssize_t n = read(fd, m, sizeof(*m));
    return n == sizeof(*m) ? 0 : -1;
}

/* renderer.c — the renderer process */
int main(void) {
    struct ipc_msg msg;
    while (ipc_recv(STDIN_FILENO, &msg) == 0) {
        if (strcmp(msg.type, "LOAD") == 0) {
            printf("Renderer loading: %s\n", msg.payload);
            /* parse HTML, run JS, send back PAINTED */
            ipc_send(STDOUT_FILENO, "PAINTED", "ok");
        }
    }
    return 0;
}
Real Browsers Use Mojo / IPC

Chrome's actual IPC layer (Mojo) is a typed message-passing system with shared memory for large payloads and pipes for control messages. It generates C++ stubs from interface definitions — much like gRPC. Our simple struct-over-pipe achieves the same isolation properties, just without the generated code.

05 — Brain Exercise

Sharpen Your Pencil

Our browser spawns one renderer per tab. Chrome actually uses a "site isolation" policy — one renderer per site (scheme + eTLD+1), not per tab. Two tabs open to mail.google.com and docs.google.com both land in the same renderer process.

Why is site-based isolation stronger than tab-based isolation for Spectre-style attacks? And why does it use less memory than one-renderer-per-tab? (Hint: think about what gets shared between tabs of the same site.)

There Are No Dumb Questions

Q: Why can't we just use threads instead of processes for tabs?
Threads share an address space — a bug in one tab's JavaScript can read or corrupt another tab's memory. Processes have separate address spaces enforced by the MMU (your CR3 per process from Module 15). A crashed or compromised renderer process cannot read the browser process's cookie store because they live in separate virtual address spaces.
Q: What's the performance cost of all these processes?
Significant: each renderer process has its own copy of the JS engine, layout engine, and font cache — easily 50–100 MB per renderer. Chrome uses memory-sharing tricks (read-only shared memory for common data) and process reuse to reduce this. It's a deliberate tradeoff: memory for security. The alternative is fast but exploitable.

06 — What's Next

Up Next: B02 — Renderer Sandbox

A separate process helps, but an exploited renderer still has the full syscall surface: it can open files, make network connections, spawn processes. The sandbox (B02) adds a syscall whitelist — the renderer is allowed only a tiny set of syscalls (read, write, exit). Everything else is blocked at the kernel level via seccomp-BPF.
