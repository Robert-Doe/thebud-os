Shared Memory

The fastest IPC: two processes, one physical frame. No kernel buffer, no copying, no syscall in the hot path. Write in one process; read instantly in the other — they're looking at the same RAM.

01 — The Big Analogy

Head First Moment

Two people sharing a whiteboard in the same room. Person A writes something; person B sees it instantly — no messenger, no copy, no delay. The whiteboard is the shared physical memory. Each person's eyes are their virtual address space, but both pairs of eyes are looking at the same physical whiteboard.

Compare this to pipes (Module 20): pipes are like passing notes through a slot in the wall. Slower (kernel copy), but safer — you can't accidentally scribble on each other. Shared memory is faster but requires you to agree on who writes when.

02 — The shm_segment Table

/* shm.h */
#define SHM_MAX_SEGS   16
#define SHM_MAX_PAGES  4     /* up to 16KB per segment */

struct shm_segment {
    int      key;                       /* user-chosen identifier */
    int      used;
    int      n_pages;
    uint32_t frames[SHM_MAX_PAGES];    /* physical frame addresses */
};

static struct shm_segment shm_table[SHM_MAX_SEGS];

/* SYS_SHMGET = 15 */
int sys_shmget(int key, int size) {
    /* find existing segment with this key */
    for (int i = 0; i < SHM_MAX_SEGS; i++)
        if (shm_table[i].used && shm_table[i].key == key)
            return i;    /* already exists, return id */
    /* allocate new segment */
    int id = shm_alloc_slot();
    int n = PAGE_ALIGN_UP(size) / PAGE_SIZE;
    shm_table[id].key    = key;
    shm_table[id].n_pages = n;
    for (int p = 0; p < n; p++)
        shm_table[id].frames[p] = pmm_alloc_page();
    return id;
}

03 — shmat: Map Into This Process

/* SYS_SHMAT = 16 */
void *sys_shmat(int shm_id, void *addr_hint) {
    struct shm_segment *seg = &shm_table[shm_id];
    if (!seg->used) return (void*)-1;

    /* find a free VA range for this process */
    uint32_t va = find_free_va_range(current,
                                     (uint32_t)addr_hint,
                                     seg->n_pages * PAGE_SIZE);
    /* map each physical frame into this process's PD */
    for (int p = 0; p < seg->n_pages; p++) {
        paging_map(current->cr3,
                   va + p * PAGE_SIZE,
                   seg->frames[p],          /* SAME physical frame */
                   PAGE_PRESENT | PAGE_WRITE | PAGE_USER);
    }
    /* also record as a vm_region so the fault handler knows */
    vm_add_region(current, va, seg->n_pages * PAGE_SIZE,
                  VM_PROT_R | VM_PROT_W);
    return (void*)va;
}

VAs Don't Have to Match

Process A maps the shared segment at 0x30000000; process B maps it at 0x40000000. The virtual addresses are different — only the physical frames are the same. This is fine as long as processes don't store raw pointers inside the shared region (a pointer valid in A's VA space is garbage in B's). Use offsets, not pointers, inside shared memory.

04 — Synchronization: The Spinlock

/* Place the lock in the shared region itself */
struct shared_data {
    volatile int lock;   /* 0=free, 1=held */
    int          value;
    char         message[64];
};

/* Spinlock using x86 XCHG (atomic test-and-set) */

    int expected = 1;

        /* spin */ ;

static inline void spin_unlock(volatile int *lock) {

}

/* Writer */
struct shared_data *shm = sys_shmat(id, 0);
spin_lock(&shm->lock);
shm->value = 42;
spin_unlock(&shm->lock);

/* Reader (other process, different VA, same frame) */
struct shared_data *shm2 = sys_shmat(id, 0);
spin_lock(&shm2->lock);
int v = shm2->value;  /* guaranteed to see 42 */
spin_unlock(&shm2->lock);
volatile Is Not Enough

volatile tells the compiler "don't cache this in a register" but doesn't prevent CPU reordering. On x86 the memory model is strong enough that volatile works in practice for simple spinlocks — but on ARM or RISC-V you'd need memory barriers (dmb / fence). The __sync_* builtins emit the right instructions for the target architecture.

06 — Brain Exercise

Sharpen Your Pencil

What happens when Process A exits while Process B still has the shared segment mapped? Our current code doesn't track attachment counts — the shm_segment entry stays allocated forever. Real Unix uses an nattach counter: shmat increments it, shmdt decrements it, and the segment is freed when count reaches 0.

Add nattach to struct shm_segment and implement a sys_shmdt (detach) syscall. What should happen to the physical frames in sys_shmdt if nattach drops to zero?

There Are No Dumb Questions

Q: How is this different from mmap on the same file?
File-backed mmap achieves the same "same physical frames, multiple processes" effect but the backing store is a file. Shared anonymous memory (like our shm) has no file — it exists only in RAM until all attachers detach. POSIX shm_open creates a file in /dev/shm (tmpfs) to give the segment a name; our key integer is the same idea.
Q: Can I use shared memory between a parent and child after fork?
Yes — if parent creates and attaches a shm segment before fork, both parent and child inherit the mapping (CoW from Module 21 skips kernel-mapped pages). Writes in one are immediately visible in the other. This is why shared memory + fork is a popular pattern for high-performance parallel programs (like web servers with a shared cache).

07 — What's Next

Up Next: Module 24 — Threads

Processes share nothing by default (separate CR3, separate file tables). Threads are like processes that share everything: same CR3 (same address space), same fd_table, but each gets its own kernel stack and CPU registers. Thread creation is cheap; synchronization is your problem.
