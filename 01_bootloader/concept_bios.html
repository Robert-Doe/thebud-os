The BIOS: Your Motherboard's Tiny, Ancient Butler

Decades before your operating system existed, a small, permanent program was already living on your motherboard — silently testing hardware, waking up devices, and knowing exactly one address to hand control to. Meet the first piece of software that ever runs on your machine.

01 — The Big Analogy

Head First Moment

Picture a hotel that's been closed for the night. A single night-shift security guard is on duty. When someone finally arrives, the guard doesn't know who they are, what they want, or what room they're headed to — but the guard knows the building cold: where the light switches are, where the fire exits are, which elevators work. The guard turns on the lobby lights, checks that the elevators respond, glances at the register for who's expected, and then walks the guest to the door of their room and says "you're on your own from here." Then the guard's job for that arrival is completely done.

That guard is the BIOS. It doesn't know what operating system you're running, what your bootloader does, or what your OS looks like once it's up. It just knows the raw physical building — RAM, keyboard, screen, disk controllers — well enough to wake them up and hand off to whatever shows up asking.

BIOS stands for Basic Input/Output System. It is firmware — software permanently stored on a chip on the motherboard, not on your hard drive, so it survives even a completely empty disk. It exists so that no operating system ever has to know, from scratch, how to talk to every possible brand and model of keyboard controller, disk controller, or display adapter — the BIOS abstracts that away with a small, standardized menu of services.

02 — A Short, Surprisingly Specific History

Where the Word Actually First Appeared

The term "BIOS" wasn't coined by IBM — it was coined by Gary Kildall in 1975 for CP/M, an early microcomputer operating system. CP/M split into two parts: a portable core (the "BDOS") and a small, hardware-specific layer called the BIOS, whose entire job was to isolate the parts of the OS that had to know about specific hardware. When IBM built the original IBM PC in 1981, they adopted both the concept and the name for their own ROM firmware — and because the IBM PC became the dominant hardware standard, "BIOS" became the universal term, even on machines with no CP/M lineage at all.

The BIOS lives on a ROM (or, on modern boards, flash memory that behaves like ROM until you deliberately reflash it) — physically soldered to the motherboard, independent of any hard drive. This is precisely why a totally blank hard drive still shows you something on screen when you power on: the BIOS runs and displays its own messages before it ever tries to touch a disk.

03 — What the BIOS Actually Does, Step by Step

  1. POST — Power-On Self Test. Before anything else, the BIOS runs a battery of sanity checks: is RAM responding correctly, is the CPU functional, are basic devices present. This is why a machine with faulty RAM often beeps in a specific pattern instead of booting — that's the BIOS reporting a POST failure through the only output device it can guarantee works (the speaker) before video is even confirmed functional.
  2. Hardware initialization. Sets up the keyboard controller, brings up basic video output, and detects what storage devices are physically connected.
  3. Boot device scan. Walks through a configured list of devices (floppy, hard disk, USB, network) in order, and for each one, reads the first 512-byte sector and checks whether the last two bytes are 0x55, 0xAA — the "magic number" signature that means "this sector is executable code, not just data."
  4. Load and jump. The moment it finds a sector ending in that signature, it copies all 512 bytes into RAM at address 0x7C00 and jumps the CPU there. From this exact instant, the BIOS's involvement in booting is over — although, importantly, its services (see §04) remain callable for as long as the CPU stays in Real Mode.
A Detail Worth Sitting With

The BIOS does not know or care what's inside those 512 bytes. It doesn't parse a filesystem, doesn't check for a valid program, doesn't verify anything beyond two magic bytes at a fixed offset. This is exactly why a bootloader bug that corrupts the signature produces total silence rather than an error message — as far as the BIOS is concerned, a disk either has the magic bytes or it simply isn't bootable, full stop.

04 — The BIOS's "API": Interrupt Services

Once your bootloader is running, it's not alone — it can still call back into the BIOS for help, the same way an app calls into an operating system's API. The mechanism is software interrupts: your code loads specific values into specific registers, then executes int with a specific number, and the CPU looks up that number in the Interrupt Vector Table (a list of addresses sitting at the very start of memory, placed there by the BIOS itself) to find and jump to the right BIOS routine.

InterruptService CategoryExample use in this project
INT 0x10Video servicesAH=0x0E "teletype output" — used by boot.asm's print_string to print "BobOS Booting..."
INT 0x13Disk servicesAH=0x02 "read sectors" — reads raw sectors off disk into RAM; this is how a real bootloader loads a kernel too big for 512 bytes
INT 0x16Keyboard servicesReading raw keypresses before your own keyboard driver exists
INT 0x15System servicesQuerying the BIOS for a memory map — essential once you need to know how much RAM is safe to use before writing a memory manager

The pattern is always the same: put a function number in AH, put whatever arguments that function needs in other registers, fire the interrupt, and the BIOS's own code — running at whatever address the Interrupt Vector Table points to — does the work and returns results in registers (often signaling success/failure via the Carry Flag). This entire calling convention is documented in community references like Ralf Brown's Interrupt List, which catalogs essentially every BIOS/DOS interrupt function ever documented, vendor quirks included.

05 — BIOS vs. UEFI

Every machine made since roughly the mid-2010s ships with UEFI (Unified Extensible Firmware Interface) instead of classic BIOS — but nearly all UEFI implementations include a CSM (Compatibility Support Module) or "legacy boot" mode that behaves exactly like classic BIOS, which is precisely the mode this project targets.

Classic BIOS (what BobOS targets)

  • 16-bit real mode only
  • Boots via MBR: first 512 bytes, 0x55AA signature
  • No native filesystem awareness — raw sector reads only
  • ~1MB addressable during boot
  • Simple, small, and — crucially for this project — simple enough to write by hand

UEFI (modern default)

  • Runs in 32/64-bit mode from the start
  • Boots via GPT partition table + a FAT32 "EFI System Partition"
  • Understands FAT32 filesystems and loads .efi executables (a PE format, like Windows .exe) directly
  • Can address far more memory, supports networking, graphics, even a mouse-driven setup menu
  • Far larger and more complex — not something you hand-assemble in 512 bytes
Why This Project Deliberately Chooses Legacy BIOS

UEFI would require producing a FAT32-formatted disk image and a PE-format executable before you've written a single line of OS logic — real complexity that has nothing to do with learning how operating systems work. Legacy BIOS lets the entire "get code running on bare metal" problem collapse down to 512 bytes and one magic number, which is exactly the right amount of complexity for Module 1.

06 — The BIOS in This Project, Specifically: SeaBIOS

When you run qemu-system-i386 -fda boot.img, QEMU doesn't invent its own boot behavior — it boots SeaBIOS, an open-source, legacy-BIOS-compatible firmware implementation bundled with QEMU. Every fact in §03 and §04 above is exactly what SeaBIOS implements, because SeaBIOS's entire purpose is to faithfully reproduce the same documented behavior real 1981-lineage PC BIOSes provide. Its source code is public, so if you ever want ground truth for exactly what INT 0x10 AH=0x0E does, you can read the actual implementation rather than trust a summary.

This is also the direct answer to a question that comes up naturally once you start writing boot code: how do I know this will work in QEMU if I've never run QEMU before? Because QEMU isn't a mystery box with its own private rules — it's a faithful implementer of a documented spec (the x86 ISA plus the BIOS interrupt contract) that you have independent access to. The full version of this argument lives in boot_asm_deepdive.html §03.

There Are No Dumb Questions

Q: Is the BIOS "the bootloader"?
No — this is the most common conflation of all four terms. The BIOS is firmware that finds and loads the bootloader; it never is the bootloader. The bootloader is separate code, written by you (or GRUB, or Windows), sitting on the disk. Full distinction in concept_bootloader.html.
Q: Can the BIOS be updated?
Yes — modern BIOS/UEFI firmware lives on flash memory, not true read-only ROM, specifically so manufacturers can patch bugs and add hardware support ("flashing the BIOS"). It's still firmware in the sense that it persists without a working OS or hard drive, which is the property that matters for booting.
Q: Why does BIOS video output look so crude compared to a modern OS?
Because INT 0x10's teletype function is decades old and was designed for the simplest possible text output on hardware from the early 1980s. It gets the job done for a boot message, but nobody would build a modern GUI on top of it — which is exactly why Module 3 of this project (03_vga_driver) exists: to replace BIOS video calls with direct hardware access once you're past Real Mode.

08 — How This Connects to the Other Three Concepts

The Short Version

BIOS is the firmware rung of the bootstrapping staircase — the first thing that runs, and the thing that finds and loads the bootloader. Both are participants inside the larger event called booting. The reason this whole layered arrangement exists at all is bootstrapping.
