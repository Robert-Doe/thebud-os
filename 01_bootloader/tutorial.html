01 — The Big Analogy

Head First Moment

Imagine your computer is a hotel. When the power turns on, a sleepy security guard wakes up — that's the BIOS. He has one job: find the first disk, read the first 512 bytes off it, check that the last two bytes say 0x55AA (the universal "yep, this is bootable" stamp), and dump them into RAM at address 0x7C00. Then he goes back to sleep. Everything after that is your code's problem.

Your bootloader is that first drop of code. It runs in 16-bit Real Mode — the same mode the 8086 from 1978 used. No protection, no paging, no C runtime. Just you, the CPU registers, and BIOS interrupt calls.

Its one job: load the kernel from disk into RAM, then jump to it.

02 — What Happens at Power-On

  1. Power on. CPU resets to address 0xFFFFFFF0. The BIOS ROM is mapped there.
  2. POST. BIOS checks RAM, keyboard, disk. It prints that annoying startup screen.
  3. Boot device scan. BIOS looks for a disk whose first sector ends in 0x55 0xAA.
  4. Load MBR. BIOS reads sector 0 (512 bytes) into RAM at address 0x7C00.
  5. Jump. BIOS executes jmp 0x7C00. Your code is now running.
  6. Load kernel. Your bootloader reads the next N sectors (the kernel) into RAM at 0x1000.
  7. Jump to kernel. jmp 0x1000. Bootloader's job is done.
Why 0x7C00?

IBM PC designers in 1981 put it there so the bootloader sits at the top of the original 32KB DOS memory area, leaving low addresses free for the OS. It's pure historical accident — and every PC BIOS since 1981 has honored it.

04 — The Code, Explained

Open boot.asm. The key pieces:

BIOS disk read (INT 0x13)

mov ah, 0x02       ; BIOS "read sectors" function
mov al, 16         ; how many sectors to read (8KB of kernel)
mov ch, 0          ; cylinder 0
mov cl, 2          ; start at sector 2 (sector 1 is us)
mov dh, 0          ; head 0
mov bx, 0x1000     ; destination address in RAM
int 0x13           ; call BIOS — it DMA's the sectors for us
jc disk_error      ; CF set = error

The boot signature

times 510 - ($ - $$) db 0   ; pad to 510 bytes
dw 0xAA55                   ; boot signature at bytes 511-512
                             ; (x86 is little-endian: 0x55 then 0xAA)
Gotcha

BIOS reads 0x55 at offset 510 and 0xAA at offset 511. Because x86 is little-endian, you write the 16-bit value as 0xAA55 in NASM. Getting this backwards = the disk is not bootable. QEMU will just hang at a blank screen.

Jumping to the kernel

jmp 0x0000:0x1000  ; far jump: sets CS=0x0000, IP=0x1000
                   ; now execution continues in kernel_entry.asm

05 — The Limits of 512 Bytes

What you cannot do in 512 bytes

  • Parse a filesystem
  • Handle errors gracefully
  • Load more than one kernel file
  • Switch to Protected Mode (that's Module 2)
  • Print more than a simple string

What this bootloader does

  • Prints "BobOS Bootloader..."
  • Reads 16 raw sectors from disk
  • Drops them at 0x1000
  • Jumps there
  • Fits in exactly 512 bytes
Why not GRUB?

GRUB abstracts all of this. But if you use GRUB you never learn that your kernel is just raw bytes in RAM, that the CPU starts in 16-bit mode, or that the BIOS is the reason you can't have more than 640KB of "conventional memory." Writing your own bootloader burns these facts into your brain permanently.

06 — Run It on Windows

Prerequisites (one-time setup)

You need three tools installed:

  • NASM — Windows native installer from nasm.us. Add it to your PATH so you can run nasm from any terminal.
  • WSL 2 + Ubuntu — Run wsl --install in PowerShell as Administrator. Inside WSL: sudo apt install gcc-multilib binutils.
  • QEMU — Windows installer from qemu.weilnetz.de. Add the install folder (e.g. C:\Program Files\qemu) to your PATH.

Run Module 01 — Bootloader

Open a Command Prompt or PowerShell in the module folder:
cd C:\Users\bobcumulus\Desktop\bob_os\01_bootloader
Build the disk image (first time only — creates disk.img):
make disk.img
Build and run in QEMU:
make run
What you should see in the QEMU window:
BobOS Bootloader...
Loading kernel from disk...
[BobOS] Kernel reached — Protected Mode active!
If QEMU shows a blank screen

The boot signature is wrong or the kernel didn't load. Run make clean then make run again. If it persists, check that NASM is in your PATH: open a new terminal and type nasm --version.

07 — Brain Exercise

Sharpen Your Pencil

Question: The bootloader loads 16 sectors (8KB) of kernel. What happens if your kernel grows past 8KB? Where in boot.asm do you change the limit — and what's the hard ceiling?

Think: BIOS INT 0x13 in CHS mode has a sector count limit. What is it? (Hint: the register AL is 8 bits.)

There Are No Dumb Questions

Q: Why is the bootloader in assembly, not C?
C requires a stack, a main(), and a startup routine. None of those exist yet. The first instruction the CPU runs has to be raw machine code, so NASM is the only option. Module 2 sets up the C environment — after that, everything is C.
Q: What's "Real Mode"?
The 8086-compatible mode the CPU boots in. 16-bit registers, 20-bit addresses (max 1MB), no memory protection, no paging. The BIOS lives here. Module 2 exits Real Mode and enters 32-bit Protected Mode permanently.
Q: Could I brick my real computer doing this?
Only if you write the disk image to your real hard drive (e.g. with dd if=os.img of=/dev/sda — which we absolutely do not do). QEMU uses a file (os.img) as a virtual floppy disk. Your real disks are untouched.

Up Next: Module 02 — Kernel Entry

The bootloader jumped to 0x1000. Now the kernel's first assembly file takes over. It exits Real Mode, sets up a stack, zeroes the BSS segment, and calls kernel_main() — which is C. From Module 2 onward, you never write assembly again (almost).
