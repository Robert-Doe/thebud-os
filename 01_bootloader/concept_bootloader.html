The Bootloader: A Program, Not Firmware

The BIOS is baked into the motherboard, permanent, vendor-written. The bootloader is the exact opposite: ordinary code sitting in an ordinary disk sector — and in this project, code that you wrote yourself, line by line.

01 — The Big Analogy

Head First Moment

Think of a relay race. The BIOS is the starting gun and the very first runner — it's already standing on the track before the race even begins, because it's built into the stadium itself. The moment the gun fires, that first runner sprints exactly one leg of the race and then does something specific: hands a baton to the second runner, who was waiting at a known, fixed spot on the track. That second runner is the bootloader. Unlike the first runner, the second runner isn't part of the stadium's permanent fixtures — they're a competitor, someone who showed up and trained for this, and in this project, that someone is you.

A bootloader is a small program whose entire purpose is to locate the next stage of the boot process — a bigger bootloader, or the kernel itself — load it into memory, and transfer CPU control to it. It runs with fewer guarantees and fewer tools than almost anything else in the entire OS: no filesystem support (usually), no C runtime, no dynamic memory, often not even reliable error reporting. It exists in the gap between "firmware trusts you exist" and "the kernel has taken over."

02 — The One Sentence That Untangles Every Confusion

Memorize This Line

The BIOS is firmware that finds and runs the bootloader. The bootloader is software that finds and runs the kernel. Same shape, one level apart. Neither one is the other.

Firmware is permanent, vendor-supplied, and lives independent of any disk. A bootloader is ordinary, replaceable, disk-resident code — the same category of thing as any other program, just running under much harsher constraints (no OS beneath it yet) than a normal app ever has to. You can delete, overwrite, or completely rewrite a bootloader (that's what installing GRUB or a new Windows boot manager does); you generally cannot casually rewrite your BIOS without deliberately reflashing your motherboard's firmware.

03 — Why One Stage Usually Isn't Enough: Stage 1 vs. Stage 2

512 bytes is a brutal budget. It's enough to zero some registers, print a short message, and read a handful of disk sectors using BIOS calls — it is nowhere near enough to parse a real filesystem (FAT32, ext2, NTFS), handle a menu of OS choices, or load a multi-megabyte kernel with any sophistication. Real-world bootloaders solve this by chaining stages, each one less constrained than the last — the exact same staircase idea from concept_bootstrapping.html, applied specifically inside the bootloader itself:

StageSize budgetWhat it's capable of
Stage 1 (MBR)Exactly 512 bytes, minus the 2-byte signatureJust enough logic to read a few more raw sectors off disk and jump there. No filesystem understanding — it typically knows only "read sectors N through M."
Stage 1.5 (GRUB specifically)A handful of KB, stored in the small gap between the MBR and the first disk partitionEnough code to understand basic filesystem structures — so it can find files by name instead of hardcoded sector numbers.
Stage 2Effectively unlimited (its own file on disk)A real filesystem driver, a boot menu, configuration file parsing, the ability to load a kernel by filename rather than by raw disk position.
Where boot.asm Sits Today

Right now, boot.asm in this repo is a Stage 1 that doesn't yet load a Stage 2 or a kernel — it proves the handoff from BIOS works (prints a message, halts) but stops there. tutorial.html in this folder previews the next version, which adds an INT 0x13 disk read and a far jump to a loaded kernel — i.e., turning this Stage 1 into a real, if minimal, loader. For the exact current bytes and registers, see boot_asm_deepdive.html.

Seeing a few real examples side-by-side makes the abstract definition concrete — and shows that "bootloader" covers a much wider range of software than just the MBR sector:

Every single one of these — no matter how sophisticated — still reduces to the same one-sentence definition from §02: find the next stage, load it, hand off control. GRUB just does an enormous amount of extra convenience work around that core job; boot.asm does the bare minimum.

05 — What a Bootloader Can and Cannot Assume

Cannot assume exists yet

  • A C runtime, or C itself
  • A heap / dynamic memory allocator
  • A filesystem driver (Stage 1 only)
  • Memory protection — a bug can silently corrupt anything
  • More than 1MB of usable, simply-addressable RAM (Real Mode)

Can rely on (because BIOS proved it)

  • The CPU executing 16-bit Real Mode instructions correctly
  • BIOS interrupt services (video, disk, keyboard — see concept_bios.html)
  • Being loaded at exactly 0x7C00, every time
  • A stack, once it sets one up itself

This "cannot assume / can rely on" split is precisely why bootloader code looks so different from every other file in an OS project — it's the one place in the entire codebase deliberately written as if none of the conveniences of modern programming exist yet, because for this one file, they genuinely don't.

06 — Brain Exercise

Sharpen Your Pencil

Before reading on: if a bootloader has no filesystem understanding in Stage 1, how does it know where on disk the kernel actually sits, so it can tell BIOS which sectors to read? (Hint: think about what information could be baked in at build time, when you already know exactly how big your kernel binary is and where you're placing it on the disk image, versus what has to be figured out at run time.)

There Are No Dumb Questions

Q: If GRUB is so much more capable, why would anyone write their own bootloader like this project does?
Because GRUB hides every fact this whole concept series is trying to teach. Writing your own Stage 1 is the only way to directly experience that the CPU starts in 16-bit mode, that "the kernel" is just raw bytes with no inherent structure, and that BIOS video output is a documented interrupt call rather than magic. Once those facts are burned in, using GRUB later is a convenience, not a mystery.
Q: Is a bootloader part of the operating system, or separate from it?
Genuinely blurry, and reasonable people draw the line differently. The practical answer: it's the earliest possible OS-authored code, but it usually isn't distributed or versioned as part of "the OS" in the way the kernel is — GRUB, for instance, is its own separate project used by many different Linux distributions.
Q: Could the BIOS itself just load the kernel directly, skipping the bootloader entirely?
Only if the kernel happened to fit in 512 bytes and needed nothing beyond what BIOS interrupts provide — which no real kernel does. The bootloader exists specifically to bridge the gap between "512 bytes, BIOS calls only" and "however large and sophisticated the kernel actually needs to be."

07 — How This Connects to the Other Three Concepts

The Short Version

The bootloader is the second rung of the bootstrapping staircase — the first one written by an OS developer instead of a firmware vendor. It's loaded and launched by the BIOS. Both are stages inside the single larger event called booting.
