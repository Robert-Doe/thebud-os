01 — Why Each Register Got the Value It Got

The most useful mental model for register choices in a bootloader: every register value in boot.asm falls into exactly one of three categories. Knowing which category a line belongs to tells you whether it's negotiable, and where the rule that constrains it actually lives.

CategoryMeaningExamples in boot.asm
Hardwired by the instruction itselfThe CPU's silicon only lets this instruction address this register/segment pair. Not a convention — a physical constraint of the 8086 design.lodsb always reads from DS:SI. You cannot make it read from DS:DI — that encoding doesn't exist.
Mandated by an external contractA spec you didn't write (BIOS, the boot process, a calling convention) demands this exact register/value or it silently does the wrong thing.AH=0x0E before INT 0x10 — that's BIOS's "teletype output" function number, documented behavior of firmware you didn't author.
Your own convention, self-imposed for safetyNothing forces this specific value; you picked it because leaving it undefined is dangerous. Any consistent alternative would also work.Zeroing DS/ES/SS to 0 and setting SP=0x7C00.

Segment registers: DS, ES, SS ← 0 (self-imposed convention)

xor ax, ax
mov ds, ax      ; Data Segment = 0
mov es, ax      ; Extra Segment = 0
mov ss, ax      ; Stack Segment = 0

Nothing in the BIOS spec demands DS=ES=SS=0. Real Mode addresses are computed as segment × 16 + offset, so any consistent segment value works as long as every address you compute agrees with it. The reason to pick 0 specifically:

  • The BIOS is documented to hand off control with segment registers in an undefined state — different BIOS implementations (AMI, Award, SeaBIOS in QEMU) leave different garbage in them. If you don't set them yourself, your addressing math is only correct by accident.
  • 0x7C00 already sits exactly on a paragraph boundary that makes "flat" 0-based addressing convenient: with DS=0, the byte at linear address 0x7C00 is simply offset 0x7C00 — no mental multiplication needed anywhere else in the file.
  • xor ax, ax then broadcasting AX into three segment registers is the idiomatic way to do this because x86 forbids loading a segment register directly from an immediate value (mov ds, 0 is not a legal encoding — check the instruction table below). You must go through a general-purpose register.

SP ← 0x7C00 (self-imposed convention, but not arbitrary)

mov sp, 0x7C00

The stack on x86 grows downward — each push decrements SP before writing. Your bootloader's own code occupies bytes 0x7C00–0x7DFF. Pointing SP at the same address your code starts at is deliberate: the stack grows down into the free, unused RAM below 0x7C00, and can never collide with your code growing up from 0x7C00. Any address ≥ 0x7C00 and below your code's own instructions would technically work, but 0x7C00 exactly is the simplest value to reason about and is the value nearly every bootloader tutorial and OS in existence uses — so much so it's a de facto convention, not just a personal choice.

What happens if you skip this

Without setting SP, it holds whatever garbage the BIOS left in it — possibly 0, possibly overlapping your own code. The moment call print_string executes, the CPU pushes a 2-byte return address at [SS:SP]. If SP happens to be small or already inside your code region, that push corrupts your own instructions or wraps around and corrupts other memory. ret then reads garbage back into IP and jumps to a effectively random address. This is one of the single most common real-mode bootloader bugs, and it's exactly why line 1 of nearly every bootloader ever written sets up DS/ES/SS/SP before doing anything else.

SI ← msg_boot, AH/BH/BL — the BIOS's calling convention (external contract)

mov si, msg_boot    ; SI = pointer to our string
call print_string
...
mov ah, 0x0E        ; BIOS video function: teletype output
mov bh, 0x00        ; Page number 0
mov bl, 0x07        ; Text color (foreground/background)
RegisterWhy this one, and not another
SIlodsb is hardwired by the CPU to always read [DS:SI]. SI isn't "the string register" by convention — it's physically incapable of being any other register for that instruction. This is category 1: hardwired.
AHBIOS's INT 0x10 handler is a dispatcher: it reads AH first to decide which of ~20 different video sub-functions you're asking for. AH=0x0E specifically means "teletype output." This value comes from IBM's original BIOS documentation (1981) — it's an external contract you have no control over. Get AH wrong (say, AH=0x02, "set cursor position") and INT 0x10 does something completely different with the same AL/BH/BL values.
BHFunction 0x0E additionally reads BH as the video page number. Multiple "pages" of text video memory exist for buffering; page 0 is the one actually displayed by default. This is again BIOS's contract, not a free choice — some other function number would interpret BH completely differently (or ignore it).
BLFor 0x0E specifically, BL (foreground color) is only honored in graphics modes — in the default text mode QEMU boots into, it's ignored by real BIOS/SeaBIOS. It's set here defensively/for documentation clarity, matching the documented calling convention even though it has no visible effect in this exact context.

AL — dual-purpose, contract from two different sources

AL is loaded by lodsb (hardwired destination for that instruction) and then read by int 0x10 function 0x0E, which is documented to expect "the character to print" in AL. Two different hardwired/contractual rules both happen to converge on the same register — which is precisely why lodsb → int 0x10 is such a clean idiom for printing strings char-by-char in real mode: no register shuffling needed between the two steps.

02 — From Source Text to boot.img: The Literal Byte-by-Byte Translation

This is not a simulated example — these are the actual bytes currently sitting in boot.img in this folder, read with a hex dump. Each row shows exactly which source line produced which bytes, so you can see NASM's job with zero abstraction left in the middle.

What "assembling" actually is

NASM's job for a flat binary (-f bin) is almost embarrassingly literal: for each instruction, look up its numeric opcode in the Intel encoding tables, glue on the operand bytes, and write the raw bytes to the file in order — no headers, no symbol table, no metadata. What you see below is the entire file.

Two things worth pointing at directly, because they show [ORG 0x7C00] is not decorative:

  • The mov si, msg_boot encoding (bytes be 23 7c) hard-codes the absolute address 0x7C23. If this file were assembled with a different ORG, or loaded at a different address at runtime, this exact byte sequence would point at the wrong place in memory and the string would print garbage. NASM computed 0x7C23 at assembly time by adding the label's offset within the file (0x23) to the ORG value (0x7C00) — it has no way to know that unless you tell it via [ORG 0x7C00], which is also why that value must match where the BIOS actually loads the sector.
  • The relative jumps (e8 02 00, 74 04, eb f7) are computed relative to the next instruction's address, not the current one — a detail that's easy to get backwards by hand but that NASM handles for you from the label names. Decoding them above and confirming they land exactly on print_string, .done, and .loop is a direct proof that the assembler did its job correctly for this specific build.

The Makefile step that produced this file

boot.img: boot.asm
	nasm -f bin boot.asm -o boot.img

-f bin is the operative flag. NASM can target many output formats (elf, win32, macho, …) that wrap your code in headers a loader/linker understands. bin means "don't wrap anything — write exactly the bytes the instructions encode to, in file order, with no header." That's mandatory here: the BIOS is not a linker. It doesn't parse ELF headers or resolve symbols. It reads 512 raw bytes off disk into RAM and starts executing at byte 0. Any format other than flat binary would hand the BIOS a file it can't execute.

03 — The Core Question: How Would You Know This Works Before You've Ever Run QEMU?

This is really a question about where confidence comes from when you can't just try things and see — or more precisely, about what lets you predict the result of running something before you run it. The honest answer has three separate pieces, and conflating them is where most of the mystery comes from.

Piece 1 — the CPU's behavior is a published, decades-stable specification

Unlike an application API that might change between versions, the 8086 real-mode instruction set has been frozen since 1978 for backward compatibility — every x86 CPU made since then, including the one in your machine right now, still understands it identically. That behavior is written down, exhaustively, in Intel's and AMD's own architecture manuals (the "Intel 64 and IA-32 Architectures Software Developer's Manuals"). Every instruction in boot.asm — xor, mov, lodsb, int, cli, hlt — has a formal, unambiguous definition of exactly what registers/flags/memory it touches and how. You're not guessing what lodsb does; you're reading a spec that has had 45+ years and billions of CPUs to be wrong in and wasn't.

Piece 2 — BIOS interrupts are also a documented (if informally standardized) contract

The BIOS functions accessed via int 0x10, int 0x13, etc. aren't something you'd have to reverse-engineer. They were documented by IBM originally and have been cataloged exhaustively by the community — the canonical reference is Ralf Brown's Interrupt List, a free document listing essentially every BIOS/DOS interrupt function, what registers it reads, what it returns, and its known quirks across BIOS vendors. When you write mov ah, 0x0E before int 0x10, you're not hoping it prints a character — you're invoking a function whose behavior is specified in a document you can go read right now, the same way you'd read a library's API docs.

Piece 3 — QEMU is not a separate thing you also have to learn by trial and error

This is the piece that resolves the "but I've never used QEMU" worry directly: QEMU doesn't invent its own rules. Its entire job is to faithfully emulate the same CPU (the x86 ISA from Piece 1) and boot with the same firmware contract (SeaBIOS, an open-source BIOS implementation, for Piece 2). It is not a mysterious black box whose behavior you must discover experimentally — it is, by design, a program that implements a specification you already have independent access to. If you know what real 1981 IBM-PC-compatible hardware is documented to do, you already know what QEMU will do, because faithfully reproducing that documented behavior is QEMU's entire reason to exist. (You can even go read SeaBIOS's own source code — it's open source — for exactly what its int 0x10 handler does, byte for byte.)

What's left over — and it's real, not hand-waved away

Specs get you predicted correctness, not verified correctness. There's still exactly one thing you can only find out by running the code:

  • Whether you personally transcribed the spec correctly. Did you actually set AH before calling INT 0x10, in the right order, with no typo in the immediate value? That's a mistake in your code, not a gap in your knowledge of the spec.
  • Undocumented or vendor-specific quirks. Real BIOS vendors occasionally deviated slightly from IBM's original documented behavior — this is precisely why community-maintained references like Ralf Brown's list exist and are constantly annotated with "works on X, not on Y."
  • Whether the assembler emitted what you expected. Section 02 above is exactly this check — decoding the real output bytes and confirming they match the spec's prediction is what closes the loop.

So the actual workflow experienced OS developers use, and the one implicit in this project's structure (write code → assemble → run in QEMU → observe), is: read the spec to form a hypothesis about what should happen, then run it to confirm the hypothesis, not to discover the behavior from scratch. QEMU's role in that loop is fast, free, disposable confirmation — not a mystery box you're exploring blind. That's also exactly why QEMU is preferred over real hardware for this stage: an emulator boots in under a second and resets instantly, so the "confirm the hypothesis" step costs almost nothing, and you can afford to do it after every single change instead of batching up guesses.

There Are No Dumb Questions

Q: So if I'd never opened QEMU before writing this, was I just lucky it worked?
No — you were relying on published, stable specs (the CPU ISA and the BIOS interrupt contract) that QEMU is built to reproduce exactly. "Never used QEMU" and "don't know what the code will do" are different states. You can know the second without the first, because QEMU isn't where the ground truth lives — the ISA manual and the BIOS interrupt documentation are.
Q: What if there were no documentation at all — how would anyone have figured out INT 0x10 AH=0x0E in the first place?
Someone at IBM wrote it and specified it as part of the original PC BIOS in 1981, and it's stayed compatible ever since for the same backward-compatibility reason 0x7C00 stuck around. The very first person to write it wasn't guessing either — they were the ones defining the contract that everyone since has been reading.
Q: Does this mean assembly/bootloader code can be written "correct by construction," with no testing?
In principle, for a program this size, remarkably close — which is exactly what Section 02's byte-by-byte decode demonstrates after the fact. In practice you still test, because typos and misreadings of the spec are real, and because it's nearly free to do so. The point isn't "skip testing," it's that testing here is confirmation of a prediction, not exploration of the unknown.
