00 — Where We Left Off

The Parse Step, Zoomed In

The previous lesson drew the shell's whole loop as five boxes — prompt, read, parse, execute, repeat — and treated "parse" as a single arrow you pass through without stopping. This lesson stops there. And it deliberately does not re-explain how fork() or execve() work — you already have that from the fork/exec deep-dive, including the worked example of a shell forking a child that execs into /bin/ls. What that lesson glossed over is where args[] in execve("/bin/ls", args, environ) actually comes from. It doesn't fall out of the sky — the shell builds it, by hand, from your raw keystrokes, every single time.

01 — The Question Underneath Everything Here

Why Does exec() Want An Array, Not One String?

It would seem simpler for execve() to just accept the whole command line as one string — "ls -l /home" — and let the new program figure out the splitting itself. That's not the design UNIX chose, and the reason is architectural, not accidental: splitting the command line into separate words is exactly the part of the job that varies per-shell and per-user, so it has to happen before the kernel is ever involved, not after.

The signature you're building toward int execve(const char *path, char *const argv[], char *const envp[]); argv is an array of pointers to C strings, terminated by a NULL pointer — never one big string the program has to re-split itself.

Think about what the new program (say, ls) actually receives when its own main(int argc, char *argv[]) starts running. It gets argc — how many arguments — and argv — an array of pointers, one per argument, already separated, already individual C strings. ls never has to know or care whether you typed one space or five between ls and -l, whether you quoted anything, or what shell you were even using. All of that ambiguity was resolved before ls ever got control, by the shell, during the parse step.

💡 The Aha Moment
Passing a pre-split array instead of a raw string is a deliberate separation of concerns, same spirit as fork() and exec() being two syscalls instead of one. Word-splitting rules, quoting rules, and escaping rules are all shell policy — different shells even disagree slightly on the details. The kernel and the target program shouldn't have to know or care about any of that. By the time argv crosses the exec() boundary, all the ambiguity has already been resolved into a flat, unambiguous list of strings. The program on the receiving end just walks the array.
argv[0]

argv[1]

Notice argv[0] holds the program's own name — that's a UNIX convention, not a technical requirement of exec() itself, but nearly every program relies on it (it's how commands like busybox or symlinked binaries decide which behavior to run). And notice the array's real length is never passed as a separate count to execve() — the array is self-terminating, ending in a NULL pointer, exactly the way a C string ends in a '\0' byte. The kernel just walks pointers until it hits NULL.

02 — Step One: Splitting On Whitespace

The Simple Case: Tokenizing

At its simplest, tokenizing a command line is just "walk the string, and every time you hit a run of spaces, that's a boundary between arguments." Here's a small, real tokenizer loop — the same shape bob_os's own shell uses, and the same shape any from-scratch shell ends up writing, because there's no C standard library to lean on inside a freestanding kernel:

C — a minimal whitespace tokenizer/* Split line in place into argv[]. Returns argc.
   line is modified: spaces between tokens become '\0'. */
int tokenize(char *line, char **argv, int max) {
    int argc = 0;
    char *p = line;

    while (*p && argc < max - 1) {
        while (*p == ' ') p++;      // skip leading spaces
        if (!*p) break;               // end of line — done

        argv[argc++] = p;              // this token starts here

        while (*p && *p != ' ') p++;  // find end of token
        if (*p) *p++ = '\0';         // cut the string here, step past it
    }

    argv[argc] = NULL;                 // the array must end in NULL
    return argc;
}

The trick worth noticing: this tokenizer doesn't allocate any new memory for the individual words. It reuses the original line buffer, overwriting each separating space with a '\0' and pointing argv[i] directly into the middle of that same buffer. One buffer, sliced into pieces in place — cheap, and exactly how bob_os's own dispatch() function does it for its single command/argument split.

That's the while (*p == ' ') p++ line doing its job: it doesn't stop at the first space, it consumes all consecutive spaces before deciding a new token has started.

03 — Where Plain Tokenizing Breaks

Quoted Strings & Escape Characters

The tokenizer above has an obvious hole: what happens with echo "hello world"? A naive whitespace-splitter sees the space inside the quotes and produces three tokens — echo, "hello, and world" — when the user clearly intended two: echo and hello world. Quoting exists specifically to let a user say "treat this whole span, spaces included, as a single argument."

❌ Naive Whitespace Split

echo "hello world" → argv = ["echo", "\"hello", "world\""]

Three arguments. The quote characters are left sitting in the strings, and the phrase is split apart — exactly backwards from what the user meant.

✅ Quote-Aware Tokenizer

echo "hello world" → argv = ["echo", "hello world"]

Two arguments. The quote characters are consumed as delimiters (never copied into the token), and the space inside them is preserved as ordinary content.

Making a tokenizer quote-aware means it needs a tiny bit of state it didn't need before: "am I currently inside a quoted span?" While that flag is true, spaces stop being token boundaries — they're just characters. The quote character that opened the span is the only thing that closes it (a real shell tracks single vs. double quotes separately, since they have slightly different rules about what's still special inside them).

InputNaive split (wrong)Quote-aware split (correct)
echo "hello world"["echo", "\"hello", "world\""] — 3 tokens["echo", "hello world"] — 2 tokens
cat 'my file.txt'["cat", "'my", "file.txt'"] — 3 tokens["cat", "my file.txt"] — 2 tokens
echo a"b c"d["echo", "a\"b", "c\"d"] — 3 tokens["echo", "ab cd"] — 2 tokens (quoting can start mid-word)

Escape characters solve a related but distinct problem: what if you want a literal space, or a literal quote character, inside an argument without wrapping the whole thing in quotes? A backslash (\) conventionally means "treat the very next character as ordinary text, even if it would normally be special" — so hello\ world is one token containing a space, and say\"hi\" is one token containing literal quote characters, with the backslashes themselves consumed and never appearing in the final string.

📖 The Mental Model: A Tiny State Machine
A real tokenizer isn't really "split on spaces" plus some patches bolted on — it's better understood as a small state machine walking the line one character at a time, tracking: am I inside a token right now? and am I inside a quote right now, and if so which kind? and was the previous character a backslash that escapes this one? Every character either extends the current token, closes it, opens/closes a quoted span, or gets consumed as an escape marker. That's genuinely most of what a shell's lexer does — the rest is bookkeeping around it.
Single quotes vs. double quotes, briefly. In bash-like shells, single quotes ('...') suppress everything special inside them, including $variable expansion and backslash escapes — what you type is exactly what you get. Double quotes ("...") suppress word-splitting and most metacharacters, but still allow variable expansion and a few backslash escapes through. That distinction is a shell-specific policy choice layered on top of the same core "track whether I'm inside a quoted span" mechanism described above — worth knowing exists, not essential to a first working tokenizer.
04 — Step Two: Assembling The Array

From Tokens To A NULL-Terminated Array

Tokenizing produces a sequence of strings. Building argv is the (smaller) remaining step: allocate — or, as in the earlier snippet, reuse — a fixed-size array of char *, write a pointer to each token into successive slots, and terminate the array with a NULL pointer in the slot right after the last real token. That NULL is not optional decoration; it is the only way execve() — or your own code walking the array — knows where it ends, since C doesn't attach a length to raw pointers or arrays.

  1. Allocate storage for the pointersA fixed-size char *argv[MAX_ARGS] is enough for a shell with a reasonable argument limit — bob_os's kernel code favors exactly this static-array style, since there's no heap-happy standard library to lean on.
  2. Walk the tokenized line, filling slots in orderargv[0] gets the command name itself, argv[1] the first argument, and so on — the same order the user typed them in.
  3. Write the NULL terminatorThe slot immediately after the last token is set to NULL. Forget this step and execve() (or anything else walking the array) reads past the end into garbage memory — a classic, nasty bug.
  4. Hand it to execve() — unchangedThis exact array — pointers into the original line buffer, NULL-terminated — is what gets passed as the second argument to execve(). No further copying or reformatting needed; this is the shape the syscall wants.
🧠 Tie It Back To fork()/exec()
Recall from the deep-dive: the shell forks, the child calls execve(path, argv, environ), and if that succeeds the child's memory is wiped and replaced by the new program — which starts at main(argc, argv) with exactly the array you just built waiting for it. Everything in this lesson happens before the fork even occurs, in the parent shell process, while it still holds the raw line you typed. By the time the child execs, parsing is long finished — the array is just cargo being carried through.

05 — The Next Layer Of Complexity

Shell Metacharacters: Not Ordinary Arguments

Everything above assumes the line you typed is destined to become exactly one program's argv. Real shells support a lot more than that: ls | grep txt runs two programs and connects them; cat > out.txt redirects output to a file instead of the screen; sleep 5 & runs a command in the background; cmd1 ; cmd2 runs two commands in sequence. The characters that trigger this behavior — |, >, <, &, ; — are called metacharacters, and they are conceptually a different animal from everything discussed so far.

| — Pipeconnects
Wires one program's stdout to the next program's stdin. Turns one command line into a small pipeline of processes.
> / < — Redirectionrewires I/O
Points a program's stdout/stdin at a file instead of the terminal — set up by the shell before the program even starts.
& — Backgroundjob control
Tells the shell not to wait for this command before printing the next prompt. The subject of Lesson 3's job-control section.
; — Sequencerchains
Separates two independent commands on one line, run one after the other regardless of whether the first succeeded.

Here's the key distinction to hold onto: a quoted space stays data; a bare metacharacter changes behavior. Tokenizing and quoting (everything covered above) determine what the words are. Metacharacters determine what the shell does with those words once they're known — do they all become one program's argv, or do they get split across a pipeline, or does one become a filename for redirected output instead of an argument at all? That's a strictly higher layer of parsing, usually handled as a second pass (or a smarter single-pass parser) after — or interleaved with — the tokenizing this lesson covered.

⚠️ Why This Matters For Quoting, Specifically
This is exactly why quoting exists in the first place: if you actually want a literal pipe character or semicolon inside an argument — say, a filename genuinely called report;final.txt — you have to quote or escape it, precisely to tell the shell "no, don't treat this as a metacharacter, this is just data." Quoting isn't only about preserving spaces; it's the general mechanism for telling the parser "everything in here is literal text, not shell syntax," metacharacters included.

This lesson deliberately stops at "metacharacters exist and change what the shell does" rather than implementing pipes or redirection — that's genuinely a separate, larger mechanism (spawning multiple processes, wiring file descriptors between them) worth its own treatment. What matters here is the boundary: plain tokenizing plus quoting gets you a correct argv for one command. Recognizing metacharacters is the first step toward a shell that can run more than one command per line.

06 — Quick Reference

Glossary & Key Terms

Tokenizing
Splitting a raw line of text into individual words (tokens), typically on whitespace, as the first stage of parsing.
Token
One unit of parsed input — a single word, quoted phrase, or metacharacter — that the parser has identified as meaningful on its own.
argv
The array of C strings (char *argv[]) passed to a program's main() and to execve() — arguments already split, quote characters already stripped.
NULL Terminator (argv)
A NULL pointer placed in the slot after the last real argument, marking the end of the argv array — the array's only length indicator.
Quoting
Wrapping text in ' or " to suppress word-splitting (and, depending on the quote type, other special meaning) within that span.
Escape Character
A backslash (\) that strips special meaning from the single character immediately following it, without needing a full quoted span.
Metacharacter
A character with shell-level meaning beyond being ordinary text — |, >, <, &, ; — that changes what the shell does rather than what argument it produces.
execve()
The exec-family syscall that loads a new program into the calling process, taking a path, a NULL-terminated argv array, and a NULL-terminated environment array.
Lexer / Parser
The general terms for code that recognizes structure (tokens, quotes, metacharacters) in raw text — a shell's line-reading logic is a small, purpose-built lexer.
