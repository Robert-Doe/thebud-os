00 — Where We Left Off

Two Pieces Are Now In Place — One Gap Remains

You've got the loop (Lesson 1) and you've got the parser that turns a line into a clean argv (Lesson 2). Combine those with the fork/exec mechanics from earlier in the series, and you can already explain how a shell runs ls -l: parse the line into argv, fork, and have the child exec /bin/ls with that argv. That covers the overwhelming majority of what you type into a shell. It does not cover a small, important handful of commands that flatly cannot work that way — and it doesn't cover what happens after you launch several things and want to control which one has your attention. Both are this lesson's subject.

01 — A Command That Breaks The Pattern

Why cd Cannot Be A Separate Program

Try to implement cd the same way you'd implement ls: write a small standalone program, /bin/cd, that calls chdir() on the path you give it. Wire it into the shell exactly like any external command — fork, then exec /bin/cd some/path. Run it. It compiles, it runs, it even calls chdir() successfully. And then your shell's prompt is still sitting in the exact same directory it started in. What went wrong?

⚠️ The Root Cause: Working Directory Is Per-Process State
A process's current working directory lives in that process's own PCB — it is exactly as private to that process as its open file table or its page table. When /bin/cd runs as a forked child, it gets its own PCB, calls chdir(), and successfully updates its own working directory. Then it exits. The child's entire PCB — including that freshly changed working directory — is torn down and discarded. The parent shell's PCB was never touched. It has no idea the child even called chdir() at all.

This is the exact same wall you met studying fork(): a child process gets its own copy of the parent's state at the moment of the fork, and from then on the two are completely independent. That independence is normally a feature — it's what makes processes safe to run concurrently without stepping on each other. Here, for exactly one narrow purpose, it's the obstacle: you specifically want the change to reach back into the parent, and fork()/exec() offers no mechanism for a child to reach back and modify its parent's PCB. It structurally cannot be done that way.

▶ Watch cd fail as a forked child, then succeed as a built-in
💡 The Aha Moment
The fix isn't a cleverer syscall or a special flag — it's architectural. If the change has to land in the shell's own PCB, then the code making the change has to run inside the shell's own process, not inside a disposable child. There is no fork() involved at all: cd is implemented as an ordinary C function inside the shell's source code, called directly from the dispatch step, which calls chdir() right there in the shell's own execution context. No new process, no new PCB, no wall to cross.
02 — The Category, Generalized

What Else Has To Live Inside The Shell?

cd isn't a special exception — it's the clearest example of a whole category: any command whose entire purpose is to modify the shell's own process state must be a built-in, because that state disappears the instant a forked child (which would hold a copy of it) exits. Once you see the pattern, the rest of the list is predictable.

cdbuiltin
Changes the process's own working directory (chdir()). A child's change dies with the child.
exitbuiltin
Terminates the shell process itself. If this were a forked child, exiting would kill the child — the shell would calmly keep running, having accomplished nothing.
export / setbuiltin
Modifies the shell's own environment variables, which are (like working directory) per-process state that a child cannot push back upward.
jobs / fg / bgbuiltin
Read and manipulate the shell's own internal job table (covered below) — data that only exists inside the shell process, nowhere else.
alias / unaliasbuiltin
Edits the shell's own in-memory alias table — again, private per-process state a separate program could never reach.
source / .builtin
Runs a script's commands directly in the current shell (not a child), specifically so any cd/export/variable changes it makes stick.
CommandWhat it needs to changeWhy fork()+exec() can't do it
cdThe shell's own current working directoryLives in the shell's PCB — a child's copy is discarded on exit
exitThe shell process's own existenceA child exiting only ends the child, not the parent shell
export FOO=barThe shell's own environment variable tableEnvironment is copied to children, never merged back up
ls, cat, grep, ...Nothing about the shell itself — just does its own job and prints outputNo conflict — this is exactly what fork()+exec() is for

That last row is the important contrast: the overwhelming majority of commands you run — ls, cat, grep, python, your own compiled programs — have no need to modify the shell's private state at all. They read input, do work, produce output, and exit. For those, fork()+exec() is not just adequate, it's the better design: it isolates a buggy or crashing external program from ever being able to corrupt the shell that launched it. Built-ins are the deliberate, narrow exception, reserved for the small set of operations where isolation is precisely the thing standing in the way.

03 — Putting It In Code

One dispatch(), Two Very Different Paths

Once you know the split exists, the dispatch step from Lesson 1 gets one more branch. Instead of "match the command name, call its handler," it becomes "match the command name — if it's a built-in, call its handler directly in this process; otherwise, go find and fork+exec an external program by that name":

C — dispatch with a builtin/external splitvoid dispatch(char **argv, int argc) {
    if (argc == 0) return;

    /* Built-ins run directly, in THIS process — no fork at all. */
    if (streq(argv[0], "cd")) {
        builtin_cd(argv[1]);           // calls chdir() right here
        return;
    }
    if (streq(argv[0], "exit")) {
        builtin_exit(argv[1]);         // calls exit() right here
        return;                       // (never actually reached)
    }

    /* Everything else: fork + exec, the pattern from the deep-dive. */
    pid_t pid = fork();
    if (pid == 0) {
        execvp(argv[0], argv);      // child becomes the external program
        perror("exec failed");
        _exit(1);
    } else {
        waitpid(pid, &status, 0); // parent waits — the shell's own state, untouched
    }
}
🔑 The Rule, Stated As A Question
Before wiring up any new shell command, ask: does this need to change something about the shell process itself — its directory, its variables, its own lifetime, its own internal tables? If yes, it must be a built-in, called directly, no fork. If no — if it just wants to read input and produce output — fork()+exec() is not only sufficient, it's the safer, more isolated choice.
04 — Beyond One Command At A Time

Foreground, Background, and the Job Table

Every example so far assumed the shell forks a child and immediately blocks in waitpid() until that child finishes — a foreground command. Type a trailing &, as in sleep 30 &, and the shell does something different: it still forks the child exactly as before, but it does not block waiting for it. It prints a new prompt immediately, while the child keeps running independently in the background.

▶️ Foreground (no &)

Shell forks, then calls waitpid() and blocks. You get your prompt back only once the child exits. Only one thing has your terminal's attention at a time.

⏩ Background (trailing &)

Shell forks, does not block — prints a new prompt right away. The child keeps running "behind" the prompt, and the shell must remember it exists to report on it later.

That last sentence is the crux of job control: once the shell stops blocking on every child, it can have several children alive simultaneously, and it needs some way to keep track of them. The mechanism is unglamorous and exactly what you'd guess — a small in-memory table, private to the shell process (which is itself a small callback to the built-ins section: jobs, fg, and bg only work because this table exists inside the shell).

Shell's Internal Job Table — 3 entries
Job [1]
PID 2201 — sleep 30 &
State: Running (background)
Job [2]
PID 2214 — make -j4
State: Running (foreground — has terminal control)
Job [3]
PID 2199 — vim notes.txt
State: Stopped (suspended via Ctrl+Z)
Why This Table Exists
Enables jobs / fg / bg
Without it, the shell would have no memory of any child once it stopped blocking on it.
▶ Launch foreground vs background jobs and watch the table

With that table in place, the rest of job control is mostly bookkeeping wired to a few more built-ins: jobs prints the table, fg %1 brings a background or stopped job back to the foreground (giving it terminal control and blocking on it again), and bg %1 resumes a stopped job but leaves it running in the background. None of these are external programs, for the exact same reason cd isn't — they exist only to read and mutate data that lives inside the shell process itself.

05 — Ctrl+C, Ctrl+Z, and a Forward Pointer

Keystrokes That Become Signals

Two keystrokes deserve a mention here at the conceptual level, because they interact directly with the job table you just met: Ctrl+C and Ctrl+Z. Neither one is "sent" to a program the way ordinary typed characters are. Both are intercepted by the terminal driver and translated into a signal — a small, asynchronous notification delivered by the kernel to a process — aimed specifically at whichever process currently has foreground status.

KeystrokeSignal SentDefault Effect On The Foreground Process
Ctrl+CSIGINTInterrupt — terminates the process (unless it specifically installed a handler to catch/ignore this)
Ctrl+ZSIGTSTPTerminal stop — suspends the process, freezing it in place without killing it (this is exactly how a job ends up "Stopped" in the table above)

Notice the phrase "aimed specifically at whichever process currently has foreground status" — this is precisely why the job table matters here too. When you press Ctrl+C, it doesn't go to the shell (which is, in a sense, always running); it goes to whatever the shell most recently marked as the foreground process group — the job that's currently blocking the shell's waitpid(). A background job, humming along without terminal control, is unaffected by Ctrl+C entirely; that's part of the whole point of backgrounding it.

🧠 Why This Stays Conceptual, For Now
Signals are a genuinely deep mechanism on their own — how they're delivered, how a process installs a handler, which ones can be blocked or ignored and which (like SIGKILL) categorically cannot, what "process group" precisely means, and how a shell sets one up for a whole pipeline at once. This lesson only needs you to walk away with the shape: keystroke → terminal driver → signal → kernel delivers it to the right process. The full mechanics get their own dedicated treatment in the signals lesson later in this series — treat this section as the preview trailer, not the feature.
One more piece worth knowing exists. A "stopped" job (post Ctrl+Z) isn't running at all — it's parked by the kernel, consuming no CPU, until something resumes it. That's exactly what fg and bg do: both send a different signal, SIGCONT, to wake the stopped process back up — fg additionally reclaims foreground/terminal status for it, bg lets it keep running without that status. Same job table, same signal-delivery mechanism, just a different target state.
06 — Quick Reference

Glossary & Key Terms

Built-in Command
A command implemented as a function called directly inside the shell's own process — no fork, no exec — because it must modify the shell's own private state.
External Command
A command implemented as a separate executable, launched via fork()+exec() and waited on (or not) by the shell.
Working Directory
Per-process state (part of the PCB) recording where relative paths are resolved from — exactly why cd cannot be a forked child.
Job
A shell's bookkeeping unit for one launched command (and its PID), tracked so jobs/fg/bg can refer back to it later.
Job Table
The shell's private in-memory list of jobs it has launched, along with each one's PID and current state (running, stopped, background, foreground).
Foreground / Background
Whether the shell is currently blocked waiting on a job (foreground) or has returned to the prompt while the job keeps running independently (background, via trailing &).
Foreground Process Group
The job currently considered "in front" from the terminal's point of view — the target that keystroke-generated signals like Ctrl+C are delivered to.
Signal
A small, asynchronous kernel-delivered notification to a process, such as SIGINT or SIGTSTP — the mechanism behind Ctrl+C and Ctrl+Z. Covered in depth in a later lesson.
SIGINT / SIGTSTP / SIGCONT
Ctrl+C's interrupt signal, Ctrl+Z's stop signal, and the continue signal fg/bg use to resume a stopped job, respectively.
