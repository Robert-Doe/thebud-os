00 — Where We Pick Up

TCP Already Got You a Reliable Byte Stream

Back in the networking module, the three-way handshake (SYN → SYN-ACK → ACK) did its job: it set up a socket pair where bytes written on one end arrive, in order, uncorrupted, on the other. That's a genuinely hard problem, and TCP solves it below the level HTTP ever has to think about. If a byte gets dropped, TCP retransmits it. If two packets arrive out of order, TCP reorders them before your application ever sees them.

But here's the part TCP doesn't do for you: it has no concept of "message boundaries." A TCP socket is just a stream — an open-ended firehose of bytes with no built-in punctuation. When your code calls recv(), the kernel hands you whatever bytes happen to be sitting in the socket's receive buffer at that moment. That might be half a header line. It might be three whole HTTP requests back to back (pipelining). It might be one byte. TCP guarantees the bytes are correct and in order — it makes zero promises about how they'll be chopped up when you read them.

🔌 The Handoff, Explicitly
TCP's contract to HTTP is exactly one sentence: "here is an ordered, reliable stream of bytes — you figure out what they mean." Everything from here on — knowing you've received a full request line, knowing you've received all the headers, knowing exactly how many body bytes to expect — is HTTP's problem, solved entirely by convention encoded into the bytes themselves.

It's worth being precise about what layer this puts HTTP at. The operating system's socket API hands your application recv() and send() calls that move raw bytes — it has no idea an HTTP request is even involved. Everything this lesson covers — request lines, header syntax, body framing — is a convention that lives entirely in application-layer code sitting on top of that socket, whether that's a browser's network stack, a language's standard library, or, in bob_os, the hand-rolled parser in B15_http_parser.

01 — The Shape of a Request

HTTP/1.1 Is Just Structured Text

Strip away every framework, every fetch() call, every browser dev-tools panel, and an HTTP/1.1 request is nothing more than plain ASCII text with a strict shape, terminated by the two-byte sequence \r\n (carriage return, line feed) after every line:

  1. One request line: method, path, and HTTP version, space-separated.
  2. Zero or more header lines: Key: Value, one per line.
  3. One blank line — just \r\n by itself — marking "headers are over."
  4. An optional body, whose exact byte length is described by the headers you just read.

Here's a complete, real HTTP/1.1 request exactly as it would sit in a TCP receive buffer — this is genuinely everything the client sends, byte for byte (line breaks shown as actual newlines for readability; each one is really a \r\n):

wire formatGET /articles/tls-handshake HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) bob_os/1.0
Accept: text/html,application/xhtml+xml
Accept-Language: en-US,en;q=0.9
Connection: keep-alive
Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543
                                        ← blank line here (just \r\n) — no body follows a GET

Notice what's not there: no length prefix on the whole message, no binary framing, no magic bytes announcing "an HTTP request follows." The parser has to recognize a request line by its shape (a method token, a space, a path, a space, a version token, then \r\n) and recognize the end of headers purely by spotting that one blank line. That's the entire contract.

💡 Why \r\n and Not Just \n?
HTTP inherited its line ending from earlier text protocols like SMTP and NNTP, which in turn inherited it from teletype hardware: \r (carriage return) physically returned the print head to the start of the line, \n (line feed) advanced the paper. HTTP/1.1's spec (RFC 7230) is strict about requiring the full \r\n pair — a parser that only watches for a lone \n will work against most real traffic (since bare \n is common in practice) but is technically non-conformant, and being loose about it is exactly the kind of front-end/back-end disagreement that enables request smuggling, covered in B15.
02 — The Shape of a Response

The Response Is the Same Shape, Mirrored

The server's reply uses an identical skeleton — status line instead of request line, otherwise the same headers-then-blank-line-then-body structure. That symmetry isn't an accident; it means one parser core can handle both directions with only the first line's grammar differing.

wire formatHTTP/1.1 200 OK
Date: Tue, 21 Jul 2026 14:32:07 GMT
Server: nginx/1.25.3
Content-Type: text/html; charset=utf-8
Content-Length: 142
Connection: keep-alive
                                        ← blank line — exactly 142 bytes of body follow, then stop
<!DOCTYPE html>
<html><head><title>TLS Handshake</title></head>
<body><h1>Hello, bob_os</h1><p>This body is exactly 142 bytes.</p></body></html>

This is the single most important line in that response, for a parser's purposes: Content-Length: 142. Without it, a parser reading from a live TCP stream has no way to know whether the body is finished or whether the next recv() call will hand it 40 more bytes belonging to the same body. The status line and headers are easy — they're self-delimiting, ended by \r\n and the blank line. The body is the hard part, because bodies can contain anything, including bytes that look like \r\n\r\n.

Status line grammar, precisely: HTTP-version SP status-code SP reason-phrase CRLF. The reason phrase ("OK", "Not Found") is technically decorative — RFC 7230 says clients must parse the three-digit status code and should ignore the reason phrase's exact text, which is why sending 200 Whatever instead of 200 OK doesn't break well-written clients.
03 — The First Real Parsing Problem

Headers Don't Care About Packet Boundaries

Here's the uncomfortable truth every from-scratch HTTP parser has to confront on day one: a single call to recv() is not guaranteed to hand you a whole HTTP message — or even a whole header line. TCP segments the byte stream however the network, the OS's socket buffers, and Nagle's algorithm see fit. A slow or congested connection can easily split a 90-byte request line across two, three, or more separate reads.

Imagine the request line and first header arrive as two separate reads from the socket:

recv() call #1 returns: "GET /index.html HTTP/1.1\r\nHost: exa" (37 bytes — cut off mid-hostname)
recv() call #2 returns: "mple.com\r\nConnection: keep-alive\r\n\r\n" (37 more bytes — headers finish here)

A naive parser that tries to interpret each recv() result independently will choke on call #1 — "Host: exa" isn't a complete header line, and there's no blank line in sight yet. The only correct approach is to buffer: append every chunk of bytes the socket hands you onto a growing buffer, and only attempt to parse once (and every time) new bytes arrive, re-scanning the accumulated buffer for the patterns you're looking for.

🧩 The General Rule
Every streaming protocol parser — HTTP, WebSocket framing, even reading a line from a file — needs the same three-part loop: (1) append newly-received bytes to a buffer, (2) try to find a complete "unit" (a line, a frame, a fixed-length block) at the front of the buffer, (3) if found, consume and process it and go back to step 2; if not found, stop and wait for more bytes. Get this loop wrong and you either crash on partial input or silently drop data.
04 — Solving the Body-Length Problem, Method 1

Content-Length: Just Tell Me How Many Bytes

Once the parser has found the blank line that ends the headers, it needs to know exactly how many more bytes belong to this message's body before the next message (on a keep-alive connection) or the connection close begins. The simplest, most common answer is the Content-Length header: a plain decimal integer telling the parser precisely how many bytes of body to read, no more, no less.

  • Parser sees Content-Length: 142 → it reads exactly 142 more bytes as the body, however many recv() calls that takes.
  • Byte 143 onward, if the connection is keep-alive, is the next request/response — not part of this body, no matter what it contains.
  • If a body legitimately contains bytes that look like \r\n\r\n (a JSON blob, an image, anything binary) — it doesn't matter. The parser isn't scanning the body for patterns anymore; it's just counting bytes.
The core invariant bytes_read_so_far_in_body < Content-Length → keep buffering, message incomplete
bytes_read_so_far_in_body == Content-Length → body complete, message done
This is exactly why the server MUST know the body's length before it starts sending — Content-Length can't be computed on the fly mid-stream.
✅ Why This Is the Common Case
Whenever a server has the full response body ready in memory or on disk before it starts writing to the socket — a static file, a fully-rendered HTML page, a JSON API response — it can just measure the byte length up front and set Content-Length. This is the cheap, simple, default path, and it's what almost every response you'll ever see actually uses.
05 — Solving the Body-Length Problem, Method 2

Transfer-Encoding: chunked — When You Don't Know Yet

But what if the server doesn't know the total body length in advance — because it's streaming a live-generated response, proxying another slow upstream server, or producing output as it goes (think: a chat completion streaming token by token)? It can't set Content-Length, because it genuinely doesn't know the final number yet, and HTTP doesn't allow "figure it out as you go" with a plain length header.

The fix is Transfer-Encoding: chunked: instead of one length declared once at the top, the body is sent as a series of self-describing pieces, each prefixed by its own length in hexadecimal, followed by \r\n, followed by that many bytes of chunk data, followed by another \r\n. A chunk of size zero marks the end of the body — no total length ever needed.

wire format — chunked bodyPOST /upload HTTP/1.1
Host: api.example.com
Transfer-Encoding: chunked

7\r\n ← next chunk is 0x7 = 7 bytes
Mozilla\r\n
9\r\n ← next chunk is 0x9 = 9 bytes
Developer\r\n
7\r\n ← next chunk is 0x7 = 7 bytes
Network\r\n
0\r\n ← zero-length chunk = end of body
\r\n ← final CRLF closes the message (optional trailers go here)

Decoded, that body is just "MozillaDeveloperNetwork" — 23 bytes, delivered in three self-announced pieces without the sender ever having to know up front that the total would be 23. The parser's loop here is different from Content-Length but no harder: read a hex length line, read exactly that many data bytes plus the trailing \r\n, repeat until the length line reads 0.

⚠️ Content-Length and Chunked Must Never Both Apply
RFC 7230 is explicit: if a message somehow specifies both a Content-Length and Transfer-Encoding: chunked, Transfer-Encoding wins and Content-Length must be ignored (or the message rejected outright). A parser and a proxy in front of it that disagree on which one wins is the exact root cause of the CL.TE / TE.CL request-smuggling attacks covered in B15_http_parser — two components silently computing two different body lengths for the same bytes.
06 — Putting It Together

Building the Parser: A State Machine

A real streaming HTTP parser is a small state machine that survives being fed the buffer's contents one arbitrary chunk at a time. Here's the shape it takes, matching the actual bob_os browser module's approach:

  1. PARSE_START_LINE Scan the buffer for the first \r\n. If found, split it into method/path/version (request) or version/status/reason (response). If not found yet, stay in this state and wait for more bytes.
  2. PARSE_HEADERS Keep consuming Key: Value\r\n lines from the buffer, storing each into a headers table, until a line is found that is just \r\n by itself — the empty line signaling "headers are done."
  3. DETERMINE_BODY_LENGTH Look up Transfer-Encoding first; if it says chunked, body mode = CHUNKED. Otherwise look up Content-Length; if present, body mode = FIXED(n). If neither header is present, body mode = NONE (or "read until connection closes," for older HTTP/1.0-style responses).
  4. PARSE_BODY_FIXED or PARSE_BODY_CHUNKED Consume exactly the promised number of bytes (fixed) or repeatedly consume length-prefixed chunks until a zero-length chunk (chunked). Either way, stop consuming exactly at the boundary — never one byte more, never one byte less.
  5. DONE Message complete. Hand it off to whatever code asked for it. If the connection is keep-alive, reset back to PARSE_START_LINE and keep scanning the same buffer — there may already be a second request sitting right behind this one.
http_parser.h — real struct from B15_http_parserstruct http_request {
    char method[16];
    char path[256];
    char version[16];
    char headers[HTTP_MAX_HEADERS][2][128]; /* [n][0=name, 1=value] */
    int  header_count;
    char body[HTTP_BODY_SIZE];
    int  body_len;
    int  content_length;  /* from Content-Length header, -1 if absent */
    int  chunked;         /* 1 if Transfer-Encoding: chunked */
};
Why does this struct keep a raw int content_length and a separate chunked flag instead of one "body mode" enum? It mirrors the wire format directly, which makes the RFC 7230 precedence rule (chunked wins if both are present) a single, obvious if check at parse time rather than something baked invisibly into a constructor. Explicit fields over clever enums — easier to audit for exactly the kind of ambiguity bug that causes smuggling.

✅ When You'll See Content-Length

Static files, API responses built entirely in memory before sending, most GET responses, uploaded form bodies from a browser (the browser already knows the file size).

⚡ When You'll See Chunked

Server-sent events, LLM streaming completions, proxied responses from a backend that itself hasn't finished generating output, dynamically compressed responses where the final compressed size isn't known until compression finishes.
08 — One More Buffering Wrinkle

Keep-Alive & Pipelining: More Than One Message Per Buffer

Section 03 showed a buffer that didn't have enough bytes yet. The opposite case is just as real: a buffer that already has more than one full message sitting in it. This happens constantly, for a completely mundane reason — Connection: keep-alive means the TCP socket stays open after one request/response finishes, specifically so it can carry another one without paying for a new TCP handshake (and, over HTTPS, a whole new TLS handshake too).

If the client and server are both fast, and the network delivers several packets back to back, a single recv() call on the server can easily return two, three, or more complete requests concatenated together — especially under HTTP/1.1 pipelining, where a client is explicitly allowed to fire off several requests without waiting for earlier responses first. The parser's state machine from section 06 already handles this correctly, almost by accident: step 5 (DONE) doesn't clear the buffer and wait — it resets to PARSE_START_LINE and re-scans whatever bytes are left over.

🔁 The Loop Has to Be a Loop
A parser that treats "one recv() call" and "one HTTP message" as the same thing will silently drop the second and third requests sitting in a pipelined buffer, or worse, mis-parse them as garbage appended to the first body. The correct mental model is: the buffer is a queue of zero, one, or many complete messages, refilled by an unrelated, arbitrarily-chunked stream of recv() calls — parse in a loop until no complete message remains, then stop and wait for more bytes.

In practice, most modern clients avoid classic pipelining (it has nasty head-of-line blocking failure modes if an early response is slow) in favor of opening several parallel keep-alive connections, or — better — using HTTP/2's multiplexed binary framing, which solves this exact ordering problem structurally instead of by convention. But keep-alive itself (one connection, many sequential messages) remains the default, which is why "does my buffer definitely contain exactly one message" can never be assumed by a correct parser.

09 — What Bites Real Implementations

Parsing Hazards: Where the Bugs Actually Live

Writing a parser that works on well-formed input is the easy 80%. The remaining 20% — the part that determines whether your implementation is secure, not just functional — is deciding what to do with input that's technically ambiguous, obsolete, or actively hostile.

Header Name Casemust normalize
HTTP header names are case-insensitive by spec — content-length, Content-Length, and CONTENT-LENGTH must all resolve to the same header. A parser that does a case-sensitive lookup can be tricked into "not seeing" a header a downstream component does see — another classic smuggling-adjacent desync.
Obsolete Line Foldingmust reject
Ancient HTTP allowed a header value to continue onto the next line if that line started with whitespace. RFC 7230 formally deprecates this and requires parsers to either reject it or normalize it — a parser that silently accepts folded headers while a peer doesn't creates yet another interpretation mismatch.
Duplicate Headersrules vary by header
Most headers may legally appear more than once and should be treated as if comma-joined into one value. But a few — Content-Length chief among them — must never appear more than once with conflicting values; a strict parser rejects the whole message rather than silently picking one.
CRLF Injectionan attacker input, not a wire quirk
If application code builds a header value from unsanitized user input and that input contains a raw \r\n, an attacker can inject an entirely new header — or, worse, terminate the headers early and inject a fabricated body or even a second smuggled request. Never build header text via naive string concatenation of untrusted data.

⚠️ Every One of These Is the Same Root Cause
Header case, line folding, duplicate headers, and Transfer-Encoding obfuscation (section 05) are all instances of one underlying problem: HTTP/1.1's grammar has more than one "reasonable" way to read certain inputs. Whenever two components in a chain — browser and proxy, proxy and origin server — each pick a different reasonable interpretation of the same bytes, you get a desync, and desyncs are where request smuggling, cache poisoning, and access-control bypasses all come from. The fix is always the same: be maximally strict about what you accept, and when genuinely ambiguous, reject rather than guess.

This is also, not coincidentally, a large part of why HTTP/2 exists. HTTP/2 replaces this entire text-based, ambiguity-prone framing with a strict, binary length-prefixed frame format — every frame declares its own type and exact byte length up front, so there is no blank-line scanning, no hex chunk parsing, and structurally no room for a Content-Length/Transfer-Encoding-style disagreement within a single hop. The catch, as the request-smuggling module covers, is that most of the internet still translates HTTP/2 down to HTTP/1.1 somewhere along the way — and that translation step can reintroduce exactly the ambiguity the binary framing was designed to eliminate.

So why does this lesson focus on HTTP/1.1 at all, if HTTP/2 fixes it? Because HTTP/1.1's text framing is still the format the vast majority of origin servers, load balancers, and this project's own http_parser.c actually implement — and because understanding exactly why a text format is ambiguity-prone is what makes HTTP/2's binary framing design decisions make sense, rather than feeling like arbitrary complexity.
10 — Quick Reference

Glossary & Key Terms

Request Line
The first line of an HTTP request: method, path, and version, space-separated, terminated by \r\n.
Status Line
The first line of an HTTP response: version, three-digit status code, and reason phrase.
CRLF
The two-byte sequence \r\n that terminates every header line and, doubled, marks the end of headers.
Content-Length
A header giving the exact byte length of the message body, known and fixed before transmission begins.
Transfer-Encoding: chunked
An alternative body-framing scheme: length-prefixed chunks ending in a zero-length chunk, for bodies whose total size isn't known upfront.
Chunk
One piece of a chunked body: a hex length, \r\n, that many data bytes, then \r\n.
Streaming Parser
A parser designed to consume input incrementally across many partial reads, buffering until a complete unit is available.
Keep-Alive
A connection left open after one request/response completes so the same TCP socket can carry another message, avoiding a new handshake.
Pipelining
Sending multiple requests on one connection before reading any responses — meaning a parser's buffer may legitimately contain more than one full message at once.
Header Folding
An obsolete continuation syntax letting a header value span multiple lines via leading whitespace; deprecated by RFC 7230 and a common source of parser disagreement.
Request Smuggling
An attack exploiting two components that disagree on where one HTTP message ends and the next begins, most often via Content-Length/Transfer-Encoding ambiguity.
