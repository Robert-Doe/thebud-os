00 — Where We Pick Up

The Plaintext Problem TLS Solves

You already know what an HTTP request looks like on the wire: readable ASCII text, a request line, headers, maybe a body — including, very often, a Cookie header carrying a session token. TCP delivers those bytes reliably, but it does nothing to hide them. Anyone who can see the packets — a coffee-shop Wi-Fi neighbor, an ISP, a compromised router along the path — can simply read your session cookie straight out of the stream.

TLS (Transport Layer Security) sits between TCP and HTTP specifically to close that gap: it takes over the raw TCP byte stream immediately after the three-way handshake completes, runs its own handshake to establish trust and a shared secret, and from that point on, every byte HTTP hands it — including the request line and headers you just spent a whole lesson learning to parse — gets encrypted before it ever touches the socket. This is exactly what "HTTPS" means: HTTP, riding inside a TLS-encrypted tunnel, riding inside a TCP byte stream.

🧱 The Layering, Explicitly
TCP's three-way handshake already got you a reliable, ordered byte stream between two sockets — that part is done and TLS doesn't redo it. TLS adds a second handshake on top of that stream, and only once that finishes does your actual GET /articles/tls-handshake HTTP/1.1 request get sent — now as encrypted bytes indistinguishable from noise to anyone without the session key.
01 — The Core Design Decision

Why Asymmetric, Then Symmetric

There are two broad families of encryption, and TLS deliberately uses both, in sequence, for different jobs:

🐢 Asymmetric (Public-Key) Crypto

A key pair — public and private — where anyone can encrypt with the public key but only the private key holder can decrypt (or sign). Solves the "how do two strangers agree on a secret over a public channel" problem beautifully. But the math (modular exponentiation, elliptic curve point multiplication) is computationally expensive — orders of magnitude slower than symmetric crypto, especially at scale across millions of connections per second.

🐇 Symmetric Crypto

One shared key, known to both sides, used to both encrypt and decrypt. Algorithms like AES-GCM or ChaCha20-Poly1305 are extremely fast — hardware-accelerated on modern CPUs, capable of encrypting gigabytes per second. The catch: both sides need to already share that one secret key, which is exactly the problem asymmetric crypto is good at solving.

So TLS uses each for what it's good at: asymmetric crypto runs briefly, once, at the start of the connection — just long enough to authenticate the server and bootstrap a shared secret — and then every actual byte of your HTTP traffic is encrypted with cheap, fast symmetric crypto using a session key both sides derived from that bootstrap. You pay the expensive asymmetric cost exactly once per connection, not once per byte.

The hybrid pattern, in one line expensive asymmetric crypto → bootstraps trust + a shared secret → cheap symmetric crypto → encrypts everything else This exact pattern — slow public-key crypto used only to establish a fast shared-key channel — shows up everywhere in security engineering, not just TLS.

A TLS 1.3 cipher suite name like TLS_AES_128_GCM_SHA256 is really this whole design compressed into one identifier — it bundles together the bulk symmetric cipher and its mode, plus the hash used for key derivation and the Finished MAC. Notice what's not in the name anymore: the key-exchange algorithm. TLS 1.3 negotiates that separately (and mandates ECDHE for all of them), which is exactly why every legal TLS 1.3 cipher suite gets forward secrecy — there's no longer a suite name like TLS 1.2's TLS_RSA_WITH_AES_128_CBC_SHA that bakes a non-forward-secret key exchange into the choice at all.

Bulk CipherAES_128_GCM

💡 A Sizing Intuition
A typical HTTPS page load might exchange a few kilobytes during the handshake but megabytes of actual page content afterward. If every one of those megabytes required expensive asymmetric operations, HTTPS would be dramatically slower than plaintext HTTP. Because only the handshake pays that cost, and the bulk data uses fast symmetric encryption, HTTPS in practice is only marginally slower than plaintext HTTP once the connection is warmed up.
02 — The Handshake, Step by Step

From ClientHello to Encrypted Data

TLS 1.3 compressed what used to take TLS 1.2 two full round trips into a single round trip. Here's exactly what happens, in order:

  1. 1. ClientHello The client opens by proposing: which TLS version it supports, a list of cipher suites it's willing to use (ranked by preference), and a 32-byte client random — freshly generated, never reused. It also includes its ephemeral public key for the key exchange (a key_share extension), guessing which key-exchange group the server will accept, so the whole thing fits in one round trip.
  2. 2. ServerHello The server picks one cipher suite from the client's list, generates its own 32-byte server random, and sends back its own ephemeral public key for the same key-exchange group. From this message onward, most of the handshake is already encrypted using keys derived from what's exchanged so far.
  3. 3. Key Exchange (ECDHE) Both sides now have enough information — their own private ephemeral key, the other side's public ephemeral key — to independently compute the exact same Diffie-Hellman shared secret, without that secret ever crossing the wire. Nobody eavesdropping on the ClientHello/ServerHello exchange can compute it themselves, even though they saw both public keys.
  4. 4. Certificate + CertificateVerify The server sends its X.509 certificate chain (covered in depth in the next lesson) and a signature, made with its long-term private key, over a hash of everything exchanged so far. This is what proves "the entity that just did this key exchange is really the certificate's owner," not just some anonymous party with a matching ephemeral key.
  5. 5. Key Derivation Both sides feed the shared secret plus the two random values into a key-derivation function (HKDF) to independently compute the same set of symmetric session keys — separate keys for handshake traffic and for application traffic, in each direction. Neither side ever transmits the derived keys; both simply compute the same output from the same inputs.
  6. 6. Finished (server, then client) Each side sends a MAC (message authentication code) over the entire handshake transcript so far, proving it derived the correct keys and that nothing in the handshake was tampered with in transit. Once both Finished messages have been sent and verified, both sides trust the connection is genuinely secure and mutually authenticated (at least server-side — client certs are optional).
  7. 7. Application Data Only now does the actual HTTP request get sent — as symmetrically encrypted TLS records, using the application traffic keys derived in step 5. Everything from here on, including the full GET /articles/tls-handshake HTTP/1.1 request line and every header, is ciphertext to anyone without those keys.
Where do the two "randoms" actually get used? The client random and server random feed directly into the key derivation function alongside the shared secret. This guarantees that even if two connections somehow negotiated the exact same shared secret (extremely unlikely, but worth defending against), the derived session keys would still differ — because the randoms would differ. It's cheap insurance against key reuse.

04 — The Property Worth Understanding Deeply

Forward Secrecy: Why Ephemeral Keys Matter

Here's a question worth sitting with: what happens to all your past encrypted traffic if a server's long-term private key is ever stolen — leaked in a breach, extracted from a misconfigured backup, seized by a court order, brute-forced years later as computers get faster?

In older TLS versions using RSA key exchange, the answer was bad: the shared secret itself was encrypted directly with the server's long-term RSA public key, so anyone who later obtained the private key could decrypt every session ever recorded — including traffic captured years earlier and stored specifically for this purpose ("harvest now, decrypt later"). One leaked key, and your entire encrypted history becomes readable in retrospect.

TLS 1.3 makes this attack structurally impossible by mandating ephemeral Diffie-Hellman (ECDHE) for every handshake. The key exchange uses a fresh, temporary key pair generated just for this one connection and discarded immediately afterward — never written to disk, never reused, never derivable from the server's long-term identity key. The long-term certificate key is used only to sign the exchange (proving authenticity), never to encrypt the secret itself.

Forward secrecy, stated precisely Compromise of the server's long-term private key today ⇏ ability to decrypt session keys from yesterday Because yesterday's session key was derived from an ephemeral key pair that no longer exists anywhere — it was never written down, and there's nothing left to steal.
✅ This Is a Real, Load-Bearing Security Property
Forward secrecy isn't a theoretical nicety — it's why intelligence agencies and attackers alike have historically stockpiled encrypted internet traffic ("harvest now, decrypt later") betting on future key compromise or advances in computing (including future quantum computers breaking today's asymmetric math). Mandatory ephemeral key exchange in TLS 1.3 means that strategy fails against properly implemented connections: there is no single key whose future compromise unlocks the past.
Doesn't the server certificate's private key matter at all, then? It still matters enormously for authentication — it's what proves you're really talking to the real server right now, via the signature in CertificateVerify. Losing it lets an attacker impersonate the server going forward (until the certificate is revoked — see the next lesson). It just can't be used to retroactively decrypt sessions that already used a now-discarded ephemeral key.
05 — What Both Sides Actually Compute

Deriving the Same Keys, Independently

By the end of the key exchange, client and server each hold the same raw shared secret — computed via elliptic-curve Diffie-Hellman, without ever transmitting it. Neither side simply uses that raw secret as the encryption key, though; both feed it through a key-derivation function (HKDF, HMAC-based Key Derivation Function) alongside the handshake transcript to produce several distinct, purpose-specific keys.

tls_state.h — real struct from B16_tls_handshaketypedef enum {
    TLS_INIT, TLS_CLIENT_HELLO_SENT, TLS_SERVER_HELLO_RCVD,
    TLS_KEYS_DERIVED, TLS_CERT_RCVD, TLS_CERT_VERIFIED,
    TLS_ESTABLISHED
} tls_state_t;

typedef struct {
    tls_state_t  state;
    uint8_t      client_random[32];
    uint8_t      server_random[32];
    uint8_t      shared_secret[32];   /* from ECDH */
    uint8_t      handshake_key[32];   /* from HKDF */
    uint8_t      app_key[32];         /* session key */
    x509_cert_t *server_cert;
} tls_ctx_t;

/* tls.c — the derivation itself */
void tls_derive_keys(tls_ctx_t *ctx) {
    /* ECDH: shared_secret = client_priv * server_pub */
    x25519(ctx->shared_secret, ctx->client_private_key, ctx->server_public_key);

    /* HKDF-Extract, then HKDF-Expand, chained twice: */
    hkdf_extract(early_secret, NULL, 0, NULL, 0);
    hkdf_expand_label(derived, early_secret, "derived", NULL, 32);
    hkdf_extract(ctx->handshake_key, ctx->shared_secret, 32, derived, 32);

    /* Application traffic secret, bound to the transcript hash */
    hkdf_expand_label(ctx->app_key, ctx->handshake_key,
                      "s ap traffic", transcript_hash(), 32);
}

Two details worth noticing: first, separate keys exist for handshake traffic versus application traffic — so even the tail end of the handshake (Certificate, Finished) is encrypted, but under a different key than your actual HTTP request will be. Second, the derivation is bound to a hash of the handshake transcript itself, so if a man-in-the-middle tampered with even one byte of any earlier message, both sides would derive different keys and the connection would fail closed rather than silently succeed with mismatched trust.

06 — The Payoff

Your HTTP Request, Finally Encrypted

Once both Finished messages have been exchanged and verified, the TLS state machine reaches TLS_ESTABLISHED, and application data starts flowing. This is the exact same HTTP request from the previous lesson — the client just hands it to the TLS layer instead of writing it directly to the socket:

17 03 03 00 8a  content_type=23(app_data) legacy_ver length=0x008a
a4 3f 91 e0 22 b7 ...  AES-256-GCM ciphertext — opaque without app_key

Everything a passive eavesdropper sees from this point on is ciphertext plus a small amount of unavoidable metadata (record type, length, timing) — the method, path, headers, cookies, and body are all opaque. This is also why TLS 1.3 went further than 1.2 and started encrypting the Certificate message too: even which certificate the server presented (and therefore, on servers hosting multiple sites, which specific site you're visiting) is hidden from a passive observer, though the ClientHello's SNI extension can still leak the hostname unless Encrypted Client Hello is also in use.

⚠️ Encryption Is Not the Same as Trust
Notice that everything in this lesson establishes confidentiality — nobody can read the bytes. It does not by itself establish that you're talking to the right server; that guarantee comes entirely from the certificate signature verified in step 4, which is the subject of the next lesson. An attacker can absolutely run their own valid TLS handshake with you, encryption and all, if your browser is tricked into trusting their certificate.
07 — What Actually Changed

TLS 1.2 vs. TLS 1.3, Concretely

The seven-step handshake in section 02 is specifically TLS 1.3. TLS 1.2, which it replaced, took two full round trips before application data could flow — one to negotiate parameters, a second (effectively) to complete the RSA or Diffie-Hellman key exchange. TLS 1.3 didn't just trim a round trip; it removed an entire category of historical misconfiguration risk along with it.

💡 The Pattern: Removing Options, Not Just Adding Speed
A recurring theme in TLS 1.3's design is deleting footguns rather than merely offering a faster path alongside the old ones. Making ephemeral key exchange mandatory — not just available — is exactly why "does this server support forward secrecy" stopped being a configuration question a server operator could get wrong. When the insecure option no longer exists in the protocol, it can't be accidentally selected.
08 — The Envelope Every Message Travels In

The TLS Record Layer

Every message this lesson has discussed — ClientHello, ServerHello, Certificate, Finished, and finally Application Data — doesn't travel raw over TCP. Each one is wrapped in a small, uniform envelope called a TLS record: a one-byte content type, a two-byte legacy version field, a two-byte length, and then the payload itself (which, past the initial ClientHello/ServerHello, is ciphertext).

TLS record header — 5 bytes, every single recordstruct tls_record_header {
    uint8_t  content_type;   /* 20=change_cipher_spec 21=alert 22=handshake 23=application_data */
    uint16_t legacy_version; /* always 0x0303 in TLS 1.3, for middlebox compatibility */
    uint16_t length;         /* length of the record payload that follows, up to 16KB */
};
/* followed immediately by `length` bytes of payload */

This is exactly the same layering idea from the previous lesson, one level deeper: just as HTTP needs Content-Length to know how many body bytes to read from a TCP stream, TLS needs its own record length field to know how many ciphertext bytes make up one record, since TCP still only hands TLS an unstructured byte stream underneath. A large handshake message (a big certificate chain, for instance) can legitimately span multiple records; a TLS implementation needs the exact same buffer-and-reassemble discipline as an HTTP parser does.

Why does the "legacy_version" field stay frozen at TLS 1.2's value? Years of deployed middleboxes (firewalls, corporate proxies, old load balancers) hard-coded assumptions about what version bytes were "acceptable" and would drop or mishandle connections advertising anything newer. TLS 1.3 sidesteps this by keeping the outer record header looking like TLS 1.2, and instead signals the real negotiated version inside the (now encrypted) handshake messages — a deliberate compatibility hack, not an oversight.
09 — Skipping the Handshake Next Time

Session Resumption & 0-RTT

Running the full seven-step handshake for every single connection — even to a server you visited ten seconds ago — is wasteful. TLS 1.3 supports session resumption: after a full handshake completes, the server issues a session ticket (an encrypted blob only the server can read) that the client can present on a future connection to skip straight to a shared secret derived from the previous session, using a pre-shared key (PSK) instead of redoing the full ephemeral exchange.

Pushed further, 0-RTT lets the client send actual application data (an HTTP request!) in the very first flight, bundled with the resumption attempt, before the server has even replied — trading one more round trip for latency at the cost of a real security property.

⚠️ 0-RTT Data Is Replayable
Because 0-RTT data is sent before any fresh randomness from the server has been mixed in, an attacker who captures that first flight can resend it to the server verbatim, and the server has no built-in way to tell the replay apart from the original. For an idempotent GET, a replay is usually harmless. For a non-idempotent POST — "transfer $50," "submit this order" — a replayed request can mean the action happens twice. Servers mitigate this by only allowing 0-RTT for requests they've marked safe to replay, or by tracking single-use tickets, but the underlying risk is structural, not a bug to be patched away.

This is also precisely where forward secrecy gets slightly weaker in practice: the 0-RTT data is encrypted using a key derived from the earlier session's resumption secret, so if that secret is ever compromised, the 0-RTT bytes from that specific early data flight become decryptable — though, notably, the rest of the resumed session (everything after the server's reply) still gets fresh ephemeral keys and full forward secrecy. 0-RTT is an intentional, scoped, opt-in trade of a small amount of security for a real latency win — not a hole in TLS 1.3's design.

10 — Two Extensions Doing Quiet, Essential Work

SNI & ALPN: Riding Along in ClientHello

Two small ClientHello extensions solve problems that would otherwise be genuinely awkward, and both are worth naming explicitly since they show up in every real handshake trace you'll ever inspect.

🌐 SNI — Server Name Indication

A single IP address can host thousands of different HTTPS sites (virtual hosting). But the server has to pick which certificate to present before it knows which site the client wants — and that choice happens before any decryption is possible. SNI solves this by having the client state the target hostname in plaintext, inside ClientHello itself, so the server can select the right certificate chain before the handshake proceeds further.

🤝 ALPN — Application-Layer Protocol Negotiation

Lets the client and server agree, during the same handshake, on which application protocol will run inside the encrypted tunnel — http/1.1 or h2 (HTTP/2), for instance — without an extra round trip after TLS finishes. This is exactly how a browser knows to speak HTTP/2 framing instead of HTTP/1.1 text framing the moment application data starts flowing.
⚠️ SNI Is a Real, Acknowledged Privacy Leak
Because SNI is sent before encryption keys exist, the hostname you're connecting to is visible in plaintext to anyone observing the handshake — even though the actual HTTP request moments later is fully encrypted. This is precisely the gap Encrypted Client Hello (ECH) was designed to close, by encrypting the ClientHello's sensitive fields (including SNI) under a separate key published in DNS — but ECH adoption is still uneven across servers, CDNs, and networks, so treat plaintext SNI as the practical default for now.
11 — Quick Reference

Glossary & Key Terms

ClientHello / ServerHello
The opening messages proposing TLS version, cipher suites, random values, and ephemeral public keys.
Cipher Suite
A bundled choice of key-exchange algorithm, bulk symmetric cipher, and MAC/AEAD scheme, e.g. TLS_AES_128_GCM_SHA256.
ECDHE
Elliptic-Curve Diffie-Hellman Ephemeral — the key-exchange method that generates a fresh key pair per connection, enabling forward secrecy.
Forward Secrecy
The property that compromising a long-term key later cannot decrypt sessions recorded earlier, because those sessions used discarded ephemeral keys.
HKDF
HMAC-based Key Derivation Function — turns a raw shared secret plus context into several distinct, purpose-bound symmetric keys.
CertificateVerify
A signature, made with the server's long-term private key, proving it genuinely owns the certificate it just presented.
Finished Message
A MAC over the full handshake transcript, sent by each side, confirming both agree on every prior message and derived the correct keys.
Application Data
The TLS record type carrying actual encrypted HTTP traffic, sent only after both Finished messages are verified.
AEAD Cipher
Authenticated Encryption with Associated Data (e.g. AES-GCM) — encrypts and authenticates in one step, detecting any tampering.
TLS Record
The 5-byte-header envelope (type, legacy version, length) wrapping every TLS message before it hits the TCP stream.
Session Resumption / PSK
Skipping a fresh full handshake by presenting a pre-shared key derived from a prior session's ticket.
0-RTT
Sending application data in the very first flight of a resumed connection, before the server replies — faster, but replayable.
SNI
Server Name Indication — the plaintext hostname sent in ClientHello so the server picks the right certificate before decryption is possible.
ALPN
Application-Layer Protocol Negotiation — agreeing on HTTP/1.1 vs HTTP/2 during the same handshake, no extra round trip.
