00 — Where We Pick Up

Encryption Without Identity Is Empty

The TLS handshake lesson ended on a deliberately uncomfortable note: encryption by itself proves nothing about who you're encrypting to. An attacker running a man-in-the-middle position can complete a perfectly valid-looking ECDHE key exchange with your browser, derive a perfectly real shared secret, and read every byte of your "encrypted" HTTP request — as long as they can get your browser to accept their certificate as belonging to the site you meant to visit.

So the entire security of HTTPS ultimately rests on one question your browser has to answer correctly, every single connection: is this certificate, presented by whoever I'm talking to right now, actually the real one for this domain? Answering that without ever having met the server before, and without a human checking manually, is what the certificate chain of trust is built to do.

🔗 One Sentence Version
A TLS certificate is a signed statement — "this public key belongs to this domain" — and your browser trusts that statement not because it trusts the server, but because it trusts whoever signed the statement, transitively, all the way up to an authority it was configured to trust before you ever opened your browser.
01 — The Object Itself

A Certificate Is a Signed Binding

Strip away the X.509 formatting and a TLS certificate is conceptually simple: a data structure that binds a public key to an identity (a domain name, typically), and is digitally signed by someone vouching for that binding. Here's roughly what one contains, matching the fields real code has to check — grounded in cert_validation.h from B16_tls_handshake:

cert_validation.h — real struct from B16_tls_handshakestruct cert {
    char common_name[128];   /* e.g. "www.example.com" */
    char issuer[128];        /* who signed THIS cert */
    char san[256];           /* comma-separated Subject Alt Names */
    long not_before;         /* unix timestamp — validity start */
    long not_after;          /* unix timestamp — validity end */
    int  is_ca;              /* can this cert sign OTHER certs? */
    int  is_self_signed;     /* true only for root CAs */
};

struct cert_chain {
    struct cert certs[8];  /* [0]=leaf (the server's cert), [last]=root */
    int count;
};

The critical field, cryptographically, isn't shown as raw bytes here but is implied by issuer: every certificate also carries a signature, produced by the issuer's private key, over the rest of the certificate's contents. Anyone holding the issuer's matching public key can verify that signature — confirming "yes, whoever holds the issuer's private key really did vouch for this exact name-to-key binding, and nothing in it has been altered since."

💡 The Notary Analogy
A certificate is structurally identical to a notarized document. The document (the key-to-domain binding) means nothing on its own — its weight comes entirely from the notary's stamp and signature, and your trust in that specific notary's judgment. A certificate authority is a notary whose "stamp" is a cryptographic signature nobody can forge without its private key, and whose judgment your browser was configured, in advance, to accept.
02 — Nobody Signs Directly for the Root

The Chain of Trust, Link by Link

In principle, a single trusted authority could sign every certificate on the internet directly. In practice, that authority's private key would then be an irresistible target — steal it once, forge certificates for any domain forever. So instead, trust is delegated through intermediate links, each one a step removed from the most precious key:

Leaf Certificate1 per domain
The certificate the server actually presents during the TLS handshake. Binds a public key to example.com (and possibly other SANs). Signed by an intermediate CA. Cannot sign other certificates.
Intermediate CA Certificate1 or more
Signed the leaf certificate. Is itself a certificate, signed in turn by the root (or by another intermediate). Its private key lives in more actively-used, higher-risk infrastructure — so it's kept separate from the root precisely so it can be revoked/rotated without touching the root's trust.
Root CA Certificate~130 in a browser
Self-signed — its own issuer field points to itself. Never presented over the wire by ordinary servers. Pre-installed directly into the browser's or OS's trust store, shipped with the software itself, implicitly trusted with no signature to verify against anything higher.

The server sends its leaf certificate plus the intermediate(s) during the handshake (recall Certificate from the last lesson's step 4) — but critically, it does not send the root. The root doesn't need to be transmitted at all, because the client is expected to already have it, baked into the trust store that shipped with the browser or operating system.

The chain, formally leaf.signature verifies with intermediate.public_key
intermediate.signature verifies with root.public_key
root ∈ trust store (pre-installed, no further verification needed) Break any one link — wrong signature, untrusted root, wrong domain — and the whole chain is worthless.
03 — What the Browser Actually Checks

Walking the Chain: Three Real Checks

When your browser receives a certificate chain during the TLS handshake, it runs a specific, ordered validation — not "does this look official," but concrete, falsifiable checks against real fields:

  1. 1. Signature Chain Integrity Starting from the leaf, verify its signature against the next certificate's public key. Then verify that certificate's signature against the next one's public key. Repeat until reaching a certificate that is both self-signed and present in the local trust store — at which point the chain is anchored and no further verification is needed upward.
  2. 2. Expiry Window For every certificate in the chain, confirm the current time falls between not_before and not_after. An expired intermediate or leaf invalidates the whole chain even if every signature is mathematically perfect — expiry exists specifically to bound how long a compromised-but-undetected key can keep doing damage.
  3. 3. Hostname Match Confirm the domain you're actually trying to reach (from the URL bar, sent as SNI during ClientHello) appears in the leaf certificate's Subject Alternative Names (or legacy Common Name). A perfectly valid, perfectly signed certificate for totally-different-site.com must still be rejected if you asked for example.com — the signature proves authenticity of the binding, not that the binding matches what you wanted.
cert_validation.h — the real check, in ordercert_result_t cert_validate(const struct cert_chain *chain,
                             const char *hostname, long now) {
    /* 1. chain each signature up to a root already in the trust store */
    if (!chain_to_trusted_root(chain)) return CERT_ERR_CHAIN_BROKEN;

    /* 2. every certificate must currently be within its validity window */
    if (any_cert_expired(chain, now))  return CERT_ERR_EXPIRED;

    /* 3. the leaf's SAN/CN must actually match the hostname we asked for */
    if (!leaf_matches_hostname(chain, hostname)) return CERT_ERR_HOSTNAME;

    /* 4. optionally, check it hasn't been revoked since issuance — see §07 */
    if (is_revoked(chain))  return CERT_ERR_REVOKED;

    return CERT_OK;
}
⚠️ Skipping Any One Check Is a Full Break
Code like return CERT_OK; unconditionally — "accept any certificate" — is exactly the bug demonstrated in B16_tls_handshake's cert_validation.c insecure path. It doesn't weaken security; it eliminates it entirely. An attacker with any man-in-the-middle position presents a self-signed certificate for the target domain, the client accepts it with no complaint, and the padlock icon shows up in the address bar while every byte flows through the attacker in plaintext-equivalent form.

Why does the root need no verification at all? Because trusting it isn't a cryptographic conclusion — it's a starting assumption, installed by whoever shipped your browser or OS, based on that vendor's own audit of the CA's practices (governed by programs like the CA/Browser Forum). Every chain of trust has to bottom out somewhere in an assumption nothing else proves; roots are where HTTPS chose to put that floor.
05 — The Trust Argument, Made Explicit

Why This Actually Works as a Trust Mechanism

Here's the part worth sitting with, because it's not obvious at first: you have never met example.com's server before, and you never will directly verify its identity yourself. So how can trusting a chain of signatures possibly be safe?

The answer is that you're not trusting example.com at all, at any point in this process. You're trusting exactly one thing: the root CA's judgment, formed once, when it (or its delegated intermediate) issued that certificate — that whoever requested a certificate for example.com genuinely controlled that domain at issuance time (typically proven via domain control validation: putting a specific token in DNS, or serving a specific file at a well-known URL, something only the real domain owner could do). Every certificate you ever encounter chaining to that root is, transitively, the root vouching: "I checked this once, so you don't have to."

✅ What Actually Scales

Your browser ships with roughly 130 root CA public keys, installed once. From that finite, pre-vetted set, it can validate certificates for the entire web — billions of domains it has never seen — without ever needing a direct relationship with any of them. The trust doesn't grow linearly with the number of sites; it's bootstrapped once and reused everywhere.

⚡ What Breaks the Model

If any single trusted root (or an intermediate under it) is compromised or issues a certificate carelessly, every domain that root's chain touches is at risk — which is exactly why CA misissuance incidents (like DigiNotar in 2011, or various Symantec distrust events) result in browsers pulling roots from the trust store entirely, not just warning about individual bad certificates.
✅ The Whole Argument, Compressed
You trust the root not because you inspected it yourself, but because the people who built your browser inspected the organization behind the root and vetted its issuance practices before shipping it as a trust anchor. Everything downstream — every intermediate, every leaf, every domain you've never visited before — inherits that one upfront decision, transitively, through nothing but verifiable signatures.

This also explains why a self-signed certificate — one whose issuer field points to itself, with no chain above it at all — triggers a hard browser warning instead of a silent connection. A self-signed certificate is, structurally, a certificate with zero delegated trust behind it: nobody vetted the binding between that key and that domain except the entity presenting it, which is exactly the scenario where you can't distinguish a legitimate internal tool from an attacker who simply generated their own key pair and claimed to be your-bank.com. Self-signed certificates are genuinely fine for a private, internal network where you control distribution of the certificate out-of-band — they're dangerous precisely when used for public-facing sites, because the entire chain-of-trust argument this section just made collapses to nothing.

06 — The Part Nobody Has Fully Solved

Revocation: When a Certificate Needs to Die Early

Expiry handles the easy case: certificates are valid for a bounded window (often 90 days to a year now, deliberately shortened over time), and eventually they simply stop being accepted. But what about a certificate that needs to be invalidated immediately — because the server's private key leaked, the company was acquired, or a CA discovers it issued the certificate in error? The certificate's not_after date might still be a year away. This is revocation, and it's a genuinely hard, still-imperfect problem.

MechanismHow it worksThe real-world limitation
CRL (Certificate Revocation List)CA publishes a signed list of all revoked serial numbers; clients download and check itLists grow huge; downloading one on every connection is far too slow, so it's rarely fetched fresh
OCSP (Online Certificate Status Protocol)Client (or browser vendor, on its behalf) asks the CA in real time: "is serial #X still valid?"Adds a live round trip and a new privacy leak (the CA learns every site you visit); if the OCSP responder is down, clients historically "soft-fail" and connect anyway
OCSP StaplingServer periodically fetches its own signed OCSP response and attaches ("staples") it to the handshakeFixes the privacy leak and the round trip — but adoption is inconsistent, and it only proves the leaf wasn't revoked, not the whole chain
CRLSets / Short-Lived CertsBrowser vendors ship a compressed list of the most critical revocations directly with browser updates; or CAs issue certs valid for only daysPractical and fast, but CRLSets only cover a curated subset, not every revocation everywhere

The uncomfortable truth is that no deployed revocation mechanism gives browsers a fast, complete, privacy-preserving, always-available answer to "has this specific certificate been revoked, right now?" — every option trades off at least one of those properties. This is why the industry's actual direction has increasingly been to make the problem smaller rather than solve it perfectly: shortening certificate lifetimes (so a leaked key is only dangerous for days, not years) reduces how much damage an imperfect revocation story can cause.

⚠️ The Padlock Still Doesn't Mean "Currently Safe"
Even a fully chain-validated, non-expired, hostname-matching certificate might be a revoked one that soft-fail revocation checking simply let through. This is the same lesson as the previous module's "the padlock means encrypted, not safe" — here it sharpens to: the padlock means the chain validated at some point recently checked, which in the worst case might mean revocation wasn't checked at all.
07 — Not All Certificates Vouch for the Same Thing

Certificate Types: DV, OV, and EV

The chain-of-trust mechanism this lesson has covered proves one specific thing: whoever requested the certificate controlled the domain at issuance time. That's Domain Validation (DV) — the baseline, and by far the most common type today, often issued automatically and for free (Let's Encrypt popularized fully automated DV issuance). It says nothing about who or what organization is behind the domain.

🔍 DV — Domain Validation

Proves domain control only, via automated DNS or HTTP challenge. Fast, cheap, often free, renewed automatically. What almost every HTTPS site uses today, including this one.

🏢 OV / EV — Organization / Extended Validation

Additionally verify the legal existence and identity of the requesting organization through manual human review — business registry checks, phone verification. Slower and costlier to obtain. Browsers largely stopped giving EV certificates special UI treatment (like a green company-name bar) around 2019, after research found users rarely noticed or relied on the indicator.

A separate axis entirely is scope: a certificate can be issued for exactly one hostname, for a wildcard (*.example.com, covering any single-level subdomain), or as a multi-domain (SAN) certificate listing several unrelated hostnames in one certificate's Subject Alternative Name field. None of these change what the chain of trust actually proves — they only change how many names one signed statement covers.

🔑 The Important Takeaway
A valid, chain-verified, non-expired certificate for example.com tells your browser exactly one thing with certainty: the entity that requested it controlled that domain when it was issued. It does not, by itself, tell you the site is trustworthy, safe, or run by a legitimate business — DV certificates are issued to phishing domains constantly, precisely because domain control is all DV certificates ever claimed to verify in the first place.
08 — Restricting Who's Even Allowed to Issue

CAA Records: Telling CAs No in Advance

The chain-of-trust model has an uncomfortable implication: any of the roughly 130 trusted root CAs (through their intermediates) can, in principle, issue a valid certificate for your domain — not just the one CA you actually use. If a CA is compromised, careless, or coerced, it could mis-issue a certificate for example.com that your browser would accept exactly as readily as the legitimate one, because the chain-verification logic in section 03 has no concept of "the wrong, but still validly-signed, CA."

CAA (Certification Authority Authorization) DNS records close part of this gap. A domain owner publishes a DNS record explicitly listing which CAs are permitted to issue certificates for that domain; a compliant CA is required to check for a CAA record before issuing and refuse if the requester isn't on the list.

DNS zone file — CAA recordexample.com.  IN  CAA  0 issue "letsencrypt.org"
example.com.  IN  CAA  0 issue "digicert.com"
example.com.  IN  CAA  0 iodef "mailto:security@example.com"
🧠 Why This Doesn't Fully Close the Gap
CAA is enforced by CAs at issuance time, checked against DNS — which means it only helps if the CA actually checks it correctly, and it does nothing to stop an attacker who has compromised DNS itself (at which point they can simply remove or rewrite the CAA record before requesting a rogue certificate). It's a genuinely useful additional layer, not a replacement for the trust-store model — one more speed bump in a system that, as the revocation section showed, still has real, unresolved gaps.
09 — Closing the First-Visit Gap

HSTS: Refusing to Downgrade

Everything so far assumes the browser is already trying to use HTTPS. But a browser's very first connection attempt to a domain — before it's ever seen a certificate, ever run a handshake — often starts as plain HTTP, either because the user typed a bare domain or clicked an old http:// link. If a server always redirects HTTP to HTTPS, that first plaintext request is a real opportunity: an attacker in a man-in-the-middle position can simply intercept it and never let the redirect happen, keeping the victim on plaintext HTTP indefinitely while silently relaying to the real site — a classic SSL-stripping attack.

HSTS (HTTP Strict-Transport-Security) closes this specific gap. A server sends a response header telling the browser: "for the next N seconds, never attempt plain HTTP to this domain again — rewrite every request to HTTPS internally, before it ever leaves the machine."

wire format — HSTS response headerHTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Once a browser has seen this header once, every future navigation attempt to that domain (and its subdomains, if includeSubDomains is set) is upgraded to HTTPS internally — no network request, no redirect to intercept, nothing for an attacker sitting on the network to strip. The preload flag goes further: it lets a site submit itself to a list baked directly into browser source code, so even the very first connection ever made — before any HSTS header could have been seen — is HTTPS-only from the start.

Why can't HSTS just be the default for every domain, always? Because HSTS is opt-in per domain specifically to avoid breaking sites that genuinely don't support HTTPS yet, or support it inconsistently across subdomains. The preload list exists precisely to offer an "opt in permanently, unconditionally" path for domains willing to commit — trading flexibility for closing the first-visit gap entirely.
10 — Quick Reference

Glossary & Key Terms

X.509 Certificate
The standard data format binding a public key to an identity, signed by an issuer, with a defined validity window.
Leaf / Intermediate / Root
The three roles in a chain: the server's own certificate, the CA that signed it, and the self-signed authority pre-installed in the trust store.
Trust Store
The set of root CA certificates shipped with a browser or OS and implicitly trusted with no further verification.
Subject Alternative Name (SAN)
The field listing every hostname a certificate is valid for — the modern replacement for relying on Common Name alone.
Domain Control Validation
The process a CA uses to confirm a certificate requester actually controls the domain before issuing, e.g. via a DNS TXT record or a file at a well-known path.
Revocation
Invalidating a certificate before its natural expiry, typically after a key leak or misissuance.
OCSP
Online Certificate Status Protocol — a live query to check whether a specific certificate has been revoked.
CRL
Certificate Revocation List — a CA-signed, downloadable list of revoked certificate serial numbers.
Certificate Transparency
Public, append-only logs that every publicly trusted certificate must appear in, so misissuance can be detected and audited.
DV / OV / EV
Domain, Organization, and Extended Validation — increasing (and increasingly manual) levels of identity checking a CA performs before issuing.
Wildcard Certificate
A certificate valid for any single-level subdomain of a domain, e.g. *.example.com.
CAA Record
A DNS record listing which Certificate Authorities are authorized to issue certificates for a domain.
HSTS
Strict-Transport-Security — a header telling the browser to never attempt plain HTTP to a domain again, closing the SSL-stripping window.
SSL Stripping
A downgrade attack where a man-in-the-middle intercepts a plaintext HTTP request before it can be redirected to HTTPS.
