HTTP was born amnesiac. Every request your browser sends arrives at the server as a total stranger — no memory of the request before it, no idea you were "logged in" three seconds ago. Cookies are the eighty-byte patch that fixed this in 1994 and, thirty years later, is still the thing quietly keeping you logged into every site you use. This lesson is the mechanism, stripped to its bones: one header out, one header back, forever.

00 — The Problem Cookies Exist To Solve

HTTP Has No Memory

Here's the fact everything in this lesson hangs off: HTTP is a stateless protocol. When your browser sends a GET request for /dashboard, that request contains a method, a path, some headers, maybe a body — and nothing else. The server that receives it has no built-in concept of "this is the same visitor who logged in a moment ago." As far as the raw protocol is concerned, every single request is a brand-new stranger walking up to the counter, even if it's the 400th request from the exact same browser in the exact same minute.

This wasn't an oversight — it was a deliberate simplicity decision by HTTP's original designers. A stateless protocol is trivially easy to scale: any server can answer any request, because no server needs to "remember" you from a previous one. The trade-off is that the protocol itself gives you zero help building anything that requires continuity — a shopping cart, a logged-in session, a "you were here before" experience. All of that has to be bolted on top.

💡 Picture It Concretely
You type your password into bank.com/login. The server checks it, decides you're legitimate, and responds "200 OK, welcome." Then you click a link to bank.com/accounts. That's a brand new TCP connection carrying a brand new HTTP request — nothing about it inherently says "this is the same person who just authenticated." Without some bolted-on mechanism, the server would have to ask you to log in again on every single click, forever. That's the actual disease cookies were invented to cure.

The fix, standardized by Netscape engineer Lou Montulli in 1994, is almost embarrassingly simple: let the server hand the browser a small, opaque piece of data on one response, and have the browser automatically hand that same piece of data back on every future request to that server. The server doesn't need to remember anything about you between requests — it just needs to recognize the token it gave out earlier. State gets pushed out to the client and echoed back, request after request, turning a stateless protocol into something that behaves statefully.

01 — The Two Headers That Do Everything

Set-Cookie Out, Cookie Back

The entire cookie mechanism is exactly two HTTP headers, used in exactly two directions. Nothing about cookies requires JavaScript, a database, or any special browser feature beyond "store this string, and re-send it later when told to."

Set-Cookieserver → browser
Sent by the server, inside an HTTP response. Tells the browser: "here is a key-value pair, store it, and here are the rules for when to send it back to me."
response headercan appear multiple times
Cookiebrowser → server
Sent by the browser, inside every matching HTTP request, automatically — no page code has to ask for this to happen. Just the name=value pairs, none of the original attributes.
request headerautomatic, not opt-in

That word automatic is doing a lot of work and is worth sitting with. The page you're visiting doesn't attach the Cookie header — the browser does, on your behalf, for every outgoing request that matches a stored cookie's rules, whether that request came from you clicking a link, a page's own JavaScript calling fetch(), an image tag loading, or a hidden form auto-submitting. This design choice is exactly what makes "staying logged in" effortless — and, as the companion lesson in this cluster covers, it's also the root cause of an entire category of attack, because the browser doesn't ask the page for permission before attaching your cookies to a request that page triggered.

  1. You log in. Your browser POSTs your username and password to bank.com/login.
  2. The server authenticates you and replies with Set-Cookie. It generates a random, unguessable session identifier, stores it server-side associated with your account, and sends it back as Set-Cookie: session_id=a1b2c3....
  3. The browser stores it. Not in the page, not in JavaScript memory — in a dedicated cookie jar tied to the site's domain, outliving that one page load.
  4. Every later request re-attaches it. You click "Accounts," and the browser automatically adds Cookie: session_id=a1b2c3... to that outgoing request, with zero involvement from the page's JavaScript.
  5. The server recognizes you. It looks up a1b2c3... in its own session store, finds it belongs to you, and serves your account page — never re-checking your password.
🔑 This Is the Entire "Staying Logged In" Mechanism
There is no deeper magic behind "why am I still logged in after refreshing the page." A random session identifier goes out once in a Set-Cookie header, gets stored by the browser, and comes back in a Cookie header on every subsequent request until it expires, gets deleted, or the server invalidates it server-side. Log out, and the server typically just deletes that session ID from its store (and asks the browser to overwrite the cookie) — the old ID becomes useless even if someone still has it.

03 — Reading the Real Thing

A Real Set-Cookie Header, Attribute by Attribute

Here's an actual Set-Cookie header, the kind a real login endpoint might send. It looks like one long string, but it's really a name=value pair followed by a semicolon-separated list of rules governing when and how the browser is allowed to send that value back.

HTTP Response HeaderSet-Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543; Domain=.example.com; Path=/; Expires=Wed, 21 Aug 2026 07:28:00 GMT; Secure; HttpOnly; SameSite=Lax
session_id=8f14e45f...
The actual name=value pair — the only part the server's application code reads back later. Everything after this is instructions to the browser, not data for the server.
Domain=.example.com
Which hosts this cookie is eligible to be sent to. Covered in full in the next section — this is the widened, subdomain-including form.
Path=/
Which URL paths on that domain the cookie applies to. / means "every path" — the most common setting for a session cookie that should follow you around the whole site.
Expires=Wed, 21 Aug...
An absolute expiration date. Without Expires (or the equivalent Max-Age=<seconds>), a cookie is a session cookie — deleted when the browser fully closes, not merely on tab close.
Secure
Only ever sent over HTTPS connections. Covered attack-by-attack in the companion lesson, 02_cookie_attributes_deepdive.html.
HttpOnly
Invisible to JavaScript's document.cookie. Also covered in depth in the companion lesson.
SameSite=Lax
Controls whether this cookie is sent on cross-site requests. The modern default, and the subject of the companion lesson's CSRF walkthrough.
📌 Attributes Are Instructions to the Browser, Not to the Server
A subtlety that trips people up: when the browser sends the Cookie header back on a later request, it sends only session_id=8f14e45f... — none of Domain, Path, Expires, Secure, HttpOnly, or SameSite travel with it. Those attributes were consumed once, by the browser, at storage time, to decide the rules of the game. The server never sees them again; it only ever sees the raw name=value pairs that survived those rules for this particular request.

One response, several Set-Cookie headers

A single HTTP response is allowed to include Set-Cookie more than once — one occurrence per cookie the server wants to plant. This is actually a special case in the HTTP spec: almost every other header is supposed to be safely combinable into one comma-separated line, but Set-Cookie is explicitly exempted, because a cookie's own value can legally contain commas, which would make merging ambiguous. A real login response often looks like this:

HTTP Response HeadersSet-Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543; Path=/; Secure; HttpOnly; SameSite=Lax
Set-Cookie: csrf_token=d3b07384d113edec49eaa6238ad5ff0; Path=/; Secure; SameSite=Strict
Set-Cookie: theme=dark; Path=/; Max-Age=31536000

Three separate Set-Cookie headers, three separate cookies, each with its own independent set of attributes — a session identifier that's HttpOnly, a CSRF token that isn't (it needs to be readable so it can be embedded in a form), and a long-lived UI preference with no security attributes at all because it isn't sensitive. On the way back out, though, the browser flattens all matching stored cookies into one single Cookie header, semicolon-separated:

HTTP Request HeaderCookie: session_id=8f14e45fceea167a5a36dedd4bea2543; csrf_token=d3b07384d113edec49eaa6238ad5ff0; theme=dark
Notice what's gone. No attributes survived the trip — just three bare name=value pairs, semicolon-joined, with no indication of which cookie was HttpOnly or Secure or what its original expiration was. The request side of this protocol is deliberately minimal; all the richness lives only in the Set-Cookie headers that established each cookie in the first place.

What the browser actually does when Set-Cookie arrives

Mechanically, parsing a Set-Cookie header is a small, precise algorithm — this project's own browser module implements exactly this logic in cookie.c. The header value is split into segments on ;. The first segment, before the first =, becomes the cookie's name; everything after that = becomes its value. Every subsequent segment is checked against a fixed list of known attribute keywords (Domain, Path, Expires, Max-Age, Secure, HttpOnly, SameSite) case-insensitively; anything matching one of those sets a field on the stored cookie struct, and anything that doesn't match a known attribute is simply ignored rather than causing an error.

04 — Where a Cookie Is Actually Sent

Domain & Path Scoping

A cookie is never just "sent everywhere." Every stored cookie carries scoping rules that the browser checks on every outgoing request before deciding whether to attach it — this is what stops your bank's session cookie from accidentally riding along on a request to an unrelated site.

No explicit Domain: host-only, exact match

If a Set-Cookie header from example.com omits the Domain attribute entirely, the browser defaults to the narrowest possible scope: a host-only cookie. It will be sent on requests to example.com itself — and, notably, not to www.example.com or shop.example.com, even though those look like "the same site" to a human. Host-only means exactly the host that set it, nothing wider.

Domain=.example.com (or Domain=example.com): widened to subdomains

Add Domain=.example.com (the leading dot is a historical convention; modern browsers treat Domain=example.com without the dot identically) and the cookie's scope widens deliberately: now it's sent to example.com, and also to every subdomain — www.example.com, shop.example.com, accounts.example.com, all of it. This is exactly what a company running services split across subdomains wants for a single sign-on session; it is also, if misused, a way to accidentally hand a cookie to a subdomain the security team doesn't fully trust.

Path narrows within a domain

Path scoping works the same way but on the URL path instead of the host. A cookie set with Path=/checkout is only attached to requests whose path starts with /checkout — a request to example.com/blog won't carry it, even from the exact same browser, same domain, same everything else. In practice almost every session cookie uses Path=/ (match everything) because there's rarely a reason to fragment a login session by URL path — but the mechanism exists, and you'll see it used for things like admin-panel-only cookies scoped to /admin.

🪆 One Domain You Can Never Widen To
Browsers maintain a "public suffix list" of registrable domain boundaries (.com, .co.uk, github.io, and thousands more) specifically to block a cookie from ever being set with Domain=.com. Without this guard, any site could set a cookie scoped to the entire top-level domain, which every other .com site would then receive. This is a narrow, cookie-specific rule — full cross-site isolation between unrelated domains is the job of the Same-Origin Policy, covered in this project's origin-security material; cookies interact with that boundary but are scoped by their own domain/path rules rather than by strict origin equality (more on that distinction in Section 07).
05 — How Long a Cookie Sticks Around

Session Cookies vs. Persistent Cookies

Every cookie falls into one of two lifecycle categories, decided entirely by whether the server included an expiration.

⏳ Session Cookie

No Expires or Max-Age attribute. Lives only as long as the browser considers the "session" ongoing — historically, until you fully close the browser (not just the tab). Most login session cookies are session cookies by design: close the browser, and you'd need to log in again next time.

📅 Persistent Cookie

Has an explicit Expires=<date> or Max-Age=<seconds>. Survives browser restarts, sometimes for years — this is how "remember me" checkboxes and long-lived tracking cookies work. The browser deletes it automatically once the expiration passes, without the server needing to do anything.

Max-Age and Expires can both appear; when they conflict, most browsers prefer Max-Age since it's relative (in seconds from now) rather than dependent on the client's system clock being correct. A server can also delete a cookie early by re-sending Set-Cookie for the same name with a date in the past — this is exactly how "log out" typically clears your session cookie client-side, on top of invalidating the session server-side.

Cookies aren't the only browser storage mechanism — so why do sessions still use them? localStorage and sessionStorage can hold far more data and aren't limited to ~4KB, but neither is automatically attached to outgoing HTTP requests the way cookies are — a page has to explicitly read them and put the value somewhere (a header, a request body). For a login session that needs to travel with every server request without extra client-side code, that automatic re-attachment is exactly the feature cookies uniquely provide — the same feature that, handled carelessly, opens the door explored in the companion lesson.
06 — The Standard Behind the Header

RFC 6265 and the Limits Every Browser Enforces

Cookies shipped in Netscape's browser in 1994 as a pragmatic, undocumented hack — there was no standard describing them at all for the first two years of their existence. An early formal attempt, RFC 2965 (1997), tried to introduce a cleaner, stricter cookie model (Set-Cookie2, explicit port lists, mandatory comments) and was largely ignored by real browsers, which kept shipping the informal Netscape behavior instead. The standard that actually describes the web's real cookie behavior, RFC 6265 (2011, later revised as 6265bis), took the opposite approach: it documented what browsers were already doing rather than prescribing something new. This is a recurring pattern in web standards — the spec that wins is usually the one that describes reality, not the one that tries to fix it from a clean slate.

That same pragmatic spirit shows up in the hard limits every browser enforces on cookies — none of which are exotic, all of which matter the moment a real application starts storing anything nontrivial in a cookie.

ConstraintTypical limitWhat happens when exceeded
Single cookie size~4096 bytes (name + value + attributes)Browser silently refuses to store that Set-Cookie header at all
Cookies per domain~50–180, browser-dependentBrowser evicts the least-recently-used cookie for that domain to make room
Total request header size~8KB, server-dependentServer rejects the whole request with 400 Bad Request — every cookie is sent on every matching request, so they add up fast
⚠️ The Total-Header-Size Limit Is an Attack Surface, Not Just a Quirk
Because every stored cookie matching a request's domain and path gets concatenated into one Cookie header automatically — the exact mechanism from Section 01 — an attacker who can set cookies for your domain (via an XSS bug, or a cookie-setting endpoint on a sibling subdomain under a widened Domain) can deliberately set enough large cookies to push the total past a server's header size limit. The next legitimate request, including the one carrying the real session cookie, gets rejected outright with a 400 error before the server ever reads it — a denial-of-service against one specific user, sometimes nicknamed a "cookie bomb." It's the size-limit table above, weaponized.

The practical upshot: cookies are meant for small, opaque identifiers — a session ID, a CSRF token, a locale preference — not for storing meaningful application state. Anything larger belongs in localStorage, IndexedDB, or server-side storage keyed by the (small) cookie value.

07 — A Boundary That Isn't Quite the Same One

Cookie Scope vs. Origin

If you've studied the Same-Origin Policy, you already know browsers usually reason about isolation using an origin: the exact triple of scheme + host + port. https://example.com and http://example.com are different origins (different scheme). https://example.com and https://example.com:8443 are different origins (different port). Two scripts on different origins normally can't read each other's DOM or data at all.

Cookies, being older than the formal Same-Origin Policy, don't fully play by that rule. Cookie scoping ignores port entirely, and — as Section 04 covered — can be deliberately widened across subdomains with Domain. So a cookie set by https://example.com is, by default, also sent to https://example.com:9999 (different origin, same cookie), and can be explicitly widened to https://accounts.example.com (different origin again) via Domain=.example.com. This is a real, known mismatch between "what counts as the same site for cookies" and "what counts as the same origin for script access" — and it's precisely why security-sensitive systems shouldn't assume a cookie is only reachable from the exact origin that set it.

⚠️ Why This Mismatch Matters in Practice
If any subdomain of example.com is compromised, or run by a less-trusted team, a Domain=.example.com cookie is fully exposed to it — that subdomain can read it (if not HttpOnly) and, depending on SameSite, can trigger requests that carry it. This is a real reason large organizations sometimes deliberately avoid widening auth cookies across all subdomains, isolating sensitive sessions to a narrower host-only scope instead. The Same-Origin Policy material in this project's origin-security lessons covers the general script-isolation boundary in depth; cookies are the one major exception that predates and doesn't fully align with it.

A third vocabulary word: "site"

To make matters slightly more confusing, the SameSite attribute — covered in full in the companion lesson — introduces a third boundary that's neither "origin" nor plain "domain": a site is the scheme plus the registrable domain (roughly, the top-level-domain-plus-one, like example.com), ignoring both port and subdomain entirely. Under this definition, https://accounts.example.com and https://shop.example.com are considered same-site (same registrable domain) even though they are different origins (different host). This is a deliberate, separate classification built specifically for cookie cross-site decisions — three different boundaries, three different words, and it's worth keeping them straight: origin for script/DOM isolation, domain/path for raw cookie eligibility, site for whether a request counts as cross-site under SameSite.

08 — Tying It Together

Why This Mechanism Is Worth Knowing Cold

Once the two-header round trip and the domain/path scoping rules actually click, a long list of everyday browser behavior stops being mysterious.

🔁
You stay logged in across page loads without re-entering a password
🚪
Clearing cookies logs you out of everything at once
🏠
Logging into shop.example.com doesn't log you into unrelated.com
🧩
Single sign-on across subdomains needs a widened Domain

Next time you see "you've been logged out, please sign in again" after clearing browser data, that's just the deletion half of this mechanism — the server-side session may still technically exist, but with no Cookie header carrying its identifier, the server has no way to associate your new, memoryless request with it. And next time a login on one subdomain "just works" on another, you now know that's a deliberately widened Domain attribute at work, not some deeper session-sharing magic.

The same mechanism, aimed at a different site, is what "third-party cookies" are. Nothing about the Set-Cookie/Cookie round trip changes when the server setting the cookie is an embedded ad or analytics script's own domain rather than the site you meant to visit — it's the identical mechanism, just triggered by a request to a third party embedded inside the page you're looking at, which is exactly how cross-site ad tracking historically worked. This is a major reason recent browsers restrict or block third-party cookies by default and lean harder on SameSite=None; Secure as the explicit, auditable opt-in for the legitimate cross-site cases that remain — the same attribute from the companion lesson, doing double duty as a privacy control and not just a CSRF control.
🎯 The One-Sentence Summary
HTTP forgets everything between requests by design, so the server hands the browser a small token via Set-Cookie, the browser stores it under domain/path rules and echoes it back via Cookie on every matching future request — and that automatic echo is simultaneously the entire mechanism behind "staying logged in" and, unprotected, the root cause of the attacks the companion lesson covers.
09 — Quick Reference

Glossary & Key Terms

Stateless Protocol
A protocol where each request is handled independently, with no built-in memory of prior requests. HTTP is stateless by design.
Set-Cookie
The HTTP response header a server uses to tell the browser to store a name=value pair, plus rules governing when to send it back.
Cookie (header)
The HTTP request header the browser automatically attaches, containing only name=value pairs of every stored cookie matching the request.
Cookie Jar
The browser's internal store of all cookies, indexed by domain and path, consulted before every outgoing request.
Session Cookie
A cookie with no explicit expiration, cleared when the browser fully closes.
Persistent Cookie
A cookie with an explicit Expires or Max-Age, surviving browser restarts until that date passes.
Host-Only Cookie
A cookie with no Domain attribute — sent only to the exact host that set it, not to its subdomains.
Domain Attribute
Explicitly widens a cookie's scope to include subdomains of the given domain.
Path Attribute
Restricts a cookie to requests whose URL path starts with the given prefix.
Origin
The scheme + host + port triple used by the Same-Origin Policy — a narrower, stricter boundary than cookie domain/path scoping.
