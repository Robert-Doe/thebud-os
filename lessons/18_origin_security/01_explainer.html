The Same-Origin Policy

You have your bank open in one tab and a random blog in another. Nothing stops both pages from running JavaScript at the same time on your machine. So why can't the blog's script just reach over and read your bank balance? One rule, enforced on every single script execution, in every browser, since 1995: the Same-Origin Policy. It's not a suggestion. It's the load-bearing wall the entire web is built on top of.

01 — First, Define The Word

What "Origin" Actually Means

Every conversation about web security uses the word "origin" like everyone already agrees what it means. They don't, at first — so let's fix that before anything else. An origin is not a domain name. It's not a website. It is a precise, three-part tuple that a browser computes from a URL:

httpsscheme
://
example.comhost
:
443port

That's it. That's the whole definition. scheme + host + port. Not the path, not the query string, not the fragment — https://example.com/inbox?x=1#top and https://example.com/settings are the exact same origin, because everything after the port is irrelevant to the origin computation. The browser strips all of that away and looks only at the triple.

The Rule, In Full origin(A) == origin(B) ⇔ scheme(A) == scheme(B) AND host(A) == host(B) AND port(A) == port(B) All three. Not two out of three. A single mismatched character in any part makes them different origins.

Ports have a wrinkle worth knowing: each scheme has a default port that's implied when none is written. https:// implies :443. http:// implies :80. So https://example.com and https://example.com:443 are, in fact, the same origin — the browser fills in the default before comparing.

🔑 The Host Field Is Not "The Domain"
This is where almost everyone trips up on their first read: host means the exact hostname string, character for character. example.com and mail.example.com and api.example.com are three completely different hosts, and therefore three completely different origins — even though a human would call all three "example.com's stuff." The browser does not know, or care, that they're related. There is no concept of "the same company" or "the same parent domain" anywhere in the origin model.
02 — The Actual Threat

Why This Rule Had To Exist

Here's the default, unrestricted behavior the Same-Origin Policy exists to prevent. Without it: JavaScript loaded from any origin, running in any tab, could freely reach out and read the full contents of any other open tab — its DOM, its cookies, its localStorage — regardless of which site that other tab belongs to. Two tabs sitting side by side, unrelated to each other in every way a human would care about, would be one fetch() call away from bleeding into each other.

Play that forward for thirty seconds and you get the actual scenario this rule is stopping: you log into your bank in Tab 1. You open Tab 2 to read a recipe blog. That blog embeds a tracking script, or worse, is itself hostile. Without SOP, that script's JavaScript could quietly issue a request to your bank's domain, and — because your browser automatically attaches your bank's session cookie to any request sent to your bank's domain — get back your real, authenticated account page. Then read it. Balance, transaction history, everything, silently, in the background, while you're reading about pasta.

⚠️ The Cookie Is the Trap Door
The reason this attack works so cleanly without SOP is that cookies are attached to requests by the browser, automatically, based on the destination domain — not based on which tab or script initiated the request. Your browser doesn't ask "did the user mean to do this?" It just sees "request going to bank.com" and attaches whatever cookies it's holding for bank.com. That behavior is necessary (it's how you stay logged in while clicking around a site) — which is exactly why something else has to be the safeguard. That something is SOP, blocking the malicious script from ever reading the response that comes back.

Notice precisely what SOP protects here: not the request. The request can still go out — your browser will still send it, cookies and all (we'll come back to why that matters in the CORS lesson). What SOP guarantees is that the malicious tab's JavaScript is blind to whatever comes back. It can throw the request over the wall, but it can never see the reply.

03 — Watch The Wall Do Its Job

The Read That Never Happens

Below is the same scenario, but this time with SOP switched on — which is the actual, default state of every browser you've ever used. The malicious script still runs, still tries the same read. Watch what's different.

▶ SOP enforcement in action — click to run
What Actually Changed Request still sent → cookies still attached → server still responds normally
but: browser compares origin(caller) vs origin(response) → mismatch → response withheld from JS The network layer barely knows anything happened. This check is enforced entirely in the browser's JavaScript engine / fetch layer — the server is never even consulted.
Where exactly does the browser check this? Every API that could leak cross-origin data enforces the check independently: XMLHttpRequest and fetch() responses, document access into another origin's <iframe>, reading localStorage/sessionStorage/IndexedDB, and calling getImageData() on a canvas that drew a cross-origin image (a "tainted" canvas). Different code paths, same underlying origin comparison, same verdict.

📌 The Most Common Real-World Surprise
New developers building a site with app.example.com (frontend) and api.example.com (backend) almost always assume, at first, that JavaScript on one can freely read from the other because "they're the same company, same domain, basically the same thing." They are not the same origin, and the browser will block it by default. This exact situation — two legitimate parts of the same product, on different subdomains, needing to talk — is precisely what the next lesson (CORS) exists to solve properly.
05 — Draw The Actual Line

What Gets Blocked, What Doesn't

SOP has a surprisingly narrow, specific target: it blocks JavaScript from reading cross-origin data. It does not block cross-origin activity in general — the web would be unusable if it did, since half of every page is other origins' images, fonts, and scripts.

🚫 Blocked By Default

  • Reading the response body of a cross-origin fetch()/XHR
  • Reading document/DOM inside a cross-origin <iframe>
  • Reading another origin's localStorage/sessionStorage/cookies
  • Reading pixel data off a canvas drawn with a cross-origin image

✅ Allowed By Default

  • Embedding a cross-origin <img src="...">‍, <script src="...">‍, <link rel="stylesheet">
  • Embedding a cross-origin page in an <iframe> (you can display it, not read into it)
  • Sending a cross-origin request at all — forms, simple GET/POST — the browser does not stop the request from going out
  • Navigating the top-level page to any origin (clicking a link, location.href = ...)

That "sending is allowed, reading is blocked" split is exactly why CDNs work at all — https://cdn.example.net/jquery.js loading into your page from a totally different origin is completely normal and unblocked, because loading a script is embedding, not programmatic reading. It's also exactly why SOP alone is not a defense against Cross-Site Request Forgery (CSRF): a malicious page can still trick your browser into sending an authenticated request to your bank, it just can't read what comes back. If the attacker doesn't need to read the response — say, the mere act of the request executes a transfer — SOP offers zero protection. That's a different problem with a different fix, and it's out of scope here.

🧠 One Sentence To Keep
Same-Origin Policy is a read restriction on JavaScript, enforced by the browser, based on a strict three-part scheme+host+port comparison — it does not restrict what gets embedded on a page, and it does not restrict what requests get sent, only what a script is allowed to see come back.
06 — Sharp Edges

Edge Cases Worth Knowing

  • The "null" origin Sandboxed iframes (<iframe sandbox>) and pages loaded from data: URLs get the special origin value "null" rather than a real scheme+host+port. Some servers historically misconfigured their CORS allowlists to trust "null", thinking it meant "no origin, therefore safe" — attackers exploited this by crafting sandboxed iframes specifically to present that origin string.
  • file:// URLs get their own private origin Open two local HTML files in the same browser and, in most modern browsers, they cannot read each other's data even though they're both "file://" — each local file is typically treated as its own unique origin, precisely to stop a malicious downloaded HTML file from reading other files on your disk via script.
  • Ports matter even when people forget they exist Running a frontend on localhost:3000 and an API on localhost:8080 during local development is a textbook cross-origin situation, even though the host — "localhost" — is identical. This trips up nearly every developer the first time they build a full-stack app locally.
  • SOP predates HTTP as we know it, and it's not written into one single spec The policy was introduced by Netscape Navigator 2.0 in 1995, back when JavaScript itself was brand new and someone had to decide, on the spot, what a script should and shouldn't be allowed to touch. It's since been codified piecemeal across the Fetch spec, the HTML spec, and the Web Storage spec rather than living in one single RFC.
    • 07 — Quick Reference

    Glossary & Key Terms

    Origin
    The scheme + host + port triple computed from a URL. The unit of trust for nearly every web security decision.
    Same-Origin Policy (SOP)
    The browser-enforced default rule that JavaScript may only programmatically read data (DOM, responses, storage) belonging to its own origin.
    Scheme
    The protocol prefix of a URL — https, http, file, etc. Part 1 of the origin triple.
    Host
    The exact hostname string — not "the domain," the literal characters. a.example.com and example.com are different hosts.
    Port
    The numeric network port, explicit or implied by the scheme's default (443 for https, 80 for http). Part 3 of the origin triple.
    Cross-Origin
    Any pair of URLs whose scheme, host, or port differ in at least one respect.
    null Origin
    A special origin value assigned to sandboxed iframes and data: URLs — historically a source of CORS misconfiguration bugs.
    Tainted Canvas
    A <canvas> that has drawn a cross-origin image becomes "tainted" — its pixel data can no longer be read via getImageData(), even though the image itself displayed fine.
