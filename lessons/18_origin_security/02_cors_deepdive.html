CORS: A Deliberate Hole
In The Wall

The Same-Origin Policy locks the door by default — but plenty of legitimate web apps genuinely need app.example.com to talk to api.example.com. Someone had to build a doorbell. That's CORS: a set of response headers that let a server, not the browser, decide which other origins are allowed to read its responses. And here's the part almost everyone gets wrong at first: the request usually still fires. CORS doesn't stop the server from being asked — it stops the browser from handing the answer back to the script that asked.

01 — The Legitimate Need

Cross-Origin Requests Are Completely Normal

Lesson 18.1 covered the threat SOP defends against — but modern web architecture routinely, deliberately, splits itself across origins for perfectly good engineering reasons, and SOP's default "block everything" stance would break all of it if there were no escape hatch.

Frontend / API Splitmost common
app.example.com serves the React/Vue frontend from a CDN or static host; api.example.com runs the actual backend on entirely different infrastructure. Different origins, same product.
Third-Party APIscommon
A weather widget on your site calling api.weatherco.com directly from browser JavaScript, rather than proxying through your own backend.
Microservice Frontendsgrowing
Large products split into independently deployed sub-apps on different subdomains, each calling several shared internal APIs from the browser.
Local Dev Toolingeveryday
A frontend dev server on localhost:3000 calling a backend on localhost:8080 — technically cross-origin the instant the ports differ.

Every one of these is a case where the request is completely legitimate and expected — the server wants to serve that other origin's JavaScript. SOP has no way to know that on its own; by default it just sees "different origin" and blocks the read. CORS exists to let the server say, explicitly, in its own response: "this one's fine, let it through."

💡 Head First Moment
Think of SOP as a locked door with no doorbell — by default, nobody outside gets in, no matter who they are. CORS installs a doorbell and an intercom on that same door. The server (whoever's inside) still decides who gets buzzed in, on a visitor-by-visitor basis, by checking a name against a list. The door doesn't unlock itself; the resident does, deliberately, every time.
02 — The Core Mechanism

Who Actually Checks The Header?

This is the single most important — and most misunderstood — fact about CORS: the browser enforces it, not the server. The server's only job is to include (or not include) a response header. What happens next is entirely up to the browser reading that header.

  • 1. JavaScript on app.example.com calls fetch("https://api.example.com/data") The browser sees this is cross-origin (different host from the calling page) and flags the request for a CORS check.
  • 2. The browser sends the request — often for real, over the network For "simple" requests (defined next section), the browser does not wait for permission first. It just sends the request, with an added Origin: https://app.example.com header identifying the caller.
  • 3. api.example.com's server processes the request completely normally The server has no idea, and doesn't need to know, whether the requester is "allowed" — it just does its job and sends a response, optionally including CORS headers like Access-Control-Allow-Origin: https://app.example.com.
  • 4. The browser inspects the response headers before handing anything to JavaScript It compares the calling page's origin against whatever Access-Control-Allow-Origin says. Match → the response is handed to the calling script. No match, or header missing entirely → the response is thrown away, and the JavaScript's fetch() promise rejects with a CORS error.
    • ⚠️ The Server Already Did The Work
    Notice something uncomfortable in step 3: for a "simple" GET request, the server has already fully processed it — read a database, maybe even written to one — by the time the browser gets around to deciding whether JavaScript is allowed to see the result. CORS is not a request firewall. If a request has a side effect (like triggering an action on GET, which is bad practice but exists in the wild), that side effect already happened, headers or no headers. CORS only ever protects the read of the response, exactly like SOP.
    03 — The Easy Case

    Simple Requests

    Not every cross-origin request gets the full preflight treatment. The CORS spec carves out a category of "simple requests" — ones that look enough like what an HTML <form> could already do before fetch() even existed — and lets those go straight through with just the after-the-fact header check described above. No extra round trip.

    ConditionRequirement To Stay "Simple"
    MethodGET, HEAD, or POST only
    Content-TypeOnly application/x-www-form-urlencoded, multipart/form-data, or text/plain
    Custom headersNone — no Authorization, no custom X-* headers, nothing beyond a small browser-managed allowlist
    No ReadableStream body, no manual upload progress listenersOtherwise disqualified automatically
    → RequestGET /api/public-prices HTTP/1.1
    Hostapi.example.com
    Originhttps://app.example.com
    ← Response200 OK
    Access-Control-Allow-Originhttps://app.example.com
    Content-Typeapplication/json

    One request, one response, one header check on the way back in. The browser sent the Origin header automatically (JavaScript can't set or override this itself), the server echoed an allowlisted origin back in Access-Control-Allow-Origin, they matched, and the promise resolves with real data.

    04 — The Careful Case

    Preflighted Requests

    Anything that doesn't qualify as "simple" — a PUT or DELETE, a JSON body with Content-Type: application/json, an Authorization header carrying a bearer token — triggers a completely different flow. Before the browser sends the real request at all, it fires off a separate, automatic preflight request using the OPTIONS HTTP method, purely to ask permission.

    → PreflightOPTIONS /api/orders/42 HTTP/1.1
    Hostapi.example.com
    Originhttps://app.example.com
    Access-Control-Request-MethodDELETE
    Access-Control-Request-Headersauthorization, content-type
    ← Preflight Response204 No Content
    Access-Control-Allow-Originhttps://app.example.com
    Access-Control-Allow-MethodsGET, POST, PUT, DELETE
    Access-Control-Allow-Headersauthorization, content-type
    Access-Control-Max-Age600

    Only after the browser sees a preflight response that authorizes the exact method and exact headers it's about to use does it fire the real DELETE /api/orders/42 request. If the preflight response is missing, doesn't list DELETE in Access-Control-Allow-Methods, or doesn't list authorization in Access-Control-Allow-Headers — the real request is never sent at all. This is the one case where CORS does stop the network call itself, not just the read, because the preflight is a distinct, side-effect-free OPTIONS request that the browser controls end to end.

    🔑 Access-Control-Max-Age Exists To Avoid Doing This Twice
    Sending a full extra round trip before every single state-changing request would be slow. Access-Control-Max-Age: 600 tells the browser it can cache this exact preflight's answer (for this origin, method, and header combination) for 600 seconds, skipping the OPTIONS call entirely for follow-up requests within that window.

Because a bare GET/POST with a simple body is something a plain HTML <form> could always have sent, with or without JavaScript, since before CORS existed. Blocking it outright would have broken the entire pre-existing web. So the spec's compromise: let it fire, but withhold the response if the server didn't explicitly authorize the read.
    06 — Reference

    The CORS Header Vocabulary

    HeaderSent ByPurpose
    OriginBrowserIdentifies the calling page's origin. Automatically attached; JavaScript cannot forge or override it.
    Access-Control-Allow-OriginServerThe single origin (or literal *) whose scripts are allowed to read this response.
    Access-Control-Allow-MethodsServer (preflight response)Which HTTP methods are authorized for the real request.
    Access-Control-Allow-HeadersServer (preflight response)Which non-simple request headers are authorized.
    Access-Control-Allow-CredentialsServerMust be exactly true for the browser to expose a response to a request sent with cookies/credentials. Cannot be paired with a wildcard ACAO.
    Access-Control-Expose-HeadersServerBy default JS can only read a small safelist of response headers; this widens what fetch()'s Response.headers can see.
    Access-Control-Max-AgeServer (preflight response)How long, in seconds, the browser may cache this preflight result before re-asking.
    Access-Control-Request-MethodBrowser (preflight request)The method the real request intends to use — what's being asked for permission.
    Vary: OriginServerNot CORS-specific, but critical when ACAO reflects the request's Origin — tells shared caches/CDNs not to serve one origin's cached allowance to a different origin.
    ⚠️ A Wildcard Plus Credentials Is Explicitly Forbidden
    Access-Control-Allow-Origin: * together with Access-Control-Allow-Credentials: true is invalid by spec, and modern browsers refuse to honor it — because "any origin in the world may read this, including your logged-in cookies" is precisely the hole SOP was built to prevent. A server that wants both credentialed requests and multiple allowed origins must dynamically echo back one specific origin per request (from a real allowlist) rather than using a blanket wildcard — and must add Vary: Origin when doing so.
    📌 Worth Remembering
    CORS headers only ever relax SOP — they cannot make a page more restrictive than SOP's default. There's no header a server can send to further lock down same-origin JavaScript; that's not what this mechanism is for. CORS is purely additive permission, granted per-response, checked fresh by the browser every time.
    07 — Quick Reference

    Glossary & Key Terms

    CORS
    Cross-Origin Resource Sharing — a set of response headers that let a server opt in to letting specific other origins' JavaScript read its responses.
    Simple Request
    A cross-origin request narrow enough (GET/HEAD/POST, simple content type, no custom headers) to be sent immediately, checked only via response headers after the fact.
    Preflight
    An automatic OPTIONS request the browser sends before a non-simple cross-origin request, asking the server to explicitly authorize the method and headers about to be used.
    Access-Control-Allow-Origin (ACAO)
    The core CORS response header naming which origin's scripts may read this response.
    Access-Control-Allow-Credentials
    Must be explicitly "true" for a browser to expose a response to a script that sent the request with cookies or HTTP auth attached.
    Access-Control-Max-Age
    How long the browser may cache a given preflight's result, avoiding a repeat OPTIONS round trip.
    Vary: Origin
    A caching header servers must add when reflecting the Origin header in ACAO, so CDNs don't serve one origin's authorization to another.
    CORB
    Cross-Origin Read Blocking — a separate, automatic browser defense that blocks cross-origin HTML/JSON/XML reads from non-fetch tags (like <img> or <script>), regardless of CORS headers.
