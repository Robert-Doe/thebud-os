Faking Reliability
Over an Unreliable Wire

IP promises almost nothing: your packet might arrive, might arrive twice, might arrive after the packet you sent behind it, or might just vanish with no explanation. TCP is built entirely on top of that shaky foundation, and yet somehow gives you a connection that feels like a perfectly ordered, lossless stream of bytes. It isn't magic — it's three simple ideas (numbered bytes, acknowledgments, and retransmission) applied with total discipline. This lesson is about how that trick actually works, and about UDP, which looks at the whole trick and says "no thanks."

01 — The Foundation TCP Has to Work Around

IP Promises Almost Nothing

It's worth stating plainly, because everything else in this lesson is a reaction to it: IP is a best-effort protocol. It makes no guarantee your packet will arrive, arrive only once, or arrive in the order you sent it. Routers drop packets under congestion. Different packets between the same two machines can take different physical paths and arrive out of order. A packet can even be duplicated by a misbehaving link. IP shrugs at all of this — its job is "try to get this packet roughly where it's going," full stop.

Drop
A router queue fills up, packet discarded
Reorder
Packet 2 arrives before packet 1
Duplicate
The same packet arrives twice
Delay
Wildly variable arrival timing
⚠️ Everything Below Exists Because of This List
Every mechanism TCP has — sequence numbers, acknowledgments, retransmission timers, reordering buffers — exists solely to paper over one or more of these four failure modes. Take any one of them away and some part of TCP would become unnecessary. Understanding TCP is really just understanding "what specific trick cancels out which specific way IP can fail you."
02 — Before Any Data Moves

The Three-Way Handshake

Before a single byte of your actual data travels anywhere, TCP spends three segments just agreeing on bookkeeping. The goal: both sides need to pick a starting number — an Initial Sequence Number (ISN) — for their own outgoing byte stream, and both sides need proof the other end is actually there and listening, not just a spoofed packet.

  1. SYN — client proposes an ISNThe client picks a (effectively random) starting sequence number, say 5000, and sends a segment with the SYN flag set and seq=5000. This says: "I'd like to connect, and my byte stream starts counting from 5000."
  2. SYN-ACK — server proposes its own ISN and acknowledges the client'sThe server picks its own starting number, say 9000, and replies with both flags set: SYN (its own proposal, seq=9000) and ACK (acknowledging the client's SYN, ack=5001 — one more than the client's ISN, since a SYN itself consumes one sequence number).
  3. ACK — client acknowledges the server's ISNThe client replies once more, ACK only, ack=9001. At this point both sides have sent, and had acknowledged, a starting number. The connection is now ESTABLISHED and ordinary data segments can flow in either direction.
▶ Run the three-way handshake
💡 The Aha Moment
Why does it take three messages, not two? Because agreement has to be mutual and confirmed. After message 2 (SYN-ACK), the server has proposed its ISN but doesn't yet know the client actually received it — for all the server knows, that segment got dropped. Message 3 closes that gap: it's the client's proof, back to the server, that the server's ISN was received. Two messages would leave the server permanently unsure; three is the minimum needed for both sides to be confident the other is synchronized.
03 — The Actual Reliability Trick

Every Byte Gets a Number

Once the handshake is done, here's the entire idea that makes TCP "reliable," stripped to its essence:

TCP's reliability trick, in one sentence Number every byte → the receiver says which bytes it has → the sender resends whatever wasn't acknowledged That's it. No byte is ever "trusted" to have arrived until the other side explicitly says so, in terms of exact sequence numbers.

Concretely: TCP doesn't track "packet 1, packet 2, packet 3" — it tracks individual byte offsets within the stream, starting from the ISN agreed on in the handshake. If the client's ISN was 5000 and it sends 200 bytes, those bytes occupy sequence numbers 5000 through 5199, and the segment carrying them is labeled seq=5000, len=200. When the server has successfully received all of them, it sends back ack=5200 — meaning, precisely, "I have everything up through byte 5199; send me 5200 next."

Sender SendsMeaningReceiver RepliesMeaning
seq=5000, len=200"Here are bytes 5000–5199"ack=5200"Got everything through 5199"

seq=5400, len=200 (lost in transit)"Here are bytes 5400–5599"ack=5400 (again)"Still only have through 5399 — resend!"
🧠 ACKs Are Cumulative, Not Per-Packet
A single ack=5400 confirms every byte up to that point, not just the most recent segment — so a lost ACK isn't fatal; the next ACK that does arrive re-confirms everything anyway. This is also exactly how gaps get detected: if the receiver keeps getting new data but a chunk is missing in the middle, it keeps re-sending the same ack number (the last byte it has contiguously) until the gap is filled, which is a strong signal to the sender that something specific needs resending.
04 — When an ACK Never Comes

Retransmission: The Safety Net

Sending data and hoping an ACK shows up isn't enough by itself — what if it never does, because the original segment was dropped by an overloaded router? TCP's answer: every segment sent starts a retransmission timer. If the corresponding ACK hasn't arrived by the time that timer expires — the Retransmission Timeout (RTO) — TCP assumes the segment (or its ACK) was lost, and sends it again.

  1. Segment sent, timer startsThe sender keeps an unacknowledged copy of the data in a local buffer — it can't discard it until it's confirmed received.
  2. RTO expires with no ACKThe sender assumes loss (of either the data or the ACK — it can't tell which, and it doesn't need to) and retransmits the exact same bytes.
  3. The timer itself is adaptiveA real TCP implementation doesn't use a fixed timeout — it continuously measures round-trip time (RTT) to the peer and sets RTO a bit above the observed average, so it retransmits promptly on a fast local network and patiently on a slow, high-latency one.
🧵 Why the Sender Can't Just "Know" Data Was Lost
There is no notification from IP saying "your packet was dropped." IP is fire-and-forget in both directions — routers that discard a packet under congestion don't (reliably) tell anyone. Silence is the only signal TCP ever gets, which is exactly why a timeout, not an error message, is the mechanism. This is a direct consequence of section 01: IP promises nothing, so TCP can't even ask it what went wrong.
05 — Not Overwhelming the Other Side

Flow Control: The Receive Window

Reliability alone would let a fast sender blast data at a slow receiver faster than it can process it — filling up buffers and forcing drops that then trigger the exact retransmission machinery from section 04, wastefully. TCP avoids this with a second, independent number riding along on every ACK: the receive window (rwnd).

What the receive window actually says "Don't send more than N more bytes beyond what I've already acknowledged" The receiver advertises this number on every ACK, based on how much free space is currently left in its own receive buffer — it shrinks under load and grows back as the buffer drains.

This is purely about pace, not about correctness — it has nothing to do with lost packets. Think of it as the receiver constantly saying "here's how much more I can currently handle," and the sender respecting that ceiling no matter how fast it's technically capable of sending. If the receive window ever drops to zero — the receiver's buffer is completely full — the sender must stop entirely and wait for a later ACK announcing free space again.

Not the same thing as congestion control: flow control protects the receiver from being overwhelmed by this one sender. Congestion control (slow start, AIMD, and similar algorithms — out of scope for this lesson, and for bob_os's current module 26 syllabus) protects the network itself from being overwhelmed by all senders combined. TCP runs both limits simultaneously and always obeys whichever one is currently smaller.
06 — The Deliberate Alternative

TCP vs UDP: A Real Choice, Not a Downgrade

Every mechanism above — the handshake, sequence numbers, ACKs, retransmission, the receive window — costs something: extra round trips before data can flow, buffering on both ends, and delay while lost data is re-requested and re-delivered. UDP is what you get by deliberately deleting all of it: no handshake, no sequence numbers, no acknowledgments, no retransmission, no ordering guarantee. You hand the kernel a datagram, it does its best-effort IP send, and that's the entire contract — precisely bob_os's own module 26 transport layer today.

🐢 When TCP's Overhead Is Worth Paying

File transfers, web pages, anything where correctness matters more than latency and losing or reordering a byte would corrupt the result. You'd rather wait an extra 100ms for a retransmit than receive a broken file.

⚡ Why Applications Deliberately Choose UDP

Live voice/video calls, competitive multiplayer games, DNS lookups. A voice packet that arrives late is worse than useless — you'd rather drop it and move on than pause the whole stream waiting for a retransmit. Lower latency, and no head-of-line blocking, matter more than perfect delivery.
✅ "No Reliability" Doesn't Mean "No Reliability Ever"
Choosing UDP doesn't forbid reliability — it just moves the decision of what kind of reliability up to the application layer, where it can be made smarter than TCP's generic one-size-fits-all guarantee. A video call might resend only the most recent frame instead of every old one; a game might only care about the latest position update, where TCP's strict-ordering retransmission of a stale packet would actively make things worse. This is precisely the "application layer" box from lesson 1 of this cluster, doing real, custom work — using UDP as its foundation instead of trusting TCP's specific tradeoffs.
07 — Quick Reference

Glossary & Key Terms

Three-Way Handshake
The SYN / SYN-ACK / ACK exchange that establishes a TCP connection and lets both sides agree on initial sequence numbers.
ISN (Initial Sequence Number)
The starting byte-offset each side chooses for its own outgoing stream, proposed during the handshake.
Sequence Number
The byte offset of the first byte in a given segment, counted from that side's ISN — TCP numbers bytes, not packets.
Acknowledgment (ACK)
A cumulative confirmation of "everything up through this byte offset has been received," carried on segments flowing the other direction.
Retransmission Timeout (RTO)
How long a sender waits for an ACK before assuming loss and resending — adaptively set based on measured round-trip time.
Receive Window (rwnd)
The amount of additional data a receiver is currently willing to accept, advertised on every ACK — TCP's flow-control mechanism.
Congestion Control
A separate mechanism (not covered in depth here) that limits sending rate to protect the shared network itself, independent of any one receiver's buffer.
Head-of-Line Blocking
When one lost or delayed unit of data forces everything queued behind it to wait, even if that later data has already arrived — a TCP tradeoff UDP avoids.
Best-Effort Delivery
IP's own guarantee level: it tries to deliver a packet but makes no promise about success, order, or duplication — the problem TCP exists to solve.
