00 — Where We Left Off

The VFS Already Told You This

The VFS lesson made a specific promise: open(), read(), write(), and close() are one interface, dispatched through a vfs_ops vtable to whichever backend actually owns the underlying resource. bob_os ships two such backends today — vga_ops for the console and bobfs_ops for real files — both reachable through identical calls from user space, with the caller never needing to know which one it's actually talking to.

A socket is a third kind of backend for that same interface — one where the "file" isn't bytes on a disk, it's a live, two-way conversation with another machine. The moment you accept that framing, the rest of this lesson is really just: what does a vfs_ops-shaped wrapper around a TCP or UDP connection have to do differently, and what stays exactly the same?

/* vfs.h — the interface you already met, verbatim */
struct vfs_ops {
    int  (*open) (const char *path, int flags);
    int  (*read) (int inode, char *buf, int n, int offset);
    int  (*write)(int inode, const char *buf, int n, int offset);
    void (*close)(int inode);
};
/* A socket backend implements exactly this same shape —
 * read() blocks for incoming data, write() sends outgoing data,
 * and the fd returned behaves like any other fd in the table. */
01 — The Unix Idea, Stretched Further Than You'd Expect

"Everything Is a File" Meets the Network

Unix's founding trick was collapsing wildly different kinds of resources — disk files, terminals, printers, pipes between programs — into one interface: a small integer (the file descriptor) that you read from and write to, without caring what's actually on the other end. When Berkeley added networking to BSD Unix in the early 1980s, the team behind it made a deliberate, non-obvious design choice: rather than invent a brand-new "network handle" concept with its own set of functions, they made a socket return an ordinary file descriptor, usable with the exact same read()/write() calls as everything else.

💡 The Aha Moment
This decision is why a shell one-liner like cat file.txt > /dev/tcp/example.com/80 even makes conceptual sense, and why languages don't need a separate I/O model for "talking to a socket" versus "reading a file" — a socket fd works with the standard library's generic file-reading functions, because as far as the syscall layer is concerned, it is a file. The network didn't get a special case; it got folded into the abstraction that already existed.

This isn't just tidiness for its own sake. It means every tool built to work with "a stream of bytes from a file descriptor" — buffering, select()/poll() for waiting on multiple sources at once, redirecting a program's stdin/stdout — works on sockets for free, with zero socket-specific code required. You already got this benefit once, for pipes, back in the IPC lesson; sockets are the same trick played on a connection that happens to cross a network instead of just crossing processes.

02 — What socket() Actually Builds

Anatomy of socket()

Calling socket(domain, type, protocol) doesn't connect to anything yet — it just asks the kernel to create a new, empty communication endpoint and hand back a file descriptor for it, exactly the way open() hands back a descriptor for a freshly opened file. Under the hood, on a full POSIX kernel, this means: allocate a socket data structure (its own send/receive buffers, its own protocol state), wire up a socket_ops-style vtable specific to the requested protocol (TCP vs UDP behave differently under read()/write()), and insert an entry into the calling process's fd table — the very same table you met in the PCB lesson, sitting right alongside any open files.

03 — The Real Server-Side Sequence

socket → bind → listen → accept

A server that wants to accept incoming connections follows a fixed four-call sequence, each call narrowing what the socket is allowed to do next:

  1. socket() — create the endpointReturns a fresh fd. At this point the socket has no address and isn't listening for anything — it's just allocated.
  2. bind() — claim a local address and portTells the kernel "incoming traffic for this IP address and port number should be routed to this socket." This is the step that reserves, say, port 80 for this process and no other.
  3. listen() — announce willingness to accept connectionsSwitches the socket from "just bound" into a passive, listening state, and tells the kernel how many completed-but-not-yet-accepted connections it's allowed to queue up (the backlog) before the kernel starts refusing new ones.
  4. accept() — block until a client shows upThis call does not return until some client, somewhere, successfully completes a connection to this address and port. When it finally does return, it hands back something surprising: a brand-new file descriptor, entirely separate from the one listen() was called on.

04 — The Detail That Trips Everyone Up First

Two File Descriptors, One Program

The single most common point of confusion the first time you write a socket server: after accept() returns, you now have two separate live file descriptors for the same server process, and they do fundamentally different jobs. Mixing them up is the single most common first-timer socket bug.

👂 The Listening Socket (from listen())

Never carries any actual application data. Its only job, forever, is to sit there and produce new connected sockets every time a client shows up. You call accept() on it again and again, in a loop, for the lifetime of the server.

🔗 The Connected Socket (from accept())

Represents exactly one specific client's conversation. This is the fd you actually read() a request from and write() a response to. Once that client disconnects, this fd is done — close() it — while the listening socket keeps right on listening.
⚠️ Why It Has to Work This Way
A single server process typically wants to talk to many clients over time, sometimes concurrently. If accept() reused the same fd for every client, the server would have no way to distinguish "bytes from client A" from "bytes from client B," and could only ever have one client connected at once. A new fd per connection means each client gets its own private, independently readable/writable channel — you can hand connection fds off to separate threads or track them in a list, exactly like juggling multiple open files.
The rule to memorize listen()'s fd never carries data. accept()'s fd never accepts new clients. One produces connections; the other is a connection. A server typically holds one of the first and zero-to-many of the second, all at once, all as ordinary fds in the same table.
05 — The Other Side of the Conversation

The Client-Side Sequence: socket → connect

A client has a much shorter job — it already knows exactly who it wants to talk to, so there's no need to bind, listen, or wait for anyone:

  1. socket() — create the endpointSame call as the server side, same empty starting state.
  2. connect() — actively reach out to a specific address and portTells the kernel "attempt to establish a connection to this remote address, right now." For TCP, this is the call that kicks off the three-way handshake covered in lesson 4 of this cluster. It blocks until the connection succeeds, fails, or times out.

Once connect() returns successfully, the client uses the same fd socket() handed it — there's no separate "connected fd" dance on this side, because a client only ever has one relationship to track: itself and the one server it's talking to. read() and write() on that fd behave exactly like they would on a file from this point forward.

06 — Being Honest About Where bob_os Is Today

Where bob_os Actually Is Today

Everything above describes the general, full-POSIX shape of sockets — the design every mainstream OS converged on. bob_os's own module 26_network implements a deliberately smaller slice of it, and it's worth being precise about the gap so you know exactly what you'd be building if you extended it:

/* syscall.h — bob_os's actual socket-shaped syscalls today */
#define SYS_SOCKET        21   /* udp_bind(port) -> sock_id */
#define SYS_SENDTO        22   /* udp_send(dst_ip, ports, buf, len) */
#define SYS_RECVFROM      23   /* udp_recvfrom(sock_id, buf, &src_ip, ...) */

🔑 Why This Is a Reasonable Place to Stop, For Now
UDP has no connection state to manage — every datagram is independent, so there's genuinely no accept()-shaped concept for it to need. Starting with UDP means bob_os could get a working socket syscall surface without first building TCP's eleven-state connection machine (covered in lesson 4). Unifying socket fds into the same table as vfs_ops, and adding TCP with real listen()/accept(), is exactly the kind of extension a later module would tackle — you now know precisely what that extension needs to add.
Worth noticing: even without fd unification, bob_os's UDP socket table already mirrors the shape of a listening/connected split conceptually — udp_input() matches an incoming datagram's destination port against a table of bound sockets, the same lookup a full TCP accept() implementation performs when deciding which listening socket a new SYN belongs to.
07 — Quick Reference

Glossary & Key Terms

Socket
A communication endpoint, represented in user space as an ordinary file descriptor readable and writable like a file or pipe.
File Descriptor (fd)
A small integer, unique per process, that indexes into that process's fd table — the universal handle for files, pipes, devices, and sockets alike.
bind()
Claims a specific local address and port number for a socket, so incoming traffic addressed there gets routed to it.
listen()
Switches a bound socket into passive mode, willing to accept incoming connection attempts, with a bounded backlog queue.
accept()
Blocks until a client connects, then returns a brand-new fd representing that one connection — distinct from the listening socket's own fd.
connect()
A client-side call that actively initiates a connection to a known remote address and port.
Backlog
The maximum number of fully-established connections a listening socket may hold, waiting for accept() to be called, before the kernel refuses new ones.
vfs_ops / socket_ops
The vtable pattern that lets one generic read()/write() interface dispatch to completely different backend implementations depending on what the fd actually represents.
