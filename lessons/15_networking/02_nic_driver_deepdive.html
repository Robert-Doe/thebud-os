A packet's first few microseconds inside your machine are almost entirely a hardware story, not a software one. By the time your interrupt handler even starts running, an electrical signal has already become a frame sitting in memory the CPU can read directly — no software copied it there. This lesson is about that handoff: how a dumb piece of wire becomes bytes the kernel can act on, and why the code that reacts to "a packet is ready" is deliberately written to do almost nothing at all.

00 — Where We Left Off

The Link Layer Lives Here

Lesson 1 of this cluster told you the link layer — Ethernet, the NIC — is kernel-owned driver code, the very bottom of the network stack. This lesson zooms into exactly that layer and answers the question a diagram never can: mechanically, moment to moment, how does a signal on a wire turn into something your kernel's ip_input() function can call a pointer at?

You've already met two of the ideas this lesson leans on hardest. From the IDT/interrupts module: the CPU can be interrupted mid-instruction by a device, completely independent of anything a running program is doing. From that same module's design philosophy: an interrupt handler should do the absolute minimum necessary before returning, because the CPU can't service other interrupts efficiently while stuck inside one. We're about to see exactly why that rule exists, using a network card as the motivating example.

Grounding note: bob_os's real ne2000.c (module 26_network) currently uses polled I/O — the scheduler calls net_poll() every timer tick and it asks the card "anything new?" — specifically so the module can be understood without interrupts and DMA in the picture yet. Everything below describes the general, production-grade pattern (what Linux, Windows, and every real NIC driver actually do) that ne2000.c would grow into if it were extended with interrupt support.
01 — Before Software Gets Involved

The Wire → The NIC's Own Memory

An Ethernet frame arrives as a sequence of electrical (or optical, or radio) transitions. The NIC's physical layer circuitry decodes that signal, checks a frame check sequence (a CRC) to make sure it wasn't corrupted in transit, and — critically — does all of this without any CPU involvement whatsoever. Your processor could be busy compiling a kernel, deep in a tight loop, or halted in the idle task; none of that matters. The NIC is an independent piece of hardware with its own clock, and it assembles the frame into its own on-board buffer memory entirely on its own.

On the NE2000 specifically, that on-board memory is a 16 KB SRAM chip living on the card itself, split into a small transmit region and a much larger receive ring. The CPU cannot address this memory the way it addresses RAM — there's no pointer you can dereference to read it. That's the whole reason the next step exists at all.

📌 Why the NIC Even Has Its Own Memory
Frames can arrive faster than the CPU can be interrupted to process them, especially under load. A small on-card buffer acts as shock absorption — the NIC keeps accepting frames from the wire even if the kernel is momentarily busy, up to the buffer's capacity. Without it, a slow interrupt response would mean dropped frames on every burst of traffic, not just under extreme load.
02 — Getting the Frame Into RAM

DMA: No CPU Copy Required

So the frame is sitting in the NIC's own memory. The kernel needs it in its memory — a buffer the CPU can actually read with ordinary load instructions, and that ip_input() can eventually be handed a pointer to. On any modern NIC (PCI, PCIe — anything built in roughly the last 25 years), this transfer is done by Direct Memory Access (DMA): the NIC itself, not the CPU, drives a transfer straight into a pre-arranged region of RAM.

The whole point of DMA, in one line NIC hardware writes the frame directly into RAM — the CPU is not involved in moving a single byte The kernel's only job beforehand is to tell the NIC where its receive buffers live in physical memory. After that, transfers happen without the CPU copying anything.

Concretely, this works through a descriptor ring: the driver allocates a fixed number of fixed-size buffers in kernel memory ahead of time, and hands the NIC a small array of descriptors — physical addresses and lengths — pointing at each one. As frames arrive, the NIC's DMA engine writes each one into the next free buffer in the ring and marks that descriptor "ready," completely independent of the CPU's attention. The driver's job, once notified, is simply to walk the ring and hand off whichever buffers are marked ready.

🧠 "Remote DMA" Is a Misleading Name Worth Knowing
The NE2000's registers are literally named RSAR (Remote Start Address Register) and the transfer is documented as "Remote DMA" — but on real ISA-era hardware like this, that name is aspirational. bob_os's own ne_remote_read() loops, reading one 16-bit word at a time from the NIC's DATA port with inw(), with the CPU driving every single word. That's programmed I/O (PIO), not true DMA — the CPU is fully occupied for the whole transfer. True bus-mastering DMA, where the device autonomously writes into RAM with zero CPU involvement per byte, is what PCI and later NICs actually provide. The concepts rhyme, but only one of them frees the CPU.

The reason this distinction matters for an OS course, not just a trivia fact: the entire justification for "interrupt-driven, not polled" networking depends on the CPU being free to do other work while a transfer happens. Programmed I/O undermines that promise partially; bus-mastering DMA delivers on it fully. Real kernels are designed around the DMA assumption — buffers described by physical address, handed to the device once, filled in asynchronously.

03 — "A Packet Is Ready"

The Interrupt Fires

Once a frame has landed in a kernel-owned DMA buffer, something still has to tell the kernel it's there. The NIC does this the same way a keyboard, a disk, or a timer chip does: it asserts a hardware interrupt line, which the PIC (or APIC on newer machines) turns into a specific interrupt vector the CPU jumps to — completely asynchronously, exactly like the timer ticks you met in the scheduling lessons.

▶ Walk through one received packet, hardware to handler

Notice what has and hasn't happened by the time the CPU is forced into the interrupt handler: the frame's bytes are already sitting in RAM, fully transferred. The interrupt isn't a request to fetch data — it's a notification that data has already arrived. This ordering is exactly why DMA-plus-interrupt beats polling: the CPU spends zero cycles checking a mailbox that's usually empty, and only gets involved once there's guaranteed to be something to do.

04 — Do Almost Nothing, On Purpose

The Quick ISR Pattern

Here's the trap a first-time driver author falls into: the interrupt handler just told you a packet arrived, so why not just... parse it right there? Strip the Ethernet header, hand it to ip_input(), let UDP match the port, copy it into the socket buffer — all inside the interrupt handler, while you have the CPU's undivided attention?

Because interrupts are usually masked (temporarily blocked) for at least the highest-priority ones while a handler runs, and even when they're not, a long-running handler starves every other device's interrupts of timely service. A NIC ISR that takes even a few hundred microseconds to fully parse a packet means the keyboard, the disk, and the timer tick can all be sitting there waiting. Do that on every single packet during a burst of network traffic, and the whole machine's responsiveness falls apart — not because of a bug, but because of where the work was done.

⚠️ The Rule From the IDT/Interrupts Lesson, Now With a Villain
An interrupt service routine should acknowledge the interrupt, capture the absolute minimum state needed to act on it later, and get out — the same "trap frame, not full context switch, unless truly necessary" discipline you saw with the scheduler's timer interrupt. A network card under heavy load is the textbook case where ignoring this rule has a real, measurable cost: dropped keystrokes, jittery audio, missed timer ticks, all because one ISR overstayed its welcome.

bob_os's actual interrupt dispatcher already embodies this discipline, even for the interrupts it does handle today — look at how little happens in isr.c's central handler before control is handed off:

/* isr.c — the entire body of every hardware-IRQ dispatch */
if (vec < 48u) {
    uint8_t irq = (uint8_t)(vec - 32u);
    pic_send_eoi(irq);                        /* ack immediately */

    if (irq == 0 && scheduler_hook != 0) {
        uint32_t new_esp = scheduler_hook((uint32_t)frame);
        if (irq_handlers[0] != 0) irq_handlers[0](frame);
        return new_esp;
    }
    if (irq_handlers[irq] != 0) irq_handlers[irq](frame);  /* one function call, no parsing here */
}

Notice the shape: acknowledge the PIC first (so the hardware knows it can raise the next interrupt), then dispatch to exactly one registered handler function and return. A hypothetical ne2000_irq_handler() registered via irq_register(NE_IRQ, ne2000_irq_handler) would follow the same law: read the NIC's interrupt status register, note "RX complete," and get out — not walk the ring buffer and call into IP and UDP from inside the handler.

05 — Finishing the Job Safely

Deferred Work: The Bottom Half

If the actual parsing can't happen inside the interrupt, where does it happen? The answer is a second, separate mechanism that real kernels build specifically for this: work that was triggered by an interrupt but runs later, outside interrupt context, where it's safe to take longer and where other interrupts aren't blocked. Different kernels give this a different name — Linux calls it a softirq (or the closely related tasklet), Windows calls it a DPC (Deferred Procedure Call) — but the shape is identical everywhere.

⏱️ Top Half — Inside the ISR

Runs with (some) interrupts masked, on the interrupt stack, for as few instructions as possible. Job: acknowledge the device, note "there's work to do," schedule the bottom half, return immediately.

🧵 Bottom Half — Deferred Work

Runs later, with interrupts re-enabled, free to take as long as it actually needs. Job: walk the ring buffer, strip Ethernet/IP/UDP headers, dispatch to the right socket — everything section 04 said not to do up top.
🔑 Why Two Halves Instead of One
Splitting the work isn't extra ceremony for its own sake — it's the only way to get both properties you actually want simultaneously: fast interrupt response (so no device gets starved) and unhurried, safe packet processing (so parsing a malformed header or copying a large payload doesn't hold the whole system hostage). One function trying to do both jobs can only be good at one of them.

bob_os's current polled design sidesteps this whole split — net_poll() runs from ordinary scheduled context on every timer tick, which is already "outside interrupt context" by construction, so there's no top-half/bottom-half distinction to make yet. That's a legitimate reason introductory network stacks often start polled: you get the safety property of deferred work for free, at the cost of the latency and CPU-efficiency properties true interrupt-driven DMA gives you. Linux's actual receive path, NAPI, mentioned in the module 26 tutorial's own Q&A, is a hybrid of exactly these two ideas: an interrupt wakes the driver, but then it switches to a budgeted polling loop to drain a burst of packets before re-arming the interrupt — the best of both under load.

06 — Sending Is Roughly the Mirror

Transmit: The Reverse Journey

Everything above described receiving (RX). Sending (TX) is close to the same story run backwards, with the kernel now on the initiating end instead of reacting to hardware:

  1. Kernel builds the frameUDP, IP, and Ethernet headers get prepended to the payload (this is the "journey down" from lesson 1), producing a complete frame sitting in a kernel buffer.
  2. Kernel queues it in a driver-owned TX ringInstead of handing bytes to the NIC one at a time, the driver places a descriptor — address and length of the frame — into its own transmit ring buffer. This is the same descriptor-ring idea as RX, just running in the opposite direction.
  3. NIC's DMA engine reads the frame out on its own scheduleThe kernel "kicks" the NIC (a single register write saying "new work is queued") and returns immediately — it does not wait for transmission to finish. The NIC's DMA engine then reads the frame directly out of RAM at its own pace, again without CPU involvement, and shifts it out onto the wire.
  4. NIC fires a TX-complete interruptOnce the frame is fully sent, the NIC raises another interrupt so the driver can free that descriptor slot for reuse. This handler follows the exact same "quick ISR, defer the rest" discipline as the RX path — it has no urgent parsing to do, just bookkeeping.
💡 The Aha Moment
RX and TX are mirror images built from the same two primitives: a descriptor ring the driver and NIC both read and write (in opposite roles), and an interrupt that fires only at the moment one side needs the other's attention. Everything in between — the actual byte movement — is DMA, invisible to the CPU. Once you see the ring-plus-interrupt pattern once, you'll recognize it in disk drivers, GPU command queues, and virtually every other high-throughput device interface.

bob_os's own ne2000.c TX path (module 26) does this today, minus interrupts: ne2000_send() writes the frame into the card's fixed TX page range via Remote DMA (the PIO-style transfer from section 02), then issues the NE_CR_TXP command bit to start transmission — the same "kick and let the hardware take it from here" shape, just with a synchronous wait for completion instead of an asynchronous TX-complete interrupt.

07 — Quick Reference

Glossary & Key Terms

DMA (Direct Memory Access)
A device transferring data directly to or from RAM without the CPU copying each byte or word — the CPU is free to do other work during the transfer.
Programmed I/O (PIO)
A transfer where the CPU itself reads or writes each byte/word via I/O instructions in a loop. Simpler to implement than DMA, but keeps the CPU busy the entire time.
Descriptor Ring
A fixed-size circular array of buffer addresses and lengths shared between driver and device, used to hand off many buffers without a syscall or interrupt per buffer.
Hardware Interrupt
An asynchronous signal from a device that forces the CPU to stop what it's doing and run a specific handler — used here to say "a DMA transfer just completed."
ISR (Interrupt Service Routine)
The handler that runs immediately when an interrupt fires. Kept deliberately short — acknowledge, note the work, defer the rest.
Softirq / Bottom Half / DPC
Kernel-specific names for work scheduled by an ISR but executed later, outside interrupt context, where it's safe to take longer.
NAPI
Linux's hybrid RX strategy: an interrupt wakes the driver, which then polls in a budgeted loop to drain a burst efficiently before re-arming the interrupt.
PIC / APIC
The Programmable Interrupt Controller (or its modern Advanced successor) that routes hardware interrupt lines to CPU interrupt vectors and must be acknowledged (EOI) once a handler is done.
