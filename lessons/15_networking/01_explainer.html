The Layered
Network Stack

Every diagram you've ever seen of "the network stack" draws four boxes stacked on top of each other — link, network, transport, application — and calls it a day. That diagram is correct, but it hides the single most important fact about how a real operating system builds it: those four boxes don't live in the same place. Some of them are hardware-adjacent kernel code you'll never see from a normal program. One of them is just your program, running exactly like any other, calling functions it doesn't know are secretly asking the kernel to do something enormous on its behalf.

00 — Where We Left Off

You Already Know the Wall

By now the pattern should feel familiar: user space is sandboxed, kernel space is privileged, and the only legal way across is a narrow, guarded doorway — a system call. You've seen this wall enforce itself around memory (paging), around files (the VFS), and around scheduling (the PCB). Networking is not a new idea bolted on top of that wall. It is the exact same wall, applied to a new kind of resource: bytes arriving on a wire from a machine that isn't yours.

The thing that makes networking feel different the first time you meet it is that the "four layers" diagram — the one every textbook opens with — never tells you where each layer physically executes. This lesson fixes that. We're going to take the classic stack you already half-know and pin every layer of it to a concrete location: a driver, a kernel subsystem, or an ordinary user-space program.

Where this fits in bob_os: everything in this cluster is the companion reading for module 26_network — the actual NE2000 driver, IP stack, and UDP socket layer live in that module's .c/.h files. This lesson explains the shape of the problem those files solve; the next three go layer-by-layer into the mechanics.
01 — The Classic Picture

Four Layers, One Job Each

Strip away the acronyms for a second. Getting a message from your program to a program on another machine requires answering four completely separate questions, in this order, every single time:

  1. How do I put bits on this specific piece of wire (or radio) right in front of me? — the Link layer, e.g. Ethernet.
  2. Given that I can reach my immediate neighbors, how do I get a message to a machine that might be on the other side of the planet? — the Network layer, e.g. IP.
  3. Given that I can get a raw message to the right machine, how do I get it to the right program on that machine, and do I need any reliability guarantees? — the Transport layer, e.g. TCP or UDP.
  4. Given a reliable (or unreliable, deliberately) byte pipe between two programs, what do those bytes actually mean? — the Application layer, e.g. HTTP, DNS, or bob_os's own tiny UDP echo protocol.
LinkLayer 1–2
Ethernet frames, MAC addresses, the physical/electrical reality of "bits on a wire." Concerned only with your immediate neighbors on the same physical segment.
Network (IP)Layer 3
IP addresses, routing, TTL. Concerned with getting a packet from any machine to any other machine, possibly through many intermediate hops it's never heard of.
Transport (TCP/UDP)Layer 4
Ports (which program), and a choice: TCP's reliable, ordered, flow-controlled byte stream, or UDP's fire-and-forget datagrams. Covered in lessons 3 and 4 of this cluster.
ApplicationLayer 7
HTTP, DNS, your own echo protocol — whatever meaning you decide to give the bytes flowing through the pipe the layers below built for you.
💡 The Aha Moment
Each layer solves its problem without knowing anything about the layers above or below it. Ethernet doesn't know it's carrying IP — it just moves a frame with a destination MAC. IP doesn't know it's carrying UDP or TCP — it just routes a packet with a destination address. This is what "layering" actually buys you: you can swap Ethernet for Wi-Fi, or UDP for TCP, without touching the layers on either side. That's also exactly why the diagram is drawn as a stack of independent boxes in the first place.
02 — The Part Diagrams Never Show You

Where Each Layer Actually Lives

Here is the fact that turns the classic stack from a memorization exercise into an OS-design lesson: those four layers are not four peer modules sitting next to each other in the same kind of code. They sit on three completely different sides of the privilege wall, and the boundary between "kernel" and "user space" cuts straight through the middle of the stack, between transport and application.

Kernel Space — Ring 0

NIC driver, Ethernet framing, IP, TCP, UDP. All four of these run with full hardware access, own the network card's I/O ports directly, and are trusted code that shipped with the OS itself. Your program never gets to see a single one of these functions.

User Space — Ring 3

Your browser, your echo server, curl, anything you compiled yourself. Talks to the network exclusively through the socket API — a handful of syscalls that ask the kernel to do the actual work.

🔑 The One Sentence That Matters Most in This Lesson
Link, network, and transport are all kernel code — one continuous, trusted pipeline with no privilege boundary anywhere inside it. Application is user code. The only place the wall appears in this entire four-layer stack is at the single seam between transport and application — and that seam is exactly the socket API.

This is worth sitting with, because it's easy to assume the four layers are drawn stacked because they're four equally-privileged modules that happen to be organized in a pipeline. They're not. Three of them are inside the walled garden. One of them is out in the world with everybody else, and has to knock.

03 — Watch It Happen

A Packet's Journey, Both Directions

Let's make this concrete with an actual packet. Someone on another machine sends a UDP datagram to your bob_os box on port 7 (the classic "echo" port). Trace what happens, layer by layer, privilege ring by privilege ring:

▶ Choose a direction to animate
  1. Wire → NICElectrical signal arrives on the cable. The NE2000 hardware assembles it into a raw Ethernet frame sitting in the card's own on-board memory — no kernel involvement yet.
  2. NIC → Kernel driver (ne2000.c)The driver pulls the frame off the NIC and into a kernel buffer. In a fully interrupt-driven design (the subject of lesson 2 in this cluster) this is triggered by a hardware interrupt; bob_os's current driver instead polls the card each timer tick — same end result, different trigger.
  3. Ethernet → IP (ip.c)The kernel strips the 14-byte Ethernet header, checks the ethertype is 0x0800 (IPv4), and hands the payload to ip_input(), still entirely inside Ring 0.
  4. IP → UDP (udp.c)The IP layer validates the checksum, strips its own 20-byte header, and — seeing protocol 17 — hands the payload to udp_input(). Still Ring 0. Still no user code has run.
  5. UDP → socket bufferUDP matches the destination port against the table of bound sockets and copies the payload into that socket's receive buffer. This is the last kernel-space step.
  6. Socket buffer → your program (user_prog.c)Your program calls recvfrom() — a syscall, crossing the wall — and the kernel copies the bytes from its buffer into memory your program owns. This is the only step in the entire journey that happens in Ring 3.
🧠 Count the Ring Crossings
Five of the six hops above happen entirely within the kernel, ring 0 to ring 0, with zero privilege transitions. There is exactly one ring crossing in the whole journey — the syscall your program makes to ask for its data. Everything else is the kernel talking to itself.
04 — The One Legal Door

The Socket API: A Very Narrow Interface

If your program never touches a packet directly, how does it send or receive anything at all? Through the same mechanism you've already seen the VFS use for files and pipes: a small, fixed set of syscalls that hide an enormous amount of kernel machinery behind a handful of simple function calls.

/* syscall.h — bob_os's socket-facing syscalls (module 26) */
#define SYS_SOCKET    21   /* udp_bind(port)               -> sock_id  */
#define SYS_SENDTO    22   /* udp_send(dst_ip, ports, buf, len)        */
#define SYS_RECVFROM  23   /* udp_recvfrom(sock_id, buf, &src_ip, ...) */

/* user_prog.c — this is the ENTIRE interface user code ever sees */
int sock = syscall(SYS_SOCKET, 7, 0, 0);          /* bind to port 7 */
int n    = syscall(SYS_RECVFROM, sock, (int)buf, (int)&src_ip);
syscall(SYS_SENDTO, (int)src_ip, ports_packed, (int)buf);

Three function calls. That's the entire surface area your program is exposed to. Everything you read about in section 03 — Ethernet framing, IP checksums, port matching, buffer copies — happens behind those three lines, invisible to the caller by design. This mirrors precisely what you already learned about the VFS: open()/read()/write() is one universal interface dispatching to wildly different backends (a real file, VGA text output, now a UDP socket). The socket API is that same idea, specialized for the network.

The narrow-waist principle Kernel complexity ↓ syscalls ↓ user-space simplicity A handful of narrow, well-defined syscalls is what lets an enormous, hardware-specific, protocol-specific kernel subsystem hide behind three function calls any program can use without knowing any of it exists.
🧵 A Preview of Lesson 3
On a full POSIX system, this narrow waist goes one step further than bob_os currently does: socket() doesn't just hand back an opaque handle — it hands back an ordinary file descriptor, the exact same kind of integer open() returns, readable and writable with the exact same read()/write() calls you use on a regular file. bob_os's SYS_SOCKET currently returns a UDP-only handle outside the VFS fd table — a simplification worth knowing about before lesson 3 walks through the fully unified design.
05 — Tying It Back

Your Browser Never Touches a Packet

Remember the browser process-model lessons: the renderer process is sandboxed and can't even open a file directly, let alone a raw socket. When a page fetches a resource, the renderer asks the browser's network service (via IPC) to fetch it; the network service asks the kernel (via the socket API) to open a TCP connection; the kernel's transport, network, and link layers do everything described in section 03; and eventually bytes come back up through exactly one syscall boundary into a buffer the network service can hand back to the renderer.

❌ What People Sometimes Imagine

"The browser reads packets off the network card and assembles them into a web page." This has never been true of any mainstream OS. User-space code has no legal path to a network device.

✅ What Actually Happens

The browser asks the kernel for a byte stream via connect()/read()/write(). The kernel's own trusted, privileged network stack does every bit of framing, routing, and reliability work, entirely out of the browser's reach.
✅ Same Shape, Every Time
This is the exact same story you've now seen for memory (paging + syscalls), for files (VFS + syscalls), and now for the network (kernel stack + socket syscalls). One recurring architecture: powerful, privileged machinery in the kernel; a narrow, safe doorway for user code to request its services; and a hard wall in between that user code cannot simply climb over.
06 — Quick Reference

Glossary & Key Terms

Link Layer
The layer responsible for moving bits between directly-connected devices on the same physical segment — Ethernet is the canonical example. Owned by the NIC driver.
Network Layer (IP)
Responsible for routing a packet from any host to any other host, possibly across many links. Lives in the kernel's IP code.
Transport Layer
Responsible for getting data to the right program (via ports) and, for TCP, providing reliability. Lives in the kernel, right up against the socket API.
Application Layer
Whatever meaning a program gives to the bytes flowing through its socket — HTTP, DNS, a custom echo protocol. Ordinary user-space code.
Socket API
The narrow set of syscalls (socket, bind, connect, send, recv, and friends) that is the only legal path from user space into the kernel's network stack.
NIC (Network Interface Card)
The hardware that actually puts bits on the wire and takes them off. In bob_os, an NE2000-compatible card driven by ne2000.c.
Ethertype
A 16-bit field in the Ethernet header telling the receiving stack what protocol is riding inside — 0x0800 means IPv4.
Ring 0 / Ring 3
x86 privilege levels. Ring 0 is the kernel, with full hardware access; Ring 3 is user space, sandboxed and unable to touch hardware directly.
