to Framebuffers

Everything so far has been characters in an 80×25 grid, painted by an ASCII code and a 4-bit color nibble. That's not a limitation of the trick you learned — memory-mapped I/O — it's a limitation of text mode specifically. The exact same trick, scaled up, is how every pixel on every modern display gets there too: one flat array of memory the CPU (or GPU) writes into directly, all the way from a single 2-byte cell to a 1080p framebuffer of eight million bytes.

00 — Where We Left Off

Same Trick, Bigger Canvas

Two lessons ago you learned the whole idea in miniature: the VGA card maps its display memory into your address space at 0xB8000, and writing bytes there paints characters on screen. One lesson ago you learned that a second subsystem, the CRTC, controls things the character buffer can't — cursor position, and which slice of a larger buffer is currently visible.

Both of those lessons were entirely about text mode: a grid of fixed-size character cells, each one either "blank" or "one of 256 glyphs from a built-in font, in one of 16 colors." That's an enormously useful mode for a kernel's early debug output — and also a real ceiling. This lesson is about what's on the other side of that ceiling, and why the underlying trick never actually changes.

💡 The Throughline for This Whole Module
From a single 2-byte character cell at 0xB8000, to a 320×200 byte-per-pixel canvas, to a full HD linear framebuffer, to a modern GPU's command buffer — it is memory-mapped I/O, over and over, at increasing scale and increasing indirection. Nothing about the core idea changes. What changes is how much the CPU is trusted to touch directly, and how much gets handed off to smarter hardware in between.
01 — The Ceiling

What Text Mode Can't Do

Text mode's entire vocabulary is: pick one of 256 pre-drawn glyphs from a fixed hardware font, place it in one of 2,000 grid cells, color it with one of 16 foreground and 16 background colors. That's it. There is no way to light up an individual pixel that isn't part of a character shape. You cannot draw a diagonal line, a circle, a photograph, or even a smoothly curved font — the glyphs are whatever shapes the VGA card's built-in font ROM happens to contain, typically an 8×16 pixel grid per character, and you don't get to touch those pixels directly.

🔤 Text Mode

Addressable unit: a character cell. You choose which pre-drawn glyph appears, not what shape it is. Perfect for a terminal. Structurally incapable of arbitrary art, photos, or smooth graphics.

🖼️ Graphics Mode

Addressable unit: a single pixel. You choose the color of every individual dot on the display. Strictly more powerful — and, as you're about to see, in some ways strictly simpler to program against.

So the historical next step — for VGA hardware in the 1980s, and conceptually for every graphics system built since — was to stop addressing the screen in terms of "which glyph" and start addressing it in terms of "which pixel, what color." That's a graphics mode, and VGA shipped with several. The most famous one, for very good pedagogical reasons, is Mode 13h.

02 — VGA's Graphics Mode

Mode 13h: 320×200, One Byte, One Pixel

Mode 13h (set via BIOS interrupt int 0x10 with AH=0x00, AL=0x13, back when BIOS calls were still available in Real Mode) switches the VGA card into a 320×200 pixel, 256-color linear framebuffer, still mapped at the very same physical base address you already know: 0xA0000 this time, rather than 0xB8000.

Here's what makes Mode 13h a beloved teaching tool even forty years later: it is, in a real sense, simpler to program than text mode. There's no two-byte cell, no attribute nibble math, no font ROM standing between you and the screen. Every single byte in the buffer is one pixel — its value (0–255) is an index into a 256-entry color palette table, and that's the whole model.

Mode 13h's Entire Addressing Formula offset = y × 320 + x No "× 2" at the end this time — one byte per pixel means the cell index and the byte offset are the exact same number. 
unsigned char *vram = (unsigned char *)0xA0000;

/* set pixel (x, y) to palette color 4 (bright red, by default palette) */
vram[y * 320 + x] = 4;

/* a filled rectangle is now just a nested loop, no glyphs involved */
for (int py = y0; py < y1; py++)
    for (int px = x0; px < x1; px++)
        vram[py * 320 + px] = color;
✅ Genuinely Simpler, Not Just Different
Compare this one-line pixel-set to the text-mode cell write from Lesson 1, which needed a character byte, a separate attribute byte, and a font ROM's cooperation to actually render anything recognizable. Mode 13h needs none of that — draw a line, draw a circle, blit a sprite, all with nothing but array indexing. This is a big reason retro game developers and OS-dev tutorials both gravitate toward Mode 13h: maximum visual capability for minimum conceptual overhead.
Where does the color actually come from? Each of the 256 possible byte values (0–255) is looked up in VGA's DAC palette — a small, separately-programmable table mapping index → actual RGB value. Change the palette table and the same stored pixel bytes instantly display completely different colors, without touching a single byte of the 64,000-byte framebuffer itself. It's the same "extra layer of indirection" idea you'll see again with GPU command buffers later in this lesson.
03 — See It Happen

Setting a Pixel in Mode 13h, Live

Same pattern as the character-cell demo from Lesson 1 — but watch how much shorter the path from "byte write" to "visible result" has become. There's no attribute byte, no font lookup, no second write at all.

▶ Choose a pixel to set
  1. 1 — Compute the offsetoffset = y * 320 + x. One multiply, one add — no ×2, because a byte and a pixel are now the same size.
  2. 2 — One single storevram[offset] = palette_index. That's the entire write. No second byte, no font, no attribute nibble.
  3. 3 — DAC palette lookup, in hardwareThe VGA DAC translates the stored index into an actual RGB triple using its currently-loaded palette table — a lookup that happens continuously, in hardware, every time that byte is scanned out.
  4. 4 — The pixel appearsExactly one dot on the 320×200 grid lights up in the resolved color. Do this 64,000 times (once per byte) and you've drawn an entire frame.
04 — The Real Modern Picture

Linear Framebuffers: VESA, GOP, and Beyond

Mode 13h is real, historically important, and still runs in QEMU today — but 320×200 with 256 colors is a museum piece next to a modern 1920×1080 (or 4K) full-color display. The idea scales up perfectly cleanly, though: a linear framebuffer is exactly the same concept — one flat array, one memory address per pixel — just at a resolution and color depth firmware is willing to hand you today.

The mechanism is conceptually identical to what you already know, just with a crucial handoff step added: instead of a hardwired legacy address like 0xB8000, the bootloader or firmware queries the graphics hardware, sets up a framebuffer of a resolution and format it chooses (or negotiates with your kernel), and then tells your kernel where that framebuffer lives in physical memory — because on modern hardware, that address isn't fixed or predictable in advance the way legacy VGA's was.

The Same Offset Formula, Scaled Up offset = (y × width + x) × bytes_per_pixel Identical shape to the text-mode formula from Lesson 1 — only the constants changed. 80 became "width" (often 1920). 2 bytes/cell became 4 bytes/pixel (one byte each for red, green, blue, and often alpha/padding). 
/* A GOP-style 32bpp linear framebuffer, handed to the kernel by
   the bootloader as a base address + width + height + pitch. */
struct framebuffer {
    uint32_t *pixels;   /* base address, e.g. from a UEFI GOP query */
    uint32_t  width;    /* e.g. 1920 */
    uint32_t  height;   /* e.g. 1080 */
    uint32_t  pitch;    /* bytes per row — may exceed width*4! */
};

void fb_set_pixel(struct framebuffer *fb, int x, int y, uint32_t rgb) {
    uint32_t *row = (uint32_t *)((uint8_t *)fb->pixels + y * fb->pitch);
    row[x] = rgb;
}
📌 Why "Pitch" and Not Just width × 4?
Real hardware often pads each row to a convenient alignment boundary for performance reasons, so a row can occupy more bytes than the visible pixels strictly need. The pitch (also called "stride") is the real per-row byte size, and a kernel that assumes pitch == width * bytes_per_pixel will draw a subtly slanted, corrupted image on hardware where that assumption is false. Always use the pitch firmware actually reports.

It's worth pausing to feel just how far the "same idea" has scaled, in raw bytes, across the eras covered in this lesson:

Nearly a ten-thousand-fold jump in buffer size from a text-mode kernel console to a 4K framebuffer — and the addressing formula from Lesson 1, (row × width + col) × bytes_per_cell, still describes every single one of them without modification.

Why did VESA VBE give way to UEFI GOP? VESA VBE calls were still routed through legacy BIOS interrupt conventions — 16-bit real-mode-style calls, awkward to invoke from a 32/64-bit Protected/Long Mode kernel without dropping back to real mode or emulating it. UEFI's GOP is a native, modern, callable-from-64-bit-code protocol that firmware exposes directly during boot, before your bootloader even calls ExitBootServices() — no real-mode gymnastics required. It's the direct modern descendant of the same idea, just with the legacy friction removed.
05 — Where It All Leads

Modern GPUs: Abstracting the Framebuffer Away

Everything so far — text cells, Mode 13h pixels, linear framebuffers — has one thing in common: the CPU itself computes every pixel and writes it with an ordinary store instruction. That's exactly how a kernel's early boot splash screen or a simple bootloader logo still works today. But it is not how a modern desktop, game, or web browser puts pixels on screen — that path goes through a GPU, and the CPU barely touches individual pixels at all anymore.

A modern GPU doesn't want the CPU writing one pixel at a time — that would be catastrophically slow for millions of pixels, sixty-plus times a second. Instead, the CPU writes a much smaller, much higher-level stream of drawing commands — "draw this triangle list with this texture and this shader" — into a region of memory called a command buffer, and the GPU itself reads that stream and does the actual pixel-by-pixel work, in parallel, across thousands of tiny cores.

🧠 The Layer Changed. The Trick Didn't.
Even at the very bottom of a modern GPU pipeline, after every shader and every triangle has been rasterized, the final step is still exactly the trick this entire lesson set has been teaching: a flat array of pixel memory that the display hardware scans out to your monitor. The GPU just moved the "who computes each pixel" job away from the CPU and onto thousands of specialized cores — the destination is still, fundamentally, a framebuffer.

This is also precisely why command buffers are so often built on shared memory rather than passed message-by-message: the CPU (in a userspace driver or the kernel's GPU driver) and the GPU need to read and write the same command stream without paying a syscall or IPC round-trip per draw call, the exact same shared-memory trade-off you may have already met when two OS processes need to exchange large, frequent data.

06 — Tying It Back

This Is Exactly What Your Browser's GPU Process Does

If you've traced through how Chromium renders a page, this should feel familiar rather than new: the renderer process doesn't draw pixels itself. It builds a display list of drawing commands — "paint this rectangle, draw this text run, composite this layer" — and hands that list to the browser's dedicated GPU process through a shared command buffer, exactly the pattern from the pipeline diagram above, just one layer higher up the stack.

✅ Same Idea, Every Layer of the Stack
Your kernel writes a character byte into 0xB8000. A DOS game writes a palette-index byte into 0xA0000. A modern OS driver writes RGBA pixels into a UEFI GOP framebuffer. A browser's GPU process issues draw commands that eventually rasterize into a framebuffer the display scans out. Four completely different eras of technology, one repeated idea: expose a chunk of memory, let someone write into it, and something downstream turns those bytes into light.

The layers of indirection have grown enormously — from "the CPU directly touches video RAM" to "the CPU asks a GPU, through a driver, through a command buffer, to eventually touch video RAM" — but the foundational primitive at the very bottom of every one of those stacks has never actually gone away. It's the same idea you started this module with: memory-mapped I/O, so ubiquitous it disappears into the plumbing of everything built on top of it.

07 — Common Pitfalls

Things That Bite Everyone Once

⚠️ Assuming 0xA0000 and 0xB8000 Coexist
Text mode and Mode 13h are different VGA modes, not two buffers you can write simultaneously. Switching into Mode 13h reprograms the CRTC and DAC away from the text-mode configuration entirely — writes to 0xB8000 stop producing readable text the moment you switch modes. A kernel that wants both a graphical splash screen and a text console has to explicitly switch modes back and forth, or commit to graphics mode and draw its own text by hand-blitting a font (which is exactly what real GUI-era OSes eventually do).
🐢 Byte-at-a-Time Pixel Loops Get Slow, Fast
64,000 individual byte stores for one Mode 13h frame is trivial for a CPU. But a 1080p, 32-bit linear framebuffer is roughly 8 million bytes per frame — filling or clearing it one pixel at a time in a naive loop is measurably slower than a bulk operation. Real drivers lean on wide stores (writing 4 or 8 bytes at once), memset-style fills, or — once you have one — offload the work to the GPU entirely rather than touching every byte from the CPU.
🧠 Pixel Format Is Not Universal
"32-bit color" doesn't pin down byte order. UEFI GOP can hand you 0xXXRRGGBB or 0xXXBBGGRR depending on the mode the firmware chose, and a kernel that assumes one when the hardware provides the other draws images with red and blue channels swapped — a subtle bug that looks like a color-calibration issue rather than a logic error. Always read the firmware-reported pixel format struct; never hardcode it.
08 — Quick Reference

Glossary & Key Terms

Graphics Mode
Any video mode where the addressable unit is an individual pixel rather than a pre-drawn character cell — Mode 13h being VGA's classic example.
Mode 13h
VGA's 320×200, 256-color, one-byte-per-pixel graphics mode, mapped at physical address 0xA0000 and set via BIOS int 0x10.
DAC Palette
A small, separately programmable lookup table mapping each stored pixel-index byte to an actual RGB color, used by palette-indexed modes like Mode 13h.
Linear Framebuffer
A flat, contiguous block of memory where each pixel's color is stored directly (not palette-indexed), addressed by a simple row/column/pitch formula.
Pitch / Stride
The real number of bytes per row in a framebuffer, which may exceed width × bytes-per-pixel due to hardware row alignment padding.
VESA VBE
A historical BIOS extension standard for querying and setting high-resolution linear framebuffer video modes from legacy real-mode-style BIOS calls.
UEFI GOP
Graphics Output Protocol — the modern UEFI firmware service that hands a kernel or bootloader a linear framebuffer address, resolution, and pixel format, without legacy BIOS calls.
Command Buffer
A shared-memory region where a CPU writes high-level drawing commands for a GPU to read and execute, avoiding per-draw-call syscall or IPC overhead.
Rasterization
The GPU process of converting geometric shapes (like triangles) into actual colored pixels in a framebuffer.
GPU Process (Browser)
Chromium's dedicated process for turning renderer-issued draw commands into actual pixels via the GPU, using the same command-buffer / shared-memory pattern as native graphics drivers.
