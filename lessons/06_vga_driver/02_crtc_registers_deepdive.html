Beyond the Buffer:
VGA's CRT Controller

Writing bytes to 0xB8000 gets characters on screen — but it doesn't move the blinking cursor, and it doesn't know how to scroll without copying thousands of bytes by hand. Both of those live somewhere else entirely: a separate bank of hardware registers called the CRT Controller (CRTC), reached not through memory at all, but through two tiny I/O ports. This is the other half of VGA text mode nobody mentions until you go looking for it.

00 — Where We Left Off

0xB8000 Doesn't Control Everything

The previous lesson established the big idea: text on screen is just bytes in a memory-mapped buffer at 0xB8000. That's true, and it's most of what you need to get a working kernel console. But two things you've almost certainly seen a real terminal do are conspicuously not explained by that buffer alone:

  • The little blinking underline or block that shows where the next character will land — the hardware text cursor. Nothing in the character buffer represents "this is where the cursor is."
  • Scrolling that happens instantly, with no visible redraw lag — which is suspicious, because copying 4,000 bytes on every newline (which is exactly what bob_os's software scroll does) is not instant on real 1980s-era hardware.

Both are controlled by a completely separate piece of the VGA chipset: the CRT Controller, or CRTC — named after the Cathode Ray Tubes it was originally built to drive, back when "monitor" meant a heavy glass tube, not an LCD panel.

💡 The Reframe
0xB8000 is data — what character and color go in each cell. The CRTC is control — where the cursor sits, what shape it is, and which part of video memory the screen is even currently looking at. Two entirely different hardware subsystems, reached through two entirely different mechanisms.
01 — A Different Kind of Address

Reaching the CRTC: Port I/O, Not Memory

Here's the twist that trips people up first: the CRTC's registers are not memory-mapped like the character buffer. x86 CPUs have an entirely separate, parallel address space just for hardware — a 16-bit space of up to 65,536 I/O ports, accessed only through two special instructions, in and out, never through a regular pointer dereference.

🧠 Memory-Mapped (0xB8000)

Lives in the same address space as RAM. Read/write it with normal pointer dereferences: *(char*)0xB8000. The CPU can't tell it apart from ordinary memory — it's the video card watching that range that makes it special.

🔌 Port-Mapped (0x3D4 / 0x3D5)

Lives in a completely separate 16-bit I/O address space. Only reachable with the dedicated in/out assembly instructions — a plain C pointer to 0x3D4 means nothing; it isn't a memory address at all.

The CRTC exposes far more internal registers (18 of them, indices 0x00–0x11) than it has actual I/O ports to address them with. Rather than giving every register its own port, VGA hardware uses a classic two-step index/data pattern: one port selects which register you mean, a second port reads or writes its value.

PortNamePurpose
0x3D4CRTC Index RegisterWrite the register number you want to target (0x00–0x11) here first.
0x3D5CRTC Data RegisterThen read or write the actual 8-bit value of whichever register was just selected.
The Two-Step Pattern, in Pseudocode outb(0x3D4, register_index); outb(0x3D5, value); Every single CRTC register access — reading or writing — is always exactly this shape: select, then transfer. There is no way to write a CRTC register in one instruction.
Why 0x3D4/0x3D5 specifically? These are the color adapter's CRTC ports, fixed by the original IBM PC/CGA/VGA hardware convention (the monochrome adapter historically used 0x3B4/0x3B5 instead). Like 0xB8000 itself, these numbers aren't something you choose — they're wired into the platform and every VGA-compatible chipset preserves them for backward compatibility, all the way into today's emulated legacy BIOS mode in QEMU.
02 — The Hardware Cursor

Moving the Cursor: Two Registers, One Position

The blinking cursor you see in a text-mode terminal isn't software drawing anything — it's a genuine hardware feature the CRTC generates on its own, at the position you tell it to, and it keeps blinking on its own timer even if your kernel is sitting in an infinite loop doing nothing else. All it takes is telling the CRTC a single number: the cursor's linear position in the buffer, using the exact same cell-index math from the offset formula in the previous lesson (just without the final ×2, since this is a cell index, not a byte offset).

Because that position can range up to 1,999 (row 24, col 79 → 24×80+79 = 1999) and a single CRTC register only holds 8 bits (0–255), the position has to be split across two registers — a high byte and a low byte:

0x0E
Cursor Location High
Bits 15-8 of the cursor's linear cell position (row×80+col). Written first by convention.
0x0F
Cursor Location Low
Bits 7-0 of the same linear cell position. Written second.
Worked Example — Move Cursor to Row 5, Col 30 pos = row × 80 + col = 5 × 80 + 30 = 430 = 0x01AE high byte = (pos >> 8) & 0xFF = 0x01  ·  low byte = pos & 0xFF = 0xAE 
void vga_set_cursor(int row, int col) {
    unsigned short pos = row * VGA_COLS + col;

    outb(0x3D4, 0x0E);            /* select "cursor location high" */
    outb(0x3D5, (pos >> 8) & 0xFF);

    outb(0x3D4, 0x0F);            /* select "cursor location low" */
    outb(0x3D5, pos & 0xFF);
}
🔑 Same Math, Different Destination
Notice this is the identical row × 80 + col cell-index math from writing characters — the only difference is where the result goes. Writing a character sends bytes to a memory address (0xB8000-relative). Moving the cursor sends a 16-bit cell index to a hardware register (via ports 0x3D4/0x3D5). Same coordinate system, two completely different delivery mechanisms.

A few registers below these, indices 0x0A and 0x0B (Cursor Start and Cursor End) control the cursor's shape — which scanlines within a character cell it actually draws on. Set them to cover only the bottom couple of scanlines and you get the classic thin underline cursor; set them to cover the whole cell height and you get a solid block cursor. Some of these registers also carry a "cursor disabled" bit, which is how a kernel can hide the hardware cursor entirely (useful once you're drawing your own cursor, or don't want one at all).

03 — See It Happen

Moving the Cursor, Register by Register

Below is the exact two-register, four-outb sequence from vga_set_cursor(), played out step by step. Watch how nothing touches 0xB8000 at all — the entire operation happens through the index/data port pair.

▶ Choose a cursor position to move to
  1. 1 — Compute the linear positionpos = row * 80 + col. This is a cell index (0–1999), not a byte offset — the CRTC's cursor registers think purely in cells.
  2. 2 — Select register 0x0E, send the high byteoutb(0x3D4, 0x0E) tells the CRTC "the next data write is for Cursor Location High." outb(0x3D5, pos>>8) sends bits 15-8.
  3. 3 — Select register 0x0F, send the low byteoutb(0x3D4, 0x0F) retargets the index port. outb(0x3D5, pos&0xFF) sends bits 7-0.
  4. 4 — The blinking cursor jumpsThe instant both bytes are latched, the CRTC's own cursor-blink circuitry starts blinking at the new cell — with zero further CPU involvement. It'll keep blinking on its own timer forever, or until you write these registers again.
04 — The Trick Behind Fast Scrolling

Screen Start Offset: Scrolling Without Copying

Recall bob_os's software scroll() from the previous lesson: it walks all 24 visible rows and copies each one up, cell by cell — roughly 4,000 byte-copies every time the screen scrolls. It works, but it's real, measurable CPU work for something that ought to feel instantaneous.

Real VGA hardware has a much cheaper trick available, and it comes from another pair of CRTC registers: Start Address High (index 0x0C) and Start Address Low (index 0x0D). Together they hold a 16-bit cell index — but this time, it isn't a cursor position. It's which cell in video memory the top-left corner of the visible screen currently corresponds to.

✅ The Reframe That Makes It Click
Nothing says the VGA buffer you write into has to be exactly the 80×25 window you can see. If you allocate a larger buffer — say, 80×50, twice the visible height — you can write new lines into the rows below what's currently shown, then simply tell the CRTC "start displaying from row 25 instead of row 0" by writing one new start-address value. The screen appears to scroll instantly. Not one byte of character data moved — only the hardware's notion of "where does the visible window begin" changed.
Scrolling Down One Row via Start Address new_start_cell = old_start_cell + 80 Advancing the start address by exactly one row's worth of cells (80) shifts the entire visible window down by one row — an O(1) register write instead of an O(rows×cols) memory copy.
ApproachCost per scrollWhat actually moves
Software scroll (bob_os today)~4,000 byte copiesEvery visible character, physically, in memory
Hardware start-offset scroll2 register writesNothing — only which memory the CRTC reads from changes
📌 The Catch
This trick only pays off if you've allocated a video buffer larger than the visible 80×25 window — otherwise there's nothing "below" to scroll into, and you're back to needing a wraparound scheme or periodic real copies to reclaim space. It's a classic time/space trade: spend extra buffer memory to avoid spending CPU cycles on every scroll. Most real-mode text editors and DOS-era TSRs that felt buttery-smooth were leaning on exactly this register, not on faster memcpy.
05 — The Rest of the Register File

Everything Else the CRTC Quietly Controls

Cursor position and start offset are the two registers worth memorizing for kernel dev, but they're only a fraction of the 18-register file. The rest mostly configure the raw timing of the video signal itself — how the electron beam (on real CRT hardware) swept across and down the screen. You'll rarely touch these directly, since the BIOS or your video mode setup already programmed sane defaults, but knowing they exist demystifies a lot of "why does changing resolution involve touching so many obscure registers" later.

IndexRegisterRoughly Controls
0x00–0x01Horizontal Total / Display EndTotal scanline width and where visible pixels stop
0x06–0x07Vertical Total / OverflowTotal frame height, including off-screen retrace time
0x09Maximum Scan LineHow many scanlines make up one character's height
0x0A–0x0BCursor Start / EndWhich scanlines within a cell the hardware cursor occupies (its shape)
0x0C–0x0DStart Address High / LowWhich buffer cell maps to the top-left of the visible screen
0x0E–0x0FCursor Location High / LowWhich cell the blinking hardware cursor sits on
0x10–0x11Vertical Retrace Start / EndTiming for the "flyback" between frames

The two rows highlighted in gold — start address and cursor location — are the ones a kernel driver actually programs after boot. Everything else is display-timing plumbing that stays fixed once the video mode (80×25, Mode 3) is established, usually by BIOS before your kernel ever gets control.

Why so many timing registers at all? A CRT monitor doesn't receive "frames" the way an LCD does — it's a beam physically sweeping left-to-right, then snapping back (horizontal retrace), and top-to-bottom, then snapping back (vertical retrace). Registers like Horizontal Total and Vertical Total exist because the CRTC has to tell that beam exactly when to start, stop, and fly back for every single scanline and every single frame, dozens of times a second. Modern LCDs and VGA emulation in QEMU don't need any of this physically — they keep these registers around purely for compatibility with forty years of software that expects them to exist.
06 — Wiring This Into bob_os

What vga.c Would Need to Add

The bob_os driver you read in the previous lesson doesn't touch the CRTC at all yet — its cursor tracking (cur_row, cur_col) is purely a software variable, invisible on screen as an actual blinking marker, and its scroll() is the honest O(rows×cols) memory-copy version. Both are completely correct starting points; the CRTC registers above are the natural "next upgrade" once the basics work. Here's the shape that upgrade takes, using the same outb-based port I/O primitive every later driver in this course (keyboard, serial, disk) will also need:

/* Generic byte-wide port output — the primitive underneath every
   outb() call in this lesson. Usually lives in a small io.h/io.c. */
static inline void outb(unsigned short port, unsigned char val) {
    __asm__ volatile ("outb %0, %1" : : "a"(val), "Nd"(port));
}

#define CRTC_INDEX 0x3D4
#define CRTC_DATA  0x3D5

void vga_set_cursor(int row, int col) {
    unsigned short pos = row * VGA_COLS + col;
    outb(CRTC_INDEX, 0x0E); outb(CRTC_DATA, (pos >> 8) & 0xFF);
    outb(CRTC_INDEX, 0x0F); outb(CRTC_DATA,  pos       & 0xFF);
}

A natural place to call this: at the end of advance_cursor() and after every explicit cursor move, so the hardware cursor always tracks cur_row/cur_col instead of those variables only existing in software. That one addition turns bob_os's console from "text appears, but there's no visible caret" into something that looks and feels like a real terminal.

Why inline assembly for outb? in/out are genuine x86 machine instructions with no C equivalent — C has no built-in concept of a separate I/O address space. Every freestanding x86 kernel ends up with a tiny io.h wrapping exactly this GCC inline-asm pattern, once, and every driver from then on calls outb()/inb() like ordinary functions.
07 — Common Pitfalls

Things That Bite Everyone Once

⚠️ Forgetting the Index Write Before Every Data Write
Because 0x3D4 and 0x3D5 are two separate ports, it's tempting to write the index once and then write several data bytes in a row, assuming the CRTC "remembers." It does — but only for that one register. If you select 0x0E, write the high byte, then write the low byte without reselecting 0x0F first, you've just overwritten Cursor Location High twice and never touched Cursor Location Low at all. Every register write is always: select, then transfer — no shortcuts.
🐢 Port I/O Is Slow — Don't Do It Per-Character
Unlike a memory-mapped write, each outb/inb can cost hundreds of CPU cycles, especially inside a VM like QEMU where every port access can trap out to the emulator. Updating the hardware cursor once per printed character (rather than once per line, or once per kprintf() call) is a classic accidental performance trap in a first VGA driver — invisible on a modern host, but a real, measurable slowdown on constrained or emulated hardware.
🧠 The CRTC Doesn't Know About Your C Struct
There's no type safety here — outb(0x3D4, 0x0E) and outb(0x3D4, 14) are identical to the hardware, and a typo'd register index (say, 0x0D instead of 0x0E) silently reprograms the wrong thing — in this case, the screen's start offset instead of the cursor — with no compiler warning and no crash, just visibly wrong behavior you have to reverse-engineer from a datasheet.
08 — Quick Reference

Glossary & Key Terms

CRT Controller (CRTC)
A distinct block of VGA hardware that manages display timing, the hardware text cursor, and which part of video memory is currently visible — separate from the character buffer itself.
I/O Port
An address in x86's separate 16-bit I/O address space, reachable only via the in/out instructions, not through ordinary memory pointers.
Index/Data Register Pair
A two-port pattern (here, 0x3D4/0x3D5) letting a small number of I/O ports address a much larger internal register file: one port selects, the other transfers.
outb / inb
The conventional C wrapper function names for the x86 out and in instructions, almost always implemented with a short inline-assembly stub.
Hardware Cursor
The blinking marker the CRTC itself renders at a programmed cell position, independent of and in addition to whatever character is stored there.
Cursor Location High/Low
CRTC registers 0x0E and 0x0F, together holding the 16-bit linear cell index (row×80+col) of the hardware cursor.
Start Address High/Low
CRTC registers 0x0C and 0x0D, together holding the cell index that maps to the visible screen's top-left corner — the basis of hardware scrolling.
Hardware Scrolling
Changing what portion of a larger-than-visible buffer is displayed by updating the start address, instead of physically copying character data.
