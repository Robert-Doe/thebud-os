Writing a Minimal HTML Tokenizer State Machine

Every browser architecture diagram draws "Parse HTML" as one friendly little box: bytes go in, a DOM comes out. Crack that box open and the very first thing inside it isn't a parser in the sense you're used to — it's a finite state machine, specified so precisely by WHATWG that it names over eighty individual states, each with its own exact character-by-character behavior. Today we build a working subset of it by hand: the states, the transitions, and the tokens each one emits.

00 — First Principles

Why This Is Genuinely a State Machine, Not "A Parser"

The render-pipeline deep-dive already told you tokenization exists and roughly what it does: turn a character stream into tokens, feed those tokens to tree construction. That was the map. This page is the one stop on that map we're going to actually build — not "explain," build: a real, working, character-by-character state machine you can trace by hand.

Here's the claim worth taking literally: the WHATWG HTML Standard does not describe the tokenizer in prose that some engineer then translates into code. It is the code, written as a state machine specification: a numbered list of named states — "Data state," "Tag open state," "Tag name state," "Attribute name state," and dozens more — where each state's definition says exactly one thing: given the next input character, what do you do, and which state do you go to next. Every conformant browser engine (Blink, Gecko, WebKit) implements this same state graph, because two browsers disagreeing about which state to be in after seeing <div class=foo'bar> is exactly how you get pages that render differently per browser.

🧭 Why Not Just Use Regular Expressions?
A regex has no memory of context — it can't ask "was I already inside a quoted attribute value when I saw this >?" A state machine's entire reason to exist is exactly that: the current state is the memory. The character > means "end this tag" in Tag name state, but means "just another character" inside Attribute value (double-quoted) state — same byte, completely different meaning, decided purely by which named state you're currently sitting in. B05_html_tokenizer's own design notes put it bluntly: "HTML is not a regular language."

This also explains a structural fact that surprises people the first time they see it: the tokenizer does not know what a DOM is. It has never heard of nesting, of a "parent element," of whether a <p> is still open. It just recognizes lexical shapes — "that looked like a start tag," "that looked like plain text" — and hands a flat stream of tokens downstream to a second machine (tree construction) that actually understands structure. Splitting these two concerns is what lets tokenization stay this small and mechanical.

01 — The Cast of States

The States We're Actually Going to Need

The full spec's 80+ states cover comments, CDATA, DOCTYPE, character references, RAWTEXT for <script>/<style>, and a long tail of error-recovery branches. We're building the subset that gets you from nothing to a working start tag, end tag, and text node — the same subset B05_html_tokenizer implements. Ten states, wired together, is already enough to tokenize real markup correctly.

Data statestart state
The default. Consumes ordinary text characters into a pending Character token. Seeing < is the only thing that knocks it out of this state.
Tag open stateafter <
Just consumed <. A letter means "start tag begins here"; a / means "this is actually an end tag" and reroutes to End tag open state.
End tag open stateafter </
Just consumed </. Starts a fresh EndTag token and immediately falls into Tag name state to read the name.
Tag name statereading a name
Appends lowercase letters into the current tag token's name buffer. Whitespace → attributes may follow. > → the tag is complete, emit it now.
Before attribute name statebetween attrs
Skips whitespace, waiting for the next attribute to begin, a self-closing /, or the tag-ending >.
Attribute name statereading a key
Appends characters into the current attribute's name buffer until whitespace, =, or > ends it.
Before attribute value stateafter =
Decides which of three value states comes next, based on whether the very next character is ", ', or neither.
Attribute value (quoted) state×2 variants
Appends every character verbatim into the value buffer — including > and whitespace — until the matching quote character reappears.
After attribute value (quoted) stateclosing
Finalizes the just-closed attribute, then expects whitespace (→ next attribute) or > (→ tag complete, emit).
Self-closing start tag stateafter /
Reached after a bare / inside a tag. Sets the token's self-closing flag, then expects > to actually emit it.
"Reconsume" — the spec's favorite trick. Several real states don't consume the current character at all — they inspect it, decide it doesn't belong here, switch state, and hand that same character to the new state on the very next step. This is why the algorithm is usually phrased as "switch to the X state" rather than "consume the next character and switch." Our simplified version below sidesteps most reconsume cases by peeking before it commits, but keep the concept in your pocket — it's essential once comments and character references enter the picture.

💡 Attributes Are Tokens Too
Notice the trace never emits a standalone "attribute token" mid-tag — the name and value get assembled into buffers first, and the whole class="x" pair rides along attached to the eventual StartTag. B05_html_tokenizer's real implementation goes one step further and gives attributes their own token type, TOK_ATTR, queued up and emitted one at a time right after the TOK_START_TAG that owns them — a small design choice that keeps every emitted token a fixed, simple shape instead of one type having a variable-length attribute list bolted on.

04 — From Trace to Code

A Simplified State-Transition Function

Here's the shape a genuinely explicit-state tokenizer takes: one enum of states, one loop, one switch deciding what the current character means given the current state. This is deliberately closer to the WHATWG spec's own structure than B05's actual tokenizer.c — that file takes a shortcut (small dedicated helper functions like read_ident() that internally loop) because its scope is narrower. But the explicit-switch version below is what you'd reach for the moment you needed to add comments, CDATA, or character references without the whole thing turning into spaghetti.

state-transition skeleton, C-style pseudocodetypedef enum {
  STATE_DATA,
  STATE_TAG_OPEN,
  STATE_END_TAG_OPEN,
  STATE_TAG_NAME,
  STATE_BEFORE_ATTR_NAME,
  STATE_ATTR_NAME,
  STATE_BEFORE_ATTR_VALUE,
  STATE_ATTR_VALUE_QUOTED,
  STATE_AFTER_ATTR_VALUE
} state_t;

void run_tokenizer(const char *input, int len) {
  state_t state = STATE_DATA;
  char buf[64] = {0}; int buf_len = 0;
  char quote = 0;

  for (int i = 0; i < len; i++) {
    char c = input[i];

    switch (state) {

      case STATE_DATA:
        if (c == '<') { emit_text_if_any(buf, &buf_len); state = STATE_TAG_OPEN; }
        else                { buf[buf_len++] = c; }               // accumulate text
        break;

      case STATE_TAG_OPEN:
        if (c == '/')              state = STATE_END_TAG_OPEN;
        else if (is_letter(c)) { buf_len = 0; buf[buf_len++] = lower(c); state = STATE_TAG_NAME; }
        break;

      case STATE_TAG_NAME:
        if (is_space(c))       state = STATE_BEFORE_ATTR_NAME;
        else if (c == '>')     { emit_tag_token(buf); state = STATE_DATA; }
        else                    { buf[buf_len++] = lower(c); }        // append to tag name
        break;

      case STATE_BEFORE_ATTR_NAME:
        if (c == '>')          { emit_tag_token(buf); state = STATE_DATA; }
        else if (!is_space(c)) { buf_len = 0; buf[buf_len++] = c; state = STATE_ATTR_NAME; }
        break;

      case STATE_ATTR_NAME:
        if (c == '=')          state = STATE_BEFORE_ATTR_VALUE;
        else                    { buf[buf_len++] = c; }        // append to attr name
        break;

      case STATE_BEFORE_ATTR_VALUE:
        if (c == '"' || c == '\'') { quote = c; state = STATE_ATTR_VALUE_QUOTED; }
        break;

      case STATE_ATTR_VALUE_QUOTED:
        if (c == quote)          { commit_attribute(); state = STATE_AFTER_ATTR_VALUE; }
        else                    { append_attr_value(c); }   // even '>' and spaces are literal here
        break;

      case STATE_AFTER_ATTR_VALUE:
        if (c == '>')          { emit_tag_token(buf); state = STATE_DATA; }
        else if (is_space(c)) state = STATE_BEFORE_ATTR_NAME;
        break;
    }
  }
}

Nine cases, one loop, one character consumed per iteration. Notice what's absent: no recursion, no backtracking, no "try this pattern, fail, try another." Every branch either appends to a buffer or fires a state transition — sometimes both. That mechanical simplicity per-state is exactly why the full spec can afford to have 80+ of them: each individual state stays this small, even though the graph they form together is large.

🔍 Where B05's Real Code Diverges — and Why That's Fine
tokenizer.c's tokenizer_next() doesn't carry an explicit state_t variable at all — it uses nested while loops inside helper functions like read_ident() and read_attr_value() that implicitly encode "which state am I in" through which function is currently on the call stack. For the narrow grammar it supports (start tags, end tags, text, attributes — no comments, no character references), that's a completely reasonable simplification: fewer states means the implicit version and the explicit-switch version behave identically. The moment you need dozens of interacting states with shared reconsume logic, the explicit table above is what stops the code from becoming unmaintainable — which is exactly why the real spec is written that way.
05 — A Machine Inside the Machine

Attributes Are Their Own Little State Machine

Look back at the state list: five of the ten states we needed — Before attribute name, Attribute name, Before attribute value, Attribute value (quoted), After attribute value — exist purely to parse the stuff between a tag's name and its closing >. That's not incidental; attribute parsing genuinely is a sub-machine nested inside Tag name state, entered and exited on well-defined boundaries.

✅ Quoted Value: class="a b"

Inside Attribute value (quoted) state, everything is literal until the matching quote — including spaces, >, even another quote character of the other kind. This is exactly why href="?a=1&b=2" parses as one attribute value instead of three: the quote is the only character with special meaning in this state.

⚠️ Unquoted Value: class=x

Drop the quotes and the spec routes you into a stricter Attribute value (unquoted) state instead, where whitespace and > both end the value immediately. <div class=foo bar> means "class is foo, then a new boolean attribute bar starts" — not "class is 'foo bar'." Same tag, wildly different meaning, decided entirely by which value-state the tokenizer entered.

B05's tokenizer.c models the "queue of attribute tokens" idea directly: while scanning a start tag it collects {name, value} pairs into a small fixed-size array (pending_attrs[], capped at MAX_ATTRS), and only once the enclosing TOK_START_TAG has been returned does the very next calls to tokenizer_next() drain that queue, one TOK_ATTR token per call. It's a clean way to keep the token shape uniform — every token the caller receives is one flat struct — without ever needing a token that itself contains a variable-length list.

⚠️ The Bug Class This Precision Prevents
A parser that guesses at attribute-value boundaries instead of following the spec's exact quoted/unquoted state split is exactly the kind of divergence that creates parser differentials — the same bytes producing two different token streams depending on which implementation reads them. B05's own design notes flag this as security-relevant: an HTML sanitizer with a slightly-wrong tokenizer can approve a string as "safe," only for the real browser's spec-correct tokenizer to read the same bytes completely differently and produce a dangerous DOM. Precision here isn't pedantry — it's the whole defense.
06 — The Payoff

Why This Buys You Correctness Under Chaos

The character-by-character trace you just ran only works because every character has a defined meaning in every state — there's no "undefined behavior" branch. That completeness is what lets a tokenizer swallow real-world garbage without crashing or guessing. A few cases worth seeing explicitly:

InputWhat HappensWhich State Handles It
<div class=foo'bar>Unquoted value stops at whitespace or >; the stray ' is just another literal character in the valueAttribute value (unquoted)
<DIV CLASS="X">Tag and attribute names are lowercased on the way into the buffer — HTML tag/attr names are case-insensitive by constructionTag name / Attribute name
<br/>The bare / before > is recognized and consumed without disturbing the tag name or starting a bogus attributeSelf-closing start tag
<div >Whitespace before > with no attribute following is simply absorbed — Before attribute name state tolerates it and moves onBefore attribute name

None of these needed a special case bolted onto a happy-path parser after the fact — every single one is just the ordinary state graph doing what it always does. That's the real argument for building the tokenizer this way: correctness on the ugly 5% of real-world HTML isn't an add-on, it falls straight out of the same machine that handles the clean 95%.

✅ What This Stage Explicitly Does Not Decide
Everything above happens without the tokenizer ever asking "is this tag allowed here?" or "does an open <p> need to auto-close?" Those are tree-construction questions, answered by the second state machine downstream — the one that turns this exact token stream into a DOM, and the one already covered at the pipeline level. Tokenization's whole job stops at "here is a clean, unambiguous list of tokens." Keeping that boundary sharp is what lets each machine stay small enough to actually specify precisely.
07 — Quick Reference

Glossary & Key Terms

Tokenizer
The stage that turns a raw character stream into a flat sequence of tokens (StartTag, EndTag, Characters, ...), with no awareness of tree structure.
Finite State Machine
A model with a fixed set of named states and defined transitions between them, where the next action depends only on the current state and the current input — no memory beyond "which state am I in."
Token
One discrete unit of lexical output — e.g. StartTag div or Characters "hi" — handed from the tokenizer to tree construction.
Data State
The tokenizer's default/start state, where ordinary text is accumulated until a < signals the possible start of a tag.
Tag Open State
Entered right after consuming <; decides whether a start tag, end tag, comment, or DOCTYPE is beginning.
Attribute Name/Value States
The nested sub-machine that reads an attribute's key and value, with distinct behavior for quoted vs. unquoted values.
Self-Closing Flag
A bit set on a start-tag token when a bare / appears before >, e.g. <br/> — interpreted differently depending on the element.
Reconsume
The spec's mechanism for a state to decline the current character, switch state, and let the new state see that same character again on the next step.
