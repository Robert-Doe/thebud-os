The CSS Cascade: How the Browser Picks ONE Winning Rule

The render-pipeline deep-dive told you CSSOM parsing has to see the whole stylesheet before it can answer anything — because "which rule wins" is a global question. This is where we answer it. Not vaguely ("more specific selectors win, usually") but exactly: an ordered sequence of tiebreakers a browser runs, in a fixed order, every single time two or more rules fight over the same property on the same element.

00 — The Shape of the Problem

Every Property, On Every Element, Has Exactly One Winner

Take a single <button> on a real page. It's plausibly matched by a browser default rule, a framework's reset stylesheet, three or four of your own author rules of varying specificity, maybe a hover state, maybe a user override for accessibility. For one CSS property — say, color — every one of those matching rules might be trying to set a different value. The browser cannot average them, cannot apply "the more recent one," cannot ask you. It has to compute a single, deterministic winner, and it has to get the same answer every time, in every browser, for the exact same input. That deterministic tiebreak procedure is the cascade.

The cascade, as an ordered filter Start with every declaration for this property that matches this element → filter by origin & importance → filter by specificity → filter by source order → one survives Each stage only runs if the previous stage left a tie. The moment one candidate is strictly better, the rest are simply discarded — no further stage is even consulted.
  • Stage 1 — Origin & ImportanceWhere did this rule come from (browser default, user stylesheet, page author), and was it marked !important? This stage alone can decide the winner outright, regardless of how specific any selector is.
  • Stage 2 — SpecificityIf Stage 1 is tied, compare each rule's selector "weight" — a three-part count of IDs, classes/attributes/pseudo-classes, and element/type selectors — compared left to right like digits, never summed.
  • Stage 3 — Source OrderIf specificity is also tied exactly, the rule that appears later in the combined, document-order stylesheet wins. This is the only stage where "which came last" matters at all.

    • Notice the order. It is not "whichever selector looks scariest wins," and it's absolutely not "last one in the file always wins" — that folk wisdom is only true once you've already survived Stages 1 and 2 without a winner. Get the order backwards in your head and you'll misdiagnose real bugs for years.

    01 — Stage One

    Origin & Importance: The First, Most Powerful Filter

    Before a single selector gets measured, the cascade asks a completely different question: whose rule is this, and did they mark it non-negotiable? Three parties can supply CSS for the same page — the browser itself (user-agent defaults like "links are blue"), the user (rare today, but real: forced high-contrast or accessibility stylesheets), and the page author (your stylesheet). Each can additionally mark any declaration !important, which doesn't just "boost specificity" — it moves the declaration into an entirely separate, higher-priority bracket.

    1. 1. Author, !importantHighest normal-use priority — your own !important rules
    2. 2. User, !importantA user/accessibility stylesheet marked !important beats your !important
    3. 3. Author, normalYour ordinary page CSS — where nearly all real-world cascading happens
    4. 4. User, normalRare in practice; user stylesheets are largely a legacy feature today
    5. 5. User-agent, normalThe browser's own built-in defaults — lowest priority of all

    Yes — a user's !important rule outranks the author's !important rule. That inversion is deliberate, not a spec bug: !important exists precisely so a user forcing 200% font size or high-contrast colors for accessibility can win even against a page author who slapped !important on everything. B06_css_cascade's own design notes call this out directly — developers who assume "!important means nothing can override this" are wrong, and the spec is intentionally built that way.

    Where do inline styles and the real UA !important tier fit? A style="..." attribute on the element itself behaves like an extra-high-specificity author declaration — it beats every selector-based author rule (short of !important). And the full W3C spec technically adds a sixth tier above even user !important: user-agent !important, reserved for a tiny number of browser-enforced rules that pages truly cannot override. We're skipping it here because — like B06_css_cascade's own cascade() implementation — it almost never matters in practice; the five tiers above cover essentially every real cascade decision you'll debug.
    ⚠️ Importance Beats Specificity — Always, No Exceptions
    A one-line, zero-specificity-effort !important declaration beats a monstrous #id .a .b .c .d selector with normal weight, every time, because Stage 1 finishes the whole cascade before Stage 2 (specificity) is ever consulted. This is exactly why !important is treated as a last resort in real codebases: it doesn't just win a fight, it makes the entire specificity system for that declaration irrelevant.

    Put actual numbers on that claim so it's not just an assertion. Two rules, both author-origin, both targeting the same <p class="text">:

    RuleSpecificityImportant?Stage 1 BracketResult
    #article .text { color: blue; }(1, 1, 0)no3 — author, normalloses
    .text { color: red !important; }(0, 1, 0)yes1 — author, !importantWINS

    Read the specificity column in isolation and #article .text looks like the obvious winner — an ID beats a bare class, full stop. But specificity is Stage 2, and these two rules never make it that far: the !important rule sits in Stage 1's bracket 1 (author, important), while the other sits in bracket 3 (author, normal). Stage 1 alone separates them, so Stage 2's tuple comparison — the one column that would have favored the ID selector — is never even computed. This is the single most common source of "but my selector is more specific, why isn't it winning?" bug reports.

    02 — Stage Two

    Specificity: A Genuine Numeric Comparison

    Once origin and importance tie — which, for two rules both living in your own stylesheet, they always do — the cascade needs a way to say "this selector is more specific than that one," mechanically, with no ambiguity. The spec's answer is a three-part tuple, one count per selector-component category:

    Specificity as an ordered triple (IDs, classes/attributes/pseudo-classes, type-selectors/pseudo-elements) Written (a, b, c) in the spec. Compared left to right, one column at a time — the first column where the counts differ decides the winner outright.
    Selector PieceCounts TowardExample
    ID selectora (ids)#submit-btn
    Class selectorb (classes).btn
    Attribute selectorb (classes)[type="submit"]
    Pseudo-classb (classes):hover, :nth-child(2)
    Type / element selectorc (elements)button, div
    Pseudo-elementc (elements)::before, ::after
    Universal selector *contributes nothing*
    Combinatorscontribute nothing> + ~ (descendant space)

    Here's the detail that trips people up and the reason B06_css_cascade's own DECISIONS.md spends an entire entry defending it: this tuple is never collapsed into one number. It is genuinely wrong — not just inelegant — to compute something like ids*100 + classes*10 + elements and compare the results as plain integers.

    why single-integer specificity is a real bug, not a style nitpick// WRONG — collapses the triple into one weighted integer
int bad_specificity(specificity_t s) {
    return s.ids * 100 + s.classes * 10 + s.elements;
}

// A selector with 11+ class components overflows the "classes" digit
// and starts polluting the "ids" digit — producing a FALSE id-level match:
// .a.b.c.d.e.f.g.h.i.j.k  -->  11 classes  -->  11*10 = 110
// bad_specificity() reports 110, which LOOKS bigger than a real #id (100)
// even though a real ID selector must always outrank any number of classes.

// CORRECT — compare the tuple component by component, left to right
int spec_cmp(specificity_t a, specificity_t b) {
    if (a.ids != b.ids)         return a.ids > b.ids ? 1 : -1;
    if (a.classes != b.classes) return a.classes > b.classes ? 1 : -1;
    if (a.elements != b.elements) return a.elements > b.elements ? 1 : -1;
    return 0;   // truly tied — Stage 3 (source order) decides
}

    Eleven chained classes is a contrived example, but the principle it protects is not: an ID selector must outrank any number of classes, and a class selector must outrank any number of bare element selectors — unconditionally. A tuple comparison guarantees that. A weighted sum only guarantees it until someone's selector gets long enough to carry a digit into the next column, at which point the browser would rank a wall of classes above a real ID — visibly wrong, and different from what every real browser actually does.

    🔢 Try It: Compute a Tuple by Hand
    #nav ul li.active a:hover → one ID (#nav), two classes-tier selectors (.active, :hover), three element-tier selectors (ul, li, a) → specificity (1, 2, 3). Compare that against .sidebar .active → (0, 2, 0). First column: 1 vs 0 — #nav ul li.active a:hover wins immediately. The remaining columns are never even inspected, because the comparison already resolved in column one.
    03 — Stage Three

    Source Order: The Tiebreaker of Last Resort

    If two competing declarations survive both Stage 1 (same origin, same importance) and Stage 2 (an identical specificity tuple — not just "close," identical in all three columns), the cascade falls back to the one rule that actually is about ordering: whichever declaration appears later, in the fully merged, document-order stylesheet, wins. "Merged" matters — every <link>, every <style> block, and every rule inside each, are treated as one continuous sequence in the order the browser encountered them.

    A genuine tie, resolved .notice.info { color: teal; } /* specificity (0,2,0) */ .notice.warn { color: goldenrod; } /* specificity (0,2,0) — declared later */ If an element matches both classes, .notice.warn wins — not because "warn" beats "info" in any selector sense, but purely because it was the last declaration parsed with an identical (0,2,0) specificity.

    This is also the stage responsible for the single most common piece of CSS folk wisdom — "just move your override to the bottom of the file" — and exactly why that trick sometimes mysteriously stops working: it only breaks the tie when the two rules already had equal specificity. Move a .button rule below a #submit-btn rule in the file and nothing changes, because Stage 2 already resolved the fight in the ID selector's favor before source order was ever consulted.

    📌 "Later in the File" Includes Media Queries and @imports
    A rule inside a currently-inactive @media block still occupies a position in source order — it just isn't a candidate at all unless its condition matches the current viewport. Once a media query does match, its rules slot into the cascade at their actual position in the merged stylesheet, exactly as if the @media wrapper weren't there.
    04 — Full Worked Example

    Four Rules Walk Into a <button>

    Here's the whole algorithm run end to end on one real element. Assume this markup and these four author rules — all normal priority, no !important anywhere, all living in the same author stylesheet in this exact order:

    markup<button id="submit-btn" class="btn primary">Submit</button>
    competing rules, in source order/* Rule A — line 12 */
button          { color: white; }

/* Rule B — line 45 */
.btn            { color: navy; }

/* Rule C — line 90 */
.primary.btn    { color: green; }

/* Rule D — line 6 (earlier in the file, but shown last for effect) */
#submit-btn     { color: gold; }

    All four match. All four set color. Origin and importance are identical for all four (author, normal), so Stage 1 produces a four-way tie and specificity has to break it. Computing each tuple:

    RuleSelectorIDsClassesElementsSpecificityResult
    Abutton001(0, 0, 1)loses
    B.btn010(0, 1, 0)loses
    C.primary.btn020(0, 2, 0)loses
    D#submit-btn100(1, 0, 0)WINS

    Rule D wins with color: gold — despite being declared first in the file (line 6, before all three others), and despite Rule C having more total selector components (two classes vs. D's one ID). Neither of those facts matter, because the very first column of the comparison — IDs — already separates D (1) from everyone else (0). Rules A, B, and C never even get compared against each other; the moment D exists as a candidate with a strictly higher first-column count, the fight is over.

    ✅ The Two Misconceptions This Example Kills
    "The last rule in the file always wins" — false; D was first and still won. "More classes beats fewer classes" — false, or rather irrelevant here; ID beats any number of classes, unconditionally, every time, because ids is compared before classes even gets a look. Both misconceptions come from skipping straight to Stage 3 or misreading Stage 2's tuple as a simple count of "selector complexity."

    06 — A Different Mechanism Entirely

    Inheritance Is Not the Cascade

    One last, important distinction, because these two ideas get merged in people's heads constantly: the cascade decides which declared rule wins when multiple rules explicitly target the same element. Inheritance is what happens when no rule targets an element at all for a given property. They're separate mechanisms that happen to run back to back.

    The actual order of operations, per property, per element 1. Run the cascade — is there a winning declared value? Use it.
    2. If not, does this property inherit? Use the parent's computed value.
    3. If not, fall back to the property's own initial (spec-defined default) value. Inheritance is Step 2 — a fallback the browser only reaches once the cascade in Step 1 comes up completely empty for that element and property.

    Not every property inherits. The spec picks this per property, based on what tends to make visual sense flowing down a tree: text-related properties overwhelmingly do; box-model properties overwhelmingly don't. Set color on a <div> and every plain-text descendant inside it — with no CSS of its own — renders in that color, because color is an inherited property and the cascade found nothing more specific for those descendants. Set border on that same <div>, and its children get no border at all, because border does not inherit — it falls through straight to its initial value (none) instead.

    ✅ Commonly Inherited

    color, font-family, font-size, line-height, visibility, text-align, list-style — properties where "look like your parent unless told otherwise" is almost always what an author wants.

    ❌ Never Inherited by Default

    margin, padding, border, width, height, background, display, position — box-model and layout properties, where a child silently copying its parent's spacing would almost always be wrong.
    🔑 The Explicit Escape Hatch: the inherit Keyword
    Any property, inheriting or not, can be forced to inherit anyway with the literal value inherit — e.g. border: inherit;. This isn't inheritance happening automatically; it's a normal cascade winner (a declared value, just like any other) whose value happens to mean "go copy whatever the parent's computed value is." It still goes through Stage 1–3 like any other declaration — it just wins the cascade and then defers to the inheritance mechanism by name.
    07 — Quick Reference

    Glossary & Key Terms

    Cascade
    The ordered algorithm — origin/importance, then specificity, then source order — that picks exactly one winning declaration per property, per element.
    Specificity
    A three-part tuple (IDs, classes/attrs/pseudo-classes, types/pseudo-elements) measuring a selector's precision, compared column by column, never summed into one number.
    Origin
    Which of the three stylesheet sources a rule came from — user-agent (browser default), user, or author (the page) — checked before specificity.
    !important
    A flag that moves a declaration into a higher-priority bracket, ahead of specificity entirely; a user's !important still outranks an author's.
    Source Order
    The final tiebreaker: when origin, importance, and specificity are all identical, the declaration parsed later in the merged stylesheet wins.
    Inherited Property
    A property (like color or font-family) that, absent any cascade winner, takes its parent's computed value instead of its own initial value.
    Computed Value
    The final value a property resolves to for an element after cascade, inheritance, and initial-value fallback have all been applied.
    User-Agent Stylesheet
    The browser's own built-in default CSS (e.g. "links are blue, h1 is bold") — the lowest-priority origin in the cascade.
