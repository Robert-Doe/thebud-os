00 — Where We Left Off

The Wall Was Never Optional — So How Does It Break?

In the last module, the wall looked absolute: a CPU register tracks your privilege level, privileged instructions are simply refused below Ring 0, and the only sanctioned crossing is a syscall trap into a fixed kernel entry point. All true. And yet — every year, security researchers and attackers find real, working ways past it. Not by breaking the rule that Ring 3 code can't execute privileged instructions. That rule genuinely never bends. Instead, they find ways to make Ring 0 itself do something it shouldn't, on the attacker's behalf, or they find a channel the ring model never accounted for in the first place.

This page is a tour of three real categories of wall-breaking, each fundamentally different from the others: tricking the kernel (privilege escalation via software bugs), eavesdropping on the kernel without ever asking it anything (Meltdown and Spectre), and attacking a fence that was never made of hardware to begin with (container and VM escapes). By the end, "the wall" will feel a lot less like a single line and a lot more like a whole perimeter with different kinds of gates, cameras, and blind spots.

01 — Tricking the Waiter Into Robbing the Kitchen

What Privilege Escalation Actually Means

Strip away the jargon and privilege escalation means exactly this: Ring 3 code finds a bug that makes Ring 0 code execute instructions, or touch memory, that the Ring 3 caller was never authorized to cause. The attacker never flips their own privilege bit — they can't, the hardware forbids it. Instead they get the already-privileged kernel to do the dirty work for them, by exploiting a mistake in the kernel's own logic.

This is a categorically different problem than anything in the last module. There, every syscall step assumed the kernel does its job correctly — validates arguments, copies data safely, checks permissions. Privilege escalation lives entirely in the gap between "the kernel is supposed to validate" and "the kernel's validation code has a bug." Security researchers gave this gap a name back in 1988: Norm Hardy called it the confused deputy problem — a more-privileged program (the "deputy," here the kernel) that gets tricked by a less-privileged party into misusing its own authority.

🧠 The Confused Deputy, Stated Precisely
A deputy is confused when it has two things mixed up: which code is running versus whose authority that code should be acting under. The kernel always runs with full Ring 0 authority — that part never changes. The bug is when the kernel fails to check that the specific action it's about to take, on behalf of this specific caller, is something that caller was actually allowed to ask for. The waiter didn't stop being a waiter; the waiter just got tricked into handing a customer the keys to the walk-in freezer because nobody checked the customer's ID against the order.

In real kernels, the confused-deputy gap opens up through a small number of recurring bug classes. Let's walk through the single most common one, honestly, in simplified but technically accurate pseudo-C.

simplified linux-style syscall handler// A syscall that copies a user-supplied preferences blob
// into a fixed-size kernel buffer. Somewhere, this pattern
// is the root cause behind an enormous fraction of real CVEs.
long sys_update_prefs(char __user *ptr, size_t len) {
    char kbuf[128];              // lives on the KERNEL stack

    // BUG: len came straight from Ring 3. Nothing here checks
    // that len <= sizeof(kbuf) before trusting it.
    copy_from_user(kbuf, ptr, len);

    apply_prefs(kbuf);
    return 0;
}

Walk through what happens if an attacker calls this syscall with len = 4096 instead of the expected ≤128. copy_from_user — a real, ubiquitous kernel helper whose entire job is safely moving bytes across the wall — will happily copy 4096 attacker-controlled bytes into a 128-byte kernel stack buffer, because nothing told it not to. That overflow doesn't stay politely inside kbuf. It marches straight over adjacent kernel stack memory: saved registers, other local variables, and — depending on the exact stack layout — a saved return address. Overwrite that return address with an address the attacker chose, and when this function returns, the CPU doesn't go back to the caller. It jumps to wherever the attacker pointed it — still running in Ring 0, because privilege level was never touched, only the instruction pointer was hijacked.

⚠️ This Is Not a Hypothetical Bug Class
The pattern above — an unchecked, user-controlled length or pointer flowing into a fixed-size kernel buffer — maps directly onto real CWE categories that show up in kernel CVE databases every single month: CWE-787 (out-of-bounds write), CWE-190 (integer overflow that later causes an undersized allocation), and CWE-416 (use-after-free, where a kernel object is freed but a stale pointer to it is used again later — often from a completely different, attacker-triggered code path). Every one of these is the same underlying failure: the kernel trusted something from Ring 3 that it should have re-verified.

Use-after-free deserves its own beat, because it doesn't even require an oversized buffer. The kernel allocates an object, some code path frees it (the memory is returned to the allocator, available for reuse), but a stale pointer to that same memory survives somewhere else in the kernel. If an attacker can force the kernel to reallocate that freed memory for something they control — say, by rapidly opening and closing file descriptors in a specific pattern — the stale pointer now points at attacker-controlled data. The next time the kernel dereferences that "trusted" internal pointer, it's actually reading (or worse, calling through) memory the attacker wrote. No overflow required at all — just a race between freeing and reusing.

Why the kernel stack, specifically? Every thread that enters Ring 0 gets its own small, fixed-size kernel stack (commonly 8–16 KB on Linux) — much smaller than a typical user-space stack. That tight size is exactly why a modest, attacker-controlled overflow can reach something valuable (a saved return address, a function pointer) so quickly. It's also why kernel code is written far more defensively around buffer sizes than the average user-space application.

Why this doesn't just work anymore, unmodified

The naive "overwrite return address, jump to a chosen address" recipe above described exploitation as it worked in the 1990s and early 2000s. Modern CPUs and kernels layer real hardware-and-software defenses directly on top of the ring model to make each step harder, without touching the ring boundary itself:

DefenseLayerWhat It Actually Blocks
SMEPCPU hardwareSupervisor Mode Execution Prevention — the CPU refuses to execute code that lives on a user-space page while running in Ring 0, even if a kernel bug redirects execution there.
SMAPCPU hardwareSupervisor Mode Access Prevention — the CPU refuses ordinary Ring-0 reads/writes to user-space memory unless the kernel explicitly opts in for that access (as copy_from_user legitimately does).
KASLRKernel + boot loaderKernel Address Space Layout Randomization — randomizes where kernel code and data actually sit in memory each boot, so an attacker's hijacked return address can't just be a fixed, known constant.
Stack canariesCompilerA random guard value placed just before a saved return address; the function checks it's unchanged before returning, catching many linear stack-buffer overflows before the corrupted return address is ever used.

None of these defenses fix the underlying bug — the missing bounds check in sys_update_prefs is still there. What they do is make each downstream step of turning that bug into working Ring-0 code execution dramatically harder, which is exactly why modern kernel exploits are usually chains of several bugs (one to leak a KASLR-defeating address, one to corrupt memory, sometimes a third to bypass SMEP/SMAP) rather than the single clean overflow shown above.

02 — This Actually Happened, Repeatedly

Named Vulnerabilities, Real Years, Real CVEs

"Confused deputy" isn't an abstract diagram — it's the root cause note on some of the most famous vulnerability disclosures in OS history. Here are four, each a slightly different flavor of the same underlying idea: the kernel trusted a caller it shouldn't have.

Dirty COWCVE-2016-5195
A race condition in the Linux kernel's copy-on-write memory handling. By racing a write to a read-only, memory-mapped file against the kernel's own COW logic, an unprivileged local user could win the race and obtain write access to files they should only be able to read — including files owned by root. Public for roughly nine years before it was found and fixed.
race conditionTOCTOU2016
Dirty PipeCVE-2022-0847
An uninitialized flag in the Linux pipe buffer implementation let an unprivileged process overwrite data in read-only files cached in the page cache — including /etc/passwd-class files — without needing any special permission. Widely described as "Dirty COW's simpler, meaner sequel."
uninitialized state2022
PwnKitCVE-2021-4034
A memory-corruption bug in Polkit's pkexec helper (a setuid-root binary present on nearly every major Linux distribution) let a local, completely unprivileged user go straight to a root shell, by manipulating environment variables passed into the vulnerable code. Sat unnoticed for over a decade.
setuid binarymemory corruption2021
runc EscapeCVE-2019-5736
A flaw in the runc container runtime (used by Docker and Kubernetes) let a malicious container overwrite the host's own runc binary via /proc/self/exe, achieving root code execution on the host — not just inside the container. A preview of the container-escape territory two sections from now.
container escape2019
💡 The Pattern Behind the Pattern
Notice none of these four needed a hardware flaw. Every one is a software bug in code that was, in principle, supposed to check something and didn't (or checked it correctly, but at the wrong moment — Dirty COW's race window is exactly a gap in timing of a correct-looking check). This is why privilege escalation bugs keep getting found: the kernel is millions of lines of C, handling input from every untrusted program on the machine, and every single syscall handler is a new opportunity for a confused deputy.
03 — When the Hardware Itself Is the Leak

Meltdown & Spectre: A Wall With No Bug In It

Everything so far has been a software mistake — fixable, in principle, by writing more careful kernel code. In January 2018, researchers disclosed something categorically different: Meltdown (CVE-2017-5754) and Spectre (CVE-2017-5753, CVE-2017-5715). These weren't bugs in any operating system's code at all. They were consequences of a performance trick built into the CPU silicon itself — a trick nearly every modern processor uses, and had used for over a decade before anyone realized it leaked data across the ring boundary.

Why CPUs guess the future

Modern CPUs don't execute your instructions strictly one at a time, in order, waiting for each to fully finish. That would waste enormous amounts of time — a conditional branch might depend on a value that's still being fetched from memory, and memory is thousands of times slower than the CPU core. So instead, the CPU does speculative execution: when it hits a branch whose outcome isn't known yet, it guesses (using a branch predictor trained on the program's recent history), and starts executing instructions down the guessed path before it knows if the guess is right — all "out of order," ahead of where the program has officially gotten to.

Most of the time the guess is correct, and the CPU just saved a huge amount of time. When the guess is wrong, the CPU throws away the speculative work: it discards the results, restores registers to their pre-guess values, and resumes down the correct path instead. From the program's point of view — its architectural state, meaning registers and memory as the program is allowed to observe them — it's as if the wrong-guess instructions never ran at all.

🎯 The Sentence That Explains Both Attacks
Rolling back a speculative instruction's architectural effects does not roll back its microarchitectural side effects — and the CPU cache is a microarchitectural side effect. If a speculatively-executed instruction touched a piece of memory, that memory's cache line stays loaded in the cache even after the CPU decides the instruction "never happened." That residue is measurable, from Ring 3, using nothing but a stopwatch.

The actual leak mechanism: Flush+Reload

Here's the concrete recipe, simplified but technically honest, for how Meltdown reads Ring-0 memory from Ring 3. It relies on one basic hardware fact: reading data that's already in the CPU cache takes a few nanoseconds; reading data that isn't cached takes closer to a hundred nanoseconds — a difference easily measurable in software.

  1. Prepare a 256-entry probe arrayThe attacker allocates an array with 256 distinct pages (one per possible byte value, 0–255), and makes sure none of them are currently in the CPU cache (a "flush" step).
  2. Speculatively read a forbidden byteThe attacker sets up code so a branch misprediction causes the CPU to speculatively execute a load from kernel memory it has no permission to read — the secret byte. On pre-patch Intel CPUs, the permission check for this load happened, but too late: the speculative execution had already raced ahead using the value before the fault was raised.
  3. Use the secret to index the probe arrayStill purely speculatively, the code computes probe_array[secret_byte * 4096] and touches it — a completely ordinary-looking array access, except secret_byte is data the attacker was never allowed to see. This touch pulls exactly one of the 256 pages into cache.
  4. Architectural rollback (the part everyone thought was safe)The CPU eventually notices the permission fault / branch misprediction and rolls back: the register holding secret_byte is wiped, no exception-visible value ever reaches the program, nothing observable in the "official" execution changed.
  5. Reload — measure, don't askThe attacker now times an access to each of the 256 probe-array pages. 255 of them are slow (not cached). Exactly one is fast — the one speculatively touched in step 3. Its index is the secret byte, recovered one bit-pattern at a time, entirely through timing, with zero privileged instructions and zero data that ever "officially" crossed the wall.
▶ Trace one byte leaking through the cache-timing side channel
Why this is fundamentally not a software bug architectural rollback ≠ microarchitectural rollback Every optimization the CPU makes to go faster — caching, branch prediction, out-of-order execution — leaves traces outside the part of the machine the ring model was designed to protect. The ring boundary governs which instructions may run and which memory may be architecturally read. It says nothing about cache state, and nobody designed it to.

Spectre (two variants: v1, bounds-check bypass, and v2, branch target injection) generalizes this even further. Rather than exploiting a permission-check race like Meltdown, Spectre tricks the branch predictor itself into speculatively executing code that was never supposed to run at all — for example, training the predictor with many in-bounds array accesses so it "expects" the next access to be in-bounds too, then supplying an out-of-bounds index right when a security check should have blocked it. Because the branch predictor is shared hardware, Spectre can leak data across process boundaries entirely — famously demonstrated reading one browser tab's memory from JavaScript running in another tab's sandboxed process, no kernel bug and no syscall involved anywhere.

So how was this fixed, if it's not a bug? It wasn't "fixed" so much as mitigated, at real cost. KPTI (Kernel Page Table Isolation) makes kernel memory mappings mostly invisible to user-space page tables entirely, so there's nothing sensitive left to speculatively read (this is part of why syscalls got measurably slower after early 2018 patches). Retpolines and other compiler mitigations reshape branches so the predictor has nothing useful to hijack. New CPU generations added hardware fixes. None of this touches the ring model itself — it's all patching around a hardware side channel the ring model was never built to see.
Meltdown and Spectre aren't the only hardware side channel. Rowhammer (first documented in 2014) is a related but distinct hardware failure mode: rapidly, repeatedly reading the same row of DRAM can cause electrical interference that flips bits in a physically adjacent row you never touched or had permission to write. Combined with careful memory-layout tricks, Rowhammer has been used to flip bits inside page-table entries themselves — turning a memory-timing quirk into full privilege escalation, no software bug required at all. Same family of lesson: physics doesn't know what a ring is.
04 — Modern Isolation, Modern Failure Modes

Container Escapes vs VM Escapes

Everything up to now assumed two worlds: Ring 3 and Ring 0. Modern cloud infrastructure adds two more isolation boundaries on top of that — containers and virtual machines — and it matters enormously, from a security standpoint, that these are built completely differently from each other.

A container is not a hardware boundary

A "container" (Docker, a Kubernetes pod, an LXC instance) is not a new privilege ring. There is no CPU hardware that knows what a container is. A container is a software-level fence constructed entirely out of ordinary Linux kernel features: namespaces (which give a process group its own private view of process IDs, network interfaces, mount points, and hostnames) and cgroups (which cap how much CPU, memory, and I/O a group of processes may consume). Every container on a given host is, from the CPU's point of view, just an ordinary Ring 3 process — tagged with different namespace IDs, but scheduled by the exact same kernel, sharing the exact same Ring 0.

📌 The Consequence, Stated Plainly
Because every container on a host shares one literal kernel, a single kernel bug — the same confused-deputy privilege-escalation category from Section 01 — can let code in one container affect the host, or another container entirely. That's exactly what CVE-2019-5736 (the runc escape from Section 02) did: a container process overwrote the host's own container-runtime binary. There was never a hardware wall between "container A" and "the host" — only a software fence maintained by the one kernel both of them depend on.

A VM adds a genuinely new hardware ring

A virtual machine is built differently, using CPU features specifically designed for this: Intel's VT-x and AMD's AMD-V. These extensions introduce a new hardware-enforced mode, formally called VMX operation, split into VMX root (where the hypervisor runs) and VMX non-root (where every guest VM runs — including the guest's own "Ring 0" kernel). Because the hypervisor in VMX root can trap and intercept privileged operations attempted by a guest's Ring 0, informally this extra layer gets called "Ring -1." A guest kernel genuinely believes it's running at full Ring 0 privilege — and for most purposes it is — but sensitive hardware operations still get intercepted and mediated one level further out, by the hypervisor.

🐳 Container Escape

Attack surface: the entire host kernel's syscall table, since containers make real syscalls into the real shared kernel. Any confused-deputy bug anywhere in that huge, shared attack surface is a potential escape route. This is why container security leans so heavily on additional software layers — seccomp syscall filtering, AppArmor/SELinux mandatory access control — stacked on top of namespaces, because namespaces alone were never a hardware guarantee.

🖥️ VM Escape

Attack surface: a much smaller, purpose-built hypervisor plus whatever hardware devices it emulates for the guest (virtual disk controllers, virtual network cards). A real historical example: VENOM (CVE-2015-3456), a buffer overflow in QEMU's emulated virtual floppy disk controller, that let a guest VM execute code on the host. Rarer than container escapes, and considered architecturally more serious, because it requires defeating hardware-assisted isolation, not just a shared-kernel software fence.

This is the honest, precise answer to "why is a VM escape a bigger deal than a container escape": a container escape needs one bug in a kernel every tenant already shares direct syscall access to. A VM escape needs a bug in the comparatively small slice of code — the hypervisor and its device emulation — that hardware virtualization extensions specifically wall off as "Ring -1," behind an entire additional layer the CPU itself enforces. More layers, smaller surface, rarer breaks — but never impossible, as VENOM and its relatives prove.

The industry's answer: microVMs, splitting the difference

Once cloud providers internalized that "container isolation = shared-kernel isolation," a whole category of hybrid sandboxes emerged specifically to close that gap without paying the full weight of a traditional VM. gVisor (used inside Google Cloud) intercepts a container's syscalls in user space and re-implements a large chunk of the Linux kernel interface itself, in a sandboxed process, so most syscalls never actually reach the real host kernel at all — shrinking the confused-deputy attack surface back down without spinning up real hardware virtualization. Kata Containers and AWS's Firecracker take the opposite approach: give every container its own real, lightweight VM — complete with VT-x/AMD-V's "Ring -1" boundary — but strip the virtual hardware down to almost nothing, so boot times stay near-container speed while escape now requires defeating an actual hypervisor, not just a shared kernel. AWS Lambda runs on Firecracker microVMs for exactly this reason: container-like density, VM-like isolation.

05 — Tying It Back

Every Attack, In Restaurant Terms

The original module's analogy holds up remarkably well under attack — because every category above is just a different way of abusing the same waiter-and-kitchen relationship, not a reason to throw the analogy out.

Confused deputy → bribing the waiter Meltdown/Spectre → reading the order tickets through the wall Container escape → a fake wall between two dining rooms, same kitchen VM escape → sneaking past the building's actual front security desk

Privilege escalation is convincing the waiter to walk an oversized, malformed order straight into the kitchen without checking it against what the customer was actually allowed to request — the waiter still only goes where waiters go, but they've been tricked into personally handing the customer a set of kitchen keys along the way. Meltdown and Spectre are not bribing anyone at all — they're standing just outside the kitchen door, and noticing that you can tell what's cooking by listening to how long the pans take to heat up, without the kitchen staff ever handing you anything or even knowing you're listening.

Container escapes are what happens when a franchise puts two "separate" restaurants in the same physical building, dividing the dining rooms with a curtain instead of a wall, while both kitchens are actually the same one kitchen underneath. A confused deputy in that one shared kitchen doesn't just affect one dining room — it can reach both. VM escapes are the harder case: each "restaurant" here has its own real building, its own real kitchen, its own real locked door — but they all sit inside one larger complex with one property manager (the hypervisor) who holds a master key to every building. Escaping your own restaurant isn't enough; you'd need to defeat the property manager's own security too.

✅ The One Idea That Survives All Four Attacks
Every wall in this whole series — Ring 3/Ring 0, namespaces, VMX root/non-root — is a trust boundary that has to be actively enforced by something, every single time. Hardware rings are enforced by silicon and almost never fail outright, but the software built on top of them (kernel syscall handlers) can still be tricked. Software-only boundaries (namespaces) inherit every bug in the one kernel underneath them. And even flawless enforcement of "what may run" (rings) says nothing about "what can be measured" (cache timing) — which is exactly the gap Meltdown and Spectre live in. Security here isn't one wall; it's a stack of walls, and each layer has to be evaluated on its own terms.
06 — Quick Reference

Glossary & Key Terms

Privilege Escalation
Getting code to execute with more authority than it was granted — typically by exploiting a bug that makes an already-privileged component (like the kernel) act on an attacker's behalf without proper checks.
Confused Deputy
A 1988 term (Norm Hardy) for a more-privileged program tricked by a less-privileged caller into misusing its own authority — the root-cause pattern behind most kernel privilege-escalation bugs.
Use-After-Free (CWE-416)
A bug where freed memory is reused while a stale pointer to it still exists elsewhere — letting an attacker who controls the reallocated memory hijack the stale pointer's next use.
Speculative Execution
A CPU performance technique: executing instructions ahead of a not-yet-resolved branch, guessing the outcome, and discarding the results if the guess was wrong — while cache state from the discarded work is not rolled back.
Architectural vs Microarchitectural State
Architectural state (registers, memory as the program officially sees it) is what gets rolled back after a misprediction. Microarchitectural state (cache contents, branch predictor history) is not — and that gap is the entire Meltdown/Spectre attack surface.
Flush+Reload
The core cache-timing side-channel technique: evict data from cache, let a victim (or speculative execution) touch it conditionally on a secret, then measure access time to infer whether that data is now cached.
Meltdown (CVE-2017-5754)
A speculative-execution attack exploiting a race between a speculative load of privileged memory and its permission check, on affected pre-2018-patch CPUs — leaked via cache timing.
Spectre (CVE-2017-5753 / -5715)
A family of attacks that mistrain the CPU's branch predictor into speculatively executing attacker-chosen code paths, leaking data across process and sandbox boundaries via the same cache-timing channel as Meltdown.
Namespaces & cgroups
The Linux kernel features containers are built from: namespaces give a process group its own private view of PIDs/network/mounts; cgroups cap its resource usage. Both are software fences inside one shared kernel — not a hardware ring.
VT-x / AMD-V
Hardware virtualization extensions that add VMX root (hypervisor) and VMX non-root (guest) operation modes — a genuine, hardware-enforced privilege layer beyond the classic four rings, informally "Ring -1."
Container Escape
Code inside a container affecting the host or another container, typically via a bug in the one kernel every container on the host shares — e.g. CVE-2019-5736 in runc.
VM Escape
Guest code breaking out to execute on the host, requiring a bug in the hypervisor or its emulated devices rather than just the guest's own kernel — e.g. VENOM, CVE-2015-3456.
