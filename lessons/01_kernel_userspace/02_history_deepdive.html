Why the Wall
Exists

You already know the wall: Ring 0 for the kernel, Ring 3 for everything else, one guarded door between them. What you haven't seen yet is the fifty years of scars that put it there — machines where a single stray pointer could corrupt the entire room-sized computer, a timesharing system that accidentally handed every user the master password file, and one Cornell graduate student's late-night experiment that took down a tenth of the internet in a single evening. This is the history the wall is built from.

00 — Where We Left Off

Same Wall, Deeper Question

In the companion piece, you learned the shape of the wall as it exists today: user space in Ring 3 with no direct hardware access, kernel space in Ring 0 with total trust, and the system call as the single sanctioned door between them, enforced by the CPU chip itself. That's the geography. This page is about the history — because the wall wasn't handed down from a textbook. It was built, piece by piece, over about three decades, almost entirely in response to things going wrong.

Here's the question this page actually answers: if hardware-enforced privilege separation is so obviously necessary, why didn't the very first computers already have it? The honest answer is that it wasn't obvious at all — for the first fifteen-odd years of electronic computing, nobody needed it, because nobody had the problem it solves. Watching exactly when and why that changed is the fastest way to actually understand what the wall is for, instead of just what it is.

01 — Before Any Wall Existed

Computers With No Wall At All

Picture a computer with exactly one program loaded into memory at any given moment — no other process, no background daemon, not even really an "operating system" in the modern sense, just a small resident piece of bootstrap code called a resident monitor that loaded the next job off tape or cards. That's not a simplified teaching example. That's a literal, accurate description of mainstream computing from the early 1950s into the mid-1960s.

On the pre-360 machines, "no protection" wasn't a missing feature so much as a concept that hadn't been invented yet. There was only ever one program resident, so the very idea of one program's memory being off-limits to another didn't have anything to apply to. The danger wasn't other users — it was that the resident monitor itself sat in the same flat, checkable-by-nothing memory as the job it was running. A wild pointer write, an off-by-one in an array, a bug in a loop counter — any of these could just as easily land on the monitor's own instructions as on the job's private data, because the hardware had no concept of "yours" versus "mine" versus "the operating system's."

⚠️ What "No Protection" Actually Meant, Concretely
When a job on a 704 or 7090 went haywire — an infinite loop, a corrupted return address, a scribbled-over monitor — there was no fault handler to catch it, because there was no hardware mechanism to detect a boundary violation in the first place. The usual outcome was the machine simply stopped doing anything useful: hung, looped forever, or executed garbage as instructions. An operator physically walked up to the console, and using front-panel switches, manually reloaded the bootstrap loader and restarted the monitor from scratch. This was not a rare edge case. It was Tuesday.
The entire trust model of the batch era, in one line Everything currently loaded into memory = fully trusted. No exceptions, no checks, no rings. This isn't a simplification for the reader — it's a literally accurate description of how the 704, 709, 7090, and early PDP machines worked at the hardware level.
Wait — if only one program ran at a time, who was there to protect against? This is exactly the right question, and the answer is: nobody, yet — which is precisely why nobody built protection hardware. The threat wasn't a rival program or a rival user; it was the running program's own bugs corrupting the very monitor that was supposed to clean up after it and load the next job. That distinction — "protect the system from bugs" versus "protect users from each other" — is the hinge this whole page turns on. Keep it in mind for the next section.
02 — The Invention That Forced the Wall

When Sharing a Machine Became Dangerous

Mainframes in the early 1960s were staggeringly expensive — a 7094 cost roughly the same as a small building — and batch processing wasted most of that expense on people standing in line. You'd submit your punch-card deck, wait hours (sometimes overnight) for your turn, get a printout back, and discover your one-character typo three hours later. Someone was going to try to fix this by letting multiple people use the same machine at the same time, interactively, through teletypes. That someone was Fernando Corbató's team at MIT, and the system was the Compatible Time-Sharing System (CTSS), running on a modified IBM 7094, first demonstrated in 1961.

This single change — from "one program owns the whole machine for its whole run" to "several different people's programs are resident in memory simultaneously, time-sliced by the second" — is the actual moment the threat model shifts. It's no longer just "protect the monitor from this job's bugs." It's now "protect User A's memory, files, and privacy from User B" — where B might be careless, might be curious, or might simply be a stranger B has never met and has no reason to trust.

  1. The problem CTSS had to solveWith several users' programs sitting in core memory at once, the 7094 needed a way to stop User A's program from simply reading or overwriting the memory holding User B's program — something the hardware had never needed to do before.
  2. The primitive solution: bounds registersMIT had IBM add a pair of hardware registers marking off the start and end of the currently-running user's memory region. Before switching to a different user's timeslice, the monitor reloaded these registers to point at the new user's region.
  3. The check happens on every single memory accessAny address the running program touched was compared against the bounds registers in hardware. Step outside your assigned region, and the machine trapped — refusing the access — instead of silently corrupting whatever happened to be there.
  4. This is the direct ancestor of everything that followedOne contiguous bounds-checked region per user is crude — no fine-grained permissions, no concept of "read but don't write," nothing like a page table. But the core idea — hardware refuses an access outside an authorized boundary — is exactly the same idea a modern MMU enforces billions of times a second.
💡 The Aha Moment
Memory protection wasn't invented because someone drew it on a whiteboard as good engineering practice. It was invented because timesharing made the old honor system physically dangerous. The moment two mutually-untrusting users' code could occupy the same machine at the same instant, "please don't touch each other's memory" stopped being a reasonable policy and started being a hardware requirement.

CTSS proved timesharing worked, and its direct successor took security far more seriously. Multics (MULTiplexed Information and Computing Service) — a joint project between MIT, Bell Labs, and General Electric starting in 1965, running on the GE-645 and later the Honeywell 6180 — was designed from the ground up with security as a first-class goal, not an afterthought. It introduced a hierarchical file system with per-file access control lists, segmented virtual memory, and, critically, a formal ring-based protection architecture supporting up to eight concentric privilege rings in hardware, though most real deployments only used a handful of them. Sound familiar? It should — when Intel's engineers designed protected mode over a decade later, they borrowed the ring terminology directly from Multics.

⚠️ A Concrete Lesson From CTSS Itself
In 1965, a CTSS operator was editing the system's message-of-the-day file at the same moment another administrator was editing the master password file, using an editor that generated temporary files by name in a shared, predictable location. A race condition in how those temp files were created caused the two files to swap contents — and for a period, every user who logged in was shown the plaintext contents of the master password file instead of the greeting message. Nobody planned this. It just fell out of a shared, timesliced, insufficiently isolated system. It's one of the earliest documented computer security incidents on record, and it's exactly the kind of accident that hardware-enforced isolation exists to make structurally impossible rather than merely unlikely.
03 — Watching x86 Learn the Lesson

Watching the Wall Get Built, Chip by Chip

Here's the twist: the lessons above were learned on exotic, expensive mainframes and minicomputers throughout the 1960s and 70s. The processor family that ended up running most of the world's desktops and servers — Intel's x86 line — started from scratch, on cheap commodity silicon, and had to relearn every one of those lessons from zero. Watching x86 evolve across three chip generations is watching the wall get bolted on in real time, mistake by mistake.

▶ Pick a chip generation to watch what happens when a program reaches somewhere it shouldn't

8086/8088 (1978/1979) — real mode, and nothing else

The chip that became the original IBM PC's brain in 1981 had zero privilege levels. Not "a weak version of protection" — none. Memory addressing worked via 16-bit segment:offset pairs giving a 20-bit, 1MB total address space, and every single piece of code running on the machine — the OS, a driver, your own program — had exactly the same, total access to everything. MS-DOS on the 8088 wasn't really "an operating system enforcing boundaries" so much as a flat, cooperative program launcher: any running application could reach directly into DOS's own memory, or into another resident program's memory, and there was no hardware anywhere in the chip capable of noticing, let alone stopping it.

80286 (1982) — protection arrives, but it's clumsy

Intel's 80286 introduced protected mode: four privilege rings (0 through 3, terminology lifted straight from Multics), segment descriptors carrying access rights that the hardware checked on every access, and even primitive hardware-assisted task switching. This was real, genuine progress — a Ring 3 program executing a privileged instruction would now be refused. But it was also famously awkward to actually use: segments were still capped at 64KB each with a 16MB total physical ceiling, there was still no paging (protection was purely segment-based, not a general virtual-memory system), and — the detail every systems engineer of the era remembers — there was no clean, documented way to get back out of protected mode into real mode without resetting the entire CPU. IBM's actual shipped workaround involved pulsing the keyboard controller to trigger a CPU reset and using a spare byte of RAM to remember where to jump back to. Given all that friction, most real-world software — DOS included — mostly just ignored 80286 protected mode.

80386 (1985) — the architecture we still run today

The 80386 is the real hinge point. It kept the same four rings as the 286, but added two things that actually made the wall usable: full 32-bit flat addressing (no more juggling 64KB segments to reach more memory), and a genuine hardware paging unit — a page table rooted at a new control register, CR3, translating 4KB virtual pages to physical frames, checked and enforced by the CPU's memory management unit on every access, independent of the ring check. It also added Virtual 8086 mode, letting a protected-mode OS run old real-mode DOS software safely, sandboxed, as if it still had the whole 8086 to itself. This combination — hardware rings for privilege, hardware paging for per-process memory isolation — is, largely unchanged in its fundamentals, still exactly what Linux and Windows do today, just extended from 32 bits to 64.

🧠 Where "Ring 0" and "Ring 3" Actually Come From
When you read "Ring 0" and "Ring 3" in the companion piece, you're reading vocabulary that traveled a specific, traceable path: Multics designed a formal ring architecture in the mid-1960s to enforce security on a timesharing mainframe → Intel's engineers explicitly borrowed that terminology and concept when designing the 80286's protected mode in 1982 → the 80386 made it actually practical by pairing it with real paging in 1985 → x86-64 inherited it essentially unchanged. The words in today's kernel documentation are, quite literally, Multics's words.
04 — What Happens When the Lesson Isn't Learned

The Night 10% of the Internet Got Infected

By 1988, Unix systems had proper user/kernel separation, multi-user protection, and file permissions — the wall, in some form, already existed. So what happened on the night of November 2, 1988 is a different kind of lesson: it shows that the wall protects processes from each other, but it says nothing about what happens when a program the wall correctly trusts gets tricked by input it should never have trusted.

Robert Tappan Morris, a graduate student at Cornell, released a self-replicating program onto the early internet — intended, by his own later account, as a research experiment to gauge the network's size, not as an attack. It combined several separate vulnerabilities into one chain:

  1. A buffer overflow in fingerdThe Unix "finger" daemon — a privileged network service running with elevated rights — had a fixed-size stack buffer and no bounds checking on input length. The worm sent an oversized request that overflowed the buffer, overwriting the return address and hijacking control flow to run injected code with fingerd's own privileges. This is one of the first widely-documented real-world buffer overflow exploits.
  2. A debug backdoor in sendmailSendmail shipped with a DEBUG command meant purely for developer testing, which let a remote sender specify an arbitrary program to pipe mail into — unintentionally giving anyone who knew about it a way to run commands on the machine remotely.
  3. Weak, guessable passwordsThe worm carried a small built-in dictionary of common passwords and simply tried them against real accounts — a depressing number of which worked.
  4. Transitive .rhosts trustUnix machines of the era often trusted specific remote hosts implicitly via .rhosts files, allowing password-free logins between "trusted" machines. Once inside one machine, the worm used these trust relationships to hop to others without needing to guess anything at all.
⚠️ The Bug That Turned an Experiment Into a Catastrophe
Morris didn't want the worm to be obviously detectable, so it was designed to avoid re-infecting a machine it had already infected. But to prevent someone from defending against it simply by running a fake "already infected" signal, he made it re-infect anyway on a fraction of attempts — and that fraction was tuned too aggressively. The result: machines got hit over and over, spawning more and more copies of the worm process until they buckled under the load. What was meant to be a quiet measurement became, functionally, a self-inflicted denial-of-service attack on a huge slice of the internet.

✅ What Ring 0 / Ring 3 Would Have Stopped

One user-space process directly reading or corrupting another process's private memory. A Ring 3 program executing a privileged instruction to reprogram hardware directly. These are exactly the failure modes hardware-enforced rings and paging exist to make structurally impossible.

⚠️ What the Wall Never Promised to Stop

fingerd and sendmail were privileged, correctly-trusted system services doing exactly what they were designed to do. The wall doesn't protect a trusted service from being fooled by malicious input it was never taught to distrust — that's a separate discipline entirely: input validation, least privilege, and defense in depth.
✅ The Aftermath Actually Changed the Industry
Within weeks of the outbreak, DARPA funded the creation of the Computer Emergency Response Team (CERT) at Carnegie Mellon University — the first formal, organized incident-response body of its kind, and the direct ancestor of today's CERT/CC and the entire modern security-response industry. The Morris Worm is widely cited as the single event that moved computer security from a niche academic curiosity into a mainstream, funded engineering discipline.
05 — Tying It Back to Ring 0 / Ring 3

The Wall You Know Is Fifty Years in the Making

Put the whole arc together and the modern picture stops looking like an arbitrary design choice and starts looking inevitable — the accumulated, hard-won answer to a sequence of very specific, very real failures.

  • 1961
    CTSS goes live at MIT
    The first practical timesharing system. Multiple users resident in memory at once forces the first hardware memory-bounds checks into existence.
  • 1964
    IBM System/360 ships with storage protection keys
    The first mainstream hardware memory protection — aimed at surviving multiprogramming, a first crack in the "everything is trusted" wall.
  • 1965
    Multics begins, with security as a first-class goal
    MIT, Bell Labs, and GE design a formal ring-based protection architecture and access-controlled file system — the direct ancestor of "Ring 0" and "Ring 3."
  • 1978
    Intel 8086 ships
    16-bit, real mode only, zero privilege levels — none of Multics's lessons have reached commodity silicon yet.
  • 1982
    Intel 80286 ships
    Protected mode arrives — four rings, borrowed straight from Multics's terminology — but segment-only, capped, and awkward to actually use.
  • 1985
    Intel 80386 ships
    Full 32-bit flat addressing plus hardware paging via CR3 — the architecture Windows NT and Linux still build on today.
  • 1988
    The Morris Worm infects ~10% of the internet
    A hardware wall around the kernel says nothing about what a privileged service does with input it was never taught to distrust.
  • 1988
    CERT founded at Carnegie Mellon
    DARPA-funded, organized incident response is born — the industry's direct answer to the previous line on this timeline.

So when you read "the system call is the only door into the kernel, guarded by hardware, not by politeness" in the companion piece, you're reading the punchline to this entire history. It's hardware-enforced specifically because the honor system was tried first, on real machines, with real users — and it failed, repeatedly, in ways that ranged from an operator walking up to reload a bootstrap loader by hand, to an accidental password leak on CTSS, to a tenth of the entire internet grinding to a halt in one night. Ring 0 and Ring 3 aren't a clever abstraction dreamed up in the abstract. They're a scar.

💡 The Final Aha Moment
Try to imagine actually sitting down at a 1959 IBM 7090. There is no login prompt, because there is no concept of "users" the machine distinguishes between. There is no crash recovery, because there is no fault handler — a bad pointer write just is what happens next, silently, whatever it touches. There is no permission-denied error, because there is no permission system. Every single one of the boring, invisible guarantees you rely on today — that your browser tab crashing doesn't take down your terminal, that another logged-in user can't read your files, that a webpage's JavaScript can't reformat your disk — is the direct, hard-won descendant of the machines and incidents on this page.
06 — Quick Reference

Glossary & Key Terms

Resident Monitor
The small piece of software present in early batch machines that sequenced jobs — the closest thing to an "OS" before protection existed, and itself unprotected from the job it was running.
Bounds / Base-Limit Registers
CTSS-era hardware registers marking off one user's memory region, checked on every access — the primordial ancestor of the modern MMU's page-table checks.
CTSS
Compatible Time-Sharing System — MIT, 1961, the first practical timesharing system, running on a modified IBM 7094. Forced the first hardware memory protection into existence.
Multics
MIT/Bell Labs/GE project starting 1965; designed formal ring-based protection and access-controlled files as first-class goals. Direct ancestor of x86's Ring 0/Ring 3 terminology.
Real Mode
The 8086's only operating mode: flat segment:offset addressing, no privilege levels, no memory protection of any kind.
Protected Mode
Introduced on the 80286: four hardware privilege rings and segment-descriptor access checks. Made genuinely practical only once the 80386 added paging.
Paging / MMU (CR3)
The 80386's hardware page-table mechanism, rooted at the CR3 register, translating 4KB virtual pages to physical frames and enforcing per-process memory isolation.
Storage Protection Key
IBM System/360's 1964 mechanism tagging 2KB memory blocks with a 4-bit key, checked against the running program's key — the first mainstream hardware memory protection.
Buffer Overflow
Writing past the end of a fixed-size buffer, overwriting adjacent memory (often a return address) to hijack control flow. The core exploit behind the Morris Worm's fingerd attack.
CERT
Computer Emergency Response Team — founded at Carnegie Mellon in late 1988, funded by DARPA, directly in response to the Morris Worm. The first organized OS/network security incident-response body.
