00 — The Distinction Everything Else Depends On

API vs ABI

You already know POSIX standardizes an API — an Application Programming Interface, a source-level contract. "Source-level" is the key phrase: an API is a promise about what happens when you compile against it. Call open() with the right arguments, get the documented behavior back — but you find that out by feeding your .c file through a compiler and linker targeting a specific system, every time, for every target.

An ABI — Application Binary Interface — is a completely different, much stricter promise: a contract about what happens when you run an already-compiled binary, with zero recompilation, on a given system. It covers things a C source file never even mentions: the exact numeric syscall number the CPU's syscall/int 0x80 instruction is given, which registers arguments go in, how the return value comes back, the binary file format (ELF, Mach-O, PE) the loader expects, structure layouts and alignment, calling conventions for function calls. None of that is visible in your C source — the compiler fills all of it in, silently, according to whatever ABI it's targeting.

The one-line distinction API: recompile against it. ABI: run the same binary against it, unmodified, forever. POSIX standardizes only the first. Each kernel is on its own for the second.

🔑 Why the Distinction Matters So Much
Every time you rebuild your project, you're re-negotiating the API contract fresh — the compiler checks it for you, and mismatches are loud, immediate, and cheap. The ABI contract is negotiated once, silently, at compile time, and then has to keep holding forever, for a binary nobody may ever recompile again. That asymmetry — cheap-to-fix-if-broken vs impossible-to-fix-once-shipped — is exactly why ABI stability is the harder, scarier promise of the two.

Why the compiler can't rescue you from an ABI break

It's worth being precise about why recompiling doesn't help an already-shipped binary. The compiler only ever sees your source code at the moment you build. It has no way to reach back in time and fix binaries that were compiled and handed out years earlier — those bytes are frozen, and whatever assumptions about syscall numbers and calling conventions were baked into them at build time are the assumptions they'll carry for as long as they exist. An ABI promise is fundamentally a promise made to the past, not just to the present:

what's actually frozen inside a compiled binary; x86-64 Linux — this is roughly what open() compiles down to
mov rax, 2          ; syscall number for open() — frozen, forever, in THIS binary's bytes
mov rdi, path_ptr   ; 1st arg register — frozen by the calling convention at compile time
mov rsi, flags      ; 2nd arg register — same
syscall              ; trap into the kernel — whatever kernel happens to be running

That mov rax, 2 is not a reference to a symbol the linker resolves later — it's a literal number, burned into the machine code the day the binary was compiled. There is no version of "the kernel changed, so let this old binary's baked-in 2 mean something different now" that doesn't require either recompiling the binary (impossible if you've lost the source, or the vendor vanished) or the kernel keeping slot 2 meaning exactly what it always meant. Real kernels choose the second option, permanently.

01 — The Promise, Concretely

Linux's "We Do Not Break Userspace" Rule

Linux's kernel maintainers, and Linus Torvalds most famously and repeatedly, have enforced a rule that goes beyond anything POSIX requires: a change to the kernel that causes an existing user-space program to stop working correctly is a kernel bug — full stop — regardless of whether the program was relying on "undocumented" or "technically unspecified" behavior. If real programs depended on it and it used to work, and a kernel change makes it stop working, the kernel change is reverted or fixed, not the program.

This is a much stronger commitment than POSIX conformance. POSIX only promises that documented, specified behavior stays correct. "Never break userspace" promises that whatever a real program actually observed and came to depend on — documented or not — keeps working. It's an engineering culture decision layered on top of, and going beyond, what any specification requires.

💡 What This Buys You, Concretely
A statically-linked Linux binary compiled in the early 1990s can, in principle, still be executed correctly by a Linux kernel built this year. Not "recompiled and it happens to work" — the exact same bytes, unmodified, still produce correct behavior, because the syscall numbers it calls and the calling convention it uses have not moved, even though nearly every line of the kernel's internal implementation has been rewritten multiple times over since.

Why this is a genuinely huge, ongoing engineering commitment

It's easy to state the rule in one sentence and easy to underestimate how much work it costs to keep. Every one of the 450+ entries in Linux's syscall table is a permanent, unretractable promise the moment it ships to a stable kernel release — the kernel can add new syscalls freely, but essentially never remove or renumber an old one, because some binary out there, possibly one nobody working on the kernel has ever seen, might still be calling it by that exact number.

😬 What Breaking the Promise Looks Like

A kernel update ships. An old game, an old scientific tool, an old statically-linked binary someone's business still depends on, suddenly segfaults or misbehaves — not because it was doing anything wrong, but because a syscall's structure layout shifted, or a return-value edge case changed. Users can't fix their binary; they can only distrust future kernel updates.

✅ What Keeping It Looks Like

When a syscall's behavior genuinely needs to evolve — say, a data structure needs new fields — the kernel adds a new syscall number (e.g. stat() → stat64() → statx()) rather than repurposing the old one, and keeps the old syscall number working exactly as it always did, indefinitely, for anyone still calling it.

Who this promise is actually for

"Never break userspace" can sound like an abstract point of engineering pride until you list out who's actually depending on it in practice:

  • Commercial software with no available source — old games, old CAD tools, old scientific instruments' control software, shipped as a binary only, whose original vendor may no longer exist to recompile anything.
  • Large enterprises running unmaintained internal tools — a payroll or inventory system built decades ago that nobody currently on staff knows how to safely rebuild, but that still needs to run correctly on servers patched for security every month.
  • Container images with pinned, ancient base layers — a container built once, years ago, still deployed unchanged today, executing on a host kernel that's been upgraded dozens of times since.
  • Embedded and appliance firmware — devices in the field that will never receive a userspace software update again, but whose host kernel (if it's Linux-based) may still receive security patches for years.

03 — How the Promise Is Actually Kept

The Mechanics of ABI Stability

"Never change a syscall number" is the headline rule, but real kernel evolution needs more tools than just freezing numbers forever. Here's the actual toolkit real kernels use to keep the promise while still moving forward.

  1. Additive-only syscall tableNew functionality gets a new syscall number appended to the table. The old number, if it still exists, keeps its old behavior forever. The table only ever grows, never shrinks — a permanent, monotonically-increasing record of every promise the kernel has ever made.
  2. Compat syscalls for changed structuresWhen a data structure genuinely needs to change shape (say, a 32-bit field needs to become 64-bit to survive past the year 2038), the kernel adds a parallel syscall — like stat() alongside stat64() alongside statx() — rather than silently changing what the original returns. Old callers keep calling the old entry and keep getting the old, correctly-shaped answer.
  3. Symbol versioning in the C libraryEven one layer up, glibc uses versioned symbols so that a binary linked against an older library version keeps calling the older (ABI-compatible) implementation of a function, while newly-compiled code gets the newer one — both coexisting in the same library file, resolved at load time based on which version the binary was actually linked against.
  4. Regression is treated as a release blockerIf a kernel change is found to break a real userspace program during testing, the default response is to revert or fix the kernel change — not to tell the program to adapt — regardless of whether the program was relying on strictly-documented behavior. "It was never guaranteed" is explicitly not an accepted excuse if real software broke.
🧠 This Is Also Why the Kernel's Internal APIs Are Allowed to Churn Wildly
Linux famously does not promise a stable internal kernel API for things like driver interfaces between kernel modules — those change release to release, sometimes drastically, and out-of-tree drivers frequently break. The stability promise is drawn at exactly one boundary: the syscall interface facing user space. Everything on the kernel-internal side of that line is free to be rewritten at will, precisely because the boundary itself never moves.

One ABI per architecture, each stable on its own terms

There's a wrinkle worth being precise about: "the syscall ABI" isn't one single global numbering — it's one numbering per CPU architecture, each frozen independently. open()'s syscall number is not a universal constant; it's whatever number that architecture's ABI assigned it, kept stable forever within that architecture.

Architectureopen() Syscall NumberWhy It Differs
x86 (32-bit, i386)5The original Linux syscall table ordering, dating to the early 1990s
x86-642Renumbered from scratch when the 64-bit syscall table was designed, deliberately decoupled from the 32-bit numbering
ARM64 (AArch64)no direct open() — openat() onlyNewer architectures were given a cleaned-up, smaller "generic" syscall table that dropped several legacy variants entirely

None of this is a contradiction of "never break userspace" — it's the same promise, scoped correctly. A given x86-64 binary's mov rax, 2 only ever needs to keep meaning open() on x86-64 kernels; it was never going to run on an ARM64 kernel unmodified anyway, because CPU instruction sets themselves aren't compatible across architectures in the first place. The ABI promise is "stable within an architecture, forever," not "identical across every architecture that has ever existed."

Even the trap mechanism itself has changed — and old binaries still work

Here's a detail that makes the stability promise even more impressive: the actual CPU instruction used to enter the kernel on x86 has changed more than once, and old 32-bit Linux binaries still run correctly today anyway.

EraTrap MechanismWhat Happened to Old Binaries
Original 32-bit Linuxint 0x80 software interruptStill works today — the kernel still honors it
Faster 32-bit path (Pentium II era)sysenter instruction, exposed via the vDSOBinaries recompiled to use it got a speed boost; old int 0x80 binaries kept working unmodified

The trick making this possible is the vDSO (virtual dynamic shared object) — a small piece of code the kernel maps into every process's address space that picks the fastest available trap mechanism for the current CPU, so most binaries never hard-code a specific instruction at all. For the ones that do (old, statically-linked, hand-written-in-assembly binaries using raw int 0x80), the kernel simply keeps that path alive as a slower but fully correct fallback, indefinitely.

The compat-syscall pattern, with real names

"Add a new syscall instead of changing the old one" sounds abstract until you see the actual lineage. Linux's stat() family is the textbook example — three generations of the same conceptual operation, all still present in a modern kernel, none of them removed:

SyscallIntroduced BecauseStill Callable Today?

📌 Notice What Never Happens in That Table
Nowhere does the kernel go back and change what stat() itself returns, or repurpose syscall number 4 (its slot on x86-64) to mean something new. The table only ever grows sideways. A binary from any era keeps calling whichever generation of the family it was compiled against, and keeps getting exactly the behavior it always got.
04 — The Process Behind the Promise

How the Kernel Community Actually Defends This

A rule is only as real as the process that enforces it. "Never break userspace" isn't kept alive by good intentions alone — it's backed by a set of concrete engineering practices baked into how kernel patches get merged, tested, and reviewed before they ever reach a stable release.

  1. Extensive automated fuzzing of the syscall surfaceTools like syzkaller continuously throw huge volumes of malformed and edge-case syscall arguments at development kernels, hunting for crashes or behavioral changes long before a change reaches ordinary users.
  2. A staging area before anything is considered stablePatches flow through maintainer trees and a integration branch (linux-next) for real-world testing across a huge range of hardware and workloads before merging into a release that distributions will actually ship.
  3. Regressions are release-blocking, by policyIf a change is reported to break a previously-working userspace program during any point in this process, the default, expected response is to revert the offending change — the burden of proof is on the change, not on the program it broke.
  4. Torvalds himself has personally enforced this, repeatedly, in publicThere's a well-known pattern of blunt, public kernel-mailing-list pushback whenever a patch is found to have broken a real userspace program, regardless of how "technically correct" or how small the change seemed — reinforcing the rule as a cultural norm, not just a written policy.
⚠️ The Uncomfortable Part of This Promise
This process only catches breaks in software the testing process actually exercises. The much scarier failure mode is a change that breaks some obscure, low-traffic corner of the ABI that nobody tests, silently, until years later someone's ancient but critical binary hits it in production. That risk is exactly why the bias is so strongly toward never touching existing behavior at all, rather than trusting testing to catch every possible regression before release.
A useful mental model: think of the syscall ABI as a public API with a userbase the maintainers can never fully enumerate, let alone contact. Ordinary software teams get to say "we're deprecating this, please migrate by such-and-such date." The Linux kernel, in practice, cannot say that credibly for any already-shipped syscall — it has no reliable way to reach everyone who might be relying on it, so the only safe default is to assume someone, somewhere, still is.
05 — Where POSIX Fits (and Doesn't)

What POSIX Doesn't Cover Here

It's tempting to assume POSIX is "the thing that makes old binaries keep running," since it's the most famous Unix standard. It isn't — and understanding exactly where its scope ends is the whole point of this lesson.

POSIX standardizes open()'s source-level behavior: what arguments it takes, what it must return, what errno values are legal. It says absolutely nothing about which raw syscall number an open() call compiles down to, which register the path pointer goes in, or how the return value is passed back to the caller. Those are pure implementation details — POSIX leaves them entirely to each operating system to decide, and explicitly does not require any two POSIX-conformant systems to agree on them at all.

📜 What POSIX Promises

Your C source code, recompiled fresh for each target, calling open(), behaves identically on any conformant system. This is an API-level, source-level, recompile-required guarantee.

🧬 What POSIX Never Promised

That a binary compiled on Linux runs on FreeBSD without recompiling — their raw syscall numbers and calling conventions are completely different and always have been, despite both exposing the identical POSIX open() source-level contract.

So the two promises stack, but they're independent, made by different parties, at different layers: POSIX (a standards committee) guarantees your source means the same thing everywhere it's conformant. Each individual kernel (Linux's maintainers, FreeBSD's, XNU's) separately, voluntarily, and at real ongoing cost, guarantees that binaries already compiled against its own ABI keep working on its own future versions. One is a portability promise across systems; the other is a durability promise across time, made by a single system to itself.

Worth noting: this is exactly why "POSIX-compliant" was never a synonym for "binary compatible." A Linux binary and a FreeBSD binary can both call the POSIX-standardized open() in their source form and both be fully conformant — while remaining completely unable to run on each other's kernel unmodified, because the ABI underneath was never part of the deal.

This split explains a fact that otherwise looks contradictory: compatibility layers like Linux's own binfmt_misc mechanism, or FreeBSD's historical Linux-binary-compatibility mode, exist specifically to bridge exactly this ABI gap between otherwise-POSIX-equivalent systems. They work by having one kernel learn to recognize and correctly translate another kernel's syscall numbers and calling convention into its own — extra engineering effort spent precisely because POSIX conformance on both sides never automatically bought binary compatibility between them.

06 — Tying It Back

ABI Stability, bob_os-Sized

Look at syscall.h and syscall.c in module 28: every syscall bob_os exposes has a fixed numeric ID that user_entry.asm loads into a register before trapping into the kernel, and syscall.c's dispatch table maps that number straight to a handler function. That numeric ID, and the register convention around it, is bob_os's own tiny syscall ABI — informal and unversioned, but structurally the same idea as Linux's syscall table.

If a future version of bob_os renumbered SYS_OPEN from, say, 2 to 7 without updating every already-compiled user program, every existing bob_os binary calling open() would silently start invoking whatever handler now lives at slot 2 instead — with no compiler error to catch it, because the mismatch lives entirely at the binary level, invisible to source code. That's the exact failure mode real kernels spend enormous engineering effort avoiding.

💡 The Practical Takeaway
Even a small teaching kernel accumulates the same obligation a production kernel has, the moment more than one compiled user-space binary exists: syscall numbers, once assigned and shipped, become a promise to keep, not a detail to casually renumber. POSIX conformance (module 28's posix.c layer) and ABI stability (module 28's fixed syscall numbers in syscall.h) are two separate disciplines bob_os practices side by side — exactly as real operating systems do.

bob_os gets to sidestep the hardest part of the real-world problem, and it's worth being explicit about why: there is exactly one bob_os kernel version in existence at a time, and no independent third party has ever shipped a compiled bob_os binary that this project doesn't control. Real kernels carry this promise for an unknown, unbounded population of binaries compiled by people the kernel maintainers will never meet, running purposes the maintainers can't anticipate, which is precisely why "never break userspace" has to be treated as an inviolable rule rather than a best-effort guideline — there's no way to know in advance which old syscall number some critical, unmaintained binary out in the world still depends on.

Small as this project is, the habit is worth building now, because it's exactly the habit that scales up into "never break userspace" the moment a kernel has real users depending on it.

07 — Quick Reference

Glossary & Key Terms

API
Application Programming Interface — a source-level contract, checked and enforced at compile time. What POSIX standardizes.
ABI
Application Binary Interface — a binary-level contract: syscall numbers, calling conventions, struct layouts, and file formats an already-compiled program depends on at run time.
Syscall Number
The fixed integer identifying which kernel operation a trap instruction is requesting — the load-bearing constant of any syscall ABI.
Calling Convention
The agreed-upon rule for which registers or stack slots hold arguments and return values across a function or syscall boundary.
"Never Break Userspace"
Linux's engineering culture rule: a kernel change that stops an existing user-space binary from working is a kernel bug, regardless of whether the binary relied on documented behavior.
Compat Syscall
A new syscall added alongside an old one (e.g. statx() beside stat()) so a changed data shape doesn't require breaking existing callers of the original.
Symbol Versioning
A C library technique letting multiple ABI-compatible versions of the same function name coexist in one shared library, so old binaries keep resolving to the version they were built against.
Statically Linked Binary
A binary with all its library code baked in at compile time — it depends only on the kernel's syscall ABI, not on any particular version of a shared library, making it an especially strong test of long-term ABI stability.
Regression
A change that breaks previously-working behavior. In Linux kernel development, any regression affecting real userspace is treated as a bug to be fixed, not a spec technicality to argue about.
Trap Frame / syscall Instruction
The CPU mechanism (e.g. x86-64's syscall instruction) that transitions from user mode into the kernel's syscall dispatcher, carrying the syscall number and arguments in registers per the ABI's calling convention.
Dispatch Table
The kernel's array mapping each syscall number to its handler function — the concrete data structure that makes the syscall-number promise real, in bob_os's syscall.c and in every production kernel alike.
Fuzzing (syzkaller)
Automated testing that generates huge volumes of malformed or edge-case syscall input to catch crashes and behavioral regressions before a kernel change reaches a stable release.
Binary Compatibility Layer
A mechanism (like Linux's binfmt_misc or FreeBSD's Linux-compat mode) that lets one kernel recognize and translate another kernel's syscall ABI, bridging a gap POSIX conformance alone never closes.
