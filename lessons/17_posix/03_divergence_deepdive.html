00 — Setting Up the Puzzle

POSIX Leaves Gaps On Purpose

The first lesson in this module made the case that POSIX is a contract, not an implementation — it standardizes behavior, not mechanism. This lesson is about the direct consequence of that design choice: POSIX explicitly, deliberately, leaves huge categories of behavior unspecified or implementation-defined. Not as an oversight — as the entire point. A standard that pinned down everything wouldn't leave room for a monolithic kernel, a hybrid kernel, and radically different filesystem and scheduler designs to all still qualify as conformant.

The pattern this lesson is about Same POSIX call. Same documented return value. Completely different strace output underneath. Because POSIX only ever graded the outside — see the explainer lesson for why.

Three big categories of legitimate divergence exist between fully POSIX-conformant systems:

  • Unspecified internal mechanism — the exact scheduling algorithm, the exact filesystem's on-disk layout and performance characteristics. POSIX defines the observable contract of read()/write(), never how fast or in what internal order a filesystem actually satisfies it.
  • Non-standard extensions — a kernel is completely free to expose extra, powerful functions beyond the POSIX baseline, as long as the required POSIX functions keep behaving correctly alongside them. This is where epoll() and kqueue() come from.
  • Userland tooling conventions — POSIX specifies a required baseline behavior for utilities like ps and ls, but says nothing about the extra flags, output formatting, or convenience options vendors bolt on top.

01 — Case Study #0

Same Scheduling Classes, Different Schedulers

Before getting to the flashier non-standard extensions, it's worth grounding the "unspecified internal mechanism" category in something POSIX does touch, but only loosely: real-time scheduling classes. POSIX.1b defines a small set of scheduling policy names a program can request — SCHED_FIFO (strict priority, run-to-completion), SCHED_RR (priority with round-robin time-slicing), and SCHED_OTHER (whatever the system's normal, non-real-time default is). Every conformant system must recognize these names and honor their broad behavioral contract. None of them specify an actual algorithm for SCHED_OTHER — the default policy nearly every ordinary process actually runs under.

SystemDefault (SCHED_OTHER) SchedulerCore Idea
LinuxCFS (Completely Fair Scheduler), replaced by EEVDF in newer kernelsModels "fair" CPU share using a virtual-runtime clock per task, red-black tree of runnable tasks

macOS (XNU)Mach-derived multilevel feedback queuePriority bands adjusted dynamically based on recent CPU usage and I/O behavior, plus QoS-class hints from the app layer

A program that just calls fork() and lets the default scheduler handle things is fully portable — POSIX guarantees it gets some reasonable, fair-ish share of the CPU on any conformant system. What it can't portably assume is which order two equal-priority processes run in from moment to moment, or exactly how quickly one starved process gets its next turn — that timing behavior is a genuinely different, independently-engineered algorithm on each of the three systems above.

📜 What's Actually Portable

Requesting SCHED_FIFO or SCHED_RR by name, setting a numeric priority within the POSIX-defined range, calling sched_yield() — all guaranteed to exist and behave per spec on any conformant system.

🎲 What Was Never Portable

Assuming a specific latency before a starved process runs, assuming two equal-priority processes alternate in strict turns, or tuning behavior around one scheduler's specific internal heuristics — none of that survives a move to a different conformant kernel.
🔑 The Filesystem Version of the Same Story
Identical pattern, different subsystem: POSIX guarantees write() followed by read() at the same offset returns what you wrote, and specifies rename's atomicity guarantees — but says nothing about on-disk layout, journaling strategy, or default case sensitivity. Linux's ext4/btrfs, a BSD's UFS/ZFS, and macOS's APFS are three separately engineered filesystems, with APFS notably shipping case-insensitive by default on new Macs — behavior a portable POSIX program should never assume, and a genuinely common source of real bugs when Linux-authored code gets ported carelessly.

This is also why benchmarking "filesystem speed" across operating systems is a notoriously misleading exercise: you're never comparing POSIX against POSIX, you're comparing one specific on-disk data structure and caching strategy against another, underneath an identical, unhelpful-for-this-purpose read()/write() contract. POSIX conformance tells you the two filesystems agree on correctness; it tells you nothing at all about which one is faster for a given workload.

02 — Case Study #1

epoll() vs kqueue() vs poll()/select()

POSIX standardizes exactly two ways to wait on multiple file descriptors at once: select() and poll(). Both work by handing the kernel a list (or bitmask, for select()) of file descriptors every single time you call them, and the kernel scans the whole list and tells you which ones are ready. That's fully portable, fully POSIX, and — at high descriptor counts, the kind a busy network server sees — genuinely slow, because the cost of each call grows with the number of descriptors you're watching, even if only one of ten thousand actually became ready.

Real-world high-performance servers don't use plain poll()/select() for exactly that reason — and this is where the divergence becomes concrete and strace-visible. Linux added a completely non-POSIX extension, epoll(), that lets the kernel maintain the watch list internally and hand back only the descriptors that became ready, in roughly constant time regardless of how many you're watching. The BSDs (and macOS, inheriting from BSD) never adopted epoll() — they built their own answer years earlier, kqueue(), which solves the same performance problem with a different API shape and broader scope (it can watch file descriptors, but also processes, signals, and filesystem changes through the same mechanism).

🐧 Linux

epoll_create(), epoll_ctl(), epoll_wait() — a Linux-only extension, not in POSIX at all. This is what nginx, Node.js's libuv, and Redis actually use on Linux under the hood.

👹 BSD

kqueue() + kevent() — originated on FreeBSD, a different non-POSIX extension solving the same class of problem with a single generalized event-queue API.

🍎 macOS

Also kqueue() — inherited straight from its BSD ancestry (more on this in the next section), plus Apple's own higher-level wrapper, Grand Central Dispatch, built on top of it.

⚠️ Why This Is Exactly the Kind of Divergence POSIX Allows
All three systems still implement poll() and select() correctly, per the standard — a program using only those calls is fully portable across all three. But the moment you strace or dtrace a real production server on each platform, you'll see it reaching for a completely different, completely non-standard syscall to do the actual heavy lifting, because POSIX never claimed to be the only interface a conformant kernel is allowed to expose — only the minimum one.

Real event-loop libraries handle this divergence exactly the way you'd expect: compile-time platform detection, picking whichever fast, non-portable extension is actually available, with a POSIX-only fallback for anything else.

simplified event-loop backend selection#if defined(__linux__)
    /* Linux: use the non-POSIX, high-performance extension */
    backend = "epoll";
#elif defined(__FreeBSD__) || defined(__APPLE__)
    /* BSD family (including macOS, via its BSD heritage): kqueue */
    backend = "kqueue";
#else
    /* Unknown or minimal POSIX target: fall back to the guaranteed baseline */
    backend = "poll";
#endif

This is precisely the pattern behind libuv (Node.js's event-loop library), and it's the same shape you'd write if you ever added a fast I/O-multiplexing path to bob_os's own syscall layer someday: keep a POSIX-guaranteed fallback that always works, and opportunistically reach for whatever faster, platform-specific mechanism is actually available underneath.

04 — Case Study #2

macOS's Mach/XNU Heritage Showing Through

macOS's kernel, XNU ("X is Not Unix"), is architecturally the odd one out of the three — and it shows in exactly the places POSIX left open. XNU is a hybrid kernel: a Mach microkernel core, originally developed at Carnegie Mellon, handling low-level primitives like virtual memory, scheduling, and inter-process communication via Mach ports and Mach messages — wrapped in a BSD-derived layer that provides the POSIX-facing process model, the standard filesystem namespace, and the traditional Unix syscalls, plus IOKit for device drivers.

From directly inside the POSIX contract, this hybrid heritage is invisible — fork(), open(), and read() behave exactly as specified. But step even slightly outside pure POSIX territory and the Mach layer shows through immediately: macOS's actual native IPC mechanism isn't POSIX pipes or System V message queues, it's raw Mach messages passed between Mach ports, and a huge amount of macOS's own internal plumbing (including parts of launchd, the system's init process, and XPC, Apple's own higher-level IPC framework) is built directly on top of that non-POSIX substrate rather than on top of the BSD-compatibility layer at all.

🔌 What POSIX Sees

A conformant Unix-like process model, standard file I/O, standard signals — XNU's BSD layer faithfully reproduces all of it, which is exactly why so much ordinary Unix software (including huge amounts of Linux server software) compiles and runs on macOS with little or no change.

👁️ What's Underneath, Invisible to POSIX

A Mach microkernel doing the actual scheduling and memory management, Mach ports as the real native IPC primitive, and a kernel architecture that shares almost no code lineage with Linux's monolithic design or even with the rest of the BSD family it borrows its userland layer from.
Worth noticing: this is the same lesson as this module's first explainer, just running in reverse. There, the point was that wildly different kernels can present an identical POSIX face. Here, the point is that the parts of the kernel POSIX doesn't cover are exactly where that underlying difference becomes visible again.

A short, concrete tour of where XNU's Mach roots surface

  1. launchd, macOS's init processResponsible for starting and supervising system and user services — talks to many of them over Mach IPC and XPC rather than exclusively over POSIX-standard mechanisms like signals and pipes.
  2. XPC (Apple's IPC framework)The mechanism most modern macOS apps and system daemons actually use to communicate with each other and with system services — built on top of Mach messaging, not POSIX message queues.
  3. Mach exception handlingCrash reporting and debugging tools on macOS (like the built-in crash reporter, or debuggers such as lldb) hook into Mach-level exception ports — a lower-level, non-POSIX mechanism sitting underneath the POSIX signal delivery a program itself sees.
  4. Mach virtual memory callsBeneath the POSIX-standard mmap() a program calls, XNU's actual memory management is expressed in terms of Mach VM primitives — mmap() is a compatibility-layer translation on top, not the native mechanism itself.
05 — Case Study #3

ps, ls & the Userland Drift

POSIX doesn't just standardize library functions — it also specifies a required baseline behavior for a set of command-line utilities, including ps and ls. And exactly like the syscall layer, the standard specifies required core behavior while leaving flags, output formatting, and convenience extensions to each vendor. Decades of separate evolution on top of that same open door produced genuinely different day-to-day conventions.

The classic, still-relevant example: BSD-style ps historically accepted options without a leading dash (ps aux), while System V/GNU-style ps expected the traditional dashed form (ps -ef). GNU's ps (what ships on virtually every Linux distribution) has since learned to accept both styles for compatibility — but macOS and the BSDs still run their original BSD-derived ps, which does not understand every GNU-only long-option extension, and vice versa. Similarly, GNU ls supports a large set of GNU-specific long options (like --color, or --group-directories-first) that BSD/macOS ls simply doesn't recognize, because they were never part of the POSIX-required baseline either implementation is obligated to share.

📌 The Pattern Across All Three Case Studies
Every single row above is a place where POSIX either specified nothing, or specified only a required minimum and explicitly left extension room. None of it makes any of these three systems less POSIX-conformant — a program written strictly to the POSIX baseline runs correctly on all three. The divergence lives entirely in the space POSIX always intended to leave open.
A practical consequence: shell scripts are the most common place this divergence actually bites people. A script that pipes ps aux into awk assuming GNU-specific column behavior, or calls ls --color for output formatting, will often fail outright or silently misbehave the moment it's run on a BSD or macOS box — not because the script did anything POSIX-illegal, just because it quietly depended on a vendor extension it never checked for. Writing genuinely portable shell scripts means deliberately sticking to the POSIX.2 baseline, the same discipline as writing portable C against the POSIX.1 baseline.
06 — Tying It Back

POSIX Is Orthogonal to Kernel Architecture

This closes the loop on the kernel-design-wars territory from earlier in the series: monolithic kernels (Linux, the BSDs), microkernels, and hybrid kernels (XNU) are a completely different axis of variation from POSIX conformance, and the two axes are, genuinely, orthogonal — independent of each other. A kernel's architecture is about how it's built internally: how much code runs in privileged mode, how subsystems communicate, where the fault-isolation boundaries are drawn. POSIX conformance is about what it presents externally, at the syscall/library boundary. You can pick any point on the first axis and, separately, choose to conform to POSIX or not on the second.

🐧 Linux — Monolithic

Nearly the entire kernel — scheduler, VFS, network stack, most drivers — runs as one privileged program in Ring 0. Fully POSIX-conformant at the boundary, architecturally about as "everything in one address space" as it gets.

👹 FreeBSD — Monolithic

Also monolithic, with its own independent codebase and design lineage from Linux — yet exposes a nearly identical POSIX face, because monolithic-vs-monolithic doesn't require shared code, only shared observable behavior.

🍎 macOS/XNU — Hybrid

A genuinely different architecture — a Mach microkernel core plus a BSD compatibility layer — and still fully POSIX-conformant, proving conformance has nothing to do with how many privilege-boundary crossings happen internally.

Push the point further: a true microkernel — one where the scheduler, filesystem, and drivers all run as separate user-space servers passing messages through a minimal privileged core — could, in principle, be made just as POSIX-conformant as Linux's monolithic design, provided its designers built a translation layer that reproduces the exact same externally observable behavior for every POSIX-mandated call. Nothing about "many small isolated servers talking over message-passing" is incompatible with "looks exactly like a Unix kernel from the outside." The architecture war and the standards-compliance question were never actually the same fight.

🧠 The Closing Idea
POSIX compliance is a promise about a boundary, not a blueprint for what's on either side of it. Wildly different kernels — different privilege models, different IPC mechanisms, different scheduling and filesystem internals, different decades of independent engineering — can all present an identical POSIX face, precisely because that face was designed, from 1988 onward, to be implementable by absolutely anyone willing to reproduce the specified behavior, by whatever internal means they choose.

bob_os sits on this same axis, just at a much smaller scale. Its own scheduler, VFS, and process model — everything you built module by module before ever reaching posix.c — are entirely bob_os's own design, unrelated to Linux's CFS, FreeBSD's ULE, or XNU's Mach-derived queues. That was always a legitimate choice, not a compromise: nothing about presenting a correct fork(), open(), and errno contract at module 28's boundary required copying anyone else's internal scheduling or filesystem design. bob_os is, in miniature, a fourth point on the same chart as Linux, BSD, and XNU — architecturally its own thing, POSIX-shaped at the seam.

07 — Quick Reference

Glossary & Key Terms

Implementation-Defined
POSIX terminology for behavior each conforming system may choose freely, as long as the choice is documented by that vendor.
Unspecified Behavior
Behavior POSIX places no requirement on at all — not even a documentation obligation — such as exact scheduling order among equal-priority processes.
epoll()
A Linux-only, non-POSIX syscall family for scalable readiness notification across large numbers of file descriptors, used internally by most high-performance Linux servers.
kqueue()
A BSD-originated, non-POSIX generalized event-notification API (also covering processes, signals, and filesystem events) adopted by all the BSDs and by macOS.
XNU
Apple's kernel ("X is Not Unix") — a hybrid combining a Mach microkernel core with a BSD-derived compatibility layer that provides the POSIX-facing surface.
Mach Microkernel
The Carnegie Mellon-originated microkernel design underlying XNU, using ports and messages as its native low-level IPC primitive instead of Unix pipes.
strace / dtrace
Tools that log every syscall a running program makes — the direct, observable evidence of which non-POSIX extension a program actually uses underneath a portable-looking call.
Hybrid Kernel
An architecture combining a microkernel core with monolithic-style compatibility layers for performance or compatibility — XNU is the canonical mainstream example.
Single UNIX Specification
The Open Group's certification standard, co-developed with POSIX, that vendors formally test conformance against to use the "UNIX" trademark.
Orthogonality (architecture vs conformance)
The property that a kernel's internal design (monolithic, microkernel, hybrid) and its external POSIX conformance are independent choices — either can vary without affecting the other.
SCHED_OTHER
POSIX's name for a system's default, non-real-time scheduling policy — required to exist and behave reasonably, with its actual algorithm left completely unspecified.
Mach Port / Mach Message
XNU's native low-level IPC primitives — a capability-protected communication endpoint and the messages passed through it, underlying much of macOS's own internal plumbing outside the POSIX-facing layer.
