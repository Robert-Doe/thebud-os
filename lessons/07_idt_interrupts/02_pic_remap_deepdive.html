Intel Built Into the Hardware

Nearly every x86 OS-dev tutorial in existence performs the same fix in the first hour. Here's exactly why it's needed and exactly what those bytes mean.

00 — Where We Left Off

A Sidenote That Deserves Its Own Page

The ISRs-and-IRQs lesson showed you the second half of every hardware interrupt handler's contract: send an EOI, or the PIC never delivers that line again. It also mentioned, almost in passing, that bob_os's handlers see IRQ0 (the timer) arrive as vector 32 and IRQ1 (the keyboard) as vector 33 — numbers that look arbitrary until you know where they came from. They aren't arbitrary. They're the result of a deliberate fix, applied at boot, before interrupts are ever turned on. This page is entirely about that fix: why it's necessary, and exactly what it does, byte by byte.

📎 One Fact to Keep Handy
From the IDT lesson: vectors 0–31 are permanently reserved by Intel for CPU-defined exceptions — divide error, page fault, general protection fault, and so on — the same on every x86 chip, not configurable by the OS. Keep that number in your other hand. It's the entire reason this page exists.
01 — What the Chip Does Out of the Box

The 8259's Factory Default

The Intel 8259A Programmable Interrupt Controller predates protected-mode x86 by a long margin — it was designed in 1976 for the 8085, then carried forward, unchanged in this respect, into every PC-compatible chipset since. Its job has always been simple: watch up to eight physical IRQ lines, and when one is asserted, tell the CPU which interrupt vector to raise for it.

A real PC has two 8259 chips, cascaded together, to get 15 usable lines instead of 8 (one line on the master is sacrificed to carry the slave's output). Left at their power-on defaults, with no software ever touching them, the mapping looks like this:

IRQ LineChipDefault VectorTypical Device
IRQ0Master8Programmable Interval Timer
IRQ1Master9Keyboard controller
IRQ2Master10Cascade line to the slave PIC
IRQ3Master11COM2 serial
IRQ4Master12COM1 serial
IRQ5Master13LPT2 / sound (varies)
IRQ6Master14Floppy disk controller
IRQ7Master15LPT1 / spurious interrupts

Notice the pattern: every single one of those default vectors — 8 through 15 — falls squarely inside the range 0–31. On the original 8086/8088, running in real mode with no concept of reserved exception vectors at all, this was completely harmless; the Interrupt Vector Table's first 32 slots weren't reserved for anything special yet. It's only once Intel introduced protected mode and formally carved out 0–31 for CPU exceptions that this same, unchanged default mapping turned into a landmine sitting in every PC's firmware.

Why didn't Intel just move the default? Backward compatibility. Millions of deployed 8259 chips, motherboards, and BIOSes already assumed IRQ0 meant vector 8. Changing the chip's power-on behavior would have broken every piece of real-mode DOS software relying on it. Instead, the fix was pushed onto every protected-mode OS: reprogram the chip yourself, at boot, before you ever enable interrupts.
02 — Why This Is a Genuine Problem

What Actually Breaks If You Skip This

It's tempting to assume this is a tidiness issue — "vectors 8-15 are used for two different things, how confusing" — but it's worse than confusing. Once the IDT is loaded and interrupts are enabled, the CPU cannot tell the difference between a hardware IRQ arriving on an unremapped vector and a genuine CPU exception with that same number. Both dispatch through the exact same gate. Both look, from the IDT's perspective, identical.

💥 The Direct Collision — IRQ0 vs #DF

Default IRQ0 (the timer) lands on vector 8. Vector 8 is also #DF, the Double Fault exception — the CPU's own mechanism for reporting "a fault occurred while I was already handling another fault." Left unremapped, a routine timer tick and a genuinely catastrophic double-fault condition dispatch through the identical gate descriptor. Your handler has no reliable way to know which one just happened.

💥 The Ambiguous Case — IRQ7 vs Vector 15

Default IRQ7 (historically LPT1, and also the PIC's own "spurious interrupt" line) lands on vector 15 — a vector Intel marks reserved. A spurious IRQ7 (the PIC's own noise-suppression mechanism, not a real device event) becomes indistinguishable from whatever a future Intel chip might someday define vector 15 to mean.
⚠️ It Gets Worse: Corrupted Exception Handling
Picture your kernel's divide-by-zero handler (vector 0, #DE) and, separately, the timer interrupt left at its unremapped default of vector 8. Now picture a genuine divide-by-zero happening in user code at the exact moment the timer also fires. Depending on timing and priority resolution inside the PIC, you can end up with a hardware timer tick landing on a vector range your kernel's exception-handling logic was written to treat as fatal-and-halt — or, just as bad, a real CPU exception landing on a vector your kernel's IRQ dispatch logic treats as "just service the device and EOI." Either mismatch means your kernel is now running the wrong handler logic entirely for what actually happened, silently, with no indication anything went wrong until the machine misbehaves in a way that's nearly impossible to trace back to its cause.

This is exactly why remapping the PIC is one of the very first things almost every x86 hobby kernel does, performed before sti ever runs — there is no safe window during which an unremapped PIC and a protected-mode IDT can coexist.

04 — The Actual Fix

Reprogramming the PIC With ICWs

The 8259 accepts a fixed sequence of four Initialisation Command Words (ICW1–ICW4), written to two I/O ports per chip — a command port and a data port. Write the command byte that starts initialization to the command port, then feed the remaining three words to the data port, one at a time, in order. Skip a step or write to the wrong port and the chip ends up in an undefined, often silently broken state.

ChipCommand PortData Port
Master PIC0x200x21
Slave PIC0xA00xA1

Here's the full sequence, with the exact byte values bob_os writes to each port — you've already seen the vector-offset numbers matter; now see where they're actually delivered.

ICW1 — Start Init
0x11 → 0x20 & 0xA0
Written to both command ports. Bit 4 (0x10) is the "this is an initialization sequence" flag; bit 0 (0x01) says "I will send you an ICW4." This single write resets both chips into their 4-word init sequence.
ICW2 — Vector Offset
0x20 → 0x21, 0x28 → 0xA1
Written to each chip's data port. This is the whole fix in one number: the master's IRQ0 now maps to vector 0x20 (32) instead of 8; the slave's IRQ8 now maps to vector 0x28 (40) instead of 70 (its own prior default).
ICW3 — Cascade Wiring
0x04 → 0x21, 0x02 → 0xA1
Tells the master "the slave is physically wired to my IRQ2 line" (bit 2 set = 0x04) and tells the slave "my own cascade identity is line 2" (value 0x02). This is board wiring, not a vector — every PC-compatible uses this exact pair.
ICW4 — Mode
0x01 → 0x21 & 0xA1
Selects 8086/8088 mode rather than the ancient MCS-80/85 mode. Without this, the chip stays in a compatibility mode that doesn't correctly acknowledge EOI — meaning the exact bug the previous lesson warned about would happen on every interrupt, unconditionally.
💡 The Aha Moment
ICW2 is the only word in the entire sequence that actually changes which vector number an IRQ line produces. ICW1, ICW3, and ICW4 are all mechanical setup — starting the sequence, describing how the two chips are physically wired together, and choosing an operating mode. If you remember nothing else from this page: the vector offset lives in ICW2, written to each chip's data port, right after ICW1 starts the sequence.
05 — The Fix, In Real Code

Same Sequence, As bob_os Writes It

Here's the complete pic_init() from bob_os's pic.c, with each write annotated against the ICW it corresponds to. Note the io_wait() calls after each write — some real 8259 hardware needs a brief settling delay between consecutive I/O port writes, a holdover from an era when the CPU could easily outrun the chip.

#define ICW1_ICW4   0x01   /* will send ICW4                 */
#define ICW1_INIT   0x10   /* initialisation bit -- must be 1 */
#define ICW4_8086   0x01   /* 8086/8088 mode                 */

void pic_init(void) {
    /* ICW1 -- start initialisation sequence on both chips */
    outb(PIC1_CMD, ICW1_INIT | ICW1_ICW4);   io_wait();   /* -> 0x20 */
    outb(PIC2_CMD, ICW1_INIT | ICW1_ICW4);   io_wait();   /* -> 0xA0 */

    /* ICW2 -- vector offsets: THIS is the actual remap */
    outb(PIC1_DATA, PIC1_OFFSET);   io_wait();  /* 0x21 <- 32 (0x20) */
    outb(PIC2_DATA, PIC2_OFFSET);   io_wait();  /* 0xA1 <- 40 (0x28) */

    /* ICW3 -- cascade wiring between the two chips */
    outb(PIC1_DATA, 0x04);   io_wait();   /* master: slave lives on IRQ2 */
    outb(PIC2_DATA, 0x02);   io_wait();   /* slave: my cascade id is 2   */

    /* ICW4 -- 8086 mode */
    outb(PIC1_DATA, ICW4_8086);   io_wait();
    outb(PIC2_DATA, ICW4_8086);   io_wait();

    /* Start with every IRQ line unmasked */
    outb(PIC1_DATA, 0x00);
    outb(PIC2_DATA, 0x00);
}

🧠 Why 32 Specifically, and Not, Say, 48?
Any value at or above 32 avoids the reserved range equally well — the choice of exactly 32 is convention, not requirement. It happens to be the smallest legal offset (since 0-31 is off-limits) and it's what nearly every OS-dev tutorial and reference OS uses, which is precisely why bob_os uses it too: vector 32 for IRQ0 is such a strong convention across the hobby-OS world that deviating from it would only make your code harder for others — and future you — to read.
06 — Two Things Remapping Does Not Do

Remapping Isn't Masking, and Isn't EOI

It's worth being precise about what pic_init() accomplishes and what it deliberately leaves for later, because conflating "remapped" with "enabled" is a common next mistake.

Remapping (this page)ICW1-4, once, at boot
Changes which vector number each IRQ line produces. A one-time setup step. Does not enable or disable any specific line, and has nothing to do with acknowledging interrupts after they're handled.
MaskingIMR, ongoing
Each PIC has an Interrupt Mask Register — one bit per line — read and written on the same data ports used for ICW2/3/4 after initialization finishes. A set bit means that line is disabled, remapped or not. bob_os starts with everything unmasked (0x00 written to both data ports at the end of pic_init()), then drivers can selectively mask lines they don't yet support.
EOIcommand port, per interrupt
Sent once per handled interrupt, to the same command ports (0x20 / 0xA0) used for ICW1 — but with value 0x20, the End-Of-Interrupt command, not an initialization byte. Covered in full in the ISRs-and-IRQs lesson; remapping and EOI use overlapping ports but are entirely separate operations.
📌 The Full Boot-Time Order, Stated Plainly
1. Remap the PIC with ICW1-4 (this page) — so IRQ vectors land at 32-47, clear of the reserved range. 2. Populate the IDT with gate descriptors for vectors 0-47 (covered in the IDT companion lesson) — so the CPU knows where to jump for each one. 3. Selectively unmask only the IRQ lines you have handlers ready for. 4. Only now execute sti to actually let interrupts fire. Reordering these steps — enabling interrupts before the IDT is populated, or before the PIC is remapped — is asking for an immediate crash or, worse, a silent vector collision like the one this page exists to prevent.
07 — Quick Reference

Glossary & Key Terms

8259 PIC
The Programmable Interrupt Controller chip (two, cascaded, on a PC) that routes up to 15 hardware IRQ lines to CPU interrupt vectors.
ICW (Initialisation Command Word)
One of four fixed-order bytes (ICW1-ICW4) written to a PIC's command/data ports to configure it — including, in ICW2, its vector offset.
Vector Offset
The value written in ICW2 that sets the vector number IRQ0 (or IRQ8, for the slave) maps to — 32 and 40 in bob_os's configuration.
PIC Remapping
The act of reprogramming both PIC chips' vector offsets away from their colliding factory default (8-15) to a safe range (typically 32-47).
Cascade
The wiring scheme connecting a slave PIC's output to the master's IRQ2 input, configured via ICW3, giving 15 usable lines from two 8-line chips.
IMR (Interrupt Mask Register)
A per-PIC register, one bit per IRQ line, controlling which lines the chip is currently willing to deliver — independent of vector offset.
EOI (End-Of-Interrupt)
The command byte (0x20) written to a PIC's command port after handling an interrupt, telling it to resume delivering that line.
Double Fault (#DF, vector 8)
The CPU exception colliding directly with an unremapped IRQ0's default vector — the sharpest example of why remapping matters.
Spurious Interrupt
A PIC-generated IRQ7 (or IRQ15) with no real device behind it, used by the chip itself for noise suppression — ambiguous with reserved vector 15 if unremapped.
