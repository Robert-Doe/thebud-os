00 — Where We Left Off

The IDT Gets You To the Handler. Now What?

The IDT deep dive walked you through the entire dispatch mechanism: a vector number, idtr, a gate descriptor fetched via idtr.base + vector×16, a ring transition, a trap frame pushed to the kernel stack, and finally a jump to whatever address the kernel wired up for that vector. That's the CPU's half of the job, and it's genuinely elegant — a fixed, table-driven, hardware-enforced dispatch mechanism.

But the CPU doesn't care what happens after the jump. It doesn't know if your handler is correct, whether it saves the registers it touches, or whether it ever tells anyone it's finished. All of that is your job, written in ordinary code, running with zero safety net. This page is about that code — the Interrupt Service Routine (ISR) — and about one specific contract every ISR handling a device interrupt has to honor, or the machine quietly stops receiving that class of interrupt forever.

📎 Quick Refresher, In One Line Each
Vector number: the integer, 0–255, that indexes into the IDT. Gate descriptor: the 16-byte (64-bit mode) IDT entry naming the handler's segment selector and offset. Trap frame: the PC/flags/registers bundle the CPU pushes to the kernel stack the instant any of the three doors — syscall, exception, interrupt — fires. If any of those three sentences felt unfamiliar, the IDT companion lesson is worth a pass before continuing here.
01 — The Function Itself

What Does an ISR Actually Look Like?

Here's the part most IDT explanations skip entirely: once the gate descriptor points at an address, something has to actually live at that address. Not a conceptual placeholder — real bytes, a real function, compiled or assembled and sitting in kernel memory before lidt ever runs. That function is the ISR.

An ISR is unlike almost every other function you'll ever write, for one reason: it doesn't have a caller in the normal sense. Nothing called it with arguments on a stack the way main() gets called. The CPU jumped to it mid-instruction, from inside whatever code happened to be running, with whatever registers that code happened to be using at the time still sitting there, un-saved, un-announced. A regular function can assume the compiler's calling convention already protected the caller's important state. An ISR cannot assume anything of the sort.

📞 A Normal Function Call

Caller and callee agree on a calling convention in advance — which registers the callee may clobber freely (caller-saved) and which it must preserve (callee-saved). The compiler generates both sides. Nobody is surprised by what changed.

⚡ An Interrupt Arriving

There is no "callee" by agreement — there's a CPU that jumped mid-instruction because a device or a fault demanded it. The interrupted code never agreed to let any register change. Every single register the ISR path touches has to be put back exactly as it was, or the interrupted program resumes broken.

Because of this, a real ISR is almost never written as a single ordinary C function reached directly from the IDT gate. It's written as two layers: a thin assembly stub, one per vector, that does the register bookkeeping the CPU itself won't do — and a normal C handler function that the stub calls once it's safe to do so. This is exactly the split bob_os uses in isr.asm and isr.c:

; isr.asm — one tiny stub per vector, all funneling into one C handler
isr14:                    ; #PF Page Fault — CPU already pushed an error code
    push dword 14         ; push the interrupt vector number
    jmp  isr_common_stub

irq1:                     ; IRQ1 Keyboard — CPU pushes no error code at all
    push dword 0          ; push a dummy error code, keeps the frame uniform
    push dword 33          ; vector = irq + 32, after the PIC remap
    jmp  isr_common_stub
💡 The Aha Moment
An ISR is not a special kind of function the CPU understands — the CPU only understands "jump here." Everything that makes a jump target safe to resume from afterward — saving registers, restoring them, correctly unwinding the stack, returning via iret instead of ret — is ordinary code you write. The IDT gets you to the front door. What's behind the door is entirely your responsibility, and getting it wrong doesn't throw a compiler error — it corrupts a running program you weren't even trying to touch.
02 — Obligation One

Save Every Register You Touch

"Every register" is not hyperbole. A normal function only has to preserve the registers its calling convention marks callee-saved — on x86, historically EBX, ESI, EDI, EBP. It's free to trash EAX, ECX, EDX because the convention says the caller already assumed those might change. An ISR gets none of that courtesy: the "caller" is arbitrary interrupted code that made no such assumption about anything, because it never called an interrupt handler — the interrupt happened to it.

  • The stub saves everything, unconditionallybob_os's isr_common_stub opens with pusha (saves EAX, ECX, EDX, EBX, ESP, EBP, ESI, EDI in one instruction) followed by explicit pushes of DS, ES, FS, and GS. Nothing is skipped, because the stub has no way to know in advance which registers the interrupted code was actively relying on — the honest assumption is "all of them."
  • Only then does kernel code get to runAfter the segment registers are pointed at the kernel's own data segment (so the handler isn't accidentally reading through whatever segment the interrupted user code had loaded), the stub passes a pointer to this saved state — the interrupt_frame — to the actual C handler.
  • The C handler runs with an ordinary calling conventionOnce inside interrupt_handler(struct interrupt_frame *frame), you're back in familiar territory — the compiler's normal ABI applies, because this function really was called, by the stub, like any other function. This is precisely why the split exists: raw assembly handles the part the compiler can't reason about, and C handles everything after.
  • The stub restores everything, in reverse, before returningpop gs / pop fs / pop es / pop ds / popa, then the vector number and error code are discarded from the stack, and only then does iret run — never a plain ret, because iret is the one instruction that knows how to restore EIP, CS, and EFLAGS from the CPU's own automatic pushes.

    ⚠️ Why "Just Write It In C" Doesn't Work
    You might reasonably ask: why not skip the assembly stub and point the IDT gate straight at a C function? The problem is that a normal C function's compiler-generated prologue only saves callee-saved registers — it assumes the caller took care of the rest, because in ordinary code, it did. An interrupt has no such caller. Point a gate directly at an unprotected C function and the first time it clobbers, say, ECX while the interrupted code was mid-calculation using ECX, that program silently gets wrong answers with no crash, no warning, and — for a timer interrupt firing constantly in the background — no realistic way to reproduce the bug on demand. Some toolchains offer an interrupt function attribute that generates the extra save/restore prologue for you, but on x86 that attribute is unreliable enough across compilers and calling conventions that most real kernels, bob_os included, just write the stub by hand in assembly where the behavior is exact and guaranteed.
    What about a "naked" function? Some architectures and compilers support a naked attribute — a function with no compiler-generated prologue or epilogue at all, leaving you to write 100% of the entry/exit code yourself in inline assembly. Conceptually, that's exactly what isr_common_stub already is, just written as a standalone assembly routine instead of an annotated C function. Either spelling gets you to the same place: a piece of code where you, not the compiler's default assumptions, control every register touched at entry.
    03 — Obligation Two

    Send the EOI, or the Line Goes Dead

    Saving registers protects the interrupted program. It says nothing about protecting future interrupts — and this is the obligation that trips up nearly everyone the first time they write a hardware interrupt handler, because forgetting it doesn't crash anything. It just makes the machine quietly stop noticing that device ever again.

    Here's the mechanism. The interrupt controller sitting between devices and the CPU — the 8259 PIC, or its modern APIC successor — doesn't just fire an interrupt and forget about it. While a given IRQ line is "in service," the controller withholds any further interrupt on that same line (and, on the PIC, any lower-priority line too), on the reasonable assumption that the CPU is still busy handling the first one. The only way to tell the controller "I'm done, you can fire this line again" is to explicitly send it an End-Of-Interrupt (EOI) signal.

    /* pic.h */
#define PIC1_CMD   0x20   /* master PIC command port */
#define PIC2_CMD   0xA0   /* slave  PIC command port */
#define PIC_EOI    0x20   /* the EOI command byte itself */

/* pic.c — must run at the END of every hardware IRQ handler */
void pic_send_eoi(uint8_t irq) {
    if (irq >= 8) {
        outb(PIC2_CMD, PIC_EOI);   /* IRQ8-15 came through the slave too */
    }
    outb(PIC1_CMD, PIC_EOI);       /* master always gets one */
}
    📌 What "Forgetting EOI" Actually Feels Like
    Not a crash. Not an error message. The keyboard just... stops working. Or the timer stops ticking and your scheduler never runs again. Everything else on the machine keeps executing perfectly normally, which is exactly what makes this bug so unpleasant to track down the first time — nothing failed loudly, one specific IRQ line simply went silent forever, because the PIC is still faithfully waiting for an acknowledgment that never came.
    ▶ Watch two key presses — with and without the EOI

    Notice where EOI sits relative to the rest of the handler. bob_os's interrupt_handler() sends it before dispatching to the device-specific handler function, not after:

    /* isr.c */
uint8_t irq = (uint8_t)(vec - 32);

/* EOI first, so the PIC can accept new interrupts on OTHER lines
 * while we're still busy servicing this one. */
pic_send_eoi(irq);

if (irq_handlers[irq] != 0) {
    irq_handlers[irq](frame);
}
    🧠 Why Order Matters Here
    Sending EOI late — after a slow handler finishes — doesn't just delay the same device's next interrupt. On the PIC, a line "in service" also blocks every lower-priority line from firing at all until it's cleared. A handler that does real work before acknowledging can end up starving unrelated devices for however long it takes to finish, for no reason other than acknowledgment order. Sending EOI first, then doing the work, keeps the controller free to deliver everything else while your handler finishes at its own pace.
    04 — Two Very Different Doors

    IRQs and Exceptions Aren't the Same Job

    The IDT dispatches both through the identical mechanism — same table, same gate descriptors, same trap frame. But once you're inside the handler, what you're supposed to do diverges sharply depending on which kind of trap got you there, and conflating the two is a common source of real bugs.

    Hardware IRQvectors 32–47 (remapped)
    Asynchronous, device-generated, routed through the PIC or APIC. Nothing about the interrupted code caused it — a key was pressed, a timer ticked, a disk finished. The handler's job: service the device, send EOI, and get out fast. The interrupted instruction was doing nothing wrong and simply resumes afterward.
    CPU Exceptionvectors 0–31 (Intel-reserved)
    Synchronous, caused directly by the instruction that just tried to execute — divide by zero, invalid opcode, a page fault. There is no controller to acknowledge and no EOI to send, because no device is waiting to be told "clear to fire again." The handler's job is entirely different: decide whether the fault is recoverable (page it in, then resume) or fatal (kill the process, or panic if it's the kernel itself).

    🔑 The One-Sentence Rule of Thumb
    If a device is involved, the controller is waiting on you — send EOI. If no device is involved and the CPU faulted on its own instruction, there's nothing to acknowledge — decide, instead, whether the interrupted program gets to continue at all.

    bob_os's interrupt_handler() makes this branch explicit rather than leaving it implicit in per-vector code — vector number alone tells it which rulebook applies:

    void interrupt_handler(struct interrupt_frame *frame) {
    uint32_t vec = frame->int_no;

    if (vec < 32) {
        /* CPU exception -- no controller, no EOI, no automatic recovery */
        kernel_panic(frame);
    } else if (vec < 48) {
        /* Hardware IRQ -- a controller IS waiting on an acknowledgment */
        uint8_t irq = (uint8_t)(vec - 32);
        pic_send_eoi(irq);
        if (irq_handlers[irq] != 0) irq_handlers[irq](frame);
    }
}
    05 — Play By Play

    A Keypress, Start to Finish

    1. You press a keyThe keyboard controller electrically asserts IRQ1. The PIC's master chip notices, checks that IRQ1 isn't masked in its Interrupt Mask Register, and — since it isn't — raises the CPU's interrupt line, presenting vector 33 (IRQ1's remapped vector, 32 + 1).
    2. The CPU dispatches through the IDTExactly the mechanism from the companion lesson: idtr.base + 33×16 locates the gate descriptor for irq1, the CPU switches stacks if needed, and pushes EIP/CS/EFLAGS automatically.
    3. irq1's stub runs firstIt pushes a dummy error code and the vector number 33, then falls into isr_common_stub, which saves every general-purpose and segment register with pusha plus explicit pushes, and repoints DS/ES/FS/GS at the kernel's own data segment.
    4. The C dispatcher takes overinterrupt_handler() sees vec = 33, which is >= 32, so it computes irq = 1 and immediately calls pic_send_eoi(1) — the PIC's IRQ1 line is now cleared to fire again, even though nothing has actually read the key yet.
    5. The registered keyboard handler runsirq_handlers[1] — whatever function the keyboard driver registered via irq_register(1, ...) — reads the scancode out of the keyboard's data port, translates it, and stashes it wherever the input subsystem expects it.
    6. The stub unwinds and returnsRegisters are restored in reverse order, the dummy error code and vector number are popped off the stack, and iret resumes the interrupted program at exactly the instruction it was on — which never knew any of this happened.
    ✅ Notice What Ties Together
    Step 4 happens before step 5 on purpose — the PIC is told "clear to fire again" before the driver even touches the hardware, so a second, unrelated interrupt (say, IRQ0, the timer) isn't kept waiting behind a keyboard handler doing its own work. Steps 3 and 6 are the register-save contract from the earlier section, executing on literally every keypress on the machine, whether you ever notice it or not.
    06 — One Sharp Edge

    Can an Interrupt Interrupt Another Interrupt?

    Recall from the IDT lesson that an Interrupt Gate automatically clears the CPU's interrupt flag (IF) on entry — the default choice for the vectors covered on this page. That single detail is what keeps the story above simple: while irq1's stub and handler are running, IF is clear, so the CPU won't accept another maskable interrupt in the middle of it, even if the PIC would otherwise be willing to deliver one.

    That protection is why the EOI-then-handle ordering from the previous section is safe rather than reckless: sending EOI early makes the PIC willing to raise a new interrupt, but IF being clear means the CPU won't actually act on it until the current handler finishes and iret restores the saved EFLAGS (and with it, IF) back to whatever it was before. The two mechanisms — PIC-level masking and CPU-level IF — work at different layers and both matter: EOI controls what the controller is willing to deliver, IF controls what the CPU is willing to accept right now.

    ⚠️ Where This Bites: Long Handlers and Reentrancy
    A handler that takes too long — or one that deliberately re-enables interrupts mid-handler with sti to stay responsive — opens the door to a second interrupt arriving while the first is still on the stack. If both handlers touch the same shared, non-reentrant state (a global buffer, a linked list, a device register) without any locking, you've built a race condition inside code whose entire job was supposedly to run atomically. The safe default for most hobby-OS interrupt handlers, bob_os included at this stage, is: keep IF clear for the handler's duration (the Interrupt Gate default already does this), keep the handler short, and defer any slow work to be picked up later outside interrupt context.
    07 — Quick Reference

    Glossary & Key Terms

    ISR (Interrupt Service Routine)
    The handler code that actually runs once the IDT has dispatched a trap — in practice, a raw assembly stub plus a normal C function it calls.
    IRQ (Interrupt Request)
    A hardware interrupt line asserted by a device, routed through the PIC or APIC to a specific IDT vector — asynchronous and requires an EOI.
    CPU Exception
    A synchronous trap the CPU raises on its own, caused by the instruction currently executing — no controller involved, no EOI to send.
    EOI (End-Of-Interrupt)
    A command byte written back to the interrupt controller telling it the current IRQ has been serviced and it's free to deliver another on that line.
    Trap Frame / interrupt_frame
    The saved-register structure a stub builds on the kernel stack — general registers, segment registers, vector number, error code, plus the CPU's own EIP/CS/EFLAGS push.
    ISR Stub
    The small, per-vector assembly routine that saves every register before calling a normal C handler, and restores them before executing iret.
    IMR (Interrupt Mask Register)
    A per-PIC register with one bit per IRQ line; a set bit means that line is disabled and the PIC will not deliver it, EOI or not.
    IF (Interrupt Flag)
    A bit in EFLAGS controlling whether the CPU will accept maskable interrupts at all; Interrupt Gates clear it automatically on entry.
    iret
    The instruction that ends an ISR, restoring EIP, CS, and EFLAGS from the CPU's own automatic pushes — never a plain ret.
