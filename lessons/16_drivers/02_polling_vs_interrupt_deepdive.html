Every driver eventually has to answer the same question: how do I know when the hardware has something for me? There are exactly two honest answers. Keep asking, over and over, until the answer is yes — that's polling. Or set up a doorbell and go do something else until it rings — that's interrupt-driven I/O. bob_os's own disk driver and keyboard driver each picked a different one, and neither choice was an accident.

00 — Where We Left Off

Not Re-Deriving Interrupts — Using Them

The IDT/interrupts lesson already covered the mechanics in depth: the IDT, the 8259A PIC, ISR stubs, pic_send_eoi(), vector remapping to 32+ so IRQs don't collide with CPU exceptions. If any of those terms are unfamiliar, that's the lesson to go back to — this page assumes you already know how an interrupt reaches a handler function.

What that lesson didn't cover is the design decision sitting one level up: given that interrupts exist and work, why would a driver ever choose not to use them? bob_os's own source answers this by example — keyboard.c registers an IRQ1 handler and does nothing else; disk.c never touches the IDT at all and instead spins in a while loop reading a status register. Same kernel, two completely different answers to "how do I know when data is ready?" This lesson is about why.

01 — Asking, Repeatedly

Polling: "Are You Ready Yet?" On Loop

Polling means the driver reads a hardware status register in a tight loop, checking one bit, over and over, until the hardware flips it. No setup beyond the loop itself, no interrupt handler to register, no vector to worry about. It's the most direct code you can possibly write, and bob_os's ATA disk driver uses exactly this pattern for every single sector it reads or writes.

/* disk.c — real code from bob_os's ATA PIO driver */

/* Spin until BSY clears.  No timeout — in a real driver you'd add one. */
static void ata_wait_bsy(void) {
    while (ata_inb(ATA_STATUS) & ATA_BSY) {}
}

/* Spin until DRQ sets (data ready) or ERR sets.
 * Returns 0 if DRQ set, -1 if ERR set. */
static int ata_wait_drq(void) {
    uint8_t s;
    for (;;) {
        s = ata_inb(ATA_STATUS);
        if (s & ATA_ERR) return -1;
        if (s & ATA_DRQ) return 0;
    }
}

Every single call to disk_read_sector() runs ata_wait_bsy(), then programs the LBA registers, issues the read command, and calls ata_wait_drq() — burning CPU cycles in a bare loop the entire time the drive is busy internally. On real spinning rust that could be milliseconds; on an emulated QEMU disk it's usually fast, but the CPU has no way to know that in advance, so it spins regardless.

⚠️ The Honest Cost of That Loop
While ata_wait_bsy() spins, the CPU is 100% occupied doing nothing useful — not running another process, not servicing a timer tick promptly, not doing anything except re-reading the same port over and over. On a single-core, non-preemptible kernel like early bob_os, that loop is the entire machine for however long it runs. There's also no timeout here, which the comment itself admits — a truly wedged drive would hang the kernel forever.

The latency story is just as blunt: how quickly you notice the drive became ready is entirely a function of how often you check. Check constantly and you notice almost instantly, at the cost of burning every spare cycle checking. Check occasionally and you save cycles, at the cost of noticing late. Polling doesn't let you have both — the loop's check frequency is the latency bound.

02 — Being Told

Interrupt-Driven I/O: The Hardware Speaks First

Interrupt-driven I/O flips the arrangement completely. Instead of the CPU asking, the CPU registers a handler once and then does something else entirely — runs other processes, even halts — until the device itself asserts an IRQ line, forcing the CPU into that handler the instant there's something to report.

/* keyboard.c — real code from bob_os's PS/2 keyboard driver */

void keyboard_init(void) {
    irq_register(1, keyboard_irq_handler);   /* registered ONCE, at boot */
}

/* IRQ1 handler -- called from the generic interrupt dispatcher,
 * only when hardware actually has a scancode waiting. */
static void keyboard_irq_handler(struct interrupt_frame *frame) {
    (void)frame;
    uint8_t sc = inb(KB_DATA_PORT);      /* read the ONE byte that's ready */
    /* ... decode + buf_push(c) ... */
}

Between keypresses, bob_os does zero work related to the keyboard — no loop, no register reads, nothing. The CPU could be running the shell, another process, or idling at a HLT instruction. The instant a key goes down, the PS/2 controller asserts IRQ1, the 8259A PIC delivers CPU vector 33, the ISR stub saves registers, and keyboard_irq_handler() runs — all without any code anywhere having asked "is a key ready?" first.

✅ What This Buys You
Two things simultaneously: the CPU is free to do genuinely useful work between events (no wasted spinning), and reaction time is essentially the hardware's own signaling latency, not "however often you happened to check." For an event like a keypress — rare, unpredictable, latency-sensitive — that's a clear win on both axes at once.
Side note — "interrupt-driven" doesn't mean interrupts are free. Taking one still costs real cycles: the CPU must finish or abort its current instruction, push a trap frame, jump through the IDT, run the ISR stub, execute the handler, send an EOI back to the PIC, and return. For something as rare as a keypress that overhead is trivial next to the alternative (constant polling). As you'll see in section 05, that overhead stops being trivial once events start arriving by the million per second.

🧠 The Actual Trade, Stated Precisely
Polling trades CPU time for simplicity and a hard ceiling on worst-case latency (you're never surprised by an interrupt arriving mid-critical-section). Interrupts trade a small, fixed per-event overhead for near-zero idle cost and near-instant reaction. Neither is strictly better — which one wins depends entirely on how often the event happens and how predictable that timing is, which is exactly what section 05 pulls apart.
05 — The Twist

Why Polling Still Wins Sometimes

Everything above makes interrupts sound strictly better for anything that isn't rare. That's true for a keypress arriving a few times a second. It stops being true once the event rate climbs into the hundreds of thousands or millions per second — which is exactly where modern storage and networking hardware live.

💥 NVMe SSDs

A single modern NVMe drive can complete well over a million I/O operations per second. Taking one full hardware interrupt — trap frame, IDT dispatch, ISR, EOI, return — for every single completion at that rate means the interrupt-handling machinery itself becomes the bottleneck, not the storage device or the software above it.

💥 10Gbps+ Networking

At line rate, small packets can arrive faster than one every microsecond. An interrupt per packet at that pace leaves almost no CPU time for anything except entering and leaving interrupt handlers — a phenomenon with an actual name, receive livelock, where a machine can be pegged at 100% CPU and yet forward zero packets, because it never escapes the interrupt storm long enough to do real work.
The crossover, in one line Interrupts win when events are rare relative to their own handling cost. Once events arrive faster than you can afford to fully context-switch into and out of a handler for each one, the fixed per-interrupt overhead — not the actual work — becomes the bottleneck.

This is exactly bob_os's ATA disk driver's situation in miniature: on a real disk, sector completion is slow enough (milliseconds) that an interrupt-driven design would be the better choice, and full OS-grade ATA/AHCI drivers do use interrupts. bob_os's teaching version polls instead, purely because a synchronous spin loop is far simpler to read and reason about at this stage — a deliberate simplicity trade-off, not evidence that polling is always fine.

06 — Best of Both

Hybrid Approaches: Poll During Bursts, Interrupt When Idle

Production kernels don't pick one strategy and stick with it forever — they switch dynamically based on load. The general pattern, used under names like NAPI (New API, Linux's networking interrupt-mitigation framework) and interrupt coalescing (common in NIC and NVMe hardware), looks like this:

  1. Start interrupt-driven, as usualWhile traffic is light, a single interrupt per event is cheap relative to how rarely it fires — exactly the regime where interrupts win outright.
  2. The first interrupt of a burst disables further interrupts for that deviceInstead of servicing just that one event and re-arming, the handler masks the device's interrupt line and switches the driver into polling mode.
  3. Drain everything available in a tight poll loopWhile the burst lasts, the driver repeatedly checks the device's ready queue directly — no per-packet interrupt overhead, because it isn't taking interrupts at all right now. This is precisely the "asking" model from section 01, deliberately chosen because the event rate has made "being told" per-event too expensive.
  4. Once the queue drains and stays empty, re-arm the interruptWhen there's genuinely nothing left to process, the driver flips back to interrupt-driven mode and the CPU is freed up again — back to section 02's regime, because now events are rare again.

📌 Interrupt Coalescing — A Simpler Cousin
NIC and NVMe hardware often expose a related, hardware-level trick: instead of firing an interrupt for every single completed event, the device batches several completions and fires one interrupt covering all of them, either after a timer expires or after N events accumulate — whichever comes first. It's the same underlying insight as NAPI (amortize the fixed per-interrupt cost across many events) implemented in silicon instead of in the driver's control flow.

The lesson underneath both techniques is the same one this whole page has been circling: polling and interrupts aren't rival philosophies to pick once and defend forever — they're two tools with opposite cost curves, and the best drivers switch between them based on what the hardware is actually doing right now.

07 — Quick Reference

Glossary & Key Terms

Polling
Repeatedly reading a hardware status register in a loop until it reports readiness — simple, CPU-hungry while waiting, latency bounded by check frequency.
Interrupt-Driven I/O
Registering a handler once and letting the hardware itself signal the CPU via an IRQ line when it has something to report — near-zero idle cost, near-instant reaction.
Busy-Wait / Spin Loop
A loop that does nothing but repeatedly test a condition — bob_os's ata_wait_bsy() and ata_wait_drq() are real examples.
Status Register
A hardware register a driver reads to check device state — e.g. ATA's 0x1F7, whose BSY/DRQ/ERR bits report drive readiness.
IRQ (Interrupt Request)
A hardware line a device asserts to force the CPU into an interrupt handler, independent of whatever the CPU was doing — see the IDT/interrupts lesson for the full mechanism.
Receive Livelock
A pathological state where a system is 100% busy handling interrupts yet accomplishes no forward progress, because event arrival outpaces the CPU's ability to fully service each one.
Interrupt Coalescing
A hardware-level optimization where a device batches multiple completions into a single interrupt, amortizing the fixed per-interrupt cost across many events.
NAPI
Linux's New API networking model: interrupt-driven under light load, switching to a polling drain loop during bursts, then re-arming interrupts once the queue empties.
Interrupt Overhead
The fixed cost of taking any interrupt — trap frame save, IDT dispatch, ISR execution, EOI, return — regardless of how much real work the event required.
Crossover Point
The event rate at which per-interrupt fixed overhead starts to dominate total cost, making a polling or hybrid strategy cheaper than pure interrupts.
