00 — Where We Left Off

You've Already Written Three Drivers — You Just Didn't Call Them That

Back in the VGA module you wrote code that pokes bytes directly into 0xB8000 to put characters on screen. In the keyboard module you wrote an IRQ1 handler that reads port 0x60 and pushes ASCII into a ring buffer. In the filesystem module you built a VFS with a vfs_ops vtable — open/read/write/close — so the shell could treat a real file and a device the same way. Every one of those was already a driver. What was missing was a name for the pattern, and a single registration table so the kernel doesn't have to know about "the VGA thing" and "the keyboard thing" and "the disk thing" as three unrelated bodies of code.

That's what bob_os's Module 27 (driver.c / driver.h) adds on top of everything you already built: a driver framework — a boot-time table that every device driver registers itself into, and a uniform /dev/ filesystem (devfs) that the VFS mounts on top of it. This lesson is about the idea underneath that code, before we get into the two big mechanical questions the next two lessons tackle: how should a driver notice a device has data ready (polling vs interrupts), and where does a device's memory actually live in the CPU's address space (MMIO vs port I/O).

01 — The Problem, Stated Bluntly

Why Hardware Refuses to Be Uniform

Picture four chips sitting on the same motherboard. None of them agree on anything.

⌨ PS/2 KeyboardIRQ1
Speaks in single bytes called scancodes, one per key transition, delivered by asserting an interrupt line. There is no concept of "reading 512 of them at once" — you get exactly one, whenever the hardware feels like sending it.
💾 ATA Disk8 registers
Speaks in 512-byte sectors, negotiated through an eight-register handshake (LBA low/mid/high, drive/head, sector count, command, status) that must be programmed in a strict order before any data moves.
🌐 NE2000 NICvariable-length
Speaks in variable-length packets that arrive with no fixed schedule at all — could be ten in a millisecond, could be none for an hour — buffered in an onboard ring the driver has to drain before it overflows.
🖥 VGA Text Bufferframebuffer
Isn't even "read" in the usual sense — it's a 2,000-cell framebuffer mapped straight into RAM at 0xB8000 that the monitor scans continuously. Writing to it is just an ordinary memory store.

Different transfer units. Different timing models. Different physical access mechanisms — some through dedicated I/O ports, some through ordinary memory addresses. If the kernel had to know all of that to talk to every device, every new piece of hardware would mean touching the scheduler, the shell, the filesystem code, and anything else that ever wants to move a byte in or out. That doesn't scale past about three devices.

⚠️ The Trap: Special-Casing Creeps
Without a driver layer, "read some data" quietly becomes "read some data, unless it's the keyboard, in which case check the ring buffer, unless it's the disk, in which case poll the status register, unless it's the network card, in which case..." Every caller of I/O has to know the internals of every device. One new peripheral means editing code all over the kernel, not just adding one file.
02 — The Deliberate Fix

The Driver as Translator

A driver's entire job is to stand between two worlds and speak both languages fluently, so nobody else has to learn either. On one side: this exact chip's registers, this exact protocol, this exact timing quirk. On the other side: a small, boring, generic contract — probe / read / write / ioctl — that looks identical no matter which chip is actually plugged in.

The one-line definition A driver is hardware-specific knowledge, wrapped in a generic shape. Everything above the driver only ever sees the generic shape. Everything below the driver is a mess particular to one chip — and that mess never leaks upward.

Notice what the right-hand side of that animation never changes: it's always read(buf, len) returning bytes. The caller — the shell reading a keypress, or a program reading a file — never once has to know whether a scancode table or an ATA status register sat behind that call. That's not an accident; it's the entire point of the abstraction.

Side note — this is the exact same move you already made once. The VFS's vfs_ops vtable (open/read/write/close) lets the shell treat a real file on BobFS and a device under /dev/ identically. The driver's driver_ops vtable is that same move applied one layer further down — this exact chip versus a generic device, instead of this exact filesystem versus a generic file. Once you've drawn one dispatch-through-vtable diagram, you've understood both.
03 — The Contract, Precisely

What Exactly Does a Driver Promise?

In bob_os the promise is a plain C struct of function pointers — a vtable — that every driver fills in and hands to the kernel exactly once, at registration time.

/* driver.h — the vtable every driver must implement */
struct driver_ops {
    const char *name;            /* "kbd", "disk", "eth0" -> becomes /dev/<name> */
    dev_type_t  type;             /* DEV_CHAR, DEV_BLOCK, or DEV_NET */

    int  (*probe)(void);                          /* detect + init hardware, 0 = found */
    int  (*read) (uint8_t *buf, uint32_t len);    /* read len bytes into buf   */
    int  (*write)(const uint8_t *buf, uint32_t len); /* write len bytes from buf */
    int  (*ioctl)(uint32_t cmd, void *arg);       /* device-specific control   */
};

🧠 The Pattern, Named
Whenever you see "a struct of function pointers, filled in differently by each implementation, called uniformly by everyone else," you're looking at a vtable — the same mechanism that gives you polymorphism in C++ under the hood, and the same mechanism Linux uses for file_operations, block_device_operations, and every driver interface it exposes. bob_os's driver_ops is a small, honest version of the exact same idea.
04 — From Registration to /dev/

How the Kernel Actually Uses the Contract

The vtable alone doesn't do anything — it has to be registered, probed, and exposed. bob_os does this in a fixed, four-step boot sequence.

  1. Each driver calls driver_register(&ops)Before kernel_main() runs anything else, every driver's .c file hands its filled-in driver_ops struct to the kernel. This just claims a slot in the fixed-size driver_table[MAX_DRIVERS] array and assigns a dev_major number — no hardware has been touched yet.
  2. The kernel calls driver_probe_all()The kernel walks every registered slot and calls each one's probe(). This is the only moment device-specific initialisation is allowed to happen — programming the PIC-adjacent chip registers, checking for a floating ATA bus, whatever that particular piece of hardware needs. A driver whose probe() returns nonzero is marked inactive and simply never appears again.
  3. devfs exposes every active driver as /dev/<name>devfs is deliberately the thinnest possible VFS backend — no inodes, no on-disk state. devfs_open("/dev/kbd") is nothing more than a call to driver_find("kbd"), which linear-scans the active drivers for a name match and stores the matching driver_ops* pointer in the file descriptor.
  4. Every later read()/write()/ioctl() is a straight vtable dispatchOnce a process has an fd open on /dev/kbd, calling read() on it is just fd->ops->read(buf,len) — a function-pointer call through the struct, with zero branching on "which device is this." The generic contract from section 03 is what makes that single line correct for every device in the table.

💡 Why probe() Instead of Just Assuming the Device Exists
QEMU, real hardware, and CI test runners don't all have the same peripherals attached. probe() is the driver's chance to say "actually, I looked, and I'm not here" — a floating ATA bus reads back 0xFF, an absent NIC never answers its EEPROM read. Marking that driver inactive means every later lookup, list, and dispatch simply skips it, instead of the kernel crashing the first time something tries to touch hardware that was never plugged in.
05 — Not All Devices Are Alike, Either

Three Families, One Vtable

The generic contract doesn't mean every device behaves the same — dev_type_t exists precisely because "a unit of data" means something different depending on what kind of device you're talking to.

📇 DEV_CHAR — character devices

An unstructured stream, one byte (or a few) at a time, with no seeking. The keyboard is the canonical example: read() returns whatever's next in the ring buffer, in order, and there's no meaningful "byte 47 of the keyboard."

💽 DEV_BLOCK — block devices

Fixed-size, addressable chunks — 512-byte sectors for the ATA disk — that support random access by number. read() on a block device is really "read sector N," even though the vtable signature doesn't show the sector number explicitly (that detail is usually folded into how the driver interprets its buffer/length arguments, or handled via ioctl).
🌐 DEV_NET — network devicespacket-shaped
Neither a byte stream nor a sector-addressed disk — a sequence of discrete, variable-length packets with no inherent ordering guarantee beyond arrival order. NE2000 and loopback both fall here; read() hands back one packet's worth of bytes at a time.

The point isn't that dev_type_t changes the function signatures — it doesn't. It's metadata the rest of the kernel (and eventually user space, through ioctl or a stat-like call) can use to decide how to interpret the bytes a generic read() handed back, without ever needing device-specific code to get those bytes in the first place.

06 — Why This Discipline Matters

What Happens Without a Driver Layer

It's worth being concrete about the alternative, because "abstraction" can sound like busywork until you picture the code it's replacing.

✅ The Real Payoff
A driver framework's value isn't visible on the happy path — it's visible the day you add device number four. Every device before that could have been special-cased by hand and nobody would notice the difference. The generic contract is what keeps device number sixteen exactly as cheap to add as device number two.

That's the shape of the problem this whole module solves. The next two lessons dig into the two decisions every read()/write() implementation has to make underneath that clean exterior: how does the driver even know data is ready (polling a status register vs. waiting for an interrupt — next lesson), and where does the device's memory actually live from the CPU's point of view (a dedicated I/O port space vs. an ordinary memory address — the lesson after that).

07 — Quick Reference

Glossary & Key Terms

Driver
The translation layer between one specific piece of hardware and a generic contract the rest of the kernel relies on, regardless of which device is actually attached.
driver_ops
bob_os's vtable of function pointers — name, type, probe, read, write, ioctl — that every driver fills in once and the kernel calls forever after.
probe()
The one-time, boot-time function that detects whether a device is actually present and performs its initial hardware setup.
devfs
The pseudo-filesystem mounted at /dev that maps device names to driver_ops pointers, with no on-disk state of its own.
Character device
A device exposing an unstructured, sequential byte stream with no meaningful random access — e.g. the keyboard.
Block device
A device exposing fixed-size, randomly addressable chunks — e.g. 512-byte disk sectors.
Network device
A device exposing discrete, variable-length packets with no fixed timing or size, arriving in send order.
ioctl
The escape hatch for device-specific control commands that don't fit the shape of read() or write().
vtable
A struct of function pointers that lets a single generic call site dispatch to wildly different implementations, chosen at registration time rather than compile time.
VFS
The Virtual File System layer one level above devfs, giving processes a single open/read/write/close interface over both real files and device nodes.
