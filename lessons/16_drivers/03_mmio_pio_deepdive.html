Every driver eventually has to read or write a device register. On x86 there are two entirely separate ways to do that: dedicated IN/OUT instructions reaching into a completely separate 64KB I/O address space, or ordinary loads and stores reaching into the same physical address space RAM lives in. bob_os uses both, in different drivers, and the choice was never arbitrary.

00 — Where We Left Off

You've Been Using Both, All Along

Go back through the drivers you've already written and you'll find both addressing models sitting right next to each other, unremarked. vga.c writes characters by storing directly into a pointer at 0xB8000 — an ordinary C write, no special instruction. pic.c, keyboard.c, and disk.c all call outb()/inb() — wrappers around the x86 OUT/IN instructions — targeting ports like 0x20, 0x60, and 0x1F0. Same CPU, same kernel, two fundamentally different ways of reaching hardware. This lesson is about what that difference actually is, and why x86 ended up with both instead of just one.

01 — A Separate Universe of Addresses

Port-Mapped I/O: x86's Dedicated Instructions

x86 CPUs have always had a second, completely separate address space just for talking to hardware — 65,536 numbered "ports," accessed only through two dedicated instructions, IN and OUT. Critically, port number 0x60 and memory address 0x60 are not the same location at all — they live on entirely different buses, and an ordinary load/store instruction can never reach a port no matter what address you compute.

/* io.h — bob_os's I/O port helpers, real code */
static inline void outb(uint16_t port, uint8_t val) {
    __asm__ volatile ("outb %0, %1" : : "a"(val), "Nd"(port));
}
static inline uint8_t inb(uint16_t port) {
    uint8_t ret;
    __asm__ volatile ("inb %1, %0" : "=a"(ret) : "Nd"(port));
    return ret;
}

Three real drivers already in this project depend on exactly this mechanism:

💡 Why an Index/Data Pair? (0x3D4 / 0x3D5)
The VGA CRTC has far more internal registers than it has I/O ports allocated to it, so it uses a common trick: write the register number you want to 0x3D4 (the index port), then read or write the actual value through 0x3D5 (the data port). Two physical ports end up addressing dozens of logical registers — a workaround born entirely from PMIO's scarce, fixed 64KB space. MMIO devices, with the whole physical address space to spread out in, rarely need this trick at all.

Port I/O also has its own instruction-level rule that ordinary memory access doesn't: IN/OUT are inherently ordered and uncacheable — the CPU never reorders or caches a port access the way it might a regular memory load, because doing so would silently break hardware that expects register reads and writes to happen exactly once, in exactly the order issued.

02 — Hardware Registers, Disguised as RAM

Memory-Mapped I/O: Ordinary Loads and Stores

MMIO takes the opposite approach: instead of a separate address space, the device's registers are mapped directly into the same physical address range that RAM occupies. From the CPU's point of view there is no special instruction at all — a plain load or store, the same one you'd use to read an int off the stack, is all it takes.

You've already used this. The VGA text buffer at 0xB8000 isn't RAM — physical addresses in that range are wired by the PC's memory controller straight to the VGA card, which watches for writes and updates the screen accordingly. But nothing about the C code that touches it looks any different from touching an array:

/* This is genuinely how vga.c writes to the screen — plain pointer writes */
volatile unsigned char *vga = (volatile unsigned char *)0xB8000;
vga[0] = 'A';      /* character cell 0 */
vga[1] = 0x0F;     /* its attribute byte -- black bg, white fg */

No outb(), no port number, no dedicated instruction — just a pointer. The volatile qualifier matters enormously here for a reason specific to MMIO: it tells the compiler this memory can change or have side effects the compiler can't see, so it must never optimize away, reorder, or cache these reads/writes the way it freely would for a normal variable.

0x00000 – 0x9FFFF — Conventional RAM
0xA0000 – 0xBFFFF — Video Memory (0xB8000 = VGA text)
0xC0000 and up — ROM / More RAM / Extended Memory

A slice of the classic x86 physical memory map. Note that 0xB8000 sits inside ordinary physical address space, sandwiched between conventional RAM below and more RAM above it — that's the entire point of MMIO: the device didn't get its own address space, it got a reserved slice of the normal one.

Side note — this is also why the paging lesson matters here. Once paging is enabled, 0xB8000 stops meaning "physical address 0xB8000" for any code running through the page tables — it means "whatever physical frame is currently mapped to that virtual address." bob_os identity-maps the low 4MB precisely so that 0xB8000 keeps pointing at the real VGA hardware even after paging comes online. MMIO devices always live at a fixed physical address; it's the driver's (and the page table's) job to make sure a virtual address actually resolves there.
03 — Watch the Instructions Diverge

An IN Instruction vs a Load

Same CPU, same goal — get one byte from a device — two completely different paths through the hardware. Run each and watch which bus the request actually travels on.

▶ Choose an access type

The PMIO path needs a dedicated instruction (IN) that the CPU recognizes as "route this to the I/O address space, not the memory bus." The MMIO path needs nothing special at all — the CPU can't even tell, at the instruction level, that vga[0] isn't a completely ordinary RAM access. The distinction is made once, upstream, by how the motherboard's address decoding is wired — not by the instruction itself.

⚠️ The Sharp Edge of MMIO: Caching
Ordinary RAM benefits enormously from CPU caches — read the same address twice, get the cached value instantly. That is exactly the wrong behaviour for a hardware register: if a device updates a status bit and the CPU keeps serving a stale cached copy, the driver can spin forever waiting for a change it will never observe. This is why MMIO regions must be mapped as uncacheable (via page table attributes) and touched only through volatile pointers — two separate safeguards against two separate optimizers (the CPU's cache and the compiler) that would otherwise "helpfully" break device access.
05 — The Industry's Answer

Why Modern Hardware Prefers MMIO

If both models work, why does virtually every modern peripheral — GPUs, NVMe drives, network cards — lean almost entirely on MMIO, using PMIO for at most a few legacy compatibility registers?

✅ MMIO's advantages compound

One uniform addressing model for both RAM and devices means the compiler needs no special support, ordinary pointers and structs can describe register layouts, and a device can claim as much address space as it needs — a modern GPU maps hundreds of megabytes of registers and framebuffer this way. It's also the only option on architectures (ARM, RISC-V) that never had a separate I/O space to begin with, so MMIO is the addressing model every architecture agrees on.

📜 PMIO survives mostly as legacy

x86's I/O ports date to the 8-bit era, when a dedicated, narrow, fast bus for device access made real sense next to a small memory space. Decades of backward compatibility mean the PC platform's oldest devices — the PIC, PS/2 controller, legacy ATA — still answer on the same ports they always did. New designs almost never choose PMIO on purpose anymore; it persists because replacing it would break things that still depend on it.
The one-line summary MMIO won because "just a pointer" beats "a whole separate instruction set" almost everywhere it's tried. Uniform addressing, ordinary compiler support, and unlimited-by-comparison address space made MMIO the default; PMIO survives on x86 as the address space the very oldest, simplest devices never left.
06 — One Step Further

How PCIe Devices Choose Their Address

Modern PCIe devices don't get a hardwired address the way the VGA card's 0xB8000 is fixed by decades of convention. Instead, each PCIe device advertises, through its configuration space, how much address space it needs via up to six Base Address Registers (BARs) — and the BIOS/firmware or OS assigns each BAR an actual base address at boot, mapping the device's registers into whichever free physical range happens to be available.

  1. Device declares its needsEach BAR reports how large a region the device wants (e.g. "I need 16MB, memory-mapped, prefetchable") and whether it wants memory space or, on x86, legacy I/O space.
  2. Firmware assigns real addressesAt boot, the BIOS/UEFI (or the OS's PCI enumeration code) walks the PCI bus, reads every device's BAR requests, and programs each BAR with an actual, non-conflicting physical base address.
  3. The driver reads the assigned BAR to find its deviceA driver never hardcodes "my registers are at 0xFEB00000" the way bob_os's VGA driver hardcodes 0xB8000 — it reads the BAR value the firmware assigned, at runtime, and maps its registers from there.
  4. Almost all of it is MMIOThe overwhelming majority of PCIe BARs request memory-mapped space; a legacy I/O BAR is rare and mostly exists for compatibility with software that still expects old-style ports.
✅ Tying It Back to bob_os
bob_os's drivers are simpler than this on purpose — 0xB8000, 0x1F0, and friends are all hardcoded, fixed-forever addresses baked into the PC platform's ancient conventions, with no negotiation required. A real PCIe NIC or NVMe driver would instead read its BAR at probe() time to discover where its MMIO registers landed this boot, then map that region before touching a single register. Same driver_ops shape from the first lesson in this module — probe/read/write/ioctl — just with one more step at the very top of probe().
07 — Quick Reference

Glossary & Key Terms

Port-Mapped I/O (PMIO)
x86's separate 64KB address space for hardware, accessed only via the dedicated IN and OUT instructions.
Memory-Mapped I/O (MMIO)
Device registers mapped into the same physical address space as RAM, accessed with ordinary load/store instructions.
I/O Port
A numbered address (0–65535) in x86's PMIO space, e.g. 0x60 for the keyboard data register.
IN / OUT
The x86 instructions that read from and write to I/O ports — the only way to reach PMIO space.
Index/Data Port Pair
A pattern (e.g. VGA CRTC's 0x3D4/0x3D5) where one port selects a register number and a second port reads or writes its value, used to address more registers than available ports.
volatile
A C qualifier telling the compiler a memory location can change outside its control, disabling caching/reordering optimizations that would otherwise break MMIO access.
Uncacheable Memory
A page-table attribute forcing the CPU to skip its cache for a memory region — required for MMIO so register reads always see live hardware state.
Base Address Register (BAR)
A PCI/PCIe configuration-space register through which a device requests address space, later assigned a real base address by firmware or the OS.
Framebuffer
A block of MMIO memory a display device reads continuously to produce its output — bob_os's VGA text buffer at 0xB8000 is one.
Address Decoding
The motherboard-level logic that routes a given physical address (or port number) to the correct chip — RAM, VGA, or another device — invisible to the CPU instruction itself.
