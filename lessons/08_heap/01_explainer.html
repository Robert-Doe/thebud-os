Building malloc()
From Scratch

Every user-space program you've ever written got malloc() for free, supplied by libc. The kernel has no such luxury — it is the thing libc eventually calls down into. This page is about the single idea that makes a from-scratch allocator possible: a linked list of free chunks, threaded through the very memory it manages, with no separate bookkeeping table anywhere.

00 — The Problem

Why the Kernel Needs Its Own Heap

In every C program you've written before this project, when you called malloc(64), you were calling into glibc (or musl, or whatever libc your platform ships). That library has already done the hard part: it asked the OS for a big slab of memory via brk() or mmap(), and then it carves that slab into whatever sizes your program asks for. You never had to think about where the memory inside that slab actually comes from.

Now flip the perspective. bob_os is the OS. There is no layer underneath it to call malloc() on. By Module 06 the kernel has a Physical Memory Manager (the PMM) that can hand out whole 4 KB pages — and only whole pages. But kernel code constantly needs small, oddly-sized, dynamically-lived chunks: a 32-byte process control block here, a 96-byte linked-list node there, a 12-byte string buffer somewhere else. Rounding every single one of those up to a full page would be catastrophic waste — a 12-byte allocation eating an entire 4096-byte page is over 99.7% wasted space.

The Aha Moment
A heap allocator is the software layer that sits between "the PMM hands out whole pages" and "kernel code wants arbitrary-sized chunks." It takes a small number of pages, and subdivides them into as many differently-sized pieces as needed — handing pieces out with kmalloc(), and taking them back with kfree(). Everything below this page is about exactly how that subdividing actually works, with zero help from any pre-existing allocator.

This is genuinely a "turtles all the way down, until they aren't" moment. User-space malloc() is implemented in terms of pages the kernel hands it. The kernel's own kmalloc() is implemented in terms of pages its own PMM hands it. Same problem, one level lower, and this time you're the one writing the solution.

Naming convention: bob_os calls its kernel allocator kmalloc()/kfree() rather than malloc()/free() — this mirrors real kernels (Linux's own internal allocator is also called kmalloc()). The "k" is just a reminder that this is the kernel's private heap, not a process's user-space heap. The underlying idea is identical either way, which is why this lesson uses "malloc" and "kmalloc" interchangeably when talking about the concept.
01 — The Core Idea

The Free List: Bookkeeping With No Bookkeeping

Here's the problem an allocator has to solve, stated plainly: given a pool of raw memory, and a stream of requests like "give me 64 bytes," "give me 128 bytes," "here, take this 64 bytes back," "give me 200 bytes" — how do you keep track of which parts of the pool are currently free, without spending memory outside the pool to track it?

You could imagine a separate array somewhere: { address: 0x1000, size: 256, free: true }, one entry per chunk. That works, but it has an ugly property: you don't know in advance how many chunks there will be, so that array itself needs its own dynamic memory — which is exactly the problem you're trying to solve in the first place. Circular.

The trick that breaks the circularity Store the bookkeeping inside the memory being managed. Every free chunk's own bytes double as a tiny record: "I am free, I am this big, and here's where the next free chunk is." No external table required — the free memory tracks itself.

This is the free list: a singly-linked list of every currently-unused chunk of memory, where the list nodes aren't allocated separately — they are the free chunks. The first few bytes of each free chunk are repurposed to hold a small header, and that header's "next" field points at the next free chunk somewhere else in the pool. Follow the chain, and you've walked every free chunk in the heap without a single byte of memory spent outside the heap itself.

Four chunks laid out contiguously in the heap pool. Only two of them (B and D) are actually part of the free list — their headers hold "next" pointers chaining them together. The used chunks A and C simply aren't in the chain at all; nothing ever needs to walk to them.

Why "Threaded Through Memory" Is the Right Phrase
Notice that chunk B's header and chunk D's header are physically far apart, separated by a used chunk (C) sitting between them in the pool. The free list doesn't care about physical adjacency — it's a logical chain built purely out of "next" pointers, laid on top of whatever the physical layout happens to be. That's exactly what "threaded through the underlying memory" means: the list is the memory, just interpreted a certain way.
02 — The Anatomy of a Chunk

The Block Header: Metadata Riding Along For Free

Every chunk in the pool — free or used — starts with a small fixed-size header immediately followed by the chunk's usable data area. The header is the only overhead the allocator ever pays per chunk, and in a minimal design it needs to answer just two or three questions:

  • How big is this chunk's data area? — a size field, so kfree() and kmalloc() both know exactly how far the data extends before the next chunk's header begins.
  • Is it currently free or in use? — a one-bit flag (often packed into the low bit of another field, since a flag rarely needs a whole extra word to itself).
  • If it's free, what's the next free chunk? — a next pointer, present in the classic explicit free-list design taught here. (You'll see in the grounding callout below that bob_os's actual heap.c skips this field and finds the next chunk by pure arithmetic instead — both are valid, and the trade-off is worth understanding.)
C — the textbook explicit free-list headertypedef struct free_block {
    uint32_t          size;   /* bytes of usable data, NOT including this header */
    uint32_t          is_free; /* 1 = free, 0 = in use */
    struct free_block *next;  /* next chunk in the free list (garbage/unused when in use) */
} free_block_t;

/* One chunk in memory looks like this:
 *
 *   [ free_block_t header ][ ......... usable data ......... ]
 *    ^ size, is_free, next   ^ this is the pointer malloc() returns
 */
The Aha Moment
The header lives immediately before the data area, at a fixed, predictable offset: exactly sizeof(free_block_t) bytes before whatever pointer the caller ends up holding. That single fact — a fixed, known distance between "the pointer the caller has" and "the header describing it" — is the entire mechanism that lets kfree() work with no lookup table. Hold onto this; the next two sections are just this idea, played out in both directions.

03 — Answering It Directly

Why Does malloc() Return a Pointer Past the Header?

This is the detail that trips people up the first time they read allocator source: kmalloc() never hands back a pointer to the header it just found. It hands back a pointer to the byte immediately after the header — the start of the usable data area. Once you see why, it becomes obvious it couldn't work any other way.

  1. The caller only wants to use the data. When kernel code calls kmalloc(64), it wants 64 usable bytes to store a struct in. It has no business reading or writing the header — that's the allocator's own private bookkeeping, and if the caller could freely scribble over the size/flags/next fields, one buggy write would corrupt the entire heap's internal structure.
  2. So the returned pointer must skip the header entirely. If the chunk starts at address 0x2000 and the header is 8 bytes, the caller's usable region starts at 0x2008 — and that's exactly the address kmalloc() returns. In C this is just pointer arithmetic on the header type: return (void*)(header_ptr + 1); — "add 1" to a free_block_t* advances by sizeof(free_block_t) bytes automatically.
  3. This keeps the header invisible and safe by construction. The caller never even needs to know a header exists. It just has a plain pointer into the middle of the pool that behaves exactly like memory from any other allocator. The header is "hidden in plain sight" a fixed number of bytes to the left.
▶ Watch kmalloc(64) search the free list and return a pointer past the header
The Pointer Math, Spelled Out
If a chunk's header sits at address H and the header type is HDR_SIZE bytes wide, the data area starts at exactly H + HDR_SIZE. That's the address returned to the caller. Go the other direction — data_ptr − HDR_SIZE — and you're back at the header. This is a plain, constant-time subtraction; no search, no table, no metadata lookup by address. That reversibility is the whole point, and it's exactly what the next section is about.
04 — Answering It Directly

How free() Finds Its Way Back

Here's the question that makes the whole design click into place: when kernel code calls kfree(ptr), all it hands the allocator is a bare pointer — the same one kmalloc() returned earlier. No size, no extra info, nothing. How does kfree() know how big the chunk is, or how to put it back in the free list?

The answer is the mirror image of section 03. Since kmalloc() always returns header_address + HDR_SIZE, kfree() can always recover the header by doing the exact opposite: subtract HDR_SIZE (or, in typed pointer arithmetic, subtract 1 from a header-typed pointer) from whatever address it was given. No searching. No guessing. The header was never lost — it was sitting exactly HDR_SIZE bytes to the left the entire time.

C — the textbook kfree()void free(void *ptr) {
    if (ptr == NULL) return;

    // Step back from the data pointer to find the header again —
    // this is possible ONLY because kmalloc() always returned
    // header + 1, so header is always exactly ptr - 1 away.
    free_block_t *blk = (free_block_t *)ptr - 1;

    blk->is_free = 1;

    // Relink it into the free list — here, pushed onto the front
    blk->next  = free_list_head;
    free_list_head = blk;
}
▶ Watch kfree(ptr) walk backward to the header and relink it
This Is the Whole Trick
No separate table ever maps "address 0x2008 → its size is 64 bytes." That mapping doesn't need to exist as a table, because it's computable: walk back HDR_SIZE bytes and read it straight out of the header that was there all along. This is why a free-list allocator needs zero memory overhead beyond the headers themselves — the headers are the entire bookkeeping system, and they travel with the memory they describe.

One consequence worth sitting with: this is also exactly why calling kfree() on a pointer that kmalloc() never actually returned is undefined and dangerous. kfree() trusts the caller completely — it will happily step back HDR_SIZE bytes from whatever address it's handed and reinterpret those bytes as a header, size and all. Hand it a pointer into the middle of an array, or a stack address, and it will cheerfully corrupt whatever bytes happen to sit there, because there is no way for it to verify the pointer's origin.

05 — Grounding This in bob_os

What 08_heap/heap.c Actually Does Differently

Everything above described the classic explicit free list — free chunks carry a literal next pointer, so walking the free list only ever touches free chunks. bob_os's real implementation in 08_heap/heap.c uses a close cousin called an implicit free list, and it's worth seeing exactly how it differs, because both approaches are common in real allocators.

C — bob_os's actual header, from 08_heap/heap.cstruct block_header {
    uint32_t size;    /* bytes of data (not including this header) */
    uint32_t flags;   /* bit 0: USED(1) or FREE(0) */
};
/* Notice: no `next` field at all. */

Instead of a next pointer, bob_os walks every chunk — free and used alike — by pure address arithmetic: next_chunk = (char*)current + HDR_SIZE + current->size. Since every chunk's header records its own size, and chunks are laid out back-to-back with no gaps, that formula always lands exactly on the start of the following chunk's header, whether that chunk happens to be free or in use. A special zero-size "sentinel" header marks the very end of the pool so the walk knows when to stop.

Explicit free list (taught above)

kmalloc() only ever visits free chunks — the next chain skips used ones entirely, which can be faster when much of the heap is in use. Costs an extra pointer-sized field in every chunk's header, whether that chunk is currently free or not.

Implicit list (bob_os's actual heap.c)

kmalloc() walks every chunk, free or used, to get from one to the next. Simpler code, a smaller 8-byte header, and one fewer field to keep consistent — at the cost of visiting used chunks it can never allocate from during a search.
Same Core Trick, Either Way
Whichever style you pick, the answer to "why does malloc return a pointer past the header" and "how does free find its way back" is identical. Both designs place a header immediately before the data and hand back header + HDR_SIZE. bob_os's kfree() does the exact same (struct block_header *)ptr - 1 step-back you saw in section 04 — go re-read the real kfree() in 08_heap/heap.c and you'll recognize it immediately.

bob_os's kfree() also coalesces — merging a freshly-freed chunk with the block immediately after it if that one is free too, so the heap doesn't slowly disintegrate into unusable slivers. That's a big enough topic to earn its own lesson: the next page in this module, First-Fit, Best-Fit, Worst-Fit, covers exactly how a real search picks which free chunk to use, and what coalescing buys you.

06 — Common Bugs

Where This Design Bites You

A hand-rolled free-list allocator is small enough to fully understand, but that same simplicity means it has almost no defenses against misuse. Three bugs show up constantly:

BugWhat Actually HappensWhy It's Dangerous
Double freekfree(ptr) called twice on the same pointerThe chunk gets linked into the free list twice, so a later kmalloc() can hand the same memory out to two different callers simultaneously.
Heap buffer overflowWriting past the end of an allocated chunk's data areaOverwrites the next chunk's header — corrupting its size/flags/next fields, which are trusted blindly on the next allocation or free.
Freeing a bad pointerkfree() called on something kmalloc() never returnedThe allocator steps back HDR_SIZE bytes and treats whatever's there as a real header — instant heap corruption, as described in section 04.
Why User-Space malloc() Is Harder to Corrupt
Production allocators like glibc's ptmalloc add extra "canary" values around headers specifically to detect this class of corruption before it causes silent damage — trading a little memory and CPU for a loud crash instead of a subtle, hard-to-debug heap corruption bug later. bob_os's heap.c deliberately skips this for teaching clarity: the goal here is to see the mechanism working, not to make it bulletproof.
07 — Quick Reference

Glossary & Key Terms

Heap Allocator
The software layer that subdivides pages from the PMM into arbitrary-sized chunks, handed out via kmalloc() and reclaimed via kfree().
Free List
A linked chain of currently-unused chunks, threaded through the pool's own memory with no external bookkeeping table.
Block Header
A small fixed-size struct placed immediately before every chunk's usable data, recording at minimum its size and free/used state.
Explicit Free List
A free-list design where each free chunk's header carries a literal next pointer, so searches only visit free chunks.
Implicit List
bob_os's real design: no next field — every chunk (free or used) is reached from the previous one via size-based address arithmetic.
Sentinel Block
A zero-size, always-used header placed at the very end of the pool, marking where the implicit-list walk should stop.
Coalescing
Merging a newly-freed chunk with an adjacent free chunk into one larger chunk, preventing the heap from fragmenting into tiny unusable slivers.
kmalloc() / kfree()
bob_os's kernel-space equivalents of user-space malloc()/free() — same concept, running with no libc underneath them.
