A single free list with first-fit or best-fit search is honest, teachable, and genuinely how bob_os's heap.c works. It is also not what Linux, glibc, or any serious kernel actually ships. This page is a tour of three ideas — buddy systems, segregated bins, and slab allocators — that all attack the same weakness: a plain free list has to search, and searching costs time.

00 — Where We Left Off

The Bill For a Plain Free List

Two lessons ago you built the core idea: a free list threaded through memory itself, headers doing all the bookkeeping. One lesson ago you saw that which chunk gets chosen from that list — first-fit, best-fit, worst-fit — trades search speed against fragmentation, and that coalescing is the standard patch-up afterward. All of that is real, correct, and it's exactly what bob_os's 08_heap/heap.c does.

It's also, structurally, an O(n) search every single time. Whether it's first-fit's best-case early exit or best-/worst-fit's mandatory full scan, the allocator is walking a linked list, one chunk at a time, comparing sizes. For a kernel with a few dozen live allocations, that's invisible. For a real OS doing millions of allocations per second across every subsystem, that linear search becomes a real, measurable bottleneck. This page is about the three main ways production allocators sidestep it.

The Shape of Every Answer Below
Notice the pattern before you even see the details: buddy systems, segregated bins, and slabs all trade a little bit of structure imposed in advance (power-of-two sizes, fixed size classes, fixed object pools) for no search at all at allocation time. That trade — pre-organize now so you don't have to search later — is the single idea underneath all three designs.
01 — Design One

The Buddy Allocator

A buddy allocator starts from a single, powerful restriction: every block handed out is a power-of-two size — 4 KB, 8 KB, 16 KB, and so on, never anything in between. In exchange for that restriction, splitting and — crucially — merging become almost trivially cheap.

Splitting: halve until it fits

Say the allocator manages one 512 KB region and a request for 100 KB arrives. The smallest power-of-two that covers 100 KB is 128 KB. To produce a 128 KB block, the allocator splits the 512 KB block in half (two 256 KB blocks), then splits one of those halves again (two 128 KB blocks), and hands out one of those. Each split produces exactly two equal "buddy" blocks — and that word "buddy" is the whole trick.

Merging: the buddy address is a computation, not a search

When a block is freed, the allocator needs to know: is my buddy — the other half I was split from — also free right now? If so, merge back into the larger parent block immediately. The genuinely elegant part is how it finds that buddy: because block sizes are powers of two and blocks are aligned to their own size, a block's buddy address is always just its own address with one bit flipped — no pointer chasing, no list search, just a single XOR.

C — computing a buddy's address// block_addr must be aligned to block_size (a power of two),
// relative to the start of the managed region.
uintptr_t buddy_of(uintptr_t block_addr, size_t block_size) {
    return block_addr ^ block_size;   // flip the one bit that matters
}

// On free: check the buddy. If it's ALSO free, merge and repeat
// one level up — this is what makes buddy coalescing so cheap.
void buddy_free(uintptr_t addr, size_t size) {
    while (size < MAX_BLOCK_SIZE) {
        uintptr_t buddy = buddy_of(addr, size);
        if (!is_free(buddy, size)) break;  // buddy is in use — stop merging
        remove_from_free_list(buddy, size);
        addr = addr & ~size;    // address of the merged parent block
        size <<= 1;
    }
    add_to_free_list(addr, size);
}
The Aha Moment
A plain free-list allocator finds an adjacent free neighbor by walking to it — following pointers or address arithmetic through memory. A buddy allocator finds its neighbor by computing its address directly from a size and an XOR. That's the entire performance win: coalescing goes from "search" to "arithmetic," and it composes — merging one level can immediately trigger checking the next level up, all the way back to one giant free block if the whole region happens to empty out.

This is not a hypothetical design — it is literally how Linux's low-level page allocator works. Linux's buddy allocator (visible in /proc/buddyinfo on any running Linux machine) manages physical page frames in exactly these power-of-two "orders," from order 0 (a single 4 KB page) up to order 10 (4 MB) by default. Every alloc_pages() call in the Linux kernel ultimately goes through this exact split/merge machinery.

03 — Grounding This in bob_os

Does bob_os's PMM Use a Buddy System?

Worth checking your assumptions against the real code: bob_os's Physical Memory Manager (06_pmm/pmm.c, carried forward into every later module including 08_heap) does not use a buddy system. It uses something simpler — a flat bitmap, one bit per 4 KB page, where 1 means free and 0 means used.

C — bob_os's actual PMM, from pmm.cstatic uint8_t bitmap[PMM_MAX_PAGES / 8];  /* one bit per page */

// pmm_alloc_page(): scan the bitmap for the first free bit —
// an O(n) linear scan over pages, byte by byte.
void *pmm_alloc_page(void) {
    for (uint32_t i = 0; i < byte_count; i++) {
        if (bitmap[i] == 0) continue;  // all 8 pages used, skip fast
        // ...find the free bit, mark it used, return that page...
    }
}

This is a deliberate, reasonable simplification for a teaching kernel: bob_os's PMM only ever hands out single, uniform 4 KB pages — it never needs to satisfy a request for "16 contiguous pages," so there's nothing for a buddy system's size classes to buy it. A bitmap scan is simple to write, simple to verify, and fast enough at the scale this project operates at.

bob_os's PMM — bitmap

One bit per page, first-fit linear scan to allocate. Coalescing isn't really a concept here — there's nothing to merge, since every unit is already the same fixed size. Simple, auditable, O(n) worst case.

Linux's low-level allocator — buddy

Powers-of-two block sizes, O(log n) split/merge, and — critically — supports handing out large contiguous runs of physical pages efficiently, which a plain bitmap scan struggles to do well once memory gets fragmented at the page level.
Same Family, Different Layer
Notice the shape of this comparison: it's exactly the shape of the first-fit/best-fit/worst-fit lesson, one layer down. bob_os's PMM made the same kind of simplicity-over-scalability trade at the physical-page level that its heap allocator made at the byte level. If you ever extend this project to hand out multi-page contiguous physical regions efficiently, a buddy system is precisely the upgrade path — this page is effectively a preview of that future module.
04 — Design Two

Segregated Free Lists — "Bins"

A different fix for "searching one big free list is slow": don't have one big free list. Instead, maintain many free lists, one per size class, and route every allocation straight to the list that already holds chunks of roughly the right size. This is the approach behind dlmalloc and glibc's ptmalloc — the allocator family behind most Linux user-space malloc() calls.

Small binsexact size
One free list per exact small size (e.g. every multiple of 8 bytes up to some threshold). An allocation request for 24 bytes goes straight to the "24-byte bin" — zero search, just a direct lookup by size.
Large binssize ranges
Above the small-bin threshold, exact-size bins stop being practical (too many possible sizes). Instead, each bin covers a range of sizes, sorted internally, and a best-fit-style search happens only within that one narrow bin.
FastbinsLIFO, no coalesce
glibc's optimization for the most common tiny sizes: a stack-like list that skips coalescing on free for extra speed, trading a bit of fragmentation risk for very hot allocation/free cycles (churn-heavy code paths).
C — the shape of a segregated-bin lookup// Conceptual sketch — NOT actual glibc source, but the same idea:
// route straight to the bin for this size class, no scanning.
struct free_block *bins[NUM_SIZE_CLASSES];

void *bin_malloc(size_t size) {
    int class_idx = size_to_bin_index(size);   // O(1) — just math on `size`
    if (bins[class_idx]) {
        struct free_block *blk = bins[class_idx];
        bins[class_idx] = blk->next;             // pop — no search inside this bin
        return (void*)(blk + 1);
    }
    return request_more_memory_for_bin(class_idx);
}
Why This Beats One Big Free List
A single free list forces every search to wade through chunks of every size, most of which are irrelevant to the current request. Segregating by size class means a request for a 32-byte object never has to look at, skip past, or even know about a 4-kilobyte chunk sitting somewhere in the heap — it goes straight to the 32-byte bin. This is the direct, structural answer to the O(n) search problem from section 00: don't search a mixed list at all.

The trade-off: more bookkeeping structure overall (many list heads instead of one), and a chunk freed in one size class doesn't automatically help satisfy a request in a different size class without extra coalescing-and-resizing logic. Real implementations like ptmalloc do coalesce across bin boundaries when chunks merge into a larger size, then re-file the merged chunk into whichever bin now fits it.

05 — Design Three

The Slab Allocator

Bins solve "route requests to the right size class." Slabs go one step further, for one specific and extremely common kernel pattern: objects that are not just similarly-sized, but identically sized and allocated/freed constantly. Think process control blocks, file descriptor structs, inode structs — the kernel creates and destroys thousands of these, always the exact same size, for the entire lifetime of the system.

A slab allocator pre-carves a chunk of memory (a "slab," usually one or a few physical pages) into an array of fixed-size, ready-to-use object slots — no header per object, no size field, no free/used flag beyond a simple bitmap or free-list-of-slots for the whole slab. Handing out an object is popping a slot off a per-slab free list; freeing is pushing it back. There's no splitting, no coalescing, no size search, ever — because every object in this slab is already exactly the size that's needed.

C — the shape of a slab cachestruct slab_cache {
    size_t object_size;        // e.g. sizeof(struct pcb) — fixed, known in advance
    struct slab *slabs_partial;  // slabs with some free slots
    struct slab *slabs_full;     // slabs fully in use
    struct slab *slabs_empty;    // slabs entirely free — candidates to release
};

void *slab_alloc(struct slab_cache *cache) {
    struct slab *s = cache->slabs_partial ? cache->slabs_partial
                                            : grow_cache(cache);
    return pop_free_slot(s);   // O(1) — every slot is already object_size
}
Why Not Just Use kmalloc() For Everything?
You could route every PCB allocation through the general-purpose kmalloc() from lesson one of this module — it would work. But every one of those allocations would pay a header (8 bytes in bob_os's design), risk internal fragmentation from rounding, and contend with whatever else is in the free list at that moment. Multiply that by thousands of PCB allocations over a kernel's lifetime, and a slab dedicated purely to "PCB-sized objects" removes all three costs at once, for exactly the objects that are allocated often enough for it to matter.

This is exactly why Linux's actual internal allocator is a two-tier system: kmalloc() for general-purpose, variable-sized kernel allocations (itself backed by size-class bins, much like section 04), and a dedicated slab layer (historically SLAB, now more often SLUB) sitting underneath and alongside it specifically for the kernel's hot, fixed-size, frequently-recycled object types.

Naming trivia: Linux has shipped three different slab-family implementations over the years — the original SLAB (per-CPU object caches, complex but fast), SLUB (the modern default since the mid-2000s, simpler internal structure with comparable performance), and SLOB ("Simple List Of Blocks," a tiny-footprint variant for memory-constrained embedded systems that behaves closer to a plain free list). All three implement the same slab concept described above — they differ in internal bookkeeping, not in the core idea.
06 — Tying It Back

bob_os's Free List: The Training Wheels Version of All Three

Here's the reassuring part. Nothing in this lesson makes lesson one's design "wrong" — it's the same conceptual DNA, minus the optimizations that only start paying off at scale. Look at how directly each idea traces back to what you already built:

The one idea underneath everything in this module Every allocator, from bob_os's simplest free list to Linux's full buddy + slab stack, answers the exact same two questions: "which free chunk do I hand out?" and "how do I get merged-back space when something's freed?" The three designs in this lesson just answer those questions with pre-computed structure instead of runtime search — faster, but built on identical foundations to what you already understand.

You now have the full arc of this module: why a kernel needs its own allocator at all, the free-list mechanism that makes one possible with zero external bookkeeping, the strategy question of which chunk to pick and the fragmentation trade-offs that follow, and finally how production systems layer smarter structure on top of that same free-list core to make allocation and coalescing fast at scale. bob_os's heap.c is a complete, correct allocator — it's simply an early point on a design spectrum that Linux, glibc, and every serious kernel continue further down.

07 — Quick Reference

Glossary & Key Terms

Buddy Allocator
Manages memory in power-of-two block sizes; splits blocks in half to satisfy requests and merges a freed block with its "buddy" via address arithmetic (XOR), not a search.
Buddy
The other half a block was split from — always computable as address ^ block_size due to power-of-two alignment.
Order
The exponent describing a buddy block's size relative to a base unit — e.g. order 0 = one page, order 3 = eight pages, in Linux's page allocator.
Segregated Free Lists / Bins
Multiple free lists, one per size class, so an allocation request is routed directly to relevant-sized chunks instead of scanning a single mixed list.
Size Class
A specific size (or narrow range) that one bin is dedicated to — small bins are often exact sizes, large bins cover ranges.
Fastbin
glibc's LIFO, non-coalescing bin for very common small sizes, optimized for allocation/free churn at the cost of some fragmentation risk.
Slab Allocator
Pre-carves memory into fixed-size object slots for one specific, frequently-allocated type, eliminating per-object headers and splitting entirely.
Physical Memory Manager (PMM)
bob_os's page-granularity allocator (06_pmm/pmm.c), implemented as a flat bitmap rather than a buddy system.
