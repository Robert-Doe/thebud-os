Here's the thing almost nobody tells you about WebSockets: there is no separate "WebSocket protocol" negotiation happening on some other port. A WebSocket connection is born as a completely ordinary HTTP GET request — the same kind your browser sends for every image, script, and stylesheet on a page. It just carries three unusual headers asking politely: "Would you mind switching to something else, on this exact same connection?"

00 — Setting the Scene

What Plain HTTP Can't Do

If you've worked through the sibling lesson on HTTP and TLS (23_http_tls in this series), you already know the shape of a normal HTTP exchange: the client sends one request, the server sends back exactly one response, and then — unless the client asks again — the conversation is over. The server can never speak first. It cannot tap you on the shoulder and say "hey, new chat message arrived" unless you walk over and ask it, over and over, "anything new? anything new? anything new?"

For a stock ticker, a multiplayer game, a chat app, or a live collaborative document, that limitation is a real problem. You want the server to be able to push data the moment it exists, and you want it to flow in both directions without renegotiating a new connection for every single message. That's the gap WebSockets were built to close — and this lesson is about exactly how a browser and server agree to open that channel, using nothing but a single, perfectly ordinary-looking HTTP request as the doorway in.

You might reasonably ask: why not just define WebSockets as their own thing on their own port, the way, say, SSH lives on port 22? The answer is almost entirely about deployability. By the time WebSockets were standardized (RFC 6455, 2011), the web already had a decade of firewalls, corporate proxies, and load balancers configured around ports 80 and 443, and around the assumption that traffic on those ports looks like HTTP. A protocol that had to convince every network operator on Earth to open a new port would have taken years longer to become usable in practice. Starting as an HTTP request sidesteps that entire fight.

🔗 This Lesson Assumes You Know Plain HTTP
We are not going to re-derive request lines, header syntax, or status codes here — that's the job of 23_http_tls. What follows leans on that foundation directly: a WebSocket handshake is an HTTP/1.1 request and an HTTP/1.1 response, just with headers that mean something special. If header syntax feels shaky, that lesson is the right place to shore it up first.
01 — The Doorway In

It Starts as a Completely Ordinary GET

Open your browser's dev tools, go to the Network tab, and load a page that uses a WebSocket — you'll see it listed right alongside every other request. Same request line format, same headers block, same everything a plain HTML page fetch would use. From the network's point of view, absolutely nothing unusual is happening yet.

📄 A Normal GET (for a stylesheet)

GET /style.css HTTP/1.1
Host: example.com
Accept: text/css

A request for a resource, answered with a normal 200 OK and a body.

🔌 A WebSocket-Upgrade GET

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade

Still GET, still HTTP/1.1 — just carrying extra headers that change what happens next.

This is a deliberate design choice, not an accident. By reusing the exact same request format the entire web already speaks, WebSocket connections get to travel through the same infrastructure everything else does — proxies, load balancers, firewalls, and any middlebox that already knows how to forward an HTTP request. A brand-new, unrelated wire protocol invented from scratch would have hit compatibility walls everywhere. Piggybacking on HTTP's own Upgrade mechanism — a feature HTTP/1.1 has always had, for switching protocols mid-connection — sidesteps all of that.

It also means every ordinary rule you already know about HTTP requests still applies at this stage, because it genuinely still is an HTTP request. The handshake runs over the same TCP connection a plain fetch would use. It can (and in production, always should) run inside a TLS tunnel, using wss:// the same way https:// wraps a normal request. The browser attaches cookies for the target origin automatically. Same-origin rules, redirects, and even HTTP authentication challenges are all still in play for this one request — none of that machinery knows or cares yet that anything unusual is about to happen.

🎯 One Sentence to Keep Coming Back To
A WebSocket connection is 100% ordinary HTTP right up until the exact moment the 101 response finishes — and then, on that same wire, it is 0% HTTP ever again. Nearly every confusing thing about WebSockets (why they need Origin checks, why proxies sometimes break them, why the handshake looks so plain) falls out of taking that sentence completely literally.
02 — The Request, In Full

The Headers That Ask For an Upgrade

Here is a real WebSocket handshake request, byte for byte the kind a browser actually sends. Every line matters — nothing here is boilerplate.

Client → ServerGET /chat HTTP/1.1
Host: example.com
Upgrade: websocket              // "I want to stop speaking HTTP after this"
Connection: Upgrade            // "...specifically, this is an Upgrade request"
Sec-WebSocket-Key: dGhlIHNhbXBsZQ==  // 16 random bytes, base64-encoded
Sec-WebSocket-Version: 13       // the WebSocket protocol version, per RFC 6455
Origin: https://example.com     // which page's script opened this connection

Three headers are doing the actual work of requesting the switch, and it takes all three together — a server that only sees one or two of them isn't supposed to treat this as a WebSocket request at all:

Upgrade: websocketwhat
States the target protocol by name. This is the generic HTTP/1.1 Upgrade header — it could in principle name other protocols too, but in practice today it almost always means exactly this.
Connection: Upgradehow
Tells any intermediary reading this request that the Upgrade header should actually be honored for this particular connection — not silently stripped as an unrecognized header.
Sec-WebSocket-Keyproof
A fresh, random, base64-encoded value the client generates for this handshake alone. The server has to do real work with it — you'll see exactly what in a moment.

Two more headers round out a real handshake request, and they're worth naming even though they don't drive the actual switch:

Sec-WebSocket-Version= 13
Pins the client to a specific revision of the WebSocket protocol. If a server only supports a different version, it responds with 426 Upgrade Required and lists the versions it does support — a normal HTTP status code doing normal HTTP-style version negotiation.
Originsent automatically
The browser attaches this on every WebSocket handshake, unprompted, the same way it does for CORS-relevant fetches. Unlike normal cross-origin fetches, though, WebSockets don't enforce same-origin policy for you — reading and acting on this header is entirely the server's responsibility.
Why GET, and never POST? The WebSocket spec (RFC 6455) requires the handshake request to use GET specifically. There's no body to send, and using a method every HTTP server, proxy, and cache already understands as "fetch/negotiate a resource" keeps the handshake maximally boring and compatible — boring is exactly what you want from a step that has to survive being relayed through infrastructure it never asked to support.
03 — A Nonce, Not a Secret

Sec-WebSocket-Key: What It Actually Proves

It's tempting to look at Sec-WebSocket-Key and assume it's some kind of authentication or encryption secret. It isn't. It carries no permission, proves no identity, and is sent in the clear right there in the headers for anyone to read. What it does do is give the server something unpredictable to prove it actually processed this specific request, rather than replaying a cached, generic "yes, upgrade" response it had lying around from earlier.

💡 The Real Reason: Confused Proxies, Not Attackers
RFC 6455's own rationale for this dance is refreshingly unglamorous: it exists mainly to stop HTTP-naive caching proxies from getting confused. A proxy that doesn't understand WebSockets at all might otherwise cache a "101 Switching Protocols" response and later replay it for a completely different client's request — corrupting both connections. Forcing the accept value to be freshly, deterministically derived from this request's random key means a cached or blindly-copied response will never match, and a well-behaved client can detect the mismatch and refuse the connection.

So think of Sec-WebSocket-Key less like a password and more like a nonce — a number used once, whose only job is to make the server's reply provably tied to this exact exchange. Real security for a WebSocket connection comes from wss:// (WebSocket over TLS) and from the server validating the Origin header — not from this key.

04 — The Server Answers

101 Switching Protocols

If — and only if — the server understands WebSockets and is willing to proceed, it answers with an HTTP status line you'll basically never see anywhere else on the web: 101, not 200, not 204, not 101's much more famous cousin 404. Status code 101 exists in the HTTP spec specifically to mean "I'm honoring your Upgrade request; this connection is about to start speaking something other than HTTP."

Server → ClientHTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=  // computed from the client's key

Notice what's missing compared to a normal HTTP response: no Content-Length, no Content-Type, no response body at all. There's nothing to send in a body, because this response isn't delivering a resource — it's delivering permission. The moment this response finishes, the meaning of every subsequent byte on this TCP connection changes completely.

⚠️ A Plain HTTP Server Would Just... Ignore This
A web server with no WebSocket support isn't broken by an upgrade request — it simply doesn't recognize Upgrade or Sec-WebSocket-Key as meaningful, and answers with a normal HTTP response (maybe a 200 serving whatever /chat normally returns, or a 404). The client-side WebSocket API checks for exactly a 101 plus a correct Sec-WebSocket-Accept — anything else, and it treats the connection as failed rather than silently trying to speak WebSocket frames at a server that never agreed to listen for them.
05 — Proof of Understanding

Computing Sec-WebSocket-Accept

Here's the part that actually does the proving. The server can't just echo the client's key back, and it can't send a canned constant either — both would be indistinguishable from a dumb HTTP server or proxy blindly copying headers around. Instead, the server must run a specific, deterministic computation that only something which actually implements RFC 6455 would know to do.

  1. Take the client's Sec-WebSocket-KeyExactly as received: dGhlIHNhbXBsZQ==
  2. Append the fixed "magic GUID"A constant string defined in the spec, the same for every WebSocket implementation on Earth: 258EAFA5-E914-47DA-95CA-C5AB0DC85B11
  3. SHA-1 hash the concatenationProducing a 20-byte binary digest of dGhlIHNhbXBsZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11
  4. Base64-encode the digestTurning those 20 raw bytes into the printable string that becomes the header value
  5. Send it back as Sec-WebSocket-AcceptThe client independently re-runs steps 1–4 itself and checks the two values match, byte for byte
The Accept-Key Formula Sec-WebSocket-Accept = base64( SHA1( Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) ) For key dGhlIHNhbXBsZQ== the result is always s3pPLMBiTxaQ9kYGzzhZRbK+xOo= — try it yourself, it's deterministic every time.

Why does this prove anything? Because the "magic GUID" string is baked into the WebSocket specification itself — it means nothing, does nothing cryptographically clever, and isn't a secret (anyone can look it up in RFC 6455 in about ten seconds). Its entire job is to be a fixed fingerprint: only code that was deliberately written to implement the WebSocket handshake would know to append that exact string before hashing. A generic HTTP server, or a caching proxy just forwarding bytes around, has no reason to know that string exists — so it structurally cannot produce a correct Sec-WebSocket-Accept by accident.

📌 This Is Not Encryption or Authentication
Don't mistake this SHA-1-and-GUID dance for a security mechanism — it protects against nothing an actual attacker would care about; the GUID is public and the whole computation is public. What it protects against is accidental protocol confusion: a proxy or cache that doesn't understand WebSockets replaying a stale response, or a server that isn't running WebSocket-aware code stumbling into a "success" by coincidence. Real WebSocket security still comes entirely from wss:// (TLS) and server-side Origin validation.
05b — Extra Credit in the Same Handshake

Negotiating Subprotocols & Extensions

The three core headers get the connection open, but the very same handshake can carry two more optional headers that let the client and server agree on how they'll use the connection, before a single WebSocket frame has been sent.

Client → Server (extended)GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: chat, superchat       // "I can speak either of these app-level dialects"
Sec-WebSocket-Extensions: permessage-deflate // "...and I support compressing frames"
Server → Client (extended)HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: superchat          // server picks exactly one of the offered choices
Sec-WebSocket-Extensions: permessage-deflate // server agrees to compress
Sec-WebSocket-Protocolapplication-level
Lets the client offer a list of application-defined sub-protocols it can speak (a JSON chat format, a binary game-state format, an MQTT-over-WebSocket dialect). The server echoes back exactly one it also supports — never a list, never something the client didn't offer. This has nothing to do with the WebSocket protocol itself; it's a label for what the messages inside the frames will mean.
Sec-WebSocket-Extensionstransport-level
Negotiates modifications to the framing layer itself — most commonly permessage-deflate, which compresses frame payloads. Unlike the subprotocol header, the server's response can add negotiated parameters, and the extension must be one both sides genuinely implement, not just recognize by name.
🧩 Same Handshake, More Questions Answered at Once
All of this — the core upgrade, the accept-key proof, subprotocol selection, and extension negotiation — happens inside one single request/response pair. Nothing about this requires a second round trip. That's the payoff of piggybacking on HTTP's existing header mechanism: arbitrarily many small negotiations can ride along for free on a handshake that was going to happen anyway.

07 — The Turning Point

Same Socket, New Rules

This is the single most important sentence in this whole lesson, so it's worth saying plainly: after the 101 response, the underlying TCP connection does not close and reopen — it keeps running, but it stops speaking HTTP entirely. There is no more request line. There is no more status line. There are no more headers. Every byte that flows across that socket from this point forward is interpreted as part of the WebSocket framing protocol instead — a compact binary format built for sending discrete messages, in either direction, at any time.

This is exactly what "Switching Protocols" means as a literal, technical description, not just a friendly status-code name. HTTP got the connection open — TCP handshake, then one HTTP request, then one HTTP response — and then handed the exact same wire over to a completely different protocol that has nothing to do with methods, status codes, or headers ever again for the life of that connection.

🔑 One Handshake, Then Silence (From HTTP's Perspective)
Everything HTTP-shaped about a WebSocket connection happens exactly once, at the very start. After that single request/response pair, HTTP is completely out of the picture — no more headers, no more methods, no more status codes ever cross that socket again. Every message from here on is a WebSocket frame: small, binary, and — as the companion deep-dive lesson covers — dramatically cheaper per message than another round of HTTP ever could be.
What actually goes wrong if the accept key doesn't match? The client-side implementation is required to abort the connection immediately, treating it as a failed handshake — exactly as if the server had returned a 4xx error. It will not fall back to attempting WebSocket framing anyway. A mismatched (or missing) Sec-WebSocket-Accept is a hard stop, precisely because it's the one signal proving the other end genuinely speaks this protocol.

Once the switch has happened, the WebSocket framing layer defines a small, fixed vocabulary for what any given frame can mean — carried in a 4-bit opcode field in every frame's header. None of this existed in the HTTP phase; all of it is new, and it's what lets the connection stay alive and useful indefinitely instead of being a one-shot exchange.

0x1
Text frame (UTF-8 payload)
0x2
Binary frame (raw bytes)
0x8
Close frame (graceful shutdown)
0x9 / 0xA
Ping / Pong (keepalive)

That last pair matters more than it looks. Because the connection can now sit open and silent for minutes or hours between real application messages, either side can send a Ping frame at any time, and the other side is required to answer with a matching Pong — a lightweight heartbeat that lets both ends (and anything watching the connection, like a load balancer's idle-timeout logic) confirm the socket is still alive without the application ever needing to invent its own keepalive message format. None of this — pings, pongs, or a proper multi-step close handshake — has any HTTP equivalent, because HTTP was never designed to keep a connection meaningfully "alive" between exchanges in the first place.

✅ Why Reuse HTTP for the Handshake At All?
Because it means a WebSocket connection can start life looking exactly like any other web request — using the same port (80 or, with TLS, 443), passing through the same proxies, firewalls, and load balancers that were already configured to handle HTTP traffic, and carrying the same cookies and Origin header the browser would send anyway. The "weird" part (persistent, bidirectional, low-overhead framing) only kicks in after all of that ordinary infrastructure has already let the connection through.
08b — Reading the Failure Modes

What Can Go Wrong Along the Way

Because the handshake is just an HTTP request/response pair passing through ordinary web infrastructure, most WebSocket connection failures aren't exotic protocol bugs — they're one of a handful of well-understood breakdowns in that infrastructure, or in how strictly the two sides follow the spec. Knowing the short list makes debugging a failed new WebSocket(...) call far less mysterious.

SymptomLikely CauseWhy It Fails Here Specifically
Connection immediately closes, no 101 seenServer doesn't support WebSocketsAnswered with a normal HTTP response (200, 404, etc.) instead of 101 — client treats anything but 101 as a failed upgrade.
Handshake fails behind a corporate proxyProxy strips or rewrites Upgrade/ConnectionAn HTTP-naive intermediary that doesn't recognize these headers may drop them, silently downgrading the request to a plain GET.
"Accept" mismatch, connection abortedNon-compliant server implementationServer computed Sec-WebSocket-Accept incorrectly (wrong GUID, skipped base64, hashed the wrong string) — client's independent recomputation catches it.
403 during handshakeServer-side Origin check rejected the requestA well-configured server refuses upgrades from origins it doesn't recognize — the primary defense against cross-site WebSocket hijacking (CSWSH).
Handshake succeeds, but no subprotocol agreedNo overlap between client's offered list and server's supported setServer omits Sec-WebSocket-Protocol in its response rather than picking something the client never offered.
🔒 Origin Checking Is the Server's Job, Not the Handshake's
Nothing about the handshake mechanism itself prevents a malicious page on a completely different site from opening a WebSocket to your server — the browser will happily send the Origin header and any cookies for that domain, exactly as it would for any other cross-origin request. It is entirely up to the server to read that Origin header and reject connections from origins it doesn't trust. This is covered in depth, with vulnerable and fixed server code, in the companion browser module B18_websockets.
09 — Quick Reference

Glossary & Key Terms

WebSocket
A protocol providing a persistent, full-duplex message channel over a single TCP connection, established via an HTTP Upgrade handshake.
Upgrade Header
A standard HTTP/1.1 header naming the protocol a client wants the connection switched to — websocket in this case.
Connection: Upgrade
Tells intermediaries the Upgrade header should be honored for this specific hop-by-hop connection, not ignored.
Sec-WebSocket-Key
A fresh, random, base64-encoded nonce the client generates per handshake — proof material, not a secret or credential.
101 Switching Protocols
The HTTP status code meaning "request honored, and everything after this response uses a different protocol on this same connection."
Sec-WebSocket-Accept
The server's proof of understanding — deterministically derived from the client's key plus the fixed magic GUID, then SHA-1 hashed and base64-encoded.
Magic GUID
The fixed constant 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, defined in RFC 6455, appended before hashing to fingerprint real WebSocket implementations.
Frame
The basic binary unit of WebSocket communication after the handshake — replaces HTTP's request/response entirely for the life of the connection.
wss://
WebSocket over TLS — the encrypted counterpart to plain ws://, exactly as https:// relates to http://.
Origin Header
Sent automatically by the browser during the handshake, identifying which page's script opened the connection — the server's main defense against cross-site WebSocket hijacking.
