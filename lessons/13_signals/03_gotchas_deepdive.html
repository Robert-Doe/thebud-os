Turning a Landmine
Into an Ordinary Event

You now know signal handlers can fire mid-instruction inside code that never expected to be interrupted, and that calling almost anything non-trivial from one is a gamble. So how does real, production networking and server code actually cope? By refusing to do any real work inside the handler at all — and turning the awkward, asynchronous signal into a boring, synchronous, ordinary file descriptor your event loop already knows how to wait on.

00 — Where We Left Off

The Warning, Restated as a Practical Problem

The delivery lesson ended on a warning: a signal handler can interrupt your program at literally any instruction boundary, including in the middle of a non-reentrant function like malloc(), and only a short, POSIX-certified list of async-signal-safe functions are genuinely safe to call from inside one. That's the theory. This lesson is about what you actually do with that constraint when you need a handler to trigger real, non-trivial work — logging, cleaning up state, waking up a worker thread, reloading a config file.

🔑 The Practical Question
If a handler can't safely call malloc(), can't safely call printf(), can't safely touch most of your own program's data structures without careful precautions — how does any real program do anything useful in response to a signal? The answer, spoiler: it doesn't. It does almost nothing in the handler, and does everything else somewhere completely safe.
01 — A Concrete, Broken Example

Two printf() Calls Walk Into a Handler

Let's make the danger from the last lesson completely concrete, with the single most tempting mistake beginners make: calling printf() from inside a handler "just to log that the signal arrived."

#include <signal.h>
#include <stdio.h>

void handle_sigusr1(int sig) {
    printf("[handler] got SIGUSR1\n");   // looks completely innocent
}

int main(void) {
    signal(SIGUSR1, handle_sigusr1);
    while (1) {
        printf("working... this line is long enough to span multiple internal buffer writes\n");
        // somewhere in the middle of THIS printf's internal buffering,
        // a SIGUSR1 can arrive and jump straight into handle_sigusr1() above
    }
}

printf() is not a single atomic operation. Internally, glibc's stdio maintains a shared, per-stream buffer and a set of pointers tracking how much of that buffer is filled, protected in multi-threaded programs by a lock — but a signal handler running on the same thread doesn't go through that lock at all, because from the CPU's point of view it's not a separate thread, it's a detour taken by the very same one. If the main loop's printf() is mid-way through appending bytes to that shared buffer when the handler's own printf() fires, the handler's call reads and writes the exact same buffer state — pointers the main call assumed nobody else was touching a moment ago.

⚠️ What Actually Goes Wrong
In the best case, you get visibly garbled or interleaved output — two partial lines mashed together. In the worse case, on an implementation where the same lock is involved, the handler's printf() tries to acquire a lock the interrupted printf() already holds — on the same thread, which can never release it because that thread is currently frozen inside the handler waiting for the lock. That's an instant, silent deadlock: the whole process just stops, with no crash, no error message, nothing — just gone.

Neither outcome is guaranteed — you might run this code a thousand times and never see it happen, because the timing window is narrow. That's exactly what makes this class of bug so miserable: it's not that the code is wrong every time, it's that it's wrong some of the time, under load, in production, at 3am, in a way that's nearly impossible to reproduce on demand.

03 — The Classic Fix

The Self-Pipe Trick

The self-pipe trick is old (it predates Linux's signalfd() by decades, and shows up in classic Unix networking code like libevent and early nginx), and the idea is almost embarrassingly simple once you see it: create an ordinary pipe at startup — the same kind you'd use for any other inter-process communication — and have the signal handler do one thing and one thing only: write a single byte to the pipe's write end.

The trick's entire value is in that last step: by the time your actual logic runs, you are not inside a signal handler anymore. You're back in ordinary code, on the normal call stack, free to call malloc(), printf(), touch any data structure you like — because nothing about this code path can be re-entered mid-instruction by itself. The signal's asynchronicity has been fully absorbed and converted into a completely ordinary, synchronous "a byte showed up on this file descriptor" event, indistinguishable to your event loop from a byte arriving on a network socket.

#include <signal.h>
#include <unistd.h>
#include <sys/select.h>
#include <fcntl.h>

static int selfpipe[2];   // [0] = read end, [1] = write end

void handle_sigusr1(int sig) {
    char byte = 1;
    write(selfpipe[1], &byte, 1);   // write() IS on the async-signal-safe list
    // that's it. nothing else. return immediately.
}

int main(void) {
    pipe(selfpipe);
    fcntl(selfpipe[1], F_SETFL, O_NONBLOCK);  // never let the handler block on a full pipe
    signal(SIGUSR1, handle_sigusr1);

    fd_set readfds;
    while (1) {
        FD_ZERO(&readfds);
        FD_SET(selfpipe[0], &readfds);
        FD_SET(listen_sock, &readfds);         // the pipe sits ALONGSIDE ordinary fds
        select(max_fd + 1, &readfds, NULL, NULL, NULL);

        if (FD_ISSET(selfpipe[0], &readfds)) {
            char buf[64];
            read(selfpipe[0], buf, sizeof(buf));  // drain it
            handle_sigusr1_for_real();          // safe: ordinary code, ordinary stack, malloc()/printf() all fine
        }
        if (FD_ISSET(listen_sock, &readfds)) { /* handle a normal network event */ }
    }
}
💡 The Aha Moment
A pipe's write end is (by default) buffered by the kernel — writing one byte to it never blocks under normal conditions, and the handler's write() is on the async-signal-safe list, so this is legal even under the strictest reading of the rules from the last lesson. The self-pipe trick doesn't work around the async-signal-safety problem — it fully complies with it, by making sure the handler's only job is something already certified safe.
Why non-blocking on the write end? If your event loop is slow to drain the pipe and many signals arrive in a burst, the pipe's kernel buffer could theoretically fill up. A blocking write() inside a signal handler that can't complete would hang the handler forever. Marking the write end O_NONBLOCK means a full pipe just makes write() fail immediately (harmlessly — you only needed to wake the loop up once anyway) instead of hanging.

05 — Linux Builds the Trick Into the Kernel

signalfd(): The Same Idea, No Pipe Required

Linux eventually noticed how common the self-pipe trick had become and gave it a first-class syscall: signalfd(). Instead of manually wiring up a pipe and a handler, you tell the kernel "give me a file descriptor that becomes readable whenever any of these specific signals are pending" — and the kernel handles the plumbing that the self-pipe trick used to require you to write by hand.

#include <sys/signalfd.h>
#include <signal.h>

sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGUSR1);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, NULL);   // IMPORTANT: block them from normal delivery first

int sfd = signalfd(-1, &mask, 0);   // -1 = create a new fd

// no handler function anywhere in this program at all —
// just add sfd to your select()/poll()/epoll() set like any other fd

struct signalfd_siginfo info;
read(sfd, &info, sizeof(info));   // blocks until a blocked signal is pending, then reads its details
// info.ssi_signo tells you exactly which signal number arrived

Notice what disappeared entirely: there's no signal()/sigaction() call, no handler function, no async-signal-safety tightrope to walk at all. You explicitly block the signals from ever going through the normal handler-delivery checkpoint from the last lesson, and instead read them out through sfd whenever it's convenient — which is always inside your ordinary, synchronous event loop.

✅ Same Trick, Fewer Moving Parts
signalfd() is conceptually identical to the self-pipe trick — "turn signal delivery into a readable file descriptor" — just implemented by the kernel instead of hand-rolled with a real pipe and a tiny handler. You get one fewer fd (no separate write end to manage), structured information about exactly which signal and why (via signalfd_siginfo, including things like the sending PID), and zero risk of ever accidentally calling something async-signal-unsafe, because there's no handler code path left to put it in.
The catch: signalfd() is Linux-specific — it's not in POSIX, and portable code that needs to run on macOS/BSD still reaches for the self-pipe trick (or kqueue's own native signal-as-event support on BSD-family systems, a different OS-specific answer to the same underlying problem).

🚫 When the Naive Approach Actually Fails You

The moment your handler needs to do anything beyond setting one volatile sig_atomic_t flag — logging, updating a linked list, calling into any library that might allocate — you're gambling on timing windows that pass every test run and fail in production under load.

✅ When to Reach for the Self-Pipe / signalfd Pattern

Any time your program already has (or could have) a central select()/poll()/epoll() event loop — which describes most non-trivial servers and daemons. The signal stops being a special case at all; it's just one more fd among many.
07 — Quick Reference

Glossary & Key Terms

Self-Pipe Trick
A pattern where a signal handler only writes one byte to a pipe; the real logic runs later in the main event loop when that pipe's read end becomes readable.
Event Loop
A central loop, typically built on select()/poll()/epoll(), that blocks until any of several file descriptors has activity, then dispatches accordingly.
select() / poll()
System calls that block a process until one or more file descriptors in a watched set become ready for I/O.
signalfd()
A Linux-specific syscall that exposes pending signals as a readable file descriptor, replacing the need for a handler entirely.
O_NONBLOCK
A file descriptor flag ensuring an operation like write() fails immediately instead of blocking — critical for a pipe's write end used inside a handler.
Shared Buffer Corruption
The failure mode when a handler and the code it interrupted both mutate the same non-reentrant internal state, like stdio's buffering.
signalfd_siginfo
The structured record returned by reading a signalfd, including which signal arrived and metadata like the sending process's PID.
Coalescing
The fact that standard POSIX signals don't queue — multiple deliveries of the same signal before it's processed collapse into one.
