A Tap On The
Shoulder

You already know a system call is a process deliberately knocking on the kernel's door. A signal is the opposite knock — the kernel (or another process entirely) reaching over and tapping a running process on the shoulder, completely uninvited, to say "something happened, deal with it." This page is about what signals are, where they come from, and the three things a process is allowed to do when one arrives.

00 — Where We Left Off

You've Met Traps. Meet Their Cousin.

From the PCB and IDT material, you already know the kernel gets involved in a running process through three doors: a deliberate syscall, an involuntary fault triggered by the CPU reacting to the current instruction, or an involuntary hardware interrupt from some device that has nothing to do with what's executing. All three are the CPU's business — they happen at the instruction level, dispatched through the IDT, and they're resolved (or not) before the CPU even finishes decoding whatever comes next.

A signal is a different animal, living one layer up. It isn't a CPU mechanism at all — it's a kernel-level, software notification mechanism aimed at a specific process (or thread). Sometimes a signal gets triggered by one of those three hardware doors — a bad memory access turns into a page fault, which the kernel decides to turn into a SIGSEGV signal aimed at the offending process. But the signal itself — the numbered flag, the pending state, the delivery — is pure kernel bookkeeping, not silicon. That's the whole subject of this module.

🔑 The One Sentence to Remember
A signal is a limited, numbered set of notifications the kernel can deliver to a process — some generated by the kernel itself reacting to what the process did, some sent deliberately by another process (or the user), and a couple set aside purely for the application to invent its own meaning.
01 — First Principles

What Is a Signal, Really?

Strip away everything else and a signal is astonishingly small: it's a number between 1 and 31 (on Linux's original set — extended ranges exist for real-time signals, but ignore those for now). That's it. No payload, no attached data, no way to pass a string or a struct. When the kernel "sends process 4021 a SIGTERM," all that really happens is: somewhere in process 4021's kernel-side bookkeeping, a single bit gets set.

You've already seen exactly where that bit lives, even if you didn't know its name yet. Go back to the PCB dossier — the kernel-only record the scheduler keeps per process. A real POSIX kernel keeps a small chunk of that dossier reserved specifically for signal state: which signals are currently pending (arrived but not yet delivered), which are currently blocked (more on this in the next lesson), and — critically — what this process wants done, per signal number, when it lands. bob_os models this with almost embarrassing directness:

/* process.h — bob_os's actual signal bookkeeping */
#define NSIG    32
#define SIG_DFL 0u   /* default action */
#define SIG_IGN 1u   /* ignore */

struct process {
    /* ... pid, state, registers, page table pointer ... */
    uint32_t pending_signals;          /* bitmask: bit N = signal N pending */
    uint32_t signal_handlers[NSIG];    /* handler addr, SIG_DFL, or SIG_IGN */
};

One 32-bit integer for "what's pending," and one small array for "what to do about each one." That's the entire data structure a signal-capable kernel needs to add to a PCB. Everything else in this module is about the mechanics of how those two fields get read, written, and acted on.

Why a bitmask and not a queue? Standard POSIX signals deliberately don't queue. If someone sends a process ten SIGUSR1s before it gets a chance to handle even one, that counts as one pending SIGUSR1 — OR-ing a bit that's already set is a no-op. This surprises people coming from event-queue backgrounds. (Real-time signals, SIGRTMIN and up, do queue — but that's a different, rarer corner of POSIX most kernels including bob_os don't bother implementing.)
💡 The Aha Moment
A signal carries no data because it was never designed to. It's not a message — it's a flag. The number itself is the entire payload: "this specific, pre-agreed-upon thing happened." If you need to pass real data between processes, you reach for pipes, shared memory, or sockets — signals are strictly for "something happened, and here's which of ~31 pre-registered somethings it was."
02 — Who Sends These, Anyway?

Three Origins, One Mechanism

Every signal your process will ever receive traces back to one of exactly three sources. The delivery machinery downstream is identical no matter which one fired — but the reason a given signal number exists at all is always one of these three stories.

Kernel-Generatedreacting to a fault
The kernel itself notices your process did something the hardware can't or won't let slide, and translates that into a signal aimed right back at you.
  • SIGSEGV — touched memory you don't own (bad pointer, stack overflow, null deref)
  • SIGFPE — integer divide-by-zero, or an invalid floating-point operation
  • SIGILL — the CPU tried to execute an instruction it doesn't recognize
  • SIGBUS — a misaligned or otherwise invalid memory access at the bus level
Deliberately Sentanother actor's choice
A human, a shell, or another process explicitly decides this process needs to know something — usually "stop" in some form.
  • SIGINT — you pressed Ctrl+C in the controlling terminal
  • SIGTERM — a polite, catchable request: "please shut down"
  • SIGKILL — an impolite, uncatchable demand: "you're gone, now"
  • SIGHUP — the controlling terminal closed, or a daemon is asked to reload config
Application-Definedyours to invent
POSIX deliberately reserves a couple of numbers that mean nothing on their own — you decide what they mean inside your own program.
  • SIGUSR1 — no built-in meaning; a common convention is "reload configuration"
  • SIGUSR2 — no built-in meaning; another process might use it as "dump your stats now"
  • Two processes that agree on a convention can use these as a crude, one-bit-of-data IPC channel
⚠️ "Kernel-Generated" Doesn't Mean "No Process Involved"
It's tempting to think of SIGSEGV as something the CPU does to you directly. It isn't. The CPU raises a page fault — one of the three hardware doors from the PCB/IDT material — and it's the kernel's page-fault handler that looks at the situation, decides "this access is genuinely invalid, not just a lazily-mapped page," and only then synthesizes a SIGSEGV and marks it pending on your process. The signal is a software decision layered on top of a hardware event, not the hardware event itself.

Notice that "deliberately sent" isn't limited to humans pressing keys. Any process with the right permissions can send any other process a signal directly through the kill() system call — a name that's historically accurate (it was originally only used to terminate things) but misleading today, since kill() can send any signal number, not just fatal ones.

/* POSIX — send SIGUSR1 to process 4021 */
int kill(pid_t pid, int sig);

kill(4021, SIGUSR1);   // despite the name, nothing dies — SIGUSR1's default action just terminates
                       // unless 4021 installed a handler for it
03 — The Process's Side of the Deal

Three Things You Can Do With a Signal

Here's the part that makes signals genuinely useful rather than just a way for the kernel to kill you unpredictably: for almost every signal number, the target process gets a say in what happens when it arrives. That say comes down to exactly three options, and every signal you'll ever handle picks one of them.

  1. 1 — Do Nothing: Take the Default ActionEvery signal number ships with a kernel-defined default behavior, and if the process never says otherwise, that's exactly what happens. For most signals the default is "terminate the process" — sometimes with a core dump (SIGSEGV, SIGABRT), sometimes without (SIGTERM, SIGINT). A few signals default to something gentler: SIGCHLD's default is simply "ignore," and SIGSTOP/SIGCONT default to pausing or resuming the process rather than killing it.
  2. 2 — Explicitly Ignore ItA process can tell the kernel "I never want to be interrupted for this one — just discard it silently, every time, forever" by setting that signal's disposition to SIG_IGN. This is different from never receiving the signal at all: the kernel still notices the signal arrived, it just throws it away instead of acting on it. This is genuinely useful — a network server, for instance, commonly sets SIGPIPE to SIG_IGN so that writing to a socket the other end already closed produces an error code instead of silently killing the whole process.
  3. 3 — Install a Custom HandlerThe interesting option: a process can register its own ordinary function — a signal handler — to run instead of the default action, the moment this signal is delivered. The kernel doesn't just call it whenever convenient, either; it has to forcibly redirect the process's own execution into that function, then get it back out again afterward. That redirect-and-return mechanism is dense enough that it gets its own lesson next — for now, just know: writing a handler is you telling the kernel "when this happens, run my code instead of your default, then let me carry on."
🧠 The One Signal With No Vote
SIGKILL (and its close cousin SIGSTOP) cannot be ignored and cannot be handled. Full stop — not "hard to," structurally impossible. The kernel doesn't even check the process's signal_handlers table for these two numbers; it hard-codes the behavior. This exists on purpose: no matter how broken, hung, or hostile a process is, the system administrator (or the kernel itself) needs at least one lever that is guaranteed to work. If SIGKILL were catchable, a buggy or malicious process could install a handler that just... never lets the process die.

This three-way choice is exactly why bob_os's signal_handlers array uses three possible states per slot — SIG_DFL, SIG_IGN, or a real function pointer — and why SIGKILL is checked and short-circuited before that array is even consulted, in the delivery code you'll trace through in the next lesson.

06 — Putting It in Code

Installing a Handler, In Practice

On a real POSIX system, the classic (if slightly dated) way to register a disposition is the signal() function — three arguments' worth of information (which signal, what to do) collapse into a single call:

#include <signal.h>

void handle_sigint(int signo) {
    /* signo will be SIGINT (2) every time — the kernel tells you which */
    const char *msg = "caught Ctrl+C, cleaning up...\n";
    write(1, msg, 30);  /* more on why write(), not printf(), next lesson */
    _exit(0);
}

int main(void) {
    signal(SIGINT, handle_sigint);   // install: SIGINT now runs our function
    signal(SIGPIPE, SIG_IGN);        // explicitly ignore: never die from a broken pipe
    // SIGTERM, SIGSEGV, etc. left untouched — they keep their SIG_DFL default

    while (1) { /* do work forever, until Ctrl+C */ }
}

And here's the bob_os equivalent — same three-way idea, expressed through this kernel's own syscall surface, matching the struct process fields you saw in section 01:

/* user_prog.c — bob_os's signal_demo.elf */
void sigusr1_handler(int sig) {
    /* runs instead of SIG_DFL when SIGUSR1 lands */
}

void user_main(void) {
    int pid = sys_getpid();
    sys_signal(SIGUSR1, sigusr1_handler);  // install a custom handler
    sys_kill(pid, SIGUSR1);                // send ourselves the signal
    sys_yield();     // handler fires here on the way back to user mode, then returns
}
✅ Notice What's Symmetric
Both snippets do the exact same three things in the exact same order: (1) write a plain function that takes the signal number as its argument, (2) hand the kernel a pointer to that function for a specific signal number, (3) let normal program flow continue — the kernel is now responsible for interrupting it at the right moment. Whether that's glibc's signal() or bob_os's sys_signal(), the contract with the kernel is identical.
07 — Quick Reference

Glossary & Key Terms

Signal
A numbered, dataless, asynchronous notification the kernel can deliver to a process — one of ~31 standard POSIX numbers.
Pending Signal
A signal that has been sent (a bit is set in the target's PCB) but not yet delivered/acted upon.
Disposition
What a process has told the kernel to do with a given signal number: SIG_DFL (default), SIG_IGN (ignore), or a handler function pointer.
SIG_DFL
"Use the kernel-defined default action for this signal" — often terminate, sometimes ignore or pause, depending on the signal.
SIG_IGN
"Discard this signal silently every time" — an explicit, deliberate choice, distinct from never registering anything.
Signal Handler
An ordinary user-space function the kernel forcibly redirects execution into the moment a signal is delivered, in place of the default action.
kill()
The POSIX system call used to send any signal (not just fatal ones) to any permitted target process.
SIGKILL / SIGSTOP
The two signals whose behavior is hard-coded in the kernel — they cannot be caught, blocked, or ignored by any process, by design.
SIGUSR1 / SIGUSR2
The two signal numbers POSIX deliberately leaves undefined, reserved purely for application-defined meaning.
