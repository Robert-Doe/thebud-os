Sees Coming

Sending a signal doesn't teleport your process into a handler mid-instruction. It marks a bit and waits. The real magic happens later, at a very specific checkpoint: the instant the kernel is about to hand the CPU back to user mode, it quietly rewrites the return trip so it goes through your handler first. That trick is elegant — and it's also exactly why handlers can wreck a program that looks completely correct on paper.

00 — Where We Left Off

You Know What. Now, How.

The explainer lesson covered the what: a signal is a numbered flag, sent by the kernel or another process, and the target gets to choose default/ignore/handler for each one. What it deliberately skipped is the mechanical question that actually matters when you're writing real code: the instant kill() is called, does the target process just... stop and jump into the handler, right then?

No. And understanding exactly why not — and what really happens instead — is the difference between writing signal handlers that work and writing ones that corrupt memory once every few thousand runs in a way that's nearly impossible to reproduce.

🔑 Recall From the PCB/IDT Material
You already know the kernel takes over a running process through traps — syscalls, faults, interrupts — and that every trap pushes a trap frame (PC, flags, a few registers) to the kernel stack, cheaply, every single time. Signal delivery piggybacks on this exact machinery rather than inventing a new one: it waits for a trap to happen anyway, then modifies what gets restored on the way back out.
01 — The Key Insight

Delivery Is Synchronous, Even Though Signals Are "Asynchronous"

Here's the sentence worth memorizing: a signal can arrive at any time, but it only ever gets delivered at one very specific checkpoint — the moment the kernel is about to return control to user mode. Everywhere else, "arrival" just means a bit gets set and nothing more happens yet.

The rule that resolves the apparent contradiction Arrival is asynchronous. Delivery is synchronous. "Asynchronous" describes when the pending bit can get set — literally any time, including mid-instruction. "Delivery" — actually redirecting execution into a handler — only happens at kernel-to-user return points, which the kernel fully controls.

Where do those return points come from? Anywhere the CPU is about to leave Ring 0 and resume Ring 3 — which, from the PCB material, you already know happens constantly:

  • Right after a system call finishes servicing and is about to return its result to the caller.
  • Right after a hardware interrupt (most commonly the timer tick) finishes, whether or not it triggered a full context switch.
  • Right after the scheduler picks this exact process/thread to run next, following a context switch back into it.

In bob_os terms, this checkpoint is a specific function, called from exactly the place you'd guess: right after the scheduler has switched the page table back to the target process, but just before the CPU actually resumes it.

/* process.c — bob_os, called from scheduler_tick() after paging_switch() */
static void deliver_user_signals(void) {
    struct interrupt_frame *f = (struct interrupt_frame*)current->esp;

    for (int sig = 1; sig < NSIG; sig++) {
        if (!(current->pending_signals & (1u << sig))) continue;
        /* only signals that are BOTH pending AND due for a checkpoint reach here */
        current->pending_signals &= ~(1u << sig);
        // ... build the redirect (next section) ...
    }
}
💡 The Aha Moment
This is why a process that's blocked deep in the kernel servicing a slow syscall doesn't get yanked into a handler mid-syscall. The kernel is Ring 0 the entire time that syscall runs — there's no return-to-user checkpoint until the syscall is actually finished. The signal sits pending, patiently, until the exact moment the kernel is already about to hand control back — and rewrites that handoff instead of interrupting kernel code directly.
02 — The Full Mechanism

What "Redirecting the Return Trip" Actually Means

At the checkpoint, the kernel has the interrupted process's saved user-mode registers and stack pointer sitting right there in the trap frame — it hasn't restored them into the CPU yet. That's the opening. Instead of just restoring them as-is, the kernel edits them first, so that when it finally does execute the "return to user mode" instruction, the CPU lands in the handler, not in the code that was originally interrupted.

  1. Read the saved user-mode stack pointer out of the trap frameNot the kernel stack — the trap frame records where the interrupted process's own stack pointer was, in user space, at the moment it was last in Ring 3.
  2. Carve out space on that user stack for a signal frameThe kernel decrements the saved user esp by enough bytes to hold whatever the handler-call convention needs — at minimum, a return address and the signal number argument.
  3. Write a fake "call" onto that carved-out spaceThe kernel writes the original interrupted program counter into that space as a return address, and the signal number as the first argument — mimicking exactly what a normal call handler(signo) instruction would have left on the stack.
  4. Overwrite the saved program counter in the trap frame with the handler's addressThis is the actual redirect. The trap frame's EIP/RIP field — the value that's about to get restored into the real CPU — now points at the handler function instead of wherever the process actually was.
  5. The trap returns normally — straight into the handlerFrom the CPU's perspective, nothing unusual happened: it just executed a normal "return from trap" (iret on x86) using the values in the trap frame. It has no idea those values were doctored — it lands at the handler's first instruction as if it had been called normally.
  6. The handler runs, then "returns" — into a trap, not into retWhen the handler function finishes and executes its own ret, it pops that fake return address you planted in step 3. On a real POSIX system that address doesn't point back into your code at all — it points at a tiny piece of trampoline code that executes the sigreturn system call, deliberately re-entering the kernel one more time.
  7. sigreturn restores the ORIGINAL frame, untouchedThe kernel had saved a complete copy of the original trap frame (all registers, the real PC, the real stack pointer, even the original signal mask) before it did any of the doctoring in steps 1–4. sigreturn's entire job is to load that saved copy back in and resume it — putting the process back exactly where the signal first found it, as if the whole detour never happened.
🧠 Why Not Just Have the Handler ret Directly Back?
Because the handler's ret only knows how to pop a plain return address into a register — it has no way to also restore every other register, the FPU/SSE state, and the signal mask that was active before delivery. A real ucontext is much bigger than one address. sigreturn exists specifically to let the kernel do that full restoration, which is more state than any ordinary function-return mechanism can carry.
⚠️ bob_os's Deliberate Shortcut
bob_os's actual delivery code fakes a plain cdecl call frame — return address plus one argument — and relies on an ordinary ret to resume the original code, with no real sigreturn and no saved ucontext. That's fine for the tutorial's demo (a handler that finishes and lets execution fall back into ordinary flow), but it's explicitly documented as a simplification: a SIGSEGV handler that tries to just ret back into the faulting instruction re-executes it and faults again immediately, so bob_os's demo handler calls sys_exit() instead of ever attempting to resume. A production kernel needs the full sigreturn/ucontext path to recover cleanly.

04 — Temporarily Saying "Not Now"

The Signal Mask

Disposition (default/ignore/handler) answers "what happens when this signal is eventually delivered." The signal mask answers a different question: "should this signal be allowed to reach a delivery checkpoint at all, right now?" Every process (technically every thread) keeps a bitmask of currently blocked signals, checked at exactly the same checkpoint as everything else in this lesson.

Blocking is not the same as ignoring. A blocked signal that arrives still gets marked pending — the bit still flips — but the delivery loop skips over it at the checkpoint as long as it stays blocked. The moment the process unblocks it again, if the pending bit is still set, delivery happens on the very next checkpoint after that.

#include <signal.h>

sigset_t block_these;
sigemptyset(&block_these);
sigaddset(&block_these, SIGUSR1);

/* critical section: don't let SIGUSR1 interrupt us here */
sigprocmask(SIG_BLOCK, &block_these, NULL);
update_shared_linked_list();      // SIGUSR1 can arrive, but delivery waits
sigprocmask(SIG_UNBLOCK, &block_these, NULL);
/* any SIGUSR1 that arrived during the critical section delivers ~now */
🔑 Handlers Get an Automatic, Temporary Mask Too
By default, while a signal's own handler is running, that same signal number is automatically added to the mask — so a flood of SIGINTs doesn't re-enter handle_sigint() on top of itself and blow the stack. sigaction()'s sa_mask field lets you extend that automatic blocking to additional signal numbers for the duration of the handler, which is exactly how you prevent two different handlers from interleaving unsafely.

This is also the missing piece bob_os's own tutorial flags as a known gap: with no mask implemented, nothing stops deliver_user_signals from being re-entered on the very next tick while a handler is still mid-flight, which is exactly how you'd get nested signal frames stacking up on the user stack unboundedly. A signal mask is precisely the mechanism that prevents that.

05 — The Warning This Whole Lesson Is Building To

Handlers Can Fire Literally Anywhere

Go back to the pipeline in section 02. The checkpoint the kernel uses is "about to return to user mode" — and that can happen after any trap, at any instruction boundary in your program. Your handler doesn't get scheduled at a convenient moment between statements. It can interrupt your program in the absolute middle of any function it was running — including functions from the standard library that were never written to expect that.

malloc()
Maintains a global free-list — mid-update when interrupted
printf()
Buffers output internally — mid-write when interrupted
strtok()
Keeps hidden static state between calls
errno
One shared variable — handler can silently overwrite it

Here's the concrete failure mode. Say your main program is in the middle of malloc(): it has already unlinked a chunk from the internal free-list, and is halfway through updating a couple of pointers to keep that list consistent — the data structure is temporarily broken on purpose, for a few instructions, because that's how in-place list surgery works. If a signal is delivered right then, and your handler itself calls malloc() (even indirectly — logging with printf() often does), that second call walks the same free-list mid-repair. It doesn't know the list is broken. It reads corrupted pointers, and depending on your luck, either crashes immediately or — worse — silently corrupts the heap in a way that surfaces as a baffling crash somewhere completely unrelated, minutes later.

▶ Watch a handler interrupt malloc() mid-repair
⚠️ This Is Not a Rare Edge Case
This isn't a contrived scenario — it's the default risk of writing any non-trivial signal handler. The function you interrupted didn't do anything wrong. It's not reentrant because almost nothing in a general-purpose standard library is written to be reentrant by default; reentrancy has to be deliberately engineered in, and it usually isn't, because it costs performance nobody wants to pay for code that never expected to be interrupted by itself.
06 — The Narrow Safe List

What's Actually Safe to Call From a Handler?

POSIX addresses this directly with the concept of async-signal-safe functions: a short, explicit list of library and system calls certified safe to call from inside a signal handler, specifically because they either don't touch any shared mutable state, or they're implemented in a way that tolerates being re-entered mid-call. Everything not on that list is guilty until proven innocent.

FunctionAsync-Signal-Safe?Why
write()YesRaw syscall, no internal buffering, no shared state to corrupt
read()YesSame — thin syscall wrapper
_exit()YesTerminates immediately; nothing left to corrupt afterward
kill() / raise()YesThin syscall wrapper, no shared library state
sig_atomic_t accessYesGuaranteed atomic read/write of this one specific integer type
malloc() / free()NoMaintains a shared heap free-list, not reentrant
printf() / fprintf()NoBuffers internally (and often calls malloc() itself)
strtok()NoKeeps hidden static state between calls
Most of <stdio.h>NoNearly all of it buffers through shared, non-reentrant state

🚫 What Most Handlers Are Tempted to Do

Log a message with printf(), allocate a buffer with malloc(), update a complex data structure directly, call some other convenience library function that "should be fine." Any of these can be running on the exact instruction the handler interrupted — and now you have two copies of the same non-reentrant function racing over the same private state, in the same thread, at the same time.

✅ What a Well-Behaved Handler Actually Does

As close to nothing as possible: set a single volatile sig_atomic_t flag, or write one byte to a pipe (the subject of the next lesson), and return immediately. All the real work happens later, back in ordinary, uninterrupted program flow, where every library function is safe to call again.
The pragmatic rule of thumb: if you're not sure whether a function is async-signal-safe, assume it isn't. The safe list is short enough to just remember directly: raw syscalls like write(), read(), _exit(), kill(), and a handful of others — roughly 30 functions total in the POSIX standard, out of the hundreds the C library offers.
07 — Quick Reference

Glossary & Key Terms

Delivery Checkpoint
The specific moment — right before returning to user mode — where the kernel checks for pending, unblocked signals and acts on them.
Signal Frame
The fake call frame the kernel builds on the process's user stack, redirecting execution into the handler as if it had been called normally.
sigreturn
A dedicated system call, invoked automatically when a handler finishes, that restores the complete original execution context saved before delivery.
ucontext
The full saved machine state (all registers, signal mask, stack) a real kernel preserves so sigreturn can restore it exactly.
Signal Mask
A per-thread bitmask of currently blocked signal numbers; blocked signals still get marked pending but delivery is deferred until unblocked.
sigprocmask() / pthread_sigmask()
The calls used to add or remove signal numbers from the calling thread's signal mask.
Reentrancy
A function's ability to be safely called again before a previous, still-in-progress call on the same thread has finished.
Async-Signal-Safe
POSIX's certified list of functions safe to call from inside a signal handler — mostly thin syscall wrappers with no shared internal state.
sig_atomic_t
A special integer type whose reads and writes are guaranteed atomic with respect to signal delivery — the one safe way to share a flag with a handler.
