00 — Where We Left Off

"The Kernel Does All the Buffering" Was Doing a Lot of Work

Lesson 1 kept the buffer itself as a black box on purpose — a pipe's whole selling point is that you never have to think about it. But a black box that never runs out of room doesn't exist, and neither does a real one here: bob_os's pipe_buf struct fixes data[PIPE_BUF] at a flat 4096 bytes, and real Linux pipes, though usually larger, are just as finite. Today we open the box: how the buffer actually wraps bytes around in fixed memory, what "full" and "empty" really mean to the two processes on either end, and the specific signal the kernel fires when a writer is shouting into a pipe that has, quite literally, no one left to hear it.

This also finally cashes in a promise from Module 3's PCB explainer. That dossier listed Process State as RUNNING / READY / BLOCKED and moved on. A pipe is one of the most common, concrete reasons a process ever actually lands in BLOCKED — and by the end of this lesson you'll be able to point at the exact line of kernel logic that puts it there.

01 — The Actual Data Structure

A Pipe Is a Ring Buffer

"Fixed-size buffer with a read end and a write end" could, in principle, be implemented a dozen ways. In practice, every mainstream kernel implements it the same way: a flat array of bytes, plus two cursors — head (next byte to read) and tail (next slot to write) — both of which wrap back to zero once they walk off the end of the array. That's a ring buffer (also called a circular buffer), and it's a good structure for exactly this job: fixed memory, no reallocation ever, and O(1) push/pop from either end.

#define PIPE_BUF  4096          /* bob_os: fixed, small, easy to reason about   */
                                  /* Linux default capacity: 65536 (tunable via
                                     fcntl(fd, F_SETPIPE_SZ, n), historically 4096 */
struct pipe_buf {
    char     data[PIPE_BUF];
    uint32_t head;    /* next byte the reader will consume */
    uint32_t tail;    /* next slot the writer will fill     */
    uint32_t count;    /* bytes currently buffered — the ONLY way to tell
                          full (count==PIPE_BUF) apart from empty (count==0),
                          since head==tail happens in both cases          */
};

/* wrap-around indexing — this is the entire "ring" in ring buffer */
data[tail % PIPE_BUF] = byte;   tail++;   count++;   /* on write */
byte = data[head % PIPE_BUF];   head++;   count--;   /* on read  */
💡 Why count Exists At All
Look closely at the comment in that struct: if you only tracked head and tail, an empty buffer (head == tail, nothing written since last fully drained) would be indistinguishable from a completely full one (head == tail again, because tail wrapped all the way around and caught up to head). That's a classic ring-buffer trap. The fix is exactly what bob_os's pipe.c does: keep an explicit count field as the single source of truth for "how full is this thing," and let head/tail just be positions.

The size is genuinely fixed at pipe-creation time (or resized in one shot via fcntl(F_SETPIPE_SZ) on Linux) — it never grows dynamically the way, say, a Vec or std::vector would as you push more data in. That fixed ceiling is the entire reason the rest of this lesson exists: a writer can eventually catch up to a reader that isn't draining fast enough, and there is nowhere left to put the next byte.

02 — When There's Nowhere Left to Write

Full Pipe: The Writer Blocks

Picture a writer producing data faster than a reader consumes it — a video encoder streaming frames to a slower network client, for instance. Eventually count reaches PIPE_BUF. The writer calls write() again. What happens is not an error, and it is not a partial write that silently drops bytes. By default, the call simply does not return.

Default (Blocking) write() On a Full Pipe The calling process is put to sleep — its PCB's Process State field flips to BLOCKED — until at least one byte of free space opens up. The kernel doesn't busy-loop checking "is there room yet?" a thousand times a second. It removes the writer from the scheduler's run queue entirely and parks it on a wait queue attached to this specific pipe, exactly the same mechanism as any other blocking I/O.

This ties directly back to the three-state PCB model from Module 3. A blocked writer isn't spinning, isn't consuming CPU, and isn't even being considered by the scheduler — it's parked. The instant a reader drains enough bytes to free space, the kernel's write() path (or, symmetrically, the reader's read() path) calls a wake-up routine that moves the writer back to READY, and the scheduler picks it up again on its own schedule, same as any other previously-blocked process.

Sidenote: POSIX actually carves out a special case here worth knowing: writes of up to PIPE_BUF bytes (a implementation-defined constant, historically 4096 on Linux) are guaranteed atomic — if two processes write to the same pipe at once, one write's bytes will never interleave with the other's, mid-write. Writes larger than PIPE_BUF carry no such guarantee and may be split into multiple chunks by the kernel, potentially interleaved with another writer's data. bob_os sidesteps this entirely by making its whole buffer exactly PIPE_BUF bytes and blocking until the full request fits — simple, but see the callout below for the tradeoff.
⚠️ All-Or-Nothing vs Partial Writes
bob_os's pipe_write_fn writes as many bytes as currently fit and returns that count immediately — it does not block waiting for the rest, and it does not guarantee your whole buffer gets written in one call. Real POSIX write() behaves similarly for large writes: a caller is expected to check the return value and loop, re-calling write() with whatever didn't fit, until everything is sent. Assuming a single write() call always writes everything you asked for is a real, common bug — always check the return value.
03 — When There's Nothing Left to Read

Empty Pipe: The Reader Blocks (Usually)

The mirror image: a reader calls read() and count == 0 — no bytes are waiting. Exactly like the full-writer case, the default behavior is to block: the reader's PCB state flips to BLOCKED, it's parked on the same pipe's wait queue, and it wakes back up to READY the instant a writer adds even one byte.

Pipe State When read() Is CalledWrite End StatusResult
Has bytes (count > 0)—Returns immediately with up to the requested number of bytes
Empty (count == 0)Still open somewhereBlocks — someone might still write more
Empty (count == 0)Closed everywhere (0 writers left)Returns 0 immediately — this is end-of-file, not an error

That third row is the exit condition for the entire mechanism, and it's the reason Lesson 1's "close the end you don't use" rule matters so much. A blocked reader isn't waiting for "more bytes forever" — it's specifically waiting for one of two things to become true: either new data arrives, or the last write end anywhere closes. The kernel can only ever notice the second condition if every single copy of that write-end fd — including any accidental extras left lying around after a careless fork() — actually gets closed.

🔑 Blocking Is Symmetric, On Purpose
Full buffer blocks the writer; empty buffer blocks the reader. Neither side ever has to poll the other, spin-wait, or implement its own signaling — the pipe's blocking semantics on read()/write() already are the synchronization primitive. This is a large part of why Lesson 1 called a pipe "the simplest possible IPC mechanism": correct producer/consumer coordination falls out of ordinary blocking syscalls, for free.

🧠 What To Notice
The writer doesn't get an error when the buffer fills — it simply stops making progress, silently, until the reader creates room. From the writer's own code's point of view, write() is just a function call that sometimes returns quickly and sometimes takes a while; the "took a while" case is a full pipe, resolved entirely by the kernel without either process writing a single line of synchronization code.
05 — Writing Into a Void

What If Nobody's Listening Anymore?

There's a third scenario, distinct from full-and-blocked: what happens if a writer calls write() on a pipe whose read end has been closed everywhere — not just temporarily slow, but permanently gone; no process anywhere holds that read fd open, and none ever will again. Blocking would be senseless here: there is no reader left to eventually drain the buffer and unblock anyone.

What The Kernel Does Instead It sends the writer process the SIGPIPE signal. By default, SIGPIPE terminates the receiving process immediately. The write() call doesn't even get a chance to return an error code in the normal case — the process is killed out from under it, at the point of the write.
▶ Reader disappears, writer keeps writing
⚠️ Why This Exists — It's a Deliberate Design Choice
Without SIGPIPE, a writer with no reader left would face two equally bad options: block forever waiting for a reader that will never come back (the kernel can't distinguish "no reader" from "slow reader" using blocking alone, since new readers could theoretically still open a named pipe later), or keep accepting writes into an ever-growing buffer with genuinely nowhere for the bytes to ever go, accumulating unboundedly. SIGPIPE sidesteps both: it stops the writer immediately, loudly, the moment writing into the void becomes provably pointless — rather than than let it spin or leak memory silently.
Sidenote: You've almost certainly triggered SIGPIPE without realizing it. Run yes | head -n 1 at a shell: yes writes the string "y" forever, as fast as it can, but head reads exactly one line and exits immediately, closing its stdin (the pipe's read end) on the way out. The very next time yes tries to write, it receives SIGPIPE and dies silently — which is exactly why the pipeline terminates cleanly instead of yes spinning forever in the background.
06 — Living With SIGPIPE

When Default Termination Is The Wrong Answer

A one-off shell command dying silently on SIGPIPE is usually fine — even desirable, as the yes | head example shows. But a long-running server process (a web server writing a response body to a client socket that just disconnected, for instance — sockets use this exact same signal) almost never wants to be killed outright by one broken connection among thousands.

💀 Default: SIG_DFL

SIGPIPE's default disposition terminates the process the instant any write hits a reader-less pipe or socket. Fine for small scripts and command-line tools; catastrophic for a server that would otherwise stay up serving thousands of other, healthy connections.

🛡️ Common Fix: Ignore It, Check errno Instead

A process can call signal(SIGPIPE, SIG_IGN) once at startup. With SIGPIPE ignored, a write to a reader-less pipe no longer kills anything — instead, write() simply returns -1 with errno set to EPIPE ("broken pipe"), which is ordinary, recoverable error-handling code can check for and react to, like any other failed syscall.

This is precisely why "Broken pipe" is such a familiar phrase to anyone who's used a Unix shell for long enough — it's the human-readable rendering of EPIPE, surfacing whenever a program's error-handling path (having ignored SIGPIPE) reports the write failure back to you in words instead of dying silently.

✅ The Takeaway For This Lesson
Everything covered here — the ring buffer, the blocking on full/empty, SIGPIPE — is identical between anonymous pipes and named pipes (FIFOs). They are, quite literally, the same kernel mechanism underneath. The only thing Lesson 3 changes is how the two ends find each other in the first place. Shared memory opts out of all of this entirely — no buffer, no blocking, no SIGPIPE — which is exactly why it's fast and exactly why it demands you build your own synchronization from scratch.
08 — Quick Reference

Glossary & Key Terms

Ring Buffer
A fixed-size array with wrap-around head/tail cursors — the data structure a pipe's kernel buffer is built from.
Head / Tail Cursor
Head marks the next byte a reader will consume; tail marks the next slot a writer will fill. Both wrap modulo the buffer's fixed size.
PIPE_BUF
An implementation-defined constant (4096 on Linux) — the maximum write size POSIX guarantees will be written atomically, without interleaving from another writer.
BLOCKED (Process State)
The PCB state a process enters when it can't make progress — e.g. writing to a full pipe or reading from an empty one — and is removed from the scheduler's run queue until woken.
Wait Queue
A kernel-side list of processes blocked on a specific resource (like one pipe); a wake-up event moves a process off this queue and back to READY.
SIGPIPE
The signal sent to a process that writes to a pipe (or socket) whose read end has no readers left anywhere. Default action: terminate the process.
EPIPE
The errno value ("broken pipe") a write() reports instead of triggering termination, if the process has set SIGPIPE's disposition to be ignored.
Signal Disposition
What a process has configured to happen when it receives a given signal — default action, ignore it, or run a custom handler.
Atomic Write
A write guaranteed not to be interleaved, byte-for-byte, with another process's concurrent write to the same pipe — only guaranteed for writes up to PIPE_BUF bytes.
