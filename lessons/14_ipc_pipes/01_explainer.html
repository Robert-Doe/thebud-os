One Byte Stream

You already know a process has an Open File Table on its PCB — a list of file descriptors pointing at things it can read and write. This lesson is about the strangest entries that table can hold: two file descriptors that don't point at a file at all, but at each other, through one small buffer the kernel manages entirely on your behalf. That's pipe() — and it's the mechanism quietly running every time you type a | at a shell prompt.

00 — Where We Left Off

That "Open File Table" Field Had More In It Than Files

Back in the PCB dossier, one field read fd 0,1,2,5,7…, captioned "which files, sockets, and pipes this process currently has open." We treated that word "pipes" as a footnote. It isn't one — it's a whole IPC mechanism, and it's the simplest one the kernel offers. Today we open that footnote all the way up: what a pipe actually is, why it's built from exactly two file descriptors instead of one, and how an entire feature of your shell — the | character — is just those two file descriptors getting handed to two different processes.

This lesson is deliberately narrow. We're not touching shared memory here — Module 3's explainer already walked through shmget()/mmap(MAP_SHARED) and the pipe-vs-shared-memory cost tradeoff in real depth, and we won't repeat that. Here, the pipe is the whole show: what it is, and the exact mechanical trick that makes ls | grep foo work.

01 — The Syscall Itself

What Does pipe() Actually Hand You?

Forget shells and forget IPC for a second. At the syscall level, pipe() is almost insultingly simple:

int fds[2];
int rc = pipe(fds);
/* fds[0] = read end  — a file descriptor you can read() from
 * fds[1] = write end — a file descriptor you can write() to
 * rc == 0 on success, -1 on failure                          */

That's the entire interface. One syscall, one output parameter, two integers written into it. But those two integers are doing something no ordinary file descriptor does: they don't point at anything on disk. They point at each other, mediated by a fixed-size buffer the kernel allocates in its own memory, invisible to user space, that lives exactly as long as somebody still has one of the two ends open.

💡 The Aha Moment
A pipe isn't a special case bolted onto the filesystem — it's proof of how far "everything is a file descriptor" goes in a UNIX-family kernel. fds[0] and fds[1] behave like completely ordinary file descriptors to the process holding them: you read() and write() exactly as you would on any fd. Underneath, bob_os's own VFS layer treats them exactly this way — pipe_alloc() installs a pipe_read_ops vtable on one fd slot and a pipe_write_ops vtable on the other, both pointing at the same slot in a shared pipe_table[]. Same read()/write() syscalls your program already knows, different backing implementation underneath.

Here's bob_os's own version of that buffer, straight out of 20_pipes/pipe.h — deliberately small enough to reason about in full:

#define PIPE_BUF  4096
#define MAX_PIPES 8

struct pipe_buf {
    char     data[PIPE_BUF];
    uint32_t head;       /* read index (mod PIPE_BUF)  */
    uint32_t tail;       /* write index                 */
    uint32_t count;      /* bytes currently available   */
    int      read_open;
    int      write_open;
    int      valid;
};

Notice what's not in that struct: no filename, no inode on any disk, no directory entry. A pipe has no address in the filesystem at all — which is exactly the limitation Lesson 3 in this module exists to fix with named pipes. For now, an anonymous pipe is just this: a slot in a kernel-side array, referenced only by the two file descriptors that happen to point at it.

02 — Why Bother Comparing It to Anything

The Simplest Possible IPC Mechanism

Every other IPC mechanism you'll meet — sockets, message queues, shared memory — adds some kind of structure: addresses, message boundaries, explicit synchronization primitives you have to manage yourself. A pipe adds none of that. It makes exactly one guarantee, and the guarantee is the entire feature:

The One Guarantee a Pipe Makes Whatever bytes go in the write end come out the read end, in the same order, and nothing else. No message boundaries. No addresses. No "who am I talking to." Just an ordered stream of bytes, exactly like a file — except the other side is a live process, not a disk.

That single guarantee is why a pipe is often described as "a FIFO byte stream" (first-in-first-out). If the writer calls write(fds[1], "AB", 2) and then write(fds[1], "CD", 2), a reader doing one big read() is guaranteed to see "ABCD" — never "CDAB", never interleaved out of order. The kernel enforces this ordering by construction: it's literally just appending bytes to one end of its buffer and removing them from the other, so order falls out for free.

💡 The Kernel Does All the Buffering — You Do None
Notice what the two processes on either end of a pipe never have to do: allocate a shared buffer, agree on its size, synchronize access to it with a lock, or handle the case where one side is faster than the other. All of that is handled by the kernel's single buffer and its blocking read()/write() semantics (the subject of the next lesson in this module). The two processes just call read() and write() like they would on any file — the pipe's entire job is to make "talking to another process" look exactly like "talking to a file you already know how to use."

One important consequence worth naming explicitly: a pipe carries bytes, not messages. If you write "HELLO" then "WORLD" in two separate calls, a reader that calls read() with a big enough buffer may get back "HELLOWORLD" in one shot, or "HEL" then "LOWORLD" in two — the pipe makes no promise about preserving your original write boundaries. If your protocol needs to know where one logical message ends and the next begins, that's something you have to encode into the byte stream (a length prefix, a delimiter like \n) — the pipe itself doesn't know or care.

Sidenote: This is exactly how a Unix pipeline like cat access.log | wc -l works at the byte level too — wc doesn't receive "lines" as discrete IPC messages, it receives a raw byte stream and does its own scanning for \n characters, same as if it had opened a regular file. The pipe never had any concept of "line" in the first place.
03 — The Feature You Use Every Day

What Is `ls | grep foo`, Really?

You've typed a pipeline like this hundreds of times. Two commands, one pipe character between them, and somehow the output of the left command becomes the input of the right one — as if by magic. There's no magic. There's exactly one syscall (pipe()), two fork() calls, and a small dance of dup2()/close() calls that your shell performs on your behalf, every single time.

Here's the crucial reframe: ls and grep know absolutely nothing about pipes. Neither program contains a single line of code that mentions IPC. ls just calls write() on file descriptor 1 (its stdout) like it always does — whether that's your terminal or a pipe is invisible to it. grep just calls read() on file descriptor 0 (its stdin) like it always does. The entire trick is that the shell, before it execs either program, secretly rewires what fd 0 and fd 1 point at. That rewiring is the real mechanism behind |, and it's what the rest of this lesson unpacks in full.

🧠 Why This Design Is Actually Brilliant
Because the rewiring happens entirely at the file-descriptor level, before ls or grep even exist as running programs (post-exec()), no program anywhere needs to be "pipe-aware." Any program that reads from stdin and writes to stdout — which is nearly every command-line tool ever written — automatically works in a pipeline, with zero code written specifically to support it. The generality of "everything is a file descriptor" is what makes this possible.
04 — The Real Mechanical Trick

fork(), dup2(), and the Rewiring

Let's build the pipeline step by step, exactly the way a real shell does it. Three ingredients, used in a specific order:

  1. The shell calls pipe() once, before forking anythingThis creates fd3 (read end) and fd4 (write end) inside the shell's own fd table. Nothing has forked yet — these two fds exist only in the shell process, for now.
  2. fork() — Child A is born, an exact fd-table clonefork() duplicates the shell's entire fd table into the child, including fd3 and fd4. Child A now has its own fd0/1/2 (its own stdin/stdout/stderr) and its own copies of fd3/fd4, all pointing at the same underlying pipe.
  3. Child A calls dup2(fd4, 1)This is the actual rewiring instruction: "make file descriptor 1 (stdout) point at whatever fd4 points at." After this call, fd1 and fd4 are two different numbers pointing at the exact same open pipe write-end — writing to either one writes to the pipe.
  4. Child A closes fd3 and fd4It no longer needs the original names — fd1 already does the job. Closing the extras keeps the fd table clean and, critically, makes sure Child A doesn't accidentally hold the read end open too (more on why that matters two sections from now).
  5. Child A execs lsexec() replaces Child A's program code with ls's — but the fd table survives exec() untouched. ls starts running, calls write() on fd1 like any program would, and every byte lands in the pipe without ls ever knowing it isn't a terminal.
  6. The shell forks Child B, from itself — not from Child AChild B inherits the shell's original fd3/fd4 (Child A's copies were local to Child A and already closed). Child B calls dup2(fd3, 0) — wiring its stdin to the pipe's read end — closes fd3/fd4, and execs grep foo.
  7. The shell closes its own fd3 and fd4, then waitsThe shell was never meant to read or write the pipe itself — it only existed to set the plumbing up. Once both children are wired and running, the shell drops its own references and waits for both to exit.

Stripped of shell-specific bookkeeping, here's roughly what that first child (the one that becomes ls) is actually doing, in C:

int fds[2];
pipe(fds);                 /* fds[0]=read end, fds[1]=write end */

pid_t child_a = fork();
if (child_a == 0) {
    /* --- this code runs inside Child A only --- */
    dup2(fds[1], STDOUT_FILENO);   /* fd 1 now IS the pipe write end */
    close(fds[0]);                  /* don't need the read end at all */
    close(fds[1]);                  /* don't need the original number either */
    execlp("ls", "ls", NULL);       /* fd table survives; ls inherits fd1 wired to the pipe */
    _exit(127);                      /* only reached if execlp() itself fails */
}

pid_t child_b = fork();
if (child_b == 0) {
    /* --- this code runs inside Child B only --- */
    dup2(fds[0], STDIN_FILENO);    /* fd 0 now IS the pipe read end */
    close(fds[0]);
    close(fds[1]);
    execlp("grep", "grep", "foo", NULL);
    _exit(127);
}

/* --- back in the shell (parent) --- */
close(fds[0]);
close(fds[1]);
waitpid(child_a, NULL, 0);
waitpid(child_b, NULL, 0);
1×
pipe() call, total, for the whole pipeline
2×
fork() calls — one per command in the pipeline
2×
dup2() calls — one per child, rewiring exactly one fd
6×
close() calls total — 2 per process × 3 processes

A pipeline of three commands (a | b | c) is the same idea extended: two pipes, three forks, and each middle command gets both ends rewired — its stdin from the pipe on its left, its stdout to the pipe on its right. The pattern doesn't change; it just repeats once per extra stage.

⚠️ Why dup2(), Not Just "Assign the Handle"
You can't just tell ls to "use fd4 as its output" — by convention, and by the standard C library, every program assumes its stdin/stdout/stderr are specifically fd 0, 1, and 2. There's no way to tell printf to write to fd4 instead. dup2(old, new) solves this by making file descriptor number new become a duplicate reference to whatever old points at — so after dup2(fd4, 1), fd1 is the pipe's write end, satisfying every piece of code that hardcodes "stdout is fd 1."
05 — The Bug Everyone Writes Once

Why You Must Close the End You Don't Use

Look back at step 4 and step 6 above: each child closes both of the original fd3/fd4 copies, even the one it just duplicated with dup2(), and even the one it never touches at all. This looks like unnecessary housekeeping. It is not — skipping it is the single most common bug in hand-written pipe code.

If you forget to close…What actually happens
The writer's copy of the read endHarmless in most cases, but wastes an fd slot and can mask bugs where you meant to read from your own pipe.
A reader's copy of the write endThe reader will block forever on read(), even after the real writer has exited — because the kernel still sees the write end as "open somewhere," so it never signals end-of-file.

That second row is the one that bites people. A pipe's read() only returns 0 (end-of-file) once every copy of the write end, across every process that ever held one, has been closed. If Child B in our pipeline forgot to close its inherited copy of fd4 (the write end) before reading, then even after ls finishes and its own fd1/fd4 close, grep's own leftover copy keeps the write end alive from the kernel's point of view — so grep hangs, waiting for a write that will never come, from a process (itself) that will never send one.

🐛 The Golden Rule of Pipe + fork()
After every fork() that's followed by dup2()-based rewiring, immediately close every fd you copied that you don't personally still need — especially the end of the pipe you're not using. A leaked write-end fd is invisible until the exact moment someone's read() hangs and never returns, which makes it one of the most confusing classes of bug to debug after the fact.
06 — Where This Fits Among IPC Options

Anonymous Pipe vs Named Pipe vs Shared Memory

This lesson is entirely about the left column below. The other two are covered elsewhere in bob_os — named pipes get their own deep-dive later in this module, and shared memory is covered in full in Module 3's explainer and in 23_shared_memory. Keep this table as a map of the territory:

✅ How to Choose, in One Sentence
Reach for an anonymous pipe when the two processes share a parent (the overwhelmingly common case, e.g. a shell launching a pipeline); reach for a named pipe when two already-running, unrelated processes need to rendezvous by name; reach for shared memory when the volume or frequency of data makes the per-byte cost of a kernel-mediated buffer too expensive.
07 — Quick Reference

Glossary & Key Terms

pipe()
The syscall that allocates a kernel buffer and returns two new file descriptors bound to it: fds[0] for reading, fds[1] for writing.
Anonymous Pipe
A pipe with no filesystem name — reachable only via file descriptors that were inherited through fork(), never by opening a path.
Read End / Write End
The two file descriptors a pipe() call produces. Bytes written to the write end appear, in order, on the read end.
FIFO Byte Stream
A pipe's core guarantee: bytes come out in the same order they went in, with no preserved message boundaries.
fork()
The syscall that clones a process, including a full copy of its open file descriptor table — the mechanism by which both ends of a pipe reach two different processes in the first place.
dup2(old, new)
Makes file descriptor number "new" become a duplicate reference to whatever "old" points at — the exact call that rewires a child's stdin/stdout onto a pipe end.
exec()
Replaces a process's running program with a new one, in place, while leaving its file descriptor table untouched — why a pipe wired up before exec() still works after it.
Shell Pipeline
The `cmd1 | cmd2` syntax: the shell creates one pipe, forks twice, and uses dup2()/close() in each child before exec()-ing the two commands.
