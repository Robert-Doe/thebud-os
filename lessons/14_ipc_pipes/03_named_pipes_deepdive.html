Everything in the first two lessons of this module assumed one thing quietly in the background: that the two processes sharing a pipe were relatives — one forked from the other, inheriting the fds. What if they aren't? What if two totally unrelated programs, started independently, minutes apart, need to talk? An anonymous pipe genuinely cannot help them. A named pipe — a FIFO — can, by doing something an anonymous pipe never does: getting a real name in the filesystem.

00 — Where We Left Off

Two Lessons In, One Assumption Unexamined

Lesson 1 built ls | grep foo from first principles: the shell calls pipe() once, then fork()s twice, so both children inherit copies of the same two file descriptors. Lesson 2 opened up what those fds actually point at — a fixed-size kernel ring buffer, with blocking on full/empty and SIGPIPE when the reader's gone for good. Both lessons quietly depended on one fact: the pipe was created by a common ancestor, before anyone forked. That's not a minor detail — it's the entire reason an anonymous pipe works at all, and it's exactly the assumption this lesson breaks.

Good news up front: nothing from Lesson 2 gets thrown away. The ring buffer, the blocking semantics, SIGPIPE — all of it carries over here completely unchanged. What changes is only how the two ends find each other in the first place.

01 — The Problem an Anonymous Pipe Can't Solve

Where Do File Descriptors Actually Come From?

Ask yourself a plain question: how does a process ever get a pipe file descriptor in the first place? There are exactly two ways. Either it calls pipe() itself, or it inherits a copy from its parent via fork(). That's the complete list. There is no third mechanism — no syscall exists that says "give me a handle to the pipe some other, unrelated process happens to have open."

The Hard Limit of an Anonymous Pipe Its file descriptors only exist because a common ancestor process created them before forking. Two already-running, otherwise-unrelated processes — say, a cron job and a long-lived daemon started at boot — have absolutely no way to end up holding fds that point at the same kernel pipe. There's no shared ancestor moment where fork() could have handed both of them a copy.

This isn't a bug or an oversight — it's a direct consequence of how anonymous pipes are identified. They have no name, no path, nothing you could type or pass as a string to a stranger process. The only "identity" a pipe has is a small integer (a file descriptor number) that's meaningful only inside the fd table of a process that already has it. Two unrelated processes each have their own private fd table, numbered independently — fd 5 in one process has nothing to do with fd 5 in another.

⚠️ A Concrete Case Where This Bites You
Imagine a logging daemon that starts at boot, and a separate command-line tool a user runs later, by hand, that wants to feed it log lines. Neither process is an ancestor of the other — the daemon was started by the init system; the tool was started later by a shell, itself a totally different process tree. An anonymous pipe cannot connect them, full stop, no matter how you juggle fork() — there is no point in either program's history where a common parent could have created and shared one.
02 — Giving a Pipe an Address

mkfifo(): A Pipe You Can Open() By Path

The fix is almost embarrassingly direct: give the pipe a name in a place both processes can already reach — the filesystem. That's mkfifo():

#include <sys/stat.h>
int rc = mkfifo("/tmp/mypipe", 0666);
/* creates a special filesystem entry at /tmp/mypipe
 * rc == 0 on success, -1 on failure (e.g. already exists)   */

After this call, ls -l /tmp/mypipe shows a real directory entry — with its own permissions, owner, and a file type marker (p in ls -l's leftmost column, corresponding to the S_IFIFO file type bit) that says "this is a FIFO, not a regular file." Any process on the system that can see that path — with no relation to whoever ran mkfifo() whatsoever — can now call open("/tmp/mypipe", ...) and get a file descriptor connected to it. That's the entire trick: discoverability by name, instead of inheritance by fork().

💡 The Aha Moment — Nothing Is Actually Stored There
Despite living in the filesystem and showing up in ls, a FIFO's directory entry holds zero bytes of pipe data. It's a rendezvous point, not a file — a name the kernel uses to find (or create) the underlying kernel pipe object, the exact same ring-buffer structure from Lesson 2, at open() time. Write 4GB through a FIFO and check the disk afterward: nothing changed, because nothing was ever written to disk. The filesystem's only job here is being a shared namespace two strangers can both look up by the same string.

03 — The Handshake Nobody Mentions

open() Itself Can Block

Here's a genuinely surprising property, and it's unique to FIFOs among all the file types you'll normally open: calling open() on a named pipe can block before you've even gotten a file descriptor back — not on read() or write(), but on open() itself.

The Default Rendezvous Rule Opening a FIFO for reading (O_RDONLY) blocks until some process opens it for writing. Opening it for writing (O_WRONLY) blocks until some process opens it for reading. Neither side's open() call returns until BOTH sides are present. This is the kernel enforcing a two-party handshake before any data can possibly flow — pass O_NONBLOCK to opt out and get an immediate error/success instead of blocking.

Think about why this makes sense. With an anonymous pipe, both ends are guaranteed to exist simultaneously — they were created together, by the same pipe() call, before anyone even forked. A FIFO has no such guarantee: process A might mkfifo() and try to open it minutes before process B ever starts. Without a blocking handshake, A's write() calls would have nowhere defined to go yet — is there a reader coming, or not? The rendezvous rule turns "wait until someone shows up" into an explicit, well-defined step, rather than leaving it ambiguous.

  1. Process A: mkfifo("/tmp/mypipe", 0666)The rendezvous point now exists in the filesystem. Nobody has opened it yet.
  2. Process A: open("/tmp/mypipe", O_WRONLY)This call does not return yet. Process A's PCB state flips to BLOCKED — the exact same three-state vocabulary from Module 3, just triggered by open() instead of read()/write() this time.
  3. Process B starts, independently, and calls open("/tmp/mypipe", O_RDONLY)The instant this call happens, the kernel sees both a waiting writer and a waiting reader for the same FIFO. Both open() calls unblock and return successfully, at essentially the same moment.
  4. From here, it's an ordinary pipeBoth processes now hold ordinary file descriptors connected to the same kernel ring buffer. read(), write(), blocking on full/empty, SIGPIPE if the other side vanishes — every rule from Lesson 2 applies, unmodified.

In C, rather than shell redirection, the same handshake looks like this — note that neither side needs to know anything about the other beyond the agreed-upon path:

/* writer.c — run whenever you like, by anyone */
#include <fcntl.h>
mkfifo("/tmp/mypipe", 0666);        /* harmless if it already exists (EEXIST) */
int fd = open("/tmp/mypipe", O_WRONLY);  /* BLOCKS until a reader opens it */
write(fd, "hello from an unrelated process\n", 33);
close(fd);
/* reader.c — started independently, possibly first */
#include <fcntl.h>
mkfifo("/tmp/mypipe", 0666);        /* also harmless — same path, same object */
int fd = open("/tmp/mypipe", O_RDONLY);  /* BLOCKS until a writer opens it */
char buf[128];
int n = read(fd, buf, sizeof(buf));      /* ordinary blocking read, exactly like Lesson 2 */
close(fd);
💡 Either Side Can Call mkfifo() — It's Idempotent In Practice
Both snippets above call mkfifo() on the same path, and that's a deliberately common pattern: whichever process happens to run first creates the rendezvous point, and the second call simply fails with EEXIST (harmless — just check for and ignore that specific error). Neither process needs to know or care which one actually "wins" the race to create the name.

In Lesson 1's shell-pipeline animation, both children existed because one parent forked them, in sequence, one after another, all within milliseconds. 05 — A Concrete, Runnable Example

Two Shell Scripts, One FIFO

You don't need to write any C to see this work — the shell exposes mkfifo as a command, and every shell's redirection operators (>, <) happily target a FIFO path exactly like a regular file. Open two separate terminals — genuinely separate processes, with no relationship to each other beyond both being your shell.

# Terminal 1 — create the rendezvous point, then read from it
mkfifo /tmp/mypipe
echo "waiting for a message..."
cat < /tmp/mypipe          # blocks here — this IS the open() rendezvous
echo "got it, script continuing"
# Terminal 2 — a completely separate shell process, run whenever you like
echo "hello from an unrelated process" > /tmp/mypipe
# the moment this runs, BOTH terminals' shell commands unblock at once

Run Terminal 1's block first — you'll see it hang at cat < /tmp/mypipe, doing nothing, because it's blocked inside open() waiting for a writer. Only once you run Terminal 2, potentially minutes later, does Terminal 1 unblock, print the message, and continue. That pause is the rendezvous, visible with your own eyes, between two shells that have never heard of each other.

Sidenote: This exact pattern — a long-running FIFO reader loop plus scripts that write to it whenever something happens — is a genuinely common lightweight IPC technique for shell tooling: a "control pipe" that a daemon script reads commands from, fed by unrelated one-off scripts elsewhere in a cron job or CI pipeline, with none of them needing to know each other's PID or relationship.
06 — Names Aren't Forever

unlink() and the Persistence Quirk

A FIFO's directory entry behaves like any other filesystem name when it comes to cleanup: unlink("/tmp/mypipe") (or rm /tmp/mypipe from a shell) removes it. But — same as unlinking a regular file that some process still has open — removing the name doesn't destroy the underlying kernel object out from under processes that already have it open.

🗂️ What unlink() Removes

Just the directory entry — the name-to-object mapping. After this, no new process can find the pipe by calling open() on that path; it simply won't exist anymore as far as the filesystem namespace is concerned.

♻️ What Survives

Any file descriptors already open, on either end, keep working exactly as before — the kernel ring buffer they point at doesn't care that its name was removed. It's only fully torn down once every fd referencing it, everywhere, is closed — the same reference-counting rule an anonymous pipe already follows.
⚠️ The Practical Upshot
A stale /tmp/mypipe left over from a crashed script is completely harmless to rm — you're never at risk of "deleting in-flight data," because, as established back in Lesson 02, no data was ever stored at that path in the first place. The name is just a rendezvous point; deleting it only closes the door for future strangers to find each other there, it doesn't touch any conversation already underway.

✅ The One-Sentence Takeaway For This Whole Module
An anonymous pipe and a named pipe are the same mechanism wearing two different hats — the only thing that changes between them is how two file descriptors end up pointing at one kernel ring buffer: inherited silently through fork(), or discovered deliberately through a filesystem path. Reach for shared memory only once you've outgrown either — when the volume or frequency of data makes paying the kernel-copy cost, on every single byte, the actual bottleneck.
08 — Quick Reference

Glossary & Key Terms

Named Pipe / FIFO
A pipe with a real filesystem path, creatable and openable by any process — as opposed to an anonymous pipe, reachable only via inherited file descriptors.
mkfifo()
The syscall (and shell command) that creates a FIFO's directory entry at a given path, without opening it or transferring any data.
S_IFIFO
The file-type bit marking a directory entry as a FIFO rather than a regular file, directory, or other special file type — shown as "p" in `ls -l`.
Rendezvous
The blocking handshake a FIFO's open() performs: a reader's open() waits for a writer's open() (and vice versa) before either call returns.
O_NONBLOCK
A flag passed to open() that opts out of the rendezvous block, returning immediately with success or an error instead of waiting for the other side.
unlink()
Removes a FIFO's name from the filesystem without affecting any file descriptors already open on it — the underlying pipe survives until every fd referencing it closes.
Well-Known Path
A filesystem location agreed upon in advance (e.g. by convention or configuration) that lets unrelated processes rendezvous without any prior direct relationship.
Kernel Ring Buffer
The same fixed-size, wrap-around byte buffer from Lesson 2 — identical underneath a FIFO as underneath an anonymous pipe.
