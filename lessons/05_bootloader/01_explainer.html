01 — Before Your Code Ever Runs

What the BIOS Does While You're Not Looking

Your boot.asm in 01_bootloader/ starts with a comment: "Loaded by BIOS at 0x7C00." That single sentence hides an enormous amount of work the machine already did before your first instruction ever executes. Think of it like arriving at a movie set as the star actor — by the time you walk in, someone already unlocked the building, turned on the lights, checked every camera, and cleared the room. You just don't see any of that happen.

The moment power hits the CPU, it doesn't reset to address 0. It resets to 0xFFFFFFF0 — sixteen bytes below the very top of its addressable space. That address is deliberately mapped, by the motherboard's chipset, to the BIOS ROM chip, not to RAM. There is a reason for this: RAM is empty garbage on power-up, but ROM is permanent and always has valid code sitting there. The CPU's very first fetch is guaranteed to land on real instructions.

  1. Reset vector fetchThe CPU begins executing BIOS firmware at the fixed ROM address burned into the chipset. It boots in 16-bit real mode by hardware default — this has been true since the 8086, and it's true on your machine today even if it eventually runs 64-bit code.
  2. POST — Power-On Self-TestThe BIOS runs a self-check: verify the CPU is sane, walk a test pattern across RAM to confirm it holds bits correctly, probe the keyboard controller, initialize the video card's own BIOS extension (that's the manufacturer splash screen you see for half a second). This is the "annoying startup screen" — it's the machine convincing itself it isn't broken.
  3. Device enumerationBIOS walks its known buses — legacy IDE/ATA controllers, then PCI — cataloging what hardware exists: disks, controllers, expansion cards. It builds internal tables describing what it found. None of this is visible to you yet; it's bookkeeping for BIOS's own service routines.
  4. Boot device scanBIOS consults its configured boot order (stored in CMOS/NVRAM — the thing a dead coin-cell battery used to reset on old desktops) and, for each candidate device in order, reads its very first sector into a scratch buffer and checks: do the last two bytes read 0x55 then 0xAA? First device that passes wins.
  5. Load and jumpBIOS copies that winning 512-byte sector verbatim into RAM at physical address 0x7C00, sets CS:IP to point there, and executes a jump. From this instruction onward, BIOS is not driving anymore — you are, and BIOS has become a passive library of interrupt-based services (INT 0x10 for video, INT 0x13 for disk, INT 0x16 for keyboard) that your code can still call, but nothing is calling you.
💡 The Aha Moment
Here's the detail that trips people up the first time: BIOS never parses, understands, or cares what's inside your 512 bytes. It doesn't check for a valid instruction stream, a sane stack, or anything resembling a "program." It performs exactly one structural check — do bytes 510 and 511 read 0x55 then 0xAA? — and if that passes, it blindly jumps into byte 0. Everything from that point on is your problem, including the possibility that your "boot sector" is actually just 510 zero bytes followed by the signature, which BIOS will happily execute as 510 ADD [BX+SI], AL instructions (the opcode for 0x00 0x00) before crashing into garbage.

POST failures deserve one more note, because they're the reason a genuinely dead machine still communicates with you even with no video output initialized yet. If POST finds something seriously wrong — bad or missing RAM, a failed keyboard controller — it can't print an error message, since the video card may not even be working yet. Instead, classic BIOS implementations fall back to a sequence of motherboard speaker beeps, a diagnostic code encoded in nothing more than timing and count.

Beep Pattern (classic AMI BIOS)Meaning

2 short beepsRAM parity error detected during the memory test

Beep codes vary by BIOS vendor. AMI, Award, and Phoenix each defined their own patterns, and modern UEFI firmware mostly replaced audible codes with onboard LED diagnostic codes instead. The underlying idea hasn't changed in forty years, though: when nothing else on the machine can be trusted to work yet, encode the diagnosis in the one output device guaranteed to need no drivers or initialization — a speaker wired directly to the motherboard.

The boot device scan itself follows an ordered list, not a fixed rule — this is exactly the "Boot Order" or "Boot Priority" screen you've probably clicked through in a BIOS setup menu:

BIOS tries each entry in order, running the exact same "read sector 0, check for 0x55AA" test on each, and stops at the first one that passes. This is precisely why, when you run make run for this project's QEMU setup, the virtual machine finds and boots disk.img — QEMU is presenting that file to the guest as though it were the highest-priority disk in this exact scan order.

02 — The Constraints You're Stuck With

Welcome to Real Mode — Population: You, in 1978

The tutorial for this module already told you real mode is "the same mode the 8086 from 1978 used." That's not a throwaway line — it's the single fact that explains almost every weird decision in boot.asm. Modern CPUs are staggeringly capable: 64-bit registers, paged virtual memory, hardware memory protection, gigabytes of flat address space. None of that exists yet. Right now, in this sector, you have exactly what a programmer had over four decades ago.

Real Mode Physical Address Formula physical address = (segment × 16) + offset Every memory access in this sector goes through this — there is no MMU, no page tables, nothing translating addresses for you.

Look at the top of boot.asm again: xor ax, ax then mov ds, ax / mov es, ax / mov ss, ax. That's not decoration — it's forcing every segment register to zero so that "address" and "offset" mean the same thing, because otherwise every single memory reference would silently mean something different depending on whatever garbage BIOS left in those registers.

🧠 No C Runtime — What That Phrase Actually Costs You
"No C runtime" sounds abstract until you list what a C program silently gets for free that you now have to build by hand or do without entirely: a stack already set up before main() runs, global variables zero-initialized (the BSS clear), a C library with printf and malloc, and a linker that resolves function addresses across files. None of it exists yet. That's precisely why line 23 of boot.asm — mov sp, 0x7C00 — is you personally setting up the stack, and why printing text means hand-rolling print_string around INT 0x10 instead of calling printf("..."). Module 02 (Kernel Entry) is precisely the module whose entire job is building enough scaffolding that C becomes usable — until then, everything is raw assembly talking directly to BIOS interrupts and raw registers.

This is also why NASM directives like [BITS 16] and [ORG 0x7C00] at the very top of boot.asm matter so much. There's no loader assigning your code an address at load time the way a modern OS assigns a program its virtual address space — you are telling the assembler, at compile time, "trust me, whatever labels you compute, add 0x7C00 to them," because that's the one and only address BIOS is contractually obligated to load you at.

The Same Physical Byte, Written Two Different Ways

Segment:offset addressing has a strange property that trips people up the first time they see it: because the formula is a multiply-then-add, there is no single unique way to write most physical addresses. 0x7C00 itself is a perfect example.

Two Segment:Offset Pairs, One Physical Address 0000:7C00 → (0x0000 × 16) + 0x7C00 = 0x07C00 07C0:0000 → (0x07C0 × 16) + 0x0000 = 0x07C00 Both notations land on the exact same physical byte. This is why some bootloaders set CS=0x07C0 and use offsets from 0 instead of CS=0x0000 with offsets from 0x7C00 — you'll see both conventions in the wild, and both are correct.

This overlap is called aliasing, and it's a direct consequence of real mode having no single canonical address space — just a formula that happens to produce the same output from more than one input. It's harmless here, but it's the same underlying quirk responsible for the historical A20 line controversy: the original 8086 only had 20 physical address pins, so address calculations that "overflowed" past 1MB silently wrapped back around to 0 due to the same segment:offset arithmetic. Some early software accidentally depended on that wraparound behavior, so when the 80286 added a 21st address line (A20) and stopped wrapping, IBM had to add a special gate to keep older software working — a gate every protected-mode OS, including the one this project is building toward in Module 02, has to explicitly enable before it can safely address memory past the 1MB mark.

The data table above mentions the IVT occupies 0x0000–0x03FF. Here's what's actually sitting in a handful of those 256 four-byte slots — the exact entries your bootloader (and every real-mode program) leans on constantly without ever touching them directly:

Sharpen your pencil. boot.asm's print_string routine sets ah, 0x0E before calling int 0x10 — that's BIOS video sub-function "teletype output," one specific service living under the single INT 0x10 vector, selected by AH exactly the same way AH selects among INT 0x13's services. If IVT offset 0x0040 holds one single handler address for all of INT 0x10's sub-functions, where does the branching to the specific teletype-output code path happen? (Answer: entirely inside BIOS's own handler routine — it reads AH itself and dispatches internally, the same pattern INT 0x13 uses, and the same pattern your own kernel's interrupt handlers will use once you're past real mode.)
03 — Why Exactly 512

The 512-Byte Ceiling Isn't Arbitrary

Why 512, and not 256, or 1024, or "however many bytes your bootloader happens to need"? The answer isn't a design choice made for bootloaders at all — it's an inherited constraint from disk hardware that predates the PC. Floppy disks and early hard drives were physically formatted into fixed-size chunks called sectors, and the industry standard sector size, going back to the earliest IBM PC-compatible floppy controllers, was 512 bytes. That size was baked into disk controller hardware, not chosen by anyone writing bootloader code.

BIOS's boot process reads exactly one sector — the very first sector of the boot device, sometimes called sector 0 or LBA 0 — into RAM and nothing more. Not "the first N bytes of a program," not "until it finds an end marker." One fixed-size disk sector, full stop. Since that hardware sector is 512 bytes, your bootloader's first-stage code is capped at 512 bytes, minus the 2 bytes reserved for the signature at the very end — 510 usable bytes for actual code and data.

Modern disks quietly moved on. Since roughly the 2010s, most hard drives and SSDs physically use 4096-byte ("4K") sectors internally, but almost all of them still expose a 512-byte logical sector size to software for backward compatibility — a scheme sometimes called 512e. The BIOS boot process, and your bootloader, never notice the difference; they still see, and are still capped at, exactly 512 logical bytes. You're relying on decades of an industry collectively agreeing to never break this.

💥 What 510 usable bytes rules out

  • Parsing any real filesystem (FAT32's own boot sector code barely manages a minimal version of this)
  • Meaningful error handling or recovery logic
  • Loading more than a handful of hardcoded disk sectors
  • Any use of the stack-heavy conventions a C compiler would generate

✅ What 510 bytes is plenty for

  • Setting segment registers and a stack (a handful of instructions)
  • Printing a short status string via INT 0x10
  • One disk-read call via INT 0x13 to load something bigger
  • A far jump into whatever you just loaded

That second column is not a coincidence — it is a description of literally every real-world stage-1 bootloader ever written, including the one sitting in this project right now. 510 bytes was never meant to hold an operating system. It was only ever meant to hold enough code to go get something that could.

04 — The Two Bytes That Matter Most

0x55AA: The Boot Signature

Look at the very bottom of boot.asm:

times 510 - ($ - $$) db 0   ; Pad with zeros up to byte 510
dw 0xAA55                    ; Boot signature (little-endian: stored as 55 AA)

The times directive is doing bookkeeping: $ is "the current assembly position," $$ is "the start of this section," so $ - $$ is exactly how many bytes have been assembled so far. Whatever's left up to byte 510 gets padded with zeros. Then dw 0xAA55 writes a 16-bit word — but because x86 is little-endian, the low byte is stored first, so the actual bytes on disk at offsets 510 and 511 are 0x55 then 0xAA, exactly what BIOS checks for.

Byte OffsetContentPurpose
0 – 509Your code and dataEverything you actually wrote — instructions, the message string, padding
5100x55First signature byte — BIOS checks this exact value
5110xAASecond signature byte — both must match or the sector is skipped
⚠️ It's a Sanity Check, Not a Checksum
A checksum verifies the contents weren't corrupted. The boot signature verifies nothing of the sort — it's a fixed, content-independent marker meaning only "the author of this sector claims it's meant to be executed as boot code." A sector of 510 zero bytes followed by 0x55 0xAA is, as far as BIOS is concerned, completely valid and bootable — it will load and jump into it exactly the same as a working bootloader, then immediately start executing whatever 0x00 0x00 decodes to (a harmless-looking but wrong instruction) until something crashes. This is precisely the failure mode the tutorial's "Gotcha" callout warns about: get the byte order backwards, and QEMU doesn't error out cleanly — it just hangs on a blank screen, because as far as the machine is concerned, nothing went wrong at all.

This also means the signature check tells you nothing about whether a disk is safe to boot, only whether it's willing to be. Historically, this is exactly the mechanism early boot-sector viruses exploited — infect the boot sector of a floppy, keep the two magic bytes intact, and the machine will faithfully execute your malicious code before the operating system ever gets a say. The check was designed to answer "is this disk bootable," and it answers exactly that question, no more.

Reading the Assembled Sector Yourself

If you assemble boot.asm with NASM and open the resulting flat binary in a hex editor, you'd see something like this near the very end of the file — worth being able to recognize on sight, since you'll be staring at raw hex dumps constantly in low-level work:

Offset  Bytes                                    ASCII
000000  FA 33 C0 8E D8 8E C0 8E D0 BC 00 7C        .3..........
...
0001F0  00 00 00 00 00 00 00 00 00 00 00 00        ............
000200  00 00 00 00 00 00 00 00 00 00 55 AA        ..........U.

That trailing 00 00 00 00 00 00 00 00 00 00 55 AA on the last line is the times 510 - ($ - $$) db 0 padding followed immediately by the signature — byte offset 0x200 is decimal 512, so the last two bytes of the sector, at offsets 0x1FE and 0x1FF (510 and 511 in decimal), read 55 then AA. If you ever suspect your bootloader isn't booting because of a signature problem, this is exactly where to look — the last two bytes of a 512-byte file, no more, no less.

05 — The Bootloader's Entire Philosophy

Load Something Bigger, Then Get Out of the Way

Here's the mental model worth keeping for the rest of this module, and honestly for every "chain of trust" system you'll ever meet in systems programming: a bootloader stage does not try to be the operating system. It does exactly one thing — locate and load the next, larger, more capable piece of code — and then it disappears, handing off control completely.

⚡
BIOS

→
💾

🧭

Exits real mode, sets up C-friendly stack, zeroes BSS
→
🏗️
kernel_main()
Finally, actual C code — the OS proper begins

Notice something about that pipeline: every stage is bigger, more capable, and less constrained than the one before it. BIOS is fixed firmware that can only understand "read a sector, jump." Stage 1 is 510 bytes of raw assembly that can read more sectors and do a far jump. kernel_entry.asm can finally afford to build the scaffolding a real language needs. Each link in the chain earns just enough trust and just enough capability to build the next link, then steps aside completely — it never comes back.

🔁 This Pattern Has a Name: Chain-Loading
Loading a small trusted program that in turn loads a bigger, more capable one is called chain-loading, and it's not unique to this project — GRUB does it (a tiny MBR stage loads GRUB's own larger core image from the filesystem), UEFI firmware does it (loads a bootloader off an EFI System Partition, which then loads a kernel), and even this project's own progression from boot.asm to kernel_entry.asm to kernel_main() is three links in exactly this chain. The deep dive on MBR vs GPT in this same lesson module goes further into how real-world partitioned disks make chain-loading a two-hop process before the kernel is even involved.

Right now, boot.asm as written in this repository doesn't load a kernel yet — it prints its message and executes cli / hlt to halt. That's deliberate: the tutorial's own "Brain Exercise" section is pointing you toward filling in the INT 0x13 disk-read call and the far jump to 0x1000 yourself. The next lesson in this series, on BIOS disk services, is exactly the missing piece — the mechanism by which stage 1 actually goes and gets stage 2.

Why Every Stage Wants Out of Real Mode Eventually

"Get out of the way" has a second meaning worth previewing here, even though the actual mode switch is Module 02's job, not this one's. Every constraint from the real-mode section earlier in this lesson — 16-bit registers, the 1MB ceiling, zero memory protection — is a constraint the entire chain is still operating under, all the way up through kernel_entry.asm, right up until the moment something finally executes the instruction that leaves real mode behind for good.

🕰️ Real Mode (where you are now)

16-bit registers, 1MB addressable, segment:offset addressing, zero memory protection, no paging — identical in spirit to an 8086 from 1978. Every byte of boot.asm runs here.

🚀 Protected Mode (Module 02's destination)

32-bit registers, 4GB flat addressable per segment, a Global Descriptor Table replacing segment:offset tricks, hardware-enforced privilege levels, and — eventually — paging. This is the mode C code and the rest of this OS actually run in.

The reason this project's own module ordering puts "Kernel Entry" immediately after "Bootloader" is exactly this dependency: stage 1's last real job, once it has loaded the kernel image into memory, is to help set the stage for that mode switch — loading a GDT, setting the Protection Enable bit in CR0, and performing a far jump that flushes the CPU's instruction pipeline into 32-bit code. None of that is this lesson's focus, but it's worth knowing the destination: everything you've learned here about 512 bytes, signatures, and real-mode constraints describes a phase of the boot process that, by design, is meant to be brief.

✅ What "No Bootable Device" Actually Means
When every candidate device fails the signature check, BIOS doesn't crash — it does exactly what it's designed to do: report failure back up. Classic BIOS implementations fall back to software interrupt INT 0x18 ("boot failure," historically pointing at ROM BASIC on the original IBM PC) or print a message like "No bootable device — insert boot disk and press any key." Either way, the machine is completely fine — the outcome is identical in spirit to your own boot.asm hitting jc disk_error after a failed INT 0x13 call: a clean, deliberate failure path, not a mystery hang.
08 — Quick Reference

Glossary & Key Terms

POST
Power-On Self-Test — BIOS's initial hardware sanity checks (CPU, RAM, keyboard, video) before it looks for anything to boot.
Reset Vector
The fixed physical address (0xFFFFFFF0) the CPU begins fetching instructions from immediately after power-on, mapped to BIOS ROM.
Real Mode
The 16-bit, unprotected, unpaged execution mode every x86 CPU boots into, unchanged in spirit since the 8086.
Segment:Offset Addressing
Real mode's memory scheme: physical address = segment × 16 + offset, giving a 1MB addressable range from 16-bit registers.
Interrupt Vector Table (IVT)
256 four-byte entries at physical address 0x0000, each pointing to a handler — this is what makes INT 0x10 / INT 0x13 / INT 0x16 work.
Boot Signature (0x55AA)
The two fixed bytes BIOS checks at offsets 510–511 of a candidate sector to decide "treat this as bootable code."
Sector
The fixed-size chunk (512 bytes, logically, on virtually all disks) that storage hardware reads or writes as one atomic unit.
Chain-Loading
The pattern of a small trusted stage loading a larger, more capable stage and handing off control completely — BIOS → stage 1 → stage 2 → kernel.
A20 Line
The 21st physical address line; historically gated off to preserve 8086-style 1MB address wraparound for compatibility, and must be enabled before addressing memory above 1MB.
Protected Mode
The 32-bit CPU mode with a flat 4GB address space, GDT-based segmentation, and hardware privilege levels — the mode Module 02 switches into permanently.
