MBR, GPT, and Why
Bootloaders Chain-Load

Your bootloader loads a flat kernel image from fixed sectors — no filesystem, no partitions, nothing standing between it and the kernel. Real-world disks aren't that simple: they're carved into partitions by a table living in that very same first sector. This is the story of the 512-byte table that ran the entire industry for decades, why it hit a wall, and the two-stage handoff pattern — chain-loading — that every real bootloader, including the one this project is building toward, is built around.

01 — One Sector, Three Jobs

Inside the Master Boot Record

You already know the boot sector is 512 bytes ending in 0x55AA. What earlier lessons in this module glossed over is that on a real, partitioned disk, that very same 512-byte sector — sector 0, the one BIOS loads to 0x7C00 — isn't only a bootloader. It's also, simultaneously, a partition table. This dual-purpose sector is called the Master Boot Record (MBR), and it packs three distinct regions into one 512-byte package.

Byte RangeSizeContents
0 – 445446 bytesBootstrap code — a tiny program, conceptually a cousin of this project's own boot.asm
446 – 50964 bytesPartition table — exactly 4 entries, 16 bytes each
510 – 5112 bytesBoot signature — 0x55 0xAA, same check BIOS already performs

Notice the math: 446 + 64 + 2 = 512, exactly the sector size you already know. This wasn't a coincidence of good planning — it was a tight squeeze. The partition table and signature had to fit inside the one sector BIOS was already contractually loading, so the bootstrap code's budget shrank from a theoretical 510 bytes (as in boot.asm, which has no partition table to make room for) down to 446. That's genuinely less room to work with than a non-partitioned boot sector gets — one more reason real MBR bootstrap code is famously terse.

⚠️ The MBR Has Also Always Been a Prime Attack Target
Every property that makes the MBR powerful — it runs first, unconditionally, before any operating system or antivirus software has loaded — also makes it a historically favorite target for malware. Classic "boot sector viruses" from the DOS and early Windows era, and their modern descendants (bootkits), infect exactly this 446 bytes of bootstrap code, patch the partition table to redirect the real OS load slightly later, and execute with full control of the machine before anything capable of detecting them has even started running. This is a direct, practical consequence of the same trust chain covered in the chain-loading section ahead: whoever controls the first link in a chain-of-trust controls everything downstream of it, which is exactly why modern systems increasingly rely on UEFI Secure Boot to cryptographically verify each stage before executing it — a protection that simply didn't exist in the classic BIOS+MBR world this lesson describes.
💡 The Aha Moment
The MBR's bootstrap code and this project's boot.asm are solving almost the same problem under almost the same constraints — both are real-mode code loaded to 0x7C00, checked for the same 0x55AA signature, given only a few hundred bytes to work with. The difference is what they load next: boot.asm currently reads fixed, hardcoded sectors straight into a kernel buffer, with no partition table involved at all. A real MBR bootstrap has to first consult its own embedded partition table to even figure out where the next stage lives, because on a partitioned disk that location isn't fixed — it depends on which partition is marked bootable and where that partition starts.
02 — Sixteen Bytes, Fully Decoded

Anatomy of a Partition Table Entry

Each of the four partition table slots is exactly 16 bytes, packed tightly with fixed-width fields — no names, no padding for readability, just raw bytes at fixed offsets, the same design philosophy as the INT 13h register contract from the disk services lesson.

That 32-bit LBA field is exactly where the 2TB wall comes from. A 4-byte field can hold values up to 2^32 − 1 = 4,294,967,295. Multiply by the 512-byte sector size and you get a hard ceiling of exactly 2,199,023,255,040 bytes — about 2TB. An MBR partition simply cannot describe a starting point or size beyond that, no matter how large the underlying disk is. Keep this number in mind; it's one of the two problems GPT was built to solve.

That single partition-type byte carries more historical baggage than its size suggests — dozens of operating systems and tools have claimed values from the same shared 256-value space over four decades, and collisions were inevitable. A few of the values you'll actually encounter poking around real disks:

03 — Why Only Four

The 4-Primary-Partition Wall

64 bytes of partition table, 16 bytes per entry — that arithmetic only ever produces one answer: exactly 4 slots. There was no policy decision that "four is enough disks for anyone"; it's simply what fits in the byte budget left over after the bootstrap code and signature claimed their share of the same 512-byte sector. When this format was standardized in the early 1980s, a single hard disk on a personal computer was a novelty — the idea that someone might eventually want a dozen partitions on one drive wasn't remotely on anyone's radar.

As disks grew and multi-boot setups became common, the industry needed a workaround without breaking every existing tool that understood the 4-entry format. The fix: let one of the four primary slots be marked as a special extended partition (type 0x05 or 0x0F) instead of a normal data partition. An extended partition doesn't hold data directly — it holds a linked list of additional partition descriptors, each one living in its own small header sector called an Extended Boot Record (EBR), chained one after another.

✅ What the Extended Partition Hack Bought You

Effectively unlimited additional logical partitions, without changing the on-disk MBR format at all — every tool that already understood "4 entries, 16 bytes each" kept working, because the extended partition looks like an ordinary single entry from the outside.

⚠️ What It Didn't Fix

Still only 4 primary slots (3 usable if one becomes the extended container); logical partitions require walking a linked list of EBRs to enumerate, adding real complexity; and none of this touched the separate, harder 2TB addressing ceiling from the 32-bit LBA field.
⚠️ A Real Constraint, Not a Historical Footnote
If you've ever partitioned a Windows machine with MBR-style disks and hit a wall trying to create a 5th primary partition, or been forced to convert one slot to "extended" before Disk Management would let you continue, you were running directly into this 40-year-old 64-byte table. It wasn't a software bug — it was the literal, physical byte budget of a 1980s design decision, still enforced on every MBR disk today.

How the EBR Chain Actually Links Together

Each EBR follows the exact same 16-byte-entry, 0x55AA-terminated layout as the MBR itself, but it only ever uses two of its four slots meaningfully: one entry describing the actual logical partition living right after this EBR, and a second entry pointing to the next EBR further down the disk — a classic linked list, just expressed in on-disk partition table format instead of in-memory pointers.

Enumerating every logical partition on an MBR disk therefore means walking this chain one EBR at a time until a terminating all-zero second entry is found — genuinely more work than GPT's approach of just reading one flat array, and a small taste of the complexity GPT was designed to avoid entirely.

04 — The Modern Replacement

GPT: Solving Three Problems at Once

The GUID Partition Table doesn't patch around MBR's limits the way the extended-partition hack did — it replaces the format outright, and it's worth being precise about what problems it actually solves, because it's exactly three, each mapping directly to a limitation you just read about.

MBR's ProblemGPT's Fix
Only 4 primary partition slots (64-byte table)A dedicated partition entry array — typically 128 entries, each 128 bytes (16KiB total), with room to configure more
32-bit LBA fields cap addressing at ~2TB64-bit LBA fields throughout — the addressing ceiling becomes astronomically large (roughly 8 zettabytes with 512-byte sectors)
One single MBR sector is the entire point of failureA primary header near the start of the disk and a full backup header + partition array at the very last LBA, each with CRC32 checksums

The GPT Disk Layout

A GPT disk still begins with something that looks like an MBR at LBA 0 — but it's a deliberately inert one, called the protective MBR, containing a single partition entry of type 0xEE that claims to span the entire disk. Its purpose is purely defensive: old, MBR-only disk tools that don't understand GPT at all will see that one entry, correctly conclude "this whole disk is already in use," and refuse to overwrite it — rather than seeing an apparently blank/unpartitioned disk and offering to helpfully repartition it, destroying the GPT data that follows.

🧭 GPT's Redundancy Is the Real Headline Feature
An MBR disk has exactly one place its partition table can live: sector 0. Corrupt that one sector — a bad write, a stray tool, a boot-sector virus like the ones mentioned in the earlier lesson on boot signatures — and every partition on the disk becomes unreadable in one stroke, even though the actual data partitions are completely intact. GPT keeps a full backup header and full backup partition array at the opposite end of the disk, and both the primary and backup carry CRC32 checksums over their own contents. Utilities can detect corruption and repair the primary from the backup (or vice versa) automatically. This single design change — treat the partition table itself as data worth protecting — is arguably a bigger practical win than either the partition-count or the 2TB fix.
Why GUIDs instead of a one-byte type code? MBR identifies a partition's purpose with a single byte (0x83 for Linux, 0x07 for NTFS, and so on) — only 256 possible values, shared across every operating system and vendor that has ever wanted one, which inevitably causes collisions and ambiguity. GPT instead gives every partition a 128-bit GUID (Globally Unique Identifier, per RFC 4122) for both its type and its own individual instance — enough distinct values that collisions are not a practical concern, ever.

05 — The Real Mechanism

How Chain-Loading Actually Works

The earlier lesson on the boot sector introduced chain-loading as a philosophy: each stage's only job is to load a bigger, more capable stage, then get out of the way. On a real partitioned disk, that philosophy becomes a concrete, two-hop mechanism, and it's worth walking through precisely because it directly parallels this project's own boot.asm → kernel_entry.asm handoff.

  1. BIOS loads the MBRExactly as covered already — BIOS reads sector 0, checks for 0x55AA, copies it to 0x7C00, and jumps in. This part is identical whether the disk is partitioned or not.
  2. MBR bootstrap code scans its own partition tableThe 446 bytes of bootstrap code walk the 4 embedded partition entries, looking for the one with its boot indicator byte set to 0x80 — the "active" partition. Real MBR code (and multi-boot tools like classic GRUB's stage 1) typically expects exactly one partition marked active; more than one is ambiguous, zero means nothing to boot.
  3. MBR code reads that partition's first sectorUsing the active entry's Starting LBA field, the MBR issues its own INT 0x13 disk read — the very same BIOS service from the disk services lesson — to load the Volume Boot Record (VBR), the boot sector belonging to that specific partition, into memory.
  4. Control jumps to the VBR — stage 2The VBR is a second, independent piece of boot code, now with its own fresh 446-ish bytes of budget (formats vary), typically filesystem-aware enough to locate a larger loader file sitting inside that partition's actual filesystem — GRUB's core.img, or Windows's Boot Manager, for example.
  5. Stage 2 loads stage 3 (or the kernel directly)This final stage is unconstrained by any 512-byte sector limit — it's an ordinary file living in a real filesystem, free to be large, to parse configuration, to present a boot menu, and finally to load and jump into the actual operating system kernel.

🔍 Where bob_os Sits in This Picture
This project's current boot.asm deliberately skips the entire MBR/VBR dance — it has no embedded partition table, no active-flag scan, and no filesystem awareness at all. It reads a fixed, hardcoded run of sectors straight into RAM at 0x1000 and far-jumps there. That's a completely reasonable simplification for a teaching bootloader: it collapses the MBR-scan and VBR-load steps into one direct read, going straight from "stage 1" to "kernel" with no stage 2 in between. GRUB, by contrast, is essentially a very sophisticated, filesystem-aware stage 2 (and beyond) — the exact link this diagram shows as "VBR" and "Stage 2" combined into one much larger program. Understanding the full real-world chain makes it obvious exactly which corners boot.asm is cutting, and why those corners are fine for a 512-byte teaching example but wouldn't survive contact with a disk holding five different operating systems.

✅ The Underlying Trade-off
Legacy BIOS+MBR booting needs chain-loading because BIOS itself is dumb — it can only read raw sectors, so every layer of intelligence (finding the right partition, understanding a filesystem) has to be built up gradually, stage by stage. UEFI is a far more capable environment — closer to a small operating system than classic BIOS firmware — and can read GPT tables and FAT32 filesystems on its own, so it can jump straight to loading a bootloader file without needing a hand-rolled MBR bootstrap or a filesystem-aware VBR at all. Chain-loading isn't a permanent architectural requirement of computing — it's what you do when your firmware is deliberately simple and your storage format demands more intelligence than that firmware has.
Sharpen your pencil. GPT disks can still be booted by legacy BIOS, not just UEFI — this is called "BIOS/GPT boot" or a "hybrid MBR" setup. Given everything in this lesson, what has to be true for that to work at all, since legacy BIOS has no native GPT understanding whatsoever? (Answer: the protective MBR at LBA 0 gets modified so its bootstrap code region — the same 446 bytes as any ordinary MBR — contains a small, hand-written program aware enough to read the GPT partition array directly and locate a BIOS Boot Partition, effectively making the "MBR" bootstrap code itself GPT-aware. It's chain-loading again, just with a more sophisticated first stage than the classic 4-primary-partition scan.)
07 — Quick Reference

Glossary & Key Terms

MBR
Master Boot Record — the 512-byte sector 0 combining 446 bytes of bootstrap code, a 64-byte 4-entry partition table, and the 0x55AA signature.
Partition Table Entry
A 16-byte MBR record: boot flag, legacy CHS bounds, a 1-byte type code, and 32-bit starting LBA / size-in-sectors fields.
Extended Partition / EBR
The workaround that lets one of the four primary MBR slots hold a linked list of additional logical partitions via chained Extended Boot Records.
GPT
GUID Partition Table — the modern replacement using 64-bit LBAs, a large partition entry array, and redundant primary/backup headers with checksums.
Protective MBR
A deliberately inert MBR at LBA 0 of a GPT disk (type 0xEE, whole-disk span) that stops legacy MBR-only tools from mistaking the disk for unpartitioned.
GUID
A 128-bit Globally Unique Identifier (RFC 4122) GPT uses for both partition type and individual partition identity, avoiding MBR's 1-byte type collisions.
VBR
Volume Boot Record — the boot sector belonging to an individual partition, loaded and executed by the MBR's bootstrap code as chain-loading's second hop.
Chain-Loading
The pattern of a small, trusted boot stage loading and jumping into a larger, more capable stage, repeated until a full OS kernel is running.
EFI System Partition (ESP)
A small FAT-formatted partition UEFI firmware reads directly on a GPT disk, holding the bootloader files it launches without any MBR-style chain.
