01 — Calling Firmware From Assembly

What Is INT 13h, Really?

You already know from Module 01's memory map that the first 1KB of RAM (addresses 0x0000–0x03FF) holds the Interrupt Vector Table: 256 slots, 4 bytes each, every slot a far pointer to a handler routine. INT 0x13 is nothing more mysterious than "jump through slot 0x13 of that table." BIOS, during POST, populated slot 0x13 with the address of its own disk-service handler. Your bootloader executing the single instruction int 0x13 is a software interrupt — a deliberate, self-inflicted trap that transfers control to that handler, exactly the way a real hardware interrupt would, except you triggered it on purpose.

Think of it as a tiny, ancient API. There's no dynamic linker, no shared library, no function name to call — just a convention: load specific 16-bit registers with specific meanings, execute int 0x13, and BIOS's handler reads those registers, does the disk work, and writes results back into registers (plus one special bit) before returning to the instruction right after your int 0x13.

🔑 The Universal Error Convention
Every one of these services reports success or failure the exact same way: the x86 carry flag (CF). Clear (0) means success; set (1) means something went wrong, with a numeric error code left in AH. This is precisely why boot.asm's disk-read pattern always ends the same way — int 0x13 immediately followed by jc disk_error (jump if carry). It's a two-instruction idiom you will type dozens of times across this project: call the BIOS service, then check the one bit that tells you whether to trust what just happened.

When AH=0x02 does fail, the numeric code BIOS leaves behind in AH tells you specifically what went wrong — useful for a more informative disk_error handler than "something broke":

AH Error CodeMeaning
0x00No error (shouldn't appear alongside CF=1, but defensively worth checking)
0x01Invalid function or invalid parameter — a malformed request
0x02Address mark not found — the requested sector's header wasn't located
0x04Sector not found — requested CHS coordinates don't exist on this media
0x05Reset failed
0x09Data boundary error — transfer crossed a 64KB DMA boundary (a classic real-mode gotcha)

0x80Drive timed out — no response, often a disconnected or missing drive
The 64KB DMA boundary gotcha (error 0x09). Classic INT 13h disk reads use DMA hardware that cannot transfer across a 64KB physical boundary in one operation — your destination buffer given in ES:BX must not straddle a 0x10000-aligned line. This is a real, sharp-edged constraint: request too many sectors into a buffer positioned wrong, and you'll get error 0x09 even though every register value you supplied looks perfectly reasonable. It's one of several reasons production bootloaders are careful about exactly where they place destination buffers, not just how big they are.
02 — Where CHS Actually Came From

CHS: A Language Built for Real Hardware

Cylinder/Head/Sector addressing wasn't an arbitrary numbering scheme someone invented for convenience — it described, literally and physically, how a spinning hard disk works. Picture the inside of an old mechanical drive: several rigid platters stacked on a spindle, a read/write head hovering over each platter surface, and all the heads moving together on one arm.

CHS TermPhysical Meaning
CylinderHow far the read/write arm has moved inward or outward. All the concentric tracks at that same arm position, across every platter surface, form one cylinder.
HeadWhich physical read/write head (and therefore which platter surface) is active — head 0 is the first surface, head 1 the next, and so on.
SectorWhich pie-slice segment of that particular track, since each circular track was itself divided into fixed-size arcs — the actual 512-byte chunks.

Reading a specific piece of data genuinely meant: move the arm to the right cylinder (this is the slow part — physically repositioning a mechanical arm), select the right head electronically (instant — no physical movement, just switching which head's signal you're reading), then wait for the disk's rotation to bring the right sector under the head. CHS numbers weren't an abstraction layered on top of the hardware — for early drives, they described exactly where a stepper motor needed to send an arm and exactly which electrical head to enable.

Original IBM PC BIOS INT 13h field widths. CH holds the low 8 bits of cylinder, with the top 2 bits smuggled into the top 2 bits of CL — giving 10 bits total, cylinders 0–1023. DH holds head, 8 bits, 0–255. The bottom 6 bits of CL hold sector, 1–63 (sector numbering starts at 1, not 0 — a detail that trips up almost everyone the first time). Multiply the ceilings together and you get the entire CHS-addressable universe through this interface: 1024 × 256 × 63 × 512 bytes ≈ 7.9GB. That number mattered enormously in the 1990s — it was a real, load-bearing ceiling, not a theoretical one.

Asking the Drive Instead of Hardcoding Numbers

boot.asm hardcodes ch=0, cl=2, dh=0 because the disk image this project builds is small and its layout is known ahead of time at build time — reasonable for a teaching bootloader with a fixed Makefile-generated disk.img. Production code, aimed at disks whose geometry isn't known in advance, typically calls AH=0x08 ("get current drive parameters") first, and lets BIOS report back the maximum cylinder, head, and sector values it believes the drive actually has, rather than assuming any particular shape.

mov ah, 0x08        ; Get drive parameters
mov dl, 0x80         ; Drive to query — first hard disk
int 0x13
jc disk_error
; On return:
;   CH = max cylinder (low 8 bits), CL bits 6-7 = max cylinder (high 2 bits)
;   DH = max head number
;   CL bits 0-5 = max sector number per track
;   DL = number of drives detected

This is the BIOS-level equivalent of asking "what are your limits?" before assuming any — precisely the same defensive posture the extended-read section later in this lesson recommends for checking whether AH=0x42 is even supported before relying on it.

03 — When the Geometry Stopped Being Real

CHS Became a Fiction

CHS worked fine as long as disks physically matched the numbers they reported. That stopped being true fairly quickly, for a very physical reason: outer tracks on a platter have more circumference than inner tracks, so a fixed sector count per track (which CHS assumes) wastes enormous capacity on the outer edge — you could easily pack more 512-byte sectors on an outer track's longer circumference than an inner one, but the traditional CHS interface has no way to express "this track has more sectors than that one."

Drive manufacturers solved this with zone bit recording: group tracks into zones, and give outer zones more sectors per track than inner zones, squeezing meaningfully more capacity out of the same platter. This immediately broke the assumption baked into CHS that every track has the same sector count. Manufacturers' fix was pragmatic rather than pure: keep reporting some CHS-shaped numbers to software for compatibility, but have the drive's own controller silently translate that fictional CHS address into whatever the real physical layout actually is.

This wasn't the first time disk encoding quietly changed underneath a stable-looking interface, either. Early drives used FM (frequency modulation) encoding, replaced by the denser MFM (Modified FM) scheme, later replaced again by even denser RLL (Run-Length Limited) encoding — each transition packed more bits into the same physical track without requiring software above the disk controller to know or care. CHS addressing survived every one of these encoding changes untouched, because it always operated one layer above the raw magnetic encoding. Zone bit recording was simply the first change that broke the geometric assumption (fixed sectors per track) rather than just the encoding underneath it.

💡 The Aha Moment
By the time you bought a hard drive in the mid-1990s, the "cylinders / heads / sectors" printed on its label were already a polite lie — a translated, BIOS-compatible geometry chosen to fit within CHS's addressing limits, not a description of the platters inside. Software calling INT 0x13 with CHS coordinates was, and still is on anything old enough to use it, talking to a translation layer, not to physical hardware. The drive firmware receives your fictional C/H/S numbers and maps them internally to wherever the data actually lives.

This translation layer created its own famous headaches, because two different translators — the disk controller (ATA/IDE) and the system BIOS — each had their own, differently-sized CHS fields, and software had to survive whichever one was more restrictive:

⚠️ The Infamous 504MB Barrier
Neither BIOS nor the ATA controller was individually the bottleneck — the disaster came from combining the narrowest field from each layer: BIOS's generous 256 heads met ATA's stingy 16-head hardware limit, and the combination capped every CHS-addressed disk at roughly 504MB (528,482,304 bytes) regardless of how large the physical drive actually was. Drives bigger than that, addressed purely through classic CHS, simply had the excess capacity become invisible to the operating system. This single number is a large part of why the industry was motivated to move away from CHS entirely rather than patch around it again.
04 — The Fiction Gets Retired

Enter LBA: Just Count the Sectors

Logical Block Addressing throws out cylinder/head/sector entirely and replaces it with the simplest possible scheme: treat the disk as one long, flat array of fixed-size sectors, numbered 0, 1, 2, 3, ... up to however many the disk holds. Sector 0 is the boot sector you already know from the previous lesson. There is no arm, no platter, no zone — just an index into an array, exactly like indexing into any other buffer.

Logical Block Addressing Byte offset on disk = LBA × 512 No geometry required at all — just multiply the sector number by the sector size.

This isn't just a software convenience — it matches modern hardware much better than CHS ever could. SSDs have no platters, no arms, no rotation at all; "cylinder" and "head" are meaningless concepts for flash memory. LBA never assumed a specific physical mechanism in the first place, so it keeps working correctly regardless of what's actually inside the drive.

🌀 CHS (Legacy)

Requires three coordinates that must be translated through however many layers of firmware disagree about the true geometry; hard limits baked into fixed-width register fields; meaningless for SSDs and modern zone-recorded drives; the field widths alone impose the 504MB barrier.

📏 LBA (Modern)

One flat number identifies any sector on the disk; field width is the only limit (32-bit LBA in classic INT 13h AH=42h reaches 2TB, 48-bit LBA in modern ATA reaches 128 petabytes); matches SSDs, RAID arrays, and virtual disks with no fictional geometry required at all.

Notice this is precisely the same conceptual shift the upcoming MBR/GPT lesson in this module covers at the partition-table level — GPT also abandons small fixed-width legacy fields in favor of a flat 64-bit LBA addressing scheme, for exactly the same underlying reason: CHS-shaped thinking runs out of room, and a flat linear index doesn't.

LBA Didn't Eliminate the Translation — It Moved It

It's worth being precise about what actually changed. Even a purely LBA-addressed modern SSD still has to translate that flat sector number into something physical internally — flash memory has its own complex internal mapping (wear leveling, bad block remapping, a flash translation layer) that's arguably far more involved than a spinning disk's old CHS translation ever was. What LBA actually eliminated wasn't translation itself — it was exposing a fictional physical geometry to software. The interface got simpler; the hardware behind it, if anything, got more complex. This is a pattern worth recognizing broadly: a clean abstraction doesn't necessarily mean less work happens underneath, only that the software above no longer needs to know about it.

📌 One More Ceiling Worth Knowing
Classic INT 13h AH=0x42 extended reads use a 32-bit LBA field inside the Disk Address Packet by convention on many older implementations, capping addressable space at 2TB — the exact same numeric ceiling the MBR partition table's own 32-bit LBA field hits, covered in the next lesson. The DAP format technically reserves a full 64-bit field for the starting LBA (shown in the worked example ahead), but not every BIOS populates or honors the upper 32 bits correctly, which is one more reason modern systems increasingly skip BIOS disk services altogether in favor of UEFI's own, cleaner block I/O protocols.
05 — A Real Call, Register by Register

Worked Example: AH=02h in Practice

boot.asm's disk read from the tutorial is the canonical AH=02h call. Here it is again, this time with every register explained as a field, not just a comment:

mov ah, 0x02       ; Function select: 0x02 = "read sectors" (CHS)
mov al, 16         ; Sector COUNT to read — 16 sectors = 8KB
mov ch, 0          ; Cylinder, low 8 bits — cylinder 0
mov cl, 2          ; Bits 0-5: starting sector = 2 (sector 1 is the boot sector itself)
                   ; Bits 6-7: cylinder's high 2 bits — 0 here since cylinder is 0
mov dh, 0          ; Head 0
mov dl, 0x80       ; Drive number — 0x80 = first hard disk, 0x00 = first floppy
mov bx, 0x1000     ; ES:BX = destination buffer — writes to ES:0x1000
int 0x13           ; Trap into BIOS's disk service handler
jc disk_error      ; CF set means the read failed — branch to your error path

06 — The Modern Way

AH=42h: Extended Reads, No Geometry Required

INT 13h Extensions (often abbreviated EDD, for Enhanced Disk Drive) arrived in the mid-1990s specifically to route around the CHS ceilings above. Instead of packing coordinates into CH/CL/DH, you build a small memory structure called a Disk Address Packet (DAP) and pass BIOS a pointer to it.

; Disk Address Packet, 16 bytes, built in memory before the call
dap:
    db 0x10        ; Packet size = 16 bytes
    db 0            ; Reserved, must be 0
    dw 16           ; Number of sectors to read
    dw 0x1000       ; Destination offset
    dw 0x0000       ; Destination segment
    dq 2            ; Starting LBA — a full 64-bit value, sector 2

; ...
mov ah, 0x42       ; Extended read
mov dl, 0x80        ; Drive number, same convention as AH=02h
mov si, dap         ; DS:SI points at the Disk Address Packet
int 0x13
jc disk_error       ; Same carry-flag convention as always

Two things stand out here. First, there's no cylinder, head, or sector field anywhere — just a single starting LBA, so the barriers from the previous section simply don't apply. Second, notice the last line of the DAP is a full quadword (dq, 8 bytes) — that's 64 bits of address space for the starting sector, which is why extended reads can address drives far larger than CHS ever could, all the way past the 2TB mark where even 32-bit LBA runs out.

🧭 Always Check Support First — AH=41h
Not every BIOS implements the extensions, particularly on genuinely old hardware, so well-behaved code checks before relying on AH=42h: set AH=0x41, BX=0x55AA, DL=drive number, then int 0x13. If the carry flag comes back clear and BX now holds 0xAA55 (the bytes swapped back), extensions are present and it's safe to use AH=42h/43h. This is the same kind of "ask before you assume" pattern you'll meet constantly in low-level programming — never assume a capability exists just because it's common; a bootloader that only ever needs to run under QEMU or a reasonably modern BIOS can often skip this check, but production bootloaders never do.

Sharpen your pencil. The DAP's sector-count field (dw 16 in the example above) is a 16-bit word, not the 8-bit AL that AH=02h uses. What does that difference in field width actually buy you in practice, beyond the LBA addressing change itself? (Answer: AH=02h's sector count tops out at 255 per call — AL is only 8 bits — while AH=42h's 16-bit count field can request up to 65,535 sectors, over 32MB, in a single BIOS call. Fewer calls means less per-call overhead when loading something as large as a full kernel image.)
07 — Quick Reference

Glossary & Key Terms

INT 13h
The BIOS software interrupt exposing low-level disk services (read, write, reset, get parameters) to real-mode code via registers.
CHS
Cylinder/Head/Sector — the original disk addressing scheme, describing an arm position, a platter surface, and a track segment.
LBA
Logical Block Addressing — treats a disk as one flat array of numbered sectors, with no geometry assumptions at all.
Zone Bit Recording
Storing more sectors per track on a platter's longer outer tracks than its shorter inner ones — the physical change that made fixed-geometry CHS obsolete.
Disk Address Packet (DAP)
The 16-byte memory structure passed to INT 13h AH=42h/43h, holding sector count, destination pointer, and a 64-bit starting LBA.
EDD / INT 13h Extensions
The mid-1990s BIOS extension adding LBA-based disk services (AH=41h/42h/43h) to route around CHS's addressing ceilings.
Carry Flag (CF)
The x86 status flag INT 13h (and most BIOS services) use as a universal success/failure signal after returning from a call.
504MB Barrier
The historical CHS capacity ceiling created by combining BIOS's 256-head field with ATA's 16-head hardware limit.
Sector Translation
The drive firmware's internal remapping of externally-reported (often fictional) CHS coordinates onto real physical storage locations.
