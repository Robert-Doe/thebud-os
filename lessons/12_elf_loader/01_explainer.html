Describes Itself

A running program on disk isn't a mystery blob the kernel has to guess about — it's a structured, self-describing document. Somewhere in the first few dozen bytes of every Linux, BSD, or bob_os executable is a table of contents that tells the loader exactly what architecture this is, exactly where execution should begin, and exactly where to find the instructions for turning the rest of the file into a running process. That format is ELF, and this page is about reading its opening pages.

00 — Before You Had a Format

What Would a Loader Do Without ELF?

Rewind to the earliest bob_os lessons: the kernel itself is a flat binary. linker.ld says "start at 0x1000," GRUB or the bootloader copies the whole image to that address, and execution begins at byte zero. That works fine when there's exactly one thing being loaded, built by one team, with one linker script everyone agrees on in advance.

It falls apart the moment you want a general-purpose loader — a piece of kernel code that can take any compiled program, from any compiler, targeting any architecture, and run it correctly. A flat binary carries no metadata. There's no way to ask it "what CPU are you for," "where should you start executing," or "which parts of you need write permission versus which parts are pure, shareable code." The loader would have to already know all of that in advance, which defeats the entire point of a loader.

💡 The Aha Moment
A file format for executables is really just an agreement: the compiler and linker promise to write certain facts in certain places, and the loader promises to read them from those exact places. Once both sides honor that contract, the loader never needs to know anything about the program in advance — it just reads the file's own description of itself. ELF is that contract.
01 — Naming the Thing

What ELF Actually Is

ELF stands for Executable and Linkable Format. It's not a bob_os invention, and it's not a Linux invention either — it was standardized in the early 1990s (originally by Unix System Laboratories, later formalized in the System V ABI) specifically to replace a mess of incompatible, platform-specific executable formats. Today it's the format Linux uses for programs, shared libraries, kernel modules, and core dumps; the BSDs adopted it decades ago too; and it's exactly the format bob_os's own loader — 16_elf_loader/elf_loader.c — parses to turn a file on BobFS into a running ring-3 process.

Crucially, ELF is one file format used for several different jobs. The same overall structure — a header, followed by tables describing the rest of the file — is reused for:

ET_EXECbob_os uses this
A statically-linked, ready-to-run executable with a fixed load address. What this whole page and its companions are about.
ET_DYNshared libs / PIE
A shared object (.so) or position-independent executable — same ELF shape, but built to be loaded at any address. Covered in the linking companion lesson.
ET_REL.o files
A relocatable object file — a compiler's output before the linker has glued everything together. Not directly runnable.
ET_COREcrash dumps
A snapshot of a crashed process's memory and registers, in the exact same container format, for post-mortem debugging.

All four share the identical opening move: a fixed-layout ELF header at offset zero. That's where we're headed next.

02 — The File's Business Card

The ELF Header, Field by Field

Every ELF file, no matter its purpose, opens with a header of fixed, known size — 52 bytes for ELF32 (the format bob_os targets, since its i686 cross-compiler is invoked with -m32), 64 bytes for ELF64. The loader doesn't need to guess this size or search for it; it's the very first thing at offset 0, always the same shape. That predictability is the entire trick: a loader can memcpy exactly 52 bytes into a known C struct and immediately have every field it needs.

🔑 The Most Famous Four Bytes in Systems Programming
Offset 0 always holds 0x7F 0x45 0x4C 0x46 — byte 0x7F (a non-printable "delete" byte, chosen so the file can never be confused with plain text) followed by the ASCII characters 'E' 'L' 'F'. Read as a little-endian 32-bit integer, that's 0x464C457F. bob_os's own loader checks exactly this in elf_load() before trusting a single other byte of the file — if the magic doesn't match, loading aborts with an error code and the kernel is completely unaffected.

Notice what's not in that header: no function names, no variable names, no source-level information at all. The ELF header only answers "what am I, and where do I point?" — it's a table of contents, not the book itself.

ELF64's header carries the exact same fields in the exact same order — only e_entry, e_phoff, and e_shoff widen from 4 bytes to 8, to hold 64-bit addresses, which is the entire reason the header grows from 52 to 64 bytes. bob_os never needs to worry about that variant: its cross-compiler targets i686 with -m32, so every ELF file it ever produces or loads is ELF32, full stop.

03 — One File, Two Audiences

Program Headers vs. Section Headers

Here's the split that trips people up the first time, because both tables describe "how this file is organized," and both sit near the top of the file, and both have similarly-named entries. But they exist for two completely different readers, and only one of those readers matters while the program is actually running.

📦 Program Headers — for the loader

Answer the question "how do I get this file into memory and running?" Each entry describes one contiguous chunk of the file (a segment) that needs to be mapped at a specific virtual address with specific permissions. This is the table a kernel's ELF loader reads at runtime — the only one bob_os's loader touches at all.

🔧 Section Headers — for the linker & debugger

Answer the question "how is this file organized internally, for people editing or debugging it?" Sections like .text, .data, .symtab, and .debug_info are the linker's and debugger's units of bookkeeping — used at build time and while poking at a binary with gdb or objdump, but almost entirely irrelevant to actually executing the program.
The one-line rule Program Headers describe the process. Section Headers describe the file. A running program's address space is built entirely from PT_LOAD program header entries — a fully stripped binary (no section headers at all) still runs perfectly.
Try it yourself, conceptually. This is exactly what the Unix tools readelf -l (lowercase L, "program headers") and readelf -S (capital S, "section headers") show you on any real Linux binary — two completely different tables, describing the same bytes for two completely different purposes.
04 — The Load Plan

Program Headers: The Segments

A Program Header entry describes one segment: a contiguous range of bytes in the file that the loader must place at a specific virtual address, with specific read/write/execute permissions. A typical small executable has just two or three PT_LOAD segments — commonly one for code (readable + executable, never writable, so a bug can't overwrite instructions) and one for data (readable + writable, never executable, so injected data can't be run as code).

FieldSizeMeaning
p_type4 bytesWhat kind of segment this is. PT_LOAD (value 1) means "map me into memory" — the only type bob_os's loader acts on; every other type is skipped.
p_offset4 bytesWhere this segment's bytes begin in the file.
p_vaddr4 bytesWhere this segment must be mapped in the process's virtual address space.
p_paddr4 bytesPhysical address hint. Ignored by bob_os's loader — paging decides physical placement, not the ELF file.
p_filesz4 bytesHow many bytes of this segment actually exist on disk.
p_memsz4 bytesHow many bytes this segment occupies in memory — always ≥ p_filesz. The gap is zero-filled BSS space.
p_flags4 bytesPermission bits: PF_R=4 (read), PF_W=2 (write), PF_X=1 (execute), OR'd together.
p_align4 bytesRequired alignment (typically the page size, 4096) — a hint, not a mandate the loader must obey byte-for-byte.

Eight fields, 4 bytes each — exactly 32 bytes, which is why e_phentsize in the header above always reads 32 for ELF32. That the two file-vs-memory-size fields can differ is the single most load-bearing detail in the whole format: it's how a program can declare "I need 4KB of zeroed global variables" without the compiler having to actually write 4KB of zero bytes to disk. We'll watch this exact mechanism run in the next lesson.

🧠 Why Permissions Live Here, Not in the File System
A regular file on disk has one set of permissions (readable, writable, by whom). But a single ELF file needs different in-memory permissions for different parts of itself simultaneously — code pages that must never be writable, data pages that must never be executable. That granularity can't come from the filesystem; it has to be declared inside the file, per-segment, which is exactly what p_flags is for.

Validating a header before trusting it

Before any of this matters, the loader has to actually confirm it's holding a real, well-formed header — the same discipline bob_os's elf_load() applies in exactly this order:

  • Cast the raw bytesTreat the start of the file buffer as an Elf32_Ehdr * — no parsing yet, just a pointer reinterpretation.
  • Check the four magic bytesReject immediately if e_ident[0..3] isn't exactly 0x7F 'E' 'L' 'F' — nothing past this point can be trusted otherwise.
  • Check class, type, and machineConfirm e_ident[4] == 1 (32-bit), e_type == ET_EXEC, and e_machine == EM_386 — three separate ways a well-formed-but-wrong-platform file gets rejected.
  • Confirm e_phnum > 0A file with zero program headers has nothing loadable in it at all — reject before the walking loop even begins.

    Section Headers: Present, But Irrelevant Here

    Section headers describe a much finer-grained breakdown of the file: .text (code), .rodata (read-only constants, string literals), .data (initialized globals), .bss (uninitialized globals — takes up zero bytes on disk despite occupying real space at runtime), .symtab (symbol names for debugging), .strtab (the strings those symbols are named with), and often dozens more. Each has its own Section Header entry recording its name, type, file offset, and size.

    This is precisely the information a linker needs when combining several .o files into one executable (which sections merge, which symbols resolve against which), and precisely what a debugger needs to answer "what function is at this address" or "what's this variable's name." Neither of those jobs happens at process-launch time.

    ⚠️ bob_os Proves the Point
    Look back at the dossier above: bob_os's loader reads e_shoff out of the header — and then never uses it for anything. No code in elf_loader.c ever walks a section header. A binary can be fully stripped (all section headers and symbol tables deleted, a common step before shipping production software to shrink file size and hide internals) and still load and run identically, because everything the loader actually needs — the entry point and the PT_LOAD segments — lives in the ELF header and Program Headers, which stripping never touches.

    So the honest mental model is: an executable file, at the moment it's launched, is really just its Program Headers plus an entry point. Everything else — section headers, symbol tables, debug info — is optional cargo carried along for humans and tools, not for the CPU.

    06 — Zooming Out

    Every OS Has One of These

    ELF isn't a uniquely clever idea — it's one answer to a question every operating system has to answer somehow: "given a file, how do I know what it is and how to run it?" Windows and macOS solve the exact same problem with their own formats, and every one of them opens the same way ELF does — a handful of unmistakable identifying bytes at offset 0, followed by a structured description of what to load and where.

    PlatformFormatMagic Bytes (offset 0)Load-Plan Table
    Linux / BSD / bob_osELF0x7F 'E' 'L' 'F'Program Headers (segments)
    WindowsPE (Portable Executable)'M' 'Z' (then a PE header further in)Section table with load characteristics baked in
    macOS / iOSMach-O0xFEEDFACE / 0xFEEDFACFLoad Commands, including LC_SEGMENT

    Notice the pattern repeats almost exactly: an unmistakable byte signature so the loader can bail out instantly on garbage input, then a structured, walkable table describing memory regions to map and permissions to apply. Even the terminology rhymes — Mach-O's LC_SEGMENT load commands are doing essentially the same job as ELF's PT_LOAD program headers. Once you understand ELF's shape deeply, recognizing the same shape in a different OS's executable format is mostly a vocabulary exercise, not a new concept.

    📌 Why 'MZ'?
    Windows' PE magic bytes, 'M' 'Z', are the initials of Mark Zbikowski, one of the original MS-DOS engineers — a signature that has survived, for backward-compatibility reasons, in every Windows executable format since the 1980s. ELF's magic byte 0x7F was chosen more pragmatically: it's the ASCII "delete" control character, guaranteeing an ELF file can never be mistaken for readable text by a naive tool that only checks the first byte.

    08 — Quick Reference

    Glossary & Key Terms

    ELF
    Executable and Linkable Format — the self-describing container format used for executables, shared libraries, object files, and core dumps on Linux, the BSDs, and bob_os.
    Magic Number
    The fixed byte sequence 0x7F 'E' 'L' 'F' at offset 0, used to confirm a file is really an ELF file before trusting any other field.
    ELF Header (Ehdr)
    The fixed-size struct at offset 0 — 52 bytes for ELF32 — holding architecture, entry point, and pointers to the Program and Section Header tables.
    Program Header (Phdr)
    One 32-byte entry describing a segment: where it lives in the file, where it must be mapped in memory, its size, and its permissions.
    Segment
    A contiguous chunk of the file that a Program Header describes for loading — the unit the runtime loader actually cares about.
    Section
    A finer-grained chunk (.text, .data, .symtab...) described by a Section Header, used by linkers and debuggers, irrelevant at launch time.
    e_entry
    The ELF header field holding the virtual address execution should begin at once loading is complete.
    ET_EXEC
    An ELF e_type value meaning "statically-linked executable with a fixed load address" — the only type bob_os's loader accepts.
    Stripped Binary
    An ELF file with its Section Headers and symbol tables removed, to save space or hide internals — still fully runnable, since only Program Headers matter at launch.
    EI_CLASS / EI_DATA
    Bytes 4 and 5 of e_ident, declaring 32- vs 64-bit layout and byte order (endianness) for every other field in the header.
    PE (Portable Executable)
    Windows' equivalent executable format — opens with the 'MZ' magic bytes and a section table describing how to load the file, the same job ELF's Program Headers do.
    Mach-O
    macOS and iOS's executable format — identified by magic number 0xFEEDFACE/0xFEEDFACF, using Load Commands (including LC_SEGMENT) in place of ELF's Program Headers.
