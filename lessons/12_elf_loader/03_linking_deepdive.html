Every program calls functions it didn't write — printf, malloc, string routines, math. Somewhere between "source code with a call to a function that doesn't exist yet in this file" and "a running process," that call has to be connected to real, addressable code. Linking is that connection. The only real question is when it happens — at build time, permanently, or at load time, every single run.

00 — The Problem Before the Choice

Why Linking Has to Happen at All

A compiler works one source file at a time. When it hits printf("hi"), it has no idea where printf's actual machine code lives — maybe it's in another file in this same project, maybe it's in a library installed system-wide. So the compiler does the only honest thing it can: it emits a call instruction to a placeholder, and leaves a note in the object file's symbol table saying, in effect, "there's an unresolved reference to a symbol named printf right here — someone else needs to fill in the real address."

That "someone else" is the linker. Its entire job is finding every unresolved symbol reference across every object file being combined, locating where each one is actually defined, and patching the real address into place. The previous two lessons assumed this had already happened — a bob_os ELF executable arrives at the loader fully linked, every internal call already pointing somewhere real. This lesson is about the one decision that changes everything about how that patching happens: static or dynamic.

💡 The Aha Moment
Static and dynamic linking aren't two different technologies — they're the same problem (connect a call site to real code) solved at two different times. Static linking finishes the job once, at build time, and never revisits it. Dynamic linking deliberately leaves part of the job unfinished until the moment the program actually runs.
01 — Finish the Job at Build Time

Static Linking: Copy-Paste, Permanently

With static linking, the linker doesn't just patch an address — it copies the actual machine code of every function your program uses (and, transitively, everything those functions call) directly into your final executable. If your program calls three functions out of libc, the linker pulls the compiled object code for exactly those three functions — and whatever they depend on — out of the static library archive (a .a file, itself just a bundle of .o object files) and welds it into your binary.

The result is a single, self-contained file. Copy it to another machine with the exact same architecture and it runs — no other files required, no version of libc that needs to already be installed, nothing to go looking for at runtime. This is precisely bob_os's current model: elf_type == ET_EXEC, fully resolved, every address already final by the time the file lands on BobFS.

Static linking's promise Whatever this file needs, this file already contains. No lookup, no missing dependency, no runtime surprise — at the cost of every program carrying its own private copy of everything.
⚠️ The Cost: Duplication, Everywhere
Picture 50 different programs on one system, each statically linked against libc. Every single one of those 50 executables now contains its own private copy of printf, malloc, strcpy, and everything else it pulled in. That's the same machine code, byte-for-byte identical, sitting in 50 separate places on disk — and, worse, loaded into 50 separate sets of physical memory pages when all 50 happen to run at once, even though every one of those pages holds exactly the same bytes.

Static linking isn't a mistake — it's a deliberate trade. It buys predictability (the exact code you tested is the exact code that ships) and independence (no risk of a system library update silently changing your program's behavior). The bill for that comes due in disk space and, more importantly, redundant physical memory once many such programs run side by side.

OS Kernelsalmost always static
A kernel can't dynamically link against its own not-yet-running userland — it has to be one self-contained image, exactly like bob_os's own flat kernel binary.
Embedded / Containersoften static
A minimal container image or firmware blob frequently statically links on purpose — no guarantee the target environment has any particular library installed at all.
Desktop / Server Appsalmost always dynamic
Hundreds of installed programs sharing libc, a GUI toolkit, and OpenSSL — exactly the scenario where dynamic linking's memory savings compound across an entire running system.
02 — Leave the Job for Load Time

Dynamic Linking: Borrow, Every Time You Run

Dynamic linking takes the opposite bet. Instead of copying libc's code into your executable, the linker just records, inside your ELF file, a note that says: "I need a library named libc.so.6, and specifically the symbols printf, malloc, and so on, out of it." Your executable ships without that code at all — it's smaller, and it stays smaller no matter how much of libc it ends up calling.

The missing piece gets filled in at load time, by a separate program called the dynamic linker (on Linux, this is ld.so / ld-linux.so). It reads your executable's list of needed libraries, locates each .so file on disk, maps it into your process's address space, and patches your program's unresolved call sites to point at the real, now-mapped addresses — every time the program starts.

✅ The Payoff: One Physical Copy, Many Processes
Here's the part that actually saves memory, not just disk space: when the dynamic linker maps libc.so into a process, it isn't decompressing or copying that library's code — it's mapping the same physical page frames that every other process using libc on the system is already mapping. Fifty running programs, all dynamically linked against libc, share one physical copy of libc's code pages in RAM. This is the exact same shared-memory trick you've already seen the kernel offer deliberately to cooperating processes — except here, the kernel and the dynamic linker set it up on your behalf, automatically, for every dynamically-linked program.

The trade is symmetric to static linking's: you give up self-containment (the library has to actually exist on the target machine, at a compatible version) in exchange for smaller files on disk and, at scale, dramatically less redundant physical memory across a whole system's worth of running programs.

03 — Side by Side

Static vs. Dynamic, Head to Head

📦 Static Linking

Library code copied in at build time. Self-contained — no runtime dependency lookups, nothing else has to be installed. Larger files, duplicated code across every program that links the same library, duplicated physical memory when several run at once. What bob_os's ET_EXEC-only loader does today.

🔗 Dynamic Linking

Library code mapped in at load time by a separate dynamic linker program. 04 — The Mechanism Underneath Both

Relocations: Why Addresses Need Patching at All

Step back to when a function is compiled, long before any linking happens. The compiler has no idea what the final memory address of printf will be — it doesn't even know for certain what address its own function will end up at, especially for code destined for a shared library that might get mapped at a different address in every process that loads it. So when it generates a call or a reference to some other symbol, it can't bake in a real address. It leaves a placeholder, plus an entry in a relocation table that says, precisely: "at this byte offset, once you know the real address of symbol X, write it in, using this patching formula."

Relocation Table EntryMeaning
r_offsetWhere in the final image the patch needs to be written — a byte offset.
r_symbolWhich symbol's final address this patch depends on, e.g. printf.
r_typeHow to combine the symbol's address into the placeholder — write it whole, add an offset, compute a relative jump distance, and so on.

Static linking processes every relocation once, at build time — by the time the executable is written to disk, every placeholder has already been replaced with a real, final address, because the linker knows exactly where every piece of code will live (bob_os's linker script fixes user code at 0x400000, permanently). Dynamic linking can't do that for the parts that live in a shared library, because the same libc.so might be mapped at a different address in every process that uses it (especially under ASLR — address space layout randomization). So those relocations stay unresolved in the file, and get processed instead by the dynamic linker, once per process, at load time.

🧠 The One-Sentence Version
A relocation is a receipt the compiler leaves behind, saying "I couldn't finish this address — here's exactly how and where to finish it once you know the real number." Static linking cashes every receipt at build time. Dynamic linking cashes the ones pointing at shared libraries at load time instead, trading a small amount of startup work for the ability to share physical code pages across every process using that library.

On bob_os's own i686 target, two relocation types cover the overwhelming majority of real cases, and seeing them named makes the abstract "patching formula" concrete:

r_type (x86, ELF32)Patching FormulaUsed For
R_386_32write32(target) = S + AAn absolute address reference — "put the real address of symbol S right here," e.g. a pointer stored in a data segment.
R_386_PC32write32(target) = S + A - PA PC-relative reference — "compute the distance from here to symbol S," the form most call/jump instructions actually use.

(S = the symbol's final resolved address, A = an addend baked into the placeholder, P = the address of the placeholder itself.) A statically-linked bob_os user program has already had every one of these formulas evaluated once, by the linker, before the file ever reaches BobFS — which is exactly why elf_load() never needs to open a relocation table at all.

05 — The Twist

The Dynamic Linker Is Just Another Program the Kernel Loads

Here's the detail that ties this whole lesson back to the previous one. When the kernel loads a dynamically-linked ELF executable, it doesn't hand control straight to that program's e_entry. It first checks the Program Header table for a special entry type: PT_INTERP. If present, that segment doesn't describe a loadable chunk of the program at all — it contains a plain string, the path to the program's requested interpreter: on Linux, almost always something like /lib64/ld-linux-x86-64.so.2.

  • 1. The kernel spots PT_INTERPIt reads the interpreter path straight out of that segment — no parsing beyond "here's a null-terminated string."
  • 2. The kernel loads the dynamic linker itself, as an ELF fileld.so is, structurally, just another ELF executable — same magic bytes, same Program Header table, same PT_LOAD segments, loaded through the exact same mechanism covered in the previous lesson. The kernel treats it no differently than any other program.
  • 3. The kernel jumps to ld.so's entry point — not the real program'sThe very first user-mode code that runs isn't your program at all. It's the dynamic linker, now running at ring 3, with your actual program's ELF information handed to it on the stack.
  • 4. ld.so does the rest of the workIt reads your program's list of needed shared libraries, maps each one in, processes every outstanding relocation against their real, now-known addresses — and only then jumps to your program's real e_entry, having finished the job the static linker would have finished at build time.
    • 🔑 So "Loading a Program" Can Mean Loading Two Programs
    For a dynamically-linked executable, the kernel's ELF loader runs twice before your code ever executes a single instruction: once to load ld.so, and once — performed by ld.so itself, in user mode, using its own internal loading logic rather than a syscall — to map in every shared library your program actually needs. The kernel only ever directly launches one thing: either your program (no PT_INTERP), or the dynamic linker (with one).
    06 — Where bob_os Stands Today

    bob_os's Loader Is Deliberately Static-Only

There's no branch that looks for PT_INTERP, no code that maps a second ELF file, no relocation-processing step at all. Every user program bob_os runs today has to be a fully statically-linked, fixed-address executable — precisely the simplest point on the spectrum this lesson describes.

    07 — One More Trick, Since You Asked

    Lazy Binding: Deferring Even the Load-Time Work

    There's a refinement production dynamic linkers add on top of everything above, because resolving every symbol a program might ever call, at startup, is wasteful — a large program might link against a library with hundreds of functions and only actually call a dozen of them in any given run. Real dynamic linkers exploit this with lazy binding: instead of resolving a symbol's address at load time, defer it until the very first time that specific function is actually called.

    The mechanism is a small indirection layer: the Procedure Linkage Table (PLT) and Global Offset Table (GOT). Every call to an external function doesn't jump directly to that function — it jumps to a tiny stub in the PLT, which reads a pointer out of the GOT and jumps through that. The first time through, the GOT entry doesn't point at the real function yet — it points back into the dynamic linker itself, which resolves the symbol right then, patches the real address into the GOT, and only then jumps to the real function. Every subsequent call reads the now-correct GOT entry and jumps straight there, at full speed, with no linker involvement at all.

  • First call to printf()Jumps to the PLT stub for printf, which loads the GOT entry — still pointing at the resolver.
  • Resolver runs, onceThe dynamic linker looks up printf's real address in libc's mapped pages, and overwrites the GOT entry with it.
  • Every later call to printf()Jumps to the same PLT stub, which now loads a GOT entry pointing directly at real code — no resolver involvement, just one extra indirect jump versus a fully static call.
    • 📌 Why This Matters Beyond Startup Speed
    Lazy binding is also why LD_BIND_NOW (or a binary marked with the -z now linker flag, common under modern hardening) is a meaningful security-vs-performance knob on real systems: forcing every relocation to resolve immediately at load time closes a small window of mutable, resolver-writable GOT state that certain exploit techniques (GOT overwrite attacks) rely on, at the cost of slower startup for programs that call into large libraries. Nothing to implement in bob_os today — but exactly the kind of trade-off this lesson's static/dynamic split scales up into.

    09 — Quick Reference

    Glossary & Key Terms

    Linker
    The tool that resolves references between object files and libraries into real addresses, producing a final executable or shared object.
    Static Linking
    Copying needed library code directly into the executable at build time — self-contained, but duplicated across every program that does it.
    Dynamic Linking
    Recording a dependency on a shared library instead of copying its code; a dynamic linker resolves and maps it in at load time, shared across processes.
    Shared Object (.so)
    A dynamically-linked library file, ELF type ET_DYN, that can be mapped into many processes' address spaces at once, sharing physical pages.
    Relocation
    An instruction left by the compiler/linker describing how to patch a placeholder address once the real, final address of a symbol is known.
    PT_INTERP
    A Program Header entry, present only in dynamically-linked executables, naming the path to the dynamic linker the kernel should load and run first.
    Dynamic Linker (ld.so)
    A user-mode program, itself loaded via the ordinary ELF-loading path, responsible for mapping in shared libraries and finishing relocations at launch time.
    ET_EXEC vs ET_DYN
    ELF header e_type values distinguishing a fixed-address static executable (ET_EXEC, bob_os's only supported type) from a relocatable shared object or PIE (ET_DYN).
    ASLR
    Address Space Layout Randomization — loading libraries (and often the executable itself) at a randomized address each run, a security measure that only dynamic-style, relocation-tolerant loading can support cleanly.
    PLT (Procedure Linkage Table)
    A small per-function stub table that indirects external calls through the GOT, enabling lazy binding — resolving each symbol only on its first call.
    GOT (Global Offset Table)
    A table of patchable pointers, one per external symbol, that PLT stubs jump through — initially pointing at the resolver, later patched to the real address.
    Lazy Binding
    Deferring symbol resolution until a function's first actual call, rather than resolving every dependency eagerly at load time — the PLT/GOT mechanism's purpose.
