00 — Where We Left Off

You Have the Blueprint. Now Build the House.

The last lesson established that an ELF file is self-describing: a fixed 52-byte header points at a table of Program Header entries, and each entry is a segment — a promise of the shape "take these bytes from the file, put them at this virtual address, with these permissions." That's a blueprint. A blueprint sitting in a file changes nothing about the machine. Something has to actually read it and act on it.

That something is the loader — in bob_os, the function elf_load() in 16_elf_loader/elf_loader.c, called from the SYS_EXEC syscall handler. This lesson walks through exactly what it does, in the exact order it does it, ending with the single instruction that hands the CPU over to code that, a moment ago, was just bytes sitting on a disk.

01 — Step One

Read the Header, Find the Program Header Table

Loading begins the same way parsing did: read the file (in bob_os, a whole-file fs_read() from BobFS into a kernel buffer, file_buf), check the magic bytes, and confirm e_type == ET_EXEC, e_machine == EM_386, and e_phnum != 0. Reject anything that fails those checks before touching a single other byte — a malformed or hostile file gets an error code, not a crash.

Once the header is trusted, three fields matter for everything that follows: e_phoff (where the Program Header table starts in the file), e_phentsize (how many bytes wide one entry is — always 32 for ELF32), and e_phnum (how many entries exist). Together they let the loader compute the address of any Program Header entry without parsing anything sequentially:

Address of Program Header entry i phdr[i] = file_buf + e_phoff + (i × e_phentsize) Straight pointer arithmetic — exactly the cast bob_os's elf_load() performs inside its loop.
🔑 Why a Fresh Address Space First
Before touching any segment, bob_os's loader calls paging_new_address_space(), producing a fresh page directory (a new CR3 value) with just the kernel's own 0–4MB identity map copied in, marked supervisor-only. Every subsequent step maps pages into this new address space — never into the currently-running kernel's own mappings — so a half-loaded or failed exec can never corrupt the process that called it.
02 — Step Two

Walk Each Entry, Skip What Isn't PT_LOAD

With the table located, the loader loops from i = 0 to e_phnum - 1, reading one Program Header at a time. Real ELF files can contain program header entries the loader doesn't care about at all — PT_NOTE (vendor metadata), PT_DYNAMIC (dynamic-linking info, covered in the next lesson), PT_GNU_STACK (a permissions hint), and others. bob_os's loader has exactly one line of policy for all of them:

if (phdr->p_type != PT_LOAD) continue;
if (phdr->p_memsz == 0)      continue;

Anything that isn't PT_LOAD — value 1 — is silently skipped. Anything PT_LOAD with zero bytes of memory footprint is skipped too (a degenerate entry with nothing to place). Everything else triggers the full map-copy-zero sequence covered in the next three sections, once per segment.

A typical user program has exactly two PT_LOAD entries. One for code and read-only data (readable + executable), one for writable globals (readable + writable). Bigger, more sophisticated executables can have more — separate segments for thread-local storage, relocation tables, or GNU_RELRO hardening — but the loop above handles any number identically, because it never assumes how many there are.
03 — Step Three

Round to Pages, Then Map Real Memory

Here's a detail that's easy to miss: p_vaddr is rarely page-aligned, and neither is p_vaddr + p_memsz. But the MMU only maps memory in whole 4KB pages — there's no such hardware primitive as "map exactly these 1,847 bytes." So before allocating anything, the loader rounds the segment's boundaries outward to the nearest page:

Page-aligning a segment's virtual range map_start = p_vaddr & ~0xFFF    map_end = (p_vaddr + p_memsz + 0xFFF) & ~0xFFF PAGE_ALIGN_DOWN and PAGE_ALIGN_UP in bob_os/16_elf_loader/elf_loader.c — round the start down, the end up, never the reverse.

Then, for every 4KB page between map_start and map_end, the loader (via install_user_page()) does three things: allocate a fresh physical frame from the physical memory manager, zero that frame completely (so no stale kernel or previous-process data ever leaks into a new process — a real security property, not just tidiness), and install it into the new page directory with PAGE_PRESENT | PAGE_WRITABLE | PAGE_USER so ring-3 code is actually allowed to touch it.

🧠 Why Round the Start Down But Not Trim It
If p_vaddr is, say, 0x400034 (not page-aligned), rounding down to 0x400000 means the loader maps a whole page that includes 52 bytes before where this segment's data actually starts. That's deliberate — those leading bytes get zero-filled and simply go unused; the alternative (a partial-page mapping) doesn't exist in hardware. In practice, linkers usually page-align p_vaddr themselves specifically to avoid wasting a shared page between two segments with different permissions.
04 — Step Four

Copy the Bytes In, Zero What's Left

Memory is mapped now, but every one of those freshly-zeroed pages is still empty. The loader copies exactly p_filesz bytes from the file (starting at p_offset) to the segment's virtual address (starting at p_vaddr) — walking page by page, computing each destination's physical address by hand-walking the new page directory, since the kernel's identity-mapped view and the new process's pages live at the same physical addresses during this bootstrap step.

Then comes the detail that makes .bss — every uninitialized global variable in a C program — work at all:

The rule that makes uninitialized globals free (on disk) if p_memsz > p_filesz: zero the bytes from (p_vaddr + p_filesz) to (p_vaddr + p_memsz) A segment can claim more memory than it ships bytes for — the difference is always assumed to be zero.
✅ The Payoff: Why Compilers Never Write Zeros to Disk
Imagine a C program with static char big_buffer[1000000]; and no other globals. The compiler doesn't emit a million zero bytes into the executable — that would bloat every binary with uninitialized-variable-shaped data nobody needs to read from disk. Instead, the linker puts big_buffer in a segment where p_memsz is a million bytes larger than p_filesz. The loader's zero-fill step is what actually materializes that space at load time, out of freshly-allocated (and already-zeroed, from the previous step) physical pages. The file stays small; the running process still sees exactly the memory layout the compiler promised.

Put differently: p_filesz is "how much of this segment is worth shipping," and p_memsz is "how much of this segment the program actually needs to exist." The gap between them is pure, disk-free zero-fill — the loader's job, not the file's.

05 — Step Five

Build a Stack Out of Nothing

Every one of the segments loaded so far came from the file. The stack does not — no Program Header describes it, because a process's initial stack isn't part of the executable's content, it's part of the environment the loader hands the process before it takes its first step. The loader has to allocate and map it itself, entirely separately from the PT_LOAD loop.

bob_os keeps this deliberately simple: syscall.c's do_exec() defines EXEC_USER_STACK_TOP at 0x800000 (8MB) — comfortably above the 4MB region where PT_LOAD segments land, so a growing stack can never collide with program code or data. It allocates one physical page, maps it user-accessible at EXEC_USER_STACK_TOP - 0x1000, and that's the entire initial stack: 4KB, growing downward, exactly as x86's push/call instructions expect.

Real operating systems do more here. A production loader (Linux included) also pushes argc, argv, envp, and an "auxiliary vector" of key/value pairs (page size, entry point, hardware capability flags…) onto this initial stack, in a precise layout the C runtime's startup code (_start → __libc_start_main) expects to unpack before ever calling your main(). bob_os's single fixed page is the minimal version of the same idea — a real, present, correctly-permissioned stack, just without the argument-passing convention layered on top yet.
06 — Step Six

Jump to e_entry — Crossing Into Ring 3

Every byte is in place. Every page is mapped and permissioned. There's a stack. What's still missing is the one thing that turns "a fully-formed process sitting in memory" into "a running process": the CPU has to actually start executing at e_entry, and it has to do so at ring 3 — user privilege, not the ring 0 the kernel itself runs at.

This should feel familiar from earlier in the series: crossing privilege levels is exactly the trap-frame machinery a syscall uses, just run in reverse. A syscall trap saves ring-3 state and moves into ring 0. Launching a process for the first time fakes up that same kind of frame from scratch and uses iret to move out to ring 3 — nothing in the CPU distinguishes "returning from a real interrupt" from "returning from a frame the kernel constructed by hand."

⚠️ The Instruction That Does It: iret
x86's iret ("interrupt return") pops a fixed sequence off the current stack — eip, cs, eflags, and (only when the target privilege level differs from the current one) esp and ss — and loads all of them atomically. There's no separate "switch to ring 3" instruction; the privilege change is a side effect of the selector value popped into cs. Load a code selector whose bottom two bits (its Requested Privilege Level) are 3, and the CPU is now executing at ring 3 the instant iret completes.

bob_os builds exactly this frame by hand in do_exec(), pushing values onto the kernel stack from high to low so that when the interrupt-return path pops them off, they land in the right registers:

*--sp = GDT_SEL_USER_DATA;   /* ss     — 0x23, ring-3 data selector */
*--sp = EXEC_USER_STACK_TOP; /* esp    — the stack page from step 5 */
*--sp = INITIAL_EFLAGS;      /* eflags — 0x202 (interrupts enabled)  */
*--sp = GDT_SEL_USER_CODE;   /* cs     — 0x1B, ring-3 code selector */
*--sp = entry;               /* eip    — e_entry from the ELF header */
/* ... zeroed general-purpose registers, then ds/es/fs/gs = 0x23 ... */

Notice GDT_SEL_USER_CODE is 0x1B and GDT_SEL_USER_DATA is 0x23 — both selectors have their low two bits set to 11 (binary), meaning RPL 3. Compare that to the kernel's own selectors, 0x08 and 0x10, whose low bits are 00 — RPL 0. The only difference between a ring-0 return frame and this ring-3 one is which selectors get loaded. Same mechanism the whole series has been building toward since the very first system call.

08 — What Could Go Wrong

When Loading Fails Partway Through

Everything above described the happy path. Real loaders spend a surprising fraction of their code handling the moment something goes wrong mid-sequence — a corrupt file, or, just as commonly, the system simply running out of physical memory in the middle of mapping a segment. bob_os's elf_load() is honest about where it can fail, and returns a distinct negative code for each case rather than one generic "error":

Return ValueMeaningWhere It's Checked
-1fs_read() failed — the named file doesn't exist on BobFS.do_exec() maps this to SYSCALL_ENOENT
-2Magic bytes wrong, wrong class, wrong e_type/e_machine, or zero program headers.do_exec() maps this to SYSCALL_ENOEXEC
-3Out of physical memory — either paging_new_address_space() or a page allocation inside install_user_page() returned nothing.do_exec() maps this to SYSCALL_ENOMEM
0Success — *out_entry and *out_cr3 are now valid.do_exec() proceeds to build the ring-3 frame

The interesting failure is -3, because unlike the other two, it can happen after real work has already been done — perhaps three of a program's four pages are already allocated and mapped into the brand-new address space when the fourth pmm_alloc_page() call comes back empty. At that point the loader simply returns -3 immediately, leaving those three already-allocated pages mapped into a fresh cr3 value that do_exec() is about to discard.

⚠️ A Real, Honest Limitation
Notice what bob_os's loader does not do on the -3 path: it never walks back and frees the pages it already allocated for this failed load attempt. Those physical frames are simply leaked — permanently unavailable until the machine reboots. A production-grade loader would track every allocation made during the attempt and roll them all back before returning an error. bob_os's version favors a simpler, more readable code path over that bookkeeping; it's a legitimate simplification for a teaching kernel, not something you'd want in anything meant to run for weeks under memory pressure.

This is also why the fresh-address-space design from Step One matters even when things go wrong: because every allocation during a failed load lands in the new, not-yet-switched-to address space, a failed exec() can never corrupt the process that called it. The caller's old code, data, and stack are all still exactly where they were — process_set_cr3() and paging_switch() are only reached on the success path, after every segment has already loaded cleanly.

09 — Quick Reference

Glossary & Key Terms

Loader
The kernel code that turns an ELF file's Program Headers into an actual mapped, running process — bob_os's elf_load() plus do_exec().
Page Alignment
Rounding a segment's virtual start down and its end up to the nearest 4KB boundary, since the MMU can only map whole pages.
BSS
The zero-filled region of a data segment where p_memsz exceeds p_filesz — uninitialized globals that cost no bytes on disk.
PAGE_USER
A page-table flag marking a page accessible from ring 3, without which user code would fault trying to touch its own memory.
Initial Stack
A stack page mapped by the loader itself (not described by any Program Header) before a process runs its first instruction.
iret
The x86 instruction that atomically restores eip/cs/eflags(/esp/ss) — the mechanism that both returns from real interrupts and launches a brand-new process at ring 3.
RPL (Requested Privilege Level)
The low two bits of a segment selector; loading a selector with RPL=3 into cs is what actually drops the CPU to user mode.
Entry Point
The virtual address (e_entry) execution begins at — the destination of the final iret in the load sequence.
ENOMEM / ENOEXEC / ENOENT
Error codes do_exec() returns to a failed SYS_EXEC caller, corresponding to bob_os's loader return values -3, -2, and -1 respectively.
Leaked Frame
A physical page allocated during a load attempt that later fails, never freed because the loader's error path doesn't roll back prior allocations — a real, acknowledged simplification in bob_os.
