Mark-and-Sweep,
From Scratch

Every managed language eventually has to answer one question honestly: when is an object actually garbage? Not "when does the programmer stop caring" — computers can't read minds. The answer engineers landed on decades ago is a purely mechanical one, called reachability, and the algorithm that acts on it is the oldest, simplest tracing collector there is: mark-and-sweep. Before you can understand V8's generational heap, Python's refcounting, or any other GC scheme, you need this one, cold, from first principles.

00 — Setting the Stage

Why Anyone Needed an Algorithm At All

In a language like C, you allocate memory with malloc() and it is your job, forever, to call free() on it exactly once — not zero times (a memory leak), not twice (a double-free, usually a crash or worse), and never while some other part of the program still holds a pointer to it (a use-after-free, one of the most exploited bug classes in software history — you've already seen this exact failure mode up close in the B09 tutorial in the browser module). All three of these bugs share a root cause: the programmer, not the machine, is tracking whether an object is still needed, and programmers get it wrong constantly, even careful ones, in large codebases with many owners of the same data.

Garbage collection is the industry's answer to that whole problem category: instead of trusting a human to know when an object is done being used, have the runtime itself figure it out, automatically, using a rule precise enough to run as code. That rule is what this lesson is actually about. The mechanism that implements the rule — mark-and-sweep — is almost secondary. Get the rule right first, and the algorithm becomes obvious.

📦 What This Lesson Deliberately Skips
This is the general, engine-agnostic theory — the stuff that's true whether you're looking at a 1959 Lisp interpreter or a browser shipping today. It is not about V8 specifically. If you want V8's actual generational Scavenger + mark-sweep-compact heap, that's covered in the sibling lesson 02_browser_xray/03_v8_deepdive.html. 01 — The Precise Definition

What "Garbage" Actually Means

Here's a tempting but wrong definition: "an object is garbage once the programmer is done using it." Tempting, because that's what we mean colloquially. Wrong, because "done using it" is a fact about the programmer's intent, and intent isn't a bit stored anywhere in memory the runtime can check. The runtime needs a definition it can actually compute — something structural, mechanical, checkable by walking pointers.

The one rule this entire algorithm is built on An object is alive if and only if it is reachable — there exists some chain of references leading to it, starting from a fixed set of roots. Anything not reachable, by definition, is garbage. Full stop. No exceptions, no intent required.

Notice what this buys you: reachability is a graph question. Objects are nodes. References (pointers, in whatever form your language uses — object fields, array slots, variables) are directed edges. "Is this object alive?" becomes "is there a path from any root to this node?" — a question you can answer with nothing fancier than a graph traversal, which a computer is extremely good at.

And because the definition is purely structural, it cuts both ways in ways that surprise people the first time they see them:

⚠️ Unreachable Is Garbage, Even If You "Meant" to Keep It

If every path to an object has been severed — the last variable pointing to it went out of scope, the last field referencing it got overwritten — the object is garbage the instant that happens, whether or not you intended it, whether or not you're about to regret it. The collector doesn't ask why. It only asks: can I still reach this from a root? If no, it's gone at the next collection.

⚠️ Reachable Is NOT Garbage, Even If You're "Done" With It

This is the sneakier one. If you forget to remove an entry from a global cache, a static list, or an event-listener registry, that object stays reachable — some root-rooted path still leads to it — even though you, the programmer, consider it finished and would call it garbage in plain English. The collector will faithfully keep it alive forever. This is precisely how "memory leaks" still happen in garbage-collected languages: not a GC bug, but a reachability truth the programmer didn't intend. 
Pseudocode — the "reachable but logically dead" trapconst sessionCache = {};    // a global — always reachable, forever, by definition

function handleLogin(userId, sessionData) {
  sessionCache[userId] = sessionData;   // sessionData is now reachable via the global
}

function handleLogout(userId) {
  // BUG: forgot to do `delete sessionCache[userId]` here
  redirectToHomepage();
}

// The user logged out. The programmer is completely done with sessionData.
// But sessionCache[userId] still points to it, and sessionCache is a root-reachable
// global. A tracing GC will faithfully keep sessionData alive forever. This is a
// real memory leak, in a garbage-collected language, and the GC is working perfectly.
🧠 The Takeaway Worth Memorizing
Reachability is not a proxy for "logically dead" — it's a completely separate, purely structural property. A tracing GC is extremely good at one narrow job: freeing objects nothing can reach anymore. It has zero opinion about objects you've forgotten about but can technically still reach. Those are still your problem — which is exactly why "memory leak" remains a meaningful bug report even in languages that have never given you a free() function to misuse.
02 — Where the Search Begins

Roots: The Starting Points of Every Traversal

The reachability definition leans entirely on one term we haven't pinned down yet: roots. A root is any reference the runtime knows about without having to trace it from somewhere else — the fixed starting set for the whole graph search. Concretely, roots typically include:

Global Variablesalways roots
Anything reachable through a global object, module-level binding, or static field is trivially rooted — nothing has to point to it from outside for the runtime to know it's there.
The Call Stackalways roots
Every local variable and parameter in every currently-executing function, all the way up the call chain, counts as a root. A function three frames deep holding the only reference to an object is enough to keep it alive.
CPU Registersalways roots
A pointer sitting in a register mid-computation, not yet spilled to the stack, is just as much a live reference as one sitting in a named variable — the collector has to account for it too.

The exact list of "what counts as a root" varies by language and runtime — some also root things like currently-registered exception handlers or pending finalizer callbacks — but the shape is always the same: roots are the references the runtime can enumerate directly, without following any pointer to find them. Everything else in the heap only counts as reachable if some chain of pointers connects it back to one of these starting points.

Why this matters more than it sounds like it should. The entire correctness of a tracing collector rests on getting the root set exactly right. Miss a real root — say, a pointer temporarily stashed somewhere the collector doesn't know to look — and you'll free an object something is still using, which is a self-inflicted use-after-free bug inside the "safe" language's own runtime. This is a genuinely hard engineering problem (compilers have to emit metadata describing exactly which stack slots and registers hold live pointers at every possible collection point), even though the theory above sounds simple.

Two Honest Ways to Find Roots: Precise vs. Conservative

Knowing "the stack is part of the root set" is the easy part. Actually scanning it raises an uncomfortable question: a stack slot is just a chunk of bytes — how does the collector know whether those bytes are a pointer into the heap, or just an ordinary integer that happens to look like one? Two honest answers exist, and real-world collectors split between them.

✅ Precise (Exact) GC

The compiler emits extra metadata alongside the code — a map saying, at this exact point in execution, stack slot 3 and register RBX hold pointers, and everything else doesn't. The collector consults this map and never has to guess. Correct by construction, but requires real cooperation from the compiler at every possible collection point.

⚠️ Conservative GC

No compiler metadata at all — the collector scans the stack and treats anything that looks like a plausible heap pointer (the right numeric range, correct alignment) as if it might be one, just to be safe. Simple to bolt onto an existing compiler, but it can accidentally treat a random integer as a "root," which means an object can be kept alive by sheer coincidence — a false positive, safe but wasteful, never a false negative.

Notice the asymmetry: a conservative collector's mistake can only ever keep something alive that didn't need to be — it can never free something that's still genuinely in use, because it only ever adds extra, spurious roots, never removes real ones. That asymmetry is exactly why "when in doubt, guess it's a root" is a defensible engineering shortcut, even though it means conservative collectors occasionally retain garbage a precise collector would have correctly freed.

03 — A Small Worked Example

Roots → A → B, and the Case of C

Theory's cheap. Let's put a tiny, concrete heap on the table and reason through it by hand before any algorithm touches it. Suppose the heap currently holds five objects: A, B, C, D, and G. The reference graph looks like this:

  • A root reference points to A.
  • A holds a reference to B, and a separate reference to D.
  • C holds a reference to G.
  • Nothing — no root, no other object — points to C.

Walk the reachability rule by hand. Starting from the root: root → A. From A you can reach B and D. So A, B, and D are all reachable — they're alive, no matter how long ago they were allocated or how little "work" A has done with them recently. C is a different story: nothing points to C. It doesn't matter that C points to G — that only matters if something can reach C first. Since nothing can, C is garbage, and critically, so is G, purely because the only path to G ran through an already-unreachable object.

🔑 The Detail Everyone Trips On Once
G has an incoming reference! Doesn't that make it reachable? No — having a reference isn't enough; the reference has to originate from something itself reachable from a root. C → G is a real edge in the graph, but C is floating disconnected from the root set, so that edge leads nowhere useful. This is exactly why reachability has to be computed by traversal from roots outward, not by checking "does anything point to me" in isolation — a whole disconnected cluster of objects can reference each other richly and still all be garbage together.
04 — Phase One

MARK: Flood the Graph From the Roots

The mark phase turns the reachability definition directly into an algorithm. Give every object one extra bit of storage — a mark bit, starting at 0 (unmarked) before every collection. Then, starting from each root, traverse outward: visit an object, flip its mark bit to 1, then recursively visit everything it references. This is a plain graph traversal — depth-first or breadth-first both work, the order doesn't affect the result, only the traversal's own memory usage.

  • Start at each root. For every root reference, if the object it points to isn't already marked, mark it and continue the walk from there.
  • Follow every outgoing reference. For the object you just marked, look at every field, array slot, or captured variable that holds a reference, and recurse into each one.
  • Skip anything already marked. This one check is what makes cycles harmless — if you arrive at an object whose mark bit is already 1, you stop immediately instead of recursing again. No infinite loop, no special-case cycle detection required.
  • Stop when there's nothing left to visit. Once every root's outward traversal has exhausted itself, the mark phase is done. Every object with its mark bit set is provably reachable. Every object without it is provably not.
    • Pseudocodefunction mark(obj) {
  if (obj is null or obj.marked) return;   // already visited — this is what handles cycles
  obj.marked = true;
  for (child of obj.references) {
    mark(child);                      // recurse into every outgoing reference
  }
}

function markPhase() {
  for (root of roots) {
    mark(root.target);
  }
}
    ✅ In Our Worked Example
    Starting from the root, mark(A) runs: A gets marked, then recurses into A's references — B and D — marking both. Neither B nor D has outgoing references here, so those branches terminate. Nothing ever calls mark(C), because nothing reachable ever points to C — so C and, transitively, G are never visited and never marked. Marked set after this phase: { A, B, D }.

    The Recursive Version Has a Hidden Landmine

    The pseudocode above is written recursively because that's the clearest way to explain it — but a real implementation almost never marks this way, and the reason is worth understanding. Every recursive call to mark() consumes a stack frame on the collector's own call stack. A long, deep chain of references — a linked list with a million nodes, a deeply nested tree, a long promise chain — turns into a million nested recursive calls before the traversal ever bottoms out and starts returning. That can overflow the collector's own stack, which means the one piece of software you absolutely cannot afford to crash just crashed, while trying to clean up memory.

    Pseudocode — iterative, stack-overflow-safefunction markPhase() {
  const worklist = [];               // an explicit stack, allocated on the HEAP, not the call stack
  for (root of roots) {
    worklist.push(root.target);
  }
  while (worklist.length > 0) {
    const obj = worklist.pop();
    if (obj is null or obj.marked) continue;
    obj.marked = true;
    for (child of obj.references) {
      worklist.push(child);          // grows a data structure, not the native call stack
    }
  }
}

    Same algorithm, same result, same handling of cycles via the "already marked, skip it" check — but the traversal's own bookkeeping now lives in an explicitly-managed data structure that can grow as large as available memory allows, instead of being limited by however deep the native call stack happens to be. This is a recurring pattern in real garbage collector implementations: the algorithm is simple and recursive-shaped, but the implementation has to defensively convert that recursion into an explicit loop, because the collector cannot be allowed to fail on exactly the kind of large, deeply-linked structure it exists to reclaim.

    05 — Phase Two

    SWEEP: Walk the Whole Heap, Free What's Unmarked

    The mark phase only ever visits reachable objects — it has no reason to touch C or G at all. So how does the collector actually find and free the garbage? A second, completely different pass: the sweep phase doesn't follow references at all. It walks the entire heap linearly, object by object, in whatever order they happen to be stored — a simple list or block scan, no graph logic involved.

  • Visit every object in the heap, one at a time. Not "every reachable object" — literally every object that currently exists, marked or not.
  • Check the mark bit. If it's set, the mark phase proved this object reachable. Leave it alone, and reset its mark bit to 0 so it's ready for the next collection cycle.
  • If it's unset, free it. The mark phase never reached this object, which — given the reachability definition — means it's garbage. Reclaim its memory back to the allocator.
    • Pseudocodefunction sweepPhase() {
  for (obj of heap) {           // every object, no exceptions, marked or not
    if (obj.marked) {
      obj.marked = false;    // clear it, ready for the next mark phase
    } else {
      heap.remove(obj);
      free(obj);           // unreachable → reclaim the memory
    }
  }
}

function collect() {
  markPhase();
  sweepPhase();
}

    In our example, the sweep pass visits A, B, C, D, and G in heap order. A, B, and D are marked — they survive, mark bits cleared for next time. C and G are unmarked — both get freed, and their memory becomes available for future allocations. Notice sweep didn't need to know why C and G were garbage, or that C used to reference G. It just trusted the mark bit the previous phase computed.

    🔀 Two Phases, Two Completely Different Access Patterns
    This split is worth sitting with: mark is a pointer-chasing traversal that only touches live data and can jump anywhere in memory unpredictably. Sweep is a linear scan that touches every object regardless of liveness but in predictable, cache-friendly order. Almost every refinement to mark-and-sweep you'll ever encounter — incremental marking, concurrent sweeping, generational splits — is really an attempt to make one or both of these two very different access patterns cheaper.

    07 — What This Costs You

    The Price of Stopping the World

    The version of mark-and-sweep described above has a property that sounds alarming once you say it out loud: nothing else can safely run while it's running. If your program kept mutating references mid-traversal — adding a new pointer, dropping an old one — the mark phase could get a wrong, inconsistent answer: it might miss marking an object that a running mutation just made reachable. The simplest fix is the one classic mark-and-sweep uses: pause every other thread of execution completely until both phases finish. This is called a stop-the-world collection.

    Where the pause time actually comes from Mark phase cost ∝ number of reachable objects (and the edges between them)
    Sweep phase cost ∝ total number of objects currently in the heap, reachable or not A heap with a lot of garbage in it doesn't make marking slower — but it does make sweeping slower, since sweep has to visit every object regardless of liveness.

    For a small heap, a stop-the-world pause is invisible. For a large, long-running program with a big heap — exactly the kind of program that benefits most from automatic memory management — that pause can become a real, user-visible stutter. This single fact is the entire motivating force behind almost every advanced GC technique that exists: incremental collectors that do a little marking at a time instead of all at once, concurrent collectors that mark alongside the running program using careful synchronization, and generational collectors (the subject of a later lesson in this series) that shrink the region being collected most of the time so the expensive full pass happens rarely.

    What about the freed memory's leftover holes? A naive sweep just adds a freed object's space to a free list — it doesn't rearrange anything, so the heap can end up with usable memory scattered in small, non-contiguous gaps between surviving objects (fragmentation). Some collectors follow sweep with a compaction pass that slides live objects together to close the gaps; others accept the fragmentation and rely on a free-list allocator that's good at reusing odd-sized holes. Either way, this is a separate design decision layered on top of the mark-and-sweep core, not part of the core algorithm itself.
    08 — Side by Side

    Manual Memory Management vs. Tracing GC

    Mark-and-sweep isn't a free lunch — it trades one set of problems for another. Worth being explicit about the trade, since "garbage collection is just strictly better" is a common oversimplification.

    PropertyManual (malloc/free)Tracing GC (mark-and-sweep)
    Who decides an object is deadThe programmer, explicitly, per allocationThe runtime, automatically, via reachability
    Use-after-free possible?Yes — a classic, exploitable bug classNo — nothing is freed while still reachable
    Double-free possible?YesNo — freeing is centralized in the collector
    Memory leaks possible?Yes — forgotten free() callsYes — forgotten references keep things reachable
    Pause behaviorNone — frees are instantaneous, localStop-the-world pauses possible (naive version)
    Peak memory usageTight — freed the instant you say soGarbage can pile up between collections
    Programmer cognitive loadHigh — must track every object's lifetimeLow — never call free() yourself
    ⚖️ Neither Side Wins Outright
    Tracing GC eliminates an entire class of catastrophic, security-relevant bugs (use-after-free, double-free) at the cost of unpredictable pause timing and looser control over peak memory. That trade is so favorable for most application code that the majority of modern languages ship a tracing collector by default. It's a much worse trade for latency-critical systems code — which is exactly why browsers still write their rendering and networking cores in C++/Rust rather than a GC'd language, even while running a GC'd language (JavaScript) safely sandboxed on top.
    09 — Quick Reference

    Glossary & Key Terms

    Garbage
    Any object not reachable from the root set. A purely structural property, unrelated to programmer intent.
    Reachability
    The property of having some chain of references leading back to a root. The formal definition of "alive" that a tracing GC computes.
    Root Set
    Global variables, the call stack's locals/parameters, and CPU registers — the references the runtime can enumerate directly, without tracing them from anything else.
    Mark Phase
    A graph traversal starting from every root that flags each reachable object by setting its mark bit, skipping anything already marked (which is what makes cycles harmless).
    Sweep Phase
    A linear scan over every object in the heap that frees anything left unmarked and clears the mark bit on everything else, in preparation for the next cycle.
    Mark Bit
    One extra bit of per-object bookkeeping, reset to 0 before each collection, set to 1 during the mark phase for every object the traversal actually reaches.
    Tracing Garbage Collector
    Any collector — mark-and-sweep included — that determines liveness by tracing reference chains outward from roots, as opposed to reference counting.
    Stop-the-World Pause
    A pause in program execution during collection, needed by naive collectors so the object graph doesn't change mid-traversal and produce an incorrect answer.
    Fragmentation
    Usable free memory left scattered in small, non-contiguous gaps after a sweep, sometimes addressed by a follow-up compaction pass.
    Use-After-Free
    A bug where code accesses memory that has already been freed — impossible under a correctly-implemented tracing GC, common under manual memory management.
    🎯 The One-Sentence Summary
    An object is garbage exactly when nothing reachable from a root points to it, mark-and-sweep computes that by flooding outward from the roots and flagging everything it touches, and then reclaims everything the flood never reached — two simple phases built entirely on one precise definition.
