Reference Counting
vs. Tracing GC

Mark-and-sweep answers "is this object garbage?" by searching outward from roots. There's a completely different strategy that never searches anything: have every object carry its own count of who's pointing at it, and free it the instant that count hits zero. It's simpler, it's more predictable — and it has exactly one blind spot, baked into its own arithmetic, that no amount of clever engineering inside the algorithm itself can fix.

00 — Where We Left Off

One Strategy Down, One Big One to Go

Last lesson established the reachability definition of garbage and walked through mark-and-sweep, the algorithm that acts on it directly: flood outward from the roots, mark everything you touch, then sweep the whole heap and free whatever wasn't marked. That's one entire family of garbage collectors — tracing collectors — and it's the dominant one in modern language runtimes. But it isn't the only idea anyone ever had.

There's a second, much older, conceptually simpler family: reference counting. Instead of periodically asking "starting from the roots, what can I still reach?", every object just keeps a running tally of how many references currently point to it — and frees itself the moment that tally reaches zero. No traversal, no roots to enumerate, no separate "collection" step at all. It sounds like a strictly better deal. It has one specific, unfixable-from-the-inside flaw, and understanding exactly why is the entire point of this lesson.

📦 Carry This Forward From Last Time
Keep the reachability definition in your head: an object is alive iff some chain of references leads to it from a root. Reference counting is going to approximate that same idea using purely local information — no object needs to know about roots at all, just its own incoming reference count. Watch closely for where that local approximation and the real, global reachability definition quietly stop agreeing with each other.

Historically, reference counting is actually the older idea of the two — early Lisp implementations experimented with it before mark-and-sweep became the more common default for languages with rich, cyclic data structures. It never went away, though; it simply found the niches its strengths were best suited for, which turns out to be a recurring theme in garbage collection design generally: very few real systems pick one pure strategy and never borrow from the other.

01 — The Alternative Strategy

Every Object Just Knows How Popular It Is

Reference counting gives every object one extra field: an integer, its reference count (refcount), starting at zero. The rule is mechanical and entirely local to the object itself:

  • A new reference to the object is created — an assignment, a function call passing it as an argument, inserting it into a list — the object's refcount goes up by one.
  • An existing reference to the object is destroyed — a variable goes out of scope, gets reassigned to point elsewhere, or its containing object is itself freed — the object's refcount goes down by one.
  • The refcount hits exactly zero. That's the whole liveness check: no traversal, no roots, no marking. Zero incoming references means nothing anywhere can possibly reach this object anymore, so it's freed immediately, right there in the code path that just dropped the last reference.
    • Pseudocodefunction retain(obj) {         // a new reference to obj is created
  obj.refcount += 1;
}

function release(obj) {        // an existing reference to obj is destroyed
  obj.refcount -= 1;
  if (obj.refcount == 0) {
    for (child of obj.references) {
      release(child);        // dropping obj also drops ITS references
    }
    free(obj);                // no traversal, no roots — just: count is zero, gone
  }
}

function assign(variable, newTarget) {
  if (variable.target) release(variable.target);  // drop the old reference first
  variable.target = newTarget;
  if (newTarget) retain(newTarget);              // then add the new one
}

    Notice what's genuinely elegant here: release() cascades. Freeing an object automatically releases every reference it was holding, which can cascade into freeing those objects too, and so on down the chain — a whole tree of no-longer-needed objects can unwind and free itself in one cheap, local operation, with no global scan of anything.

    🔑 The Key Structural Difference From Tracing GC
    Mark-and-sweep answers "is this object alive?" by asking a global question — can I reach it from a root, right now, via some path through the whole graph? Reference counting answers the same question using only local information stored on the object itself — how many incoming edges does it currently have? Local information is cheap to check and update incrementally. It's also, as you're about to see, an imperfect proxy for the real, global answer.
    Objective-C did this by hand for years before ARC existed. Before Apple introduced ARC in 2011, Objective-C programmers wrote retain and release calls themselves, directly, by hand — close to literally the retain()/release() pseudocode above. Forgetting a release leaked memory; calling it one time too many freed an object something else still needed, a manual-refcounting double-free. ARC's actual innovation wasn't the counting scheme itself — that stayed the same — it was having the compiler insert those calls automatically and correctly, at every possible point a reference is created or destroyed, removing an entire category of by-hand bookkeeping mistakes.

    The Cascade Has a Cost Too

    That cascading release() is elegant, but it hides a real performance trap of its own — one with an almost eerie parallel to a problem in the mark-and-sweep lesson. Recall that a naively-recursive mark phase can blow the collector's own call stack on a long, deep chain of objects. The exact same failure mode exists here: dropping the last reference to the head of a million-node linked list triggers release() on node 1, which — because its refcount also hits zero — recursively calls release() on node 2, and so on, a million recursive calls deep, all inside what looked to the programmer like one simple, "instant" statement: list = null.

    ⏱️ Refcounting's Own Hidden "Pause"
    This is the sharpest myth to retire about reference counting: "no collection pass" does not mean "no possible pause." Dropping one reference can, in the worst case, trigger an arbitrarily long cascade of frees, all happening synchronously on whatever thread happened to drop that one reference — a real-time stall with a shape that's arguably harder to predict than a tracing collector's, precisely because it can be triggered by code that looks like it's doing nothing more than a single, ordinary assignment. Production-grade refcounting implementations typically guard against this the same way the mark-and-sweep lesson's fix worked: convert the recursive cascade into an explicit worklist and free iteratively, or defer some of the cascade to a background thread instead of doing it all inline.
    02 — Why It Feels Different to Use

    No Collection Pass — Freed the Instant It's Zero

    Tracing GC, even a well-engineered one, has an inherently episodic character: garbage piles up between collections, and then a collection runs — possibly pausing your program — and reclaims a batch of it all at once. Reference counting has no such rhythm at all. There is no "collection" as a distinct event; freeing is smeared continuously across ordinary program execution, one decrement at a time, exactly at the moment the last reference disappears.

    The practical consequence Tracing GC: garbage accumulates → a collection pass runs → a batch gets reclaimed, possibly with a pause
    Reference counting: an object is reclaimed the instant refcount hits zero — no batching, no separate pass, no pause tied to "collection" This is why refcounting is often called deterministic — you can reason about exactly when an object's destructor runs, just by reading the code.

    That determinism is not just a performance footnote — it's a genuine feature real programs rely on. If an object's destructor also releases a scarce external resource (closing a file handle, releasing a lock, returning a database connection to a pool), knowing exactly when that happens, synchronously, at the point the last reference is dropped, is extremely useful. Under a tracing collector, an unreachable object might sit around uncollected for an indeterminate amount of time before a collection finally reclaims it and runs its cleanup — which is why languages with tracing GC generally need a separate, explicit resource-management idiom (like a with block or a try-with-resources construct) instead of leaning on garbage collection for that job.

    This is exactly what Swift's ARC and Python's refcounting buy their respective ecosystems. Swift's deinit and Python's __del__ both run synchronously and predictably at the moment an object's refcount hits zero — not at some later, GC-scheduled moment. Objective-C's ARC (Automatic Reference Counting) — the mechanism Swift's reference counting descends from — was specifically designed around this predictability for exactly this reason, in a systems context (Apple's frameworks) where deterministic resource cleanup mattered a great deal. 
    Why deterministic timing matters, concretelyfunction processFile(path) {
  const handle = openFile(path);  // handle.refcount = 1 (held by this local variable)
  readAndParse(handle);
}                                // `handle` goes out of scope here → release(handle) → refcount hits 0
                                 // → handle's destructor runs RIGHT HERE, closing the OS file descriptor,
                                 // synchronously, before the next line of the CALLER even executes.

// Under a tracing GC, `handle` would just become unreachable when the function
// returns — but WHEN its finalizer actually runs is up to the collector's own
// schedule, which could be milliseconds or seconds later. If the program opens
// file descriptors faster than the GC gets around to closing old ones, it can
// exhaust the OS's file descriptor limit despite every object being, eventually,
// correctly collected. Determinism isn't just nice — it avoids this entire class
// of "technically not a leak, but runs out of a scarce resource anyway" bug.
    03 — The Fatal Flaw

    Two Objects, Pointing at Each Other

    Here's the scenario that breaks everything. Suppose object A holds a reference to object B, and object B holds a reference back to object A — a reference cycle. Now suppose every external reference to both of them — the variable in the code that originally created them — goes away: the function returns, the variable goes out of scope, whatever it was gets reassigned.

    Walk the refcounts by hand, step by step, and the failure becomes impossible to miss:

  • A is created. One external variable points to it. A.refcount = 1.
  • B is created, and A.field = B. A now references B. B.refcount = 1.
  • B.field = A closes the cycle. B now references A back. A.refcount = 2 (the external variable, plus B's pointer).
  • The external variable goes out of scope. release(A) runs: A.refcount drops from 2 to 1 — not zero, because B is still pointing at it. Nothing further happens. No cascade, no free.
  • Final state, forever. A.refcount = 1 (held by B). B.refcount = 1 (held by A). Both are completely unreachable from any root — precisely the scenario that made C garbage in the mark-and-sweep worked example last lesson — but neither count will ever reach zero on its own.
    • The arithmetic that never resolves A.refcount = 1 (held by B) · B.refcount = 1 (held by A) Both counts are honestly, correctly nonzero — refcounting isn't malfunctioning here. It's doing exactly what it was designed to do. The design itself has a blind spot.
    🚫 Why This Isn't a Bug You Can Patch
    Reference counting only ever looks at local information: "how many things point at me, right now?" A cycle of otherwise-unreachable objects satisfies that local check for every object in the cycle simultaneously — each one genuinely has an incoming reference, it's just a reference from another equally-unreachable object. Detecting this requires exactly the kind of global reasoning reference counting was specifically designed to avoid: you have to ask "is there a path from any root to this whole cluster?" — which is the reachability question mark-and-sweep answers, and refcounting, by construction, cannot ask on its own.

    The refcounts drop from 2/1 to 1/1 and then simply... stop. Nothing further happens, because nothing further can happen — both objects still show a positive count, and refcounting only ever frees an object whose count is exactly zero. Compare that against what a mark-and-sweep collector, from last lesson, would do with this exact same graph: it doesn't look at counts at all. It starts at the root, finds nothing reachable now that the root reference is gone, and correctly frees both A and B in the very next collection.

    Sit with how quietly this failure happens. There's no crash, no exception, no error message — refcounting doesn't know anything went wrong, because from its own local, per-object point of view, nothing did. Every increment and decrement it ever performed was arithmetically correct. The bug isn't in the mechanism's execution; it's in the mechanism's fundamental inability to ask the one question — "is there a path back to a root?" — that would have revealed A and B were garbage the moment the root reference was dropped.

    05 — Real-World Fallout

    How Python and Swift Actually Handle This

    This isn't a theoretical footnote — it's a well-known problem that every production reference-counted language has had to solve one way or another. Two very different real answers:

    Python: Refcounting + a Bolted-On Cycle Detectorautomatic
    CPython's primary memory management is straight reference counting — every PyObject carries a refcount field, and it's why del obj or a variable going out of scope can trigger immediate, synchronous deallocation. But CPython also ships a supplementary generational cycle detector (the gc module), which periodically scans specifically for groups of container-like objects (objects that can hold references to other objects) that reference each other but aren't reachable from anywhere else, and reclaims them. Refcounting handles the vast majority of frees immediately and cheaply; the cycle detector runs occasionally to mop up exactly the pathological case this lesson is about.
    automatic, no code changes needed
    Swift / Objective-C: ARC, No Built-In Cycle Collectormanual
    Swift's Automatic Reference Counting (and the Objective-C ARC it's descended from) is pure compiler-inserted reference counting — the compiler automatically emits the retain/release calls for you, but there is deliberately no runtime cycle detector at all. If your object graph forms a cycle, ARC will leak it, permanently, with no automatic recovery. The classic real-world instance: a closure that captures self strongly while also being stored as a property on that same object — a textbook two-node cycle, common enough that it has its own well-known name in the Swift community ("strong reference cycle" / "retain cycle").
    programmer must break cycles manually
    🧩 Same Root Cause, Two Different Bets
    Python's designers judged the cost of a periodic cycle-scanning pass acceptable in exchange for programmers never having to think about this at all. Swift's designers, targeting performance-sensitive UI and systems code, judged the unpredictability and overhead of any background scanning pass unacceptable, and pushed the responsibility for breaking cycles explicitly onto the programmer instead. Neither choice is "solving" the underlying limitation of reference counting — both are managing it, in opposite directions.

    It's Not Just Application Languages, Either

    Reference counting shows up below the application-language layer too, wherever a language wants automatic memory management without the overhead of a full tracing runtime. C++'s std::shared_ptr<T> and Rust's Rc<T> (and its thread-safe counterpart Arc<T>) are both library-level, opt-in reference counting — you choose to wrap a value in one when you specifically need shared ownership, rather than the whole language defaulting to it. Both have the exact same cycle blind spot described above: a Rc<RefCell<Node>> tree with parent pointers back to children, or two shared_ptrs pointing at each other, will leak in precisely the way A and B leaked in the example above — and both ecosystems ship the identical fix, a non-owning Weak<T> / std::weak_ptr<T> type, for the identical reason: break the cycle by hand, on the edge you choose, because neither runtime is scanning for cycles on your behalf.

    Why Rust in particular makes this an interesting case study. Rust's ordinary ownership model (its borrow checker) is not reference counting at all — most Rust values have exactly one owner and are freed deterministically when that owner's scope ends, no counting required. Rc<T> is a deliberate, explicit opt-out from that model, reached for specifically when a value genuinely needs more than one simultaneous owner. Rust's designers considered a full tracing GC and rejected it for the language's core; reference counting survives as an opt-in escape hatch precisely because its cost and its cycle limitation are both easy to reason about locally, one Rc<T> at a time, rather than being an invisible, ambient runtime cost.
    06 — Breaking Cycles on Purpose

    Weak References: A Pointer That Doesn't Count

    If a language gives you no automatic cycle detector, you need a manual way to prevent cycles from forming in the first place — without simply refusing to let two objects reference each other, which is often exactly the relationship your data actually has (a parent and child that both need to reach one another, for instance). The tool for this is a weak reference: a reference that lets you access an object, but that deliberately does not increment its refcount.

    Swift-flavored pseudocodeclass Parent {
  var child: Child?          // STRONG reference — increments child's refcount
}
class Child {
  weak var parent: Parent?   // WEAK reference — does NOT increment parent's refcount
}

// parent.child = someChild retains someChild → someChild.refcount += 1
// child.parent = someParent does NOT retain someParent → refcount unchanged
// When every STRONG (external) reference to parent is dropped, its refcount
// can finally reach zero — the weak edge from child never held it up.

    The pattern above is the standard fix: pick one direction of a naturally-cyclic relationship (commonly, the "back-pointer" — a child pointing back to its parent, a delegate pointing back to the object that owns it) and make that direction weak. The strong references still form a clean tree with no cycle in it; the weak reference lets code still navigate "upward" without contributing to anyone's refcount. When the last strong, external reference to the parent goes away, its refcount can finally reach zero — normally, correctly — because the child's pointer back to it was never counted in the first place.

    ✅ What Happens If You Follow a Weak Reference to a Freed Object
    A correctly-implemented weak reference doesn't leave you holding a dangling pointer if the object it points to gets freed through its strong references — that would just reintroduce use-after-free by another name. Instead, weak references are typically implemented so that accessing one after the target is deallocated safely yields "nothing" (nil/None, or an explicit "expired" state), rather than a pointer to freed memory. The runtime tracks outstanding weak references and clears or invalidates them at deallocation time — which is itself a small amount of extra bookkeeping refcounting has to do, on top of the basic increment/decrement, to make weak references safe to use.

    Swift Actually Gives You Two Flavors, on Purpose

    Swift is worth a closer look here because it doesn't stop at one non-counting reference type — it offers two, and the difference between them is a genuinely useful piece of real-world nuance. A weak reference (shown above) is for relationships where the referenced object might legitimately outlive or not exist independent of the reference holder, so it has to support becoming "nothing" safely — which is why weak references in Swift must always be declared as optional. An unowned reference is for relationships where the two objects are guaranteed, by the programmer's own reasoning about the code, to have the same lifetime or a strictly dependent one — it skips the extra "safely becomes nil" bookkeeping entirely, and trades that safety for slightly less overhead.

    Reference KindIncrements Refcount?If Target Is Freed
    StrongYesN/A — it's the reason the target stays alive
    WeakNoSafely resolves to nil / "expired" — always optional
    UnownedNoUndefined / a crash if accessed — programmer guarantees this never happens

    That third row is the trade being made explicit: unowned is a promise from the programmer that the reference will never outlive its target, in exchange for not paying the (small) runtime cost of tracking and safely nil-ing the reference. Get that promise wrong, and you've reintroduced exactly the dangling-pointer bug reference counting was supposed to prevent — which is a good reminder that "break the cycle with a non-counting reference" moves the correctness burden from "did I remember to free this" onto "did I correctly reason about which direction of this relationship is safe to leave uncounted."

    07 — Side by Side

    Reference Counting vs. Tracing GC

    Neither strategy is a strict upgrade over the other — they trade different costs for different guarantees. Worth having the full comparison in one place.

    PropertyReference CountingTracing GC (mark-and-sweep)
    When is an object freedInstantly, when its refcount hits zeroIn a batch, during the next collection pass
    Handles reference cycles?No — cycles leak forever without extra helpYes — cycles are collected naturally
    Per-object memory overheadExtra refcount field on every objectJust a mark bit (or none, between collections)
    Per-operation costEvery pointer assignment touches a counterPointer assignments are free; cost is at collection time
    Pause behaviorNo distinct "collection" pause (mostly)Can pause the program during collection
    Destructor timingDeterministic — exactly when refcount hits 0Non-deterministic — whenever GC gets to it
    Needs to know the root set?No — purely local bookkeepingYes — must enumerate globals, stack, registers
    Real-world usersCPython, Swift/ARC, Rust's Rc<T>, C++'s shared_ptrV8/JavaScript, JVM, Go, .NET CLR

    ✅ Pick Refcounting When

    You need deterministic, immediate cleanup of external resources; your object graphs are naturally tree-shaped (or cycles are rare and easy to mark with weak references by hand); and you'd rather pay a small, constant cost on every pointer write than an occasional larger collection pause.

    ⚠️ Pick Tracing GC When

    Your object graphs are rich, deeply interconnected, and likely to contain cycles that would be error-prone to hunt down and manually break; per-pointer-write overhead would dominate hot paths; and occasional, batched collection pauses (especially ones you can make short with modern incremental/concurrent techniques) are an acceptable trade.
    These two strategies aren't always an either/or choice in practice. Some real systems hybridize them — for instance, using refcounting for large, expensive-to-scan resources (like buffers or native objects wrapped by a scripting language) while the scripting language's own object graph is managed by a separate tracing GC underneath, with the two systems bridged carefully at the boundary. Even Python's own architecture is arguably a hybrid: refcounting as the primary mechanism, with a tracing-style cycle detector bolted on specifically to cover refcounting's blind spot. The next lesson in this series takes tracing GC in a different optimization direction entirely — splitting the heap by object age rather than changing the underlying liveness test.
    08 — Quick Reference

    Glossary & Key Terms

    Reference Count
    A per-object integer tracking how many active references currently point to it — incremented on reference creation, decremented on reference destruction.
    Retain / Release
    The two operations that adjust a refcount: retain increments it (a new reference), release decrements it and frees the object if the count reaches zero.
    Reference Cycle
    A group of objects that reference each other (directly or transitively) such that every member has a nonzero refcount even though nothing outside the group can reach any of them.
    Cycle Detector
    A supplementary mechanism (like CPython's gc module) that periodically scans for unreachable reference cycles and collects them, layered on top of ordinary refcounting.
    Strong Reference
    An ordinary reference that increments the target's refcount — the default kind of reference in a refcounted system.
    Weak Reference
    A reference that lets code access an object without incrementing its refcount, used deliberately to break potential cycles; safely resolves to "nothing" if the target has already been freed.
    Unowned Reference
    Swift's non-counting reference that skips the safety bookkeeping weak references pay for, trading it for a programmer's promise that the reference will never outlive its target.
    ARC (Automatic Reference Counting)
    Swift's (and Objective-C's) compiler-inserted reference counting — the compiler automatically emits retain/release calls, with no built-in cycle collector.
    Deterministic Destruction
    The property of reference counting where an object's cleanup (destructor/deinit) runs synchronously and predictably at the exact point its last reference is dropped.
    Tracing Garbage Collector
    The alternative family covered in the prior lesson — determines liveness via reachability traversal from roots rather than local reference counts.
    Root Set
    Globals, the call stack, and registers — the starting points a tracing collector needs; reference counting notably never needs to know this set at all.
    🎯 The One-Sentence Summary
    Reference counting trades a global reachability search for cheap, local, per-object bookkeeping that frees things the instant they're truly unreferenced — but that same locality is exactly why it structurally cannot see a cycle of mutually-referencing garbage, which is why every real refcounted language ships either an automatic cycle detector or a manual weak-reference convention to cover the gap.

    One closing thought worth carrying forward: notice that both garbage collection strategies covered so far — tracing and refcounting — are trying to answer the exact same underlying question, "is this object still needed?" They just answer it from opposite directions: tracing GC asks it globally, by searching from roots outward; refcounting asks it locally, by tallying incoming edges. Every other GC scheme you'll ever encounter is, in some way, a variation, hybrid, or optimization of one of these two answers.
