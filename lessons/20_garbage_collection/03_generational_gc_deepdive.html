Mark-and-sweep works, but a naive version does the same amount of work on every single collection: scan the whole live set, walk the whole heap. Real programs have a wildly lopsided pattern hiding in their allocations — one so consistent across languages and decades that GC designers built an entire architecture around exploiting it. That architecture creates one genuinely subtle correctness problem of its own, and a small, elegant piece of bookkeeping that solves it.

00 — Where We Left Off

Two Strategies Down, One Optimization to Go

Two lessons ago: mark-and-sweep, the baseline tracing algorithm — flood outward from roots, mark what's reachable, sweep away what isn't. One lesson ago: reference counting, a completely different strategy with its own fatal blind spot around cycles. This lesson stays inside the tracing-GC family from lesson one, but asks a different question entirely: mark-and-sweep is correct, but is it efficient? Specifically — does it do more work than it needs to, every single time it runs?

The answer is yes, dramatically so, and the fix is one of the most impactful ideas in the whole history of automatic memory management: generational garbage collection. This lesson builds it from first principles, the same way the mark-and-sweep lesson built that algorithm from the bare reachability definition. If you've already read the V8 deep-dive in the Browser X-Ray series, the shape of this is going to look familiar — that's not a coincidence, and we'll come back to exactly why near the end.

📦 What This Lesson Deliberately Skips
This is the general, engine-agnostic theory — true of generational collectors going back to 1980s Lisp and Smalltalk systems, long before any of today's JavaScript engines existed. 01 — The Empirical Observation

The Generational Hypothesis

Think about what a typical running program actually allocates, moment to moment. A loop that builds up a result computes several small intermediate values per iteration — almost all of them discarded the instant the next iteration starts. A function call allocates a stack frame's worth of local objects that exist only for the duration of that call. A request handler builds up temporary parsing structures that are irrelevant the microsecond the response is sent. Meanwhile, a much smaller category of objects — a cache, a piece of long-lived application state, a data structure built once at startup — sticks around for the entire life of the program.

The generational hypothesis, stated plainly In most real programs, the overwhelming majority of allocated objects become garbage almost immediately.
A small minority survive for a very long time. This was first formalized and exploited by David Ungar's 1984 "generation scavenging" work on Smalltalk-80 — and it has held up remarkably consistently across languages, workloads, and four decades of software since.

This isn't a guess or a rule of thumb pulled from nowhere — it's been measured, repeatedly, across an enormous range of real programs, and it holds up with striking consistency: allocate a huge number of objects, and the large majority of them are already dead by the time you'd get around to checking again a fraction of a second later. That skew is the single fact the entire architecture in this lesson is built to exploit.

💡 Why a Naive Collector Wastes This Fact
Recall from the mark-and-sweep lesson: sweep cost is proportional to the total number of objects in the heap, live or dead, because it has to visit every single one to check its mark bit. If 98% of your heap's objects are already garbage on any given collection, a naive full-heap sweep is spending the overwhelming majority of its time confirming, one object at a time, something the generational hypothesis already told you was overwhelmingly likely: yes, this one's dead too. 
Where the skew actually comes fromfunction sumOfSquares(numbers) {
  let total = 0;
  for (const n of numbers) {
    const squared = { value: n * n };   // allocated fresh, every single iteration
    total += squared.value;
    // `squared` becomes unreachable the INSTANT this iteration ends —
    // nothing outside the loop body ever sees it. It was garbage before
    // the loop even finished running.
  }
  return total;                        // `total` is the one value that actually escapes the loop
}

// One loop over 100,000 numbers: 100,000 short-lived allocations,
// exactly ONE value (`total`) that has any chance of surviving past the
// function returning. This ratio — a torrent of throwaway intermediate
// objects around a trickle of things that actually matter later — is
// completely ordinary code, not a contrived worst case.
02 — The Architecture This Motivates

Split the Heap: Young and Old

If most objects die almost immediately, the fix writes itself: don't scan the whole heap every time. Carve out a small region — the young generation (sometimes called the nursery) — where every new object is born, and collect only that small region, extremely frequently. Because it's small, each of these minor collections is fast — you're only ever scanning a slice of the heap, not the whole thing.

03 — Earning Your Way Out of the Nursery

Promotion: Proving You're a Survivor

The young generation can't just grow forever — it has to stay small to stay cheap to collect. So what happens to the minority of young objects that keep surviving collection after collection instead of dying quickly like the hypothesis predicts? They get promoted (also called tenured) — moved out of the young generation and into the old generation, typically after surviving some small number of minor collections (a common threshold is something like two or three survivals, though the exact number is a tuning knob, not a law of nature).

  • Object is allocated in the young generation. Like almost everything else, it starts here — allocation is fast and always goes into the nursery first.
  • A minor collection runs. If the object is still reachable, it survives this pass — the collector notes it lived through one collection.
  • It survives a second (or third) minor collection. Repeated survival is treated as evidence the object doesn't fit the "dies young" pattern — it's behaving like the minority the hypothesis said would stick around.
  • It gets promoted into the old generation. From here on, it's only examined during the much rarer, more thorough old-generation collection — the young generation stops paying any attention to it at all on future minor collections.

    • This is a bet, not a proof — the collector is speculating, based on observed survival, that an object which has lived this long is likely to keep living, so it's worth moving somewhere that gets scanned less often. Like most bets in GC design (recall TurboFan's type speculation, if you've read the V8 lesson), it's cheap to be wrong about occasionally and enormously valuable to be right about most of the time.

    When the Bet Goes Wrong: Premature Promotion

    Sometimes the bet is wrong, and it's worth naming the failure mode because it's a well-known, recurring headache in generational collector design. An object can survive two or three minor collections purely by unlucky timing — it happened to be allocated right before a collection ran, rather than because it's genuinely long-lived — and get promoted into the old generation anyway. This is called premature promotion, and it has a cost beyond just "one wrong guess": once an object is in the old generation, it's only reclaimed by the rare, expensive major collection, even if it actually becomes garbage moments later. Worse, an object that gets promoted early can drag other objects it references along with it — a phenomenon sometimes called the nepotism problem, where a genuinely short-lived object survives an extra collection or two purely because something else, prematurely promoted, happens to be holding a reference to it.

    Why not just make the young generation bigger, to reduce these mistakes? That trades one problem for another. A bigger nursery does mean more time for genuinely short-lived objects to die before a minor collection ever has to judge them — fewer premature promotions. But it also means each minor collection takes longer (more memory to scan for survivors) and nurseries fill up more slowly, so you collect less often — eroding exactly the "small and frequent" property that made minor collections cheap in the first place. Real collectors tune the nursery size and promotion threshold as a deliberate, measured trade-off, not a "bigger is always better" knob.
    04 — The Genuinely Tricky Part

    The Problem Splitting the Heap Creates

    Here's the catch, and it's a real correctness problem, not just a performance nuance. A minor collection is fast specifically because it only scans the young generation — it doesn't want to pay the cost of walking the entire old generation just to find roots, every single time it runs (that would defeat the whole point of splitting the heap in the first place).

    But reachability doesn't respect the boundary you just drew. Consider this sequence: an object Old has already been promoted, and now sits happily in the old generation. Later, ordinary program execution creates a brand-new object, Young, in the nursery — and then does something completely mundane: Old.field = Young. Now Old, sitting in the old generation, holds the only reference to Young, sitting in the young generation.

    The scenario that breaks a naive minor collection Young is reachable — via Old.field — but Old lives in the region the minor collector doesn't scan. If the minor collector's root set is only "globals, stack, registers, and nothing else," it will never discover the Old → Young edge, conclude Young is unreachable, and free an object that is very much still in use.

    That's not a slowdown — that's a correctness bug indistinguishable, from the running program's point of view, from the use-after-free bugs the whole point of automatic GC was supposed to eliminate. The young generation's scan is fast precisely because it ignores the old generation — but ignoring the old generation completely means missing exactly the references that originate there and point back into the young generation.

    ⚠️ Why You Can't Just "Also Scan the Old Generation"
    That's the obvious fix, and it's exactly the thing generational GC exists to avoid — if every minor collection has to fully scan the (large, slow) old generation for cross-generational pointers, you've just recreated the cost of a full-heap collection on every minor collection, and gained nothing over the naive single-generation collector from two lessons ago. The fix has to find old-to-young references without re-scanning the entire old generation each time.
    05 — The Fix

    Write Barriers: Catching the Moment It Happens

    The insight that solves this: you don't need to go looking for old-to-young references by scanning — you just need to notice the exact instant one is created, and jot it down. That reference was created by one specific action: a pointer write, somewhere in the running program's code, that just stored a young-generation address into an old-generation object's field. If the runtime intercepts every pointer write and checks "did this just make an old object point at a young one?", it can catch every single case, cheaply, as it happens — instead of re-deriving the same information later by brute-force scanning.

    That interception is called a write barrier: a small piece of bookkeeping code the compiler or runtime inserts around every pointer-field assignment, everywhere in the program, without exception.

    Pseudocodefunction setField(obj, fieldName, newValue) {
  obj[fieldName] = newValue;               // the ordinary pointer write itself

  // ── THE WRITE BARRIER — inserted on EVERY pointer write, no exceptions ──
  if (obj.generation == OLD and newValue.generation == YOUNG) {
    rememberedSet.add(obj);                // record: "obj now points into the young generation"
  }
}

function minorCollection() {
  const roots = globals.concat(stackAndRegisters);
  roots = roots.concat(rememberedSet);     // old objects that point young count as EXTRA roots
  markPhase(roots, youngGenerationOnly=true);
  sweepPhase(youngGenerationOnly=true);
}

    The set of old-generation objects flagged this way is usually called the remembered set (some real implementations track it at a coarser granularity — dividing old-gen memory into fixed-size "cards" and marking a whole card dirty rather than tracking individual objects, an optimization called card marking — but the core idea is identical). On every minor collection, the young-generation collector treats the remembered set as additional roots, on top of the usual globals/stack/registers. It never has to scan the old generation to build this list — the write barrier already built it incrementally, one cheap check at a time, exactly when each cross-generational pointer was created.

    ✅ Why This Is Cheap Enough to Do on Every Write
    The write barrier's check is small and constant-time: "is the object I just wrote into old, and is the value I just wrote young?" — two field reads and a comparison, nowhere near as expensive as a scan. Paying that tiny, constant cost on every single pointer write is a genuinely good trade for never having to scan the entire old generation on every minor collection — which is exactly the trade that makes generational GC's core promise (fast, frequent young-gen collections) actually deliver on its promise, correctly.

    Card Marking: The Coarser, Cheaper Real-World Version

    Tracking a precise remembered set of "exactly which objects contain a young pointer" adds a set data structure that itself has to be maintained, resized, and scanned. Many real collectors trade a little precision for a lot of simplicity using card marking: divide the entire old generation into small, fixed-size chunks called cards (a common size is a few hundred bytes to a few kilobytes), and keep one dirty bit per card in a flat array — the card table.

    Pseudocode — card-marking write barrierfunction setField(obj, fieldName, newValue) {
  obj[fieldName] = newValue;

  if (obj.generation == OLD and newValue.generation == YOUNG) {
    const cardIndex = addressToCard(obj);   // which card does obj's address fall inside?
    cardTable[cardIndex] = DIRTY;             // mark the WHOLE card, not just this one object
  }
}

function minorCollection() {
  const roots = globals.concat(stackAndRegisters);
  for (card of cardTable) {
    if (card == DIRTY) {
      roots = roots.concat(objectsInCard(card));  // scan just this card's contents, not the whole old gen
    }
  }
  markPhase(roots, youngGenerationOnly=true);
  sweepPhase(youngGenerationOnly=true);
}

    The trade is explicit: card marking is less precise (a minor collection now has to re-scan every object inside a dirty card, not just the exact object that wrote a young reference — some of that re-scanning turns out to be unnecessary) but far cheaper to maintain (a single bit flip per write, into a flat array with excellent cache behavior, instead of inserting into a general-purpose set). For most real workloads, that trade comes out favorably enough that card marking, in some form, is the more common real-world write barrier implementation.

    An Old Object Reaches Into the Nursery

    Watch the exact scenario from a few sections ago play out: an already-promoted old-generation object writes a reference to a fresh young object, the write barrier catches it, and the next minor collection correctly keeps the young object alive using the remembered set as an extra root. Then compare what would happen without the barrier.

    With the barrier: the moment Old.field = Young executes, the barrier fires and adds Old to the remembered set. When the minor collection runs, it scans the ordinary roots plus the remembered set, finds the path Old → Young, and correctly keeps Young alive. Without the barrier: the minor collection only scans the ordinary roots, never discovers the Old → Young edge because Old itself is never scanned, and frees Young — even though a live, promoted object still holds a perfectly valid pointer to it. That's a self-inflicted dangling pointer, created entirely by the optimization meant to make collection faster.

    07 — Same Idea, One Layer Down

    This Is Exactly What V8 Does

    Everything in this lesson — the young/old split, promotion after surviving a couple of collections, and a write-barrier-fed remembered set catching old-to-young references — is not a simplified toy version of what real engines do. It's the literal architecture used by V8, the JavaScript engine covered in 02_browser_xray/03_v8_deepdive.html. That lesson names V8's specific pieces: the Scavenger as the young-generation collector (implemented as a copying collector between two semi-spaces, a specific technique for how to reclaim the young generation that this lesson didn't need in order to explain why the split exists at all), and a mark-sweep-compact pass for the old generation, with V8's Orinoco project spending years making that expensive old-generation pass run incrementally and concurrently so it blocks the main thread less.

    🔁 What Changed Between the Two Lessons, and What Didn't
    The V8 lesson describes this exact strategy, with V8's real names, real thresholds, and real engineering trade-offs bolted on. Nothing about the underlying reasoning is different — the generational hypothesis, the young/old split, promotion, and the write-barrier fix for cross-generational references are the general theory this whole architecture is built from, in any language, in any era. V8 is simply one very well-engineered, very real instance of applying it.

    This is a useful pattern to notice in general: a huge fraction of what looks like "V8-specific cleverness" in a real engine turns out to be a well-known general GC technique, applied carefully. Learning the general theory first — like you just did — means the next real engine's GC section of documentation reads as "oh, that's generational collection" rather than as an unfamiliar wall of proper nouns.

    08 — Side by Side

    Minor Collection vs. Major Collection

    Worth having the two collection types side by side — the entire architecture exists to make you pay the row on the right as rarely as possible.

    PropertyMinor Collection (Young Gen)Major Collection (Old Gen)
    Region scannedSmall nursery onlyEntire old generation — large
    FrequencyVery often — nursery fills fastRare — old gen fills slowly
    Typical pause lengthShortLonger, unless incremental/concurrent
    Root set usedGlobals + stack/registers + remembered setGlobals + stack/registers (full scan anyway)
    Needs write barrier data?Yes — to catch old→young referencesNo — it scans everything directly anyway
    What survives moves toStays young, or gets promoted to old genStays in old gen (may be compacted in place)

    ✅ What Generational GC Buys You

    Collection cost tracks the (small) amount of work actually needed most of the time, instead of the (large) total heap size every single time — because the generational hypothesis says most heap objects don't need re-checking on every pass in the first place.

    ⚠️ What It Costs You

    A small, constant per-write overhead everywhere in the program (the write barrier check), extra bookkeeping memory for the remembered set, and real implementation complexity — getting the barrier wrong is a correctness bug, not just a slowdown, exactly as shown above.
    🌱
    Nursery collections are cheap and constant
    🏛️
    Old-gen collections are rare and expensive
    ✍️
    Every pointer write pays one small barrier check
    🎯
    Correctness depends on the barrier catching every case

    None of this is free architecture — it's a deliberate, load-bearing trade, engineered specifically around one empirical fact about how real programs allocate memory. Change that fact (a workload that allocates almost nothing short-lived, for instance) and the whole justification for splitting the heap this way weakens considerably. Generational GC isn't universally correct engineering — it's extremely good engineering for the specific, extremely common shape of allocation behavior the hypothesis describes.

    09 — Quick Reference

    Glossary & Key Terms

    Generational Hypothesis
    The empirical observation that most allocated objects die almost immediately, while a small minority survive a long time — the premise this entire architecture is built to exploit.
    Young Generation (Nursery)
    The small heap region where every new object is allocated, collected frequently because it's cheap to scan.
    Old Generation (Tenured Space)
    The larger heap region holding objects that have proven long-lived, collected rarely with a thorough full pass.
    Promotion (Tenuring)
    Moving an object from the young generation into the old generation after it survives some number of minor collections.
    Minor GC
    A collection that scans only the young generation (plus the remembered set as extra roots) — fast, frequent.
    Major GC
    A full collection of the old generation — slow, infrequent, and the reason generational splitting exists in the first place.
    Write Barrier
    Bookkeeping code inserted on every pointer write that detects when an old-generation object starts referencing a young-generation object.
    Remembered Set
    The set of old-generation objects (or memory regions) flagged by the write barrier as containing a reference into the young generation — used as extra roots during minor GC.
    Cross-Generational Reference
    A pointer from an object in one generation into another — specifically old-to-young references are the ones a minor collection would otherwise miss.
    Card Marking
    A common optimization of the remembered set: dividing old-gen memory into fixed-size "cards" and marking a whole card dirty on a write, instead of tracking individual objects.
    🎯 The One-Sentence Summary
    Because most objects die almost immediately, splitting the heap into a small, frequently-collected young generation and a large, rarely-collected old generation makes the common case cheap — but doing that safely requires a write barrier to catch the one case a young-only scan would otherwise miss: an old object that has just started pointing at a young one.

    Across this three-lesson arc: mark-and-sweep gave you the correctness rule (reachability), reference counting showed you a different, locally-computed approximation of that same rule and exactly where it breaks (cycles), and generational GC showed you how to make the correct rule fast in practice without sacrificing correctness — provided you're careful about exactly where the boundary you drew can be silently violated. That's the whole shape of garbage collector design: pick a rule, then earn back the performance the naive version of that rule leaves on the table.
