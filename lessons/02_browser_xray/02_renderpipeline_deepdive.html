The Map You Already Have

💡 Not Actually a Straight Line
Real browsers don't run these seven stages once per page and stop. HTML parsing is streaming and incremental. Layout, Paint, and Composite can each re-run independently, on their own, for a single frame, without redoing the stages before them — that's the entire point of splitting them apart. Treat the pipeline below as "the full path a brand-new element takes," and treat each section as also explaining "and here's when this one stage alone gets re-triggered."
01 — Stage One

Parsing HTML: Bytes → Tokens → DOM

Somewhere a response body is arriving as a raw byte stream. Before anything resembling a "tag" exists, the browser has to decide a character encoding (from the Content-Type header, a <meta charset>, or a BOM), decode those bytes into a stream of Unicode characters, and only then start looking for structure. HTML parsing happens in two tightly coupled phases: tokenization and tree construction, and — unlike almost everything else in this pipeline — it happens incrementally, as bytes arrive off the network, not after the whole document is downloaded.

  1. TokenizerA state machine (literally specified as a state machine with states like "Tag open state," "Attribute name state," "Comment start state") consumes the character stream one character at a time and emits a stream of tokens: StartTag, EndTag, Character, Comment, DOCTYPE. It doesn't know or care about document structure yet — it's just recognizing lexical shapes.
  2. Tree ConstructionA second state machine consumes that token stream and builds the actual DOM tree, maintaining a "stack of open elements" and switching between insertion modes ("in head," "in body," "in table," "in select"...) that determine where each new token's node gets attached, and when a tag needs to be auto-closed or ignored.
  3. DOM TreeThe result: a live, structured, in-memory tree of node objects — the thing document.querySelector actually walks, and the input the Style stage needs.

Here's the part that makes HTML parsing genuinely weird compared to almost any other parser you've written: real-world HTML is catastrophically malformed, constantly, and the browser is contractually required to render it anyway. Unclosed <p> tags, a <table> with stray text before the first <tr>, mis-nested tags like <b><i>text</b></i> — a strict parser would just throw an error and stop. A browser can't. Nobody would ever see the New York Times homepage if "one malformed tag halts the page" were the rule.

This is exactly why the WHATWG HTML5 parsing specification exists, and why it's unusually, almost obsessively precise: it doesn't just define valid HTML, it defines a byte-for-byte-identical error-recovery algorithm that every conformant browser must implement — precisely what to do when a start tag shows up in an insertion mode that doesn't expect it, precisely when an open <p> gets implicitly closed, precisely how misnested formatting elements get reconstructed. Before this spec (pre-2008-ish), every browser guessed differently, and "works in one browser, breaks in another" was routine. Standardizing the recovery behavior, not just the happy path, is what let broken-but-common markup render the same way everywhere.

🧵 Why This Stage Can Be Incremental
Tree construction can attach a node to the DOM the instant tokenization produces it, because a DOM node's identity and position in the tree don't depend on tags that haven't arrived yet. That's what lets the browser start building structure — and even kick off a Style/Layout/Paint pass on the parts it already has — before the full response has finished downloading. CSS, as you're about to see, cannot get away with this trick.
What about <script>? A parser-blocking <script> tag (no async/defer) pauses tree construction entirely — the browser must run it before continuing, since that script might call document.write() and change what comes next. To hide the cost, Chromium runs a preload scanner alongside the paused main parser: a lightweight scan ahead in the raw bytes that spots upcoming <img>, <link>, and <script src> references and kicks off their network requests early, even though tree construction itself is stalled.

One more piece of error recovery worth naming, because it quietly reaches all the way into the Layout stage later: a missing or malformed <!DOCTYPE html> doesn't just fail to validate — it drops the whole document into quirks mode. Tree construction still succeeds (that's the point of the recovery algorithm), but a flag gets set on the document that later changes how the box model itself is computed: quirks-mode table cells and form controls size percentage heights differently, and historically even folded border/padding into declared width the way box-sizing:border-box does today, before that was ever a real property. A single missing line at the top of the file is technically an HTML-parsing decision, but its consequences don't show up until Layout, three stages later.

02 — Stage Two

Parsing CSS: Rules → CSSOM

CSS gets tokenized and parsed too — into the CSSOM (CSS Object Model), a tree of stylesheet objects, each holding rules, each rule holding a selector and a list of declarations. Structurally it looks like a cousin of the DOM parse you just read about. Behaviorally, it's almost the opposite.

The one-sentence reason HTML parsing can emit structure the instant it sees a tag. CSS parsing can't emit a final answer for any single rule until it has seen every rule that could possibly compete with it. Cascading and specificity are global questions — "which of these seventeen rules wins for this element" requires the whole stylesheet to already be sitting in memory.

Think about what "resolving the cascade" actually requires. Two selectors of equal specificity: the one that appears later in the stylesheet wins — you can't know which is later until you've parsed the whole file. An !important declaration three rules down can override something you already parsed. A @media block might not even apply until the viewport changes. Multiple <link> stylesheets and inline <style> blocks all get merged into one cascade, in document order. None of that can be decided rule-by-rule as bytes stream in — it's fundamentally a "read everything, then compute" problem, unlike tree construction, which is fundamentally a "react to each token as it arrives" problem.

"Specificity" itself is just a tie-breaker the CSSOM has to be able to compute for any two competing rules, and it's mechanical, not fuzzy: count inline styles, then ID selectors, then class/attribute/pseudo-class selectors, then type/element selectors, and compare those counts left to right like digits in a number.

Specificity as a 4-digit tuple (inline, #ids, .classes/[attrs]/:pseudo-classes, elements) e.g. #nav .item.active → (0, 1, 2, 0) beats .item → (0, 0, 1, 0), regardless of source order — but two rules with an identical tuple fall back to "whichever was parsed later wins," which is exactly the rule that requires the whole stylesheet to be in memory first.

The practical consequence: CSS is render-blocking. The browser deliberately withholds first paint until the CSSOM for the page's stylesheets is complete, specifically to avoid a "flash of unstyled content" — briefly showing your black-on-white unstyled markup before the real design snaps in a moment later. It's a deliberate correctness trade-off: better to delay the first frame slightly than show the user a wrong one.

CSS can even block JavaScript. If a parser-blocking <script> appears after a pending <link rel="stylesheet">, the browser holds that script until the CSSOM is ready too — because the script might synchronously call getComputedStyle(), and handing back stale or partial style data would be a correctness bug, not just a performance one. This is sometimes called the "CSSOM blocks JS" rule, and it's why a page with a slow stylesheet can visibly delay script execution that has nothing to do with styling at all.
⚡ Same Shape, Different Physics
Both parsers turn text into a tree. But HTML's tree-construction algorithm is built around "never stop, always recover, emit structure as you go," while CSS's cascade algorithm is built around "never finalize an answer until you've seen everything." Same pipeline slot, opposite constraints — which is exactly why they're two separate stages instead of one shared "parse everything" pass.
03 — Stage Three

Style: Where DOM Meets CSSOM

Now the browser walks the DOM tree, and for every single node, asks the CSSOM: "given every rule that could apply to you, plus whatever you inherit from your parent, what is your actual computed style?" — final resolved values for color, font-size, display, margin, all of it, no more cascading left to do. The output is the render tree (Chromium's Blink engine calls its version the "layout tree," but the concept is the same): a tree of the boxes that will actually need geometry and pixels.

And "the boxes that will actually need geometry and pixels" is a deliberately narrower set than "the DOM." Three kinds of nodes never make it into the render tree at all, or make it in a strange half-state — and the exact rules here are one of those classic distinctions that sound like trivia but are actually 100% mechanistic.

🚫 display:none

The node and its entire subtree are excluded from the render tree. Not measured. Not painted. Takes up zero space — as if it doesn't exist for layout purposes at all. Toggling it back on is expensive: the browser has to build render-tree entries for it from scratch and run Layout again.

👻 visibility:hidden

The node is in the render tree. It gets full, real geometry computed during Layout — an actual x, y, width, and height, reserving space exactly like a visible box. It's simply skipped during the Paint stage: the box is real, the ink just never hits it.

That's the whole distinction, stated mechanistically instead of as a memorized fact: display:none is a Style-stage decision (never enters the tree that Layout even looks at). visibility:hidden is a Paint-stage decision (fully present through Layout, invisible only once Paint runs). Toggle visibility and you can skip Layout entirely and go straight to a cheap Paint-only update; toggle display and you're paying for Layout every time, because the shape of the tree itself just changed.

Two more housekeeping notes on this stage: non-visual DOM nodes (<head>, <script>, <meta>, <title>) simply never get render-tree entries — there's nothing to draw. And generated content from ::before/::after pseudo-elements gets synthesized into the render tree right here, even though it never existed as a DOM node at all.

🎯 The Interview Question, Answered Properly
"What's the difference between display:none and visibility:hidden?" isn't really asking you to memorize two CSS properties — it's asking whether you understand that the render tree is a filtered, computed structure sitting between the DOM and Layout, and that different kinds of invisibility get filtered at different points in that pipeline.
04 — Stage Four

Layout: Computing Exact Geometry

The render tree now knows what exists and roughly how it's styled. It still doesn't know where anything is or how big it is in actual pixels. That's Layout's entire job (also called Reflow): walk the render tree and compute a concrete box — an x, a y, a width, a height — for every single node, on every axis, recursively.

The Box Model, Refresher border-box width = content width + padding(L+R) + border(L+R) margin sits outside the box's own size — it doesn't count toward the element's width, but it absolutely counts toward how much space it reserves next to its siblings. box-sizing:border-box folds padding and border into your declared width instead of adding on top of it — same property name, two different arithmetic paths through this exact stage.

Why is this expensive enough to get its own dedicated, heavily optimized engine subsystem (Blink's is called LayoutNG)? Because Layout is very rarely "visit each box once, write down its size, move on." Boxes depend on each other.

  • A percentage width (width:50%) can't be resolved until the parent's width is known — which might itself depend on its parent, chaining upward.
  • Flexbox has to first measure every flex item's natural ("hypothetical") size, then run a second pass distributing free space or negative space across the group according to flex-grow/flex-shrink — genuinely two-plus passes over the same items before a final size is settled.
  • CSS Grid is worse: track sizes can mix fixed lengths, percentages, auto, and fr units, and resolving auto/intrinsic tracks may require measuring the content of cells that live in other, not-yet-sized tracks — the spec's own track-sizing algorithm runs in explicit, ordered passes for exactly this reason.
  • Text is the classic ripple case: widen a container by ten pixels, a line of text that used to wrap at word 8 now wraps at word 9, the box gets one line shorter, its height shrinks, and every sibling positioned below it in normal flow now needs to move up.

That ripple is the real reason Layout is feared. Changing one box's size isn't a local edit — it can force recomputing the position of dozens of unrelated-looking boxes below and around it. In the worst case (a change near the root, or a change to something everything else depends on, like the page's base font size loading in late), the browser has no choice but to lay out the entire tree again. And unlike Paint or Composite, which can farm work out to other threads, Layout in Chromium is a synchronous, essentially single-threaded operation running on the renderer's main thread — the same thread your JavaScript runs on.

⚠️ This Is the Stage JS Can Accidentally Force, On Demand
Layout doesn't only run on the browser's own schedule. If your JavaScript reads a geometry property — offsetHeight, offsetWidth, getBoundingClientRect(), getComputedStyle() — right after it just wrote a style change, the browser cannot answer with stale numbers. It has to run Layout synchronously, immediately, right there in your script, before your next line executes. Hang onto that fact — it's the entire mechanism behind "layout thrashing" in the Jank section below.
05 — Stage Five

Paint: Geometry Becomes Draw Commands

Every box now has an exact size and position. Paint's job is to figure out what ink goes where — but critically, Paint does not produce pixels. It produces a list of drawing instructions: "fill this rectangle with this color," "draw these text glyphs at these coordinates in this font," "draw this image here," "draw a blurred shadow along this edge." Chromium builds this as a display list (backed by its graphics library, Skia, as a PaintRecord) — a vector-ish, resolution-independent recipe for pixels, not pixels themselves.

Order matters enormously here, and it's not arbitrary — it follows the stacking-context painting order originally defined back in CSS2.1's Appendix E: background and borders first, then block-level children, then floats, then inline content, then positioned/z-indexed elements on top. Get this order wrong and semi-transparent, overlapping, or z-indexed elements render incorrectly — so Paint effectively re-walks the tree in a carefully specified visual order, not simply the DOM's document order.

✅ Paint-Only Changes Are Already Cheap
Anything that changes ink without changing geometry — color, background-color, box-shadow, border-radius, toggling visibility — skips Layout entirely and only needs to re-run from Paint onward. That's meaningfully cheaper than a Layout-triggering change, even before Compositing enters the picture at all.
06 — Stage Six

Compositing: Skipping Layout and Paint on Purpose

Certain elements get pulled out of the normal paint flow and promoted onto their own layer — a separate texture the GPU can manipulate independently. Once an element has its own layer, it gets painted into its own texture once — and then, for every subsequent animation frame, the compositor can transform or fade that already-painted texture using nothing but GPU matrix math.

  • A CSS transform (2D or 3D) applied to the element.
  • An opacity value that's actively being animated or transitioned.
  • will-change: transform or will-change: opacity — an explicit author hint asking the engine to promote ahead of time, before the animation even starts, so the first frame isn't the one paying the promotion cost.
  • Native video (<video>) and <canvas> elements, which already need their own composited surface for decoding/drawing reasons.
  • position:fixed elements in some engines, so they can stay pinned during scroll without repainting.

This also ties directly back to the paint-order rules from the last section: elements that create a new stacking context (non-static position with a z-index, an opacity below 1, a transform, filter, or will-change) were already being painted as a self-contained visual unit by Paint's stacking-context algorithm. Compositing takes that same self-contained unit and, for the promotion triggers above, gives it its own literal GPU texture instead of just its own slot in paint order.

This is the actual mechanism behind the single most-repeated piece of web performance advice on the internet: animate transform and opacity, never top/left/width/height. Not a style guideline — a pipeline consequence.

✅ transform / opacity (promoted layer)

Paint happens once, up front. Every animation frame after that: Layout — skipped. Paint — skipped. The compositor thread just re-positions or re-blends an existing GPU texture. Pure GPU math, every frame, off the main thread.

❌ top / left / width / height

Each of these is a geometry property. Changing it on any frame forces the full climb back to the top: Layout re-runs (geometry actually changed) → Paint re-runs (new draw commands needed for the new geometry) → Composite re-runs. Every single frame, on the main thread, competing with your JavaScript for the same 16.7ms.

And this is exactly why the renderer keeps a compositor thread that's architecturally separate from the main JS thread. Once a frame's layers are painted and handed off, the compositor thread owns purely GPU-side work — scrolling, transform/opacity animation, pinch-zoom — and none of that requires asking the main thread for anything. So if your JavaScript is stuck running a long synchronous task, scrolling and transform-based animations can often keep gliding at 60fps anyway, because the compositor never had to wait in the main thread's task queue to begin with. It's the browser-internals version of "don't put your slow work on the thread other things depend on."

Layers aren't free, though. Every promoted layer needs its own GPU texture memory. Slap will-change: transform on hundreds of elements "just in case" and you can trigger "layer explosion" — enough GPU memory pressure that you actually make things slower, not faster. Promotion is a scalpel, not a global setting.
07 — Stage Seven

Rasterization: Vectors Finally Become Pixels

Everything up to this point — the display list, the layer textures the compositor arranges — has still been resolution-independent vector instructions. Somewhere, something has to actually walk those draw commands and fill in real pixel values in a real bitmap. That's rasterization, and it's deliberately treated as its own separate stage, done on its own threads, because it's the most raw-computation-heavy part of the whole pipeline.

Two things make rasterization efficient enough to happen dozens of times a second. First, tiling: instead of rasterizing an entire layer as one giant bitmap, Chromium chops it into small tiles (roughly 256×256px), rasterizes only the tiles that actually changed or that are near the viewport, and prioritizes tiles the user is about to scroll into view. Second, this work increasingly happens directly on the GPU (Skia's GPU-backed rasterizer) rather than the CPU, and even when it's CPU-side, it runs on dedicated raster worker threads — not the main thread, not even strictly the compositor thread — so it can proceed in parallel with everything else.

Once tiles are rasterized into real GPU textures, they still need to physically reach the GPU process to be composited into the final on-screen frame. And here's where this page reconnects directly with the multi-process wall from Browser X-Ray: the renderer process is sandboxed and cannot touch the graphics driver itself, so how does it hand over potentially thousands of draw operations per frame without drowning in per-call IPC overhead?

Not one IPC message per draw call Renderer writes a stream of GPU commands into a shared-memory command buffer → GPU process reads directly from that same shared memory, no per-command Mojo round trip This is the identical shared-memory trick Browser X-Ray flagged in the pixel pipeline overview — at 16.7ms per frame, paying full IPC serialization/validation cost for every individual rectangle and glyph would blow the budget before a single pixel landed on screen. A shared ring buffer turns "thousands of tiny messages" into "one memory region both sides already trust the shape of."
🧩 The Full Trust Boundary, End to End
The renderer paints and rasterizes as much as it safely can inside its own sandbox, but the literal final act of putting pixels on your physical screen is still gated behind the one process trusted to speak to the graphics driver — the GPU process. Even rasterized tiles cross that same privileged/unprivileged wall Browser X-Ray described; they just cross it via a shared command buffer instead of a one-off message, because this particular door gets used thousands of times a second.
08 — Zooming Out

Browser X-Ray already told you a renderer keeps a single-threaded, cooperative main thread plus a separate compositor thread. Read down that grid and a pattern jumps out: the first four pipeline stages (Parse HTML, Parse CSS, Style, Layout) and half of the fifth (Paint recording) are all stuck on the same single main thread as your JavaScript. Only once you cross into Compositing does work escape onto threads — and eventually a whole separate process — that your JavaScript can't block. That's not an accident of implementation; it's the entire architectural reason "promote it to a layer and only animate transform/opacity" is the escape hatch power users reach for.

💡 The Real Reason the Advice Works
"Animate transform/opacity" isn't a style-guide superstition — it's a request to move your work off the one thread that's also running your JavaScript, DOM updates, and Layout, and onto the two things downstream of it (compositor thread, GPU process) that keep going even when the main thread doesn't.
09 — When It All Goes Wrong

Jank: Missing the 16.7ms Deadline

60fps means a new frame is expected roughly every 16.7 milliseconds (1000ms ÷ 60). Inside that budget the renderer has to handle input, run any due JavaScript, recompute Style, run Layout if geometry changed, record Paint if pixels changed, composite, rasterize, and submit the frame — realistically closer to 10ms of actual headroom once OS and browser overhead are accounted for. Miss the deadline and the compositor has nothing new to show, so it re-shows the previous frame. That's a dropped frame. String enough of them together and you get jank — the stutter you can feel even if you can't name which stage caused it.

Two causes account for the overwhelming majority of real-world jank, and each one points at a specific stage you now understand in detail.

Cause 1 — Long JS Tasks Blocking the Main Thread

Remember the renderer's main thread is single-threaded and cooperative — it runs one task from its queue to completion before picking up the next, no preemption. Style, Layout, and Paint-recording all live on that same thread. A JavaScript task that runs for 40ms straight — a big .sort(), an unoptimized loop, a synchronous JSON parse of a huge payload — doesn't just delay other JavaScript. It delays Style, Layout, and Paint from even starting, because the thread they need is still busy. The frame deadline doesn't pause and wait; it just gets missed.

Cause 2 — Forced Synchronous Layout ("Layout Thrashing")

You already saw the mechanism in the Layout section: reading a geometry property forces Layout to run synchronously, right then, if a style write happened first. The genuinely damaging version of this is a loop that alternates writes and reads:

the classic mistakefor (const box of boxes) {
  box.style.width = box.style.width + 1 + 'px';  // WRITE — invalidates layout
  const h = box.offsetHeight;                    // READ — forces sync Layout, right now
}
// N boxes → N full synchronous Layout passes, one per iteration

Every iteration writes a style, then immediately reads a geometry property — and because the browser refuses to hand back a stale number, it has no choice but to run a full, synchronous Layout pass on every single loop iteration, instead of once for the whole batch. This is exactly what "layout thrashing" means: turning an O(1) Layout cost into an O(n) one, entirely by interleaving reads and writes in the wrong order. Batch it the other way — read everything first, then write everything — and the browser only needs one Layout pass at the end, because nothing invalidated geometry until every read was already done.

▶ Naive loop vs. batched loop — same 6 boxes, watch the frame-budget cost
🛠️ The Fix Is Always the Same Shape
Never interleave a geometry read right after a style write inside a loop. Read every value you need first (getBoundingClientRect() for everyone), then write every style change. Libraries like FastDOM exist purely to enforce this batching automatically, and requestAnimationFrame callbacks give you a natural checkpoint to do reads at the start of a frame and writes at the end.

11 — Quick Reference

Glossary & Key Terms

Tokenizer
The HTML parser's first-stage state machine, turning a decoded character stream into a stream of tags, attributes, and text tokens — no tree structure yet.
DOM
The tree of live node objects built by tree construction from the HTML token stream; the structural half of what Style needs.
CSSOM
The tree of parsed stylesheet rules; can't be finalized incrementally because cascade/specificity resolution needs the entire stylesheet.
Render Tree
DOM + CSSOM merged into the set of boxes that will actually need geometry and pixels; excludes display:none subtrees entirely.
Box Model
Content, padding, border, and margin — the four concentric regions Layout uses to compute an element's footprint and reserved space.
Layout (Reflow)
Computing the exact x, y, width, and height of every render-tree box; expensive because one box's size can ripple into many others'.
Display List
The ordered list of vector draw commands (rects, glyphs, shadows) Paint records per layer — still resolution-independent, not yet pixels.
Compositor Layer
A separate GPU-backed texture given to elements with transform/opacity animation or will-change, so they can be re-positioned without re-running Layout or Paint.
Rasterization
Converting vector paint records into actual pixel bitmaps, done tile-by-tile, often on dedicated raster threads or the GPU.
Command Buffer
A shared-memory region the renderer writes GPU commands into so the GPU process can read them directly, avoiding one IPC message per draw call.
Layout Thrashing
Forcing repeated synchronous Layout passes by interleaving style writes and geometry reads inside a loop instead of batching them.
Jank
Visible stutter from a dropped frame — the pipeline missed the ~16.7ms budget, usually from a long main-thread JS task or layout thrashing.
