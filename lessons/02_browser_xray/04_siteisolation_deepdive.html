00 — Quick Recap

The Wall You Already Know About

From Browser X-Ray, you already know the shape of it: Chrome's browser process is the trusted "kernel," renderer processes are the sandboxed "user space," and Mojo IPC is the guarded door between them. What that story glossed over is that before 2018, the renderer side of that wall was drawn more loosely than you'd think — Chrome would often let multiple unrelated websites share a single renderer process for efficiency, most commonly when a page embedded a cross-origin iframe (think an ad network's frame, or a "Log in with…" widget, sitting inside someone else's page). Same process, same address space, two strangers who never agreed to room together.

🪆 Where This Picks Up
This isn't a new wall — it's a crack found in the old one. Everything below assumes you already know why renderer processes are sandboxed from the OS's point of view. The question this page answers is narrower and sharper: why wasn't "different origins, same process" good enough, and what specific 2018 event made Chrome's architects decide it never could be again?
01 — The Old Assumption

One Process, Two Strangers

Here's why sharing a renderer process across origins seemed perfectly safe for years: JavaScript, as a language, simply has no instruction for reading arbitrary memory. There's no pointer arithmetic, no *(address), no way to say "give me the bytes sitting 400KB to the left of this object." Every JS object is accessed through a reference the V8 engine hands you — never a raw address. If origin A's JavaScript and origin B's JavaScript both happened to be running inside the same OS process, A's code still had no language-level way to reach across and read B's variables, B's cookies-in-memory, or B's decrypted response bodies, even though they were, physically, bytes sitting in the same address space a few thousand cells apart.

That's the crucial detail: the isolation between origins A and B was entirely a software-level guarantee, enforced by V8's own rules about what JavaScript is allowed to express — not a hardware-level guarantee enforced by the OS's page tables. The OS process boundary (the one that stops your Chrome tab from reading your Spotify app's memory) simply wasn't being used between origins inside one renderer, because nobody thought it needed to be. The language sandbox was assumed to be sandbox enough.

The pre-2018 assumption
"As long as JS can't address another origin's memory directly, it doesn't matter if that memory is technically reachable in the same process. The language itself is the wall."
→
Why that assumption failed
Reading memory doesn't require an instruction that says "read." It just requires a way to infer a byte's value from something observable — like how long an operation takes.
This is the same trust boundary as file permissions. Two OS-level processes owned by the same user can technically both read a world-readable file — the OS lets them, on purpose. Pre-2018 Chrome's stance on cross-origin sharing was similar: "the platform's own rules make this fine," right up until someone finds a way to read data the platform's rules were never designed to protect against in the first place.
🧠 Software Isolation vs. Hardware Isolation, Precisely
Software-level isolation: a set of rules enforced by a program (here, V8's JS semantics) that a well-behaved caller can't violate no matter what it writes. Hardware-level isolation: a physical boundary enforced by the CPU and OS (page tables, process address spaces) that a caller can't violate even if it tries something the software layer never anticipated. Pre-2018 cross-origin sharing rented only the first kind. Spectre is exactly the "tries something the software layer never anticipated" case.
The pre-2018 isolation formula origin A cannot read origin B's memory ⇐ V8's language rules forbid JS from expressing a raw memory read Holds exactly as long as "read memory" only means "execute an instruction the language rules cover." Spectre reads memory without ever executing one.
02 — The Attack

What Spectre Actually Broke

In January 2018, Google's Project Zero and academic researchers jointly disclosed Spectre (alongside a related attack, Meltdown) — a class of attacks against a performance feature almost every modern CPU relies on: speculative execution. To go fast, your processor doesn't wait around to find out whether a branch (an if) will actually be taken — it guesses, and starts executing down the predicted path before it knows the guess is right. If the guess was wrong, the CPU throws away the speculative results and rewinds... architecturally. But it turns out the rewind isn't perfectly clean.

Specifically: while speculatively executing down a mispredicted path, the CPU can end up touching memory it never should have accessed — and that memory access leaves a side effect in the CPU's cache, even after the speculative instructions themselves are discarded. An attacker who can't read that memory directly can still ask, indirectly: "is this particular address now sitting in the fast cache, or not?" Timing how long it takes to re-access various addresses (a technique like Flush+Reload) turns "in cache or not" into a single leaked bit. Repeat that across a byte's worth of possible values, and you've reconstructed a byte you were never supposed to see — one bit of hidden information smuggled out per timing measurement, entirely through a side channel with no data-read instruction anywhere in sight.

conceptual gadget// simplified illustration of the shape of a Spectre-style gadget —
// not exploit code, just the pattern that makes the leak possible
function maybeRead(index) {
  if (index < array1.length) {          // (1) branch the CPU will *speculate* past
    let secretByte = array1[index];      // (2) speculatively read OOB memory
    let touch = array2[secretByte * 4096]; // (3) leak it into the cache as an index
  }
}
// after misprediction is discovered, (2) and (3) are architecturally undone —
// but array2's cache-line state is NOT undone. Timing which offset of
// array2 is now fast to access reveals secretByte, one guess at a time.
⚠️ The Point That Matters Most
Spectre did not find a bug in V8's sandbox. It did not find a way for JavaScript to violate the language's own rules. Ordinary, rule-following, spec-compliant JavaScript — just written in a particular shape, and given a sufficiently precise timer — could use the CPU's own speculative-execution behavior to read bytes that JavaScript's language semantics say it should never be able to see. The attack lives one full layer below the sandbox: it broke a promise the hardware made, not a promise the language made. No amount of auditing V8's source code fixes a hardware promise that isn't kept.

And that's precisely why "different origins sharing one renderer process" stopped being safe overnight. It was never protected by an OS-level wall to begin with — only by V8's language rules. Spectre is an attack that specifically operates underneath language rules. So if origin B's secret data was sitting anywhere in the same process's address space as origin A's malicious JavaScript, Spectre gave A a route to it that had nothing to do with what the JS sandbox permitted.

03 — The First Response

Band-Aids Before the Structural Fix

Site Isolation wasn't the very first thing Chrome shipped after the January 2018 disclosure — it was the thing that took longest to finish, because reassigning process boundaries across the entire browser is a large, invasive change. In the meantime, engineers reached for faster, narrower mitigations that could ship within days, aimed directly at the mechanics of the attack rather than at the architecture around it. Two mattered most.

First: value poisoning inside V8 itself. The idea is to make the JIT-compiled code for a bounds check speculation-safe — inserting logic so that even if the CPU speculatively executes past an array bounds check, the value it reads gets masked into something harmless (often just zero) before it can be used as an index into a second array, which is the step that actually leaks a bit into the cache. It doesn't stop speculation from happening; it tries to make speculation's result useless to an attacker. Second: timer degradation — deliberately making performance.now() (and similar high-resolution timers) coarser and jittered, since every version of this attack fundamentally depends on measuring a timing difference small enough to distinguish a cache hit from a cache miss. Chrome dropped performance.now()'s resolution from roughly 5 microseconds down to 100 microseconds, with added jitter, specifically to make that measurement noisier.

Software Mitigation

Value Poisoning & Timer Jitter

100µs
Shippable in days. Targets the mechanics of one specific gadget shape and one specific measurement technique. Raises the difficulty of a leak, but doesn't remove the underlying shared address space — new gadget shapes and finer-grained timing tricks (a second thread as a makeshift clock, for instance) kept the cat-and-mouse game alive.
Structural Fix

Site Isolation

1 / site
Took longer to ship (full rollout in Chrome 67, mid-2018). Doesn't care what shape the gadget takes or how the timer is built, because it removes the thing every variant of the attack needs: another origin's secret sitting anywhere inside the same address space.
💡 Why Ship Both, Not Just the Real Fix
Value poisoning and timer jitter are defense in depth, not a substitute for Site Isolation — they buy time and narrow the attack surface for the many cases Site Isolation can't fully cover on its own (data still shared within one origin's own process, for instance, isn't helped by putting other origins elsewhere). This is the same layered-defenses instinct as an OS shipping both stack canaries and non-executable memory pages: neither one alone is the whole answer, and a hardware-level attack rarely has a single clean patch.

What actually changed between the two runs? Nothing about the JavaScript changed — the same timing-probe technique runs in both. What changed is what's reachable. In the shared case, both origins' data live in one address space, so a hardware-level side channel has something to find. In the isolated case, the OS's own page tables mean origin A's process doesn't have origin B's bytes mapped in at all — there's nothing there to leak, timing probe or not.
05 — Chrome's Response

Moving the Wall from Software to Hardware

Chrome's actual fix was not a cleverer JavaScript sandbox — there isn't a purely software patch for a hardware side channel that runs underneath the language. Instead, Chrome shipped Site Isolation as a default-on feature (Chrome 67, mid-2018, after early testing the previous year): it became much stricter about which pages are allowed to share a renderer process, generally enforcing one renderer process per site — not per tab, per site (roughly, scheme plus registrable domain), so that even a cross-origin iframe embedded inside another page gets pulled out into its own process, communicating back to the parent frame only via IPC. These pulled-out iframes even got their own name: out-of-process iframes, or OOPIFs.

  • 1. A navigation or embed requests a new site. Whether it's a top-level navigation or an iframe, Chrome checks which "site" the content belongs to.
  • 2. Chrome compares that site against the current process's site. If they match, the content can stay. If they don't, isolation kicks in.
  • 3. A separate renderer process is spawned (or reused) for the foreign site. That process gets its own OS-level address space, enforced by the OS's real page tables — the same mechanism keeping your Chrome tab out of your Spotify app's memory.
  • 4. Cross-origin iframes become OOPIFs. The parent page still visually contains the iframe, but under the hood it's compositor magic stitching together output from a genuinely separate process.
  • 5. The result: nothing to leak. A Spectre-style probe running in origin A's process can still read "everything in this address space" — it's just that origin B's data was never mapped into that address space to begin with.

    • Notice what this move actually is, structurally: Chrome took the exact hardware-enforced guarantee it already relies on for the browser-process/renderer-process split — the OS's page-table wall between processes — and applied that same guarantee one layer deeper, between origins that used to cheerfully share a process. It didn't invent new isolation technology. It just stopped trusting a software-only boundary for a job that, post-Spectre, only a hardware-enforced boundary can actually do.

    ❌ Before Site Isolation

    Renderer processes were assigned roughly per tab. A page and its cross-origin iframes (ad frames, embedded widgets, third-party login forms) could easily share one process. Isolation between them existed only at the JavaScript-language level.

    ✅ After Site Isolation

    Renderer processes are assigned per site. Cross-origin iframes become OOPIFs in their own process. Isolation between origins is now enforced by the OS's page tables — the same hardware-backed wall that separates unrelated applications on your machine.
    🔑 The One-Sentence Version
    Site Isolation doesn't make Spectre impossible inside a process — it makes Spectre irrelevant across origins, by guaranteeing there's no longer any other origin's data sitting inside the process a Spectre probe could reach.
    The pattern, reused one more layer down Ring 0 / Ring 3: hardware wall between OS kernel and user processes
    Browser process / renderer process: OS-process wall reused for browser "kernel" vs. "user space"

    06 — The Opt-In Layer

    COOP, COEP, and the SharedArrayBuffer Story

    Site Isolation solved the "different sites, different processes" half of the problem. But Spectre also had an immediate, uncomfortable side effect on a specific web API: SharedArrayBuffer, which lets JavaScript share a raw block of memory between the main thread and a Web Worker for high-performance code (WebAssembly threading, for instance). A SharedArrayBuffer, by design, is exactly the kind of shared memory a Spectre-style timing probe loves — and worse, JS running against it could build extremely precise custom timers out of nothing but a second thread incrementing a shared counter, sidestepping any timer-precision defenses the browser tried to add elsewhere. So in January 2018, browser vendors — Chrome included — disabled SharedArrayBuffer across the board, in every renderer, as an emergency stopgap, while the real fix (Site Isolation) was finished and rolled out.

    SharedArrayBuffer eventually came back — but not unconditionally. It's now gated behind a pair of HTTP response headers a site must opt into: Cross-Origin-Opener-Policy (COOP) and Cross-Origin-Embedder-Policy (COEP). Set both correctly and your page becomes what the platform calls cross-origin isolated (you can check this yourself with self.crossOriginIsolated) — which is really a site formally promising the browser "I am not casually sharing my process with unrelated cross-origin content," in exchange for which the browser trusts it with SharedArrayBuffer, high-resolution timers, and other APIs that are only safe once process-level isolation is guaranteed rather than assumed.

    📌 Why an Opt-In, Not a Default
    The browser can't unilaterally guarantee your page is cross-origin isolated — that depends on what other sites choose to do when embedding or opening it. COOP/COEP exist because "isolated enough for dangerous APIs" isn't a property the browser alone can promise; it's a property the whole surrounding web of pages has to agree to. The header pair is the web platform's way of making that agreement explicit and checkable, instead of assumed.
    🖼️ A Concrete Case: The Ad-Network Iframe
    Picture a news site embedding a third-party ad iframe, pre-2018. Nothing malicious required — the ad network's script and the news site's own script could easily have ended up in the very same renderer process, sharing an address space, purely because Chrome's old process-assignment heuristics didn't see a reason to split them. Post-Site-Isolation, that ad iframe is now, by default, an OOPIF running in its own process — so even a fully compromised ad-network script has no shared address space left to run a timing probe against.
    Notice the shape of this fix, too. It's the COOP/COEP pattern that WebAssembly threading libraries and browser-based video/audio codecs now routinely require just to function — if you've ever seen a library README say "requires cross-origin isolation," now you know exactly which January 2018 chain of events put that requirement there.
    07 — Zooming Out

    Every Layer Asks the Same Question

    Step back across everything this series has covered and a single question keeps reappearing at every layer, just rephrased: who is allowed to share a room with whom? CPU rings answered it by drawing a hardware line between privileged and unprivileged instructions. The OS answered it by drawing a hardware-backed line between kernel and user-space processes. Chrome's original architecture answered it by drawing that same line again, in software, between the browser process and renderer processes. And for years, "which website's JavaScript gets to share a room" was answered by a much weaker, purely linguistic promise — until Spectre proved that promise didn't hold once the question moved from "can your code address that memory" to "can your code learn that memory's contents by any means at all."

    ⚡
    CPU rings: hardware wall, instruction-level
    🖥️
    OS processes: hardware wall, page-table-level
    🌐
    Browser/renderer: software wall, reusing OS processes
    🔓
    Pre-2018 origins: software wall, language-level only

    Site Isolation is the sharpest example yet of that boundary needing to be redrawn — not because anyone found a bug, but because an assumption about what "sharing an address space safely" even means quietly stopped being true, for every process on every machine with a speculating CPU, all at once. The fix, tellingly, wasn't a new idea. It was the oldest idea in this entire series — put untrusted things in genuinely separate processes, and let the hardware, not a promise, keep them apart — applied one layer further than anyone had previously bothered to draw it.

    🎯 The One-Sentence Summary
    Spectre didn't break the rules of the JavaScript sandbox — it broke the CPU's unspoken promise that speculative work leaves no trace, and because pre-2018 Chrome relied on the language sandbox alone to keep origins apart inside a shared process, Chrome's only real fix was to stop sharing processes at all, moving the origin-vs-origin wall from software policy to the same OS-enforced, hardware-backed boundary that has separated processes all along.
    08 — Quick Reference

    Glossary & Key Terms

    Speculative Execution
    A CPU performance technique: guessing the outcome of a branch and executing ahead of that guess before it's confirmed, rewinding architecturally if wrong.
    Spectre
    A 2018-disclosed class of attacks that uses speculative execution plus a cache-timing side channel to read memory a program's own language rules say it shouldn't be able to see.
    Side Channel
    A way to infer secret information from an observable side effect (like timing) rather than from a direct, sanctioned data read.
    Cache Timing Attack
    Measuring how long it takes to access memory to infer whether that memory is already sitting in the fast CPU cache — and from that, infer secret data indirectly.
    V8
    Chrome's JavaScript engine. Enforces the language-level rules (no raw pointers, no arbitrary memory reads) that used to be considered sufficient isolation between origins sharing a process.
    Site Isolation
    Chrome's post-Spectre architecture change: one renderer process per site by default, so cross-origin content is never loaded into the same address space, closing off what a same-process side channel could reach.
    OOPIF
    Out-of-process iframe — a cross-origin iframe rendered in its own separate renderer process, then visually composited back into the embedding page.
    SharedArrayBuffer
    A JS API for raw memory shared between threads. Briefly disabled browser-wide after Spectre's disclosure because it made high-precision timing attacks trivially easy.
    COOP
    Cross-Origin-Opener-Policy — an HTTP header a page uses to promise it won't share a browsing-context group with unrelated cross-origin windows.
    COEP
    Cross-Origin-Embedder-Policy — an HTTP header requiring embedded cross-origin resources to explicitly opt into being loaded, enabling stronger isolation guarantees.
