You already know the renderer process runs Blink and V8, that your JavaScript is sandboxed, and that it all cooperates through an event loop. Fine — but what actually happens between the moment a <script> tag's bytes land in memory and the moment your code is genuinely, measurably fast? V8 has an entire internal pipeline for that, with names — Ignition, TurboFan, Scavenger — and a set of surprisingly mechanical reasons behind the performance advice you've heard a hundred times. Let's crack it open.

00 — Where We Left Off

That "V8 JS Engine" Pill You Skipped Past

Back in Browser X-Ray, we mapped the renderer process the same way we mapped everything else: a sandboxed, per-site worker running Blink and V8, forbidden from touching the filesystem or the network directly, cooperating with the rest of the page through a single-threaded event loop. That was the right altitude for that story — the renderer was one box on a much bigger diagram, and "V8 JS engine" was just a feature pill stuck inside it, sitting quietly next to "DOM" and "Blink engine."

We're done zooming out. This time we zoom into that one pill. V8 isn't a black box that mysteriously "runs JavaScript" — it's a genuinely engineered system with a parser, two different compilers, a garbage collector with two heaps, and a caching scheme so central to real-world JS performance that half the "best practices" you've absorbed from blog posts are really just this one mechanism, described secondhand.

📦 What's Already In Your Head
You know a renderer sandboxes JS, that fetch() secretly goes through IPC, and that one blocking JS loop freezes a tab's whole UI because there's only one main thread. Good — hang onto all of that. Nothing here contradicts it. We're just opening the V8 box that was sitting inside the renderer the whole time.
01 — Before Any Code Runs

V8 Barely Reads Most of Your Code (At First)

Here's a question worth sitting with: a typical page loads a JS bundle full of functions — event handlers, utility helpers, framework internals, code for UI states the user may never even reach. What fraction of those functions actually get called during a typical page visit? Often a small one. V8's parser is built around exactly that observation.

When V8 first sees your script, it doesn't fully parse every function body into a complete syntax tree up front. Instead it runs a fast, cheap pre-parse pass: just enough to find where each function starts and ends, record its parameter list and which outer variables it references, and confirm the syntax isn't broken. It deliberately does not build the full internal representation a function needs to actually execute.

Only when a function is actually invoked for the first time does V8 go back and do the full parse — building the real abstract syntax tree needed to generate bytecode. This is called lazy compilation, and pre-parsing is what makes it cheap: V8 doesn't have to re-scan the whole file from scratch when a function finally runs, because pre-parsing already recorded exactly where it starts, where it ends, and what it closes over.

⚡ Why Laziness Is a Load-Time Optimization
Fully parsing every function into an AST is memory-hungry and CPU-hungry — ASTs are large, pointer-heavy structures, and building one for a function that never runs is pure waste. Multiply that by every unused utility function in a large bundle, and full eager parsing would visibly slow down page load for zero benefit. Pre-parsing lets V8 pay only a small "is this syntactically valid, and where are the boundaries" tax up front, and defer the expensive work to the moment it's actually justified — exactly when a function is called.
Why the parens sometimes matter. You may have seen JS minifiers wrap function expressions in extra parentheses, like (function(){...})(). Older V8 heuristics used that pattern as a hint that a function was about to be invoked immediately, nudging it to skip straight past the lazy path. Modern V8's heuristics have gotten smarter about detecting immediately-invoked functions on their own, but the underlying lazy/eager split those tricks were exploiting is still exactly the mechanism described above.
02 — First Time a Function Runs

Meet Ignition, the Bytecode Interpreter

So a function just got called for the first time, got fully parsed into an AST — now what? You might assume V8 immediately compiles it down to optimized native machine code, the fastest possible form. It deliberately does not. That would be a trap.

Optimized native machine code is large, slow to generate, and — this is the key part — only pays for itself if the function runs enough times to amortize the cost of producing it. Most functions on a typical page run once, or a handful of times, and then never again. Eagerly compiling everything straight to optimized machine code would mean spending real CPU time and real memory generating fast code for functions that will never benefit from being fast.

So instead, V8's first tier is Ignition: a register-based bytecode interpreter. The AST is compiled into a compact bytecode format — a much smaller, simpler instruction set than native machine code — and Ignition just interprets that bytecode directly, instruction by instruction, the way a simple virtual machine would.

✅ Why Bytecode First

Bytecode is fast and cheap to generate, and dramatically more compact in memory than native machine code for the same logic. For a function that runs once, this is close to the best possible deal: quick to produce, quick enough to execute once.

⚠️ The Cost

Interpreting bytecode instruction-by-instruction is inherently slower per-execution than running native machine code directly — there's dispatch overhead on every single instruction. Fine for code that runs a few times. Not fine for a loop that runs 500,000 times.

That tension — cheap-but-slower vs. expensive-but-faster — is exactly why V8 doesn't stop at Ignition. But there's a second job Ignition is quietly doing while it interprets: it watches. Every time a bytecode instruction touches a value, Ignition records what kind of value it actually was — was that + adding two small integers, two floats, or concatenating two strings? Was that property read on an object shaped like this, or shaped like that? This running record is called type feedback, and it's the fuel for the next tier.

The deal Ignition strikes Interpret now (slower per-run, cheap to start) + quietly record what types actually show up so a smarter compiler can specialize later — only for the functions that turn out to deserve it.
03 — When Code Gets "Hot"

TurboFan: Compiling for the Types You've Actually Seen

V8 keeps an invocation counter (roughly — call frequency and loop iteration counts both factor in) on every function running through Ignition. Once a function crosses a "this is being called a lot" threshold, V8 marks it as hot and hands it off to TurboFan, V8's optimizing JIT (just-in-time) compiler.

TurboFan's job isn't to compile a generic, handles-anything version of your function. It compiles a version specialized for the exact types Ignition's type feedback already observed. If every call so far added two small integers, TurboFan doesn't emit code that checks "is this a number, a string, an object, or something else?" on every single execution — it emits lean native machine code that assumes both operands are small integers, skips the generic type-dispatch machinery entirely, and runs dramatically faster as a direct result.

This is what "speculative" optimization means: TurboFan is betting that the future will look like the recent past. It bakes that bet directly into the machine code it generates, complete with lightweight guard checks that verify the bet is still true on every call — and an escape hatch for when it isn't. That escape hatch is deoptimization, and it's important enough to get its own section shortly.

🎲 "Speculative" Is the Load-Bearing Word
TurboFan doesn't prove your function will always receive small integers — it can't, JavaScript is dynamically typed. It speculates, based on what Ignition actually observed, and generates machine code that is only correct under that assumption. The guard checks it inserts are cheap precisely because they only need to confirm the bet, not re-derive the answer from scratch the way a fully generic implementation would.
04 — The Shape Underneath Every Object

Hidden Classes: Why Property Order Isn't Free

Quick question: are {x: 1, y: 2} and {y: 2, x: 1} the same to V8? They have the same keys, the same values — surely it doesn't matter which order you wrote them in? It matters a lot, and understanding why is the single most useful piece of V8 mental model you can carry around.

JavaScript objects are dynamic — properties can be added, removed, reordered at runtime. A naive implementation would store every object's properties in something like a hash map, and look up a value by hashing the property name every single time. That's correct, but slow — far slower than the fixed-offset memory reads that make languages like C or Java fast at field access.

V8's answer is hidden classes (internally, V8 calls them Maps — an unfortunate name collision with JS's own Map, so most explanations, including this one, say "hidden class" or "shape"). Every object secretly carries a pointer to a hidden class that encodes exactly one thing: the precise sequence of property names that were added to it, and the fixed memory offset where each one lives.

Same final key set, different hidden class (C2′ ≠ C2), because the transition chain that produced it was different. Code optimized for C2 doesn't apply to a C2′ object — V8 has to treat them as genuinely different shapes.

JSfunction Point(x, y) {
  this.x = x;   // every Point: hidden class transition C0 → C1
  this.y = y;   // every Point: hidden class transition C1 → C2
}
const a = new Point(1, 2);   // shares hidden class C2
const b = new Point(3, 4);   // shares hidden class C2 — fast!

const c = {};
c.y = 2;             // different order
c.x = 1;             // ends up on a DIFFERENT hidden class than a/b

Deleting a property is worse than reordering it. delete obj.x can't just be "undo a transition" — V8 typically has to bail the object into a much slower dictionary mode, where it genuinely does fall back to hash-map-style property storage, giving up the fixed-offset fast path entirely for that object.

🛋️ The Furniture Floor-Plan Analogy
Think of a hidden class as a moving company's floor plan for a specific apartment layout: "couch goes in the northwest corner, bookshelf against the east wall." If every apartment on the same floor plan gets furnished in the same order, the movers can work from memory — no need to ask where anything goes, they just know the offset. Build the same furniture in a different order, or rip a piece out later, and you no longer have "the same floor plan" — the movers have to stop, look around, and figure out the layout from scratch. That look-around is the slow path.
05 — Remembering the Last Lookup

Inline Caches, and What Deoptimization Really Means

Hidden classes explain how property lookups can be fast. Inline caches (ICs) are the mechanism that actually makes a specific line of your code fast, by remembering its own recent history.

Every property access in your code — every obj.x — is a specific bytecode location V8 can attach a small cache to. The first few times that exact line executes, V8 records: "the object here had hidden class C2, and the property I wanted lived at offset 0." The next time that same line runs, V8 checks whether the incoming object still has hidden class C2. If yes, it skips the lookup entirely and reads offset 0 directly. No search, no hashing — just a pointer-plus-offset memory read, guarded by one cheap comparison.

IC StateWhat It MeansSpeed
MonomorphicThis call site has only ever seen one hidden classFastest — direct offset read
PolymorphicThis call site has seen a small number (roughly up to 4) of distinct hidden classesStill fast — checks a short list
MegamorphicThis call site has seen many different hidden classesSlow — falls back to a generic, dictionary-style lookup

This is also exactly the feedback TurboFan reads when deciding how to specialize a hot function — a monomorphic call site gives TurboFan one shape to bet on; a megamorphic one gives it nothing worth speculating on, so it either compiles slower generic code for that spot or declines to optimize it as aggressively.

So what happens when the bet is wrong?

Say TurboFan already compiled an optimized, specialized version of add(a, b) that assumes both arguments are small integers — because that's all it ever saw during profiling. Now your code calls add("1", "2"). The optimized machine code's guard check notices immediately: this isn't the type it was built for.

V8 can't patch the optimized code on the fly to also handle strings — it was generated assuming integers, all the way down. So it does the only safe thing: it throws the optimized code away, jumps back into the slower Ignition interpreter at the equivalent point in the bytecode, and lets the function keep running correctly, just slowly again. This is called deoptimization, or "bailing out."

▶ Same pipeline canvas, one step further — trigger a bailout

The function then has to re-warm from the interpreter — Ignition re-collects type feedback, and if the function gets hot again, TurboFan may recompile it, this time accounting for the wider range of types actually seen (or sometimes giving up on aggressive specialization for that call site entirely). A function that deoptimizes repeatedly on the same call site can end up permanently stuck running slower, unoptimized code, because V8 concludes further optimization attempts aren't paying off.

🚫 Where the "Best Practices" Actually Come From
"Don't change an object's shape after creation" and "keep a function's argument types consistent" aren't arbitrary style rules — they're direct consequences of the two mechanisms above. Change an object's shape and you force a hidden-class transition, potentially turning a monomorphic call site polymorphic or megamorphic. Feed a hot, type-specialized function a new type and you trigger a deoptimization, discarding real compiled work and forcing V8 to re-profile from scratch. The advice is downstream of the mechanism, not the other way around.
06 — Cleaning Up After Your Code

Garbage Collection: Two Heaps, Two Speeds

Every object, closure, and array your JS creates has to live somewhere, and eventually most of it becomes unreachable garbage that needs reclaiming. V8's garbage collector is built around one empirical observation, sometimes called the generational hypothesis: most objects die young. A temporary object created inside a loop iteration, a short-lived closure, an intermediate array in a .map().filter() chain — the overwhelming majority of allocations become garbage almost immediately, while a small minority (a cache, a long-lived DOM-backing object, application state) survive for the life of the page.

V8 splits its heap in two to exploit that pattern directly.

Young Generationsmall, frequent
A small nursery region where every new object is born. Collected extremely often by the Scavenger, a fast copying collector that only has to scan a small area of memory.
semi-space copyminor GC
Old Generationlarge, infrequent
Where objects that survive a couple of young-generation collections get promoted. Collected far less often by a mark-sweep-compact collector, because scanning and compacting the whole thing is genuinely expensive.
mark-sweep-compactmajor GC

The Scavenger works by splitting the young generation into two halves — "from-space" and "to-space." When it runs, it copies every still-reachable (live) object out of from-space into to-space, then instantly treats the entire rest of from-space as reclaimed, no per-object bookkeeping required. Because most young-generation objects are already dead by the time a scavenge runs, this copy is cheap: it does work proportional to the (small) number of survivors, not the (large) number of objects that were allocated.

An object that survives being copied a couple of times gets promoted into the old generation, on the theory that anything living this long is probably going to stick around. The old generation is collected with a full mark-sweep-compact pass: mark every reachable object starting from GC roots, sweep away everything unmarked, and periodically compact survivors together to avoid fragmenting memory into unusable slivers. This is more thorough — and more expensive — which is exactly why it runs far less often, and why V8's Orinoco project spent years making as much of this old-generation work as possible run incrementally and concurrently on background threads, specifically to keep it from blocking your main thread for long stretches.

Why generational GC beats one naive full-heap collector Cost of a naive full-collection ∝ total live heap size, every single time
Cost of a young-gen scavenge ∝ number of survivors in a small nursery, most of the time Doing the cheap, frequent thing (scavenge) far more often than the expensive, thorough thing (mark-compact) is what keeps average GC pause times low.
So does GC ever still cause visible jank? Yes — a large old-generation mark-compact pass, even partially concurrent, can still show up as a stutter, especially on memory-pressured pages with lots of long-lived objects. This is part of why keeping large, long-lived object graphs lean is real performance advice, not superstition: it's directly shrinking the amount of work the less-frequent, more-expensive collector has to do.
07 — Ordering Everything V8 Runs

The Event Loop, Precisely

You already know a renderer's main thread runs one task at a time from a queue. Here's the precise version, because "a queue" is actually two queues with a strict ordering rule between them, and that rule explains a piece of behavior every JS developer eventually trips over.

Call Stacksynchronous
Where currently-executing function calls live, innermost on top. While anything is on the stack, nothing else runs — this is the "one slow loop freezes the tab" stack.
Microtask Queuedrains fully, every time
Holds Promise .then()/.catch()/.finally() callbacks and queueMicrotask() callbacks. Once the call stack empties, V8 runs every microtask currently queued — including new ones added by microtasks that just ran — before doing anything else.
Macrotask Queueone per loop turn
Holds setTimeout/setInterval callbacks, I/O completion callbacks, and UI events. After the microtask queue is fully empty, the event loop takes exactly one macrotask, runs it, then checks the microtask queue again before taking the next.

That "microtasks always fully drain before the next macrotask" rule is not a minor implementation detail — it's a hard guarantee of the spec, and it's why Promise.resolve().then(...) reliably beats setTimeout(fn, 0) to the console, no matter how fast the timer is.

JSconsole.log('A');

setTimeout(() => console.log('B'), 0);   // → macrotask queue

Promise.resolve().then(() => console.log('C')); // → microtask queue

console.log('D');

// Output, every single time: A, D, C, B

Walk it in order: 'A' and 'D' run synchronously on the call stack, back to back — the setTimeout and .then() calls only schedule work, they don't run it yet. Once the synchronous code finishes and the call stack is empty, V8 checks the microtask queue first, always — so 'C' runs. Only once the microtask queue is completely empty does the event loop pull the next macrotask off its queue — so 'B' runs last, even though it was scheduled with a 0ms delay and scheduled before the promise callback.

🔁 Why "0ms" Never Meant "Immediately"
setTimeout(fn, 0) has always meant "put fn on the macrotask queue as soon as possible," never "run fn right now." It still has to wait for the current synchronous code to finish and the entire microtask queue to fully drain. A page that queues a lot of promise work can genuinely starve macrotasks for a while — which is also why an infinite chain of .then() calls that keeps re-queueing itself can freeze a tab just as effectively as an infinite while loop, without ever technically blocking on one giant synchronous call.

Ignition vs. TurboFan

Worth having the two tiers side by side, because the tradeoff between them is the entire reason V8 has two compilers instead of one.

✅ The Whole Point, in One Line
Ignition makes sure every function is cheap to start running. TurboFan makes sure the small minority of functions that run a lot become genuinely fast — without ever paying that optimization cost for the majority that don't. Two tiers exist because "cheap to start" and "fast once hot" are different engineering goals, and no single compiler design is great at both simultaneously.
09 — Tying It All Together

Why This Actually Changes How You Write Code

None of this is trivia. Once the mechanism clicks, a whole set of JS performance folklore stops being "rules someone told me" and starts being "obvious consequences of how V8 is built."

🏗️
Construct objects with the same property order every time
🎯
Keep a hot function's argument types consistent
🧹
Avoid deleting properties — set to undefined instead if you must
⏱️
A microtask storm can starve timers exactly like a sync loop

"Give objects a consistent shape" means: give V8's hidden-class machinery a chance to reuse work across your instances instead of fragmenting into dozens of near-identical shapes. "Don't polymorphize hot functions" means: don't force a monomorphic inline cache into polymorphic or megamorphic territory, and don't hand TurboFan's speculative guess a reason to deoptimize. "Watch out for long promise chains blocking timers" means: remember the microtask queue always drains completely before the next macrotask, every single time, no exceptions.

🎯 The One-Sentence Summary
V8 gets JavaScript fast by being lazy where laziness is free (pre-parsing, Ignition's cheap bytecode), by speculating aggressively where speculation is safe (TurboFan's type-specialized machine code, backed by hidden classes and inline caches), and by cleaning up memory at two different speeds for two different kinds of garbage — and almost every piece of "JS performance advice" you've heard is just a human-readable description of one of those mechanisms.
10 — Quick Reference

Glossary & Key Terms

Pre-Parse
V8's fast first pass over a script: finds function boundaries and checks syntax without building a full AST, so full parsing can be deferred until a function is actually called.
Lazy Compilation
Deferring the expensive full parse + bytecode generation of a function until the moment it's first invoked, instead of doing it eagerly for the whole script up front.
Ignition
V8's baseline tier: compiles the AST to compact bytecode and interprets it directly. Cheap to start, slower per-execution than optimized machine code.
TurboFan
V8's optimizing JIT compiler. Compiles hot functions into native machine code specialized for the types observed during interpretation.
Type Feedback
The record Ignition keeps, per call site, of what types of values actually flowed through it — the raw data TurboFan speculates from.
Hidden Class (Map / Shape)
V8's internal descriptor for an object's exact property layout: the sequence properties were added in, and the fixed memory offset of each one.
Hidden Class Transition
Moving from one hidden class to another as a property is added, typically triggered on the first few objects built by a given constructor — later objects of the same shape reuse the resulting chain.
Inline Cache (IC)
A per-call-site cache remembering "the last hidden class(es) seen here, and where the property lived" — monomorphic (1 shape), polymorphic (a few), or megamorphic (many, slow).
Deoptimization ("Bailout")
Discarding a TurboFan-optimized, type-specialized function when it receives a type its compiled guess didn't cover, falling back to Ignition and re-profiling.
Generational Hypothesis
The empirical observation that most objects die young — the design premise behind splitting the heap into young and old generations.
Scavenger
V8's young-generation collector: a fast, frequent copying collector that moves live objects between two semi-spaces and reclaims the rest instantly.
Microtask Queue
The queue holding Promise callbacks and queueMicrotask() work, guaranteed to fully drain before the event loop runs the next macrotask.
