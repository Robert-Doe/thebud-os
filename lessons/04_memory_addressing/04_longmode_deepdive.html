01 — Setting the Stage

A Feature's Slow Fade

Segmentation wasn't always a formality. Rewind to the original 16-bit 8086, and segment:offset addressing was load-bearing in the most literal sense: a "segment" really was a relocatable 64KB window into memory, real-mode code juggled "near" and "far" pointers explicitly, and C compilers of the era offered entire named memory models — tiny, small, medium, compact, large, huge — just to describe how aggressively a given program depended on crossing multiple segments. There was no paging unit yet to fall back on. Segmentation wasn't a first line of defense; it was the entire translation story.

The two base modules in this series pick the story up at its second act: 32-bit protected mode, where segmentation stays a real, active participant — Base and Limit genuinely computed with, on every access — while paging joins as a second, independent stage running in series right after it. Two circuits, both doing real work, wired together into the MMU.

This article covers the third act. In 64-bit long mode, segmentation's translation duties get switched off in silicon for four of the six segment registers, and paging inherits the entire job alone. What follows is exactly how that happened, and exactly which two registers didn't get the memo.

1️⃣ 16-bit Real Mode

Segmentation is the only translation mechanism in existence. Segment:offset addresses real, 64KB-windowed memory directly — no paging unit exists yet to share the job.

2️⃣ 32-bit Protected Mode

Segmentation and paging both run, genuinely in series, each doing real translation and protection work — the subject of the two base modules this article builds directly on.

3️⃣ 64-bit Long Mode

Segmentation's translation role is hardware-disabled for CS/SS/DS/ES; paging translates alone; FS/GS survive for one narrow, genuinely useful job.
02 — The Big Change

Segmentation Gets Neutered

Ask this question honestly: in 64-bit long mode, what does the CPU actually do with the Base and Limit fields sitting inside a CS, SS, DS, or ES segment descriptor? The answer isn't "not much." The answer is nothing. The processor does not read them. For those four segment registers, long mode hardwires the behavior as if every descriptor said Base = 0 and Limit = unbounded, regardless of what bits are actually sitting in the GDT slot the selector points to.

This is not an OS convention, the way Linux's flat 32-bit segments were a convention. A convention is something software chooses and could, in principle, choose differently. This is different: it's a hardware mandate. Even if a kernel deliberately loaded a CS descriptor with Base = 0xdeadbeef and a Limit of 4KB, a 64-bit CPU running that code segment in long mode would silently disregard both fields and behave exactly as if Base were 0 and the segment were unbounded. There's no way to opt back in for CS, SS, DS, or ES. The hardware simply stopped implementing the feature for them.

💡 You Can Write Whatever You Want In the Descriptor — the CPU Won't Read It
This is the detail that trips people up. In 32-bit protected mode, a "flat" segment (Base=0, Limit=4GB) is a choice the OS makes, and the segmentation unit still genuinely performs that addition and that limit check on every access — it just happens to add zero. In 64-bit long mode for CS/SS/DS/ES, the circuitry that would perform that addition and that check has been switched off entirely. Base and Limit for those four registers become dead fields — present in the descriptor's bit layout for backward compatibility, invisible to the address-translation logic.

One more piece falls with it: segment-limit protection. In 32-bit protected mode, an offset larger than the segment's Limit field triggers a general-protection fault — the segmentation unit was, among other things, a bounds checker. In long mode, for CS/SS/DS/ES, that bounds check is gone too. There's no limit to violate because there's no limit being enforced. That includes the Stack Segment: 32-bit protected mode could rely on the SS Limit field to catch a stack that grew past its allotted segment and raise a fault right there. Long mode gives that up completely — a 64-bit OS instead relies on guard pages (unmapped pages sitting just past the end of a stack region) and lets the ordinary paging fault mechanism catch an overrun instead. One less job for segmentation, one more job quietly absorbed by paging.

Register-by-register, here's exactly what long mode keeps versus discards. Notice DS and ES don't just lose their translation power — 64-bit code frequently doesn't bother loading them with anything meaningful at all, since every instruction that would have used them can simply address memory without a segment override and get the identical (Base=0) result.

So why not just remove CS/SS/DS/ES entirely? Instruction-set compatibility. Decades of encoded instructions still carry segment-override prefixes, and MOV to/from a segment register is still a legal, decodable instruction. Removing the registers would mean removing instructions — breaking encodings rather than just disabling a behavior. It was far cheaper, silicon-wise, to keep the registers and the descriptor format intact and simply stop consulting Base/Limit for four of the six.

One more small consequence worth naming: since DS and ES no longer contribute anything to address translation, 64-bit code frequently just loads them with a null selector — index 0, pointing nowhere meaningful — and leaves them alone for the rest of the program's life. That's not laziness; it's a completely valid, deliberate simplification once you know the descriptor those selectors would have pointed to wouldn't have been consulted for its Base or Limit anyway.

03 — The Arithmetic, Simplified to Nothing

Why the Formula Collapses

Put the two base modules' central formula next to what long mode actually computes, and the shift is almost anticlimactic:

32-bit protected mode — the segmentation unit's real job Linear Address = Descriptor.Base + Offset Base comes from a real GDT/LDT lookup, and really gets added.
64-bit long mode — CS, SS, DS, ES Linear Address = 0 + Offset = Offset Base is hardwired to zero. The segmentation "stage" of the MMU pipeline is now a pass-through wire.

Why would Intel and AMD's engineers do this? Because the entire reason segmentation's Base field existed in the first place was to solve a capacity problem — relocating a program, or a segment, somewhere inside a limited flat address space smaller than what programs collectively wanted to address. A 32-bit offset alone only reaches 4GB, so if you needed more structure than "one 4GB pile," Base gave you a second knob to work with.

A 64-bit offset does not have that problem. Sixty-four bits of raw offset already reaches 16 exbibytes — a number so far past any RAM you could physically rack into a data center, let alone screw into a desktop, that "relocate a segment to make room" stopped being a real engineering constraint. There was no capacity left to solve. So rather than requiring every OS on earth to remember to manually set up four flat, Base=0 segments the way Linux already did by convention in 32-bit mode (as covered in the GDT article's Linux section), the hardware designers simply hard-disabled the feature for CS/SS/DS/ES. Nobody can get it wrong, because nobody can turn it back on.

There's a pleasing bit of historical closure here, too. Segmentation's Base field was originally one of the tools programs used for relocation — loading the same code at different addresses in memory without recompiling it. Modern position-independent executables (PIE binaries, the default on virtually every current Linux distribution) still need exactly that capability, for exactly the same reason it always mattered plus a new one: ASLR (Address Space Layout Randomization) deliberately loads a program at a different address on every run, to make memory-corruption exploits harder to aim. Segmentation isn't involved in any of that anymore — it's paging, and the OS's own loader, picking a fresh base address and building fresh page tables to match, with zero help from a Base register that no longer does anything.

🧠 Long Mode Made Mandatory What Linux Already Chose Voluntarily
Remember the GDT article's punchline: Linux, even back in 32-bit protected mode, defined its kernel and user code/data segments with Base=0 and a Limit spanning the whole address space — deliberately flattening segmentation down to "cover everything, differ only by privilege level" and leaning on paging for real protection. Long mode takes that same design decision and bakes it into the silicon for CS/SS/DS/ES. What was smart OS engineering in 1998 became a hardware guarantee by the time 64-bit chips shipped in the 2000s.
04 — The Exception That Survived

FS and GS: Still Armed

Here's the twist: two of the six segment registers were not neutered. FS and GS keep a genuinely live, genuinely usable Base field in long mode — the CPU really does compute FS.base + Offset when you address memory through them. Everything you just read about CS/SS/DS/ES simply doesn't apply to these two.

Why keep exactly two? Because a real problem remained that a flat, single global address space can't solve on its own: every thread in a process needs some private storage that the exact same compiled code can reach without a lookup, a branch, or a pointer chase. That's Thread-Local Storage (TLS), and FS/GS are the hardware feature that makes it essentially free.

And why two registers rather than just one? Because userspace TLS and the kernel's own per-CPU bookkeeping both want exactly this trick, at the same time, without stepping on each other. On Linux, userspace claims FS for __thread variables while the kernel reserves GS (swapped via SWAPGS) for its own per-CPU structures — one register per "customer," each fully independent of the other, both riding the identical hardware mechanism.

🚫 CS / SS / DS / ES

Base forced to 0. Limit ignored. In long mode these four registers do no translation work at all — they're along for the ride.

✅ FS / GS

Base field is real, per-register, and settable independently for every thread. The last surviving piece of "real" segmentation math in 64-bit mode.

Here's the mechanism, concretely. Compilers implement a C/C++ __thread global (or C11 _Thread_local) by emitting memory operands like mov rax, fs:[0x28] or mov rax, gs:[0x28] — the exact same machine instruction, byte for byte, in every thread's copy of the compiled binary. What differs between threads isn't the instruction — it's the value sitting in the FS (or GS) base register at the moment that instruction executes. Thread A might have FS.base = 0x00007f1a40008700; Thread B, running the identical instruction stream, might have FS.base = 0x00007f1a40009d00. Same offset, same opcode, two completely different physical variables — resolved automatically, in hardware, with zero branching and zero table lookups.

The one segment-math formula that still really runs Linear Address (FS- or GS-relative) = FS.base (or GS.base) + Offset Identical shape to the old Descriptor.Base + Offset formula — just restricted to two registers, and loaded per-thread instead of per-segment-type.

There isn't just one way to load that base value, either — three mechanisms exist, layered across roughly two decades of hardware, and a modern OS typically supports all three so it keeps working on older silicon:

WRFSBASE / RDFSBASEfastest
Ring-3 instructions, available since Ivy Bridge when the kernel sets CR4.FSGSBASE. Userspace sets its own FS/GS base directly — no syscall, no ring transition, ideal for user-mode threading libraries and JIT runtimes that create threads constantly.
WRMSR on IA32_FS_BASE/GS_BASEuniversal fallback
The original mechanism, present on every 64-bit x86 chip. WRMSR is a Ring-0-only instruction, so this path always requires a trip into the kernel — slower, but guaranteed to exist even on the oldest AMD64/Opteron-era silicon.
arch_prctl(ARCH_SET_FS, …)Linux syscall wrapper
The portable interface glibc actually calls — it picks whichever underlying mechanism (WRFSBASE or WRMSR) the running kernel and CPU support, so userspace code never has to care which generation of hardware it's on.

By convention (not hardware mandate — the silicon doesn't care which register an OS picks), Linux uses FS to point at each thread's Thread Control Block, which is where __thread variables and glibc's own per-thread state (like errno) actually live. Windows uses GS to point at the Thread Environment Block (TEB), the data structure the Win32 API and the CLR both lean on constantly. Two different operating systems, two different registers, one identical hardware trick underneath both.

How the Base Actually Gets Set

  1. A new thread is createdThe thread library (glibc's pthread_create on Linux, or the Windows thread-creation path) allocates a fresh block of memory to hold that thread's private TLS data.
  2. The kernel is asked to point FS or GS at itOn Linux, glibc issues the arch_prctl(ARCH_SET_FS, addr) syscall, handing the kernel the address of the new thread's TLS block. This is a privileged operation — user code can't just scribble into the base register from nowhere.
  3. ...or, on newer CPUs, userspace sets it directlySince Ivy Bridge, if the kernel has enabled CR4.FSGSBASE, userspace itself can use the WRFSBASE / WRGSBASE instructions (and read them back with RDFSBASE/RDGSBASE) without a syscall at all — faster thread setup, same underlying idea. The older, universally-supported fallback writes the base through Model-Specific Registers IA32_FS_BASE (MSR 0xC0000100) and IA32_GS_BASE (0xC0000101) via the privileged WRMSR instruction.
  4. Every later fs:/gs:-relative access just worksFrom that point on, any instruction the compiler emitted with an FS or GS prefix resolves through that thread's base value — automatically, on every core, with no per-access decision-making required from software.
GS's other job: SWAPGS. The kernel needs its own private "GS.base" too — pointing at per-CPU kernel data structures — but a thread's user-mode GS.base is obviously the wrong value to use once you're inside the kernel. The SWAPGS instruction, run automatically on kernel entry/exit (via syscall/sysret and interrupt handling), atomically swaps the live GS.base with a shadow value cached in the IA32_KERNEL_GS_BASE MSR. It's fast enough to run on every single system call — and, as a fun/alarming real-world footnote, a timing side channel in exactly this swap logic was the basis of the 2019 "SWAPGS" speculative-execution vulnerability (CVE-2019-1125), a reminder that even a register nobody thinks about is still real, exploitable hardware state.
💡 The Windows Mirror Image
Everything said above about FS on Linux has a near-exact Windows counterpart on GS. On 64-bit Windows, GS:[0x30] holds the linear address of the calling thread's own TEB (Thread Environment Block) — the same self-referential trick glibc uses, just at a different fixed offset and through the other register. The Windows API intrinsic __readgsqword(0x30), and the equivalent NtCurrentTeb() helper, both boil down to exactly one FS/GS-relative memory read. Same hardware feature, same one-instruction cost, two unrelated operating systems independently landing on the identical design.

The Same Idea, Three Spellings

None of this requires a programmer to ever type fs: or gs: by hand — the compiler emits the segment-prefixed instructions automatically, triggered by nothing more than a keyword on a variable declaration:

__threadGCC / Clang
The original GNU C extension: static __thread int counter; — one keyword, and every access to counter compiles down to an FS-relative load or store.
thread_local / _Thread_localC11 / C++11
The standardized spelling — thread_local int counter; — that compiles to the identical FS/GS-relative machine code on any conforming x86-64 compiler.
__declspec(thread)MSVC
Microsoft's pre-C11 equivalent on Windows — same underlying GS-relative mechanism, different keyword predating the C++11 standard.
05 — What's Left in the GDT

Segmentation's Second Job: Carrying the CPL

If Base and Limit are dead weight for CS/SS/DS/ES, does the GDT itself become pointless in long mode? No — and this is the piece that ties directly back to the GDT article's core lesson: a CS selector's DPL bits are still how the CPU tracks Ring 0 vs. Ring 3, even in 64-bit mode. Segmentation didn't disappear. It got demoted from "does address translation" down to "carries privilege level, and occasionally a TLS base."

A 64-bit OS still needs a valid Code Segment descriptor sitting in the GDT — one with the L bit (Long-mode) set to 1, marking it as a 64-bit code segment, and the D bit cleared, since operand size defaults are handled differently once L=1. The CPU still loads a CS selector into the CS register on every privilege transition, still reads that selector's RPL and the descriptor's DPL, and still uses exactly that comparison to decide whether code is currently executing as the kernel or as an ordinary user process. Every ring-crossing check from the segmentation article — GP faults on privilege violations, the whole DPL-vs-CPL-vs-RPL dance — is alive and well. It's just no longer doing anything about where memory physically is.

What's genuinely still computed on every access, long mode or not Current Privilege Level (CPL) = RPL / DPL of the active CS selector Untouched by the 64-bit transition — segmentation's protection role survives even though its translation role doesn't.
🧠 A Faster Path That Still Needs Real Descriptors
For speed, the actual ring transition on a system call doesn't always walk the full GDT lookup path you traced in the GDT article's worked example. The SYSCALL/SYSRET instruction pair — the normal way user code enters the kernel on x86-64 — loads CS and SS selector values straight out of a Model-Specific Register called IA32_STAR, rather than taking a far-call-style path through descriptor tables on every single call. But those selector values still name real slots in the GDT, whose L-bit, DPL, and other attributes still have to be set up correctly at boot — the shortcut is in how fast the selector gets loaded, not in whether a legitimate descriptor has to exist.

There's a second GDT resident that survives for a related reason: the Task State Segment (TSS). Its descriptor is still a real, system-type entry in the GDT — still needed even though x86-64 dropped hardware task-switching (the classic 32-bit feature of jumping between TSSs to context-switch) entirely. What's left of the TSS in long mode is narrower but essential: a 64-bit TSS holds RSP0, RSP1, RSP2 — the stack pointers the CPU should load automatically when a lower-privileged context traps or interrupts into Ring 0, 1, or 2 — plus up to seven Interrupt Stack Table (IST) entries, alternate known-good stacks that specific interrupt vectors (like a double fault or an NMI) can be forced onto regardless of whatever the current stack pointer happens to be doing.

Why IST matters more than it sounds like it should. If a stack overflow itself is what triggers a fault, handling that fault on the same (already-broken) stack is a recipe for a silent, unrecoverable failure. By pointing specific interrupt vectors at a dedicated IST stack instead of RSP0, the kernel guarantees the handler always starts from clean, known-good memory — a small mechanism, but the reason a kernel stack overflow reliably produces a diagnosable double-fault instead of just corrupting memory silently.
64-bit TSS FieldPurpose

So the honest one-line summary of this section: the GDT survives 64-bit long mode fully intact as a data structure — same 8-byte descriptor format, same gdtr register, same base + index×8 arithmetic you saw in the GDT article. What changed is how much of each descriptor the CPU actually uses. For CS, essentially just the privilege and long-mode bits. For SS, similarly little. For DS and ES, in 64-bit code, often nothing at all — many 64-bit OSes barely bother loading them meaningfully.

06 — A Detail Worth Knowing

How a CPU Actually Gets Into Long Mode

None of the previous four sections happen automatically the instant you power on a 64-bit chip. Every x86-64 CPU still boots up in the old 16-bit real mode your grandfather's BIOS used, and has to be walked, deliberately, step by step, through protected mode and finally into long mode by the bootloader and early kernel code — the exact same segmentation and paging machinery from the base modules gets used as scaffolding to bootstrap the very system that will later retire most of it.

This isn't theoretical — it's code you can go read. On a Linux box, the relevant handoff lives in the kernel's own boot assembly (historically arch/x86/boot/compressed/head_64.S and neighboring files): firmware hands off in 16- or 32-bit mode, GRUB or another bootloader gets the kernel image into memory, and the kernel's earliest instructions perform precisely the five-step dance below before a single line of "normal" 64-bit C code ever runs.

  1. Enable PAESet CR4.PAE = 1. Physical Address Extension was originally a 32-bit feature for reaching more than 4GB of RAM, but it's also a hard prerequisite for long mode's page-table format — long mode paging is, structurally, PAE paging with two extra levels bolted on top.
  2. Build an initial page-table hierarchyThe bootstrap code hand-constructs at least one PML4 table (and the PDPT/PD/PT beneath it) somewhere in RAM — typically an "identity map" where linear addresses equal physical addresses, just enough to keep execution coherent through the switch — then loads that table's physical address into CR3.
  3. Set IA32_EFER.LMEUsing the privileged WRMSR instruction, set the LME (Long Mode Enable) bit in the EFER (Extended Feature Enable Register) MSR. This doesn't turn long mode on yet — it tells the CPU "turn it on the moment paging is enabled."
  4. Enable pagingSet CR0.PG = 1. The instant paging switches on with LME already set, the CPU automatically sets IA32_EFER.LMA (Long Mode Active) and drops into compatibility mode — long mode is technically live, but the CPU is still executing 32-bit-style code, because CS still points at an old-style 32-bit code descriptor.
  5. Load CS with an L=1 descriptorA far jump (or equivalent) into a GDT code-segment descriptor with the L bit set to 1 is what finally flips execution into genuine 64-bit mode — full 64-bit registers, RIP-relative addressing, the works. This is the exact same L bit mentioned back in the CPL section, now shown as the actual on/off switch for 64-bit execution.

EFER carries a few other bits worth knowing by name, since kernel boot code sets several of them in the same breath as LME:

EFER BitNameWhat It Actually Does

8LMELong Mode Enable — the "arm it" bit the OS sets before turning paging on.

11NXENo-Execute Enable — lets page-table entries mark pages non-executable, the hardware backbone of W^X / DEP protections.
⚠️ Compatibility Mode Isn't a Third Address-Translation Scheme
Compatibility mode can feel like a mysterious in-between state, but it isn't a third translation mechanism to memorize — it's IA-32e paging (the same 4-level walk described next) running underneath what's still, instruction-encoding-wise, 32-bit-looking code, because CS hasn't been switched to an L=1 descriptor yet. It exists purely so a kernel can run brief stretches of legacy 32-bit boot/initialization code without tearing down paging first. Production 64-bit kernels spend virtually their entire runtime in true 64-bit mode, not compatibility mode.

Three genuinely different execution submodes exist inside "a 64-bit-capable CPU," and it's worth keeping them straight — the terminology gets thrown around loosely enough that it's easy to conflate them:

🕰️ Legacy Mode

EFER.LMA = 0. Ordinary 16-bit real mode or 32-bit protected mode. Full segmentation from the base modules applies exactly as written — Base and Limit are real, and paging (if on at all) is 2- or 3-level.

🌗 Compatibility Mode

EFER.LMA = 1, but the active CS descriptor has L=0. Paging is already 4-level IA-32e paging, but code executes with 32-bit-style semantics — a deliberately brief stepping-stone, not a destination.

⚡ 64-bit Mode

EFER.LMA = 1 and the active CS descriptor has L=1. Full 64-bit registers, RIP-relative addressing, and everything described in this article — where a 64-bit OS spends essentially all of its runtime.
A brief history of the name. AMD designed this 64-bit extension first and called it AMD64 (originally "x86-64"), shipping it in 2003 on the Opteron server line. Intel licensed the same instruction set rather than shipping an incompatible alternative, initially under the name "IA-32e" and later "EM64T," before eventually settling on the marketing name Intel 64. Different names, same architecture — a rare case of a full 64-bit ISA extension arriving from the "smaller" of the two x86 vendors first.
07 — Who Actually Does the Work Now

Paging Takes Over Completely

If segmentation isn't translating addresses anymore, something has to be — and the answer is the same paging unit from the base module, just scaled up dramatically. Where 32-bit protected mode typically used two-level paging (a Page Directory and a Page Table), 64-bit long mode uses four-level paging (Intel calls it IA-32e paging): a linear address gets sliced into five pieces, four of them table indices and one a final byte offset.

PML4Level 4
Page Map Level 4 — the top table. Its physical address is loaded into register CR3, exactly the way gdtr anchors the GDT.
PDPTLevel 3
Page-Directory-Pointer Table — each PML4 entry points to one of these.
PDLevel 2
Page Directory — the same structure 32-bit paging already used, one level deeper now.
PTLevel 1
Page Table — its entries finally point at actual 4KB physical page frames.

Each table is itself just one 4KB page holding 512 entries, and each entry is 8 bytes — 512 × 8 = 4096. That regularity is exactly why the bit-slicing works out so cleanly: 9 bits is precisely enough to index 512 (2⁹) entries, so a 64-bit linear address hands 9 bits to each of the four levels, plus 12 bits of byte offset within the final 4KB page.

  1. CR3 anchors the walkJust like gdtr holds the GDT's base, CR3 holds the physical address of the current process's top-level PML4 table.
  2. Bits 47–39 index the PML4The CPU multiplies that 9-bit index by 8 bytes and reads one PML4 entry — which itself is just a pointer to a PDPT table's physical address.
  3. Bits 38–30 index the PDPT, bits 29–21 index the PDSame pattern, two more times — each step following a pointer down one more level, entirely in hardware (with the results cached by the TLB so this full walk isn't repeated on every access).
  4. Bits 20–12 index the final Page TableThis entry finally contains the physical page frame number — the actual location in RAM, plus permission bits (writable, user/supervisor, no-execute, and more).
  5. Bits 11–0 finish the job untouchedThe low 12 bits of the linear address are simply appended to the physical frame number as-is — the byte offset within that 4KB page needs no translation at all.

A Worked Example

Take a concrete canonical linear address: 0x00007F3C88A01FE0. Slicing it exactly along the boundaries in the bitfield above — no rounding, just shifting and masking the real bits — produces one specific path through the hierarchy:

PML4 index47–39254
PDPT index38–30242

Four separate 8-byte reads — CR3-plus-254×8 for the PML4 entry, then that entry's pointer plus 242×8 for the PDPT entry, then plus 69×8 for the PD entry, then plus 1×8 for the final PT entry — followed by adding the untouched offset 0xFE0 to whatever physical frame number that last entry contains. Four table walks for one memory access sounds expensive, and it would be, every single time, if it weren't for the TLB (Translation Lookaside Buffer) caching recently-used translations so the full four-level walk only actually happens on a cache miss.

Why context switches aren't free. Reloading CR3 with a different process's PML4 address — the normal thing a kernel does on every context switch — historically flushed the entire TLB, since cached translations from the old address space are meaningless for the new one. Modern CPUs soften this with PCID (Process-Context Identifiers), tagging TLB entries by address space so switching back to a recently-active process doesn't necessarily require re-walking everything from scratch. It's a detail that never shows up in the formula, but it's a large part of why "just switch CR3" isn't quite as free as the one-line description makes it sound.
💡 And When 48 Bits Isn't Enough: 5-Level Paging
Four levels of 9-bit indices plus a 12-bit offset covers exactly 48 bits of usable address space — 256 TiB. That was enormous in 2003 when AMD64 shipped, and it's still enormous for almost everyone, but very large servers (think in-memory databases, huge sparse address-space allocators) started bumping into it. Since Intel's Ice Lake server chips, a fifth level — PML5 — can be enabled via CR4.LA57, stretching usable addresses to 57 bits (128 PiB). Same mechanism, same 9-bit-per-level slicing, one more hop before you reach the PDPT.

One more piece of realism worth having: the walk doesn't always go all the way down to a PT. Each PD entry (and each PDPT entry) has a PS (Page Size) bit. Set it in a PD entry, and that entry stops pointing at a PT and instead directly maps a 2MB huge page — the PT idx and offset fields of the linear address effectively merge into one 21-bit offset. Set it in a PDPT entry, and you get a 1GB huge page straight from the third level. Databases, hypervisors, and JVMs reach for huge pages constantly, for a very concrete reason: fewer page-table levels to walk per access means fewer TLB entries needed to cover the same amount of memory, which means far fewer expensive page-table walks on a TLB miss.

Why this doesn't need its own bitfield diagram. A 2MB huge page just means the walk stops one level early — PML4 idx and PDPT idx still work exactly as drawn above, the PD entry itself is marked "this is a leaf," and its remaining bits (21 of them) become the in-page offset instead of a pointer to yet another table.
08 — The Bits That Don't Get Used

Canonical Addresses and the Fault Nobody Expects

Look back at that bitfield diagram: bits 63 through 48 aren't assigned to any paging level at all. Current x86-64 hardware only actually consults 48 bits (or 57, with 5-level paging enabled) when it walks the page tables — a full 64-bit register genuinely offers more bits than any implemented paging hierarchy currently uses.

Rather than silently ignoring those unused upper bits, the architecture makes a rule out of them: every one of those top bits (63 down to 47, or 63 down to 56 with 5-level paging) must be an exact copy of the highest bit the paging hardware does use — bit 47 in the common case. An address obeying that rule is called canonical. One that doesn't is non-canonical, and using it — loading it into RIP, or referencing it as most kinds of memory operand — doesn't produce a page fault. It produces a #GP(0) general-protection fault instead, because the CPU refuses the address before the page-table walk even begins.

The canonical-address rule (48-bit / 4-level case) bits[63:47] must all equal bit 47 (0×0000… or 0xFFFF… prefix only) Anything else is non-canonical — rejected with #GP before paging is ever consulted.

This is exactly why user-space and kernel-space addresses on a 64-bit Linux box look like they jump dramatically instead of sitting side by side: valid user addresses run from 0x0000000000000000 up to about 0x00007fffffffffff (bit 47 = 0, so the prefix must be all zero), and valid kernel addresses start around 0xffff800000000000 (bit 47 = 1, so the prefix must be all one). Everything in between — the vast canonical hole — is simply unusable address space by architectural rule, not by OS policy.

Put two addresses side by side and the rule becomes concrete instead of abstract. Take 0x00007F3C88A01FE0 — the same address sliced into page-table indices two sections ago. Bit 47 of that address is 0, and every bit above it (63 down to 48) is also 0, so it's canonical: valid, usable, ready for the page-table walk. Now flip exactly one higher bit — bit 48 — leaving every lower bit untouched: 0x00017F3C88A01FE0. Bit 47 is still 0, but bit 48 is now 1, so the "must all match bit 47" rule breaks on the very first bit it checks. That single flipped bit is enough to turn a perfectly normal-looking address into one the CPU refuses outright.

AddressBit 47Bits 63–48Verdict
0x00007F3C88A01FE00all 0 — matches bit 47Canonical — walk proceeds
0x00017F3C88A01FE00not all 0 (bit 48 = 1)Non-canonical — #GP(0)
Not the same fault as a bad page. Don't confuse this with a page fault. A page fault means "this address is canonical and well-formed, but the page tables say nothing is mapped there" — recoverable, and exactly the mechanism that backs demand paging and swapping. A non-canonical #GP means "this address could never have been valid in the first place" — the hardware rejected the very shape of the number.
🧠 Even the "Wasted" Bits Are Getting Reclaimed
Those unused upper bits didn't stay idle forever. Newer Intel chips support Linear Address Masking (LAM), which lets software stash metadata — a pointer tag for a memory-safety sanitizer, say — directly inside a pointer's otherwise-unused canonical bits, while the CPU quietly masks them off before doing the real page-table walk. It's the same instinct behind ARM's Top-Byte Ignore, arriving on x86 only after decades of those bits sitting completely unused — proof the "canonical hole" isn't just an accident of history, it's inventory the industry is still finding new ways to spend.
09 — Theory Meets Terminal

Where You'll Actually See This

All of this is easy to wave off as trivia until you notice it staring back at you from a debugger or a disassembly. A few concrete places this exact material shows up in ordinary day-to-day tooling:

  • GDB's info registers on any x86-64 process prints fs_base and gs_base as real, named registers, right alongside rax and rip — direct confirmation that these two bases are live CPU state, not some software-level abstraction.
  • strace on a freshly-started multi-threaded Linux program shows a burst of arch_prctl(ARCH_SET_FS, 0x7f...) calls, one per thread creation — glibc quietly wiring up TLS exactly as described in this article, one syscall at a time.
  • readelf -S on almost any dynamically linked ELF binary lists .tdata and .tbss sections — the actual on-disk storage for initialized and zero-initialized __thread variables, which the loader copies into each new thread's TLS block.
  • Disassembling stack-protector-enabled code (the GCC/Clang default almost everywhere) with objdump -d turns up exactly the instruction used as this article's running example: mov %fs:0x28,%rax in a function's prologue, followed by a matching check in the epilogue.
  • A crash in a Linux kernel oops report often prints an address like 0xffff888012345678 — the ffff88… prefix is a dead giveaway of the kernel's direct-mapped physical-memory region, a canonical address whose fixed upper bits alone tell you you're looking at kernel space before reading a single further digit.
💡 That 0x28 Offset Wasn't Arbitrary
The fs:[0x28] instruction used throughout the TLS canvas above isn't a made-up teaching example — it's the real, well-known offset where glibc's Thread Control Block stores the stack canary on Linux x86-64. Every function compiled with -fstack-protector (the default in most modern distros) loads that canary through exactly this FS-relative access at the top of the function and checks it again before returning, catching stack-buffer overruns before they can hijack a return address. One instruction, one offset, and it's simultaneously a textbook TLS access and a piece of real exploit mitigation running in essentially every userspace program on your machine right now.
Newer kernels make it even easier to inspect. Since Linux 5.9, /proc/[pid]/task/[tid]/arch_status exposes a running thread's current fs_base and gs_base values directly as text, without needing ptrace at all — a small but telling sign of how ordinary these two registers have become in everyday systems work.
10 — The Complete Picture

Then vs. Now

Put the whole story side by side, and long mode's real move becomes obvious: it didn't add a new translation mechanism, it retired an old one and let the mechanism that was already doing the harder job — paging — take over everything.

Aspect32-bit Protected Mode64-bit Long Mode

💡 The One-Sentence Version
In 32-bit protected mode, segmentation and paging share the translation job — two hardware circuits in series, both doing real arithmetic. In 64-bit long mode, segmentation keeps the badge (CPL) and one spare tool (FS/GS for TLS), but hands the entire translation job to paging alone — because a 64-bit offset made the capacity problem segmentation was built to solve simply disappear.

None of this makes the earlier two articles in this series obsolete — quite the opposite. The GDT, segment selectors, descriptors, DPL, and the whole privilege-checking apparatus are still exactly what a 64-bit kernel configures at boot and still exactly what the CPU consults on every ring transition. What changed is narrower and, once you see it, obvious in hindsight: the one job segmentation used to share with paging — turning an offset into a real address — got handed over entirely, for all but two registers, the moment the offset alone became big enough to need no help.

Not an x86-only idea. The FS/GS-for-TLS pattern is specific to this architecture, but the underlying need isn't. ARM64 solves the identical problem with a dedicated register built for exactly this purpose from day one — TPIDR_EL0 — read directly by a single MRS instruction rather than repurposing a legacy segmentation register. Different architecture, same problem, a cleaner-slate solution once there was no 1978-vintage segmentation hardware left to repurpose.
11 — Quick Reference

Glossary & Key Terms

Long Mode
x86-64's native 64-bit execution mode, where CS/SS/DS/ES segment Base and Limit fields are hardwired inactive and paging alone performs address translation.
Thread-Local Storage (TLS)
Per-thread private variables (C/C++ __thread) implemented by giving each thread a different FS (Linux) or GS (Windows) base address, resolved automatically in hardware.
FSGSBASE
CPU feature (enabled via CR4.FSGSBASE) letting userspace read/write FS.base and GS.base directly with WRFSBASE/RDFSBASE/WRGSBASE/RDGSBASE, skipping a syscall.
arch_prctl
Linux syscall used (with ARCH_SET_FS) to set a thread's FS base address — the traditional, universally-supported way to establish TLS.
SWAPGS
Instruction that swaps the live GS.base with the value cached in the IA32_KERNEL_GS_BASE MSR on kernel entry/exit, giving the kernel its own private per-CPU GS-relative data.
PML4 / PDPT / PD / PT
The four levels of x86-64 paging (Page Map Level 4, Page-Directory-Pointer Table, Page Directory, Page Table), each a 512-entry, 4KB table indexed by 9 bits of the linear address.
CR3
Control register holding the physical address of the current process's top-level page table (PML4) — the paging-side analog of gdtr.
5-Level Paging (LA57)
Extension adding a PML5 level, expanding usable linear addresses from 48 to 57 bits (128 PiB), enabled via CR4.LA57 on supporting CPUs.
Canonical Address
A 64-bit address whose unused upper bits are all copies of the highest bit paging actually uses; using a non-canonical address triggers #GP instead of a page fault.
CPL (Current Privilege Level)
Ring 0 vs. Ring 3, still tracked in long mode via the active CS selector's RPL compared against its descriptor's DPL — segmentation's one surviving protection duty.
EFER (Extended Feature Enable Register)
MSR holding the LME (Long Mode Enable), LMA (Long Mode Active), SCE, and NXE bits — the switches a bootloader flips to bring a CPU into long mode and enable SYSCALL/NX protections.
Compatibility Mode
A transitional IA-32e submode where paging (and long mode) is active but CS still points at a 32-bit-style descriptor (L=0) — used briefly during boot before switching CS to L=1.
TSS (Task State Segment)
A system-type GDT descriptor still required in long mode; its 64-bit form holds RSP0–2 and the Interrupt Stack Table, not the old hardware task-switch state.
TLB (Translation Lookaside Buffer)
On-chip cache of recently-used linear-to-physical translations, letting most memory accesses skip the full 4-level (or 5-level) page-table walk entirely.
LAM (Linear Address Masking)
Newer Intel feature letting software store metadata in a pointer's unused canonical bits, which the CPU masks off before the real page-table walk — reclaiming address bits paging never used.
PAE (Physical Address Extension)
CR4 bit required as a prerequisite for long mode; long mode's 4-level page-table format is structurally PAE paging extended with two more levels.
Guard Page
An intentionally unmapped page placed just past a stack's end; touching it triggers an ordinary page fault, replacing the SS-limit check long mode no longer performs.
