"Segmentation fault (core dumped)" is the single most common sentence in every C programmer's life, and almost nobody who reads it actually knows what happened inside the chip in the microsecond before it appeared. You already know the MMU translates logical → linear → physical, address by address, billions of times a second, silently. This page is about the much rarer, much more interesting case: the translation that fails — exactly which hardware circuit says no, exactly what the CPU does in the next few nanoseconds, and why most of those failures aren't actually bugs at all.

00 — Where We Left Off

Two Circuits, Two Ways to Fail

You already know the pipeline cold: an instruction issues a logical address (segment + offset), the segmentation unit turns that into a flat linear address, and the paging unit walks page tables to turn that linear address into the physical address that actually hits the memory bus. Two hardware circuits, wired in series, running on every single memory access with zero software involved — as long as nothing goes wrong.

You also already know, from the PCB and threads piece, that exceptions and faults are one of exactly three doors into the kernel — synchronous, involuntary, and caused by the instruction currently executing. A segfault is that door, slammed open by hardware, and today we're going to walk through it in slow motion.

It's worth sitting with why that classification matters here specifically. A system call is voluntary — your program decided to knock. A hardware interrupt is asynchronous — it has nothing to do with what your code was doing at all. A fault is neither: it is forced, and it is entirely about the one instruction your program just tried to execute. That's precisely why the CPU can hand the kernel such precise forensic evidence about it — unlike a timer interrupt, which could land on literally any instruction, a fault always has a specific, knowable cause baked into the instruction that triggered it.

💡 The One-Sentence Version
Address translation has exactly two stages, so it has exactly two distinct ways to reject an address: the segmentation unit can refuse at the logical→linear step (a General Protection Fault), or the paging unit can refuse at the linear→physical step (a Page Fault). Everyone calls both of these "segfaults" in casual speech. They are not the same fault, they are not detected by the same circuit, and — as you'll see — one of them is barely used on modern Linux at all.
A naming accident worth knowing. The Unix signal is called SIGSEGV — "segmentation violation" — a name coined back when segmentation was the primary protection mechanism. On a modern x86-64 Linux system, segments are set up flat (base 0, limit max) and do almost no protection work at all; the paging unit does essentially all of it. So the overwhelming majority of what people casually call a "segfault" is, mechanically speaking, a page fault, not a true segmentation fault. The name stuck around long after the mechanism it named became the minority case.

01 — Failure Point One

The General Protection Fault: Segmentation Says No

Recall that a logical address is a segment selector plus an offset, and the segmentation unit resolves the selector by looking up a Segment Descriptor — a small hardware-readable record living in the GDT or LDT that carries, among other things, a Base, a Limit, a Type field (code? data? readable? writable? executable?), and a DPL (Descriptor Privilege Level, 0–3, with 0 being the kernel's ring). Every single time the segmentation unit is asked to resolve a logical address, it doesn't just do the arithmetic — it checks whether the request is even allowed.

A General Protection Fault (GPF), x86 exception vector 13 (#GP), fires when that check fails at the segmentation stage, before the paging unit ever sees anything. Concretely, this happens when:

  • The instruction loads a segment register with a null selector and then tries to use it to address memory.
  • The requesting privilege level (the CPU's current CPL, from its code-segment selector) doesn't satisfy the target segment's DPL — e.g. Ring 3 user code trying to load a selector whose descriptor is marked DPL 0, kernel-only.
  • The offset, added to the segment's base, would exceed the segment's Limit field — reaching past the end of what that segment is declared to cover.
  • The access type doesn't match the segment's declared Type — e.g. attempting to write through a selector that points at a descriptor marked execute-only or read-only code.

The Type field: not every segment is the same kind of thing

A descriptor's Type field doesn't just say "code" or "data" — it distinguishes finer shades that the segmentation unit enforces directly, and a mismatch between what an instruction is trying to do and what the Type field permits is its own flavor of GPF, distinct from a bad DPL.

Descriptor Type (illustrative)Segmentation Unit AllowsA GPF-Triggering Misuse
Data, read-onlyLoadsAny store instruction through this selector
Data, read/writeLoads and storesN/A for data access — a DPL or limit violation instead

Code segments carry an especially interesting bit: conforming. An ordinary (non-conforming) code segment can only be entered at exactly its own DPL; a conforming code segment can be entered by code running at a numerically lower privilege (more privileged) than its DPL, and execution simply continues at the caller's CPL rather than being raised to the callee's. This was historically used for shared library-style code (like math routines) callable from multiple privilege levels without a full privilege transition — an idea that has a distant echo in how the kernel very deliberately does not let user code jump into it this casually; that's what the syscall gate is for instead.

⚠️ Why You Almost Never See a Real GPF on Linux
Linux's memory-protection story is deliberately built almost entirely on paging, not segmentation. At boot, the kernel sets up a tiny, fixed set of segment descriptors — kernel code, kernel data, user code, user data — each with base 0 and a limit covering the entire linear address space. Since every segment is "the whole address space, flat," offset-vs-limit violations essentially never occur, and DPL checks reduce to the same Ring 0 vs Ring 3 split you already get from paging's own supervisor/user bit. The segmentation unit still runs on every access — the hardware pipeline is fixed — it just almost never has anything to object to. This is precisely why "General Protection Fault" is a much rarer message on Linux than "Segmentation fault": GPFs mostly show up from genuinely corrupted or forged selectors, not from ordinary application bugs.

Contrast this with 32-bit Windows history, where segment-based stack/heap protection saw more real use, or with the historical MS-DOS/early-Windows world your logical-address intuition was probably first built on. The mechanism never went away in the silicon — Linux just chose not to lean on it.

The privilege check, spelled out

Every code segment descriptor carries the two-bit DPL field, and the CPU always knows its own current privilege level — the CPL — from the low two bits of the code segment selector currently in use. The segmentation unit's privilege rule for most accesses boils down to one comparison: is the requester's CPL numerically less than or equal to the target's DPL (remembering 0 is most privileged)? A few example combinations make it concrete:

Current CPLTarget Descriptor DPLMeaningResult
0 (kernel)0Kernel code touching a kernel-only segmentAllowed
3 (user)3User code touching an ordinary user segmentAllowed
3 (user)0User code trying to directly load a kernel-only selector#GP — denied
0 (kernel)3Kernel code reading a user segment (common, deliberate)Allowed

This is exactly the check that makes it impossible for ordinary application code to simply load a selector pointing at kernel structures and start reading — the only sanctioned way across that boundary is the guarded door you already know: a system call, which raises the CPL itself under kernel control, rather than the user program raising its own privilege by hand.

💡 Keep This Distinction in Your Back Pocket
Everything in this section — DPL, CPL, descriptor Type, segment Limit — is checked entirely by the segmentation unit, before a linear address even exists yet. The next section moves one stage downstream, to checks the paging unit runs against an address that has already survived segmentation. Keep the two apart: a GPF means "the segment itself said no"; a page fault means "the segment was fine, but the specific page wasn't."
02 — Failure Point Two

The Page Fault: Paging Says No

Assuming the segmentation unit is satisfied and hands over a clean 32- or 64-bit linear address, the paging unit takes over. It splits that linear address into pieces — on x86-64 with 4-level paging, that's indices into the PML4, PDPT, PD, and PT, plus a final page offset — and walks the process's page tables level by level, following the pointer chain that starts at the value in register CR3 (the same CR3 value your process's PCB keeps a pointer to).

At the very last step, the paging unit reads the Page Table Entry (PTE) for the target page and checks its flag bits before returning a physical frame. A Page Fault, x86 exception vector 14 (#PF), fires when that check fails, for one of exactly three reasons:

🚫 Not Present

The PTE's Present bit is 0 — there is currently no valid physical frame backing this page at all, for any reason. (This single condition covers both "genuinely unmapped" and "intentionally deferred," which is exactly the ambiguity the next section is about.)

✍️ Write to Read-Only

The page is present and mapped, but its Read/Write bit says read-only, and the faulting instruction was a store, not a load.

🔒 Privilege Violation

The page is present and the access type is fine, but it's marked supervisor-only (U/S bit) and the CPU was executing at Ring 3 (user mode) when it tried to touch it.

Notice the structural symmetry with the GPF section above: the segmentation unit checks a descriptor's Type/DPL/Limit fields; the paging unit checks a PTE's Present/Read-Write/User-Supervisor bits. Same idea — "is this access allowed?" — enforced by two completely different hardware tables, at two completely different stages of the same pipeline.

How the paging unit finds that PTE in the first place

On x86-64, a 64-bit linear address isn't looked up in one giant flat table — that would need billions of entries. Instead it's sliced into five pieces, and the paging unit walks four levels of tables, using one slice per level as an index, before finally reaching the page offset:

64-bit linear address, sliced for a 4-level page-table walk [ 16 unused ][ 9 bits → PML4 ][ 9 bits → PDPT ][ 9 bits → PD ][ 9 bits → PT ][ 12 bits → page offset ] Each 9-bit slice indexes a 512-entry table; CR3 supplies the physical address of the top-level PML4 for the current process.

The fault can technically happen at any level of that walk — if a higher-level entry (say, the PDPT entry) itself has its Present bit clear, the walk stops right there and #PF fires just the same, with CR2 still recording the original linear address the CPU was trying to resolve. In practice the overwhelming majority of faults people encounter are resolved at the final, page-table level, which is why this page focuses there.

The U/S bit has grown teeth over the years. Modern x86 CPUs add two hardware features built directly on top of that same bit: SMEP (Supervisor Mode Execution Prevention) faults if kernel code ever tries to execute instructions from a user-mapped page, and SMAP (Supervisor Mode Access Prevention) faults if kernel code tries to merely read or write user memory without first explicitly signaling it means to. Both exist to turn an entire historical class of kernel exploits — tricking the kernel into jumping into or trusting attacker-controlled user-space memory — into an immediate, loud page fault instead of a silent privilege escalation.
Present (P)bit 0
Is there a valid physical frame behind this entry right now? Clear on unmapped memory, deferred allocations, and swapped-out pages alike.
Read/Write (R/W)bit 1
If clear, only reads are allowed — a write faults. This is the bit copy-on-write manipulates on purpose.
User/Supervisor (U/S)bit 2
If clear, only Ring 0 code may touch this page — user-mode access faults, no exceptions.
Accessed (A) / Dirty (D)bits 5–6
Set automatically by hardware on first read / first write — how the kernel's page-replacement code finds "cold" pages worth swapping out, without ever faulting on them.
No-Execute (NX)bit 63
If set, fetching an instruction from this page faults, even if it's readable — the hardware backbone of W^X ("writable xor executable") stack/heap protection.
Global (G)bit 8
Tells the CPU this translation stays valid across a context switch (used for kernel mappings present in every process) — the entry survives the very TLB flush the PCB/threads piece warned you a page-table switch usually triggers.

Fewer, bigger pages means fewer faults

Standard x86-64 pages are 4KB, meaning a process touching 1GB of memory could in principle trigger up to roughly 262,000 individual demand-paging faults just to fully populate it. Hardware also supports huge pages — 2MB (by collapsing the PD level to point straight at a frame instead of a PT) and 1GB (collapsing the PDPT level too) — which cover far more memory per PTE, shrinking both the page-table walk depth and the raw number of faults needed to back a large region. This is exactly why databases, JVMs, and hypervisors specifically request huge pages (via madvise(MADV_HUGEPAGE) or hugetlbfs) for their largest allocations: fewer faults, fewer TLB entries needed to cover the same memory, and less time spent walking tables on every access.

03 — The Instant It Happens

CR2, the Error Code, and the IDT

So the paging unit just rejected an address. What does the CPU actually do, in hardware, in the next few clock cycles — before a single line of kernel C code has run? This is the exact trap-frame mechanism from the PCB/threads piece, specialized to this one exception.

  1. The faulting linear address is latched into CR2x86 has a dedicated control register, CR2, whose entire job is holding the linear address that caused the most recent page fault. The CPU writes it there automatically, in hardware, the instant the fault is detected — nothing else uses CR2 for anything else.
  2. An error code is pushed onto the (kernel) stackAlongside CR2, the CPU pushes a 32-bit error code describing exactly what kind of page fault this was, bit by bit: bit 0 (P) — was the page present but a protection check failed (1) or was it simply not-present (0)? bit 1 (W/R) — was this a write (1) or a read (0)? bit 2 (U/S) — did it happen in user mode (1) or supervisor mode (0)? A GPF pushes an analogous error code identifying which selector was at fault, though it carries no CR2 equivalent, since GPFs aren't tied to a linear address at all.
  3. Control transfers via the IDTEvery exception and interrupt has a fixed vector number — 13 for #GP, 14 for #PF — that the CPU uses as an index into the Interrupt Descriptor Table (IDT), the exception/interrupt sibling of the GDT you met in the segmentation piece. The matching IDT entry (a gate descriptor) points straight at the kernel's registered handler function for that vector — for #PF, that's the kernel's page-fault handler, compiled once, living at a fixed kernel address, ready to run at Ring 0.
  4. A trap frame is pushed, privilege escalates to Ring 0Exactly as in the PCB/threads piece: the CPU pushes the minimal trap frame — program counter, flags, stack pointer, a handful of registers — onto the kernel stack, switches to Ring 0, and jumps to the handler address it just read from the IDT. The interrupted user instruction is frozen in time, fully recoverable, the instant this frame is on the stack.
What the CPU hands the kernel's #PF handler CR2 = the bad linear address · Error Code = { P, W/R, U/S, … } · Trap Frame = saved PC/flags/registers Three pieces of evidence, assembled entirely in hardware, before the kernel has executed a single instruction of its own logic.
Error Code (P, W/R, U/S)Plain-English Reading
0, 0, 0Not present, was a read, happened in kernel mode

1, 1, 1Page present, was a write, user mode — the classic copy-on-write shape

Why a dedicated register instead of just passing it as a normal argument? By the time the fault fires, the CPU can't trust the normal calling-convention registers to still hold anything meaningful for "here's the address" — the fault happened mid-instruction, possibly mid-addressing-mode calculation. A dedicated, hardware-guaranteed register (CR2) sidesteps that entirely: no matter what the faulting instruction was doing, CR2 is guaranteed to hold exactly the address that upset the paging unit.

Not every IDT gate behaves identically

The IDT doesn't hold one uniform kind of entry — each gate descriptor also specifies whether hardware interrupts stay enabled while the handler runs. An interrupt gate clears the CPU's interrupt flag on entry (used for most device interrupts, where you don't want a second interrupt interleaving mid-handler); a trap gate leaves it set. Exceptions like #GP and #PF use trap gates — the kernel is fine being interrupted again while it's still figuring out what to do about your bad address, since the fault handler is regular, re-entrant kernel code, not a tight hardware-service routine.

📌 A Fault About a Fault
If the CPU is already trying to deliver #GP or #PF and something goes wrong during that delivery — say, the kernel stack itself isn't mapped — the CPU escalates to a double fault (#DF), vector 8. If handling that also fails, the CPU gives up entirely and triple-faults, which on real hardware simply resets the machine. This is one reason the kernel keeps a dedicated, always-mapped, always-valid stack reserved specifically for entering exception handlers — so a fault involving a corrupted stack pointer can't take the whole system down with it.

05 — The Big Aha

Every Page Fault Asks One Question First

Here's the part that surprises almost everyone learning this for the first time: the CPU raising #PF does not mean anything went wrong. It just means "paging unit says this address isn't currently backed by a present, correctly-permissioned page." Whether that's a catastrophe or business-as-usual is a judgment call the kernel's own page-fault handler has to make, fresh, on every single fault, by consulting its own data structures — not anything the hardware told it.

On a real, busy Linux system, that judgment call goes "this is expected" far more often than "this is a bug." Two mechanisms account for almost all of it:

Demand paging: presence deferred on purpose

When you call malloc() for a large block, or the kernel maps a fresh anonymous region for a growing heap or a freshly mmap()'d file, it does not immediately go find physical RAM frames and wire up PTEs for the whole range. That would waste real memory on pages you might never touch. Instead, the kernel creates the bookkeeping for the region — a VMA (virtual memory area, vm_area_struct in Linux) recording "this range of addresses belongs to this process and behaves like this" — and leaves every PTE in that range marked Not Present, deliberately.

The first time your program actually reads or writes a byte in that range, the paging unit finds Present=0 and faults, exactly like it would for a genuine bug. The kernel's handler catches it, checks its VMA list, finds "oh — this address falls inside a valid VMA, it's just never been touched," allocates one physical frame right then, fills in the PTE, and resumes your instruction as if nothing unusual happened. Your program never even sees a hiccup. This is demand paging — allocate physical memory lazily, one page at a time, exactly when it's first needed, not a moment sooner.

Copy-on-write: read-only marked on purpose

When a process calls fork(), the kernel does not copy the parent's entire address space into new physical frames — that would be enormously wasteful if, as is common, the child immediately calls exec() and discards it all anyway. Instead, the child's page tables are set up to point at the exact same physical frames as the parent's, and both processes' copies of those shared PTEs are marked read-only, deliberately, even for pages that were writable before the fork.

The moment either process writes to one of those shared pages, the paging unit sees Read/Write=0 on a store and faults with the Protection bit set (P=1, W/R=1 in the error code). The handler recognizes this specific pattern — a private, writable-in-theory mapping backed by a shared frame — allocates a fresh physical frame, copies the old page's contents into it, repoints that one process's PTE at the new frame marked writable, and resumes. This is copy-on-write (COW): defer the actual copy until — and unless — someone actually writes, so two processes sharing gigabytes of identical memory after a fork() never pay for copies they'll never need.

🧠 What If the Kernel Itself Faults?
Everything above assumes the faulting code was running at Ring 3 (user mode). If the kernel's own code dereferences a bad pointer, the exact same #PF mechanism fires — same CR2, same error code, same IDT dispatch — but the destination isn't "deliver SIGSEGV to a process." Since there's no more-privileged level to hand the problem to, the kernel instead prints an oops (a diagnostic dump of the offending kernel stack and registers) and, depending on how critical the corrupted code path was, may escalate to a full kernel panic, halting the whole machine. This is the same U/S bit distinction from the paging-unit section doing double duty: it tells the handler not just whether the access was legitimate, but which of two entirely different failure-response paths to take.
✅ The Reframe
A page fault is not an error signal — it's an interrupt requesting a kernel decision. Most of the time on a healthy running system, that decision is "allocate a frame" or "copy a page," resolved in microseconds, completely invisibly to the faulting program. Demand paging and copy-on-write aren't edge cases bolted onto the fault mechanism — they are the fault mechanism's primary job. Killing a process with SIGSEGV is the minority outcome, reserved for the case the next sections cover: an address that doesn't correspond to anything valid in any VMA at all.

Minor faults vs major faults — the resolution isn't always free

Even among the "expected, not a bug" faults, there's a real performance split worth knowing. A minor fault (Linux calls it a "minflt") is resolved entirely in memory — a fresh demand-paged page that just needs a zeroed frame, or a COW copy from a frame already resident in RAM. It costs a trap and a bit of kernel bookkeeping, nothing more, typically low microseconds. A major fault ("majflt") is resolved only after real I/O — the page has to be read in from a swap device or from the backing file of an mmap()'d region — and can cost milliseconds, five or six orders of magnitude slower, because it's now waiting on a disk or SSD rather than just touching RAM.

⚡ Minor Fault

Resolved from memory alone — zero a fresh page, or copy from a page already resident. Fast enough that a running program's demand-paged startup is essentially free.

🐢 Major Fault

Requires blocking I/O — reading a swapped-out page back in, or pulling a page of a memory-mapped file off disk. This is the fault type behind the sluggish first few seconds after you launch a huge application from cold cache.
You can watch this happen on a real machine. ps -o min_flt,maj_flt -p <pid> or /usr/bin/time -v ./program report exactly these two counters per process, and /proc/vmstat tracks system-wide pgfault and pgmajfault totals. A healthy, RAM-resident workload racks up thousands of minor faults per second — that's demand paging and COW doing their job — while a spike in major faults is usually the first sign a system is under real memory pressure and swapping.

06 — Real Crash Forensics

Three Ways a C Program Actually Dies

Time to make this concrete. Here's a small C file with three classic bugs. Read it once, then walk through what each one actually does at the MMU level — because the honest answer is "not always what you'd guess."

/* crashcases.c — three classic memory bugs */
#include <stdlib.h>
#include <string.h>

void null_deref(void) {
    int *p = NULL;
    *p = 42;              // write through address 0x0
}

void heap_overflow(void) {
    char *buf = malloc(16);
    strcpy(buf, "this string is way longer than sixteen bytes");
    free(buf);          // heap metadata already corrupted by now
}

void stack_overflow(int n) {
    char frame[4096];      // no base case — recurses forever
    frame[0] = (char)n;
    stack_overflow(n + 1);
}

1. The null pointer — a page fault you can predict

null_deref() writes to linear address 0x0. The kernel deliberately never maps anything at or near address zero — this reserved "guard region" at the bottom of the address space exists specifically so that null-pointer bugs fault immediately and loudly instead of silently touching some other structure that happens to live at a low address. Present bit is 0, there's no VMA covering it, the handler's first check fails immediately, and the result is a clean, instant SIGSEGV — the easiest of the three to debug, because the crash happens at the exact instruction that caused it.

2. The heap overflow — often doesn't segfault at all

heap_overflow() is the dangerous one, precisely because it usually does not crash on the spot. malloc(16) reserves 16 bytes, but the underlying physical page backing that allocation is 4KB (or larger). Writing 47 bytes into a 16-byte buffer almost always still lands well inside that same present, writable, mapped page — the paging unit has no way to know your buffer was "logically" only 16 bytes; it only knows the page is present and writable. So the write succeeds, silently corrupting whatever heap metadata or adjacent allocation happened to sit right after your buffer. The segfault, if one ever comes, shows up later — maybe in a totally unrelated free() call, maybe never — pointing you at the wrong line of code entirely.

⚠️ Why This Is the Scary One
A crash that happens at the instruction that caused it is a debugging inconvenience. A crash that happens hundreds of instructions and possibly several function calls after the instruction that caused it is a debugging nightmare — this is exactly why heap corruption bugs are notorious, and exactly why tools like AddressSanitizer exist: they add their own bookkeeping around every allocation specifically so an out-of-bounds write faults immediately, on purpose, instead of silently succeeding.

A handful of standard mitigations exist precisely because the MMU alone can't catch an in-bounds-of-the-page, out-of-bounds-of-the-buffer write like this one — they add checks the hardware never promised:

Notice the throughline: every one of these tools is really just manufacturing an artificial page fault (or an artificial, checkable corruption signature) out of a bug the raw MMU pipeline would otherwise let through silently, because as far as the paging unit is concerned, a byte 5 past the end of your 16-byte buffer is still just an ordinary, present, writable byte on an ordinary, present, writable page.

3. The stack overflow — a page fault into a guard page

stack_overflow() recurses with no base case, and every call pushes another 4KB local array onto the stack. The stack isn't infinite: it's a single VMA that the kernel is willing to grow automatically, downward, up to a limit (typically controlled by RLIMIT_STACK — 8MB is a common default). Just below the lowest address the stack is allowed to reach, the kernel leaves a deliberately unmapped guard page. Eventually one recursive call's stack frame lands partly or fully inside that guard page, the paging unit finds Not-Present, the handler checks — "is this a legitimate stack-growth request?" — and if the address is past the configured limit, the answer is no. SIGSEGV, and the classic "stack overflow" crash, which is mechanically just a page fault against a specific, intentionally booby-trapped unmapped page.

P=0, W/R=1, U/S=1
Not present, was a write, happened in user mode — a normal-looking stack push, on a page that isn't there.
VMA Lookup Result
no covering VMA
The address falls outside the stack VMA's current (grown) bounds and past RLIMIT_STACK.
Handler Verdict
genuine fault
Not demand paging, not COW, not a legitimate stack-growth candidate — deliver SIGSEGV.
Null Derefimmediate
Crashes at the exact faulting instruction. CR2 is a suspiciously round, tiny number like 0x0 or 0x8 (a null struct pointer plus a small field offset) — a dead giveaway in any dossier.
Heap Overflowdelayed
Often doesn't fault at all at the write. Surfaces later as heap-metadata corruption, a crash in an unrelated free()/malloc() call, or silent wrong answers — no fault ever fires.
Stack Overflowimmediate
Crashes reliably, right at the guard page. CR2 sits just past the stack's low-water mark; the backtrace is typically a long, repetitive tower of the same one or two recursive frames.

What the human actually sees

Here's a representative gdb session for null_deref() — this is what all that hardware machinery ultimately buys you: a plain-English pointer straight back to the offending source line.

$ gdb ./a.out core
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x0000000000401136 in null_deref () at crashcases.c:7
7           *p = 42;              // write through address 0x0
(gdb) print p
$1 = (int *) 0x0
(gdb) bt
#0  0x0000000000401136 in null_deref () at crashcases.c:7
#1  0x0000000000401189 in main () at crashcases.c:20
Why a "wild" uninitialized pointer reliably crashes too. You might expect an uninitialized pointer's garbage value to occasionally point somewhere valid by sheer luck. In practice, ASLR (Address Space Layout Randomization) randomizes where the heap, stack, libraries, and executable actually land in the linear address space on every run, so any fixed or garbage bit pattern has an overwhelming chance of landing in one of the vast unmapped gaps between those regions rather than inside any of them. This is exactly the "genuine bad access" branch in the interactive pipeline above — no VMA covers the address, so the handler's very first check fails and SIGSEGV follows immediately.
07 — From Fault to Human

SIGSEGV, Core Dumps, and How gdb Knows Where You Were

Once the kernel's #PF handler decides a fault is genuine, it doesn't just silently drop the process — it has to hand the bad news to the process itself, through the ordinary Unix signal mechanism, using exactly the same trap-frame state it already has sitting on the kernel stack.

  1. The kernel delivers SIGSEGVThe handler calls into the signal-delivery machinery, marking signal 11 (SIGSEGV) pending for this process. Before returning to user mode, the kernel checks: does this process have a custom handler installed for SIGSEGV (via sigaction())? If not — the overwhelmingly common case — the default disposition applies: terminate the process and dump core.
  2. A core dump is writtenIf the process's core-dump resource limit allows it (ulimit -c, often 0 by default on interactive shells), the kernel writes a core file — a snapshot of the process's entire address space at the moment of death: every mapped page, the full register state from the trap frame, open file descriptor info, and the exact program counter that was executing when CR2 got written. This is, quite literally, a point-in-time copy of everything the PCB and page tables knew about this process.
  3. gdb reads the corpseRunning gdb ./a.out core loads that snapshot back up. Because the core file preserves the saved program counter and full register set from the trap frame, gdb can map that PC value straight back to a source line (using the debug symbols compiled into the binary) and print a backtrace — the exact chain of function calls, frame by frame, that led to the fault, plus the live value of every local variable and register at that instant.
🧠 Tying It Back to the PCB Module
This is the same trap-frame mechanism you already learned, doing double duty. The trap frame's job was always "let the kernel resume exactly where a process left off." Here, the kernel doesn't resume the process — it hands that exact same saved state (PC, flags, registers) to the core file instead, so a human can resume investigating exactly where the process left off. gdb's backtrace is, functionally, reading a PCB-style snapshot that was captured for a process that's never going to run again.

Your own code can intercept CR2, too

A process isn't limited to the "get killed, leave a core file" default. Installing a handler with sigaction() and the SA_SIGINFO flag gives you a siginfo_t struct on every SIGSEGV delivery, and its si_addr field is populated from exactly the same value the CPU latched into CR2 — the kernel simply copies it out of the trap frame into user-visible form before invoking your handler. This is the mechanism behind things like garbage collectors that deliberately provoke page faults as a signal (some GCs mark pages read-only to detect writes without instrumenting every store), and behind graceful crash reporters that log a stack trace before exiting instead of leaving nothing but a raw core file.

/* catching the fault yourself — si_addr mirrors CR2 */
#include <signal.h>
#include <stdio.h>

void handler(int sig, siginfo_t *info, void *ctx) {
    printf("SIGSEGV at address %p\n", info->si_addr);
    _exit(1);          // don't return — the fault will just re-fire
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_sigaction = handler;
    sa.sa_flags = SA_SIGINFO;
    sigaction(SIGSEGV, &sa, NULL);
    int *p = NULL;
    *p = 1;              // handler prints "SIGSEGV at address 0x0"
}
Why the handler must not just return. The instruction that faulted never completed — the CPU rewinds the program counter back to the start of that instruction before invoking the trap frame path, precisely so a fix-and-resume handler (like the kernel's own demand-paging logic) can retry it. If your user-mode handler returns normally without having fixed the actual problem (there's still no page mapped at that address), execution resumes at that same faulting instruction, faults again, and re-enters the handler — which is why real handlers either fix the underlying condition, longjmp elsewhere, or simply exit.

One caveat worth flagging for anyone about to write one of these handlers for real: a SIGSEGV handler runs in a genuinely broken environment — the heap might be corrupted, the stack might be the very thing that overflowed. POSIX only guarantees a small allow-list of async-signal-safe functions are safe to call from inside it (write() is safe; printf(), strictly speaking, is not, because it may itself allocate). The example above uses printf() for readability, exactly like most tutorials do — production-grade signal handlers lean on the safe subset, or simply record the fault and re-raise the default handler to let the normal core-dump path take over.

📌 Live Debugging Skips the Core File Entirely
You don't strictly need a core dump to see this in action — running a program directly under gdb ./a.out and letting it crash live works the same way, because gdb is watching for exactly the same SIGSEGV delivery via ptrace(), catching the process the instant the signal would otherwise terminate it, and reading its live register file, which at that moment holds precisely the trap-frame values the kernel captured.

One more practical tool, for when you only have an address and a binary, not a live process or a core file: addr2line -e ./a.out 0x401136 maps a raw program-counter value straight back to a source file and line number using the binary's debug info — useful for turning a bare address out of a crash log (say, from a remote server where you can't attach gdb) into something you can actually act on.

09 — Quick Reference

Glossary & Key Terms

🚦 Detection

Two hardware units, two vectors: the segmentation unit raises #GP over selector/DPL/limit problems; the paging unit raises #PF over Present/Read-Write/User-Supervisor problems in a PTE.

📋 Evidence

On a page fault specifically, the CPU hands the kernel three hardware-assembled facts before any software runs: CR2 (the address), the error code (what kind of violation), and the trap frame (where execution was).

⚖️ Verdict

Only the kernel's own handler, consulting its VMA list, decides whether that evidence describes a genuine bug (SIGSEGV, core dump, gdb) or routine, deliberate lazy memory management (demand paging, copy-on-write — fixed and resumed, invisibly).
General Protection Fault (GPF)
Exception vector 13 (#GP), raised by the segmentation unit when a logical address's selector, privilege, or limit check fails.
Page Fault
Exception vector 14 (#PF), raised by the paging unit when a linear address's page is not present, or fails a read/write or privilege check.
CR2
The x86 control register that hardware automatically loads with the faulting linear address the instant a page fault occurs.
Page-Fault Error Code
A value pushed to the kernel stack alongside CR2, whose bits encode Present/Not-Present, Read/Write, and User/Supervisor.
IDT (Interrupt Descriptor Table)
The table, indexed by exception/interrupt vector number, whose entries point the CPU at the kernel's registered handler — the GDT's sibling table.
Demand Paging
Deliberately leaving a valid VMA's pages marked Not Present, allocating a physical frame only the first time each page is actually touched.
Copy-on-Write (COW)
Deliberately marking shared pages (e.g. after fork()) read-only, so a write triggers the kernel to copy the page privately for the writer only.
SIGSEGV
The Unix signal (11) the kernel delivers when its page-fault handler decides a fault was genuinely invalid; default action terminates the process.
Core Dump
A file capturing a terminated process's full memory image and saved trap-frame register state at the moment it was killed.
Guard Page
A deliberately unmapped page placed just past the end of a growable region (like the stack) so overrunning it reliably faults instead of silently corrupting adjacent memory.
VMA (vm_area_struct)
The kernel's per-region bookkeeping record — what a range of a process's address space is for and how a fault inside it should be resolved.
Minor / Major Fault
A minor fault resolves entirely in RAM (fast); a major fault requires real I/O — swap-in or reading a mapped file — and is orders of magnitude slower.
Double Fault (#DF)
Vector 8 — raised when the CPU fails while trying to deliver another exception; if delivery of the double fault itself fails, the CPU triple-faults and resets.
