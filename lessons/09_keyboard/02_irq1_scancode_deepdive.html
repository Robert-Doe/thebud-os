00 — Where We Left Off

Quick Recap

Lesson one established the core fact: the keyboard sends numeric scancodes identifying physical key positions, not characters — and it does so through the 8042 controller, over I/O port 0x60. This lesson assumes you already know, generally, what an interrupt request (IRQ) and an interrupt service routine (ISR) are — how the CPU gets yanked out of whatever it's doing and into kernel code the instant a hardware line is asserted. What we haven't covered yet is which line the keyboard uses, what a well-behaved keyboard ISR actually does inside that handler, and how a raw byte stream becomes real text with Shift, Ctrl, and Alt behaving correctly.

01 — The Wire

The Keyboard Is Wired to IRQ1

On the classic PC interrupt architecture, every hardware device that can interrupt the CPU is wired to one specific numbered line on the Programmable Interrupt Controller (PIC). The keyboard's line has been fixed since the original IBM PC: IRQ1. (IRQ0, for comparison, is reserved for the system timer — you'll meet that one when the scheduler shows up.)

In bob_os, IRQ1 gets remapped during PIC initialization onto CPU interrupt vector 33 — vector 32 + 1, since pic_init() offsets the PIC's IRQ lines past the CPU's own reserved exception vectors (0–31). The moment the 8042 controller has a fresh scancode byte sitting in its output buffer, it asserts IRQ1, the PIC turns that into vector 33 on the CPU's interrupt bus, and the CPU — assuming interrupts are enabled — immediately stops what it's doing and jumps to whatever handler is registered for vector 33.

bob_os's keyboard_init() doesn't touch the PIC or IDT directly — it calls irq_register(1, keyboard_irq_handler), handing its handler function to the generic interrupt-dispatch layer built back in the IDT/interrupts module. That layer already knows how to route vector 33 to whatever's registered for IRQ 1. This is exactly the same registration pattern every other IRQ-driven driver in bob_os uses — the keyboard isn't special at the dispatch level, only at the port-and-scancode level.

One controller, two IRQ lines. The same 8042 controller chip handles both the keyboard (IRQ1) and, historically, a PS/2 mouse on a second internal port (IRQ12). They share the chip but not the interrupt line — the controller can tell which physical device a byte came from and routes the interrupt accordingly, which is why your keyboard ISR never has to worry about accidentally reading a mouse-movement byte.
02 — Inside the Handler

What a Keyboard ISR Actually Does

Here's the rule that governs every hardware ISR, keyboard included, and it's worth stating bluntly: an interrupt handler must be fast, and it must never block. While your ISR is running, that CPU core typically has interrupts of equal-or-lower priority masked — other time-sensitive work is on hold. A keyboard ISR that took even a few milliseconds to "helpfully" do more work would risk dropped or delayed keystrokes, or worse, delay something entirely unrelated, like the timer tick your scheduler depends on.

So what does bob_os's handler actually do? Look at the real function from keyboard.c:

static void keyboard_irq_handler(struct interrupt_frame *frame) {
    (void)frame;

    uint8_t sc = inb(KB_DATA_PORT);        /* 1. read the byte — mandatory, clears OBF */

    if (sc == SC_LSHIFT_MAKE || sc == SC_RSHIFT_MAKE) { shift_held = 1; return; }
    if (sc == SC_LSHIFT_BREAK || sc == SC_RSHIFT_BREAK) { shift_held = 0; return; }

    if (sc & 0x80) return;                 /* 2. break code for a non-modifier — ignore */
    if (sc >= 88)  return;                 /* 3. outside our table — ignore */

    char c = shift_held ? sc_shift[sc] : sc_normal[sc];
    if (c != 0) {
        buf_push(c);                       /* 4. push into the ring buffer, done */
    }
}

Notice everything this function does not do. It doesn't print to the screen. It doesn't call into the shell. It doesn't wait for anything. It reads one byte, does a handful of comparisons and one array lookup, pushes at most one character into a ring buffer, and returns. That's the entire job. Whoever actually wants the character — the kernel's main loop, calling keyboard_getchar() — picks it up later, on its own schedule, completely outside interrupt context.

The Aha Moment
An ISR's job is to capture the event cheaply, not to handle it fully. The keyboard ISR's entire responsibility is: read port 0x60 (this is mandatory — it's what clears the controller's "buffer full" flag and re-arms IRQ1), do the absolute minimum translation work, and hand the result off to a buffer for someone else to consume later. This "defer the real work" pattern — sometimes called a top half/bottom half split in other kernels — is why interrupt-driven I/O can service dozens of devices without any one of them freezing the machine.
Don't Forget the EOI
Reading port 0x60 clears the controller's output-buffer-full flag, but the PIC also needs to be told "I've handled this interrupt, you may deliver the next one" — that's the End-Of-Interrupt signal, sent with pic_send_eoi(irq). bob_os's shared dispatcher in isr.c sends it for you, automatically, before calling your registered handler — so every IRQ handler gets EOI handling for free and never has to remember it individually, and a slow handler still can't accidentally delay the EOI itself. Look at the real dispatcher below; it's the one piece of code that runs for every single hardware interrupt in the kernel, keyboard included. 
/* isr.c — the shared dispatcher every IRQ (0-15) funnels through */
void interrupt_handler(struct interrupt_frame *frame) {
    uint32_t vec = frame->int_no;

    if (vec < 32) {
        kernel_panic(frame);              /* CPU exception — not an IRQ */
    } else if (vec < 48) {
        uint8_t irq = (uint8_t)(vec - 32);
        pic_send_eoi(irq);                /* ACK the PIC first, always   */
        if (irq_handlers[irq] != 0) {
            irq_handlers[irq](frame);     /* THEN run the registered ISR */
        }
    }
}

Notice vector 33 (IRQ1, the keyboard) and vector 32 (IRQ0, the timer) both funnel through this exact same function — the dispatcher doesn't know or care that one of them is a keyboard. It just maps a vector number to an IRQ number, sends EOI, and calls whatever function was registered for that slot via irq_register(). That registration table (irq_handlers[16]) is the entire mechanism connecting "IRQ1 fired" to "keyboard_irq_handler runs" — no special-casing anywhere in the dispatch path.

03 — One Key, Two Events

Make Codes and Break Codes

Every physical key press actually generates two separate hardware events, not one: the moment it goes down, and the moment it comes back up. Scancode Set 1 — the classic, oldest PS/2 scancode convention, and the one bob_os and QEMU use by default — represents both with a beautifully simple trick.

The Set 1 convention break_code = make_code | 0x80 The release event is exactly the press event's byte, with the top bit (bit 7) forced to 1. Nothing more complicated than that.

Bit 7 is the entire signal: 0 = make (press), 1 = break (release). The remaining 7 bits (0–127) always identify the same physical key regardless of press or release.

Because of this, testing sc & 0x80 — exactly what bob_os's ISR does — is a complete, correct test for "is this a release event?" And masking it off (sc & 0x7F) recovers the original make code if you ever need to know which key was released, not just that a release happened.

Why bob_os Ignores Every Break Code Except Shift's
Look back at the ISR: the very first two comparisons special-case Shift's break codes to clear shift_held, and only after that does the generic if (sc & 0x80) return; silently discard every other release event. That's deliberate. A simple driver that only ever types characters on press doesn't need to know when an ordinary letter key is released — but it absolutely must know when a modifier is released, or Shift would appear to stay "stuck" forever after the first press.

05 — The Translation Step

Scancode → ASCII Is Just an Array Index

The actual translation from a numeric scancode to a printable character is, deliberately, the least exciting part of the whole pipeline — and that's a feature, not a shortcoming. It's a flat array where the scancode is the index:

/* Index = scancode (0x00-0x57). Value = ASCII character. 0 = no printable char. */
static const char sc_normal[88] = {
/*00*/  0,
/*01*/  0x1B,                                            /* ESC        */
/*02*/  '1','2','3','4','5','6','7','8','9','0','-','=',
/*0E*/  '\b',                                             /* Backspace  */
/*0F*/  '\t',                                             /* Tab        */
/*10*/  'q','w','e','r','t','y','u','i','o','p','[',']',
/*1C*/  '\n',                                             /* Enter      */
/*1D*/  0,                                                /* Left Ctrl  */
/*1E*/  'a','s','d','f','g','h','j','k','l',';','\'','`',
/*2A*/  0,                                                /* Left Shift */
    /* ... */
};

Lookup is then just sc_normal[sc] — no branching, no parsing, O(1) and cache-friendly, which matters because this runs inside an interrupt handler where speed is the whole point. bob_os keeps a second, parallel table, sc_shift, holding the shifted character for the same index — 'A' instead of 'a', '!' instead of '1' — and the ISR simply chooses which table to read from based on whether Shift is currently held.

✅ Why a Flat Array, Not a Switch Statement

A 128-entry switch compiles to something far larger and slower than a direct array index. The array approach is exactly the same "trade software flexibility for hardware simplicity" idea from lesson one, taken one step further: even the software side stays about as fast as it can possibly be.

🚫 What a Flat Array Can't Do Alone

Nothing about a single array knows about Shift, Ctrl, or Alt. Those require the driver to track state across multiple scancode events, not just decode one in isolation — which is exactly the next section's subject.
06 — Handing Off Safely

The Ring Buffer: Why It's Lock-Free By Construction

There's one more piece of the "keep the ISR fast" discipline worth pulling apart, because it explains a few lines in keyboard.c that would otherwise look like unexplained ceremony: volatile on the buffer indices, and the specific power-of-2 size of the buffer itself.

#define KB_BUF_SIZE  256u
static volatile char     kb_buf[KB_BUF_SIZE];
static volatile uint32_t kb_head = 0;   /* next write position — ISR only  */
static volatile uint32_t kb_tail = 0;   /* next read  position — main loop */

static void buf_push(char c) {
    uint32_t next = (kb_head + 1u) & (KB_BUF_SIZE - 1u);
    if (next != kb_tail) {          /* full? then drop silently */
        kb_buf[kb_head] = c;
        kb_head = next;
    }
}

Two design facts are doing real work here. First, the buffer is exactly 256 bytes — a power of two — specifically so that wrapping the index around is (head + 1) & 255 instead of a genuine modulo/divide. On hardware with no divide instruction handy (or where you simply don't want to spend the cycles), a bitwise AND is effectively free, which matters because this line runs inside an interrupt handler on every single keystroke.

Second, kb_head and kb_tail are marked volatile. The keyboard ISR is the only writer of kb_head; the kernel's main loop is the only writer of kb_tail — one producer, one consumer, each touching only their own index. That single-writer discipline is exactly what makes this buffer safe without locks, which matters enormously in a kernel that (at this stage of bob_os) has no mutex or spinlock primitive yet. But without volatile, the compiler would be free to assume kb_head never changes underneath the main loop's read — and could legally cache it in a register forever, never noticing the ISR updated the real variable in memory. volatile forces every read and write to actually touch memory, which is the only way two independent contexts (interrupt vs. normal execution) can reliably see each other's updates.

What Happens When the Buffer Is Full
buf_push() computes where the next write would land and compares it against kb_tail before committing. If they'd collide, the new character is dropped silently — the buffer is "full" whenever advancing head one more slot would make it equal tail again (one slot is deliberately sacrificed so "full" and "empty" don't look identical). For a keyboard, at human typing speed against a 256-byte buffer, this essentially never triggers — but the policy matters conceptually: an ISR must never block waiting for space, so overflow has to resolve instantly, one way or the other, without stalling.
Why Not Just kmalloc a Buffer When Needed?
It's tempting to imagine a fancier, dynamically-sized buffer allocated on demand. The problem is where that allocation would have to happen: inside the ISR, at the exact moment a key arrives. bob_os's heap allocator is not written to be safely re-entered from interrupt context — if the code the ISR interrupted happened to be in the middle of its own kmalloc() call, walking the same free-list data structure from inside the interrupt could corrupt it. The fix used here is the standard one: allocate the buffer once, statically, at compile time (it lives in BSS, zero-initialized), so the interrupt handler only ever does fixed, fast array arithmetic — never allocation.

Put together, this is the same "fast and non-blocking" principle from the ISR section, just applied one layer further down: not only does the handler avoid doing slow work, its one piece of shared state is deliberately structured — fixed size, power-of-2, single-writer-per-index, volatile — so that handing data off to the rest of the kernel costs almost nothing and needs no synchronization primitive that doesn't exist yet.

07 — The Part That Isn't Stateless

Why Modifiers Need Memory Across Events

Here's the conceptual trap: it's tempting to think of scancode translation as a pure function — one input byte, one output character, no history required. That's true for ordinary letter keys. It is not true the instant Shift, Ctrl, or Alt enter the picture, because those keys don't produce a character themselves at all — they change how every subsequent scancode should be interpreted, for as long as they stay physically held down.

Consider what "Shift+A" actually looks like on the wire. It isn't one event. It's a sequence of at least three, and your driver has to correctly connect them:

#ScancodeMeaningbob_os's Response
10x2ALeft Shift — makeshift_held = 1; — no character produced
20x1EA — makeLooks up sc_shift[0x1E] because shift_held is true → pushes 'A'
30x9EA — breakBreak bit set, not a modifier → silently ignored
40xAALeft Shift — breakshift_held = 0; — modifiers restored to normal

If your ISR treated scancode 0x1E as a stateless, self-contained event — "always produce 'a', full stop" — Shift would never work, because nothing about the byte 0x1E itself carries any information about what else is currently held down. The information "Shift is down right now" doesn't live in the current scancode; it lives in a variable your driver maintains between interrupts. That's shift_held in bob_os: a small piece of state that persists across many separate ISR invocations, updated by Shift's own make/break events and consulted by every other key's event.

The General Pattern, Beyond Just Shift
A production keyboard driver extends the exact same idea to Ctrl and Alt: one boolean (or small bitmask) per modifier, set on that modifier's make code, cleared on its break code, consulted whenever a non-modifier key's make code needs translating. Ctrl combinations (like Ctrl+C generating an interrupt signal) and Alt combinations (like Alt+Tab) are typically intercepted even earlier — checked before falling through to normal character translation at all — precisely because they mean something other than "type a character." The unifying idea is the same one this whole lesson has been building to: scancodes are events in a stream, and correct interpretation of any one event can depend on the events that came before it.
Tying It Back to Lesson One
This is the natural extension of "scancodes aren't characters." It's not just that translation requires a lookup table — it's that translation sometimes requires a lookup table plus memory of recent history. The hardware still only ever reports "position X changed state." Every layer of meaning on top — which letter, which case, which control combination — is software's responsibility, accumulated one event at a time.
What about non-US keys and extended scancodes? Scancode Set 1 reserves a special prefix byte, 0xE0, before certain keys — arrow keys, the right Ctrl/Alt, the Windows/Super key, and others added after the original 84-key layout. Seeing 0xE0 tells your ISR "the next byte is from the extended set, interpret it differently." bob_os's minimal driver in this module doesn't yet handle the 0xE0 prefix (it simply won't recognize those keys), which is a reasonable simplification for a first pass — and a natural place to extend the driver once the fundamentals here are solid.
08 — Quick Reference

Glossary & Key Terms

IRQ1
The hardware interrupt line dedicated to the keyboard controller, mapped to CPU vector 33 in bob_os after PIC remapping.
Make Code
The scancode byte sent when a key goes down. Top bit (bit 7) is 0.
Break Code
The scancode byte sent when a key is released. In Set 1, it's the make code with bit 7 forced to 1 — make | 0x80.
Scancode Set 1
The original, oldest PS/2 scancode numbering scheme, still the default the 8042 controller presents on QEMU and real BIOS-initialized keyboards.
Extended Scancode (0xE0 prefix)
A lead byte signaling that the following scancode belongs to an extended key set (arrows, right Ctrl/Alt, etc.) added after the original layout.
ISR (Interrupt Service Routine)
The handler function that runs when an interrupt fires — must be fast and non-blocking, deferring real work to code outside interrupt context.
EOI (End of Interrupt)
The signal sent to the PIC after handling an interrupt, telling it to deliver further interrupts on that line. Skipping it silences the IRQ permanently.
Ring Buffer
The fixed-size circular buffer the ISR writes translated characters into, and the main kernel loop reads from — the hand-off point between interrupt context and normal code.
volatile
A C qualifier forcing every read/write of a variable to touch real memory instead of a cached register value — required whenever an ISR and normal code share state.
Modifier Key
Shift, Ctrl, or Alt — a key that produces no character of its own, but changes how subsequent scancodes are translated for as long as it's held.
shift_held
bob_os's persistent state variable tracking whether Shift is currently down, updated by Shift's own make/break events and read by every other key's translation.
