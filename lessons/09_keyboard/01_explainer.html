Scancodes,
Not Letters

When you press the "A" key, the keyboard does not send the letter "A" to your computer. It has no idea what a letter is. It sends a small number identifying a physical switch, and it is entirely up to your kernel to decide what that number means. This is the single idea that unlocks everything else about keyboard drivers — and it's why QWERTY, Dvorak, and every non-US layout on Earth are pieces of software, not pieces of hardware.

00 — The Idea Everything Else Rests On

A Keyboard Reports Positions, Not Characters

Here's a genuinely surprising fact once you sit with it: the physical keyboard sitting on your desk contains no concept of the letter "A." It doesn't know English exists. It doesn't know what a QWERTY layout is. What it does know, deep in its own tiny onboard microcontroller, is a grid of switches — rows and columns wired underneath the keycaps — and it constantly scans that grid asking "is anything pressed right now?" That's not a metaphor; it's literally where the word scancode comes from.

When switch position number 30 (decimal) closes, the keyboard's own tiny processor packages up a message that means, roughly, "physical position 30 just went down" — and sends that message down the wire. It does not send "A". It has no way to send "A", because "A" isn't a concept it has access to. The mapping from "position 30" to "the character A" happens entirely somewhere else: in your operating system.

The Aha Moment
A key press generates a scancode — a raw numeric identifier for a physical key position. Translating that number into a character is a software decision, made fresh every single time, by a lookup table your driver owns. The keyboard is a position-reporting device. Your kernel is the thing that decides what those positions mean.

Once that clicks, a pile of things that used to seem like separate facts snap into one picture. Why can you remap Caps Lock to Ctrl in software with no hardware change? Because the mapping was always software. Why does a French AZERTY keyboard produce a "Q" on the physical key most English speakers would call "A"? Because it's the exact same physical position, reporting the exact same scancode, being fed through a different lookup table. Nothing about the wire, the chip, or the electrical signal changed at all.

01 — Meet the Middleman

The PS/2 Controller, Not the Keyboard, Talks to Your CPU

There's actually a small chain of hardware between "finger presses key" and "byte shows up for your driver to read," and it's worth naming each link once so nothing later feels like magic.

That middle box — historically an Intel 8042 chip, and on every modern PC an emulated equivalent baked into the chipset (or, in QEMU's case, software-emulated for you) — is the actual thing your kernel code talks to. You never touch the keyboard directly. You touch the controller, and the controller happens to be sitting between you and whatever's plugged in.

Why "PS/2"? The name comes from IBM's Personal System/2 line of computers (1987), which standardized the small round mini-DIN connector and protocol that keyboards (and later mice) used for the next two decades. USB has mostly replaced the physical PS/2 port on real hardware, but the logical interface — a controller chip exposing ports 0x60 and 0x64 to the CPU — lives on inside every PC's chipset for legacy compatibility, and it's exactly what QEMU emulates for bob_os. Real USB keyboards go through an entirely different, far more complex stack (a USB host controller driver, the USB protocol, and a HID class driver) — one reason this course starts with PS/2.
Why This Matters for Driver Code
Because your kernel talks to the controller, not the keyboard, the exact same port-level code works whether a real PS/2 keyboard, a USB keyboard being translated by the chipset's legacy support, or QEMU's emulated keyboard is attached. The controller is the stable interface. That's the whole point of it existing.

02 — The Two Doors

I/O Ports 0x60 and 0x64

The 8042 controller exposes exactly two x86 I/O ports. Everything your keyboard driver does boils down to reading and occasionally writing these two addresses with the inb / outb instructions — the same port I/O mechanism used for the PIC, the PIT, and every other classic PC peripheral.

PortDirectionNameWhat You Get / Send
0x60ReadData PortThe next scancode byte waiting from the keyboard.
0x60WriteData PortCommands/data sent to the keyboard itself (e.g. set the LED state) — not used by the minimal bob_os driver.
0x64ReadStatus RegisterA byte of status flags — most importantly, "is there a byte waiting at 0x60 right now?"
0x64WriteCommand RegisterCommands sent to the 8042 controller chip itself (e.g. "run self-test," "disable port 2") — controller-level, not keyboard-level.
The Detail That Trips People Up
Port 0x60 means two different things depending on whether you read it or write it, and port 0x64 means two completely different things depending on read vs. write — one gives you status flags, the other accepts controller commands. Same address, opposite meaning, purely based on direction. This is common in old PC hardware and is exactly why io.h's inb/outb take a port number but nothing about "which register" — the register is the combination of port number and direction.

For a minimal driver like the one in this module, you can go remarkably far using only the read side of 0x60. The keyboard fires an interrupt (covered fully in the next lesson) precisely when there's a fresh byte sitting at 0x60 ready to be picked up — so in the common case, you don't even need to check the status register before reading; the interrupt itself is the signal.

The write side isn't unused forever. outb(0x60, 0xED) followed by a second byte is the real PS/2 command to set the Num Lock / Caps Lock / Scroll Lock LEDs, and 0xF3 sets the typematic repeat rate and delay. bob_os's Module 09 driver never sends these — it only reads — but the capability lives at the exact same port, just flowing the other direction. A driver that wanted its Caps Lock LED to actually light up when toggled would write to 0x60, not just read from it.
03 — Mechanics

What Happens When You Read a Byte

Walk through the full sequence once, slowly, with an actual key press. Say the physical "A" key goes down.

  1. 1. The switch closes.Underneath the "A" keycap, a physical contact makes a connection in the keyboard's internal switch matrix.
  2. 2. The keyboard's own tiny processor notices.It's continuously scanning the matrix (typically hundreds of times per second) and detects this specific row/column intersection just changed state.
  3. 3. A scancode byte is generated and serialized.Under the PS/2 protocol's default numbering (Scancode Set 1), the position conventionally called "A" produces the byte 0x1E. The keyboard clocks this out one bit at a time over the PS/2 data line.
  4. 4. The 8042 controller receives it and buffers it.The controller deserializes the bits back into a byte, places that byte into its output buffer (which is exactly what you'll read at port 0x60), and sets a "output buffer full" flag in its status register.
  5. 5. The controller asserts IRQ1.This is the hardware interrupt line dedicated to the keyboard — the CPU gets interrupted, control jumps into your kernel's interrupt-handling machinery. (Precisely how IRQ1 turns into a running ISR is the subject of the next lesson — for now, just know it fires whenever there's a byte waiting.)
  6. 6. Your code reads port 0x60.A single inb(0x60) pulls the waiting byte — 0x1E — out of the controller's output buffer. That read also clears the "buffer full" flag, telling the controller it's safe to accept the next byte.
  7. 7. Translation happens — in software.Your driver looks 0x1E up in a table it owns, and only there does the number become the character 'a'.

Notice What's Missing
Nowhere in steps 1 through 6 does anything know what a "letter" is. Position, byte, buffer, interrupt, read — all pure hardware and raw numbers. The character 'a' doesn't exist until step 7, entirely inside code your kernel wrote. If you deleted your lookup table but kept everything else running, the driver would still correctly receive 0x1E every time that key is pressed — it just wouldn't know it meant anything.
Held keys repeat, and that's the hardware's doing too. Hold a key down and characters keep appearing — that's typematic repeat, and on a real PS/2 keyboard it's handled by the keyboard's own onboard microcontroller, not your driver: after an initial delay, it starts re-sending fresh make codes for the still-held key at a configurable rate, entirely on its own. Your ISR has no way to tell "this is a genuinely new press" from "this is the keyboard auto-repeating" — both look exactly like an ordinary make code arriving at port 0x60. That distinction, if a driver needs it at all, has to be inferred in software from timing, not from anything the byte itself carries.
04 — The Status Byte

What Port 0x64 Actually Tells You

Reading port 0x64 doesn't give you a scancode — it gives you a byte of independent status flags describing the controller's current state. Why Interrupt-Driven Beats Polling Here
A polling driver would sit in a loop reading port 0x64, checking bit 0 over and over, burning CPU cycles waiting for a human to press a key — which, on a keyboard timescale, is an eternity between events. An interrupt-driven driver (what bob_os uses) does none of that: it does nothing at all until IRQ1 physically fires, which only happens the instant bit 0 actually becomes set. The status register still exists and still means the same thing — you're just letting the hardware tap you on the shoulder instead of asking it "are we there yet?" in a tight loop.
05 — Numbers About Numbers

Scancodes Aren't Even One Fixed Numbering

If "the keyboard sends numbers, not letters" was the first surprise, here's a second one that tends to catch people off guard: there isn't even a single, universal numbering scheme for those numbers. The PS/2 world defines three distinct scancode sets, and the byte for "the A key went down" is different in each one.

Scancode Set 1A = 0x1E
The original IBM PC/XT numbering from 1981. Still the set the 8042 controller presents to software by default on real hardware and in QEMU — which is why it's the set bob_os's driver and the next lesson are built around.
Scancode Set 2A = 0x1C
Introduced with the IBM AT (1984) and, in practice, what almost every modern PS/2-protocol keyboard actually speaks natively over the wire today, regardless of when your motherboard was made.
Scancode Set 3rarely used
Also from the AT era; adds per-key configurability (which keys auto-repeat, for instance). Supported by the controller but essentially unused by mainstream operating systems.
So Why Does Software Only Ever See Set 1?
Because the 8042 controller itself performs a translation: even though the physical keyboard is very likely speaking Set 2 on the wire, the controller's default "translation mode" quietly converts every incoming Set 2 byte into its Set 1 equivalent before placing it at port 0x60. Your driver never has to know or care — it always sees Set 1 unless it explicitly reprograms the controller's command byte to disable translation. This is one more layer of exactly the same idea from earlier in this lesson: a controller sitting in the middle, presenting a simplified, stable interface over whatever the actual hardware happens to be doing underneath.

This is also a useful preview of what's coming in the next lesson: because bob_os's driver assumes Set 1 (the controller's translated output), the make/break convention it relies on — break = make | 0x80 — is specifically a Set 1 property. Set 2 encodes press and release completely differently (a distinct 0xF0 prefix byte for releases, rather than a single flipped bit), which is exactly why "which scancode set am I looking at" is a question worth asking early, not an afterthought.

06 — The Payoff

This Is Why Keyboard Layouts Are Pure Software

Now the earlier claim can be made precise. A "keyboard layout" — QWERTY, Dvorak, AZERTY, a German QWERTZ layout, a Japanese JIS layout — is nothing more than a choice of lookup table mapping scancode numbers to characters. The physical hardware underneath is frequently identical or near-identical across all of these. What differs is which table the operating system consults.

✅ What Changes Between Layouts

Only the contents of the scancode → character table your driver owns. Position 0x1E can map to 'a' (QWERTY), 'a' in the same physical spot for Dvorak too (it happens to coincide there), or a completely different letter for AZERTY, where the physical position conventionally labeled "A" on a US keyboard sits under a "Q" keycap in the French layout and is expected to produce 'q'-equivalent behavior.

🚫 What Never Changes Between Layouts

The scancode itself. The switch matrix. The wire protocol. The controller. Port 0x60. IRQ1. None of these know or care what layout you've selected — they report the exact same numbers for the exact same physical positions no matter what software choice sits on top.
The one-line summary character = layout_table[ scancode ] Swap the table, and you've swapped the entire keyboard layout — with zero hardware changes, zero firmware changes, not even a reboot.

This also explains a detail that used to confuse a lot of people switching between US and UK keyboards: the physical keys can be in genuinely different places on some non-US layouts (an extra key near Enter, for instance), but that's a difference in the physical matrix wiring, not the software layer — the OS still just receives whatever scancode that new physical position happens to generate, and maps it through a layout table built for that hardware.

A Common Misconception, Corrected
It's tempting to think "the keyboard knows it's a UK keyboard, so it sends different codes for UK-specific keys." In reality the keyboard just reports whatever position closed — it's the operating system's layout table, selected by the user in software settings, that decides what those reports mean. Two keyboards with identical physical wiring can behave completely differently depending purely on which OS-level layout is active. bob_os's driver, as you'll see in the next lesson, ships with exactly one hardcoded table — a US QWERTY Scancode Set 1 map — which is a deliberate simplification, not a hardware limitation.
07 — Quick Reference

Glossary & Key Terms

Scancode
A raw numeric code identifying which physical key position changed state — not a character, and not tied to any language or layout.
PS/2
The serial protocol and mini-DIN connector standard, from IBM's Personal System/2 line, still emulated by every PC chipset (and QEMU) for keyboard/mouse I/O.
8042 Controller
The (historically Intel) chip sitting between the keyboard and the CPU, exposing ports 0x60 and 0x64 and buffering incoming scancode bytes.
Data Port (0x60)
Read to retrieve the next waiting scancode byte; write to send data/commands to the keyboard device itself.
Status/Command Port (0x64)
Read for controller status flags (like "byte waiting"); write to send commands to the controller chip itself.
Output Buffer Full (OBF)
Status register bit 0 — set when a byte is waiting at port 0x60 for the CPU to read; corresponds to IRQ1 firing.
I/O Port
A dedicated hardware address, separate from RAM, accessed via the CPU's in/out instructions (inb/outb in bob_os's io.h).
Keyboard Layout / Keymap
A software-defined lookup table mapping scancodes to characters — QWERTY, Dvorak, AZERTY, and every non-US layout are all just different tables over identical hardware signals.
Scancode Set
One of three distinct PS/2 numbering schemes (Set 1, 2, 3) for the same physical keys. The 8042 controller translates Set 2 (what most keyboards speak) into Set 1 by default.
Polling
Repeatedly reading a status register in a loop to check if data is ready — wasteful compared to letting an interrupt notify you instead.
IRQ1
The hardware interrupt line dedicated to the keyboard controller — fires whenever a fresh byte is waiting at port 0x60. Fully covered in the next lesson.
