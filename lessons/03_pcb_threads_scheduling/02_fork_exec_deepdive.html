00 — Where We Left Off

That "Parent / Children" Field Was Hiding A Whole Mechanism

Back in the PCB dossier, one field read PPID 3980 → [4022, 4023], captioned "who spawned this process, and what it has spawned — the process tree." We treated that as a given: processes just... have children. But how does PID 4022 actually come into existence? What runs first, the kernel's bookkeeping or the new program's code? And when 4022 eventually finishes, does its PCB just evaporate, or does something else happen first? Those are today's questions, and the honest answer to the first one is genuinely surprising.

01 — The Surprising Core Fact

There Is No "Run This Program" Syscall

If you had to design process creation from scratch, you'd probably reach for something like spawn_process("/bin/ls") — one call, in goes a path, out comes a running program. That is not how Linux, or any UNIX-family kernel, actually does it. There is no such syscall. Instead, "run a new program" is always a two-step dance performed by two completely separate, much more primitive syscalls:

The Universal Idiom fork() — clone the calling process into an exact duplicate
then, usually, exec() — replace the caller's own code with a different program Two narrow tools, composed, instead of one do-everything syscall.

fork() takes the process that is currently running it and clones it into a second, independent, schedulable process — same code, same data, same open files, brand-new PID. exec() (really the execve() family) then throws away a process's current code and data and replaces them with a different program entirely, keeping the same PID. Neither one, alone, is "run a new program." Together, they are.

💡 The Aha Moment — Why Split It Into Two?
This isn't historical baggage; it's a genuinely elegant separation of concerns. fork()'s entire job is "manufacture a new schedulable entity with its own PCB" — nothing about what program that entity eventually runs. exec()'s entire job is "load a specific program into the currently running process" — nothing about where that process came from. Because they're decoupled, you can use either one without the other: exec() alone (no prior fork) is exactly what a login shell does to replace itself, and — as the next paragraph shows — fork() alone, with no exec() at all, is a genuinely useful thing to do.
🟢 fork() Without exec(): When You Actually Want An Identical Twin
Sometimes the goal really is "give me a second copy of exactly what's already running," with no new program involved at all. This is literally how a UNIX shell backgrounds a job with & in some implementations, and it's the classic architecture behind old-school "pre-fork" servers (Apache's prefork MPM is the textbook example): the master process calls fork() repeatedly with no following exec(), producing a pool of worker processes that are identical clones of the master, each one then independently accepting connections. No new program was ever loaded — the clone itself was the point.
02 — fork(): Cloning A Running Process

fork() Duplicates The Calling Process

Think of fork() the way a biology textbook describes a cell dividing: one cell becomes two, each a complete, independent copy of the original, both now free to live separate lives. When a process calls fork(), the kernel builds a brand-new PCB for a child process: a new PID, but — at the instant of the split — the same open file descriptors, the same environment variables, the same code, and (conceptually) the same entire memory image as the parent.

Here's the detail that trips people up the first time they see it: both the parent and the child resume execution from the exact same point — the line immediately after the fork() call — because that's where the parent was when the kernel cloned it. There is no separate "child's starting line." The only way either process can tell which one it is comes from fork()'s own return value, which is different in each:

fork() returns…To whomMeaning
0The child"You are the new process. Your own PID, if you need it, is getpid()."
> 0 (the child's PID)The parent"Cloning succeeded — here is your new child's PID, in case you need to wait() on it later."
< 0The (would-be) parent onlyCloning failed (e.g. too many processes already) — no child was created at all.
 
C — the classic fork() branchpid_t pid = fork();

if (pid == 0) {
    // This branch runs in the CHILD only.
    // pid is 0 here — that's how the child knows it's the child.
    printf("child: my pid is %d\n", getpid());
} else if (pid > 0) {
    // This branch runs in the PARENT only.
    // pid holds the CHILD's new pid here.
    printf("parent: spawned child %d\n", pid);
} else {
    // fork() itself failed — no child exists.
    perror("fork");
}

Notice what this snippet does not do: it never explicitly tells the kernel "now go create a child that starts at some other function." It calls fork() exactly once, and the if/else is how one piece of source code ends up steering two different, now-independent processes down two different paths — purely based on which copy is asking.

03 — The Trick That Makes fork() Fast

Copy-on-Write: Sharing Until Someone Writes

Here's the obvious objection to everything in the last section: if a real process has hundreds of megabytes (or gigabytes) of memory, doesn't fork() have to copy all of it the instant it's called? That would make fork() catastrophically slow for any process with a large memory footprint. The kernel's actual answer is Copy-on-Write (COW), and it's one of the cleaner tricks in all of OS design.

At the moment of fork(), the kernel does not copy the parent's memory pages at all. Instead, it duplicates only the page table — the map of virtual addresses to physical page frames — so that the child's page table entries point at the exact same physical pages the parent is already using. Both processes' entries for those shared pages are then marked read-only, even for pages the parent had previously marked writable.

📖 The Analogy: Sharing a Textbook
Picture two students who both need the same textbook. Instead of photocopying the entire book for the second student the moment they're assigned a partner, the library just says "share this one copy — but no writing in the margins until you get your own." Both students read from the identical physical book, freely, at zero extra cost. Only the instant one of them actually reaches for a pencil to write a note does the library step in, run to the copier, and hand that one student their own private, writable copy of just that page — not the whole book.

That "someone reaches for a pencil" moment is a genuine hardware event: the writing process attempts a normal store instruction to what it believes is ordinary writable memory, the MMU sees the page table entry is marked read-only, and it raises a page fault — not a bug, not a crash, but the exact same fault mechanism you've already met in the memory-addressing material, deliberately engineered as a trap the kernel is waiting to catch. The kernel's fault handler recognizes "oh, this is a COW page," allocates one fresh physical frame, copies just that single page's worth of bytes into it, updates the faulting process's page table entry to point at the new private frame (now writable), and lets the store instruction retry — this time succeeding for real. The other process (and any other pages that were never written) never notices a thing.

⚡ Why This Is Such A Big Performance Win
Consider how fork() is actually used in practice: an enormous fraction of calls to it are immediately followed by exec(), which is about to discard the entire memory image anyway and load a completely different program. Eagerly copying gigabytes of memory the child is going to throw away a few microseconds later would be pure waste — CPU cycles and memory bandwidth spent producing bytes nobody will ever read. Copy-on-Write means fork() stays fast (essentially: duplicate a page table, not the memory it describes) regardless of the parent's size, and actual copying only ever happens for the specific pages that turn out to genuinely need it.
Going further — vfork(), posix_spawn(), and Windows' different answer. Because "fork() immediately followed by exec()" is so common, some systems offer even leaner shortcuts: vfork() skips setting up COW page tables altogether by briefly having the child share the parent's address space directly (with the parent suspended until the child execs or exits), and posix_spawn() wraps the whole fork-then-exec sequence into one library call for callers who never wanted a plain fork() in the first place. It's worth knowing that not every OS made the same design bet: Windows' CreateProcess() really is a single call that both creates a process and loads a program into it — there's no Windows equivalent of "fork() alone." The UNIX two-step is a deliberate design choice, not the only possible one.
04 — exec(): Same PCB, Brand New Program

exec() Doesn't Create Anything — It Replaces Everything

If fork() is "new PCB, old code," then exec() — the execve() family of syscalls — is precisely its mirror image: same PCB, entirely new code. Calling execve() does not create a new process. The calling process keeps its own PID, its own PPID, its own PCB. What changes is everything inside that PCB's memory description: the old program's code, data, heap, and stack are all discarded and replaced wholesale with a brand-new program loaded fresh from disk, and the saved program counter is reset to point at that new program's entry point.

C — the child execs into ls// Runs only in the branch where pid == 0 (the child)
char *args[] = { "/bin/ls", "-l", NULL };
execve("/bin/ls", args, environ);

// If execve() succeeds, THIS LINE NEVER RUNS —
// the process is now running /bin/ls's code, same PID.
perror("execve failed");
_exit(1);

That comment is not decoration — it's the single most important thing to understand about exec(). A successful execve() never returns to the calling code at all, because the code that called it no longer exists in that process's memory to return to. The only way execve() ever returns is if it failed (bad path, permission denied, bad executable format) — in which case the original program is still there, completely intact, exactly as if nothing happened.

🧠 Say The Distinction Out Loud
fork() makes a new PCB that keeps running the old code. exec() keeps the same PCB but starts running entirely new code. One multiplies the number of running processes; the other transforms one process in place. They are not two flavors of the same operation — they're opposites that happen to be used together constantly.
05 — Putting It Together

How A Shell Runs ls

You now have both halves. Here is the exact sequence your shell performs every time you type a command and hit Enter — the textbook illustration of why the two-step design pays off:

  1. You type ls -l and press EnterThe shell process (say PID 900) parses the command line and prepares to run it — but the shell itself must not turn into ls, or it would never come back to give you another prompt.
  2. The shell calls fork()The kernel clones PID 900 into a new child, say PID 901 — a Copy-on-Write duplicate of the shell itself, sharing the shell's memory pages read-only, exactly as in the last section.
  3. Both processes resume — and immediately divergePID 900 (parent) sees fork() return 901 and goes on to call waitpid(901, …), blocking. PID 901 (child) sees fork() return 0 and, instead of continuing as a shell, calls execve("/bin/ls", …).
  4. Only the child execsPID 901's memory is wiped and reloaded with /bin/ls's code. It is still PID 901 — same PCB — but it is now, for all practical purposes, the ls program, not the shell.
  5. ls runs, prints its output, and exitsMeanwhile PID 900 — the original shell — was never touched. It didn't fork again, didn't exec, didn't change at all; it's just been sitting in waitpid() the whole time.
  6. The shell's wait() returns, and you get your prompt backPID 900 collects PID 901's exit status and prints a fresh $ — ready to fork a brand-new child for your next command.

When a process calls exit() (or falls off the end of main(), or is killed by a signal), the kernel immediately reclaims almost everything expensive: its memory pages, its open file descriptors, its page table. But it does not immediately delete the PCB. Why? Because the parent might still want to know how the child ended — its exit status, or which signal killed it — and that information has to be stored somewhere until the parent actually asks for it. So the kernel keeps a stripped-down remnant of the PCB around, and the process enters the zombie state: dead, but not yet fully gone.

The zombie stays exactly like this — occupying a PID and a slot in the process table, contributing nothing, doing nothing — until its parent calls wait() or waitpid(). That call is what programmers mean by reaping: the kernel hands the parent the stored exit status, and only then deletes the last remnant of the PCB. This is exactly the waitpid(pid, &status, 0) call from the shell walkthrough above — the shell wasn't just "waiting" in some vague sense, it was performing the specific act of reaping its zombie child so the prompt could return.

⚠️ Why Zombie Pile-Up Is A Real Resource Leak
A single zombie is harmless. A pile of them is not. Every zombie still occupies a slot in the kernel's process table and still holds onto a PID — and PIDs are a finite resource (on a default Linux config, commonly capped somewhere in the tens of thousands, configurable via /proc/sys/kernel/pid_max). A parent that spawns children in a loop and never calls wait() on any of them will, given enough time, accumulate thousands of zombies and eventually be unable to fork any new process at all — not because it ran out of memory or CPU, but because it ran out of PID slots. This is a genuine, well-known class of production bug, usually caused by a parent process that forgets — or, in a long-running daemon, simply never gets around to — reaping its children.

07 — When The Parent Dies First

Parent Dies First? PID 1 Adopts The Orphan

Zombies assume the parent is still around, just slow to call wait(). But what if the parent dies — crashes, gets killed, exits on purpose — while its child is still running, or is a zombie nobody has reaped yet? The child doesn't die too, and it doesn't get orphaned into limbo either. The kernel immediately gives it a new parent: it gets re-parented, and on Linux that new parent is, by default, PID 1 — historically init, on most modern distributions now systemd.

PID 1 has a standing responsibility baked into how the kernel treats it: it must periodically call wait() on any child that shows up attached to it, precisely because it's going to keep inheriting other processes' orphans for as long as the system runs. This is the actual mechanism that keeps orphaned processes from becoming permanent zombies — someone has to be willing to reap children they never spawned, and on Linux, PID 1 is contractually that someone.

❌ Common Misconception

"An orphaned process immediately becomes a zombie, since its parent is gone." This conflates two unrelated states — orphan describes who your parent is, zombie describes whether you've exited and been reaped yet.

✅ What Actually Happens

An orphan just means "re-parented to PID 1." A re-parented process keeps running completely normally. It only becomes a (very briefly) zombie when it eventually exits — and PID 1 reaps it almost immediately, since reaping orphans is its job.
🧠 Why This Matters In Practice
This is precisely the mechanism daemonizing processes rely on: a program that wants to detach from its launching shell and keep running in the background typically forks, has the original process exit immediately, and lets the child get re-parented to PID 1 — outliving the terminal session that launched it entirely. It's also why, on a Linux box, ps -ef often shows a scattering of long-lived processes with PPID 1: not because systemd launched them originally, but because whatever did launch them is long gone.
08 — Quick Reference

Glossary & Key Terms

fork()
Clones the calling process into a new, independent child process with its own PID and PCB. Both processes resume right after the call, distinguished only by fork()'s return value.
exec() / execve()
Replaces the calling process's code, data, heap, and stack with a different program, keeping the same PID/PCB. Never returns on success.
Copy-on-Write (COW)
The fork() implementation trick: share physical pages read-only between parent and child at fork() time, and only copy a page the moment either side actually writes to it.
Page Fault
A CPU trap fired when an instruction touches memory in a way its page table entry disallows — including, deliberately, a COW-marked write.
wait() / waitpid()
Syscalls a parent calls to block until a child changes state (usually exits), retrieve its exit status, and free its remaining PCB — a.k.a. "reaping."
Zombie Process
A process that has exited but whose exit status hasn't yet been collected by its parent — dead, but still holding a PID and a PCB remnant.
Orphan Process
A still-running process whose original parent has died before it did. Immediately re-parented — on Linux, typically to PID 1.
PID 1 (init / systemd)
The first process the kernel starts at boot. Standing responsibility: adopt every orphan and reap it once it exits, preventing permanent zombies.
vfork() / posix_spawn()
Leaner variants for the common "fork immediately followed by exec" pattern — skipping or wrapping the general-purpose COW machinery.
Reaping
The act of a parent calling wait()/waitpid() on a zombie child, retrieving its exit status and allowing the kernel to finally free its PCB.
