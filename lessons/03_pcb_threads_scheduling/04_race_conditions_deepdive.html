00 — Where We Left Off

The Sentence That Got Skipped Over

You already know threads inside one process share the same address space, the same open files, the same everything — except each gets its own registers, its own stack, its own program counter. And you already read the warning that came with that fact: two threads touching the same variable with zero kernel involvement is fast, but unsafe without discipline, and that "this is precisely why threaded code needs mutexes/locks."

Fair sentence. Completely unhelpful sentence, on its own. It tells you locks exist and never tells you what goes wrong without them, at the level of an actual instruction stream — which means "use a mutex" reads like a rule to obey rather than a fact you could have derived yourself. So let's derive it. By the end of this page you'll be able to look at two lines of ordinary-looking code running on two threads and predict, correctly, whether they can silently corrupt each other's work.

01 — The Aha the Base Module Skipped

Something That Looks Atomic Usually Isn't

Here's a line of code so ordinary you've written it a thousand times without thinking twice:

The line everyone assumes is one step counter++; One line of source code. One semicolon. Looks like a single, indivisible action — read it, bump it, done.

It is not one step. Not even close. The CPU doesn't have an instruction that means "go find this variable in memory, add one to it, and put it back," all in a single uninterruptible motion. What it actually has is three separate, independently-schedulable instructions, and the compiler quietly expands your one line into all three:

// what you wrote:
counter++;

// what the CPU actually executes — three separate instructions:
LOAD   R1, counter     // (1) read the current value of counter from memory into a register
INC    R1              // (2) increment the register — memory itself is still untouched
STORE  counter, R1   // (3) write the register back out to memory

Three instructions, three separate moments in time, with a register sitting in between holding a value that only the executing thread can see. As long as exactly one thread is doing this, it's harmless — the three steps always run back-to-back, and the result is always correct. The trouble starts the instant a second thread is allowed to run any of its own load/increment/store sequence on the same memory location before the first thread has finished all three of its steps.

💡 The Aha Moment
"Atomic" is not a property of how a line of code looks in your source file. It's a property of whether the hardware executes it as one uninterruptible unit. counter++ looks atomic because it's short. It isn't atomic, because underneath, it's a load, then a separate increment, then a separate store — three points where another thread could legally step in.
Real-world escape hatch: hardware often does provide a genuinely atomic increment — x86 has a LOCK XADD instruction, for instance, that performs load-modify-store as one indivisible, bus-locked step. But your compiler will only emit it if you explicitly ask for atomic semantics — std::atomic<int> in C++11, AtomicInteger in Java, atomic.AddInt64 in Go. Plain int counter with plain counter++ gets you the naive three-instruction version, every time, on every mainstream compiler.

Worth being precise about why the compiler doesn't just make everything atomic by default: bus-locked atomic instructions are meaningfully slower than their ordinary counterparts, because on a multi-core machine they have to coordinate across cores — stalling other cores' access to that same cache line while the atomic operation completes. If every plain variable increment paid that cost, most programs would slow down for a guarantee the vast majority of code never actually needs, since most variables are never touched by more than one thread. So the default is fast-and-unsafe, and atomicity is something you opt into, deliberately, only where it matters.

And this three-instruction pattern isn't unique to ++. Any read-modify-write on shared state has the same shape: balance -= amount, list.append(item), flag = flag || newCondition — all of them decompose into "read the current state, compute something from it, write the result back," and all of them are vulnerable to exactly the interleaving you're about to see below. counter++ is just the smallest possible example that still shows the whole mechanism.

02 — Watch It Happen

The Interleaving That Loses an Entire Increment

Let's make this concrete instead of hand-wavy. Two threads, Thread A and Thread B, both run counter++ on a shared variable that currently holds 5. If they ran one after another, with no overlap, the answer is obviously 7: 5 → 6 → 7. Here is a perfectly ordinary interleaving — no malice, no bugs in either thread's code, nobody did anything wrong in isolation — that instead lands on 6.

  1. Thread A: LOADA reads counter from memory. Its register, RA, is now 5. Memory itself still says 5.
  2. ⚡ PreemptedBefore A can run INC, the scheduler cuts it off — a timer interrupt, or A simply loses the core to B on another physical core. A is frozen mid-job, holding RA = 5.
  3. Thread B: LOADB now reads counter from memory. It's still 5 — A never got far enough to change it. B's register, RB, is now 5.
  4. Thread B: INC, then STOREB increments RB to 6, then stores it back. Memory now correctly says 6 — as far as B knows, it just did its job perfectly.
  5. Thread A resumes: INCThe scheduler lets A continue exactly where it paused. A never re-reads memory — it already has RA = 5 sitting in its register from step 1. It increments that stale value: RA becomes 6.
  6. Thread A: STORE — the update vanishesA writes RA (6) back to memory. Memory now says 6 — overwriting B's write, which also produced 6, purely by coincidence of both starting from 5.
Expected vs. actual 5 + 1 + 1 = 6, not 7 Two increments happened. Only one is reflected in memory. That silently disappeared increment is the entire definition of a lost update — the signature symptom of a race condition.

⚠️ Nobody Did Anything Wrong
Look back at those six steps. Thread A's code is correct. Thread B's code is correct. Neither thread is buggy in isolation — you could unit-test each one forever and never see a problem. The bug exists only in the interleaving, in the timing relationship between two otherwise-correct pieces of code. That's what makes race conditions uniquely nasty: they're not in any one function you can read and audit; they're in the gaps between functions.

Zoom out from "a counter" for a second, because the pattern generalizes to something that costs real money. Imagine counter is actually a bank account balance, and instead of incrementing it, Thread A and Thread B are each processing a $50 deposit at the same moment on the same account. Run the exact same interleaving — both LOAD the starting balance, both compute "+$50" in their own private register, both STORE — and one entire $50 deposit evaporates, silently, with no error, no exception, no log line to point at. The customer's receipt says the deposit went through. The ledger disagrees. This is not a hypothetical: unguarded read-modify-write races on financial and inventory systems are a real, recurring, expensive category of production bug, and the mechanism is exactly the one you just watched happen to a variable named counter.

💡 How To Spot One in the Wild
The tell is always the same shape: some piece of state is read, then a decision or computation is made based on that read, then the state is written back — and any other thread could touch that same state in the gap between the read and the write. "Check if the seat is free, then book it." "Read the current stock count, then subtract one." "See if the file exists, then create it." All read-modify-write. All racy without a lock.
03 — Tying Back to the Kernel

The Scheduler Makes This Worse, Not Better

Here's the part the base module set you up to understand but never connected: you already learned that the kernel can preempt a running thread at essentially any point, because a hardware timer interrupt fires hundreds to a thousand times a second, completely independent of what the running code is doing. It doesn't wait for a convenient moment. It doesn't know or care that a thread is halfway through a load/increment/store sequence. It can land between LOAD and INC. It can land between INC and STORE. It can land anywhere.

That means the bad interleaving from the last section isn't some rare, hard-to-trigger edge case that only shows up if you're unlucky or malicious. It's a routine, statistically inevitable consequence of two threads touching the same unprotected memory, given enough iterations. Run counter++ from two threads a million times each with no lock, and you will not get 2,000,000. You'll get some smaller number, and it'll be a different smaller number practically every run — because exactly which interleavings occurred depends on scheduling decisions and interrupt timing that are, from your program's point of view, essentially random.

🔑 And Multi-Core Makes It Worse Again
Everything above assumed the two threads take turns on one core, interleaved in time. On a multi-core machine — which is to say, on basically every machine — Thread A and Thread B can be running their LOAD/INC/STORE sequences on two physically separate cores at the exact same instant, not just interleaved but genuinely simultaneous. You don't even need a preemption for the race to occur; you just need ordinary, unremarkable concurrent execution. Multi-core didn't invent race conditions, but it turned them from "an occasional consequence of scheduling" into "the default outcome of running code in parallel without coordination."

This is also why race conditions are so miserable to debug: they're timing-dependent, so they can pass every test you run on your laptop and then show up once a month in production under real load, on a machine with a different core count, a different scheduler mood, a different set of background processes stealing time slices. The bug was always there. The interleaving that exposes it just wasn't common enough to hit in your test run.

There's a second, subtler multi-core effect worth flagging even though it's a step beyond what this page needs to fully unpack: false sharing. CPU caches move data around in fixed-size chunks called cache lines (64 bytes on most modern hardware), not single variables. If counter for Thread A and some unrelated variable used only by Thread B happen to land in the same 64-byte cache line, the cores end up fighting over that line even though the two threads never touch each other's actual data — a performance problem, not a correctness one, but it's another reminder that on real multi-core hardware, "shared memory" has physical consequences that go beyond the clean load/store model in a textbook.

🔁 Adding It Up
Preemption can land mid-instruction-sequence at any time. Multiple cores can execute truly simultaneously. Neither of those facts is a bug in the scheduler or the hardware — they're the entire point of preemptive, multi-core scheduling, which is what makes your machine fast and responsive. The cost of that design is that your code now has to explicitly declare "don't interleave here" wherever it matters, because the kernel has no way to know which few instructions in your program were secretly meant to be one atomic unit.
04 — Naming the Danger Zone

The Critical Section

Now that you've seen the mechanism, it's worth naming the exact span of code where the danger lives. The critical section is the specific span of code that touches shared, unprotected state — in our example, precisely the three instructions LOAD, INC, STORE. Not the whole function. Not the whole program. Just that narrow window during which a thread has read a value it hasn't yet finished acting on.

A precise definition Critical section = any code that must run to completion, on shared state, without another thread interleaving into the middle of it Everything before the LOAD and everything after the STORE is perfectly safe to interleave freely. Only the window in between is dangerous.

Every synchronization primitive that exists — mutexes, spinlocks, futexes, semaphores, the works — exists for exactly one purpose: guaranteeing that only one thread is ever inside a given critical section at a time. That guarantee has a name, and it's hiding in plain sight in the word you've been reading this whole page: mutual exclusion — mutually excluding every other thread from a region that's currently occupied. Say "mutex" out loud slowly and you're saying "MUTual EXclusion." That's not a coincidence; that's the entire feature, compressed into a name.

🧠 One Sentence That Explains All of Synchronization
If you remember nothing else from this page: a race condition happens when two threads are both inside the same critical section at the same time. Every lock, of every kind, at every layer of the stack, exists solely to make that impossible.

It helps to mark the boundary explicitly, because "critical section" is a property of a specific stretch of code, not of a whole function or a whole program:

void increment(Counter* c) {
    setup_local_state();          // safe to interleave freely — touches no shared state

    // ---- critical section begins ----
    c->value = c->value + 1;    // LOAD, INC, STORE on shared memory — the danger zone
    // ---- critical section ends ----

    log_locally("incremented");   // safe again — no shared state involved
}

✅ Outside the critical section

Local variables, function arguments, anything not visible to other threads — freely interleavable, no lock needed, no race possible, because there's nothing to race over.

⚠️ Inside the critical section

Any read-modify-write touching state another thread can also reach — this, and only this, is what a lock needs to wrap. Lock too little and you're back to a race; lock too much and you've turned a concurrent program into an accidentally serial one.
05 — The Standard Tool

Meet the Mutex

A mutex is a lock object with exactly two operations: lock() (sometimes called acquire()) and unlock() (release()). The rule is simple to state and absolute in effect: a thread calling lock() either gets the mutex immediately, if it's currently free, or it gets blocked — moved into the BLOCKED state you met on the PCB dossier in the last module, set aside by the scheduler entirely — until whichever thread currently holds the mutex calls unlock(). At that point the kernel wakes exactly one waiting thread, moves it back to READY, and eventually schedules it to actually acquire the lock and proceed.

void increment(Counter* c) {
    mutex_lock(&c->lock);      // blocks here if another thread already holds it
    c->value++;                 // the critical section — now provably safe
    mutex_unlock(&c->lock);    // wakes the next waiting thread, if any
}

Notice what changed versus the bare counter++: the three-instruction load/increment/store sequence is now wrapped so that no second thread can ever be inside it while the first is still there. Run the mutex-protected scenario in the canvas above again if you skipped it — Thread B doesn't spin, doesn't retry, doesn't waste a single cycle guessing. It's parked, asleep, until the kernel taps it on the shoulder.

✅ Blocked, Not Busy
"Blocked" is the operative word. A thread waiting on a mutex isn't consuming CPU while it waits — it's sitting in the same BLOCKED state a thread enters while waiting on disk I/O or a network packet. The scheduler is completely free to run other, unrelated, ready threads on that core in the meantime. This is precisely why mutexes are the default, go-to synchronization tool for ordinary application code: waiting costs you nothing but latency, never wasted CPU cycles.

Two practical failure modes are worth knowing before you go add mutexes everywhere. First: a thread that calls lock() a second time on a mutex it already holds — without an unlock in between — will simply block forever, waiting for itself to release something it's still holding. Ordinary mutexes aren't reentrant by default; if you need that pattern, you reach for a specifically-documented recursive mutex instead, which tracks an owner and a count. Second: forgetting to call unlock() on every exit path out of a function — including exception/error paths — leaves the mutex permanently held, and every other thread that ever calls lock() on it blocks forever too. This is exactly why most languages pair mutexes with a scope-based guard (C++'s std::lock_guard, Rust's MutexGuard, Python's with lock:) that calls unlock() automatically when control leaves the block, no matter how it leaves.

Mutex vs. semaphore, briefly: a mutex is really a special case of a more general primitive called a semaphore — a counter that lock()/wait() decrements (blocking if it would go below zero) and unlock()/signal() increments. A mutex is a semaphore capped at 1, with the extra rule that only the thread that acquired it may release it. A general semaphore initialized to N instead lets up to N threads through at once — the tool of choice when the shared resource has more than one interchangeable unit, like a fixed-size connection pool.
06 — The Honest Alternative

Spinlocks: Waiting Without Sleeping

A spinlock is a lock with the same intent — mutual exclusion around a critical section — but a completely different waiting strategy. Instead of blocking, a thread that can't acquire a spinlock just loops: check if it's free, check again, check again, "spinning" in a tight loop, burning CPU cycles the entire time, until the lock becomes available.

That sounds obviously worse than a mutex — you're wasting CPU instead of yielding it, right? Not always, and the honest tradeoff is worth sitting with rather than dismissing. Blocking on a mutex isn't free either: putting a thread to sleep and later waking it up means a full context switch, at minimum, possibly twice (once to sleep, once to wake) — and you already know from the last module that a context switch, especially one that crosses process boundaries, is real, measurable, non-trivial work. If the expected wait for the lock is shorter than a context switch would cost, spinning and immediately getting the lock beats sleeping and paying two switches to wait for something that was about to free up anyway.

Those numbers are order-of-magnitude, not gospel — actual costs depend heavily on the CPU, the OS, and whether the wake path has to cross cores — but the ratio is the point: a context switch can easily cost a thousand times what a single spin check costs. Spin for a handful of iterations while genuinely waiting on a lock that's about to be released, and you're still cheaper than blocking. Spin for a long time because the holder is stuck doing disk I/O with the lock held, and you've just wasted a huge amount of CPU for nothing — which is exactly why holding a spinlock across anything that could block (I/O, another lock, a page fault) is considered a serious bug in kernel code.

✅ Spinning makes sense

Critical section is a handful of instructions, expected to be held for nanoseconds — common deep inside kernel code (interrupt handlers, scheduler internals) protecting tiny shared data structures, on systems with multiple cores so the lock-holder is actively running elsewhere and will finish soon.

⚠️ Spinning backfires

Critical section is long, or might block on I/O while held, or you're on a single core (the spinning thread just burns the only CPU that could ever free the lock) — the waiting thread can spin for a very long time doing nothing useful, starving everything else that wanted that core.
📌 Why This Is Rare in Application Code, Common in the Kernel
Ordinary user-space application code almost always reaches for a mutex, because you rarely have tight guarantees on how short your critical section will stay, and wasting a whole CPU core spinning is a bad trade for typical app workloads. Inside the kernel itself, though, spinlocks are everywhere — protecting very short, very hot data structures where a context switch would cost dramatically more than the few dozen cycles spent spinning. Same tool, same goal (mutual exclusion), radically different verdict depending on how long the wait is expected to be.
07 — What's Actually Under the Hood on Linux

The Futex: Fast Userspace Mutex

Here's a question worth asking: if calling into the kernel to block and wake a thread is genuinely expensive, why does every pthread_mutex_lock() call on Linux seemingly involve the kernel at all? The honest answer is: most of the time, it doesn't. The mechanism that makes this possible is the futex — literally short for "fast userspace mutex" — and it's the real machinery underneath most user-space mutex implementations on Linux today.

The clever optimization is a split into two paths, and it hinges entirely on whether the lock is actually contested:

lock(futex_word) {
    if (compare_and_swap(futex_word, 0, 1))
        return;                                     // uncontended: pure userspace, zero syscalls

    syscall(SYS_futex, &futex_word, FUTEX_WAIT, 1);   // contended: ask the kernel to sleep us
}
  • Uncontended case (nobody else wants the lock): acquiring and releasing it is done entirely with a userspace atomic CPU instruction — a compare-and-swap (CAS) that flips a single word from 0 to 1. No syscall, no kernel involvement whatsoever, no cost beyond a couple of machine instructions. This is the overwhelmingly common case in most real programs.
  • Contended case (someone's already holding it): only now does the thread make an actual futex() syscall, asking the kernel to put it to sleep — genuinely BLOCKED, off the CPU — and the holder's eventual unlock() makes a matching syscall to wake it back up.

The name is the whole idea, restated: it's fast precisely because it only pays the "ask the kernel" tax exactly when it's truly unavoidable — when there's real contention that requires putting a thread to sleep. For the common, lucky case of an uncontended lock, a futex-backed mutex is barely more expensive than incrementing a variable.

Real-world fact: the futex syscall was added to Linux in 2003 (kernel 2.5.7) specifically because glibc's threading library needed a way to build fast mutexes without paying a syscall on every single lock/unlock pair. Today, pthread_mutex_t, std::mutex in C++, and the locks underneath most language runtimes on Linux are, one layer down, futexes.

One more detail that shows how carefully this is engineered: when unlock() happens and there are multiple threads waiting, the kernel-side FUTEX_WAKE operation can be told to wake exactly one waiter rather than all of them. Waking every waiting thread just so all but one immediately discover the lock is taken and go back to sleep is called the thundering herd problem — a burst of wasted context switches for nothing. A well-implemented futex-backed mutex wakes precisely as many threads as could plausibly make progress, which in the simple mutex case is exactly one.

08 — The Cost of Fixing It Carelessly

Locks Solve Races. They Can Cause Deadlock

Locking everything isn't automatically safe — it trades one failure mode for another if you're not careful. The classic illustration is the Dining Philosophers problem: five philosophers sit around a round table, a single fork placed between each adjacent pair — five forks total. To eat, a philosopher needs both the fork to their left and the fork to their right. If every philosopher simultaneously picks up the fork on their left, every single fork is now held, and every philosopher is stuck waiting forever for the fork on their right — which will never come, because whoever holds it is equally stuck waiting on their own left neighbor's fork. Nobody eats. Nobody ever will, without outside intervention.

That frozen standstill is a deadlock: a set of threads each holding a resource the next one needs, in a closed loop, none willing to give up what they're holding. Computer science names four conditions that must all be true simultaneously for deadlock to occur — break any single one, and deadlock becomes structurally impossible.

Mutual Exclusion1 of 4
At least one resource (a fork, a lock) can only be held by one thread at a time — which is, uncomfortably, exactly the property mutexes exist to provide in the first place.
Hold and Wait2 of 4
A thread is holding at least one resource while simultaneously waiting to acquire another one held by someone else — like a philosopher gripping their left fork while reaching for the right.
No Preemption3 of 4
A resource can't forcibly be taken away from the thread holding it — it can only be released voluntarily. Nobody can walk up and pry a fork out of a philosopher's hand.
Circular Wait4 of 4
There's a closed loop of threads, each waiting on a resource held by the next one in the circle — philosopher 1 waits on 2's fork, 2 waits on 3's, ... , and the last waits on 1's.
⚠️ Why This Matters Right After Learning Mutexes
The moment you start sprinkling mutexes around shared state to fix races, you've reintroduced mutual exclusion, hold-and-wait becomes possible the instant any thread needs two locks at once, and preemption of a held lock is exactly what a mutex refuses to allow by design. Three of the four conditions come essentially free with correct, ordinary mutex usage. The only one left to actively defend against is circular wait.

Which leads to the simplest practical fix in wide real-world use: a strict, consistent lock-ordering convention — decide on one global order for every lock in your system (by memory address, by an assigned ID, whatever's consistent), and require every single thread, everywhere in the codebase, to always acquire locks in that same order, never the reverse. If every philosopher were instead required to always pick up the lower-numbered fork first, deadlock becomes structurally impossible — there's no way to form a circular wait when everyone is queuing up in the same global direction. It costs nothing at runtime and requires zero clever detection machinery; it just requires discipline enforced at the moment locks are taken.

Lock ordering isn't the only strategy in the toolbox, just the cheapest one. Some systems instead use timeout-based acquisition — try_lock_for(500ms) — and back off, release whatever they're holding, and retry if they can't get everything they need in time, trading a guaranteed-no-deadlock property for occasional wasted retries. Databases go further and run actual deadlock detection: periodically build a graph of who's waiting on whom, look for cycles, and forcibly abort one transaction to break the cycle if one is found. Both are heavier machinery than lock ordering, and both exist because lock ordering requires every piece of code touching those locks to cooperate — which gets harder to guarantee as a codebase grows across teams.

🧠 The Throughline
A race condition is what happens when you forget to protect a critical section. A deadlock is what happens when you protect too many critical sections, in an order that lets threads box each other in. Both are consequences of the exact same underlying fact: threads share memory by default, and coordinating access to it is a real design problem, not a checkbox you tick once by sprinkling lock() calls around and moving on.
09 — Quick Reference

Glossary & Key Terms

Race Condition
A bug that occurs only because of the specific timing/interleaving of two or more threads touching shared state — correct in isolation, wrong together, depending on scheduling luck.
Critical Section
The specific span of code that touches shared, unprotected state — for counter++, precisely the load, increment, and store instructions.
Lost Update
The signature symptom of a race condition: two writes happen, but only one survives, because the second overwrote the first without ever seeing it.
Mutual Exclusion
The guarantee that only one thread is ever inside a given critical section at a time — the property every lock exists to provide. It's the "mutex" in "mutex."
Mutex
A lock with two operations, lock() and unlock(). A thread that can't acquire it is put in the BLOCKED state and woken by the kernel once it's free.
Spinlock
A lock where a waiting thread loops, repeatedly checking if it's free, instead of blocking — wastes CPU cycles but avoids context-switch cost, useful only for very short waits.
Futex
"Fast userspace mutex" — acquired via a pure userspace atomic instruction when uncontended (zero syscalls), falling back to a real futex() syscall only when a thread must actually block.
Compare-and-Swap (CAS)
An atomic CPU instruction that checks a memory location's current value and, only if it matches an expected value, swaps in a new one — the building block of lock-free and futex fast paths.
Deadlock
A standstill where a cycle of threads each hold a resource the next one needs, and none will release what they hold — requires mutual exclusion, hold-and-wait, no preemption, and circular wait all at once.
Lock Ordering
A convention requiring every thread to acquire multiple locks in the same global order, which makes circular wait — and therefore deadlock — structurally impossible.
Semaphore
A counting generalization of a mutex — allows up to N threads through at once, decremented on wait()/lock() and incremented on signal()/unlock(), instead of being capped at exactly one holder.
Reentrant Mutex
A mutex variant that tracks an owner and a hold-count, allowing the same thread to lock() it multiple times without deadlocking itself — not the default behavior of an ordinary mutex.
Thundering Herd
The waste that occurs when releasing a lock wakes every waiting thread instead of just one, causing most of them to immediately find the lock taken and go back to sleep.
False Sharing
A multi-core performance problem (not a correctness bug) where unrelated variables used by different threads land on the same CPU cache line, causing needless cross-core contention.
