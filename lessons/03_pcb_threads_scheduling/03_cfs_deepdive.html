00 — Where We Left Off

Two Phrases We Glossed Over

The PCB dossier card in the base module had a field labeled Scheduling Info, with the value written as priority, quantum left and the description "how important the scheduler thinks this process is, and how much more CPU time it's owed right now." Fair enough at the time — we were busy establishing that a PCB exists at all. Then, one section later, in the middle of explaining that the scheduling policy is identical whether you're picking among threads of one process or threads scattered across many, we dropped this sentence: "round robin, priority-based, Completely Fair Scheduler, whatever." And moved on.

Both of those are placeholders for a real, specific, elegant piece of engineering. Modern Linux does not schedule with a fixed round-robin timeslice and a simple priority number. It runs the Completely Fair Scheduler (CFS), the default scheduling algorithm for ordinary tasks since kernel 2.6.23, and CFS decides "who runs next" using a completely different mental model than "give everyone the same slice, in turn." This page opens that box.

💡 Why This Deserves Its Own Page
"Priority, quantum left" makes it sound like the scheduler keeps a countdown timer per task and a coarse priority tag. CFS keeps neither of those things in the way you'd guess. It keeps one running number per task — vruntime — and the entire scheduling decision, every single time, reduces to a one-liner: run whoever's vruntime is lowest. Everything else in this page is just explaining what that number means and how the kernel finds the minimum fast enough to do it thousands of times a second.

By the end of this page, you'll be able to answer, precisely: what number is actually being compared when the scheduler picks a task; why two tasks at different nice values don't just get "different-sized turns" but accumulate that one number at genuinely different rates; what data structure holds every runnable task in order and why that specific structure was chosen over the more obvious candidates; and how the whole vruntime story sits underneath an even simpler first-pass decision about real-time versus ordinary versus idle work. That's the full mechanism the base module's two placeholder phrases were standing in for.

01 — The Problem CFS Is Actually Solving

What Does "Fair" Even Mean Here?

Say ten threads are runnable right now and you've got one CPU core. What's the fair way to share it? Your first instinct is probably "give each of them a fixed timeslice, then rotate" — that's plain round robin, and it's not wrong, exactly. But it has a specific, nagging flaw: it treats every task as equally important, and real systems don't want that. Your audio driver's thread and a background log-compression thread should not get identical treatment.

So "fair" needs a better definition than "identical." CFS's actual definition comes from an idealized, imaginary model called perfectly fair, processor-sharing scheduling: imagine the CPU were infinitely divisible — a smooth, continuous resource you could slice into arbitrarily small, simultaneous portions, like a pie you can cut as thin as you like. On that imaginary hardware, every one of N runnable tasks would receive an equal, continuous, simultaneous 1/N share of the CPU at every instant (or a weighted share, if some tasks are declared more important than others). Nobody waits in line. Nobody gets starved. Everyone advances at once, just slower than if they had the whole machine to themselves.

The ideal CFS is explicitly modeling On an infinitely divisible CPU, every runnable task advances at rate (its weight ÷ sum of all runnable weights) — continuously, simultaneously, forever. No real CPU can do this — a real core executes exactly one instruction stream at a time. CFS's entire job is approximating this ideal as closely as it can with hardware that can't actually divide itself.

This isn't a Linux-specific invention, either — the ideal model has a name in the wider scheduling-theory literature: Generalized Processor Sharing (GPS), the theoretical basis behind fair-queueing algorithms used well beyond CPU scheduling, including network packet scheduling (deciding whose packets get sent first on a shared link). CFS is, in a real sense, the CPU-scheduling application of the same family of ideas that gave network engineers Weighted Fair Queueing. Different resource, same underlying question: how do you fairly divide something only one consumer can use at a time, when consumers deserve different-sized shares?

That's the whole game. CFS isn't "a fair algorithm" in the sense of a fixed rule like round robin — it's a simulation. It constantly asks: if the ideal, infinitely-divisible CPU existed, who would be furthest behind their fair share right now? Then it hands the one real CPU to exactly that task, for a little while, and asks the question again. The name is honest: it isn't "the Round-Robin Scheduler" or "the Priority Scheduler" — it's the scheduler that's completely fair, relative to that ideal model, to the degree one real core running one thing at a time possibly can be.

🔁 Plain round robin's notion of "fair"

Every task gets an identical fixed timeslice, in a fixed rotation, regardless of importance. Equal treatment, full stop — which sounds fair until you remember not every task should be treated equally, and round robin has no built-in way to express that a task matters more or less than another.

🎯 CFS's notion of "fair"

Every task advances at a rate proportional to its declared importance (weight), relative to an ideal continuous model — not an identical slice, a proportional one. Two equally-weighted tasks do end up getting equal treatment, as a special case, but importance is a first-class input to the model rather than something bolted on afterward.
Why not just measure and enforce fairness directly? Because you can't — fairness in the ideal model is defined over infinitesimally small time slices, which don't exist on real hardware. CFS instead needs a proxy: a number that tracks, for each task, "how much of its ideal fair share has it consumed so far," updated every time it actually gets to run. That proxy is vruntime, and it's the subject of the very next section.

This wasn't Linux's first scheduler for ordinary tasks, either — worth knowing, because it explains why CFS's design reads as a deliberate correction rather than a first attempt. Kernels before 2.6.23 used a scheduler nicknamed the "O(1) scheduler" for its constant-time complexity, built around fixed priority arrays and heuristics for guessing whether a task was "interactive" enough to deserve a bonus. Those heuristics were notoriously easy to get wrong in ways that were hard to reason about. CFS's designer, Ingo Molnar, replaced the whole heuristic pile with the single, principled idea covered in this page — model the ideal, then track each task's distance from it — partly inspired by Con Kolivas's earlier "Rotating Staircase Deadline" scheduler patches, which had explored similar fairness-first thinking outside the mainline kernel.

02 — The Number Everything Pivots On

vruntime: A Score Where Lowest Wins

Here's the concrete mechanism. Every task CFS manages carries a value called vruntime — "virtual runtime." Think of it like a score in a strange game where the goal is to keep your number low, and everyone's clock ticks at a speed set by how important they are. Every task's vruntime only ever goes up — there's no going back down — but different tasks' vruntime clocks tick at different speeds, even while running the exact same real wall-clock duration.

Concretely: while a task is actually running on the CPU, its vruntime increases roughly proportionally to the real CPU time it consumes, adjusted by a per-task weight derived from its priority (nice value — covered next section). A task with a lower weight (a less favored, "nicer" task) has its vruntime increase faster per unit of real time — meaning it "uses up its fair share" sooner and gets scheduled away sooner. A task with a higher weight (a more favored, higher-priority task) has its vruntime increase more slowly for that same real CPU time, which lets it keep running longer before the scheduler considers it to have had its fair turn.

vruntime accumulation, every time a task actually runs Δvruntime = Δ(real time running) × ( NICE_0_WEIGHT ÷ this task's weight ) NICE_0_WEIGHT is the baseline weight, 1024 — a task at nice 0 running for the same time as another task at nice 0 accumulates vruntime at exactly the same rate: the multiplier is 1024/1024 = 1.

Sit with that formula for a second, because it's the whole trick. A heavier (more important, lower-nice) task divides by a bigger weight, so the multiplier shrinks below 1 — its vruntime crawls upward slowly even while burning real CPU seconds. A lighter (less important, higher-nice) task divides by a smaller weight, so the multiplier grows above 1 — its vruntime rockets upward for the same real time spent running. The scheduler doesn't need to know anything about "priority" as a separate concept once vruntime exists — priority has already been baked directly into how fast the score climbs.

🎮 The Game Analogy, Made Precise
Picture a co-op game where every player has their own stopwatch, and the rule is "whoever's stopwatch reads the least gets to move next." Important players (low nice, high weight) have stopwatches that run in slow motion — they get to make lots of moves before their watch catches up to everyone else's. Background, low-priority players have stopwatches running in fast-forward — their watch races ahead, so they get skipped more often. Nobody is ever permanently skipped, though — the moment your watch is the lowest again, whether you're the "important" player or not, it's your move.

And that skip-vs-move rule — "whoever's watch reads the least gets to move" — is, word for word, CFS's actual decision rule. Not a metaphor for it: the literal thing the kernel does. We'll state it as a formula in section 04. First, the weight itself needs a source, and that source is the nice value.

Notice, too, what this formula quietly buys the kernel: it never has to store or reason about "how much CPU time is this task owed for the rest of its life," the way a naive fixed-quantum scheme might. Fairness isn't a running balance the kernel has to remember and pay down — it's an emergent property of always comparing everyone's current score and picking the smallest one. Delete a task from the system, or add a hundred new ones, and the rule doesn't change at all; it just has a different set of numbers to compare.

03 — Where Weight Actually Comes From

Nice Values & the Weight Table

Linux (like classic UNIX before it) lets a process declare how "nice" it intends to be to other processes, via a single integer called the nice value, ranging from -20 (least nice — I want more CPU, get out of my way) to +19 (most nice — I'll happily wait, give others priority). The default, for essentially every process you start, is 0. You've probably typed nice -n 10 ./build.sh or renice without ever seeing what actually happens to that number inside the scheduler.

What happens is: the kernel translates every nice value into a weight via a fixed lookup table, and that weight is exactly the denominator in last section's vruntime formula. Nice 0 maps to weight 1024 — the baseline. Each step away from 0 multiplies the weight by roughly 1.25 (a 25%-ish change) in the appropriate direction, which compounds into a genuinely exponential relationship across the full -20..19 range, not a linear one. That's deliberate: it makes the extremes (nice -20 versus nice 19) enormously different in practice, while adjacent nice values differ only modestly — the same texture as how humans actually want "somewhat less important" to feel different from "run only if literally nothing else wants the CPU."

🧠 One Table, Two Jobs
Notice the weight table does double duty. First, it sets the vruntime accumulation multiplier, which is what actually determines scheduling order moment-to-moment. Second — as a side effect of the ratio between any two tasks' weights — it also determines their long-run relative CPU share whenever both are continuously runnable: two tasks at nice 0 and nice 0 split the CPU 50/50; a nice -5 task (weight 3,121) against a nice 5 task (weight 335) ends up getting roughly 3121/(3121+335) ≈ 90% of the CPU between them, over a long enough window. One number, two consequences.

A Worked Example, With Real Numbers

Formulas are easy to nod along to and hard to actually trust until you push real numbers through them. Say two tasks, P at nice 0 (weight 1,024) and Q at nice 5 (weight 335), are both runnable, and the scheduler hands the CPU to each of them for a 10 millisecond real-time slice in turn.

  1. P runs for 10ms (real time)Δvruntime for P = 10ms × (1024 ÷ 1024) = 10ms × 1.0 = 10ms of vruntime. Nice 0 is the baseline, so its virtual clock ticks in lockstep with the real clock — no surprise there.
  2. Q runs for the same 10ms (real time)Δvruntime for Q = 10ms × (1024 ÷ 335) = 10ms × 3.057 ≈ 30.6ms of vruntime. Q burned the identical 10ms of actual CPU time, but its virtual clock leapt forward roughly three times as far.
  3. The scheduler compares scores, not real timeAfter this single exchange, P's vruntime sits around 10ms while Q's sits around 30.6ms. P is now the lower score, so P gets picked again next — even though both tasks have, so far, received the exact same amount of real CPU time. Q will keep getting shorter, less frequent turns from here on, precisely because its multiplier keeps outrunning P's.
Why this converges to a stable ratio, not to P starving Q entirely. Once P has run enough extra real time to push its vruntime back up near Q's, P stops being the minimum and Q gets picked instead. Run this exchange out over a long window and it settles into P getting roughly 1024/(1024+335) ≈ 75% of the CPU and Q getting the remaining 25% — matching the weight ratio exactly, which is the "long-run relative CPU share" mentioned above, now derived instead of just asserted.
🐳 If You've Ever Set a Container CPU Limit, You've Used This
Every time you set a Docker --cpu-shares value or a Kubernetes pod's resources.requests.cpu, you're setting a weight in this exact same machinery — the Linux cgroup CPU controller's cpu.shares/cpu.weight feeds directly into CFS's group-scheduling mode, where a whole cgroup (all of a container's tasks together) is treated as one weighted competitor in a parent run queue, with the weighted vruntime split recursively among the tasks inside it. There's no separate "container fairness" algorithm — it's the nice-value weight table's exact mechanism, just applied one level higher, to groups instead of individual tasks.
04 — The Actual Decision Rule

CFS's Rule, Stated Simply and Correctly

The entire CFS scheduling decision, in one sentence Of all currently runnable tasks on this CPU, run the one with the LOWEST vruntime. That's it. Not "next in line." Not "highest priority number." The literal minimum of a single floating value, recomputed continuously as tasks run, sleep, wake up, and get created.

Watch what this produces on its own, with no other rule bolted on. A task that just ran for a while has a vruntime that just increased, so it's now less likely to be the minimum — someone else probably has a lower score and runs next. A task that's been asleep (say, blocked on disk I/O) hasn't had its vruntime increase at all while sleeping, so when it wakes up, its old, comparatively low vruntime tends to put it near or at the front of the line again — which is exactly the behavior you want for I/O-bound, interactive tasks: get woken up, get serviced promptly, go back to waiting.

Each bar above is a task's vruntime, climbing over simulated time. Only the task the scheduler judges to be "running" accumulates any vruntime at all in a given instant — exactly like real CFS, where a sleeping or non-running task's vruntime is frozen. Because the sim re-picks the minimum extremely frequently, you'll see the highlighted "running" task hop between bars rapidly, and — this is the point — the bars stay roughly locked together in height rather than one racing far ahead. That's CFS approximating the section 01 ideal: nobody's watch gets to run away from the pack for long, and the low-weight (green) task's bar visibly climbs in bigger jumps each time it's picked, because its multiplier is largest.

⏱ But Doesn't Switching That Often Cost Something?
Yes — this is a real engineering tension, not just a simulation artifact. Switching threads has real overhead (a context switch, as covered in the base module). So real CFS doesn't literally re-pick every nanosecond; it enforces a minimum granularity before it will preempt the running task for a lower-vruntime rival, even if one becomes available sooner. It's a deliberate, tunable compromise between "as close to the ideal as possible" and "don't spend more time context-switching than actually computing."

How Big Is "A While," Precisely?

CFS gives that "a while" a real, tunable shape through two numbers. sched_latency is a target period — historically defaulting around 6 milliseconds — within which, ideally, every currently runnable task gets at least one turn. A task's actual slice length is computed as roughly sched_latency × (its weight ÷ total weight of every runnable task on this core), which is just the section 01 ideal made concrete for a fixed window instead of an infinitesimal instant. But if forty tasks are runnable at once, dividing 6ms forty ways gives slices so tiny that context-switch overhead would dominate — so a second number, sched_min_granularity (historically around 0.75ms), acts as a floor: no task's slice is allowed to shrink below it, even if that means the "ideal period" stretches longer than sched_latency to accommodate everyone.

05 — Finding the Minimum, Fast, Over and Over

Why a Red-Black Tree, Specifically

Okay — "run the lowest vruntime" is a clean rule, but it implies a computational problem: with potentially hundreds of runnable tasks on one CPU's run queue, and a scheduling decision needing to happen constantly (every context switch, every wakeup, every timer tick that might trigger preemption), how do you find the current minimum fast, while tasks are constantly being inserted (waking up), removed (blocking, exiting), and re-sorted (their vruntime changing every time they run)?

CFS's answer: keep every runnable task on a CPU in a red-black tree — a self-balancing binary search tree — keyed by vruntime. A plain sorted array or linked list would make "find the minimum" trivially O(1) if you kept it sorted, but keeping it sorted through constant insertions would cost O(n) per insert, shifting everything else. A plain unsorted list makes insertion O(1) but finding the minimum O(n) every single time — unacceptable when it happens thousands of times a second. A basic (unbalanced) binary search tree can degrade to a linked list in the worst case, giving you O(n) again. A red-black tree specifically guarantees O(log n) worst-case for insert, delete, and search, no matter what order operations happen in, by enforcing balance rules (a handful of coloring and rotation invariants) on every mutation.

Try Insert Random Task a couple of times before clicking anything else, and look at where the new node lands relative to the existing ones — it slots in purely by vruntime value, with no regard for insertion order, which is exactly the "ordered by key, not by arrival" property a binary search tree gives you for free and a plain queue does not.

Click Run Leftmost a few times and watch the tree reshuffle. The currently-leftmost task runs, its vruntime jumps forward by a chunk sized according to its weight, and — because the tree is re-keyed on the new vruntime values — a completely different task can become the new leftmost immediately. That constant reordering, happening on essentially every scheduling event, is precisely why the balance guarantee matters: an unbalanced tree fed this kind of relentless, adversarial-looking insert/remove pattern is exactly the case that degrades toward a linked list.

⚡ The Detail That Makes This Even Faster Than It Sounds
Technically, finding the minimum in a red-black tree is an O(log n) walk down the left spine. But CFS doesn't even pay that — the kernel's cfs_rq run-queue structure keeps a cached pointer, rb_leftmost, updated incrementally as the tree changes. So the actual "who runs next" lookup on the hot path is O(1): follow the cached pointer. The O(log n) cost only shows up on insert and delete — when a task wakes up, sleeps, or gets re-queued after running — which is exactly where a red-black tree's guarantees are worth paying for.
One more wrinkle: sleepers don't get to "cash in" a huge backlog. If a task slept for ten minutes, its vruntime is now far behind everyone else's — naively, it would win every scheduling decision for a long time once it wakes, monopolizing the CPU to "catch up." Real CFS guards against this: on wakeup, a task's vruntime is adjusted (bumped up close to the run queue's tracked minimum, min_vruntime) so it gets a fair, prompt turn — not an unlimited backlog of free turns.
06 — The Layer Above CFS

Not Every Task Even Reaches the Red-Black Tree

Here's a piece the "vruntime, always run the minimum" story leaves out on its own: vruntime comparisons only happen among tasks that are already competing under CFS. Linux doesn't run every runnable thing through the same red-black tree. The real "which task runs next" decision is a two-level decision — first pick the highest-priority scheduling class that currently has any runnable task at all, and only then, within that one class, apply that class's own algorithm.

⚠️ What This Means in Practice
A single misbehaving SCHED_FIFO task — say, an infinite loop mistakenly given real-time priority — can starve the entire rest of the system, including every SCHED_NORMAL task no matter how favorable its nice value, because the class check happens first and CFS's red-black tree never even gets consulted. This is exactly why SCHED_FIFO/SCHED_RR require elevated privilege to set, and why it's used sparingly and deliberately, not as a general "make my app faster" priority knob.
For completeness: there's actually a fourth class, above real-time. SCHED_DEADLINE (added in kernel 3.14) sits even higher than SCHED_FIFO/SCHED_RR in the real priority order, scheduling tasks by an Earliest-Deadline-First algorithm paired with a bandwidth-reservation mechanism, for workloads that need to guarantee "this much CPU time, within this exact window" rather than just "run me first." It's rarer in practice than the three classes covered above, which is why this page focuses on those — but the full stack, top to bottom, is deadline → real-time → fair (CFS) → idle.

So the fully precise version of the decision is: pick the highest-priority class with a runnable task; within the real-time class, pick by fixed priority and FIFO/round-robin order; within the fair class, pick the lowest vruntime via the red-black tree; the idle class only ever gets a turn when both classes above it are completely empty. CFS, and everything in this page, is entirely the middle tier of that stack.

07 — One Detail the Single-CPU Story Skips

There's One Tree Per Core, Not One Tree Total

Every diagram so far has quietly assumed one CPU core and one red-black tree. Real machines have many cores, and Linux does not keep one single global tree of every runnable task on the whole system — that would mean every core contending on one shared data structure for every scheduling decision, an obvious bottleneck. Instead, each CPU core has its own run queue (its own cfs_rq, its own red-black tree, its own min_vruntime), and a task's vruntime is only ever directly compared against other tasks sitting in the same core's tree.

⚡ Why per-core trees are the right call

No cross-core lock contention on the hot path — picking "who runs next" on core 3 never has to wait on core 0's scheduler doing the same thing. Each core's decision is fully independent, which is exactly what you want when the decision happens thousands of times a second, per core, simultaneously.

⚖️ The cost: queues can drift out of balance

If core 0 ends up with six runnable tasks and core 3 ends up with none, per-core fairness alone doesn't fix that — the tasks stuck behind each other on core 0 are worse off than they'd be spread across idle cores, even though each core's own tree is perfectly "fair" internally.

The fix is a separate mechanism layered on top, called the load balancer. Periodically — and also reactively, whenever a core goes idle and looks for work — the kernel compares how much runnable work sits on each core and migrates tasks from busier cores to idle or lighter ones. Migrating a task means removing its sched_entity from one core's red-black tree and inserting it into another's, with its vruntime re-anchored against the destination core's min_vruntime so it doesn't unfairly jump the queue or get unfairly buried, the same normalization trick used for a task waking up from sleep.

🔧 Related Knob: CPU Affinity
A process can request (via sched_setaffinity(), or the taskset command) that it only ever run on a specific subset of cores, opting out of the load balancer's freedom to move it anywhere. This trades potential load-balancing benefit for cache locality — a task that always runs on the same core keeps reusing that core's L1/L2 cache contents instead of starting cold every time it migrates.
08 — Tying It Back

Back to the PCB Dossier

Remember the dossier card's Scheduling Info field: priority, quantum left? You can now translate that placeholder into the real fields Linux's task_struct actually carries for an ordinary SCHED_NORMAL task: a prio/nice value, the sched_entity struct holding vruntime and load.weight, and a run_node linking the task into its CPU's red-black tree. "Quantum left" was never a literal countdown timer for CFS — there's no fixed quantum to count down at all. What's actually being tracked is a relative position in an ordering, constantly recomputed, not a shrinking allowance.

And "Completely Fair Scheduler, whatever" was quietly doing a lot of work in that earlier sentence. Now you know precisely what it means: an approximation of an idealized, infinitely-divisible CPU, implemented via a virtual clock (vruntime) that ticks at a rate set by weight (derived from nice value), always handing the real CPU to whoever's virtual clock reads lowest, using a red-black tree so that "find the minimum" and "insert/reorder constantly" both stay fast — sitting one layer below an even simpler decision about which scheduling class gets to compete at all.

✅ The Full Picture, One Sentence
Every scheduling decision on a Linux box is: pick the highest-priority class with something runnable, and if that class is CFS, run whoever's vruntime — a real-time-weighted proxy for "share of the ideal fair CPU consumed so far" — is currently lowest, found in O(1) via a cached pointer into a red-black tree that stays balanced in O(log n) no matter how often tasks wake, sleep, or get re-queued. That sentence was hiding, in full, behind eleven words in the base module.

None of This Is Hidden — You Can Read It Live

Everything in this page is directly observable on any running Linux box, no kernel debugger required. A handful of commands turn the abstract vruntime story into numbers on your own terminal:

CommandWhat it shows you
cat /proc/<pid>/schedThe live sched_entity fields for that task — se.vruntime, se.sum_exec_runtime, its current nice value, and more, straight from the kernel
nice -n <N> cmd / reniceLaunch a process at (or change a running process's) nice value — directly picks its row in the weight table from section 03
chrt -p <pid>Show or set a task's scheduling policy and priority — including moving it into SCHED_FIFO/SCHED_RR, the real-time class from section 06
taskset -pc <cpus> <pid>Pin a task to specific cores — the CPU affinity knob from section 07, opting it out of the load balancer
A note on staying current. Everything above describes CFS, which was the default SCHED_NORMAL implementation from kernel 2.6.23 (2007) through kernel 6.5. Starting with Linux 6.6 (2023), the default was replaced by EEVDF (Earliest Eligible Virtual Deadline First) — a scheduler from the same intellectual family, still built on a per-task virtual-time concept and a red-black tree, but that additionally tracks an eligibility time and a virtual deadline per task for tighter latency guarantees. The vruntime/weight/red-black-tree mental model in this page is still exactly the right foundation — EEVDF refines it rather than discarding it — but if you go reading current kernel source and see vdeadline alongside vruntime, that's why.
09 — Quick Reference

Glossary & Key Terms

vruntime
A per-task "virtual runtime" score that increases roughly proportionally to real CPU time consumed, scaled inversely by weight. CFS always runs whichever runnable task's vruntime is lowest.
Run Queue (cfs_rq)
The per-CPU structure holding that core's red-black tree of runnable CFS tasks and its own min_vruntime. Each core has its own — there is no single global run queue.
Load Balancer
The kernel mechanism that periodically migrates tasks between cores' run queues to keep runnable work spread evenly, since per-core fairness alone can't fix an unevenly loaded machine.
Nice Value
A user/administrator-set integer from -20 (least nice, most favored) to +19 (most nice, least favored), defaulting to 0, that the kernel translates into a scheduling weight.
Weight (load weight)
A number derived from nice value via a fixed table (1024 at nice 0) that sets how fast a task's vruntime accumulates relative to real time spent running — and, as a side effect, its long-run CPU share.
NICE_0_LOAD
The baseline weight, 1024, assigned to any task at nice 0 — the reference point every other weight (and every vruntime multiplier) is computed relative to.
Red-Black Tree
A self-balancing binary search tree guaranteeing O(log n) worst-case insert, delete, and search regardless of insertion order — what CFS uses to keep runnable tasks ordered by vruntime.
min_vruntime
A run queue's tracked floor value, used to keep the tree's overall vruntime range from drifting unboundedly and to fairly re-anchor a task's vruntime when it wakes from sleep.
Scheduling Class
The top-level layer that picks which algorithm governs a task at all — real-time, fair (CFS), or idle — checked in strict priority order before any within-class comparison happens.
SCHED_FIFO / SCHED_RR
Real-time scheduling policies, strictly higher priority than any CFS task, used for latency-critical work like audio processing; require elevated privilege to set.
SCHED_IDLE
The lowest-priority scheduling class — only runs when no real-time or CFS task anywhere is currently runnable.
sched_entity
The struct embedded in a Linux task_struct holding a task's CFS-specific bookkeeping: vruntime, weight, and its node in the run queue's red-black tree.
sched_latency / min_granularity
Tunable target period (~6ms) within which every runnable task should get a turn, and the floor (~0.75ms) below which no task's slice is allowed to shrink regardless of how many tasks are competing.
Generalized Processor Sharing (GPS)
The academic ideal-fairness model — an infinitely divisible resource shared continuously in proportion to weight — that CFS is explicitly designed to approximate as closely as one real CPU allows.
Preemption
The kernel forcibly interrupting a running task to switch to another before its slice would naturally end — how CFS actually enforces the "run the lowest vruntime" rule once sched_min_granularity allows it.
