00 — Where We Left Off

The Wall Is Old News Now

You already know the headline: user space is sandboxed, kernel space is privileged, and a system call is the one guarded door between them. What we glossed over is bookkeeping — when the kernel lets a process run, stops it, and hands the CPU to someone else, it needs somewhere to actually write down "here's exactly where this program was, so I can put it back exactly as I found it." That somewhere is today's first character: the Process Control Block.

01 — The Kernel's Dossier On You

What Is a PCB, Really?

Picture a hotel's front desk keeping a card for every guest currently checked in: room number, key status, do-not-disturb flag, what they last ordered from room service, when their reservation started. The Process Control Block (PCB) is exactly this, but for a process, kept by the kernel, one per process (well — per schedulable entity, more on that soon).

The PCB isn't optional bureaucracy — it's the only reason the kernel can stop a process mid-instruction, run twelve other things, and then resume that exact process later as if no time had passed at all. Without it, "pausing" a process would mean losing it forever.

💡 The Aha Moment
A PCB is never touched by user code — it lives entirely in kernel memory, exactly as privileged as the kernel itself. That's not incidental: if a process could edit its own PCB, it could just set its own priority to "run forever" or point its page table at someone else's memory. The PCB being kernel-only is the enforcement mechanism for a huge chunk of what the OS guarantees.
02 — The Critical Difference

Thread vs Process

Back to the restaurant. A process is the whole restaurant location: its own building (address space), its own walk-in freezer (open files), its own lease and business license (resources granted by the OS). A thread is one chef working inside that restaurant. You can have several chefs (threads) working in the very same kitchen (address space) at the same time, each chopping a different vegetable (executing different code), but all of them reach into the same walk-in freezer, because there's only one.

The one-line critical difference A process owns resources. A thread owns nothing but its own execution — and borrows everything else from the process it lives in. Multiple threads in one process share the same memory, same open files, same everything — except each gets its own stack, its own registers, and its own program counter.

⚠️ Why This Makes Threads Dangerous and Cheap
Because threads share memory by default, two threads can read and write the exact same variable with zero kernel involvement — which is fast (no IPC, no syscalls, no copying), but also unsafe without discipline: two chefs grabbing the same knife at once is a race condition. This is precisely why threaded code needs mutexes/locks, while two separate processes are automatically protected from each other by the page-table wall you already know — no discipline required, just less sharing by default.

One more piece of vocabulary worth having: a single-threaded process is really just a process that happens to contain exactly one thread. There's no such thing as a process running with zero threads — the thread is the thing that actually executes; the process is the container of resources around it.

03 — Answering Your Question Directly

Is Scheduling a Process the Same as Scheduling a Thread?

Short answer: the algorithm is the same; the unit it's applied to is not the same, and the cost of switching between units is not the same either. Let's unpack both halves.

Same algorithm, finer-grained unit

Classic OS courses teach "the scheduler picks the next process to run." In reality, on every modern OS (Linux included), the scheduler doesn't actually operate on whole processes — it operates on individual threads (Linux calls the underlying schedulable unit a task, represented by a task_struct, which is really a merged PCB-plus-thread record). A single-threaded process just happens to have exactly one schedulable entity, so the distinction was invisible in the simple case everyone learns first.

🧠 So What Is the PCB, Precisely, in a Multi-Threaded World?
Think of it split into two layers: a shared process-level record holding the things all threads share (address space pointer, open file table), and a per-thread record (sometimes literally called a Thread Control Block, or just a lighter-weight task_struct in Linux) holding the things that must be unique per thread (saved registers, program counter, stack pointer, scheduling state). The scheduler's run queue is a queue of these per-thread records — never a queue of whole processes.

Same algorithm, very different switching cost

Here's the part that actually matters in practice. Whether the scheduler is switching between two threads of the same process, or between threads of two different processes, it runs the exact same priority/quantum logic to decide who goes next. But the mechanical cost of actually performing the switch differs enormously:

🧵 Switch between two threads, same process

Registers and stack pointer change, but the page table stays identical — same address space, so no TLB flush, no expensive memory-mapping reload. This is why threads are often called "lightweight" — the switch is cheap.

🏢 Switch between threads of different processes

Everything above, plus the kernel must load a different page table (a different CR3 value on x86), which typically flushes the translation lookaside buffer (TLB) — a real, measurable performance cost. This is a genuine "process context switch," not just a thread switch.

So to directly answer it: the scheduling policy (round robin, priority-based, Completely Fair Scheduler, whatever) is identical whether you're picking among threads of one process or among threads scattered across many processes — it's one unified run queue of schedulable entities. What differs is purely the execution cost of actually carrying out the switch once it's been decided, because crossing a process boundary means crossing the memory-isolation wall too.

04 — Answering Your Question Directly

Is the Kernel Idle Until a System Call Happens?

No — and this is a common and very reasonable misconception, because syscalls are the door we spent the most time on. But syscalls are only one of three separate doors into Ring 0, and the other two fire constantly, with zero cooperation from any running program.

That third row is the answer to your question. A hardware timer chip fires an interrupt hundreds to a thousand times a second (on traditional "ticking" kernels), completely independent of whether any program made a syscall. Every disk finishing a read, every network packet arriving, every key you press generates its own interrupt. The kernel is woken up by all of these, constantly, whether or not anyone asked it for anything.

✅ So What Does "The Kernel Is Idle" Actually Mean?
When there's genuinely nothing runnable, the CPU doesn't sit inside "kernel code doing nothing" in a busy loop burning power — it runs a special, lowest-priority idle task, which typically executes a halt instruction (like x86's HLT) that pauses the core until the next interrupt of any kind arrives. Modern "tickless" kernels go further: instead of a fixed periodic timer interrupt firing even with nothing to do, they compute the next actually-necessary wakeup and program a one-shot timer for exactly then — saving power, especially on laptops and phones. Either way: the kernel's idle state is itself just another kind of scheduled entity, waiting on the same three doors as everyone else.
05 — Answering Your Question Directly

Registers, Traps, and the PCB

So is a syscall the only time registers get saved? No — any of the three doors above forces at least a minimal register save, because the CPU must be able to resume exactly where it left off no matter which door was used. But there are actually two different levels of "saving," and mixing them up is where most confusion comes from.

▶ Compare a light trap vs a full context switch
  1. Level 1 — The Trap Frame (always happens)The instant any trap fires — syscall, fault, or interrupt — the CPU (often with a little help from the kernel's entry-point code) pushes a small, fixed set of values onto the kernel stack: the program counter, flags register, stack pointer, and a handful of general registers. This minimal bundle is the trap frame. It costs almost nothing and happens on every single trip into Ring 0, no exceptions.
  2. The kernel handles the trapUsing just the trap frame, the kernel runs whatever handler is appropriate — the syscall's logic, the fault handler, or the interrupt service routine. Often, this is fast and the answer is "nothing else needs to change" — e.g., a disk-completion interrupt just marks some data ready and returns.
  3. The kernel decides: reschedule or resume?This is the fork in the road. If the trap handler decides the currently interrupted thread should keep running next (very common for a quick interrupt), the kernel simply restores the trap frame and resumes exactly where it stopped — no PCB/TCB involved at all beyond what was already there.
  4. Level 2 — The Full Context Switch (only sometimes)If instead the kernel decides a different thread should run next — because the current thread's time quantum expired, or it just blocked on I/O, or a higher-priority thread just became ready — then it performs a full context switch: save every remaining register the interrupted thread cares about into that thread's own PCB/TCB, then load an entirely different saved register set from the next thread's PCB/TCB, possibly swap the page table too, and only then return to Ring 3 — now running someone else entirely.
🔑 The Relationship to the PCB, Stated Plainly
The trap frame is a short-lived, on-the-kernel-stack scratchpad used for the duration of handling one trap. The PCB/TCB is the long-term, permanent parking spot for a thread's saved state whenever that thread isn't currently running at all. A full context switch is precisely the act of moving saved register state out of a trap frame and into a PCB/TCB (for the outgoing thread), and pulling previously parked state out of another thread's PCB/TCB and back into live registers (for the incoming thread). Most traps never reach this step — they're resolved with just the cheap trap frame.
06 — Answering Your Question Directly

Shared Memory: When Do Processes Actually Use It?

Threads get shared memory automatically — it's simply what "same process" means. Processes do not: by design, the wall (separate page tables) keeps every process's memory invisible to every other process. So if two processes want to share memory, they have to explicitly ask the kernel to punch a deliberate, controlled hole in that wall — once, during setup. This is exactly what shmget()/shmat() (System V) or mmap() with MAP_SHARED (POSIX) do.

▶ Shared Memory vs a Pipe — Where the Kernel Gets Involved

🐌 Pipe / Socket IPC

Every single message requires a syscall in each direction — the kernel copies data from one process's buffer into its own, then out into the other process's buffer. Safe and simple, but every byte pays the "cross the wall" tax.

⚡ Shared Memory IPC

One-time setup cost: the kernel maps the same physical page frames into both processes' page tables (at possibly different virtual addresses). After that, both processes read and write with ordinary load/store instructions — zero syscalls per access, because the CPU's normal memory hardware, not the kernel, is doing the work.
📌 The Catch: You Traded Safety for Speed
Shared memory removes the kernel's involvement in each access — which also removes the kernel's automatic protection against race conditions. Two processes writing the same shared page at once is exactly as dangerous as two threads doing so, for exactly the same reason: they're now, deliberately, sharing memory. This is why shared-memory IPC is almost always paired with a separate kernel-mediated synchronization primitive — a semaphore, futex, or named mutex — used sparingly, only to coordinate who gets to touch the shared region when, while the actual data transfer stays syscall-free.

So, precisely answering "at which point": processes reach for shared memory when they need to exchange large or frequent data and the per-message cost of pipes/sockets would dominate — think video frame buffers, large scientific datasets, or (as you're about to see) a browser's rendering pipeline. It's a deliberate trade: pay a one-time setup cost through the guarded door, then enjoy unguarded, wall-free access for as long as the mapping lives.

07 — Tying It Back

This Is Exactly What Your Browser Does

Remember the renderer process handing paint instructions to the GPU process via Mojo IPC? In practice, Chromium doesn't want to pay a full IPC round-trip for every single drawing command during heavy rendering or video playback — that's the "pipe" cost, at browser scale. So the renderer and GPU process actually set up a shared memory command buffer: a chunk of memory mapped into both processes once, into which the renderer writes a stream of draw commands directly, with the GPU process reading them out the other side — no IPC message per command, only a lightweight IPC "signal" to say "new commands are ready."

✅ Same Trade-off, One Layer Up
Exactly like OS-level shared memory: one guarded setup step through Mojo IPC (the "door"), then raw, wall-free memory access for the actual high-frequency data (draw commands, video frames), with a small separate signal used only to coordinate timing — the browser's version of a semaphore.
08 — Quick Reference

Glossary & Key Terms

Process Control Block (PCB)
The kernel-only data structure holding everything needed to pause and later perfectly resume a process/thread: state, registers, program counter, memory pointers, open files, scheduling info.
Thread Control Block (TCB)
The per-thread slice of that bookkeeping — unique registers, stack, and scheduling state — while address space and open files stay shared at the process level.
Process
A container of resources: its own address space, open files, and at least one thread of execution.
Thread
A schedulable unit of execution that borrows its process's resources but keeps its own registers, stack, and program counter.
Task (Linux)
Linux's actual scheduled unit (task_struct) — effectively a merged PCB/TCB representing one thread, whether or not it shares a process with others.
Trap Frame
The minimal register/PC/flags snapshot pushed to the kernel stack on every trap (syscall, fault, or interrupt) — cheap, short-lived, always happens.
Context Switch
The full save of an outgoing thread's state into its PCB/TCB and load of an incoming thread's state from its own — only performed when the kernel actually decides to run someone else next.
Exception / Fault
A synchronous, involuntary trap caused by the currently executing instruction itself — a page fault or divide-by-zero, for example.
Hardware Interrupt
An asynchronous, involuntary trap caused by a device, unrelated to whatever instruction the CPU happens to be running.
Idle Task
The lowest-priority schedulable entity that runs (often halting the CPU) when nothing else is ready, until the next interrupt wakes it.
Shared Memory
A region of physical memory deliberately mapped into more than one process's page tables via the kernel, enabling syscall-free reads/writes after a one-time setup.
TLB (Translation Lookaside Buffer)
A CPU cache of virtual-to-physical address translations. Switching page tables (a process-level context switch) typically flushes it, adding real cost beyond a same-process thread switch.
