Before B-trees, before journaling, before permissions even existed, there was a filesystem so simple you can implement it in an evening: a flat array where table[N] tells you what comes after cluster N. That's FAT — and forty-plus years later, it's still the format your BIOS boots from, your USB stick uses, and every OS on Earth can read without asking permission.

00 — The Big Idea

A Filesystem Is Just a Breadcrumb Trail

Strip away every detail and FAT is answering one question, over and over: "I'm looking at chunk of disk number N — where's the next chunk that belongs to this file?" The chunks are called clusters (a fixed group of sectors — say, 4 sectors of 512 bytes each). And the answer to "what comes next" lives in a big, flat, boring array called the File Allocation Table — the thing FAT is actually named after.

The entire idea, in one line table[N] = the cluster number that comes after cluster N in whatever file currently owns it Follow the chain until you hit a special "end of chain" value — that's the last cluster of the file.

That's genuinely most of it. A file isn't stored as one contiguous blob — it's stored as a chain of clusters scattered wherever there was free space, linked together purely through this array. Cluster 5 might be followed by cluster 190, which might be followed by cluster 6. Physically scattered; logically one unbroken sequence, because the table says so.

Why "Allocation Table," Specifically
Two jobs, one array. First, it's the chain: reading table[N] tells you the next cluster of whatever file cluster N belongs to. Second, it's the free space bitmap, just encoded differently than a bitmap: a cluster whose table entry reads 0 is free, full stop. No separate free-list, no separate bitmap structure — the same array that links files together also tracks what's available to hand out next.
01 — The Metadata

The Boot Sector Holds the Instruction Manual

Before any of that chain-walking can happen, a driver needs to know basic geometry: how big is a sector, how big is a cluster, where does the FAT table even start on disk. All of that lives in sector 0 — the volume's boot sector — inside a small header block universally called the BIOS Parameter Block (BPB). It's the same sector that (on a bootable disk) also contains the tiny bit of x86 machine code your BIOS jumps to at boot, which is exactly why bob_os's own bootloader lessons care about sector 0 in the first place.

BPB FieldTypical ValueWhat It Tells the Driver
Bytes Per Sector512The atomic unit of disk I/O this volume assumes.
Sectors Per Cluster1, 4, 8…How many sectors get grouped into one cluster — the FAT's actual unit of allocation.
Reserved Sector Count1 (FAT12/16), 32 (FAT32)How many sectors (including the boot sector itself) come before the FAT table starts.
Number of FATs2FAT is almost always duplicated on disk — a built-in backup copy in case one gets corrupted.
Root Entry Count512 (FAT12/16 only)Fixed size of the root directory — FAT32 removes this limit entirely (see below).
Total Sectorsvolume-dependentHow big the whole volume is, in sectors — used to compute how many clusters exist.

Every other structure on the volume — where the FAT table sits, where the root directory sits, where cluster data begins — is computed from these few numbers. There's no separate "table of contents" pointing to each structure; the BPB is the whole map, and it fits in the first few dozen bytes of the disk.

02 — The Table Itself

Reading a Table Entry

Each slot in the FAT table is a fixed-width number — 12, 16, or 32 bits, depending on which FAT variant you're looking at — and its value means one of a small handful of things:

table[N] ValueMeaning
0x000Cluster N is free — not part of any file, available to allocate.
0x002 – 0xFFEF (roughly)Cluster N is used, and its value is the number of the next cluster in the chain.
0xFF7 (FAT12) / 0xFFF7 (FAT16) / 0x0FFFFFF7 (FAT32)Cluster N is marked bad — the driver should never allocate it (a real disk defect, historically).
0xFF8–0xFFF (FAT12) / 0xFFF8–0xFFFF (FAT16) / 0x0FFFFFF8–0x0FFFFFFF (FAT32)End of chain — this is the last cluster of the file. Stop walking here.

Notice there's exactly one array doing double duty as both "which cluster comes next" and "is this cluster in use at all." A completely empty volume is just a FAT table full of zeros (after a couple of reserved entries at the start), plus an empty root directory. That's the entire "format the disk" operation — there is nothing else to initialize.

A Directory Is Just Another File, Chain-Wise
Past the tiny fixed-size root directory in FAT12/16, every FAT32 directory — including the root — is itself stored as a chain of clusters, exactly like a regular file's data, just interpreted differently: instead of raw bytes, its clusters hold a sequence of fixed-size directory-entry records. Walking a subdirectory's contents means following its starting cluster through the FAT table, precisely the same mechanism used for file data.
03 — Naming Things

The Root Directory: Fixed-Size Entries

The FAT table only knows about cluster numbers — it has no idea any given chain is called readme.txt. Names, sizes, and "where does this file's chain start" all live in a separate structure: the directory, made up of fixed-size 32-byte records, one per file or subdirectory.

Reading a file by name, end to end, is therefore a two-stage lookup: scan the directory's 32-byte entries for a name match to get a starting cluster, then hand that starting cluster to the FAT table and walk the chain until end-of-chain, reading each cluster's data sectors along the way. No indirection blocks, no B-trees — just two flat structures used one after the other.

Where "long filenames" come from: the classic 8.3 format is brutally limiting — no lowercase, no spaces, 8+3 characters max. Windows 95 bolted on VFAT, which stores long names across extra directory entries marked with a special attribute combination that older DOS drivers simply ignore (they just see harmless-looking junk entries and skip past them). It's a genuinely clever backward-compatibility hack layered entirely on top of the original 32-byte entry format — nothing about the underlying FAT table changed at all.

Notice the chain is not in numeric order — 5 → 8 → 12 → 13 → EOC. That's completely normal and, in fact, the common case on a disk that's had files created and deleted over time: free clusters get handed out from wherever they happen to be, and the table is what stitches them back into one logical sequence. This is also exactly why heavily-fragmented FAT volumes get slow — physically jumping the disk head around to satisfy one "sequential" file read.

05 — One Family, Three Sizes

Why FAT12, FAT16, and FAT32 Even Exist

Here's the pleasant surprise: FAT12, FAT16, and FAT32 are not three different filesystems with different structures. They are the exact same design — boot sector, FAT table, directory entries, cluster chains, all of it — differing in exactly one number: how many bits wide each FAT table entry is. That single choice cascades into how many clusters the table can address, which caps how large a volume the format can describe.

VariantBits Per EntryMax Addressable ClustersPractical Max Volume SizeWhere You'd See It
FAT1212~4,084~16 MBFloppy disks, tiny boot partitions
FAT1616~65,524~2–4 GBOld hard disks, early flash cards
FAT3232 (28 used)~268 million~2 TB (spec), often OS-capped smallerUSB sticks, EFI system partition, SD cards

Fewer bits per entry means fewer distinct cluster numbers you can express, which means fewer clusters total, which — for a fixed cluster size — caps the maximum volume size. FAT12's 12 bits cap out around four thousand clusters; that's fine for a 1.44 MB floppy, hopeless for a modern drive. FAT32 only actually uses 28 of its 32 bits (the top 4 are reserved), but that's still enough addressable clusters to describe multi-terabyte volumes, which is why it's the variant still shipping on new hardware today.

The One Real Structural Difference: The Root Directory
There's a second wrinkle worth knowing: FAT12/16 give the root directory a fixed size, stored in its own reserved region right after the FAT tables — commonly capped at 512 entries. FAT32 removes that limit by making the root directory just another cluster chain, exactly like every other directory, so it can grow arbitrarily large. Every other structural idea — boot sector, FAT table, 32-byte directory entries, cluster chaining — carries over unchanged across all three variants.
06 — A Trade-off Hiding in Plain Sight

Cluster Size: The Knob Nobody Warns You About

"Sectors per cluster," sitting quietly in the boot sector's BPB, is one of the more consequential numbers on the whole volume, and it's chosen once, at format time, and effectively baked in from then on. It controls a genuine trade-off between two kinds of waste that pull in opposite directions.

Cluster SizeFAT Table SizeTypical Wasted Space Per File
Small (e.g. 512 B)Large — more clusters to track means more table entriesSmall — a file's last cluster wastes at most ~512 B
Large (e.g. 32 KB)Small — fewer, bigger clusters means fewer table entriesLarge — a file's last cluster can waste up to ~32 KB

Here's the mechanism behind that second column: FAT can only allocate whole clusters, never partial ones. A 1-byte file still consumes one entire cluster. On a volume formatted with 32 KB clusters, a directory full of tiny 1 KB text files can genuinely waste more space to rounding than the files themselves contain — every single one burns a full 32 KB cluster for barely 1 KB of real content. This is exactly why mkfs.fat and Windows' own formatting tool pick cluster size based on volume size: bigger volumes default to bigger clusters, because a FAT12/16-style table just can't stay small if it has to track millions of tiny clusters on a multi-gigabyte disk.

Why Not Just Track Space in Bytes Instead of Clusters?
Because the table itself would explode: addressing every individual byte on even a modest volume would require a table with one entry per byte — billions of entries for a multi-gigabyte disk, hopelessly large to keep in memory or scan. Grouping sectors into clusters is what keeps the table itself a manageable, cacheable size. The wasted "slack space" inside a file's last cluster is the price paid for a table that stays small enough to be practical in the first place — a genuine trade-off, not a design oversight.
07 — Why This, Still

Why FAT Remains a Genuinely Reasonable Teaching Filesystem

FAT is, by any modern measure, ancient and limited: no permissions, no journaling, terrible fragmentation behavior, a filename scheme that needed a backward-compatibility hack bolted on within fifteen years of its own invention. And yet it keeps showing up as the very first "real" filesystem in nearly every OS-dev tutorial that exists — bob_os's own lesson cluster included. That's not laziness; it's a genuinely good pedagogical trade, for two concrete reasons.

✅ Simple Enough to Implement By Hand

The entire read path is: parse a small fixed header, scan fixed-size 32-byte directory entries for a name match, then walk a flat array following integer links until a sentinel value. No B-trees, no journaling replay logic, no extent trees, no compression. A determined student can write a working FAT12 reader in an afternoon — genuinely not true of ext4 or NTFS.

⚠️ But Still Real Enough to Matter

Unlike a toy format invented purely for a tutorial, FAT is what your BIOS/UEFI firmware, every major OS, and every disk-imaging tool already speaks fluently. A FAT volume you build by hand is immediately readable by Windows Explorer, macOS Finder, and Linux's mount — no custom tooling required on the other end.

That second point is exactly why FAT earns its keep even in a project like bob_os. Module 12's own BobFS deliberately skips FAT's complexity entirely — no clusters, no 8.3 names, just a 32-entry superblock and raw sectors — because the point of that module is disk I/O and filesystem concepts, not FAT parsing. But the moment you want your bootable disk image to be mountable by an ordinary desktop OS without any bob_os-specific tooling — inspecting it, dragging files onto it, debugging it with tools you already have — FAT is what you'd reach for. It's the one on-disk format where "hand-rolled and simple" and "universally readable" are the same choice.

The Takeaway
FAT isn't taught first because it's the best filesystem — it's taught first because it's the smallest filesystem that's still a real one. Every concept you need for ext4, NTFS, or any modern format — metadata separate from data, a table mapping logical position to physical location, directories as structured data rather than magic — is present in FAT in its simplest possible form. Learn to walk a FAT chain by hand, and reading the ext4 or NTFS spec afterward is a matter of degree, not of kind.
08 — Quick Reference

Glossary & Key Terms

File Allocation Table (FAT)
The flat array where table[N] holds either 0 (free), a bad-cluster marker, an end-of-chain marker, or the number of the next cluster in a file's chain.
Cluster
The smallest unit of allocation in FAT — a fixed group of sectors (e.g. 4 × 512 bytes) treated as one indivisible chunk when building a file's chain.
BIOS Parameter Block (BPB)
The metadata header in sector 0 recording bytes-per-sector, sectors-per-cluster, reserved sectors, and other geometry the driver needs to locate every other structure.
End-Of-Chain (EOC) Marker
A reserved high value (e.g. 0xFFF8–0xFFFF for FAT16) written into a table entry to mean "this is the last cluster of this file — stop walking here."
8.3 Filename
The classic FAT naming scheme: 8 characters of name, 3 of extension, uppercase, space-padded, stored in a fixed 32-byte directory entry.
VFAT / Long Filenames
A backward-compatible extension storing long, mixed-case names across extra directory entries that older 8.3-only drivers simply skip over.
Root Directory
The top-level directory; fixed-size and separately located in FAT12/16, an ordinary growable cluster chain in FAT32.
Fragmentation
The condition where a file's clusters are scattered non-contiguously across the disk, forcing the FAT chain-walk to jump around physically to read what's logically one sequential file.
