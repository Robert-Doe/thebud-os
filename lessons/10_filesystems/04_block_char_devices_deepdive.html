00 — The Extension

"Everything Is a File" — Including Hardware?

The earlier lessons in this cluster covered how the VFS gives every real, disk-backed filesystem a uniform open/read/write/close interface. Unix took that idea one step further, and made it apply to hardware itself: your disk, your keyboard, your serial port, even /dev/null, all show up as files under /dev, all openable with the same open() call as anything else.

But hardware isn't uniform the way filesystem content is. A disk really can be read in any order, at any position — that's what "random access storage" means. A keyboard fundamentally cannot: there is no "byte 47 of the keyboard," only "whatever key gets pressed next." Unix's answer isn't to pretend these are the same thing. It's to explicitly split device files into two categories that behave differently on purpose, while still sharing the outer open/read/write/close shape.

The Split, Stated Plainly
A block device is addressed in fixed-size chunks and supports random access — you can ask for chunk 4, then chunk 900, then chunk 4 again, in any order, and the kernel buffers/caches chunks in memory between requests. A character device is a stream — bytes arrive (or leave) strictly in order, there's no "chunk number" to jump to, and there's generally nothing meaningful to cache ahead of time because the next byte might not exist yet.
01 — Random Access, In Chunks

Block Devices: Disks Behave Like Arrays

The canonical block device is a disk — /dev/sda on Linux. Its defining trait is that it's addressed by a block number (commonly a 512-byte sector, though modern disks often use 4096-byte physical sectors), and any block can be requested at any time, independent of which block was requested before it. Want block 4? Ask for block 4. Want block 900,000 right after that? Also fine — no ordering requirement at all.

Because random reads and writes to physical storage are comparatively slow and the same blocks are frequently reused, the kernel sits a buffer/page cache between programs and the actual device: recently read blocks stay in RAM, and writes are often batched and flushed rather than hitting the disk instantly. None of this caching is visible to a program calling read() — it's a performance layer entirely below the VFS interface, exactly like the dentry cache from the previous lesson in this cluster.

bob_os Already Has a Block Device — It Just Doesn't Call It That
Module 12's disk_read_sector(lba, buf) is a textbook block device operation: it takes an arbitrary sector number (the LBA — Logical Block Address) and returns exactly 512 bytes, and it can be called with any LBA in any order — reading sector 0, then sector 4000, then sector 0 again is perfectly valid. bob_os doesn't happen to add a buffer cache on top of it, which is a completely reasonable simplification for a teaching OS, but the underlying access pattern — fixed-size chunk, addressed by number, random order — is exactly what makes something a block device rather than a character device.
02 — Sequential, No Seeking

Character Devices: Streams Behave Like Queues

The canonical character device is a terminal — /dev/tty — or, further down, the keyboard or a serial port. Its defining trait is the opposite of a disk's: there is no address space to jump around in. Bytes show up (for input) or get sent out (for output) strictly in the order they occur, one at a time, and a read() on a character device just means "give me the next byte(s) that are available," full stop. There's no equivalent of "give me byte 500 of the keyboard" — the concept doesn't parse.

This has a direct, practical consequence: read() on a character device can genuinely block — the call just sits there, doing nothing, until a byte actually arrives. A disk read never has this problem in the same way; the data already physically exists on the platter or flash chip, waiting to be fetched. A keyboard press hasn't happened yet until it happens.

bob_os's Keyboard Driver Is Already a Character Device
Module 09's keyboard driver is interrupt-driven: a hardware interrupt fires each time a key goes down, the interrupt handler pushes that one scancode into a small in-kernel queue, and whatever's reading from the keyboard pulls bytes out of that queue one at a time, in the order they were typed. There's no "seek to keypress #12" — only "give me the next one, whenever it shows up." That queue-of-bytes-in-arrival-order shape is precisely what a character device is, independent of whether bob_os's own code labels it that way internally.

05 — Edge Cases That Prove the Rule

mmap(), and the Character Devices With No Hardware Behind Them

Two loose ends worth tying up, because both make the block/character split sharper rather than blurring it.

Why you can mmap() a file but not a keyboard

mmap() maps a file's contents directly into a process's address space, so ordinary memory reads and writes turn into file reads and writes without an explicit read()/write() call per access. This works naturally for block devices and the regular files sitting on top of them, precisely because random access is exactly what a memory mapping needs — the CPU can dereference any address in the mapping at any time, which lines up perfectly with a block device's "any block, any order" contract. A character device generally cannot be mapped this way, for the same reason it can't be seeked: there's no fixed, indexable range of bytes sitting there to map. A keyboard doesn't have "byte 900 of itself" waiting to be dereferenced — it has whatever hasn't been typed yet.

Character devices that aren't really hardware at all

Not every character device corresponds to a physical component. /dev/null, /dev/zero, and /dev/random are character devices with no hardware behind them whatsoever — pure kernel logic wearing a device file's clothes, for exactly the same reason procfs wears a filesystem's clothes in the earlier lesson in this cluster.

Each of these still has to be sequential, no-seek, byte-at-a-time in spirit — /dev/zero can't hand you "the 500th zero byte specifically," because that request is as meaningless as asking a keyboard for a specific byte offset. The category isn't about physical hardware at all; it's about the shape of the access pattern the driver honestly supports.

06 — What the Driver Actually Owes the VFS

Same Vtable Shape, Different Obligations

Recall from the first lesson in this cluster: every backend plugs into the VFS by filling in the same vfs_ops struct — open, read, write, close. A block driver and a character driver both do exactly that. What differs is what each one has to do inside those functions to honestly satisfy what its device type promises.

A real char driver typically needs to answer "is data available right now without blocking?" so a shell can wait on multiple input sources at once.

Neither driver gets to lie about its shape. A block driver that silently only supported sequential access would break any program that legitimately seeks around a file — which is most of them. A character driver that pretended to support seeking would have nothing sensible to do with the request; "seek to byte 12 of the keyboard" simply has no answer. The VFS interface stays uniform at the syscall level; the honesty about what a given device can and cannot do lives entirely inside the driver that implements it.

The Takeaway
"Everything is a file" was never a claim that all files behave identically — it's a claim that they can all be opened, read, written, and closed through one interface, while remaining honest about their real capabilities underneath. A block device's honesty is "I support random access and I'm probably cached." A character device's honesty is "I only ever give you what's next, and I might make you wait for it." The VFS's job is to let both kinds sit behind the same four function calls without either one having to pretend to be the other.
07 — Quick Reference

Glossary & Key Terms

Block Device
A device addressed in fixed-size chunks with true random access — any block, in any order — typically sitting behind a kernel buffer/page cache.
Character Device
A device that delivers or accepts a strict, ordered stream of bytes with no concept of seeking — read() means "give me whatever's next."
Logical Block Address (LBA)
The numeric address of a specific fixed-size block on a block device — the unit block drivers actually operate on.
Buffer / Page Cache
In-memory storage of recently used disk blocks, letting the kernel avoid repeated slow physical reads — invisible to the program calling read().
Blocking read()
A read() call that pauses the calling process until data actually becomes available — the normal behavior for character devices like a keyboard.
Device Driver
The code implementing a specific device's vfs_ops functions, translating generic open/read/write/close calls into real hardware operations.
Major/Minor Number
The pair of numbers Unix uses to identify which driver (major) and which specific device instance (minor) a /dev entry refers to.
ioctl()
A catch-all system call for device-specific operations that don't fit read/write/seek — e.g. querying a disk's total size or a terminal's window dimensions.
poll() / select()
System calls letting a process ask "is any of these file descriptors ready without blocking?" — essential for character devices whose data arrival time is unpredictable.
