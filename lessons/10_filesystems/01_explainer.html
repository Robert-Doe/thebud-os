00 — The Problem

Your Disk Is Not One Thing

Sit down at almost any real computer and ask "what filesystem is on this machine," and the honest answer is: several, at once. The root partition might be ext4 (Linux) or NTFS (Windows) or APFS (macOS). The EFI system partition that boots the machine is almost always FAT32, by spec. Plug in a USB stick and it's probably exFAT or FAT32 too, for compatibility. Mount a shared drive over the network and now you're talking NFS or SMB — a filesystem that isn't even stored on a local disk. And under Linux, /proc and /sys present thousands of "files" that don't correspond to any bytes on any disk at all — they're generated fresh, on the spot, every time you read them.

These are not small variations on a theme. FAT32 is a flat array of cluster links with fixed-size 32-byte directory entries. ext4 uses inodes, extents, and B-trees for large directories. NTFS stores almost everything — including tiny files — as records in a master database called the Master File Table. NFS isn't a disk format at all; it's a network protocol wrapping remote procedure calls. procfs has no on-disk format whatsoever, because there's no disk involved. Four of these five don't agree on anything about how bytes are actually laid out.

And yet — this is the part that should feel almost suspicious — none of that mess ever shows up in the program you write. You open a file with open(), you get bytes back with read(), you push bytes out with write(), you're done with close(). Same four calls, whether the bytes are coming from a spinning disk, a USB stick, a server on the other side of campus, or a struct the kernel just built in memory thirty milliseconds ago. Something in the middle is absorbing all of that difference. That something is today's subject.

The Aha Moment
Imagine the alternative: every program that touches a file has to contain a giant if (fs == FAT32) ... else if (fs == EXT4) ... else if (fs == NFS) ... chain, and every time someone invents a new filesystem, every program on Earth needs to be patched to understand it. That's obviously unworkable — which means the "which filesystem is this, really" question has to be answered in exactly one place, once, and hidden from everyone above it. That one place is the kernel, and the layer that does the hiding is the Virtual File System, or VFS.
01 — The Head First Moment

The Restaurant With One Menu

Picture a food court with five different restaurants behind it: a diner grilling burgers over an open flame, a sushi counter running knives and rice cookers, a noodle stall boiling water in giant pots, a bakery running ovens, and a smoothie bar blending fruit. Every kitchen works completely differently — different equipment, different techniques, different staff training.

But you, the customer, never see any of that. You walk up to one counter and read one menu: appetizer, main, dessert, drink. You point at "main course," and whichever kitchen is behind that particular counter does whatever it needs to do — grill, steam, boil, bake — and a plate comes back. You never learn to operate a wok. You never need to. The menu is the interface; the kitchen is the implementation; and critically, the menu items are the same words no matter which kitchen is behind the counter.

FAT32 Kitchenclusters
Serves your "read a file" order by walking a flat linked list of clusters until it hits an end-of-chain marker. Simple, ancient, works everywhere.
ext4 Kitcheninodes
Serves the same order by looking up an inode, following extent pointers to data blocks. Different equipment, same plate comes out.
procfs Kitchenno pantry
Has no ingredients in storage at all — it cooks the "file" from scratch, live, the instant you order it, from whatever the kernel currently knows.
NFS Kitchenphone order
Doesn't have its own pantry either — it phones a completely different building (a remote server) and relays the order over the network, then plates whatever comes back.
NTFS Kitchenmaster ledger
Runs everything through one big database-like ledger (the Master File Table) instead of a pantry-and-shelves layout — a completely different kitchen floor plan, same menu items served.

The menu in an operating system is a tiny, fixed set of operations: open, read, write, close (plus a handful of extras like seek and stat). The kitchens are the individual filesystem drivers — FAT, ext4, NTFS, NFS, procfs — each one free to do absolutely anything it wants internally, as long as it can answer those same four orders. The layer standing at the counter, taking your order and routing it to the right kitchen, is the VFS.

02 — The Mechanism

A Struct Full of Function Pointers

Here's where "the menu" stops being a metaphor and becomes actual C code. The VFS defines one struct — call it vfs_ops — that's just a bundle of function pointers, one slot per menu item. Every filesystem driver that wants to plug into the VFS has to fill in that exact same struct with its own functions.

/* The "menu" — every backend must fill in a struct shaped exactly like this */
struct vfs_ops {
    int  (*open) (const char *path, int flags);
    int  (*read) (int inode, char *buf, int n, int offset);
    int  (*write)(int inode, const char *buf, int n, int offset);
    void (*close)(int inode);
};

/* Three completely different kitchens, same menu shape */
struct vfs_ops fat32_ops   = { fat32_open,   fat32_read,   fat32_write,   fat32_close   };
struct vfs_ops ext4_ops    = { ext4_open,    ext4_read,    ext4_write,    ext4_close    };
struct vfs_ops procfs_ops  = { procfs_open,  procfs_read,  procfs_write,  procfs_close  };

Notice what's not in that struct: any mention of clusters, inodes, extents, B-trees, or network sockets. The struct only knows about "a function that opens," "a function that reads." What happens inside fat32_read versus ext4_read is each driver's private business — one of them might be walking a cluster chain, the other might be dereferencing extent pointers, and the VFS genuinely does not care, because it never looks inside those functions. It only ever calls through the pointer.

This Is Just Polymorphism, Written By Hand
If you've used an object-oriented language, this should feel familiar: vfs_ops is exactly what a base class's virtual method table (vtable) is in C++ or Java, except C has no built-in notion of classes or virtual functions, so the kernel builds the same mechanism manually out of a struct of function pointers. "Call ops->read(...) and let whichever concrete implementation is plugged in there handle it" is dynamic dispatch — the OS-level ancestor of every interface keyword you've ever typed.

The other half of the trick is: how does the VFS know which vfs_ops struct to use for a given file? Every open file gets a small record — commonly called a file descriptor — that, alongside "where am I reading from right now" (an offset), also carries a pointer to the correct vfs_ops struct for whatever backend that file actually lives on. Once that pointer is set at open() time, every subsequent read() or write() on that file descriptor just follows the pointer — no re-deciding required.

There Are No Dumb Questions
Q: Doesn't bouncing every read() through a function pointer make file I/O slower? In practice, no — not in any way that matters. A function-pointer call costs a handful of extra CPU cycles at most; an actual disk read costs on the order of milliseconds, and even a fast SSD read costs microseconds. The dispatch overhead is many orders of magnitude smaller than the I/O it's dispatching to. This is exactly why the VFS pattern is used pervasively throughout real operating systems rather than being reserved for rare cases — the abstraction is essentially free relative to the work it's abstracting over.
03 — Watch It Happen

Watching open() Find Its Kitchen

Let's make the dispatch mechanism concrete. A single process calls open() on three different paths in a row. Each path lives on a different backend. Pick one below and watch the same syscall get routed to three completely different kitchens.

▶ Pick a path to open()
  1. The program calls open(path, flags)It has no idea, and doesn't ask, what kind of filesystem the path resolves to. It just wants a file descriptor back.
  2. The VFS resolves the mount tableEvery mounted filesystem is recorded against the path prefix it owns — /mnt/usb → FAT32 driver, /home → ext4 driver, /proc → procfs driver. The VFS walks this table to find the matching entry.
  3. The VFS calls ops->open() through the matched vtableWhichever vfs_ops struct is registered for that mount point gets its open function pointer called. This is the one and only moment where the "which filesystem" question gets answered.
  4. The backend does whatever it needs to doFAT32 walks a directory's fixed-size entries; ext4 looks up an inode; procfs just checks whether "1" is a live PID and prepares to fabricate text. Each is invisible to the other.
  5. A file descriptor comes back, tagged with that backend's vtableEvery future read()/write()/close() on this fd will follow the pointer stored right here — no re-resolving the path required.
04 — The Fine Print

What's Guaranteed, What Varies

The VFS doesn't make every filesystem identical — it can't, and it shouldn't try. It normalizes the interface, not the capabilities behind it. Some things are guaranteed no matter which backend you're touching; other things quietly depend on which kitchen you landed in.

✅ Guaranteed The Same Everywhere

The function signatures (open/read/write/close), the meaning of a file descriptor as a small integer, the fact that read() returns bytes and advances an offset, and the fact that errors come back through the same return-value/errno convention regardless of backend.

⚠️ Varies By Backend, Silently

Maximum filename length, whether filenames are case-sensitive, whether permissions/ownership exist at all (FAT32 has none; ext4 has full Unix permissions), whether a file can be sparse, and whether writes are even meaningful — you cannot write() to most of /proc.
Watch out: the "inode number" the VFS hands back to your program doesn't mean the same thing on every backend. On ext4 it really is a disk inode index. On FAT32 — which has no concept of inodes at all — the driver has to invent a stand-in number, often derived from the directory entry's location, purely so it has something to plug into that slot of the interface. The VFS's uniformity is a promise about the shape of the API, not a promise that every number flowing through it means the same thing underneath.

This is precisely why a program that only uses the VFS-level API can genuinely be filesystem-agnostic, while a program that pokes at backend-specific quirks (checking a FAT "archive bit," say) instantly stops being portable. The abstraction is honest about where it ends.

05 — Tying It Back

This Is Exactly What Module 19 Builds

bob_os builds this same architecture from scratch, deliberately in the same shape as the real thing. Module 12 gives you BobFS: a flat, hand-rolled filesystem talking to a disk over ATA PIO. On its own, BobFS's three functions — fs_read, fs_create, fs_delete — are exactly the kind of backend-specific API that would poison every caller with disk-format knowledge if nothing sat above it.

Module 19 is that "something above it." It introduces the exact same vfs_ops vtable shown earlier in this lesson, plus a per-process fd_table mapping small integers to {inode, offset, ops} records. When a bob_os user process calls SYS_OPEN, the kernel's vfs_resolve() picks the right backend's vtable — BobFS for a real file, the VGA driver's vga_ops for stdout — and every subsequent SYS_READ/SYS_WRITE just follows the pointer stored in that process's fd_table entry. Same dispatch, same reason: so that SYS_READ's implementation never needs an if-chain for every backend that might ever exist.

06 — One More Wrinkle

What Happens When One Path Crosses Two Filesystems?

There's a detail the dispatch walkthrough glossed over: mount points can nest, and a single absolute path can legitimately cross a filesystem boundary partway through. /mnt/usb/photo.jpg isn't one lookup against one backend — /mnt might live on your root ext4 filesystem, while /mnt/usb is where an entirely different FAT32 volume has been grafted on. The VFS has to figure out exactly where that handoff happens, using nothing but the path string.

  1. Every mounted filesystem registers its mount pointWhen FAT32 gets mounted at /mnt/usb, the VFS records that exact path prefix against the FAT32 driver's vtable, alongside whatever else is already mounted (root at /, maybe /proc, maybe others).
  2. Path resolution finds the longest matching prefixFor /mnt/usb/photo.jpg, both / and /mnt/usb are valid prefixes — but /mnt/usb is longer and more specific, so it wins. The VFS always dispatches to the most specific mount that matches.
  3. Only the remaining suffix gets handed to that backendThe FAT32 driver never sees /mnt/usb at all — from its point of view, the file is simply at /photo.jpg within its own volume. The prefix that got it selected is stripped off before the backend ever sees the path.

This is also exactly the mechanism behind Linux's /proc, /sys, and /dev: each is its own filesystem, mounted at a specific point in an otherwise ordinary directory tree, dispatched to by the same longest-prefix-match logic as a physically distinct disk would be. There's no special-case code path for "this one happens to be fake" — procfs is just another entry in the same mount table, competing for the same longest-prefix match as everyone else.

Why This Matters for Permissions and Behavior, Not Just Routing
Crossing a mount boundary can silently change what's even possible with a file. Copy a file from your ext4 home directory onto a FAT32 USB stick, and its Unix permission bits, its symbolic links, and any extended attributes it had are simply gone — not because anything went wrong, but because FAT32 has no on-disk field to store them in. The VFS routes the request correctly every time; it never promised the destination could represent everything the source could.
07 — Quick Reference

Glossary & Key Terms

Virtual File System (VFS)
The kernel layer that presents one uniform open/read/write/close interface over any number of differently-implemented filesystem backends.
vfs_ops / vtable
A struct of function pointers — one slot per operation — that every backend fills in with its own implementations. The mechanism behind the uniform interface.
Filesystem Driver
The code behind one specific vtable — FAT32, ext4, NTFS, NFS, or procfs — that knows how to translate the four VFS calls into real work on its own storage format.
Mount Point
The path prefix (e.g. /mnt/usb) that a particular filesystem instance is attached to; the VFS uses this to decide which driver's vtable to dispatch a path to.
File Descriptor
A small per-process integer that stands in for an open file; internally it carries an offset and a pointer to the correct backend's vtable.
procfs
A filesystem backend with no disk storage at all — every "file" under /proc is generated live from live kernel state the instant it's read.
NFS (Network File System)
A filesystem backend whose "disk" is actually a remote server, reached over the network via remote procedure calls instead of local block I/O.
Dynamic Dispatch
Calling a function through a pointer determined at runtime rather than at compile time — the general mechanism a vtable provides, in any language.
Longest-Prefix Match
The rule the VFS uses to pick which mounted filesystem owns a path when more than one mount point is a valid prefix — the most specific match always wins.
Bind / Nested Mount
A filesystem mounted at a path that sits inside another already-mounted filesystem, requiring the VFS to route by path prefix rather than by whole-path lookup.
