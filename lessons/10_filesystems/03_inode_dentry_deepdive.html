The File That
Has No Name

Ask Linux "what is this file's name," and the honest answer is: the file itself doesn't know. Its metadata record — the inode — stores size, permissions, timestamps, and where its data lives, but deliberately not a name. Names live one layer up, in directory entries. That split sounds like a technicality. It's actually the entire reason hard links, and fast path lookups, work at all.

00 — Zooming In

What Is an Inode, Really?

The earlier lesson in this cluster explained the VFS as a universal menu sitting in front of many different kitchens. This lesson walks into one specific kitchen — Linux's ext-family filesystems — and looks at exactly how it represents "a file" on disk. The answer starts with the inode (index node): one fixed-size record per file, holding every piece of metadata about it except its name.

Everything a program might want to know about a file via stat() — its size, its permissions, when it was last touched, how many blocks it occupies — is answered entirely from this one record, using only a number (the inode number) as the lookup key. No name required. That's not an oversight. It's the whole design.

01 — The Deliberate Omission

Why the Inode Doesn't Know Its Own Name

If you've only used Windows or a GUI file manager, this feels backwards — surely a file's name is one of its most basic properties? On Linux's underlying model, a name isn't a property of the file at all. It's a property of the directory that mentions it. A directory's actual content, on disk, is nothing more than a list of pairs: a name, and the inode number that name currently refers to. Those pairs are called directory entries, or dentries.

Name (in the directory's data)Inode Number It Points To
report.txt142857
notes.txt88231
final_report.txt142857

Look closely at that table: report.txt and final_report.txt both point at inode 142857. That's not a typo, and it's not two copies of the same file. It's one file, one set of data blocks, one piece of metadata, reachable by two completely independent names in the directory. This is only possible because the name lives in the directory entry and not in the inode — the inode has no idea it even has two names, because it was never designed to know its own name in the first place.

The Aha Moment
A directory isn't a container that "holds" files the way a folder icon suggests. A directory is a lookup table — a list of (name → inode number) mappings, and nothing more. "Renaming" a file doesn't touch the file's data or its inode at all; it just edits one entry in the directory's name-to-number table. "Moving" a file within the same filesystem is the same operation: remove one (name → inode) pair, add another, in a different directory's table. The file itself — its inode, its data — never moves or changes.
02 — Watch It Happen

Hard Links: Two Names, One File

Once you see the (name → inode) split, hard links stop being a special feature and become an obvious consequence of the data structure. Creating a hard link with ln report.txt final_report.txt does exactly one thing: it adds a second directory entry pointing at the same inode number, and bumps that inode's link count by one. No data is copied. No new inode is allocated.

▶ Create a hard link, then delete the original name
  1. Before: one name, one inode, link count 1report.txt is the only directory entry pointing at inode 142857.
  2. ln adds a second directory entry, same inode numberNo new data is written anywhere. The kernel just writes a new (name → inode) pair into the directory, and increments the inode's link count to 2.
  3. rm report.txt removes only that one directory entryThe inode's link count drops back to 1 — but it does not hit zero, because final_report.txt still points at it.
  4. The data survives, reachable only through the surviving nameOnly when an inode's link count hits zero — meaning no directory entry anywhere points at it anymore — does the filesystem actually reclaim its data blocks.
This Is Also Why "Deleting" a File Doesn't Always Free Space
Unix's unlink() system call is named accurately: it removes one link (one directory entry), not "the file." If a process still has that same inode open via a file descriptor when the last directory entry is removed, the inode's data isn't freed until that process closes the file too — the kernel tracks both link count and open-file-descriptor count before actually reclaiming a data block. This is precisely the trick behind an anonymous temp file: open() it, immediately unlink() it, and it stays fully usable through your file descriptor while being invisible to everyone else and automatically cleaned up the moment you close it.
03 — Watch It Happen

Resolving /usr/bin/ls, One Component at a Time

Now put the pieces together to answer a deceptively simple question: how does the kernel turn the string /usr/bin/ls into an actual inode? Not in one leap — a path is resolved one directory-lookup at a time, each step using exactly the (name → inode) mechanism above.

▶ Resolve /usr/bin/ls component by component
  1. Start at the root inodeEvery absolute path resolution begins from a well-known inode: the root directory, /.
  2. Look up "usr" in the root directory's entriesRead the root directory's data, scan its (name → inode) pairs for "usr", get back an inode number — call it the usr inode.
  3. Look up "bin" in the usr directory's entriesSame operation, one level down: read that inode's directory data, find "bin", get the bin inode.
  4. Look up "ls" in the bin directory's entriesOne more lookup, and you finally have the inode for the actual ls executable — three separate directory reads for a three-component path.

That's the part worth sitting with: a "single" path lookup is really N separate directory reads for an N-component path, each one potentially a real disk I/O. For a short interactive command that's barely noticeable. For a kernel doing this constantly — every open(), every exec(), every shell script sourcing another file — those lookups add up fast.

Why the Kernel Caps Symlink Depth
Each step above assumed a plain directory entry. But any component along the way could instead be a symlink, which forces the resolver to detour into resolving that path before it can continue — and nothing stops a symlink from pointing at another symlink, which points at another. Without a limit, a maliciously (or accidentally) circular chain of symlinks would spin the kernel forever trying to resolve one path. This is exactly why Linux hard-caps symlink resolution depth (historically 8, now typically 40) and simply fails the lookup with ELOOP past that point — a small, unglamorous safety valve on an otherwise straightforward walk.
04 — The Performance Layer

The Dentry Cache: Skipping the Disk, Not the Steps

Linux doesn't eliminate the per-component nature of path resolution — it can't, the (name → inode) structure genuinely requires walking one level at a time. What it does instead is keep an in-memory cache, the dentry cache (often just "dcache"), holding recently-resolved (name → inode) results so that the second, third, and millionth time someone resolves /usr/bin, the kernel can answer straight from RAM instead of re-reading directory blocks off disk.

🐌 Cold Lookup — Nothing Cached

Resolving /usr/bin/ls the first time means three separate directory reads, each a potential disk I/O: root → usr, usr → bin, bin → ls. Slow relative to everything else the kernel does.

⚡ Warm Lookup — Dentry Cache Hit

The next process that resolves /usr/bin/ls — or even just /usr/bin as a prefix of some other path — finds each component's (name → inode) mapping already sitting in the dcache. Zero disk I/O, just following in-memory pointers.
Why this matters more than it sounds like it should: shells, compilers, and package managers resolve paths constantly, and a huge fraction of those paths share common prefixes — /usr/bin, /usr/lib, /usr/include are each resolved thousands of times a day on a busy machine, all sharing the same "root → usr" first hop. The dentry cache turns that repeated first hop into a cache hit instead of a repeated disk read, which is a meaningful chunk of why a warmed-up Linux system "feels" fast at anything filesystem-heavy — builds, package installs, shell tab-completion.

Crucially, the dentry cache is purely a performance layer sitting in front of the real structure, not a replacement for it. If an entry isn't cached, the kernel falls back to reading the actual directory data from the actual filesystem backend — exactly the walk described above — and then populates the cache with the result for next time. Nothing about correctness depends on the cache; only speed does.

The Cache Also Remembers "No"
A subtler trick: the dcache doesn't just cache successful lookups — it also caches negative results, called negative dentries, remembering "this name does not exist in this directory" so a repeated failed lookup (a shell checking a dozen PATH directories for a command that only lives in the last one) doesn't re-hit the disk each time either. A negative dentry gets invalidated the moment something with that name is actually created, keeping the cache honest without ever forcing a program to fall back to a slow path just because the answer happened to be "not found."
05 — A Close Relative, Clarified

Hard Link vs Symbolic Link

It's worth explicitly separating hard links from symbolic links, because they solve superficially similar problems ("more than one name for a thing") through completely different mechanisms — one exploiting the (name → inode) split directly, the other sitting entirely outside it.

PropertyHard LinkSymbolic Link
What it actually isA second directory entry pointing at the same inode numberA tiny separate file whose data is a path string
Has its own inode?No — shares the target's inode entirelyYes — its own inode, own small data block holding the path text
Survives target deletion?Yes — data lives until link count hits 0No — becomes a "dangling" link pointing nowhere
Can cross filesystems?No — inode numbers are only meaningful within one filesystemYes — it's just a stored string, resolved fresh each time
Can link a directory?Generally forbidden (would break tree structure)Yes, freely

A symbolic link resolves by being read like any other file — its "content" is a path — and then that path gets resolved fresh, from scratch, through the exact same component-by-component walk described above. A hard link needs no such extra step at all: the directory entry is already a direct (name → inode) pointer, indistinguishable at the filesystem level from any other name for that same file.

Where bob_os Stops, On Purpose
Module 19's own tutorial is upfront that its VFS "inode" is really just a loosely-borrowed word — an integer handle meaningful only to whichever backend owns it, with no permissions, no link count, no data-block pointers behind it, and BobFS itself has no directory structure at all, let alone (name → inode) entries or hard links. That's a deliberate, reasonable scope cut for a teaching kernel: everything in this lesson — the split between metadata and naming, link counts, dentries, the cache in front of them — is exactly the next layer of "real filesystem" bob_os's own modules choose not to build, so that Module 19 can stay focused on the dispatch mechanism instead of disk-format bookkeeping.
06 — Quick Reference

Glossary & Key Terms

Inode
The unique on-disk record holding a file's metadata — size, permissions, timestamps, link count, and data block pointers — deliberately excluding any filename.
Dentry (Directory Entry)
A (name → inode number) pair stored inside a directory's data — the only place a filename actually lives.
Link Count
The number of directory entries currently pointing at a given inode; data is only reclaimed once this (and open file descriptor count) reaches zero.
Hard Link
A second directory entry pointing at an already-existing inode number — two independent names sharing one file's data and metadata exactly.
Symbolic Link (Symlink)
A separate small file whose own data is a path string, resolved fresh through a full path lookup each time it's followed.
Path Resolution
Turning a path string into an inode by looking up one component at a time, each step reading the previous step's inode as a directory.
Dentry Cache (dcache)
An in-memory cache of recently resolved (name → inode) pairs, letting repeated path lookups skip disk reads without changing the underlying resolution mechanism.
unlink()
The system call behind "deleting" a file — it removes one directory entry and decrements a link count; it does not necessarily free any data.
