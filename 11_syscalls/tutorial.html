MODULE 11 — PHASE 2

System Calls

Processes need to ask the kernel for things — exit, print, get their PID, yield. But they can't just call kernel functions directly (that would be a security nightmare). The int 0x80 gate is the controlled doorway between user and kernel.

the syscall instruction
EAX

EBX/ECX/EDX
arguments 1, 2, 3
DPL=3
gate allows ring-3 to call it

01 — The Big Analogy

Head First Moment

Imagine a drive-through window at a fast-food restaurant. The kitchen (kernel) is off-limits to customers. But there's a little window (int 0x80) where you can place an order (syscall number in EAX) and pass your ingredients (arguments in EBX, ECX, EDX). The kitchen prepares your order and passes it back through the window (return value in EAX). You never go inside — but you get what you need.

The syscall gate is that window. Without it, user code would have to call kernel functions directly — and could then corrupt kernel memory, escalate privileges, or crash everything.

02 — How int 0x80 Works

When user code executes int 0x80, the CPU:

  1. Looks up IDT entry 0x80 — finds your syscall handler.
  2. Checks the gate's DPL — it's 3, so ring-3 code is allowed to trigger it.
  3. Switches to ring 0 using the TSS's esp0 (kernel stack pointer).
  4. Pushes EFLAGS, CS, EIP (and old ESP/SS since we crossed rings) onto the kernel stack.
  5. Jumps to your syscall_handler.
/* syscall.c */
void syscall_handler(struct interrupt_frame *f) {
    switch (f->eax) {       /* syscall number */
    case SYS_EXIT:  do_exit(f);            break;
    case SYS_WRITE: do_write(f);           break;
    case SYS_GETPID:f->eax = current->pid; break;
    case SYS_YIELD: do_yield(f);           break;
    default:        f->eax = -1;           break; /* ENOSYS */
    }
}

void syscall_init(void) {
    /* Register IDT entry 0x80 with DPL=3 so ring-3 can trigger it */
    idt_set_gate(0x80, (uint32_t)syscall_stub, 0x08, 0xEE);
    /*                                                  ^^^^
         0xEE = 32-bit interrupt gate, DPL=3 */
}

SYS_WRITE Security Warning

Our SYS_WRITE takes a raw pointer from user space and passes it to kprintf. In a real kernel, you must validate every user pointer before dereferencing it — is it in the user's address space? Is it mapped? A bad pointer from user space should return EFAULT, not crash the kernel. We skip this validation for simplicity; Module 15 (per-process address spaces) is where this matters most.

04 — The User-Side Wrapper

/* syscall.h — inline wrappers so user code can call syscalls in C */
static inline int syscall(int num, int a, int b, int c) {
    int ret;
    __asm__ volatile (
        "int $0x80"
        : "=a"(ret)
        : "a"(num), "b"(a), "c"(b), "d"(c)
        : "memory"
    );
    return ret;
}

static inline void sys_exit(int code)   { syscall(SYS_EXIT,  code, 0, 0); }
static inline void sys_write(char *s)   { syscall(SYS_WRITE, (int)s, 0, 0); }
static inline int  sys_getpid(void)     { return syscall(SYS_GETPID, 0, 0, 0); }
static inline void sys_yield(void)      { syscall(SYS_YIELD, 0, 0, 0); }

06 — Brain Exercise

Sharpen Your Pencil

Question: The TSS (Task State Segment) holds esp0 — the kernel stack pointer to use when a ring-3 → ring-0 transition happens. If you have multiple processes, each needs its own kernel stack. But there's only one TSS.

How does the OS handle this? (Hint: before scheduling a new process, update tss.esp0 to point at that process's kernel_stack_top. When a syscall fires, the CPU uses whatever esp0 currently says.)

There Are No Dumb Questions

Q: Why int 0x80 specifically? Why not some other vector?
Pure convention. Linux uses 0x80 on x86-32, and we follow it. Any unused IDT vector would work — as long as its gate has DPL=3. Modern x86-64 uses the syscall instruction instead of int 0x80, which is faster because it avoids the IDT lookup overhead. We use int 0x80 because it uses the IDT infrastructure we already built.
Q: Why pass arguments in registers rather than on the stack?
The stack switches from user to kernel when int 0x80 fires — the kernel stack is empty at that point (or rather, it's pointing at esp0 which is the top of the kernel stack). The user stack is inaccessible until we explicitly switch to the user CR3 and map it. Registers survive the privilege transition without any extra work.
