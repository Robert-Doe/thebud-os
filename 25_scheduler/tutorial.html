The Scheduler

The scheduler is the OS's traffic cop. It decides which process runs next, for how long, and in what order. Get this wrong and your OS either starves background tasks or lets real-time work miss its deadlines.

01 — The Big Analogy

Head First Moment

Imagine a hospital emergency department. Patients arrive and are triaged into four queues: Critical (HIGH), Urgent (NORMAL), Semi-urgent (LOW), and Non-urgent (IDLE). Doctors always see the most critical patient first. A broken-leg patient (LOW) waits until every chest-pain patient (HIGH) has been seen. When all high-severity patients are gone, they handle NORMAL. Only when the waiting room is completely empty do they see the Non-urgent cases.

Your scheduler works exactly the same way. HIGH processes run first. If none are ready, NORMAL runs. The IDLE process (an infinite hlt loop) only runs when literally every other process is blocked waiting for I/O.

02 — The PCB Gets a Priority Field

/* process.h — ONE new field added in Module 25 */
struct process {
    /* ... all existing fields from Module 24 ... */
    int priority;   /* SCHED_PRIO_IDLE/LOW/NORMAL/HIGH — set at spawn time */
};
One Field, Big Impact

Adding int priority to the PCB is all that's needed at the data level. The scheduler reads this field on every tick to decide which queue to pull from. Existing code that creates processes sets priority to SCHED_PRIO_NORMAL by default — no other changes needed in process.c.

03 — The Four Queues: pick_next()

/* sched.c — one circular head pointer per priority level */
static int rq_head[SCHED_NUM_PRIOS];  /* [0..3] */

static struct process *pick_next(void) {
    /* Walk from HIGH (3) down to IDLE (0) */
    for (int prio = SCHED_NUM_PRIOS - 1; prio >= 0; prio--) {
        for (int n = 0; n < MAX_PROCESSES; n++) {
            int idx = (rq_head[prio] + n) % MAX_PROCESSES;
            struct process *p = &proc_table[idx];

            if (p->state == PROC_READY && p->priority == prio) {
                rq_head[prio] = (idx + 1) % MAX_PROCESSES; /* round-robin */
                return p;
            }
        }
    }
    return current; /* nothing runnable — stay */
}
Two Nested Loops — Walk Priority, Then Scan Slots

Outer loop: try HIGH first, then NORMAL, then LOW, then IDLE. Inner loop: scan all MAX_PROCESSES PCB slots starting from rq_head[prio]. The first match wins. This is O(4 × 8) = O(32) — effectively constant time for our kernel size.

The tick that drives the context switch

uint32_t sched_tick(uint32_t current_esp) {
    current->esp = current_esp;
    if (current->state == PROC_RUNNING)
        current->state = PROC_READY;   /* back in the runnable pool */

    struct process *next = pick_next();
    if (next == current) {
        current->state = PROC_RUNNING;
        return current_esp;            /* no switch — return same ESP */
    }

    current = next;
    current->state = PROC_RUNNING;
    tss_set_kernel_stack(current->kernel_stack_top);

    if (next->cr3 != 0)
        asm volatile("mov %0, %%cr3" :: "r"(next->cr3) : "memory");

    return current->esp;   /* ASM stub restores registers from this ESP */
}

04 — The Spinlock: Interrupt-Safe Runqueue

/* spinlock.h — test-and-set, all inline */
typedef struct { volatile uint32_t locked; } spinlock_t;

static inline void spinlock_acquire(spinlock_t *l) {
    while (__sync_lock_test_and_set(&l->locked, 1))
        asm volatile("pause");  /* tell CPU we're spinning — saves power */
}
static inline void spinlock_release(spinlock_t *l) {
    __sync_lock_release(&l->locked);
}
Why Does a Single-CPU OS Need a Spinlock?

On SMP, spinlocks protect shared data from concurrent CPUs. On a single CPU the danger is interrupts. If the timer IRQ fires in the middle of sched_yield() — which is itself writing to rq_head[] — you get a corrupt runqueue. The spinlock prevents this re-entry. On x86 IRQ handlers run with IRQs disabled, so the lock is never actually contended — but the habit is correct and prepares you for SMP kernels.

PAUSE — The Polite Spin

asm volatile("pause") is an x86 hint that says "I'm spinning waiting for memory to change." Without it, the CPU's out-of-order speculative execution can mispredict the branch when the lock releases, causing a pipeline flush. pause avoids that and signals the hardware to reduce power while spinning.

Seeing priority in action from user space

/* user_prog.c — spawn one HIGH and one LOW task */
void low_prio_task(void) {
    sys_setpriority(SCHED_PRIO_LOW);
    vga_print("[low_task] running at LOW — will be preempted by high_task\n");
    for (int i = 0; i < 5; i++) sys_yield();
    sys_exit(0);
}

void high_prio_task(void) {
    sys_setpriority(SCHED_PRIO_HIGH);
    for (int i = 0; i < 10; i++) {
        vga_print("[high_task] tick "); vga_printint(i); vga_print("\n");
        sys_yield();   /* voluntarily yield — but we'll be picked again first */
    }
    sys_exit(0);
}

06 — The IDLE Process: Never Let pick_next() Return NULL

/* kernel.c — IDLE trampoline */
static void kernel_idle(void) {
    while (1) asm volatile("hlt");
    /* HLT suspends the CPU until the next IRQ.
       IRQ0 fires, sched_tick runs, picks the highest-priority ready process.
       If nothing else is ready, hlt again. */
}

void kernel_main(void) {
    /* ... init all subsystems ... */
    uint32_t idle_pid = process_create(kernel_idle);
    sched_add(&proc_table[idle_pid], SCHED_PRIO_IDLE);
    for (;;) asm volatile("hlt"); /* hand off — this never returns */
}
What Happens Without the IDLE Process?

If the shell is blocking on keyboard input and there are no other PROC_READY processes, pick_next() returns current (a PROC_WAITING process). That works — until current also calls process_wait(). Then pick_next() finds nothing and returns NULL. Dereferencing NULL to load the next CR3 is an instant triple fault. The IDLE process is the safety net: always PROC_READY, so pick_next() always succeeds.

08 — Brain Exercise

Sharpen Your Pencil

Three NORMAL-priority processes: A, B, C. A calls sys_setpriority(SCHED_PRIO_HIGH), then immediately sys_yield(). On the very next tick, which process runs? Write your answer before reading on.

Answer: A runs again. When A yielded, its priority was already HIGH. pick_next() scans HIGH first and finds A as the only HIGH entry — it gets the CPU back. B and C (both NORMAL) starve until A finishes or blocks. This is starvation by design — exactly what you want for a real-time interrupt handler that must never wait.

There Are No Dumb Questions

Q: What's the difference between our scheduler and Linux's CFS?
Linux's Completely Fair Scheduler tracks "virtual runtime" — the total CPU time each process has consumed — and always picks the process with the smallest vruntime. This achieves fairness without hard priority tiers. Our scheduler uses strict priority + round-robin: simpler, and better suited to real-time embedded systems where some tasks genuinely must run first.
Q: Why does sched_tick check if current->state == PROC_RUNNING before resetting it to PROC_READY?
A process might have set its own state to PROC_WAITING (e.g., by calling process_wait()) before the timer fired. Unconditionally resetting to PROC_READY would wake it prematurely — it's still waiting for a child to exit. The check preserves the PROC_WAITING state through the tick.
Q: Our spinlock uses __sync_lock_test_and_set. Is that portable?
It's a GCC built-in that compiles to XCHG on x86 — always atomic because x86 XCHG has an implicit LOCK# prefix. C11's stdatomic.h provides atomic_flag for the same purpose in standard C. Both work fine in freestanding mode without a libc. In real OS kernels you'd use architecture-specific primitives and memory barriers explicitly.
