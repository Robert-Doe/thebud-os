Keyboard Driver

Every key press fires IRQ1. The keyboard controller sends a scancode byte. Your job: catch the IRQ, read the byte, translate it to ASCII, and put it in a ring buffer for the shell to consume.

01 — The Big Analogy

Head First Moment

Imagine a receptionist (the keyboard controller) sitting at a desk outside your office. Every time a visitor (key press) arrives, the receptionist rings a bell (IRQ1) and writes a note (scancode) on a slip of paper. Your IRQ handler runs to the desk, grabs the slip, translates it ("scancode 0x1E → the letter 'A'"), and drops it in an in-tray (ring buffer).

Your main code doesn't wait at the desk — it just checks the in-tray whenever it wants input. That decoupling is the whole point of interrupt-driven I/O.

02 — Scancodes vs ASCII

The keyboard doesn't send ASCII. It sends scancodes — hardware codes specific to the PS/2 keyboard protocol. Key press = scancode. Key release = scancode | 0x80.

03 — The IRQ Handler

/* keyboard.c */
#define KB_DATA_PORT 0x60

static char  ring_buf[256];
static uint8_t ring_head = 0, ring_tail = 0;

static void keyboard_irq_handler(struct interrupt_frame *f) {
    uint8_t scancode = inb(KB_DATA_PORT);

    if (scancode & 0x80) return; /* key release — ignore */
    if (scancode >= 128)  return; /* extended key — ignore for now */

    char ascii = scancode_map[scancode];
    if (!ascii) return;

    ring_buf[ring_head++] = ascii; /* head wraps via uint8_t overflow */
    pic_send_eoi(1);               /* MUST send EOI to re-enable IRQ1 */
}

char keyboard_getchar(void) {
    while (ring_head == ring_tail) { /* spin until a key is available */
        __asm__ volatile ("hlt");    /* sleep until next interrupt */
    }
    return ring_buf[ring_tail++];
}
The hlt trick

keyboard_getchar() spins waiting for a key. The hlt instruction stops the CPU until the next interrupt fires. That interrupt is the keyboard IRQ itself — which fills the ring buffer and then lets hlt return. Without hlt, the spin loop burns 100% CPU doing nothing useful while waiting for a keypress.

04 — The Ring Buffer

The ring buffer is a fixed-size circular array. ring_head is where new characters go in; ring_tail is where they come out. Because both are uint8_t, they wrap from 255 back to 0 automatically — no modulo needed.

Buffer Overflow

If you type 256 characters without the consumer reading them, ring_head wraps around and overwrites old data. For a kernel driver demo this is fine — a real driver would check (ring_head + 1) != ring_tail before writing and silently drop the character if full.

06 — Brain Exercise

Sharpen Your Pencil

Question: The shift key (scancode 0x2A / 0x36) is a modifier — it doesn't produce a character itself. But when held down, the next key should produce its uppercase version. Our simple scancode_map doesn't handle this.

How would you implement shift support? You need to track whether shift is currently pressed. Where in the IRQ handler would you add this, and how would you select between the normal and shifted scancode maps?

There Are No Dumb Questions

Q: Why does the keyboard send scancodes instead of ASCII?
Because the keyboard doesn't know your locale, your keymap, or whether Shift/Alt/Ctrl is held. It just reports raw hardware events — "key 0x1E went down." The OS driver decides what that means in context. This separation lets you implement any keyboard layout in software without changing the keyboard hardware.
Q: What's the difference between PS/2 and USB keyboards at this level?
PS/2 uses a direct wire to port 0x60 and fires IRQ1 — it's simple and always works in QEMU. USB keyboards need a USB controller driver (XHCI/EHCI), USB protocol stack, HID class driver — hundreds of times more code. QEMU emulates a PS/2 keyboard even when you plug in a real USB keyboard on the host, which is why we can use PS/2 for this module.
