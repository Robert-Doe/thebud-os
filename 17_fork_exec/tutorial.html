MODULE 17 — PHASE 3

fork & exec

The Unix process model in two syscalls. fork() clones the current process — address space and all. exec() replaces it with a new ELF binary. wait() lets the parent collect the exit code. Together they are how every Unix process ever born came to exist.

SYS_FORK
deep-copy address space, return twice
SYS_EXEC
replace current image with ELF
SYS_WAIT
block until child becomes zombie
0 / pid
fork return values: child=0, parent=child_pid

01 — The Big Analogy

Head First Moment

Imagine a photocopier (fork) that makes a perfect physical copy of every document on your desk. Now you have two identical desks. Then one of you (the child) throws away all the documents and replaces them with new ones from a filing cabinet (exec). The original desk is untouched.

That's fork+exec. Fork makes the copy. Exec replaces the copy's contents. The parent never changed. And when the child is done, it hands a note (exit code) to the parent who was waiting for it (wait).

parent (PID 1) calls fork()
├── parent continues: fork() returns child_pid (e.g. 2)
└── child created: fork() returns 0
child calls exec("hello.elf") → image replaced
child runs hello.elf → exits with code 0
parent calls wait() → unblocks, gets exit code 0

02 — fork: Cloning the Address Space

/* process.c */
int process_fork(void) {
    struct process *child = kmalloc(sizeof(*child));
    *child = *current; /* copy all PCB fields */
    child->pid        = next_pid++;
    child->parent_pid = current->pid;
    child->state      = PROC_READY;
    child->stack      = kmalloc(STACK_SIZE);
    child->kernel_stack_top = (uint32_t)child->stack + STACK_SIZE;

    /* Deep-copy the address space */
    child->cr3 = paging_clone_address_space(current->cr3);

    /* Build child's kernel stack so it "returns" from fork with EAX=0 */
    /* Copy current interrupt frame to child's kernel stack,
       then set child_frame->eax = 0  (fork returns 0 in child) */
    struct interrupt_frame *cf = copy_frame_to_child(child);
    cf->eax = 0;

    /* Parent's fork() will return child->pid via the syscall return path */
    enqueue(child);
    return child->pid;
}
The famous "fork returns twice"

Fork returns once in the parent (returns child PID) and once in the child (returns 0). How? The child's kernel stack is set up to look like it just returned from a syscall with EAX=0. When the scheduler runs the child, it pops that frame and "returns" from the syscall into user space — as if the child had called fork() itself and got 0 back.

03 — exec: Replace the Image

/* syscall.c — SYS_EXEC handler */
int do_exec(const char *filename) {
    uint32_t new_cr3;
    uint32_t entry = elf_load(filename, &new_cr3);
    if (!entry) return -1;

    /* Free old address space */
    uint32_t old_cr3 = current->cr3;
    current->cr3 = new_cr3;
    paging_switch(new_cr3);             /* switch NOW before freeing old */
    paging_free_address_space(old_cr3); /* safe: we're no longer using it */

    /* Reset user stack */
    uint32_t user_stack = 0x800000;
    /* map user stack pages into new_cr3... */

    /* Jump to new entry point at ring 3 */
    jump_to_usermode(entry, user_stack);
    /* never returns */
    return 0;
}
Switch CR3 BEFORE freeing old one

You must call paging_switch(new_cr3) before paging_free_address_space(old_cr3). If you free the old page directory while it's still in CR3, the very next memory access (including the code doing the freeing) uses a page directory you just freed — instant corruption or triple fault. Order matters enormously here.

04 — wait: Blocking Until Child Exits

/* process.c */
int process_wait(uint32_t *esp) {
    /* look for a zombie child */
    struct process *z = find_zombie_child(current->pid);
    if (z) {
        int code = z->exit_code;
        z->state = PROC_DEAD; /* reap it */
        return code;
    }
    /* no zombie yet — block */
    current->state = PROC_WAITING;
    scheduler_yield(esp);    /* give up CPU */
    /* when we wake up (zombify woke us), a zombie child is ready */
    z = find_zombie_child(current->pid);
    int code = z->exit_code;
    z->state = PROC_DEAD;
    return code;
}

/* In process_exit: if parent is PROC_WAITING, wake it */
static void zombify(struct process *p, int code) {
    p->state     = PROC_ZOMBIE;
    p->exit_code = code;
    struct process *parent = find_pid(p->parent_pid);
    if (parent && parent->state == PROC_WAITING)
        parent->state = PROC_READY; /* wake parent */
}

06 — Brain Exercise

Sharpen Your Pencil

Question: paging_clone_address_space does a deep copy — it allocates new physical frames and copies every page. If a process has 4MB of user data, fork copies 4MB. That's slow and wasteful if the child immediately calls exec.

This is exactly the problem Copy-on-Write (Module 21) solves. How would CoW make fork faster? What does it do instead of copying pages immediately?

There Are No Dumb Questions

Q: Why does Unix use fork+exec instead of just "create process from file"?
The separation gives flexibility: between fork() and exec(), the child can set up file descriptors (pipes, redirections), change its working directory, set environment variables, adjust signal handlers — all before the new program starts. A single "create process" call would need parameters for all of this. Fork+exec is more composable. Windows has CreateProcess() which does it in one call with many parameters — a different design tradeoff.
Q: What happens if the child never calls exec and just exits?
Perfectly fine — the child runs as a copy of the parent's code, exits normally, becomes a zombie, and the parent's wait() reaps it. This is how a shell runs a built-in command: fork, child runs the built-in function, child exits, parent waits. No exec needed.
