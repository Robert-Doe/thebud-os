Processes & Scheduler

01 — The Big Analogy

Head First Moment

Think of a chef managing several dishes on a stove. Every 10 seconds (timer tick), the chef puts down their current pan, writes a note about its current state ("burner 3, 40% done, lid on"), picks up the next pan, reads its note, and continues stirring. Each dish thinks it has the chef's full attention — but really the chef is time-sharing between all of them.

Each "dish" is a process. The "note" is the PCB (Process Control Block) — mainly the saved stack pointer. The chef is the CPU. The context switch is putting down one pan and picking up another.

02 — The Process Control Block

typedef enum { PROC_READY, PROC_RUNNING, PROC_WAITING,
               PROC_ZOMBIE, PROC_DEAD } proc_state_t;

struct process {
    uint32_t     pid;
    uint32_t     esp;           /* saved stack pointer — the whole context */
    uint8_t     *stack;         /* base of the kernel stack allocation */
    uint32_t     kernel_stack_top;
    uint32_t     cr3;           /* page directory (Module 15+) */
    uint32_t     parent_pid;
    int          exit_code;
    proc_state_t state;
    struct process *next;       /* intrusive linked list */
    /* ... extended in later modules: signals, fds, vm_regions, threads */
};
Why just ESP?

The timer IRQ is a normal hardware interrupt. When it fires, the CPU pushes EIP, CS, EFLAGS (and ESP/SS for ring switches) onto the current stack before calling your handler. Your isr_common_stub then pushes all the general-purpose registers. So when scheduler_tick runs, the entire CPU state is already on the stack. Saving ESP is enough — the full context comes along for free.

03 — The Context Switch

/* process.c — called from the timer IRQ handler */
uint32_t scheduler_tick(uint32_t current_esp) {
    if (current) current->esp = current_esp; /* save outgoing ESP */

    /* find next READY process (round-robin) */
    struct process *next = pick_next();
    if (!next) return current_esp; /* nothing else to run */

    current = next;
    current->state = PROC_RUNNING;
    return current->esp; /* return incoming ESP */
}

/* isr.asm — the timer IRQ stub */
timer_irq_stub:
    pusha
    push esp            ; pass current ESP to scheduler_tick
    call scheduler_tick ; returns new ESP
    mov esp, eax        ; switch stacks!
    popa
    iret                ; resume the new process
The Magic Line

mov esp, eax is the entire context switch. Before it, ESP points at the outgoing process's kernel stack. After it, ESP points at the incoming process's kernel stack — which has that process's saved registers waiting to be popped by popa and its saved EIP waiting for iret. One instruction, full CPU context switch.

ZOMBIE = process has exited but parent hasn't called wait() yet. The PCB is kept so the parent can read the exit code. DEAD = PCB can be recycled.

05 — Creating a Process

int process_create(void (*entry)(void)) {
    struct process *p = kmalloc(sizeof(*p));
    p->pid   = next_pid++;
    p->state = PROC_READY;
    p->stack = kmalloc(STACK_SIZE);  /* 8KB kernel stack */
    p->kernel_stack_top = (uint32_t)p->stack + STACK_SIZE;

    /* Build an initial interrupt frame on the new stack
       so scheduler_tick can "return" into the new process */
    uint32_t *sp = (uint32_t*)p->kernel_stack_top;
    *--sp = 0x00000202; /* EFLAGS: interrupts enabled */
    *--sp = 0x08;       /* CS: kernel code selector */
    *--sp = (uint32_t)entry; /* EIP: function to run */
    /* 8 zeros for pusha's registers */
    for (int i = 0; i < 8; i++) *--sp = 0;
    p->esp = (uint32_t)sp;

    /* add to ready list */
    enqueue(p);
    return 1;
}

07 — Brain Exercise

Sharpen Your Pencil

What happens if you forget the 8 zeros? What does popa pop instead — and what does iret try to use as EIP?

There Are No Dumb Questions

Q: Is this real multitasking or fake?
It's real preemptive multitasking — the timer genuinely interrupts processes without their cooperation. What makes it "simple" is that it's cooperative within a tick (no priorities, no sleep/wake), all processes share kernel address space (until Module 15), and there's only one CPU core. But the mechanism is identical to what Linux does on a single core.
Q: What's the difference between a process and a thread at this point?
At this stage, all "processes" share the same page directory (same address space). They're really threads by modern terminology. True process isolation — separate page directories — comes in Module 15. Actual threads sharing an address space come in Module 24.
