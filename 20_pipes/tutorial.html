Pipes & IPC

Two processes. One kernel ring buffer connecting them. The writer drops bytes in one end; the reader picks them up from the other. Shell pipelines — ls | grep — are built on exactly this mechanism.

01 — The Big Analogy

Head First Moment

Imagine two people on opposite ends of a pneumatic tube system (like old department stores used for cash). Person A shoves documents in one end (write); person B pulls them out the other (read). The tube is the kernel pipe buffer. If B is fast and the tube is empty, B waits. If A is slow and the tube is full, A waits. Neither person knows or cares what the other looks like — they just use the tube.

That's IPC via pipes: anonymous, kernel-mediated, first-in-first-out byte streams between processes.

02 — The Pipe Buffer

/* pipe.h */
struct pipe_buf {
    char     data[4096];
    uint32_t head;        /* next write position */
    uint32_t tail;        /* next read position */
    uint32_t count;       /* bytes currently in buffer */
    int      read_open;   /* 1 = read end still open */
    int      write_open;  /* 1 = write end still open */
};

#define MAX_PIPES 16
static struct pipe_buf pipes[MAX_PIPES];

/* VFS backends */
struct vfs_ops pipe_read_ops  = { NULL, pipe_read,  NULL,       pipe_close_read  };
struct vfs_ops pipe_write_ops = { NULL, NULL,        pipe_write, pipe_close_write };

03 — Read, Write, Block

/* pipe.c */
int pipe_read(int pipe_id, char *buf, int n, int offset) {
    struct pipe_buf *pb = &pipes[pipe_id];
    /* if empty AND write end closed → EOF (return 0) */
    if (pb->count == 0 && !pb->write_open) return 0;
    /* if empty but writer still open → block */
    while (pb->count == 0) {
        current->state = PROC_WAITING;
        scheduler_yield_current();  /* give up CPU */
    }
    /* drain up to n bytes from ring */
    int r = 0;
    while (r < n && pb->count > 0) {
        buf[r++] = pb->data[pb->tail++ % 4096];
        pb->count--;
    }
    return r;
}

int pipe_write(int pipe_id, const char *buf, int n, int offset) {
    struct pipe_buf *pb = &pipes[pipe_id];
    if (!pb->read_open) return -1; /* broken pipe */
    /* block if full */
    while (pb->count + n > 4096) {
        current->state = PROC_WAITING;
        scheduler_yield_current();
    }
    /* fill ring */
    for (int i = 0; i < n; i++) {
        pb->data[pb->head++ % 4096] = buf[i];
        pb->count++;
    }
    /* wake any blocked reader */
    wake_waiters_on_pipe(pipe_id);
    return n;
}
Waking the Reader

After writing, pipe_write scans all PROC_WAITING processes to see if any are blocked on this pipe's read end, and sets them back to PROC_READY. This is a simple O(n) scan — production kernels use a wait queue per pipe to avoid scanning all processes. For our single-pipe-at-a-time demos, the scan is fine.

04 — SYS_PIPE and the Fork Pattern

/* The classic Unix pipe+fork pattern */
int fds[2];
sys_pipe(fds);   /* fds[0]=read end, fds[1]=write end */

int child = sys_fork();
if (child == 0) {
    /* child is the WRITER */
    sys_close(fds[0]);            /* close unused read end */
    sys_write(fds[1], "hello", 5);
    sys_close(fds[1]);
    sys_exit(0);
} else {
    /* parent is the READER */
    sys_close(fds[1]);            /* close unused write end */
    char buf[16];
    int n = sys_read(fds[0], buf, sizeof(buf));
    /* buf now contains "hello", n=5 */
    sys_close(fds[0]);
    sys_wait(NULL);
}
Why close the unused end?

If the reader keeps the write end open, write_open is never 0 — so the reader's EOF check (count == 0 && !write_open) never triggers. The reader blocks forever even after the writer exits. Always close the end you don't use. This is the most common pipe bug in Unix programming.

06 — Brain Exercise

Sharpen Your Pencil

Question: Our pipe buffer is 4096 bytes. What happens if the writer tries to write 5000 bytes in one call? Our implementation blocks until there's room — but it only unblocks when the entire N bytes fit.

A better implementation would write as many bytes as fit, return the count, and let the caller write the rest. How would you restructure pipe_write to do partial writes instead of full blocking? What does POSIX say about this?

There Are No Dumb Questions

Q: How do shell pipelines like "ls | grep foo" use this?
The shell calls pipe(), forks twice (one child for ls, one for grep). It closes/dups file descriptors so ls's stdout (fd 1) points to the pipe write end, and grep's stdin (fd 0) points to the pipe read end. Then it execs ls and grep. They both run concurrently — ls writes into the pipe while grep reads from it. Neither knows about the other.
Q: What's the connection to Module 23 (shared memory)?
Pipes copy data through the kernel buffer — zero-copy it's not. Shared memory (Module 23) maps the same physical pages into both processes so data doesn't need to be copied at all. Pipes are safe (the kernel controls access); shared memory is faster (no copy) but requires explicit synchronization. Different tools for different jobs.
