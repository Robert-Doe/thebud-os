VFS Layer

One interface to rule them all. Whether you're reading a file from disk, a pipe from another process, or a character from the terminal — the VFS makes it look identical: open → read → write → close. The backend is just a vtable.

01 — The Big Analogy

Head First Moment

Think of a universal TV remote. You don't care if the TV is a Samsung, LG, or Sony — you press "volume up" and it works. The remote is the VFS. The "volume up" button is read(fd, buf, n). The Samsung/LG/Sony driver is the backend (BobFS, pipe, terminal). Each backend implements the same four buttons differently, but your code only ever touches the remote.

This is classic object-oriented design in C: a struct of function pointers (vtable) that different backends fill in differently.

02 — The VFS Stack

User code
calls SYS_READ(fd, buf, n) — doesn't know what fd points to
↓
VFS / syscall
looks up fd in process fd_table → gets struct file_descriptor
↓
fd_table[fd].ops
calls ops->read(inode, buf, n, offset) via function pointer
↓
BobFS backend
reads sectors from disk, copies bytes into buf
Pipe backend
copies bytes from pipe ring buffer into buf
VGA/terminal
for writes: calls vga_putchar for each byte

03 — The Key Structs

/* vfs.h */
struct vfs_ops {
    int  (*open) (const char *path, int flags);
    int  (*read) (int inode, char *buf, int n, int offset);
    int  (*write)(int inode, const char *buf, int n, int offset);
    void (*close)(int inode);
};

struct file_descriptor {
    int          valid;    /* 1 = slot occupied */
    int          inode;    /* backend-specific handle */
    int          offset;   /* current read/write position */
    struct vfs_ops *ops;   /* pointer to the backend's vtable */
};

/* Each process gets a table of open file descriptors */
#define MAX_FDS 16
/* In struct process: */
struct file_descriptor fd_table[MAX_FDS];

/* Backend vtables — defined in their respective .c files */
extern struct vfs_ops bobfs_ops;
extern struct vfs_ops vga_ops;    /* stdout: write calls kprintf */
extern struct vfs_ops pipe_read_ops, pipe_write_ops; /* Module 20 */

04 — Opening stdin / stdout / stderr

/* process.c — when creating a new process */
void setup_standard_fds(struct process *p) {
    /* fd 0: stdin — terminal input (keyboard, stub for now) */
    p->fd_table[0].valid  = 1;
    p->fd_table[0].inode  = 0;
    p->fd_table[0].offset = 0;
    p->fd_table[0].ops    = &vga_ops;  /* or keyboard_ops */

    /* fd 1: stdout — VGA terminal */
    p->fd_table[1].valid  = 1;
    p->fd_table[1].inode  = 0;
    p->fd_table[1].offset = 0;
    p->fd_table[1].ops    = &vga_ops;

    /* fd 2: stderr — same as stdout */
    p->fd_table[2]        = p->fd_table[1];
}

/* SYS_OPEN: find a free fd slot, call ops->open */
int do_open(const char *path, int flags) {
    int fd = find_free_fd(current);
    if (fd < 0) return -1;
    /* determine which backend based on path prefix */
    struct vfs_ops *ops = vfs_resolve(path);
    int inode = ops->open(path, flags);
    if (inode < 0) return -1;
    current->fd_table[fd] = (struct file_descriptor){1, inode, 0, ops};
    return fd;
}

/* SYS_READ: look up fd, call its ops->read */
int do_read(int fd, char *buf, int n) {
    if (fd < 0 || fd >= MAX_FDS || !current->fd_table[fd].valid) return -1;
    struct file_descriptor *f = ¤t->fd_table[fd];
    int r = f->ops->read(f->inode, buf, n, f->offset);
    if (r > 0) f->offset += r;
    return r;
}
fork inherits file descriptors

When a process forks, the child's fd_table is copied from the parent's — the child inherits all open file descriptors with the same offsets. This is how shell pipelines work: the parent opens a pipe, forks, and both parent and child have the same pipe fds. The child then writes to the pipe; the parent reads from it.

06 — Brain Exercise

Sharpen Your Pencil

Question: The offset field in file_descriptor tracks the current read position. Two processes that both open the same file get separate fd_table entries — so they have independent offsets.

But after fork(), the fd_table is copied — so parent and child initially have the same offset for each fd. If the child reads 100 bytes from fd=3, does the parent's offset advance? How does Linux solve this with "open file description" objects shared between processes?

There Are No Dumb Questions

Q: Why not just use BobFS directly instead of a VFS layer?
Without VFS, every syscall would have an if (is_file) ... else if (is_pipe) ... else if (is_terminal) ... chain. Every new backend requires editing the syscall handler. With VFS, adding a new backend means implementing four functions and registering a vtable — zero changes to SYS_READ/SYS_WRITE. It's the Open/Closed Principle applied to OS design.
Q: What's an inode in our VFS vs a real filesystem?
In our VFS, "inode" is just an integer handle that means something to the backend — for BobFS it's the inode table index, for a pipe it's the pipe buffer index, for VGA it's meaningless (always 0). Real filesystems have full inode structures with permissions, timestamps, link counts, and block maps. We use the word loosely as "backend file handle."
