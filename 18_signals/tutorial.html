MODULE 18 — PHASE 3

Signals

The OS's pager system. A signal interrupts whatever a process is doing — delivers a notification asynchronously, redirects execution to a user-space handler, then returns to the original code as if nothing happened. Phase 3 complete.

send a signal to any process

uncatchable — always kills
SIGSEGV
catchable — recover from bad access

01 — The Big Analogy

Head First Moment

Imagine you're deep in thought working at your desk (process running). Your phone buzzes (signal arrives). You put a bookmark in your work (OS saves EIP), pick up the phone (run signal handler), finish the call (handler returns), and pick up exactly where you left off (resume original EIP). The interruption was transparent.

SIGKILL is the fire alarm — you don't finish your phone call, you don't save your work, you leave immediately. No handler, no choice. SIGSEGV is someone calling to say "you're about to fall off a cliff" — you can choose to run a recovery handler instead of dying.

/* process.h additions */
#define NSIG    32
#define SIG_DFL 0u   /* default action */
#define SIG_IGN 1u   /* ignore */

struct process {
    /* ... existing fields ... */
    uint32_t pending_signals;          /* bitmask: bit N = signal N pending */
    uint32_t signal_handlers[NSIG];    /* handler addr, SIG_DFL, or SIG_IGN */
};

03 — How Delivery Works

Signals are asynchronous — they can arrive at any time. But delivery is actually synchronous at one point: just before the scheduler hands the CPU back to a ring-3 process.

/* process.c — called from scheduler_tick after paging_switch */
static void deliver_user_signals(void) {
    struct interrupt_frame *f = (struct interrupt_frame*)current->esp;

    for (int sig = 1; sig < NSIG; sig++) {
        if (!(current->pending_signals & (1u << sig))) continue;
        current->pending_signals &= ~(1u << sig); /* clear pending bit */

        if (sig == SIGKILL) { process_exit_with_code(9); return; }

        uint32_t handler = current->signal_handlers[sig];
        if (handler == SIG_DFL || handler == SIG_IGN) {
            if (handler == SIG_DFL) process_exit_with_code(sig);
            continue;
        }

        /* Build cdecl call frame on user stack:
           [new_esp+0] = original EIP (acts as return address)
           [new_esp+4] = signo (first argument)           */
        uint32_t *user_esp = /* pointer to user_esp word in f */;
        *user_esp -= 8;
        uint32_t *frame = (uint32_t*)(*user_esp);
        frame[0] = f->eip;   /* return address = where we were interrupted */
        frame[1] = sig;      /* argument: signal number */
        f->eip   = handler;  /* redirect execution to handler */
    }
}
The cdecl Frame Trick

A cdecl function call expects [esp] = return_address and [esp+4] = first_arg on entry. By pushing those two words onto the user stack and setting EIP to the handler, we fake a normal function call. When the handler executes ret, it pops the original EIP and resumes right where the process was before the signal. Zero assembly required.

04 — SIGSEGV: Catching a Fault

/* process.c — replaces raw page-fault kill for ring-3 */
uint32_t process_fault_handler(uint32_t esp) {
    struct interrupt_frame *f = (struct interrupt_frame*)esp;
    uint32_t handler = current->signal_handlers[SIGSEGV];

    if (handler != SIG_DFL && handler != SIG_IGN) {
        /* Build signal frame — same trick as deliver_user_signals */
        /* Handler fires instead of killing the process */
        return esp; /* modified frame: EIP now points at handler */
    }
    /* No handler registered — kill the process */
    process_exit_with_code(11);
    return esp; /* unreachable */
}
SIGSEGV Handler Must Not Return

Returning from a SIGSEGV handler re-executes the faulting instruction — which faults again — infinite loop. The demo's handler always calls sys_exit(0) explicitly. Production signal handling uses sigreturn to restore a saved ucontext to a known-good state. We document this clearly in DECISIONS.md.

05 — The Three-Part Demo

/* user_prog.c — signal_demo.elf */
void user_main(void) {
    int pid = sys_getpid();

    /* Part A: SIGUSR1 delivered during yield */
    sys_signal(SIGUSR1, sigusr1_handler);
    sys_kill(pid, SIGUSR1);
    sys_yield();   /* handler fires here, then returns, then we continue */

    /* Part B: catch SIGSEGV from intentional fault */
    int child = sys_fork();
    if (child == 0) {
        sys_signal(SIGSEGV, sigsegv_handler); /* handler calls sys_exit(0) */
        __asm__ volatile("movl (1), %%eax" : : : "eax"); /* fault! */
        /* never reached */
    }
    sys_wait(NULL); /* parent waits for child (should exit 0) */

    /* Part C: plain fork/wait regression check */
    /* ... */
    sys_exit(0);
}

07 — Brain Exercise

Sharpen Your Pencil

Question: What happens if a signal handler itself causes a signal? For example: SIGUSR1 handler is running. Inside the handler, the code dereferences a null pointer, causing SIGSEGV.

Our implementation has no signal mask — no way to block signals during handler execution. What does deliver_user_signals do when it's called on the next tick while a handler is still running? Can you get nested signal frames on the user stack?

There Are No Dumb Questions

Q: How does kill(pid, SIGKILL) from another process work safely?
When process A calls kill(B_pid, SIGKILL), we're currently running in A's address space (A's CR3). B's PCB is a kernel structure — accessible from any CR3. We immediately zombify B and call paging_free_address_space(B->cr3). This is safe because we're using A's CR3, not B's. B's physical pages get freed, B's PCB moves to PROC_ZOMBIE, and A continues.
Q: Why use a bitmask instead of a queue for pending signals?
POSIX standard signals don't queue — sending SIGUSR1 ten times before delivery counts as one delivery. A bitmask models this exactly: OR-ing a bit that's already set is a no-op. The entire mask fits in one 32-bit register. Real-time signals (SIGRTMIN+) do queue, requiring a linked list per signal — we don't implement those.
