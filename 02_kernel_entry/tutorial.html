01 — The Big Analogy

Head First Moment

Think of Real Mode like waking up from a coma in 1978. You're conscious, but your surroundings are tiny — only 1MB of RAM, 16-bit registers, no protection from anything. Kernel Entry is the moment you take your medication, fully wake up, and step into the modern world. You flip a single bit in a special register called CR0, and suddenly you have 4GB of address space, memory protection, and everything a modern OS needs. That transition is what this module is about.

Before kernel_main() can run, three things must exist that don't exist yet: a stack (C needs one to call functions), a BSS segment zeroed out (C assumes global variables start as zero), and a 32-bit execution environment. kernel_entry.asm builds all three.

02 — The Protected Mode Switch

The switch from 16-bit to 32-bit happens in exactly three steps, in this order. Mess up the order and the CPU triple-faults (crashes so hard it resets).

1. Load the GDT
The CPU needs to know about memory segments before entering Protected Mode. A temporary GDT (Global Descriptor Table) is loaded with lgdt. Don't worry about the details yet — Module 4 builds the real one.
lgdt [gdt_descriptor]
2. Set the PE bit in CR0
CR0 is the "mode control" register. Bit 0 is the Protected Mode Enable (PE) bit. Set it and the CPU instantly switches modes.
mov eax, cr0  |  or eax, 1  |  mov cr0, eax
3. Far jump to flush the pipeline
The CPU has already fetched some 16-bit instructions into its pipeline. A far jump forces the CPU to discard them and start fetching 32-bit instructions. Without this, the CPU executes garbage.
jmp 0x08:protected_mode_start
4. Set up segment registers
In Protected Mode, segment registers hold selectors (indices into the GDT), not raw addresses. All data segments get selector 0x10.
mov ax, 0x10  |  mov ds, ax  |  mov es, ax  |  mov ss, ax
5. Set up the stack and call kernel_main
ESP is pointed at the top of a 16KB block of RAM. Then BSS is zeroed. Then call kernel_main. If kernel_main ever returns (it shouldn't), we halt forever.
mov esp, stack_top  |  call kernel_main  |  hlt
What Is a Triple Fault?

If the CPU gets an exception while handling an exception while handling an exception, it gives up entirely and resets. In QEMU you'll see it as the window going blank and "rebooting." The most common cause: forgetting the far jump after setting PE=1, or having a corrupt GDT descriptor. Always check CR0 and GDT first when debugging a blank-screen crash.

03 — Real Mode vs Protected Mode Side-by-Side

Real Mode (where we started)

  • 16-bit registers (AX, BX…)
  • Max 1 MB addressable RAM
  • Segment:Offset addressing
  • No privilege levels (ring 0–3)
  • No memory protection at all
  • BIOS calls via int instructions
  • x86 from 1978 compatibility

Protected Mode (where we go)

  • 32-bit registers (EAX, EBX…)
  • Up to 4 GB addressable RAM
  • Segment selectors → GDT descriptors
  • Ring 0 (kernel) vs Ring 3 (user)
  • MMU enforces access rights per page
  • No BIOS — we write our own drivers
  • Everything we build from here

04 — The C Environment Bootstrap

C looks simple but it secretly requires a lot of setup before main() can run. Here's what kernel_entry.asm does before calling kernel_main:

Zero the BSS segment

; BSS = Block Started by Symbol = uninitialized global variables
; The C standard says they start at zero. The linker doesn't zero them.
; We do it ourselves.
xor eax, eax          ; value to write: 0
mov edi, bss_start    ; start of BSS (from linker script)
mov ecx, bss_end
sub ecx, edi          ; length in bytes
rep stosd             ; write EAX (0) into [EDI] ecx/4 times
Why Does This Matter?

If you forget to zero BSS, global variables have random values — whatever bytes happened to be in RAM. This causes incredibly hard-to-debug bugs where a global counter "starts at 37" or a pointer "starts as non-null." Zero BSS once at boot and you never think about it again.

The linker script sets the memory layout

/* linker.ld */
OUTPUT_FORMAT(binary)    /* flat binary, no ELF headers */
ENTRY(kernel_entry)

SECTIONS {
    . = 0x1000;          /* kernel loads at 0x1000 */
    .text   : { *(.text) }
    .rodata : { *(.rodata) }
    .data   : { *(.data) }
    bss_start = .;
    .bss    : { *(.bss) ALIGN(4) }
    bss_end = .;
    kernel_end = .;      /* exported symbol: where kernel ends in RAM */
}
The kernel_end Symbol

Notice kernel_end — future modules use this to know where free RAM starts. The PMM (Module 6) calls &kernel_end to find the first safe page to hand out. The linker fills in this address automatically.

Common Issue: WSL can't find the files

The Makefile uses wsl -d Ubuntu -- to run GCC. The path it passes is the Windows path converted to a WSL mount path (e.g. /mnt/c/Users/...). If you get "No such file or directory" from GCC, verify WSL 2 is the default: run wsl --set-default-version 2 in PowerShell, then wsl --set-default Ubuntu.

07 — Brain Exercise

Sharpen Your Pencil

Question: What happens if you forget to do the far jump (jmp 0x08:protected_mode_start) immediately after setting PE=1 in CR0?

Hint: the CPU has already fetched several instructions ahead of the one that set PE=1. Those pre-fetched instructions are 16-bit encoded. What does the CPU do when it tries to decode 16-bit instructions in 32-bit mode?

There Are No Dumb Questions

Q: Why can't we just stay in Real Mode? It was working fine.
Real Mode gives you a max of 1 MB of RAM and zero protection between programs. You can't have multiple processes (they'd overwrite each other), you can't have user/kernel separation, and you can't use more than 640KB for anything useful. Everything from Module 4 onward requires Protected Mode.
Q: What's a "selector" vs a raw address?
In Protected Mode, segment registers (CS, DS, SS…) don't hold raw addresses anymore. They hold an index (the "selector") into the GDT table — e.g. 0x08 means "entry 1 in the GDT." The CPU looks up that entry to find base address, limit, and permissions. Module 4 builds the full GDT.
Q: What if kernel_main() returns?
The code after call kernel_main is an infinite hlt loop. hlt stops the CPU until the next interrupt. This is fine — it just means the OS died gracefully instead of executing random bytes after kernel_main's stack frame.
